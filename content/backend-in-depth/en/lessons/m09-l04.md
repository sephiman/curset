## Distributed rate limiter
<!-- bullets: 9.4.a -->

Local per-process counters break behind load balancers: the same client bypasses limits by hitting different instances (`redis-rate-limiter#why-the-problem-is-hard`).

The rate limiter needs a centralized store fast enough to sit on the request path without adding meaningful latency (`redis-rate-limiter#why-the-problem-is-hard`).

Counters live behind keys scoped to the dimension you are limiting on (user, IP, API key, tenant, model) (`redis-rate-limiter#how-redis-supports-the-solution`).

`INCR` and `EXPIRE` give you atomic fixed-window counters with automatic time-window cleanup (`redis-rate-limiter#how-redis-supports-the-solution`).

Hashes, sorted sets, and strings cover the data shapes needed for sliding window and token bucket algorithms (`redis-rate-limiter#how-redis-supports-the-solution`).

Hash field expiration in Redis 8 (`HEXPIRE`) further simplifies time-bound rate limiting at the field level (`redis-rate-limiter#how-redis-supports-the-solution`).

Lua scripting with `EVAL` keeps the read-decide-update cycle atomic, so concurrent requests cannot double-spend tokens or lose counter updates (`redis-rate-limiter#how-redis-supports-the-solution`).

Resilience4j provides a `RateLimiter` which splits all nanoseconds from the start of epoch into cycles (`resilience4j-ratelimiter#internals`).

Each cycle has a duration configured by `RateLimiterConfig.limitRefreshPeriod` (`resilience4j-ratelimiter#internals`).

At the start of each cycle, the `RateLimiter` sets the number of active permissions to `RateLimiterConfig.limitForPeriod` (`resilience4j-ratelimiter#internals`).

The default implementation of `RateLimiter` is `AtomicRateLimiter` which manages its state via `AtomicReference` (`resilience4j-ratelimiter#internals`).

The `AtomicRateLimiter.State` is completely immutable (`resilience4j-ratelimiter#internals`).

The state field `activeCycle` is the cycle number that was used by the last call (`resilience4j-ratelimiter#internals`).

The state field `activePermissions` is the count of available permissions after the last call and can be negative if some permissions were reserved (`resilience4j-ratelimiter#internals`).

The state field `nanosToWait` is the count of nanoseconds to wait for permission for the last call (`resilience4j-ratelimiter#internals`).

There is also a `SemaphoreBasedRateLimiter` which uses Semaphores and a scheduler that will refresh permissions after each `RateLimiterConfig#limitRefreshPeriod` (`resilience4j-ratelimiter#internals`).

The `RateLimit-Policy` and `RateLimit` HTTP header fields are for servers to advertise their quota policies and the current service limits, thereby allowing clients to avoid being throttled (`ietf-httpapi-ratelimit-headers#content`).

The `RateLimit` header fields are specified in `draft-ietf-httpapi-ratelimit-headers`, an active Internet-Draft of the httpapi working group (`ietf-httpapi-ratelimit-headers#content`).

The value of the `RateLimit-Policy` field SHOULD remain consistent over a sequence of HTTP responses, which differentiates it from the `RateLimit` field that contains information that MAY change on every request (`ietf-httpapi-ratelimit-headers#content`).

The REQUIRED `q` parameter of a quota policy item indicates the quota allocated by the policy measured in quota units (`ietf-httpapi-ratelimit-headers#content`).

The OPTIONAL `w` parameter of a quota policy item conveys a time window (`ietf-httpapi-ratelimit-headers#content`).

The default quota unit is `requests` (`ietf-httpapi-ratelimit-headers#content`).

The draft defines three quota units: `requests`, `content-bytes` and `concurrent-requests` (`ietf-httpapi-ratelimit-headers#content`).

The time window MUST be a non-negative, non-zero, Integer value expressing an interval in seconds (`ietf-httpapi-ratelimit-headers#content`).

Sub-second precision is not supported (`ietf-httpapi-ratelimit-headers#content`).

Using delay-seconds aligns with `Retry-After`, which is returned in similar contexts, e.g. on 429 responses (`ietf-httpapi-ratelimit-headers#content`).

If a response contains both the `RateLimit` and `Retry-After` fields, the `Retry-After` field MUST take precedence and the effective window MAY be ignored (`ietf-httpapi-ratelimit-headers#content`).

The draft does not mandate a specific throttling algorithm (`ietf-httpapi-ratelimit-headers#content`).

Network bandwidth quotas define byte-rate thresholds (`kafka-design#quotas`).

Request rate quotas define CPU utilization thresholds as a percentage of network and I/O threads (`kafka-design#quotas`).

:::judgement{source="Google, Site Reliability Engineering, chapter 21 (Handling Overload)" ref="sre-book-handling-overload#client-side-throttling-a7sYUg"}
According to Google's Site Reliability Engineering book, a backend task that rejects out-of-quota requests still spends resources on them. If the amount of rejected requests is significant, the backend can become overloaded even though the vast majority of its CPU is spent just rejecting requests.

The book describes client-side throttling as the answer. When a client detects that a significant portion of its recent requests have been rejected due to "out of quota" errors, it starts self-regulating and caps the amount of outgoing traffic it generates. Requests above the cap fail locally without even reaching the network.

In the book's adaptive throttling, each client task keeps `requests` and `accepts` for the last two minutes of its history. Clients can continue to issue requests to the backend until `requests` is K times as large as `accepts`.
:::

## Booking and inventory engine under high contention
<!-- bullets: 9.4.b -->

`FOR UPDATE` causes the rows retrieved by the `SELECT` statement to be locked as though for update (`pg-explicit-locking#LOCKING-ROWS`).

A `FOR UPDATE` lock prevents the rows from being locked, modified or deleted by other transactions until the current transaction ends (`pg-explicit-locking#LOCKING-ROWS`).

Row-level locks do not affect data querying; they block only writers and lockers to the same row (`pg-explicit-locking#LOCKING-ROWS`).

Row-level locks are released at transaction end or during savepoint rollback, just like table-level locks (`pg-explicit-locking#LOCKING-ROWS`).

Within a `REPEATABLE READ` or `SERIALIZABLE` transaction, however, an error will be thrown if a row to be locked has changed since the transaction started (`pg-explicit-locking#LOCKING-ROWS`).

`FOR SHARE` behaves similarly to `FOR NO KEY UPDATE`, except that it acquires a shared lock rather than exclusive lock on each retrieved row (`pg-explicit-locking#LOCKING-ROWS`).

`FOR KEY SHARE` behaves similarly to `FOR SHARE`, except that the lock is weaker: `SELECT FOR UPDATE` is blocked, but not `SELECT FOR NO KEY UPDATE` (`pg-explicit-locking#LOCKING-ROWS`).

A shared lock blocks other transactions from performing `UPDATE`, `DELETE`, `SELECT FOR UPDATE` or `SELECT FOR NO KEY UPDATE` on these rows (`pg-explicit-locking#LOCKING-ROWS`).

Locking a row might cause a disk write, e.g., `SELECT FOR UPDATE` modifies selected rows to mark them locked, and so will result in disk writes (`pg-explicit-locking#LOCKING-ROWS`).

With `NOWAIT`, the statement reports an error, rather than waiting, if a selected row cannot be locked immediately (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

With `SKIP LOCKED`, any selected rows that cannot be immediately locked are skipped (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

`NOWAIT` and `SKIP LOCKED` apply only to the row-level lock(s) — the required `ROW SHARE` table-level lock is still taken in the ordinary way (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

If a `LIMIT` is used, locking stops once enough rows have been returned to satisfy the limit (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

Rows skipped over by `OFFSET` will get locked (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

The locking clauses cannot be used in contexts where returned rows cannot be clearly identified with individual table rows; for example they cannot be used with aggregation (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

Applications using `SERIALIZABLE` must be prepared to retry transactions due to serialization failures (`pg-transaction-iso#XACT-SERIALIZABLE`).

The monitoring done by `SERIALIZABLE` does not introduce any blocking beyond that present in repeatable read (`pg-transaction-iso#XACT-SERIALIZABLE`).

Applications must not depend on results read during a transaction that later aborted; instead, they should retry the transaction until it succeeds (`pg-transaction-iso#XACT-SERIALIZABLE`).

To guarantee true serializability PostgreSQL uses predicate locking (`pg-transaction-iso#XACT-SERIALIZABLE`).

In PostgreSQL, predicate locks do not cause any blocking and therefore can not play any part in causing a deadlock (`pg-transaction-iso#XACT-SERIALIZABLE`).

A `READ COMMITTED` or `REPEATABLE READ` transaction which wants to ensure data consistency may need to take out a lock on an entire table (`pg-transaction-iso#XACT-SERIALIZABLE`).

The safety property of the Redis distributed lock design is mutual exclusion: at any given moment, only one client can hold a lock (`redis-distributed-locks#safety-and-liveness-guarantees`).

Liveness property A of the design is deadlock freedom: eventually it is always possible to acquire a lock, even if the client that locked a resource crashes or gets partitioned (`redis-distributed-locks#safety-and-liveness-guarantees`).

Liveness property B of the design is fault tolerance: as long as the majority of Redis nodes are up, clients are able to acquire and release locks (`redis-distributed-locks#safety-and-liveness-guarantees`).

Per RFC 9110, the methods `OPTIONS`, `HEAD`, `GET`, `PUT` and `DELETE` are idempotent while methods `POST` and `PATCH` are not (`ietf-httpapi-idempotency-key#content`).

The HTTP `Idempotency-Key` request header field can be used to make non-idempotent HTTP methods such as `POST` or `PATCH` fault-tolerant (`ietf-httpapi-idempotency-key#content`).

The idempotency key MUST be unique and MUST NOT be reused with another request with a different request payload (`ietf-httpapi-idempotency-key#content`).

It is RECOMMENDED that a UUID [RFC9562] or a similar random identifier be used as an idempotency key (`ietf-httpapi-idempotency-key#content`).

An idempotency fingerprint MAY be used in conjunction with an idempotency key to determine the uniqueness of a request (`ietf-httpapi-idempotency-key#content`).

If the `Idempotency-Key` request header is missing for a documented idempotent operation requiring this header, the resource SHOULD reply with an HTTP 400 status code (`ietf-httpapi-idempotency-key#content`).

If there is an attempt to reuse an idempotency key with a different request payload, the resource SHOULD reply with an HTTP 422 status code (`ietf-httpapi-idempotency-key#content`).

If the request is retried, while the original request is still being processed, the resource SHOULD reply with an HTTP 409 status code (`ietf-httpapi-idempotency-key#content`).

## Multi-channel notification platform
<!-- bullets: 9.4.c -->

At most once means messages may be lost but are never redelivered (`kafka-design#message-delivery-semantics`).

At least once means messages are never lost but may be redelivered (`kafka-design#message-delivery-semantics`).

Exactly once means each message is processed once and only once (`kafka-design#message-delivery-semantics`).

A message is considered committed only when all replicas in the in-sync replicas (ISR) for that partition have applied it to their log (`kafka-design#message-delivery-semantics`).

If a producer attempts to publish a message and experiences a network error, it cannot be sure if this error happened before or after the message was committed (`kafka-design#message-delivery-semantics`).

Since 0.11.0.0, the Kafka producer also supports an idempotent delivery option which guarantees that resending will not result in duplicate entries in the log (`kafka-design#message-delivery-semantics`).

To achieve this, the broker assigns each producer an ID and deduplicates messages using a sequence number that is sent by the producer along with every message (`kafka-design#message-delivery-semantics`).

Also beginning with 0.11.0.0, the producer supports the ability to send messages atomically to multiple topic partitions using transactions, so that either all messages are successfully written or none of them are (`kafka-design#message-delivery-semantics`).

A consumer that reads the messages, then saves its position in the log, and finally processes the messages gets at-most-once semantics, because on a consumer failure messages may not be processed (`kafka-design#message-delivery-semantics`).

After a crash between saving the position and processing, the process that took over would start at the saved position even though a few messages prior to that position had not been processed (`kafka-design#message-delivery-semantics`).

A consumer that reads the messages, processes the messages, and finally saves its position gets at-least-once semantics in the case of consumer failure (`kafka-design#message-delivery-semantics`).

In the default `read_uncommitted` isolation level, all messages are visible to consumers even if they were part of an aborted transaction, but in `read_committed` isolation level, the consumer will only return messages from transactions which were committed (and any messages which were not part of a transaction) (`kafka-design#message-delivery-semantics`).

Kafka supports exactly-once delivery in Kafka Streams (`kafka-design#message-delivery-semantics`).

Exactly-once delivery for other destination systems generally requires cooperation with such systems (`kafka-design#message-delivery-semantics`).

Kafka guarantees at-least-once delivery by default, and allows the user to implement at-most-once delivery by disabling retries on the producer and committing offsets in the consumer prior to processing a batch of messages (`kafka-design#message-delivery-semantics`).

Messages from a queue can be "dead-lettered", which means these messages are republished to an exchange when any of four events occur (`rabbitmq-dlx#overview`).

A message is dead-lettered when it is negatively acknowledged by an AMQP 0.9.1 consumer using `basic.reject` or `basic.nack` with the `requeue` parameter set to false (`rabbitmq-dlx#overview`).

A message is dead-lettered when it expires due to per-message TTL (`rabbitmq-dlx#overview`).

A message is dead-lettered when it is dropped because its queue exceeded a length limit (`rabbitmq-dlx#overview`).

A message is dead-lettered when it is returned more times to a quorum queue than the delivery-limit (`rabbitmq-dlx#overview`).

If an entire queue expires, the messages in the queue are not dead-lettered (`rabbitmq-dlx#overview`).

Dead letter exchanges (DLXs) are normal exchanges (`rabbitmq-dlx#overview`).

When RabbitMQ delivers a message to a consumer, it needs to know when to consider the message to be successfully sent (`rabbitmq-confirms#consumer-acknowledgements`).

The kind of acknowledgement logic that is optimal depends on the system, so it is primarily an application decision (`rabbitmq-confirms#consumer-acknowledgements`).

Achieving non-blocking retry / dlt functionality with Kafka usually requires setting up extra topics and creating and configuring the corresponding listeners (`spring-kafka-retrytopic#page-title`).

Since 2.7 Spring for Apache Kafka offers support for non-blocking retry and dead-letter functionality via the `@RetryableTopic` annotation and `RetryTopicConfiguration` class (`spring-kafka-retrytopic#page-title`).

Since 3.2, Spring for Apache Kafka supports non-blocking retries with `@KafkaListener` on a Class (`spring-kafka-retrytopic#page-title`).

Non-blocking retries are not supported with Batch Listeners (`spring-kafka-retrytopic#page-title`).

Non-Blocking Retries cannot combine with Container Transactions (`spring-kafka-retrytopic#page-title`).

A properly designed disk structure can often be as fast as the network (`kafka-design#dont-fear-the-filesystem`).

Linear writes on a JBOD configuration with six 7200rpm SATA RAID-5 array run at about 600MB/sec, but random writes only at about 100kB/sec, a difference of over 6000X (`kafka-design#dont-fear-the-filesystem`).

All data is immediately written to a persistent log on the filesystem without necessarily flushing to disk (`kafka-design#dont-fear-the-filesystem`).

Java garbage collection becomes increasingly fiddly and slow as the in-heap data increases (`kafka-design#dont-fear-the-filesystem`).

The pagecache stays warm even if the service is restarted, whereas an in-process cache will need to be rebuilt in memory (`kafka-design#dont-fear-the-filesystem`).

Once poor disk access patterns have been eliminated, there are two common causes of inefficiency in this type of system: too many small I/O operations, and excessive byte copying (`kafka-design#efficiency`).

The Kafka protocol is built around a “message set” abstraction that naturally groups messages together (`kafka-design#efficiency`).

Batching leads to larger network packets, larger sequential disk operations and contiguous memory blocks, all of which allows Kafka to turn a bursty stream of random message writes into linear writes that flow to the consumers (`kafka-design#efficiency`).

The common data path for transfer of data from file to socket has four copies and two system calls (`kafka-design#efficiency`).

Using `sendfile`, the OS sends the data from pagecache to the network directly, so only the final copy to the NIC buffer is needed (`kafka-design#efficiency`).

On a Kafka cluster where the consumers are mostly caught up you will see no read activity on the disks whatsoever, as they will be serving data entirely from cache (`kafka-design#efficiency`).

`sendfile` is not used when SSL is enabled (`kafka-design#efficiency`).

In some cases the bottleneck is actually not CPU or disk but network bandwidth (`kafka-design#end-to-end-batch-compression`).

Efficient compression requires compressing multiple messages together rather than compressing each message individually (`kafka-design#end-to-end-batch-compression`).

The broker decompresses the batch in order to validate it (`kafka-design#end-to-end-batch-compression`).

The batch of messages is written to disk in compressed form (`kafka-design#end-to-end-batch-compression`).

The batch will remain compressed in the log and it will also be transmitted to the consumer in compressed form (`kafka-design#end-to-end-batch-compression`).

Kafka supports GZIP, Snappy, LZ4 and ZStandard compression protocols (`kafka-design#end-to-end-batch-compression`).

Alignment happens only for operators with multiple predecessors (joins) as well as operators with multiple senders (after a stream repartitioning/shuffle) (`flink-stateful-stream-processing#exactly-once-vs-at-least-once`).

Dataflows with only embarrassingly parallel streaming operations (`map()`, `flatMap()`, `filter()`, …) actually give exactly once guarantees even in at least once mode (`flink-stateful-stream-processing#exactly-once-vs-at-least-once`).

For applications that require consistently super low latencies (few milliseconds) for all records, Flink has a switch to skip the stream alignment during a checkpoint (`flink-stateful-stream-processing#exactly-once-vs-at-least-once`).

Metrics consist of data point–timestamp pairs, identified by dimension fields, that can be used in aggregation queries (`es-time-series-data-stream#when-to-use-tsds`).

Choose a time series data stream if you typically add metrics data to Elasticsearch in near real-time and in `@timestamp` order (`es-time-series-data-stream#when-to-use-tsds`).

For other timestamped data, such as logs or traces, use a logs data stream or a regular data stream (`es-time-series-data-stream#when-to-use-tsds`).

## URL shortener and distributed ID generation
<!-- bullets: 9.4.e -->

UUIDs can be used to create unique, reasonably short values in distributed systems without requiring coordination (`rfc9562#section-2.1`).

Schemes such as "auto-increment" do not work well in distributed applications: the effort required to coordinate sequential numeric identifiers across a network can easily become a burden (`rfc9562#section-2.1`).

UUID versions that are not time ordered, such as UUIDv4, have poor database-index locality (`rfc9562#section-2.1`).

New values created in succession are not close to each other in the index, so they require inserts to be performed at random locations (`rfc9562#section-2.1`).

The 100-nanosecond Gregorian Epoch used in UUIDv1 timestamps is uncommon and difficult to represent accurately using a standard number format (`rfc9562#section-2.1`).

Exposed MAC addresses in the node field of UUIDv1 can be used as an attack surface to locate network interfaces (`rfc9562#section-2.1`).

UUIDv7 features a time-ordered value field derived from the widely implemented and well-known Unix Epoch timestamp source, the number of milliseconds since midnight 1 Jan 1970 UTC, leap seconds excluded (`rfc9562#section-5.7`).

UUIDv7 values are created by allocating a Unix timestamp in milliseconds in the most significant 48 bits and filling the remaining 74 bits, excluding the required version and variant bits, with random bits for each new UUIDv7 generated to provide uniqueness (`rfc9562#section-5.7`).

Implementations MAY fill the 74 bits, jointly, with a combination of subfields to guarantee additional monotonicity within a millisecond (`rfc9562#section-5.7`).

Implementations SHOULD utilize UUIDv7 instead of UUIDv1 and UUIDv6 if possible (`rfc9562#section-5.7`).

UUIDv1 and UUIDv6 both utilize a Gregorian Epoch timestamp, while UUIDv7 utilizes a Unix Epoch timestamp (`rfc9562#section-6.1`).

If other timestamp sources or a custom timestamp Epoch are required, UUIDv8 MUST be used (`rfc9562#section-6.1`).

UUIDv7 features a millisecond level of precision by default within the Unix Epoch (`rfc9562#section-6.1`).

UUIDv7 features a 48-bit timestamp valid until the year 10889 AD (`rfc9562#section-6.1`).

If a system overruns the generator by requesting too many UUIDs within a single system-time interval, the UUID service can return an error or stall the UUID generator until the system clock catches up and MUST NOT knowingly return duplicate values due to a counter rollover (`rfc9562#section-6.1`).

The key space of a Redis Cluster is split into 16384 slots (`redis-cluster-spec#key-distribution-model`).

The base algorithm used to map keys to hash slots is `HASH_SLOT = CRC16(key) mod 16384` (`redis-cluster-spec#key-distribution-model`).

14 out of 16 CRC16 output bits are used, which is why there is a modulo 16384 operation in the formula (`redis-cluster-spec#key-distribution-model`).

When the cluster is stable, a single hash slot will be served by a single node (`redis-cluster-spec#key-distribution-model`).

## Search and autocomplete
<!-- bullets: 9.4.f -->

The `search_as_you_type` field type is a text-like field that is optimized to provide out-of-the-box support for queries that serve an as-you-type completion use case (`es-search-as-you-type#elastic-docs-v3`).

A `search_as_you_type` field supports both prefix completion and infix completion (`es-search-as-you-type#elastic-docs-v3`).

`my_field._index_prefix` wraps the analyzer of `my_field._3gram` with an edge ngram token filter (`es-search-as-you-type#elastic-docs-v3`).

The size of shingles in subfields can be configured with the `max_shingle_size` mapping parameter; the default is 3, and valid values are integer values 2 - 4 inclusive (`es-search-as-you-type#elastic-docs-v3`).

Increasing `max_shingle_size` will improve matches for queries with more consecutive terms, at the cost of larger index size (`es-search-as-you-type#elastic-docs-v3`).

The most efficient way of querying to serve a search-as-you-type use case is usually a `multi_match` query of type `bool_prefix` that targets the root `search_as_you_type` field and its shingle subfields (`es-search-as-you-type#elastic-docs-v3`).

A `bool_prefix` query can match the query terms in any order, but will score documents higher if they contain the terms in order in a shingle subfield (`es-search-as-you-type#elastic-docs-v3`).

To search for documents that strictly match the query terms in order, use a `match_phrase_prefix` query on the root field (`es-search-as-you-type#elastic-docs-v3`).

Using phrase queries may be less efficient than using the `match_bool_prefix` query (`es-search-as-you-type#elastic-docs-v3`).

To use the completion suggester, map the field from which you want to generate suggestions as type `completion` (`es-completion-mapping#elastic-docs-v3`).

Mapping a field as `completion` indexes the field values for fast completions (`es-completion-mapping#elastic-docs-v3`).

The `suggest` parameter of the search API suggests similar looking terms based on a provided text by using a suggester (`es-search-suggesters#elastic-docs-v3`).

The term suggester's score is based on the edit distance (`es-search-suggesters#elastic-docs-v3`).

Using `suggest` across multiple indices with different analysis chains is not supported (`es-search-suggesters#elastic-docs-v3`).

An inverted index is a data structure that maps each token to the documents that contain it (`es-how-full-text-works#elastic-docs-v3`).

The dictionary of an inverted index is a sorted list of all unique terms in the collection of documents in the index (`es-how-full-text-works#elastic-docs-v3`).

The posting list of an inverted index holds, for each term, a list of document IDs where the term appears, along with optional metadata like term frequency and position (`es-how-full-text-works#elastic-docs-v3`).

Query text is analyzed the same way as the indexed text, and the resulting tokens are used to search the inverted index (`es-how-full-text-works#elastic-docs-v3`).

The default similarity algorithm Elasticsearch uses for calculating relevance scores is Okapi BM25, a variation of the TF-IDF algorithm (`es-how-full-text-works#elastic-docs-v3`).

BM25 calculates relevance scores based on term frequency, document frequency, and document length (`es-how-full-text-works#elastic-docs-v3`).

In the BM25 similarity, `k1` controls non-linear term frequency normalization (saturation), and its default value is 1.2 (`es-similarity#bm25`).

In the BM25 similarity, `b` controls to what degree document length normalizes tf values, and its default value is 0.75 (`es-similarity#bm25`).

You can use the `search_after` parameter to retrieve the next page of hits using a set of sort values from the previous page (`es-paginate-search-results#search-after`).

Using `search_after` requires multiple search requests with the same query and sort values (`es-paginate-search-results#search-after`).

If a refresh occurs between these requests, the order of your results may change, causing inconsistent results across pages (`es-paginate-search-results#search-after`).

To prevent inconsistent results across pages, you can create a point in time (PIT) to preserve the current index state over your searches (`es-paginate-search-results#search-after`).

All PIT search requests add an implicit sort tiebreaker field called `_shard_doc`, which can also be provided explicitly (`es-paginate-search-results#search-after`).

If you cannot use a PIT, we recommend that you include a tiebreaker field in your sort (`es-paginate-search-results#search-after`).

If you don’t include a tiebreaker field, your paged results could miss or duplicate hits (`es-paginate-search-results#search-after`).

Elasticsearch no longer recommends the scroll API for deep pagination (`es-paginate-search-results#scroll-search-results`).

## Agentic diagnostics platform and enterprise AI gateway
<!-- bullets: 9.4.g -->

The Model Context Protocol (MCP) allows servers to expose tools that can be invoked by language models (`mcp-tools#page-title`).

Each MCP tool is uniquely identified by a name and includes metadata describing its schema (`mcp-tools#page-title`).

Every MCP request MUST include the required `_meta` fields (`mcp-tools#page-title`).

To invoke a tool, clients send a `tools/call` request (`mcp-tools#calling-tools`).

An MCP proxy server is an MCP server that connects MCP clients to third-party APIs, offering MCP features while delegating operations and acting as a single OAuth client to the third-party API server (`mcp-security-best-practices#terminology`).

A static client ID is a fixed OAuth 2.0 client identifier used by the MCP proxy server when communicating with the third-party authorization server (`mcp-security-best-practices#terminology`).

The static client ID refers to the MCP server acting as a client to the third-party API, and it is the same value for all MCP server to third-party API interactions regardless of which MCP client initiated the request (`mcp-security-best-practices#terminology`).

A third-party authorization server may lack dynamic client registration support, requiring the MCP proxy to use a static client ID for all requests (`mcp-security-best-practices#terminology`).

Attackers can exploit MCP proxy servers that connect to third-party APIs, creating “confused deputy” vulnerabilities (`mcp-security-best-practices#confused-deputy-problem`).

The confused deputy attack allows malicious clients to obtain authorization codes without proper user consent by exploiting the combination of static client IDs, dynamic client registration, and consent cookies (`mcp-security-best-practices#confused-deputy-problem`).

A Prompt Injection Vulnerability occurs when user prompts alter the LLM’s behavior or output in unintended ways (`owasp-llm-top10-prompt-injection#main`).

Prompt injections do not need to be human-visible/readable, as long as the content is parsed by the model (`owasp-llm-top10-prompt-injection#main`).

Research shows that Retrieval Augmented Generation (RAG) and fine-tuning do not fully mitigate prompt injection vulnerabilities (`owasp-llm-top10-prompt-injection#main`).

Jailbreaking is a form of prompt injection where the attacker provides inputs that cause the model to disregard its safety protocols entirely (`owasp-llm-top10-prompt-injection#main`).

Effective prevention of jailbreaking requires ongoing updates to the model’s training and safety mechanisms (`owasp-llm-top10-prompt-injection#main`).

Prompt injection and jailbreaking are related concepts (`owasp-llm-top10-prompt-injection#main`).

Indirect prompt injections occur when an LLM accepts input from external sources, such as websites or files (`owasp-llm-top10-prompt-injection#indirect-prompt-injections`).

A successful prompt injection can lead to executing arbitrary commands in connected systems (`owasp-llm-top10-prompt-injection#indirect-prompt-injections`).

## Key points

- A per-process counter lets the same client bypass the limit behind a load balancer, so the counter lives in a centralized store.
- Redis provides `INCR` and `EXPIRE` for fixed windows, hashes, sorted sets and strings for sliding window and token bucket, and Lua `EVAL` for an atomic read-decide-update cycle.
- The default Resilience4j `RateLimiter` is `AtomicRateLimiter`, which keeps an immutable state in an `AtomicReference`.
- A `RateLimit` header advertises the quota currently available, and `Retry-After` takes precedence over it.
- `SELECT … FOR UPDATE` locks the rows it returns until the transaction ends, and plain reads of those rows are not blocked.
- `SKIP LOCKED` skips rows that cannot be locked immediately and suits queue-like tables, while `NOWAIT` reports an error instead of waiting.
- Applications that use `SERIALIZABLE` must be prepared to retry transactions that fail with a serialization failure.
- An idempotency key is unique and is not reused with a different payload; a reused key gets `422`, and a retry during processing gets `409`.
- Kafka guarantees at-least-once delivery by default; at-most-once needs retries disabled and offsets committed before processing.
- A consumer that saves its position before processing gets at-most-once semantics, and one that saves it after processing gets at-least-once.
- Kafka supports exactly-once delivery in Kafka Streams; other destination systems need their cooperation.
- RabbitMQ dead-letters a message on a negative acknowledgement without requeue, on per-message TTL expiry, on a queue length limit or on a quorum queue delivery-limit, and not when a whole queue expires.
- Spring for Apache Kafka non-blocking retries are not supported with batch listeners or container transactions.
- Kafka writes to a persistent log on the filesystem and relies on the pagecache, and a properly designed disk structure can often be as fast as the network.
- The Kafka protocol is built around a message set abstraction that groups messages together, which lets Kafka turn a bursty stream of random message writes into linear writes.
- `sendfile` removes copies on the path from pagecache to socket, and it is not used when SSL is enabled.
- Kafka compresses a batch of messages together, and the batch stays compressed in the log and on the way to the consumer.
- Elasticsearch recommends a time series data stream for metrics added in near real-time and in `@timestamp` order.
- UUIDs create unique, reasonably short values in distributed systems without requiring coordination, while auto-increment schemes need to coordinate across a network.
- UUIDv4 is not time ordered and has poor database-index locality.
- UUIDv7 puts a Unix timestamp in milliseconds in its most significant 48 bits and fills the rest with random bits.
- UUIDv8 MUST be used for other timestamp sources or a custom epoch.
- Redis Cluster maps a key to one of 16384 hash slots with `CRC16(key) mod 16384`.
- Elasticsearch builds an inverted index from analyzed tokens, analyzes the query text the same way, and scores with Okapi BM25 by default.
- The `search_as_you_type` field type creates shingle and edge ngram subfields, and a `multi_match` query of type `bool_prefix` is usually the most efficient way to query it.
- The completion suggester needs a field mapped as `completion`.
- `search_after` pages through results with the sort values of the last hit, and a tiebreaker field or a point in time keeps pages from missing or duplicating hits.
- MCP servers expose tools that language models invoke, and each tool is uniquely identified by a name and has a schema.
- A client invokes a tool by sending a `tools/call` request.
- An MCP proxy server can be exploited in a confused deputy attack through static client IDs, dynamic client registration and consent cookies.
- Prompt injections do not need to be human-visible, and RAG and fine-tuning do not fully mitigate them.

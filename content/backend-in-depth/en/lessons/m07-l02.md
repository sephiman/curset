# HTTP/1.1, HTTP/2 and HTTP/3

## What each version solves
<!-- bullets: 7.2.a -->

The performance of applications using HTTP is linked to how each version of HTTP uses the underlying transport, and the conditions under which the transport operates (`rfc9113#section-1`).

HTTP fields are often repetitive and verbose, which causes unnecessary network traffic and makes the initial TCP congestion window fill quickly (`rfc9113#section-1`).

HTTP/2 addresses these issues by defining an optimized mapping of HTTP's semantics to an underlying connection (`rfc9113#section-1`).

HTTP/2 allows interleaving of messages on the same connection and uses an efficient coding for HTTP fields (`rfc9113#section-1`).

HTTP/2 also allows prioritization of requests, letting more important requests complete more quickly (`rfc9113#section-1`).

HTTP/2 can use fewer TCP connections than HTTP/1.x, which means less competition with other flows and longer-lived connections (`rfc9113#section-1`).

HTTP/2 enables more efficient processing of messages through use of binary message framing (`rfc9113#section-1`).

:::esquema{kind=tabla title="What each HTTP version changes for concurrency"}
| Version | What the source says | Source |
|---|---|---|
| HTTP/1.0 | Allowed only one request to be outstanding at a time on a given TCP connection | `rfc9113#section-1` |
| HTTP/1.1 | Added request pipelining, which only partially addressed request concurrency and still suffers from application-layer head-of-line blocking | `rfc9113#section-1` |
| HTTP/2 | Allows interleaving of messages on the same connection; TCP head-of-line blocking is not addressed | `rfc9113#section-1` |
:::

## HTTP/1.1 persistent connections and pipelining
<!-- bullets: 7.2.a -->

HTTP/1.1 defaults to the use of persistent connections, allowing multiple requests and responses to be carried over a single connection (`rfc9112#section-9.3`).

If the close connection option is present, the connection will not persist after the current response (`rfc9112#section-9.3`).

A client that supports persistent connections may pipeline its requests, that is, send multiple requests without waiting for each response (`rfc9112#section-9.3.2`).

A server may process a sequence of pipelined requests in parallel if they all have safe methods, but it must send the corresponding responses in the same order that the requests were received (`rfc9112#section-9.3.2`).

Idempotent methods are significant to pipelining because they can be automatically retried after a connection failure (`rfc9112#section-9.3.2`).

A user agent should not pipeline requests after a non-idempotent method until the final response status code for that method has been received, unless it can detect and recover from partial failures (`rfc9112#section-9.3.2`).

## HTTP/2 streams, multiplexing and flow control
<!-- bullets: 7.2.a -->

A stream is an independent, bidirectional sequence of frames exchanged between the client and server within an HTTP/2 connection (`rfc9113#section-5`).

A single HTTP/2 connection can contain multiple concurrently open streams, with either endpoint interleaving frames from multiple streams (`rfc9113#section-5`).

Streams are identified by an integer, and the endpoint initiating a stream assigns its identifier (`rfc9113#section-5`).

Recipients process frames in the order they are received (`rfc9113#section-5`).

A peer can limit the number of concurrently active streams using the SETTINGS_MAX_CONCURRENT_STREAMS parameter within a SETTINGS frame (`rfc9113#section-5.1.2`).

The maximum concurrent streams setting is specific to each endpoint and applies only to the peer that receives the setting (`rfc9113#section-5.1.2`).

Clients specify the maximum number of concurrent streams the server can initiate, and servers specify the maximum number of concurrent streams the client can initiate (`rfc9113#section-5.1.2`).

Endpoints must not exceed the limit set by their peer (`rfc9113#section-5.1.2`).

Streams in either of the reserved states do not count toward the stream limit (`rfc9113#section-5.1.2`).

Using streams for multiplexing introduces contention over use of the TCP connection, resulting in blocked streams (`rfc9113#section-5.2`).

Flow control is used for both individual streams and the connection as a whole (`rfc9113#section-5.2`).

HTTP/2 provides for flow control through use of the WINDOW_UPDATE frame (`rfc9113#section-5.2`).

## Header compression
<!-- bullets: 7.2.a -->

The details of HTTP/2 field section compression and decompression are defined in a separate compression format, which for historical reasons refers to these processes as header compression and decompression (`rfc9113#section-4.3`).

HPACK treats a list of header fields as an ordered collection of name-value pairs that can include duplicate pairs (`rfc7541#section-1.1`).

In HPACK, names and values are considered to be opaque sequences of octets, and the order of header fields is preserved after being compressed and decompressed (`rfc7541#section-1.1`).

HPACK encoding is informed by header field tables that map header fields to indexed values (`rfc7541#section-1.1`).

HPACK literal values are either encoded directly or use a static Huffman code (`rfc7541#section-1.1`).

The HPACK encoder is responsible for deciding which header fields to insert as new entries in the header field tables (`rfc7541#section-1.1`).

The HPACK dynamic table consists of a list of header fields maintained in first-in, first-out order (`rfc7541#section-2.3.2`).

The first and newest entry in a dynamic table is at the lowest index, and the oldest entry is at the highest index (`rfc7541#section-2.3.2`).

The dynamic table is initially empty, and entries are added as each header block is decompressed (`rfc7541#section-2.3.2`).

A decoder must not treat duplicate entries in the dynamic table as an error (`rfc7541#section-2.3.2`).

To limit the memory requirements of the decoder, the dynamic table size is strictly bounded (`rfc7541#section-2.3.2`).

Field blocks must be transmitted as a contiguous sequence of frames, with no interleaved frames of any other type or from any other stream (`rfc9113#section-4.3`).

Field block fragments can only be sent in HEADERS, PUSH_PROMISE or CONTINUATION frames because these frames carry data that can modify the compression context maintained by a receiver (`rfc9113#section-4.3`).

A decoding error in a field block must be treated as a connection error of type COMPRESSION_ERROR (`rfc9113#section-4.3`).

Like HPACK, QPACK uses two tables for associating field lines to indices (`rfc9204#section-2`).

QPACK defines unidirectional streams for sending instructions from encoder to decoder and vice versa (`rfc9204#section-2`).

## QUIC and HTTP/3
<!-- bullets: 7.2.b -->

QUIC is a secure general-purpose transport protocol (`rfc9000#section-1`).

QUIC packets are carried in UDP datagrams to better facilitate deployment in existing systems and networks (`rfc9000#section-1`).

QUIC provides the necessary feedback to implement reliable delivery and congestion control (`rfc9000#section-1`).

QUIC integrates the TLS handshake, although using a customized framing for protecting packets (`rfc9000#section-1`).

QUIC relies on a combined cryptographic and transport handshake to minimize connection establishment latency (`rfc9000#section-7`).

In the QUIC cryptographic handshake, a server is always authenticated (`rfc9000#section-7`).

In the QUIC cryptographic handshake, a client is optionally authenticated (`rfc9000#section-7`).

QUIC includes an option for clients to send data immediately (0-RTT), which requires some form of prior communication or configuration to enable (`rfc9000#section-1`).

QUIC endpoints must explicitly negotiate an application protocol (`rfc9000#section-7`).

QUIC streams can be unidirectional or bidirectional (`rfc9000#section-2`).

QUIC streams can be created by sending data (`rfc9000#section-2`).

A single STREAM frame can open, carry data for, and close a QUIC stream (`rfc9000#section-2`).

QUIC streams can be created by either endpoint, can concurrently send data interleaved with other streams, and can be canceled (`rfc9000#section-2`).

QUIC does not provide any means of ensuring ordering between bytes on different streams (`rfc9000#section-2`).

QUIC streams are flow controlled both individually and across a connection as a whole (`rfc9000#section-4`).

The primary function of a connection ID is to ensure that changes in addressing at lower protocol layers do not cause packets for a QUIC connection to be delivered to the wrong endpoint (`rfc9000#section-5.1`).

Multiple connection IDs are used so that endpoints can send packets that an observer cannot identify as being for the same connection without cooperation from an endpoint (`rfc9000#section-5.1`).

Each endpoint selects the connection IDs that its peer uses (`rfc9000#section-5.1`).

The use of a connection ID allows connections to survive changes to endpoint addresses, such as those caused by an endpoint migrating to a new network (`rfc9000#section-9`).

Only clients are able to migrate in version 1 of QUIC (`rfc9000#section-1`).

An endpoint must not initiate connection migration before the handshake is confirmed (`rfc9000#section-9`).

An endpoint must perform path validation if it detects any change to a peer's address, unless it has previously validated that address (`rfc9000#section-9`).

NAT rebinding is a change of address due to a middlebox, usually a NAT, allocating a new outgoing port or even a new outgoing IP address for a flow (`rfc9000#section-9`).

QUIC offers several ways to end a connection: a graceful shutdown, a negotiated timeout period, immediate teardown on errors, and a stateless mechanism for after one endpoint has lost state (`rfc9000#section-1`).

Once established, an HTTP/3 connection can be used for many requests and responses over time until the connection is closed (`rfc9114#section-5`).

## WebSockets
<!-- bullets: 7.2.c -->

The WebSocket protocol has two parts: a handshake and the data transfer (`rfc6455#section-1.2`).

The WebSocket opening handshake is intended to be compatible with HTTP-based server-side software and intermediaries, so that a single port can be used by both HTTP clients and WebSocket clients (`rfc6455#section-1.3`).

The Request-URI of the GET method identifies the endpoint of the WebSocket connection, to allow multiple domains to be served from one IP address and multiple WebSocket endpoints to be served by a single server (`rfc6455#section-1.3`).

The Origin header field protects against unauthorized cross-origin use of a WebSocket server by scripts using the WebSocket API in a web browser (`rfc6455#section-1.3`).

The first line of the server's handshake is an HTTP Status-Line with the status code 101 (`rfc6455#section-1.3`).

Any status code other than 101 indicates that the WebSocket handshake has not completed and that the semantics of HTTP still apply (`rfc6455#section-1.3`).

The Sec-WebSocket-Accept header field must include a hash of the client's nonce sent in Sec-WebSocket-Key along with a predefined GUID (`rfc6455#section-1.3`).

The server returns the base64-encoded SHA-1 hash (160 bits) of the Sec-WebSocket-Key value concatenated with the GUID (`rfc6455#section-1.3`).

If the Sec-WebSocket-Accept value does not match the expected value, if the header field is missing, or if the HTTP status code is not 101, the connection will not be established (`rfc6455#section-1.3`).

```java snippet=m07-l02/WebSocketAccept.java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.Base64;
import java.util.HexFormat;

public class WebSocketAccept {
    static final String GUID = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11";

    public static void main(String[] args) throws NoSuchAlgorithmException {
        String key = "dGhlIHNhbXBsZSBub25jZQ==";
        byte[] hash = MessageDigest.getInstance("SHA-1").digest((key + GUID).getBytes(StandardCharsets.US_ASCII));
        System.out.println(HexFormat.of().formatHex(hash));
        System.out.println(Base64.getEncoder().encodeToString(hash).equals("s3pPLMBiTxaQ9kYGzzhZRbK+xOo="));
    }
}
```

Hashing the sample key followed by the GUID with SHA-1 gives the bytes `b37a4f2c...c4ea`, which the snippet prints in hexadecimal.

The base64 encoding of that hash equals the `Sec-WebSocket-Accept` value of the specification's sample, so the snippet prints `true`.

After the handshake the data transfer is a two-way communication channel where each side can, independently from the other, send data at will (`rfc6455#section-1.2`).

After a successful handshake, clients and servers transfer data back and forth in conceptual units called messages (`rfc6455#section-1.2`).

This version of the WebSocket protocol defines six frame types and leaves ten reserved for future use (`rfc6455#section-1.2`).

Either peer can send a control frame to begin the closing handshake (`rfc6455#section-1.4`).

Upon receiving that frame, the other peer sends a Close frame in response, if it has not already sent one (`rfc6455#section-1.4`).

Upon receiving that response, the first peer closes the connection, safe in the knowledge that no further data is forthcoming (`rfc6455#section-1.4`).

After sending a control frame indicating the connection should be closed, a peer does not send any further data (`rfc6455#section-1.4`).

It is safe for both peers to initiate the WebSocket closing handshake simultaneously (`rfc6455#section-1.4`).

The closing handshake complements the TCP closing handshake, which is not always reliable end-to-end, especially in the presence of intercepting proxies and other intermediaries (`rfc6455#section-1.4`).

## Server-Sent Events
<!-- bullets: 7.2.c -->

The EventSource interface enables servers to push data to web pages over HTTP or using dedicated server-push protocols (`whatwg-html-sse#server-sent-events-intro`).

The event stream format's MIME type is text/event-stream (`whatwg-html-sse#parsing-an-event-stream`).

Event streams must always be encoded as UTF-8 (`whatwg-html-sse#parsing-an-event-stream`).

Event streams are always decoded as UTF-8, and there is no way to specify another character encoding (`whatwg-html-sse#server-sent-events-intro`).

The default event type is message (`whatwg-html-sse#server-sent-events-intro`).

Lines in an event stream must be separated by a CRLF pair, a single LF character, or a single CR character (`whatwg-html-sse#parsing-an-event-stream`).

Event stream requests can be redirected using HTTP 301 and 307 redirects as with normal HTTP requests (`whatwg-html-sse#server-sent-events-intro`).

Clients will reconnect if the connection is closed, and a client can be told to stop reconnecting using the HTTP 204 No Content response code (`whatwg-html-sse#server-sent-events-intro`).

When reestablishing the connection, the user agent waits a delay equal to the reconnection time of the event source (`whatwg-html-sse#sse-processing-model`).

If the previous attempt failed, user agents might introduce an exponential backoff delay to avoid overloading a potentially already overloaded server (`whatwg-html-sse#sse-processing-model`).

Once the user agent has failed the connection, it does not attempt to reconnect (`whatwg-html-sse#sse-processing-model`).

The Last-Event-ID HTTP request header reports an EventSource object's last event ID string to the server when the user agent is to reestablish the connection (`whatwg-html-sse#the-last-event-id-header`).

Block buffering or line buffering with different expected line endings can cause delays in event dispatch (`whatwg-html-sse#parsing-an-event-stream`).

## Key points

- HTTP/1.0 allowed one outstanding request per TCP connection, and HTTP/1.1 added pipelining, which only partially addressed concurrency.
- A server must send the responses to pipelined requests in the order it received the requests.
- An HTTP/2 stream is an independent, bidirectional sequence of frames, and one connection can carry many concurrently open streams.
- `SETTINGS_MAX_CONCURRENT_STREAMS` limits the streams the receiving peer can open, and HTTP/2 flow control uses `WINDOW_UPDATE` for streams and for the connection.
- The HPACK dynamic table is maintained in first-in, first-out order.
- A field block is sent as a contiguous sequence of frames, and a decoding error in it is a connection error of type `COMPRESSION_ERROR`.
- QUIC packets travel in UDP datagrams, and QUIC integrates the TLS handshake with its own packet protection.
- QUIC provides no ordering between bytes on different streams, and a single `STREAM` frame can open, carry data for and close a stream.
- A QUIC connection ID keeps packets going to the right endpoint when addresses change, and only clients migrate in version 1.
- The first line of the server's WebSocket handshake is an HTTP Status-Line with the status code `101`.
- A WebSocket peer answers a Close frame with a Close frame, and the first peer then closes the connection.
- An event stream has the MIME type `text/event-stream`.
- A reconnecting `EventSource` reports its last event ID in the `Last-Event-ID` request header.

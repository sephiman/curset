# Concurrency anomalies, locking and connection pooling

## The four phenomena
<!-- bullets: 6.2.a -->

The SQL standard defines the three levels below Serializable in terms of phenomena resulting from interaction between concurrent transactions, which must not occur at each level (`pg-transaction-iso#TRANSACTION-ISO`).

A dirty read is a transaction reading data written by a concurrent uncommitted transaction (`pg-transaction-iso#TRANSACTION-ISO`).

A nonrepeatable read is a transaction re-reading data it has previously read and finding that data modified by another transaction that committed since the initial read (`pg-transaction-iso#TRANSACTION-ISO`).

A phantom read is a transaction re-executing a query that returns a set of rows satisfying a search condition and finding that the set has changed because of another recently committed transaction (`pg-transaction-iso#TRANSACTION-ISO`).

A serialization anomaly is a result of successfully committing a group of transactions that is inconsistent with all possible orderings of running those transactions one at a time (`pg-transaction-iso#TRANSACTION-ISO`).

## What each PostgreSQL 18 level allows
<!-- bullets: 6.2.a -->

:::esquema{kind=tabla title="Phenomena per isolation level in PostgreSQL 18"}
| Level | Dirty read | Nonrepeatable read | Phantom read | Serialization anomaly | Source |
|---|---|---|---|---|---|
| Read uncommitted | Allowed, but not in PG | Possible | Possible | Possible | `pg-transaction-iso#TRANSACTION-ISO` |
| Read committed | Not possible | Possible | Possible | Possible | `pg-transaction-iso#TRANSACTION-ISO` |
| Repeatable read | Not possible | Not possible | Allowed, but not in PG | Possible | `pg-transaction-iso#TRANSACTION-ISO` |
| Serializable | Not possible | Not possible | Not possible | Not possible | `pg-transaction-iso#TRANSACTION-ISO` |
:::

In PostgreSQL, a request for Read Uncommitted is accepted, but its Read Uncommitted mode behaves like Read Committed (`pg-transaction-iso#TRANSACTION-ISO`).

PostgreSQL's Repeatable Read implementation does not allow phantom reads, which is acceptable under the SQL standard because the standard specifies which anomalies must not occur at certain levels and higher guarantees are acceptable (`pg-transaction-iso#TRANSACTION-ISO`).

Repeatable Read prevents all the phenomena of the isolation table except serialization anomalies (`pg-transaction-iso#XACT-REPEATABLE-READ`).

Under the SQL standard, none of the phenomena are possible at Serializable (`pg-transaction-iso#TRANSACTION-ISO`).

## Anomalies at Read Committed
<!-- bullets: 6.2.a -->

A Read Committed `SELECT` sees only data committed before the query began (`pg-transaction-iso#XACT-READ-COMMITTED`).

Two successive `SELECT` commands in one Read Committed transaction can see different data, if other transactions commit changes in between (`pg-transaction-iso#XACT-READ-COMMITTED`).

An updating command in Read Committed can see the effects of concurrent updating commands on the rows it is updating, but not their effects on other rows of the database (`pg-transaction-iso#XACT-READ-COMMITTED`).

This behavior makes Read Committed unsuitable for commands that involve complex search conditions (`pg-transaction-iso#XACT-READ-COMMITTED`).

In a two-row table `website` with `hits` equal to 9 and 10, a `DELETE FROM website WHERE hits = 10` run while a concurrent `UPDATE website SET hits = hits + 1` is in progress has no effect (`pg-transaction-iso#XACT-READ-COMMITTED`).

The `DELETE` has no effect because the pre-update row value 9 is skipped, and when the `UPDATE` completes and the `DELETE` obtains a lock, the new row value is 11, which no longer matches the criteria (`pg-transaction-iso#XACT-READ-COMMITTED`).

## Anomalies at Repeatable Read and Serializable
<!-- bullets: 6.2.a -->

A Repeatable Read transaction that tries to modify or lock a row changed and committed by a concurrent transaction after its start is rolled back (`pg-transaction-iso#XACT-REPEATABLE-READ`).

```text
ERROR: could not serialize access due to concurrent update
```

Even a read-only transaction at Repeatable Read may see a control record updated to show that a batch has been completed but not see one of the detail records that is logically part of the batch (`pg-transaction-iso#XACT-REPEATABLE-READ`).

In the `mytab` example, serializable transaction A sums the rows of class 1 and inserts the result as a row of class 2, while transaction B sums the rows of class 2 and inserts its result as a row of class 1 (`pg-transaction-iso#XACT-SERIALIZABLE`).

If either transaction were running at Repeatable Read, both would be allowed to commit, although there is no serial order of execution consistent with the result (`pg-transaction-iso#XACT-SERIALIZABLE`).

Under Serializable, one of the two transactions commits and the other is rolled back (`pg-transaction-iso#XACT-SERIALIZABLE`).

```text
ERROR: could not serialize access due to read/write dependencies among transactions
```

Detection of the conditions that could cause a serialization anomaly triggers a serialization failure (`pg-transaction-iso#XACT-SERIALIZABLE`).

Serialization failures always return with an SQLSTATE value of `40001` (`pg-transaction-iso#XACT-SERIALIZABLE`).

Applications using Serializable must be prepared to retry transactions due to serialization failures (`pg-transaction-iso#XACT-SERIALIZABLE`).

## Write skew
<!-- bullets: 6.2.a -->

Write skew, called A5B in the critique of ANSI SQL isolation levels, is the history in which T1 reads x and y, which are consistent with a constraint, and then T2 reads x and y, writes x and commits, and then T1 writes y (`paper-berenson-critique-ansi-isolation#p9`).

If there is a constraint between x and y, write skew might violate it (`paper-berenson-critique-ansi-isolation#p9`; `paper-berenson-critique-ansi-isolation#p10`).

Write skew can occur in a Snapshot Isolation history (`paper-berenson-critique-ansi-isolation#p10`).

Snapshot Isolation histories prohibit histories with the phantom anomaly A3 but allow write skew (`paper-berenson-critique-ansi-isolation#p10`).

The simplest snapshot isolation anomaly occurs between two concurrent transactions that read the same data but modify disjoint sets of data (`paper-ports-grittner-ssi#p2`).

In the doctors example, each of two transactions checks whether at least two doctors are on call and, if so, takes one doctor off call (`paper-ports-grittner-ssi#p2`).

Under snapshot isolation, both doctors transactions read a snapshot that shows both doctors on call, so they both proceed to take their doctor off call (`paper-ports-grittner-ssi#p2`).

The write locks taken on update do not prevent this, because the two transactions modify different rows and thus do not conflict (`paper-ports-grittner-ssi#p2`).

Executing the two doctors transactions sequentially in either order leaves at least one doctor on call (`paper-ports-grittner-ssi#p2`).

Serializable Snapshot Isolation runs transactions using snapshot isolation but adds additional checks to determine whether anomalies are possible (`paper-ports-grittner-ssi#p3`).

PostgreSQL's Serializable level is implemented with Serializable Snapshot Isolation, which rolls back one transaction of a conflicting pair with a serialization failure (`pg-transaction-iso#XACT-SERIALIZABLE`).

## Lost updates and optimistic locking
<!-- bullets: 6.2.a 6.2.b -->

Optimistic locking is a system of concurrency control where each revision of an item of data is assigned a version number or timestamp (`jakarta-persistence-spec#a2056`).

An optimistic lock failure occurs when the version or timestamp held in the database changes between reading the data and attempting to update or delete it (`jakarta-persistence-spec#a2056`).

Optimistic lock verification ensures that an update of an item succeeds only when no intervening transaction has already updated it, which prevents the loss of updates made by such intervening transactions (`jakarta-persistence-spec#a2056`).

Failure to use optimistic locking often leads to inconsistent entity state, lost updates, and other anomalies (`jakarta-persistence-spec#a2056`).

The persistence provider is required to perform optimistic locking automatically for every entity with a version (`jakarta-persistence-spec#a2056`).

A portable application specifies the version field or property of an optimistically locked entity with the `@Version` annotation (`jakarta-persistence-spec#a2056`).

When an optimistic lock failure is detected, the persistence provider must throw an `OptimisticLockException` and mark the current transaction for rollback (`jakarta-persistence-spec#a2056`).

The persistence provider must update the entity version each time the state of an entity instance is written to the database (`jakarta-persistence-spec#a2059`).

The persistence provider must throw an `OptimisticLockException` when it merges a detached entity instance that holds a stale revision of the entity state (`jakarta-persistence-spec#a2059`).

The persistence provider may check the version synchronously with the call to `merge()`, or delay the check until a flush operation or until the transaction commits (`jakarta-persistence-spec#a2059`).

If an update involves entities with versions and entities without versions, the provider is only required to verify the entities that have a version, and the consistency of the whole object graph is not guaranteed (`jakarta-persistence-spec#a2059`).

If an entity has no version, the application itself must bear the burden of maintaining data consistency during optimistic units of work (`jakarta-persistence-spec#a2056`).

Hibernate provides two mechanisms for storing versioning information, a dedicated version number or a timestamp (`hibernate-user-guide#locking-optimistic`).

In Hibernate, the entity manager uses the version property to detect conflicting updates and to prevent the loss of updates that would otherwise be overwritten by a last-commit-wins strategy (`hibernate-user-guide#locking-optimistic-version-number`).

In Hibernate, an application is forbidden from altering the version number that Hibernate sets (`hibernate-user-guide#locking-optimistic-version-number`).

:::judgement{source="Hibernate ORM user guide, Locking" ref="hibernate-user-guide#locking-optimistic"}
According to the Hibernate user guide, optimistic locking guarantees some isolation, scales well and works particularly well in read-often-write-sometimes situations.
:::

:::judgement{source="Jakarta Persistence 3.2 specification, section 3.5" ref="jakarta-persistence-spec#a2066"}
According to the Jakarta Persistence 3.2 specification, optimistic locking is typically appropriate in dealing with moderate contention among concurrent transactions, while in some applications it may be useful to immediately obtain long-term database locks because of the often late failure of optimistic transactions.
:::

## Pessimistic locking and row locks
<!-- bullets: 6.2.b -->

Once a transaction has obtained a pessimistic lock on an entity instance, no other transaction may successfully modify or delete that instance until the transaction holding the lock has ended (`jakarta-persistence-spec#a2066`).

When an entity instance is locked using pessimistic locking, the persistence provider must lock the database rows that correspond to the non-collection-valued persistent state of that instance (`jakarta-persistence-spec#a2066`).

Whenever a pessimistically locked entity with a version attribute is updated on the database, the persistence provider must also increment the version column (`jakarta-persistence-spec#a2066`).

Jakarta Persistence defines six distinct lock modes, and the lock mode types `READ` and `WRITE` are synonyms for `OPTIMISTIC` and `OPTIMISTIC_FORCE_INCREMENT` (`jakarta-persistence-spec#a2084`).

Hibernate always uses the locking mechanism of the database and never locks objects in memory (`hibernate-user-guide#locking-pessimistic`).

`FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE` and `FOR KEY SHARE` are locking clauses that affect how `SELECT` locks rows as they are obtained from the table (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

Row-level locks do not affect data querying; they block only writers and lockers to the same row (`pg-explicit-locking#LOCKING-ROWS`).

`FOR UPDATE` prevents the retrieved rows from being locked, modified or deleted by other transactions until the current transaction ends (`pg-explicit-locking#LOCKING-ROWS`).

Within a `REPEATABLE READ` or `SERIALIZABLE` transaction, `SELECT FOR UPDATE` throws an error if a row to be locked has changed since the transaction started (`pg-explicit-locking#LOCKING-ROWS`).

`FOR SHARE` acquires a shared lock on each retrieved row (`pg-explicit-locking#LOCKING-ROWS`).

A shared lock blocks other transactions from performing `UPDATE`, `DELETE`, `SELECT FOR UPDATE` or `SELECT FOR NO KEY UPDATE` on those rows, but it does not prevent `SELECT FOR SHARE` or `SELECT FOR KEY SHARE` (`pg-explicit-locking#LOCKING-ROWS`).

`SELECT FOR UPDATE` modifies the selected rows to mark them locked, and so results in disk writes (`pg-explicit-locking#LOCKING-ROWS`).

With `NOWAIT`, the statement reports an error, rather than waiting, if a selected row cannot be locked immediately (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

With `SKIP LOCKED`, any selected rows that cannot be immediately locked are skipped (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

Skipping locked rows provides an inconsistent view of the data, so it is not suitable for general purpose work, but it can be used to avoid lock contention with multiple consumers accessing a queue-like table (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

## Sizing a HikariCP pool
<!-- bullets: 6.2.c -->

The HikariCP pool sizing guide gives the formula `connections = ((core_count * 2) + effective_spindle_count)` for the number of active connections that gives optimal throughput (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

The core count in that formula should not include hyperthreading threads, even if hyperthreading is enabled (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

The effective spindle count is zero if the active data set is fully cached, and approaches the actual number of spindles as the cache hit rate falls (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

For a 4-core server with one hard disk, the formula gives 9 = ((4 * 2) + 1) (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

The guide states that there has been no analysis of how well the formula works with SSDs (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

:::judgement{source="HikariCP wiki, About Pool Sizing" ref="hikaricp-pool-sizing#axiom-you-want-a-small-pool-saturated-with-threads-waiting-for-connections"}
According to the HikariCP wiki, you want a small pool of a few dozen connections at most, saturated with threads waiting for connections, set right at the limit of the number of queries the database can process simultaneously.
:::

The default value of the HikariCP property `maximumPoolSize` is 10 (`hikaricp-readme#frequently-used`).

When the pool reaches `maximumPoolSize` and no idle connections are available, calls to `getConnection()` block for up to `connectionTimeout` milliseconds before timing out (`hikaricp-readme#frequently-used`).

The default value of `connectionTimeout` is 30000 milliseconds (`hikaricp-readme#frequently-used`).

If `connectionTimeout` is exceeded without a connection becoming available, a `SQLException` is thrown (`hikaricp-readme#frequently-used`).

The pool size that makes deadlock impossible is `pool size = Tn x (Cm - 1) + 1`, where Tn is the maximum number of threads and Cm is the maximum number of simultaneous connections held by a single thread (`hikaricp-pool-sizing#pool-locking`).

With three threads that each require four connections, that formula gives a pool size of 10 (`hikaricp-pool-sizing#pool-locking`).

The result of that formula is not necessarily the optimal pool size, but the minimum required to avoid deadlock (`hikaricp-pool-sizing#pool-locking`).

## PgBouncer pooling modes
<!-- bullets: 6.2.c -->

The PgBouncer setting `pool_mode` specifies when a server connection can be reused by other clients (`pgbouncer-config#pool_mode`).

In session pooling mode, the server connection is released back to the pool after the client disconnects, and this is the default (`pgbouncer-config#pool_mode`).

In transaction pooling mode, the server connection is released back to the pool after the transaction finishes (`pgbouncer-config#pool_mode`).

In statement pooling mode, the server connection is released back to the pool after the query finishes, and transactions spanning multiple statements are disallowed (`pgbouncer-config#pool_mode`).

Transaction pooling breaks client expectations of the server by design and can be used only if the application cooperates by not using non-working features (`pgbouncer-features#sql-feature-map-for-pooling-modes`).

:::esquema{kind=tabla title="PgBouncer 1.26 features by pooling mode"}
| Feature | Session pooling | Transaction pooling | Source |
|---|---|---|---|
| `SET` / `RESET` | Yes | Never | `pgbouncer-features#sql-feature-map-for-pooling-modes` |
| `LISTEN` | Yes | Never | `pgbouncer-features#sql-feature-map-for-pooling-modes` |
| `NOTIFY` | Yes | Yes | `pgbouncer-features#sql-feature-map-for-pooling-modes` |
| `PREPARE` / `DEALLOCATE` | Yes | Never | `pgbouncer-features#sql-feature-map-for-pooling-modes` |
| Session-level advisory locks | Yes | Never | `pgbouncer-features#sql-feature-map-for-pooling-modes` |
| Protocol-level prepared plans | Yes | Yes, with `max_prepared_statements` non-zero | `pgbouncer-features#sql-feature-map-for-pooling-modes` |
:::

With `max_prepared_statements` set to a non-zero value, PgBouncer tracks protocol-level named prepared statements in transaction and statement pooling mode (`pgbouncer-config#max_prepared_statements`).

When `max_prepared_statements` is 0, prepared statement support for transaction and statement pooling is disabled (`pgbouncer-config#max_prepared_statements`).

The default value of `max_prepared_statements` is 200 (`pgbouncer-config#max_prepared_statements`).

SQL-level `PREPARE`, `EXECUTE` and `DEALLOCATE` commands are forwarded straight to Postgres, so PgBouncer does not track them (`pgbouncer-config#max_prepared_statements`).

The default value of `default_pool_size` is 20 server connections per user and database pair (`pgbouncer-config#default_pool_size`).

## Key points

- Read Uncommitted behaves like Read Committed in PostgreSQL, so dirty reads never occur.
- Read Committed allows nonrepeatable reads, phantom reads and serialization anomalies.
- Repeatable Read does not allow phantom reads in PostgreSQL but allows serialization anomalies.
- Serializable fails one of two conflicting transactions with a serialization failure, SQLSTATE `40001`, and the application retries it.
- Optimistic locking verifies a version number or timestamp and throws an `OptimisticLockException` when the revision is stale.
- `FOR UPDATE` blocks other writers and lockers of the row, and `FOR SHARE` still lets other `FOR SHARE` locks through.
- `SKIP LOCKED` skips rows that cannot be locked immediately, and `NOWAIT` raises an error instead.
- The HikariCP guide gives `connections = ((core_count * 2) + effective_spindle_count)`, and `maximumPoolSize` defaults to 10.
- PgBouncer releases a server connection after the client disconnects in session mode and after the transaction in transaction mode.
- Transaction pooling does not support `SET`, `LISTEN`, `PREPARE` or session-level advisory locks.

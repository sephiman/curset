# Advanced indexing, partitioning and SQL optimisation

## B-tree and hash indexes
<!-- bullets: 6.3.a -->

B-trees can handle equality and range queries on data that can be sorted into some ordering (`pg-indexes-types#INDEXES-TYPES-BTREE`).

The PostgreSQL query planner will consider using a B-tree index whenever an indexed column is involved in a comparison using `<`, `<=`, `=`, `>=` or `>` (`pg-indexes-types#INDEXES-TYPES-BTREE`).

Constructs equivalent to combinations of these operators, such as `BETWEEN` and `IN`, can also be implemented with a B-tree index search (`pg-indexes-types#INDEXES-TYPES-BTREE`).

The optimizer can use a B-tree index for `LIKE` and `~` when the pattern is a constant anchored to the beginning of the string, as in `col LIKE 'foo%'` and not in `col LIKE '%bar'` (`pg-indexes-types#INDEXES-TYPES-BTREE`).

B-tree indexes can also be used to retrieve data in sorted order (`pg-indexes-types#INDEXES-TYPES-BTREE`).

Hash indexes store a 32-bit hash code derived from the value of the indexed column (`pg-indexes-types#INDEXES-TYPES-HASH`).

Hash indexes can therefore only handle simple equality comparisons (`pg-indexes-types#INDEXES-TYPES-HASH`).

## GiST and GIN indexes
<!-- bullets: 6.3.a -->

GiST indexes are not a single kind of index but an infrastructure within which many different indexing strategies can be implemented (`pg-indexes-types#INDEXES-TYPE-GIST`).

The operators with which a GiST index can be used vary depending on the indexing strategy, which is the operator class (`pg-indexes-types#INDEXES-TYPE-GIST`).

GiST indexes can also optimize nearest-neighbor searches, such as finding the ten places closest to a given target point (`pg-indexes-types#INDEXES-TYPE-GIST`).

GIN indexes are "inverted indexes" which are appropriate for data values that contain multiple component values, such as arrays (`pg-indexes-types#INDEXES-TYPES-GIN`).

An inverted index contains a separate entry for each component value (`pg-indexes-types#INDEXES-TYPES-GIN`).

A GIN index can efficiently handle queries that test for the presence of specific component values (`pg-indexes-types#INDEXES-TYPES-GIN`).

The standard distribution of PostgreSQL includes a GIN operator class for arrays, which supports the operators `<@`, `@>`, `=` and `&&` (`pg-indexes-types#INDEXES-TYPES-GIN`).

:::esquema{kind=tabla title="Index types in PostgreSQL 18"}
| Index type | What it handles | Source |
|---|---|---|
| B-tree | Equality and range queries on data that can be sorted into some ordering | `pg-indexes-types#INDEXES-TYPES-BTREE` |
| Hash | Only simple equality comparisons | `pg-indexes-types#INDEXES-TYPES-HASH` |
| GiST | An infrastructure for many indexing strategies, with operators that depend on the operator class | `pg-indexes-types#INDEXES-TYPE-GIST` |
| GIN | Data values that contain multiple component values, such as arrays | `pg-indexes-types#INDEXES-TYPES-GIN` |
:::

## Composite (multicolumn) indexes
<!-- bullets: 6.3.a -->

An index can be defined on more than one column of a table (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

In PostgreSQL 18, only the B-tree, GiST, GIN and BRIN index types support multiple-key-column indexes (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

Indexes can have up to 32 columns, including `INCLUDE` columns (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

A multicolumn B-tree index can be used with query conditions that involve any subset of the index's columns, but the index is most efficient when there are constraints on the leading (leftmost) columns (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

The exact rule is that equality constraints on leading columns, plus any inequality constraints on the first column that does not have an equality constraint, will always be used to limit the portion of the index that is scanned (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

Constraints on columns to the right of these columns are checked in the index, so they always save visits to the table proper, but they do not necessarily reduce the portion of the index that has to be scanned (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

Given an index on `(a, b, c)` and the condition `WHERE a = 5 AND b >= 42 AND c < 77`, the index might have to be scanned from the first entry with `a = 5` and `b = 42` up through the last entry with `a = 5` (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

```sql
CREATE INDEX t_abc_idx ON t (a, b, c);
SELECT * FROM t WHERE a = 5 AND b >= 42 AND c < 77;
```

If a B-tree index scan can apply the skip scan optimization effectively, it applies every column constraint when navigating through the index via repeated index searches (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

Skip scan works by generating a dynamic equality constraint internally, one that matches every possible value in an index column (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

Given an index on `(x, y)` and the condition `WHERE y = 7700`, a B-tree index scan might be able to apply the skip scan optimization (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

The planner generally takes the skip scan approach only when there are so few distinct `x` values that it expects the scan to skip over most of the index (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

For a multicolumn GiST index, the condition on the first column is the most important one for determining how much of the index needs to be scanned (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

For a multicolumn GIN index, index search effectiveness is the same regardless of which index columns the query conditions use (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).

:::judgement{source="PostgreSQL 18 documentation, Multicolumn Indexes" ref="pg-indexes-multicolumn#INDEXES-MULTICOLUMN"}
According to the PostgreSQL 18 documentation, multicolumn indexes should be used sparingly. In most situations an index on a single column is sufficient and saves space and time. Indexes with more than three columns are unlikely to be helpful unless the usage of the table is extremely stylized.
:::

## Partial indexes
<!-- bullets: 6.3.a -->

A partial index is an index built over a subset of a table, and the subset is defined by a conditional expression called the predicate of the partial index (`pg-indexes-partial#INDEXES-PARTIAL`).

The index contains entries only for those table rows that satisfy the predicate (`pg-indexes-partial#INDEXES-PARTIAL`).

One major reason for using a partial index is to avoid indexing common values (`pg-indexes-partial#INDEXES-PARTIAL`).

A query searching for a common value, one that accounts for more than a few percent of all the table rows, will not use the index anyway (`pg-indexes-partial#INDEXES-PARTIAL`).

A partial index that excludes common values requires that the common values be predetermined, so it is best used for data distributions that do not change (`pg-indexes-partial#INDEXES-PARTIAL`).

A partial index can be used in a query only if the system can recognize that the `WHERE` condition of the query mathematically implies the predicate of the index (`pg-indexes-partial#INDEXES-PARTIAL`).

The system can recognize simple inequality implications, for example that `x < 1` implies `x < 2` (`pg-indexes-partial#INDEXES-PARTIAL`).

Otherwise the predicate condition must exactly match part of the query's `WHERE` condition, or the index will not be recognized as usable (`pg-indexes-partial#INDEXES-PARTIAL`).

Matching takes place at query planning time, not at run time, so parameterized query clauses do not work with a partial index (`pg-indexes-partial#INDEXES-PARTIAL`).

A unique partial index enforces uniqueness among the rows that satisfy the index predicate, without constraining those that do not (`pg-indexes-partial#INDEXES-PARTIAL`).

```sql
CREATE UNIQUE INDEX tests_success_constraint ON tests (subject, target)
WHERE success;
```

With a large set of non-overlapping partial indexes, the system does not understand the relationship among them and tests each one to see if it is applicable to the current query (`pg-indexes-partial#INDEXES-PARTIAL`).

With partitioning, the system does understand that the tables and indexes are non-overlapping (`pg-indexes-partial#INDEXES-PARTIAL`).

## Covering indexes and INCLUDE
<!-- bullets: 6.3.a -->

All indexes in PostgreSQL are secondary indexes, meaning that each index is stored separately from the table's main data area, which is called the table's heap (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

In an ordinary index scan, each row retrieval requires fetching data from both the index and the heap (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

Index-only scans can answer queries from an index alone without any heap access (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

The index type must support index-only scans, and B-tree indexes always do (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

GIN indexes cannot support index-only scans because each index entry typically holds only part of the original data value (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

The query must reference only columns stored in the index (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

Given an index on columns `x` and `y` of a table that also has a column `z`, `SELECT x FROM tab WHERE x = 'key' AND y < 42` could use an index-only scan, but `SELECT x, z FROM tab WHERE x = 'key'` could not (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

Visibility information is stored only in heap entries, not in index entries (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

An index-only scan checks the visibility map bit for the heap page of a candidate index entry (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

If that bit is not set, the heap entry must be visited, so no performance advantage is gained over a standard index scan (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

An index-only scan will be a win only if a significant fraction of the table's heap pages have their all-visible map bits set (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

A covering index is an index specifically designed to include the columns needed by a particular type of query that you run frequently (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

The `INCLUDE` clause lists extra columns that are just payload and are not part of the search key (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

```sql
CREATE INDEX tab_x_y ON tab(x) INCLUDE (y);
```

An index defined like this could handle `SELECT y FROM tab WHERE x = 'key'` as an index-only scan, because `y` can be obtained from the index without visiting the heap (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

A non-key column cannot be used in an index scan search qualification, and it is disregarded for purposes of any uniqueness or exclusion constraint enforced by the index (`pg-sql-createindex#id-1.9.3.69.6`).

In a unique index with an `INCLUDE` clause, the uniqueness condition applies only to the key column, not to the combination of key and included columns (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).

Expressions are not supported as included columns (`pg-sql-createindex#id-1.9.3.69.6`).

The B-tree, GiST and SP-GiST index access methods support included columns (`pg-sql-createindex#id-1.9.3.69.6`).

Columns listed in `INCLUDE` do not need appropriate operator classes (`pg-sql-createindex#id-1.9.3.69.6`).

Non-key columns duplicate data from the index's table and bloat the size of the index, thus potentially slowing searches (`pg-sql-createindex#id-1.9.3.69.6`).

:::judgement{source="PostgreSQL 18 documentation, Index-Only Scans and Covering Indexes" ref="pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS"}
According to the PostgreSQL 18 documentation, it is wise to be conservative about adding non-key payload columns to an index, especially wide columns. There is little point in including payload columns unless the table changes slowly enough that an index-only scan is likely to not need to access the heap.
:::

## Reading plans with EXPLAIN (ANALYZE, BUFFERS)
<!-- bullets: 6.3.b -->

The structure of a query plan is a tree of plan nodes (`pg-using-explain#USING-EXPLAIN-BASICS`).

Nodes at the bottom level of the tree are scan nodes, which return raw rows from a table (`pg-using-explain#USING-EXPLAIN-BASICS`).

The first line of the `EXPLAIN` output has the estimated total execution cost for the plan, and it is the number the planner seeks to minimize (`pg-using-explain#USING-EXPLAIN-BASICS`).

The costs are measured in arbitrary units determined by the planner's cost parameters (`pg-using-explain#USING-EXPLAIN-BASICS`).

The cost of an upper-level node includes the cost of all its child nodes (`pg-using-explain#USING-EXPLAIN-BASICS`).

The `rows` value is the number of rows emitted by the node, not the number processed or scanned by it (`pg-using-explain#USING-EXPLAIN-BASICS`).

With the `ANALYZE` option, `EXPLAIN` actually executes the query and then displays the true row counts and true run time accumulated within each plan node (`pg-using-explain#USING-EXPLAIN-ANALYZE`).

The `ANALYZE` parameter defaults to `FALSE` (`pg-sql-explain#id-1.9.3.148.8`).

The actual time values are in milliseconds of real time, whereas the cost estimates are expressed in arbitrary units, so they are unlikely to match up (`pg-using-explain#USING-EXPLAIN-ANALYZE`).

The thing that is usually most important to look for is whether the estimated row counts are reasonably close to reality (`pg-using-explain#USING-EXPLAIN-ANALYZE`).

When a node is executed more than once, the `loops` value reports the total number of executions, and the actual time and rows values shown are averages per execution (`pg-using-explain#USING-EXPLAIN-ANALYZE`).

Multiply the actual time by the `loops` value to get the total time actually spent in the node (`pg-using-explain#USING-EXPLAIN-ANALYZE`).

Index Scan nodes show an `Index Searches` line that reports the total number of searches across all node executions (`pg-using-explain#USING-EXPLAIN-ANALYZE`).

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM tenk1 WHERE unique1 < 100;
```

The `BUFFERS` parameter includes the number of shared blocks hit, read, dirtied and written, the number of local blocks hit, read, dirtied and written, and the number of temp blocks read and written (`pg-sql-explain#id-1.9.3.148.8`).

A hit means that a read was avoided because the block was found already in cache when needed (`pg-sql-explain#id-1.9.3.148.8`).

Shared blocks contain data from regular tables and indexes, local blocks contain data from temporary tables and indexes, and temporary blocks contain short-term working data used in sorts, hashes and similar cases (`pg-sql-explain#id-1.9.3.148.8`).

The number of blocks shown for an upper-level node includes those used by all its child nodes (`pg-sql-explain#id-1.9.3.148.8`).

In PostgreSQL 18, buffers information is automatically included when `ANALYZE` is used (`pg-sql-explain#id-1.9.3.148.8`).

Network transmission costs are not included in the run times measured by `EXPLAIN ANALYZE`, because no output rows are delivered to the client (`pg-using-explain#USING-EXPLAIN-CAVEATS`).

I/O conversion costs are not included either, unless `SERIALIZE` is specified (`pg-using-explain#USING-EXPLAIN-CAVEATS`).

The measurement overhead added by `EXPLAIN ANALYZE` can be significant, especially on machines with slow `gettimeofday()` operating-system calls (`pg-using-explain#USING-EXPLAIN-CAVEATS`).

Results on a toy-sized table cannot be assumed to apply to large tables (`pg-using-explain#USING-EXPLAIN-CAVEATS`).

On a table that only occupies one disk page, you will nearly always get a sequential scan plan whether indexes are available or not (`pg-using-explain#USING-EXPLAIN-CAVEATS`).

When plan node execution is stopped short by a `LIMIT`, the estimated cost and row count are shown as though the node were run to completion, and this is not an estimation error (`pg-using-explain#USING-EXPLAIN-CAVEATS`).

## Offset and keyset pagination
<!-- bullets: 6.3.c -->

`OFFSET` says to skip that many rows before beginning to return rows (`pg-queries-limit#QUERIES-LIMIT`).

If both `OFFSET` and `LIMIT` appear, `OFFSET` rows are skipped before starting to count the `LIMIT` rows that are returned (`pg-queries-limit#QUERIES-LIMIT`).

When using `LIMIT`, it is important to use an `ORDER BY` clause that constrains the result rows into a unique order, because otherwise you will get an unpredictable subset of the query's rows (`pg-queries-limit#QUERIES-LIMIT`).

The rows skipped by an `OFFSET` clause still have to be computed inside the server, so a large `OFFSET` might be inefficient (`pg-queries-limit#QUERIES-LIMIT`).

PostgreSQL also supports the SQL:2008 syntax `OFFSET start ROWS FETCH FIRST count ROWS ONLY` (`pg-sql-select#SQL-LIMIT`).

The `WITH TIES` option returns any additional rows that tie for the last place in the result set according to the `ORDER BY` clause, and `ORDER BY` is mandatory in this case (`pg-sql-select#SQL-LIMIT`).

Spring Data offset scrolling uses an offset counter to skip a number of results and lets the data source return results beginning at the given offset (`spring-data-jpa-query-methods#repositories.scrolling.offset`).

Most databases require materializing the full query result before your server can return the results of an offset scroll (`spring-data-jpa-query-methods#repositories.scrolling.offset`).

`ScrollPosition.offset(0)` skips the first element and translates to an offset of 1 (`spring-data-jpa-query-methods#repositories.scrolling.offset`).

Keyset filtering maintains a set of keys to resume scrolling by passing keys into the query, effectively amending your filter criteria (`spring-data-jpa-query-methods#repositories.scrolling.keyset`).

A `ScrollPosition` captures the keyset of the last entity within the current `Window` (`spring-data-jpa-query-methods#repositories.scrolling.keyset`).

With keyset filtering, the database needs to construct only a much smaller result from the given keyset position, without fully materializing a large result and then skipping results until reaching a particular offset (`spring-data-jpa-query-methods#repositories.scrolling.keyset`).

Keyset filtering requires the keyset properties, those used for sorting, to be non-nullable (`spring-data-jpa-query-methods#repositories.scrolling.keyset`).

Keyset filtering works best when your database contains an index that matches the sort fields (`spring-data-jpa-query-methods#repositories.scrolling.keyset`).

The keyset query mechanism amends your sort order by including the primary key, to ensure each query result is unique (`spring-data-jpa-query-methods#repositories.scrolling.keyset`).

Scroll queries applying keyset filtering require the properties used in the sort order to be returned by the query (`spring-data-jpa-query-methods#repositories.scrolling.keyset`).

An offset-based `Window` fetches `limit + 1` rows at `OffsetScrollPosition.getOffset()`, while a keyset-based `Window` fetches `limit + 1` rows using a rewritten `WHERE` condition (`spring-data-jpa-repositories-query-methods-details#repositories.scrolling.guidance`).

A `Window` can only navigate to the next `Window` (`spring-data-jpa-repositories-query-methods-details#repositories.scrolling.guidance`).

A `Page<T>` query can require a `COUNT(...)` query to determine the total number of elements (`spring-data-jpa-repositories-query-methods-details#repositories.scrolling.guidance`).

:::esquema{kind=tabla title="Offset-based and keyset-based scrolling in Spring Data JPA"}
| Aspect | Offset-based | Keyset-based | Source |
|---|---|---|---|
| Window query | Fetches `limit + 1` rows at `OffsetScrollPosition.getOffset()` | Fetches `limit + 1` rows using a rewritten `WHERE` condition | `spring-data-jpa-repositories-query-methods-details#repositories.scrolling.guidance` |
| How it resumes | An offset counter skips a number of results | A set of keys is passed into the query and amends the filter criteria | `spring-data-jpa-query-methods#repositories.scrolling.offset`; `spring-data-jpa-query-methods#repositories.scrolling.keyset` |
| Cost of a deep position | Most databases materialize the full query result | The database builds only the smaller result after the keyset position | `spring-data-jpa-query-methods#repositories.scrolling.offset`; `spring-data-jpa-query-methods#repositories.scrolling.keyset` |
:::

## Declarative partitioning
<!-- bullets: 6.3.c -->

Partitioning refers to splitting what is logically one large table into smaller physical pieces (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

The benefits of partitioning will normally be worthwhile only when a table would otherwise be very large (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

A rule of thumb is that the size of the table should exceed the physical memory of the database server (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

Bulk loads and deletes can be accomplished by adding or removing partitions, if the usage pattern is accounted for in the partitioning design (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

Dropping an individual partition with `DROP TABLE`, or running `ALTER TABLE DETACH PARTITION`, is far faster than a bulk operation (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

These commands also entirely avoid the `VACUUM` overhead caused by a bulk `DELETE` (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

PostgreSQL offers built-in support for range, list and hash partitioning (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

In range partitioning, each range's bounds are inclusive at the lower end and exclusive at the upper end (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

If one partition's range is from 1 to 10 and the next one's range is from 10 to 20, the value 10 belongs to the second partition (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

In hash partitioning, each partition holds the rows for which the hash value of the partition key divided by the specified modulus produces the specified remainder (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

:::esquema{kind=tabla title="Forms of declarative partitioning in PostgreSQL 18"}
| Form | How the rows are assigned | Source |
|---|---|---|
| Range | Ranges defined by a key column or set of columns, with no overlap between partitions | `pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW` |
| List | The key values that appear in each partition are listed explicitly | `pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW` |
| Hash | A modulus and a remainder are specified for each partition | `pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW` |
:::

The partitioned table itself is a "virtual" table having no storage of its own (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

All rows inserted into a partitioned table are routed to the appropriate partition based on the values of the partition key columns (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

Updating the partition key of a row will cause it to be moved into a different partition if it no longer satisfies the partition bounds of its original partition (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

It is not possible to turn a regular table into a partitioned table or vice versa (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

Partition pruning is a query optimization technique that improves performance for declaratively partitioned tables (`pg-ddl-partitioning#DDL-PARTITION-PRUNING`).

With partition pruning enabled, the planner examines the definition of each partition and excludes a partition when it can prove that the partition could not contain any rows meeting the query's `WHERE` clause (`pg-ddl-partitioning#DDL-PARTITION-PRUNING`).

```sql
SET enable_partition_pruning = on; -- the default
EXPLAIN SELECT count(*) FROM measurement WHERE logdate >= DATE '2008-01-01';
```

Partition pruning is driven only by the constraints defined implicitly by the partition keys, not by the presence of indexes (`pg-ddl-partitioning#DDL-PARTITION-PRUNING`).

Partition pruning can be performed not only during the planning of a query but also during its execution (`pg-ddl-partitioning#DDL-PARTITION-PRUNING`).

Partitions pruned during initialization of the query plan do not show up in `EXPLAIN` or `EXPLAIN ANALYZE`, and the `Subplans Removed` property reports how many were removed (`pg-ddl-partitioning#DDL-PARTITION-PRUNING`).

Partitions removed during initialization of the query plan are still locked at the beginning of execution (`pg-ddl-partitioning#DDL-PARTITION-PRUNING`).

Partition pruning can be disabled using the `enable_partition_pruning` setting (`pg-ddl-partitioning#DDL-PARTITION-PRUNING`).

Too many partitions can mean longer query planning times and higher memory consumption during both query planning and execution (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE-BEST-PRACTICES`).

The query planner is generally able to handle partition hierarchies with up to a few thousand partitions fairly well, provided that typical queries allow it to prune all but a small number of partitions (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE-BEST-PRACTICES`).

An entire partition can be detached fairly quickly (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE-BEST-PRACTICES`).

:::judgement{source="PostgreSQL 18 documentation, Best Practices for Declarative Partitioning" ref="pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE-BEST-PRACTICES"}
According to the PostgreSQL 18 documentation, the best partition key is often the column or set of columns that most commonly appear in the `WHERE` clauses of queries on the partitioned table. It also advises never to assume that more partitions are better than fewer, nor the reverse, and to simulate the intended workload.
:::

## ORM anti-patterns
<!-- bullets: 6.3.d -->

Fetching breaks down into two questions: when the data should be fetched, and how (`hibernate-user-guide#fetching-basics`).

"Now" is generally termed eager or immediate, and "later" is generally termed lazy or delayed (`hibernate-user-guide#fetching-basics`).

The `SELECT` fetch strategy performs a separate SQL select to load the data, and this is the strategy generally termed N+1 (`hibernate-user-guide#fetching-basics`).

The `JOIN` fetch strategy is inherently eager, and the data is obtained through an SQL outer join (`hibernate-user-guide#fetching-basics`).

The `BATCH` fetch strategy performs a separate SQL select to load a number of related data items, using an `IN` restriction based on a batch size (`hibernate-user-guide#fetching-basics`).

A fetch profile and an entity graph are mutually exclusive, and when both are present the entity graph takes effect and the fetch profile is ignored (`hibernate-user-guide#fetching-basics`).

A fetch join overrides the laziness of a given association, specifying that the association should be fetched with a SQL join (`hibernate-user-guide#hql-explicit-fetch-join`).

A `join fetch` only returns base entities with an associated entity, while a `left join fetch` returns all the base entities, including those with no associated entity (`hibernate-user-guide#hql-explicit-fetch-join`).

Without `join fetch`, you will quickly run into the "n+1 selects" problem when using HQL (`hibernate-user-guide#hql-explicit-fetch-join`).

Fetching multiple collections or to-many associations in parallel results in a Cartesian product at the database level (`hibernate-user-guide#hql-explicit-fetch-join`).

Fetch joins are disallowed in subqueries (`hibernate-user-guide#hql-explicit-fetch-join`).

A query with `left join fetch e.projects` loads an `Employee` and its `Projects` in exactly one database query (`hibernate-user-guide#fetching-strategies-dynamic-fetching`).

The `@BatchSize` annotation can be used when fetching uninitialized entity proxies (`hibernate-user-guide#fetching-batch`).

In the guide's example, only two SQL statements fetch the `Employee` entities of several `Department` entities, where without `@BatchSize` 10 queries would be needed (`hibernate-user-guide#fetching-batch`).

:::judgement{source="Hibernate ORM 7.4 User Guide, Batch fetching" ref="hibernate-user-guide#fetching-batch"}
According to the Hibernate ORM 7.4 User Guide, `@BatchSize` is better than running into an N+1 query issue, but most of the time a DTO projection or a `JOIN FETCH` is a much better alternative, since it fetches all the required data with a single query.
:::

The select list of an HQL query identifies which objects and values to return as the query results, and this operation is called projection (`hibernate-user-guide#hql-select-clause`).

The guide says it is better to specify the projection explicitly, except in the simplest cases (`hibernate-user-guide#hql-select-clause`).

With several expressions in the select list, each query result is by default packaged as an `Object[]` (`hibernate-user-guide#hql-select-clause`).

If the class `Tuple` is passed to `createQuery()`, each result is packaged as an instance of `jakarta.persistence.Tuple` (`hibernate-user-guide#hql-select-clause`).

The instantiation expression, `NEW`, is a special expression type that is only legal in the select clause (`hibernate-user-guide#hql-select-clause`).

In the session-per-request pattern, the application opens a Hibernate `Session` at the beginning of a request, starts a transaction, performs all data related work, ends the transaction and closes the `Session` (`hibernate-user-guide#session-per-request`).

The crux of the session-per-request pattern is the one-to-one relationship between the transaction and the `Session` (`hibernate-user-guide#session-per-request`).

JDBC batching means that drivers generally send the batched operation to the server in one call, which can save on network calls to the database (`hibernate-user-guide#batch-jdbcbatch`).

The `hibernate.jdbc.batch_size` setting controls the maximum number of statements Hibernate will batch together before asking the driver to execute the batch (`hibernate-user-guide#batch-jdbcbatch`).

A zero or negative `hibernate.jdbc.batch_size` disables JDBC batching (`hibernate-user-guide#batch-jdbcbatch`).

JDBC batching is not enabled by default, so every insert statement requires a database round trip (`hibernate-user-guide#batch-session-batch`).

Hibernate disables insert batching at the JDBC level transparently if you use an identity identifier generator (`hibernate-user-guide#batch-session-batch`).

When 100 000 entities are persisted in one transaction, Hibernate caches all the newly inserted instances in the session-level cache, so they are all managed by the persistence context when the transaction ends (`hibernate-user-guide#batch-session-batch`).

Long-running transactions can deplete a connection pool so other transactions do not get a chance to proceed (`hibernate-user-guide#batch-session-batch`).

The setting `hibernate.order_inserts` forces Hibernate to order inserts to allow more batching to be used, at a performance cost (`hibernate-user-guide#batch-jdbcbatch`).

Since version 5.2, Hibernate allows overriding the global JDBC batch size on a per-`Session` basis with `setJdbcBatchSize` (`hibernate-user-guide#batch-jdbcbatch`).

## Key points

- A B-tree index handles equality and range queries, while a hash index handles only simple equality comparisons (`pg-indexes-types#INDEXES-TYPES-BTREE`; `pg-indexes-types#INDEXES-TYPES-HASH`).
- Equality constraints on leading columns, plus any inequality constraints on the first column that does not have an equality constraint, always limit the portion of a multicolumn B-tree index that is scanned (`pg-indexes-multicolumn#INDEXES-MULTICOLUMN`).
- A partial index contains entries only for the rows that satisfy its predicate, and a query uses it only when its `WHERE` condition implies that predicate (`pg-indexes-partial#INDEXES-PARTIAL`).
- An index-only scan needs an index type that supports it and a query that references only columns stored in the index (`pg-indexes-index-only-scans#INDEXES-INDEX-ONLY-SCANS`).
- `INCLUDE` columns are non-key columns that cannot be used in an index scan search qualification (`pg-sql-createindex#id-1.9.3.69.6`).
- `EXPLAIN ANALYZE` executes the query, and its actual time values are in milliseconds while cost estimates are in arbitrary units (`pg-using-explain#USING-EXPLAIN-ANALYZE`).
- A large `OFFSET` might be inefficient because the skipped rows still have to be computed inside the server (`pg-queries-limit#QUERIES-LIMIT`).
- Keyset filtering requires non-nullable sort properties and works best with an index that matches the sort fields (`spring-data-jpa-query-methods#repositories.scrolling.keyset`).
- Partition pruning is driven only by the constraints defined by the partition keys, not by the presence of indexes (`pg-ddl-partitioning#DDL-PARTITION-PRUNING`).
- A fetch join overrides the laziness of an association and fetches it with a SQL join (`hibernate-user-guide#hql-explicit-fetch-join`).
- JDBC batching is not enabled by default in Hibernate, so every insert statement requires a database round trip (`hibernate-user-guide#batch-session-batch`).

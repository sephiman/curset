# Event sourcing and CQRS

## The event log, rehydration, snapshots and optimistic concurrency
<!-- bullets: 8.6.a -->

An event-sourced entity stores no state directly (`axon-event-sourced-entity#cmdk-launch`).

Every state change is recorded as an event, and the entity's current state is reconstructed by replaying those events in order (`axon-event-sourced-entity#cmdk-launch`).

This makes the event log the single source of truth, with a complete and immutable audit trail of everything that ever happened to the entity (`axon-event-sourced-entity#cmdk-launch`).

Every command that targets an entity instance must identify which instance to load (`axon-event-sourced-entity#_entity_identification`).

Axon filters the event stream of an entity through the identifier field marked with `@EventTag` on the events, matched by `tagKey` on the entity annotation (`axon-event-sourced-entity#_entity_identification`).

An entity creator method can be no-argument, identifier-based, or first-event-based (`axon-event-sourced-entity#_entity_creator`).

Snapshots can significantly reduce the number of events that must be replayed when sourcing an entity (`axon-snapshotting#_why_use_snapshots`).

With a snapshot, the system restores the entity from it and only applies the events that occurred afterwards (`axon-snapshotting#_why_use_snapshots`).

Snapshotting is activated by configuring a `SnapshotPolicy` on the repository (`axon-snapshotting#_snapshot_lifecycle`).

If a snapshot is available and can be used, the entity is initialized from that snapshot (`axon-snapshotting#_snapshot_lifecycle`).

Any events that occurred after the snapshot's position are then applied to bring the entity up to date (`axon-snapshotting#_snapshot_lifecycle`).

The dynamic consistency boundary replaces the focus on the aggregate identifier with user defined tags (`axon-event-store-internals#dynamic_consistency_boundaries_dcb`).

The consistency marker is returned as the final entry when sourcing events from an event store (`axon-event-store-internals#consistency_marker`).

When appending events with tags, Axon automatically attaches the consistency marker to the append condition (`axon-event-store-internals#consistency_marker`).

This prevents write conflicts, because concurrent writes to the same logical boundary are detected (`axon-event-store-internals#consistency_marker`).

An `AppendCondition` combines an `EventCriteria` with a `ConsistencyMarker` to enforce write conflict detection (`axon-event-store-internals#conditions`).

If events matching the criteria were appended after the marker's position, the append operation fails (`axon-event-store-internals#conditions`).

:::esquema{kind=tabla title="Three condition types of the event store"}
| Condition | Used when | Source |
|---|---|---|
| `AppendCondition` | Appending events to the event store | `axon-event-store-internals#conditions` |
| `SourcingCondition` | Sourcing events to rebuild entity state | `axon-event-store-internals#conditions` |
| `StreamingCondition` | Streaming events for event processors | `axon-event-store-internals#conditions` |
:::

## CQRS: write and read models, projections and eventual consistency
<!-- bullets: 8.6.b -->

Queries are messages that express the request for data (`axon-queries#cmdk-launch`).

Axon routes queries by the query's `MessageType`, qualified name and version, independent of the Java class of the payload (`axon-queries#cmdk-launch`).

When following CQRS, publishing an event should be regarded as updating a command model (`axon-event-processors-subscribing#cmdk-launch`).

Handling an event to update an entity is seen as a query model update in virtually all scenarios (`axon-event-processors-subscribing#cmdk-launch`).

A Subscribing Processor that reads from the `EventBus` only receives current events, so replaying is not an option (`axon-event-processors-subscribing#cmdk-launch`).

With the `EventBus` as source, a failing handler propagates its failure back to the publisher, failing the event publication (`axon-event-processors-subscribing#cmdk-launch`).

The `EventBus` delivers events to subscribers in the publishing thread (`axon-event-processors-subscribing#cmdk-launch`).

The Streaming Processor receives events from a `StreamableEventSource` (`axon-event-processors-streaming#cmdk-launch`).

The Pooled Streaming Event Processor is the default Event Processor (`axon-event-processors-streaming#cmdk-launch`).

The `SubscribingEventProcessor` is not the default in Axon Framework (`axon-event-processors-subscribing#cmdk-launch`).

All event handling components assigned to a single processor share the same configuration (`axon-event-processors#_assigning_handlers_to_processors`).

To advance and replay multiple projections as a unit or isolate failures across them, assign them to the same processor (`axon-event-processors#_assigning_handlers_to_processors`).

:::judgement{source="Martin Fowler, CQRS" ref="fowler-cqrs#banner"}
According to Martin Fowler, CQRS stands for Command Query Responsibility Segregation. At its heart is the notion that you can use a different model to update information than the model you use to read information. The models may share one database or use separate databases, and with separate databases there needs to be some communication mechanism between the two models. He adds that having separate models raises the question of how hard to keep them consistent, which raises the likelihood of using eventual consistency.
:::

## Event evolution: versioning, transformation and reversal
<!-- bullets: 8.6.c -->

Because events are stored indefinitely, the application should be able to cope with several versions of an event (`axon-event-versioning#cmdk-launch`).

Axon calls its approach payload conversion at handling time, which lets different handlers receive events in the format they expect (`axon-event-versioning#event_versioning_at_handling_time`).

Stored events retain their serialized form along with metadata about their `MessageType` (`axon-event-versioning#event_versioning_at_handling_time`).

When a handler needs to process an event, Axon converts the payload to the handler's expected type at that moment (`axon-event-versioning#event_versioning_at_handling_time`).

Different handlers can process the same event using different Java representations (`axon-event-versioning#event_versioning_at_handling_time`).

With payload conversion, event handling can evolve without modifying stored events (`axon-event-versioning#event_versioning_at_handling_time`).

A converter changes an event's representation, while a transformation changes its structure (`axon-message-transformation#_when_to_reach_for_a_transformation`).

Adding fields with defaults, dropping fields a handler no longer reads, renaming fields, and changing compatible field types are all typically handled by the converter (`axon-message-transformation#_when_to_reach_for_a_transformation`).

A change needs a transformation when the payload itself must be restructured, for example by combining `firstName` and `lastName` into one `fullName` (`axon-message-transformation#_when_to_reach_for_a_transformation`).

Axon Framework 5 keys events off a logical `MessageType` decoupled from the class, so a rename declares the old and new identity and carries the payload over unchanged (`axon-migration-upcasters#_renaming_an_event`).

An Axon Framework 4 upcaster could turn one stored event into several (`axon-migration-upcasters#_splitting_an_event`).

:::judgement{source="Martin Fowler, Event Sourcing" ref="fowler-event-sourcing#ReversingEvents"}
According to Martin Fowler, an event can reverse itself most easily when it is cast as a difference, such as adding 10 dollars to an account, as opposed to setting the account to a value. If the input events are not differences, he says an event should store what it needs for reversal, such as the previous values. He adds that reversal is never absolutely needed, because the same result comes from reverting to a past snapshot and replaying the event stream, but reversing a few events can be far more efficient than replaying many.
:::

## Projections in production: tracking position, claims, segments, replay and dead letters
<!-- bullets: 8.6.d -->

A streaming processor keeps its progress by updating and saving the tracking token after handling batches of events (`axon-event-processors-streaming#tracking_tokens`).

The streaming processor uses the `TokenStore` for the create, read, update and delete operations on tracking tokens (`axon-event-processors-streaming#tracking_tokens`).

To process any events, a streaming processor needs a claim on a tracking token (`axon-event-processors-streaming#tracking_tokens`).

If a token claim is not extended for a configurable amount of time, other processor threads can steal the claim (`axon-event-processors-streaming#tracking_tokens`).

A processor updates its claim every time it has finished handling a batch of events (`axon-event-processors-streaming#tracking_tokens`).

`tokenClaimInterval` defaults to 5000 milliseconds (`axon-event-processors-streaming#token_claim_config`).

A processor starting for the first time constructs an initial token that by default starts at the first position of the event stream (`axon-event-processors-streaming#initial_token`).

The events of that initial pass are handled as regular events, not as a replay (`axon-event-processors-streaming#initial_token`).

When no token store is explicitly defined, an `InMemoryTokenStore` is used (`axon-event-processors-streaming#token_store`).

The `InMemoryTokenStore` is not recommended in most production scenarios, because it cannot maintain the progress through application shutdowns (`axon-event-processors-streaming#token_store`).

Axon recommends a token store in the same database where the event handlers update the view models (`axon-event-processors-streaming#token_store`).

That way, changes to the view model can be stored atomically with the changed tokens, which guarantees exactly once processing semantics (`axon-event-processors-streaming#token_store`).

Each token instance represents a segment of the event stream, identified through a number (`axon-event-processors-streaming#parallel_processing`).

The default number of segments for a `PooledStreamingEventProcessor` is sixteen (`axon-event-processors-streaming#parallel_processing`).

A streaming processor can only initialize its number of segments when it starts for the first time (`axon-event-processors-streaming#parallel_processing`).

Axon guarantees that events in the same segment are processed sequentially (`axon-event-processors-streaming#sequencing_policies`).

`FullConcurrencyPolicy` tells Axon that the processor may handle all events concurrently (`axon-event-processors-streaming#sequencing_policies`).

`SequentialPolicy` tells Axon that it can process all events sequentially (`axon-event-processors-streaming#sequencing_policies`).

`SequentialPerAggregatePolicy` forces events raised from the same aggregate or entity to be handled sequentially (`axon-event-processors-streaming#sequencing_policies`).

The default `PropagatingErrorHandler` rethrows, so the segment retries the same event indefinitely (`axon-event-processors-streaming#stalled_segments`).

Handler work and the token update share one transaction (`axon-event-processors-streaming#stalled_segments`).

Events within a segment are processed in order, so one slow handler delays every sequence behind it (`axon-event-processors-streaming#stalled_segments`).

Handling events again by adjusting the position on the stream is called a replay (`axon-event-processors-streaming#replaying-events`).

Replaying events is not yet available in Axon Framework 5.0 and will be reintroduced in Axon Framework 5.1 (`axon-event-processors-streaming#replaying-events`).

A replay is done by adjusting the token position of the processor (`axon-event-processors-streaming#tracking_tokens`).

A `@ResetHandler` is a hook to prepare an event handling component before the replay begins (`axon-event-processors-streaming#_replay_api`).

After a partial replay, event handlers need to be aware that some events might not have been handled at all (`axon-event-processors-streaming#_partial_replays`).

The `DeadLetter` parameter of an event handler is null during normal event handling and non-null when the event is retried as part of dead-letter processing (`axon-dead-letter-queue#_detecting_dead_letter_processing_in_handlers`).

## Axon Framework: command bus, aggregates, event processors and sagas
<!-- bullets: 8.6.e -->

The `SimpleCommandBus` is the standard command bus implementation (`axon-command-infrastructure#_simplecommandbus`).

The `SimpleCommandBus` runs in a single JVM and cannot distribute commands across multiple instances (`axon-command-infrastructure#_simplecommandbus`).

Spring Boot configures a `SimpleCommandBus` through the Axon Spring Boot starter unless Axon Server is configured (`axon-command-infrastructure#_simplecommandbus`).

Axon provides distributed command bus implementations for applications that distribute command handling across multiple JVM instances (`axon-command-infrastructure#_distributed_command_bus`).

The `DistributedCommandBus` takes a local `CommandBus` called the `localSegment`, a `CommandBusConnector`, and a `DistributedCommandBusConfiguration` (`axon-command-infrastructure#_distributed_command_bus`).

The `CommandBusConnector` dispatches and receives commands to and from other JVMs (`axon-command-infrastructure#_distributed_command_bus`).

Command handlers come in three styles, depending on whether they need prior state and where that state lives (`axon-commands#_command_handler_styles`).

In an event-sourced entity the command handlers live on the entity class itself, alongside its state fields and event sourcing handlers (`axon-commands#_command_handler_styles`).

Stateful command handlers live in a dedicated class and receive the entity as a parameter via `@InjectEntity` (`axon-commands#_command_handler_styles`).

A saga coordinates a process through event handlers and persisted fields (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

Association values route events to the right saga instance (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

A workflow expresses the process as a method containing durable steps, waits, branches, and loops (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

Workflows source their state from dedicated workflow events in the regular event store instead of a persistent `SagaStore` blob (`axon-migration-sagas#workflows`).

Workflows are an Axoniq Framework feature and require an Axoniq license to run in production (`axon-migration-sagas#workflows`).

A retry in a workflow can repeat an external call, so a stable idempotency key is needed when the call must tolerate repetition (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

:::esquema{kind=tabla title="Saga and workflow compared"}
| Concern | Saga | Workflow | Source |
|---|---|---|---|
| Timeouts | Schedule a deadline, store its identifier, handle expiry, and cancel it on success | Configure a timeout on the step and branch on its outcome | `axon-migration-sagas-to-workflows#sagas-and-workflows` |
| Retries | Persist an attempt counter and arrange the next attempt, often through a deadline | Configure a step retry policy and backoff, or model a business retry loop explicitly | `axon-migration-sagas-to-workflows#sagas-and-workflows` |
| Compensation | Store enough state to decide which effects must be undone in later handlers | Express compensation around the relevant steps, preserving the same guards and failure handling | `axon-migration-sagas-to-workflows#sagas-and-workflows` |
:::

## Personal data in an immutable log: crypto-shredding and erasure
<!-- bullets: 8.6.f -->

With event sourcing, all data is stored as a series of immutable, undeletable events (`axon-data-protection#_about`).

Encrypting parts of the data and storing a key outside the event stream so that it can be deleted makes erasure possible again, because deleting the key effectively deletes the data (`axon-data-protection#_about`).

Changing the immutable events is another approach, but it suffers from significant drawbacks and potential operations costs (`axon-data-protection#_about`).

Axon Data Protection encrypts and decrypts individual fields of a Java object, using a key determined by the value of another field of the object (`axon-data-protection#_about`).

The GDPR became enforceable in 2018 and is an important cause of mandatory erasure (`axon-data-protection#_about`).

When encrypting, it retrieves the existing key for the value of the `@DataSubjectId` field or creates a new one if it does not exist yet (`axon-data-protection#_how_it_works`).

The `FieldEncryptingConverter` wraps any other Axon Framework `Converter` and performs encryption before converting and decryption after converting (`axon-data-protection#_how_it_works`).

## When not to use event sourcing and CQRS
<!-- bullets: 8.6.g -->

:::judgement{source="Martin Fowler, CQRS" ref="fowler-cqrs#WhenToUseIt"}
According to Martin Fowler, many systems fit a CRUD mental model and so should be done in that style. He calls CQRS a significant mental leap for all concerned, which should not be tackled unless the benefit is worth the jump. He says CQRS should only be used on specific portions of a system, a bounded context in domain-driven design, and not on the system as a whole. He sees benefits in a few complex domains, which he calls very much the minority case, and in high performance applications that scale reads and writes independently.
:::

:::judgement{source="Martin Fowler, Event Sourcing" ref="fowler-event-sourcing#when-to-use-it"}
According to Martin Fowler, packaging up every change as an event is an interface style that not everyone is comfortable with and many find awkward, so using it means you expect some form of return. He names the audit log and debugging by replaying events into a test environment as returns. He says event sourcing is the foundation for parallel models and retroactive events, and that it is very hard to retrofit those patterns onto a system that was not built with it. He warns that reader systems fed by an event stream are liable to be out of sync with the master because of differences in timing with event propagation.
:::

:::judgement{source="Martin Fowler, Event Sourcing" ref="fowler-event-sourcing#CodeChanges"}
According to Martin Fowler, rules that change over time, such as charging 10 dollars before a date and 15 dollars after it, need to go into the domain model itself, and conditional logic for them gets messy. He says that bi-temporal behavior can get very messy and he advises not to go down that path unless you really need to.
:::

## Key points

- An event-sourced entity stores no state directly; its state is rebuilt by replaying its events, and the event log is the single source of truth.
- A snapshot lets Axon initialize an entity from saved state and apply only the events that occurred after the snapshot's position.
- The consistency marker is returned when sourcing events and is attached to the append condition, so concurrent writes to the same logical boundary are detected.
- Axon routes queries by `MessageType`, and an event handler that updates an entity is a query model update.
- Axon converts a stored payload to the handler's expected type at handling time, so event handling can evolve without modifying stored events.
- A streaming processor keeps its position in a tracking token held in a token store, and it needs a claim on the token to process events.
- Each token represents a segment of the event stream; the default number of segments for a `PooledStreamingEventProcessor` is sixteen.
- A replay adjusts the token position of a streaming processor; a Subscribing Processor on the `EventBus` cannot replay.
- The `SimpleCommandBus` runs in a single JVM, and the `DistributedCommandBus` distributes commands through a `CommandBusConnector`.
- A workflow sources its state from dedicated workflow events in the regular event store, where a saga persisted fields in a `SagaStore`.
- Axon Data Protection encrypts personal fields with a key kept outside the event stream, and deleting the key effectively deletes the data.

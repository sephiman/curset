# Remote work and asynchronous communication

## Written communication, asynchronous unblocking and living documentation
<!-- bullets: 12.2.a -->

:::judgement{source="Google, eng-practices: Writing good CL descriptions" ref="eng-practices-cl-descriptions#first-line"}
According to Google's engineering practices, the first line of a change description is a short summary of what the change does, followed by a blank line. By tradition it is a complete sentence written as an order, such as "Delete the FizzBuzz RPC and replace it with the new system." The practices say it should be informative enough that readers skimming history do not need to open the change.
:::

:::judgement{source="Google, eng-practices: Writing good CL descriptions" ref="eng-practices-cl-descriptions#informative"}
According to the same page, the rest of the description fills in the details a reader needs to understand the change as a whole. It says to include enough context for reviewers and future readers, and that even small changes deserve a little attention to detail.
:::

:::judgement{source="GitLab Handbook, Asynchronous communication" ref="gitlab-communication#asynchronous-communication"}
According to the GitLab handbook, asynchronous communication is communicating and moving projects forward without needing other stakeholders to be available at the same time the message is sent. The handbook describes Slack, documents and issues as its asynchronous layer, which scales across time zones and leaves durable artifacts. It says some decisions still need a synchronous exchange, such as aligning on a strategy shift or resolving a real disagreement. In its account, an async-only habit leaves threads that fork, context that drifts and no clear record of who decided what.
:::

:::judgement{source="GitLab Handbook, Communication" ref="gitlab-communication#top-tips-and-best-practices"}
According to the GitLab handbook, people should use asynchronous communication when possible, with merge requests preferred and issues next. It says nobody is expected to be available all the time or to respond outside their planned working hours. Synchronous communication is sometimes better, such as a video call when someone is blocked, but the handbook says not to default to it. It asks people to ask questions where many can answer and benefit, in issues or public channels rather than direct messages.
:::

:::judgement{source="GitLab Handbook, Communication" ref="gitlab-communication#top-tips-and-best-practices"}
According to the same handbook page, an answer to a request should be either a deadline or a note that the work is done, because replies such as "will do" or "it is on my todo list" are not helpful. It asks for explicit needs together with an @ mention of who must act, since a CC alone may lead to no action. It also asks people to use low-context communication and to give as much context as possible, because the company is remote-only and spread around the world.
:::

:::judgement{source="GitLab Handbook, Communication" ref="gitlab-communication#start-with-a-merge-request"}
According to the GitLab handbook, a discussion is best started with a merge request instead of an issue, because a merge request is tied to a specific proposed change and is actionable. It says to submit the smallest viable and valuable change and to cross-link related issues and merge requests. It also says that when a change is accepted or rejected, the description should be updated with the final conclusion.
:::

:::judgement{source="Tom Manshreck, Software Engineering at Google, ch. 10 Documentation" ref="abseil-swe-ch10#documentation_is_like_code"}
According to Tom Manshreck, documentation is so tightly coupled to code that it should be treated as code, placed under source control and reviewed along with the code it documents. He says documents should have clear owners, because documents without owners become stale and difficult to maintain. When two documents conflict, he recommends designating a canonical document and consolidating the others into it or deprecating the duplicates. He also lists tracking issues against documents like bugs and periodically evaluating them.
:::

:::judgement{source="Tom Manshreck, Software Engineering at Google, ch. 10 Documentation" ref="abseil-swe-ch10#deprecating_documents"}
According to Tom Manshreck, old documents can cause problems as old code does. When a document no longer serves a purpose, he says to remove it or mark it obsolete and point to where the new information lives. He describes Google attaching freshness dates to documents, with email reminders when a document has not been touched for a period such as three months. He reports that adding a "Last reviewed by" byline with the owner increased adoption.
:::

## Time-zone overlap
<!-- bullets: 12.2.a -->

:::judgement{source="Google, eng-practices: Speed of Code Reviews" ref="eng-practices-speed#tz"}
According to Google's engineering practices, a reviewer working across time zones should try to answer the author while the author still has time to respond before the end of their working day. If the author has already finished for the day, the practices say the review should be done before they start the next day.
:::

:::judgement{source="Google, eng-practices: Speed of Code Reviews" ref="eng-practices-speed#responses"}
According to the same page, response time matters more than the time a change takes to get through the whole review. A reviewer who is too busy for a full review can still reply with when they will get to it, suggest other reviewers or give initial broad comments. The practices say this should be sent at a reasonable break point and not by interrupting focused work.
:::

:::judgement{source="Google, eng-practices: Speed of Code Reviews" ref="eng-practices-speed#why"}
According to the same page, slow reviews lower the velocity of the team, make developers protest the review process and put code health at risk. The practices say most complaints about code review are actually resolved by making it faster.
:::

# REST API design

## Resources and naming
<!-- bullets: 7.5.a -->

:::judgement{source="Google, API Improvement Proposals, AIP-121" ref="google-aip-121#resources"}
According to Google's AIP-121, a resource-oriented API is modelled as a resource hierarchy in which each node is either a simple resource or a collection of resources of the same type. The AIP also says that an API identical to the underlying database schema is an anti-pattern, because it tightly couples the surface to the underlying system.
:::

:::judgement{source="Google, API Improvement Proposals, AIP-121" ref="google-aip-121#methods"}
According to Google's AIP-121, a typical resource-oriented API exposes a large number of resources with a small number of methods on each, and APIs should prefer the standard methods (Get, List, Create, Update, Delete) over custom methods. A custom method does not define a new HTTP verb: it uses a traditional verb, usually `POST`, and puts the custom verb in the URI.
:::

## Idempotency keys and safe retries
<!-- bullets: 7.5.b -->

In RFC 9110, a request method is considered idempotent if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request (`rfc9110#section-9.2.2`).

Of the request methods that RFC 9110 defines, `PUT`, `DELETE` and the safe request methods are idempotent (`rfc9110#section-9.2.2`).

A server is free to log each request separately, retain a revision control history, or implement other non-idempotent side effects for each idempotent request (`rfc9110#section-9.2.2`).

Idempotent methods are distinguished because the request can be repeated automatically if a communication failure occurs before the client is able to read the server's response (`rfc9110#section-9.2.2`).

A client SHOULD NOT automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent, or some means to detect that the original request was never applied (`rfc9110#section-9.2.2`).

A proxy MUST NOT automatically retry non-idempotent requests (`rfc9110#section-9.2.2`).

A client SHOULD NOT automatically retry a failed automatic retry (`rfc9110#section-9.2.2`).

The `POST` method requests that the target resource process the representation enclosed in the request according to the resource's own specific semantics (`rfc9110#section-9.3.3`).

If a `POST` has created one or more resources, the origin server SHOULD send a `201` (Created) response containing a `Location` header field that identifies the primary resource created (`rfc9110#section-9.3.3`).

According to the IETF Idempotency-Key draft, an idempotency key is a unique value generated by the client which the resource uses to recognize subsequent retries of the same request (`ietf-httpapi-idempotency-key#content`).

In that draft the `Idempotency-Key` request header field carries the idempotency key, and its value MUST be a String (`ietf-httpapi-idempotency-key#content`).

The idempotency key MUST be unique and MUST NOT be reused with another request with a different request payload (`ietf-httpapi-idempotency-key#content`).

The draft RECOMMENDS a UUID or a similar random identifier as the idempotency key (`ietf-httpapi-idempotency-key#content`).

The resource MAY require time based idempotency keys to be able to purge or delete a key upon its expiry, and SHOULD publish its expiration policy in the documentation (`ietf-httpapi-idempotency-key#content`).

An idempotency fingerprint MAY be used with an idempotency key to determine the uniqueness of a request, and the resource generates it from request payload data (`ietf-httpapi-idempotency-key#content`).

For a first-time request, whose idempotency key and fingerprint have not been seen, the resource SHOULD process the request normally (`ietf-httpapi-idempotency-key#content`).

For a retry that arrives after the original request completed, the resource SHOULD respond consistently with the request being completed according to the user's intent (`ietf-httpapi-idempotency-key#content`).

For a concurrent request, retried before the original request completed, the resource SHOULD respond with a resource conflict error (`ietf-httpapi-idempotency-key#content`).

If the `Idempotency-Key` header is missing for a documented idempotent operation that requires it, the resource SHOULD reply with a `400` status code (`ietf-httpapi-idempotency-key#content`).

If an idempotency key is reused with a different request payload, the resource SHOULD reply with a `422` status code (`ietf-httpapi-idempotency-key#content`).

If the request is retried while the original request is still being processed, the resource SHOULD reply with a `409` status code (`ietf-httpapi-idempotency-key#content`).

## Optimistic concurrency with ETag and If-Match
<!-- bullets: 7.5.c -->

The `ETag` field in a response provides the current entity tag for the selected representation (`rfc9110#section-8.8.3`).

An entity tag is an opaque validator for differentiating between multiple representations of the same resource (`rfc9110#section-8.8.3`).

An entity tag consists of an opaque quoted string, possibly prefixed by a weakness indicator (`rfc9110#section-8.8.3`).

An entity tag can be either a weak or a strong validator, with strong being the default (`rfc9110#section-8.8.3`).

An origin server that cannot meet all the characteristics of a strong validator MUST mark the entity tag as weak by prefixing its opaque value with `W/`, which is case-sensitive (`rfc9110#section-8.8.3`).

Conditionals can be applied to state-changing methods such as `PUT` and `DELETE` to prevent the lost update problem, in which one client accidentally overwrites the work of another client acting in parallel (`rfc9110#section-13`).

The `If-Match` header field makes the request method conditional on the origin server having a current representation whose entity tag matches a member of the list of entity tags in the field value (`rfc9110#section-13.1.1`).

An origin server MUST use the strong comparison function when comparing entity tags for `If-Match` (`rfc9110#section-13.1.1`).

An origin server that evaluates an `If-Match` condition MUST NOT perform the requested method if the condition evaluates to false (`rfc9110#section-13.1.1`).

When the condition is false, the origin server MAY indicate that the conditional request failed by responding with a `412` (Precondition Failed) status code (`rfc9110#section-13.1.1`).

The `412` status code indicates that one or more conditions given in the request header fields evaluated to false when tested on the server (`rfc9110#section-15.5.13`).

:::esquema{kind=tabla title="Status codes around conditional requests"}
| Status | Meaning | Source |
|---|---|---|
| `412` | One or more conditions in the request header fields evaluated to false when tested on the server | `rfc9110#section-15.5.13` |
| `428` | The origin server requires the request to be conditional | `rfc6585#section-3` |
:::

The typical use of `428` is to avoid the lost update problem, where a client gets a resource's state, modifies it, and puts it back while a third party has modified the state on the server (`rfc6585#section-3`).

Responses with the `428` status code MUST NOT be stored by a cache (`rfc6585#section-3`).

## Pagination and links
<!-- bullets: 7.5.d -->

The `Link` header field provides a means for serialising one or more links into HTTP headers (`rfc8288#section-3`).

RFC 8288 establishes the link parameters `rel`, `anchor` and `rev`, which are part of the general link model (`rfc8288#section-3`).

A `Link` header with `rel="previous"` indicates that the target is previous to this resource in a logical navigation path (`rfc8288#section-3.5`).

One `Link` header field can carry several links separated by commas, and it is equivalent to sending each link in its own `Link` header field (`rfc8288#section-3.5`).

:::judgement{source="Google, API Improvement Proposals, AIP-158" ref="google-aip-158#guidance"}
According to Google's AIP-158, RPCs that return collections must provide pagination at the outset, because adding pagination to an existing method is a backwards-incompatible change. Request messages for collections should define an `int32` `page_size` field that is not required. If the user does not specify `page_size` or specifies 0, the API chooses a default, which it should document, and must not return an error. If the user specifies a `page_size` above the maximum, the API should coerce it down to the maximum, and for a negative value the API must send an `INVALID_ARGUMENT` error.
:::

:::judgement{source="Google, API Improvement Proposals, AIP-158" ref="google-aip-158#guidance"}
According to the same AIP, request messages for collections should also define a string `page_token` field that is not required. The user is expected to keep all other arguments the same when advancing, and if any argument differs the API should send an `INVALID_ARGUMENT` error. Response messages should define a string `next_page_token` field, which must be empty when the end of the collection has been reached. The AIP calls that the only way to communicate end-of-collection to users.
:::

:::judgement{source="Google, API Improvement Proposals, AIP-158" ref="google-aip-158#skipping-results"}
According to the same AIP, a paginated request may define an `int32` `skip` field, and its value refers to the number of individual resources to skip, not the number of pages. A request with no page token and a `skip` of 30 returns a single page starting with the 31st result. If a `skip` cannot be fulfilled, for example because of the latency of querying a massive data set, the response must be `200 OK` with an empty result set.
:::

## Problem Details
<!-- bullets: 7.5.e -->

The canonical model for problem details is a JSON object, identified with the `application/problem+json` media type (`rfc9457#section-3`).

In the RFC 9457 example, `title` gives the reason for the `403` and `instance` identifies the specific problem occurrence (`rfc9457#section-3`).

In the validation example the `errors` extension is an array whose members each hold `detail` and a `pointer` that locates the problem in the request's content with a JSON Pointer (`rfc9457#section-3`).

When an API meets several problems that do not share the same type, RFC 9457 RECOMMENDS representing the most relevant or urgent problem in the response (`rfc9457#section-3`).

If a member of a problem details object has a value type that does not match the specified type, the member MUST be ignored (`rfc9457#section-3.1`).

Problem type definitions MAY extend the problem details object with additional members that are specific to that problem type (`rfc9457#section-3.2`).

Clients consuming problem details MUST ignore any extensions that they do not recognize, which allows problem types to evolve (`rfc9457#section-3.2`).

Problem details are not a debugging tool for the underlying implementation, but a way to expose greater detail about the HTTP interface itself (`rfc9457#section-4`).

Truly generic problems, which might apply to any resource on the Web, are usually better expressed as plain status codes (`rfc9457#section-4`).

Problem details are intended to avoid the need for new fault or error document formats, not to replace existing domain-specific formats (`rfc9457#section-4`).

A new problem type definition MUST document a type URI, a title, and the HTTP status code it is used with (`rfc9457#section-4`).

A problem type definition MAY specify the use of the `Retry-After` response header in appropriate circumstances (`rfc9457#section-4`).

A problem type URI SHOULD resolve to HTML documentation that explains how to resolve the problem (`rfc9457#section-4`).

In Spring Framework, `ProblemDetail` is the representation of an RFC 9457 problem detail, a simple container for both the standard fields and non-standard ones (`spring-fw-webmvc-ann-rest-exceptions#page-title`).

`ErrorResponse` is the contract to expose HTTP error response details, including the status, the response headers and a body in the RFC 9457 format, and all Spring MVC exceptions implement it (`spring-fw-webmvc-ann-rest-exceptions#page-title`).

`ErrorResponseException` is a basic `ErrorResponse` implementation that others can use as a convenient base class (`spring-fw-webmvc-ann-rest-exceptions#page-title`).

`ResponseEntityExceptionHandler` is a convenient base class for a `@ControllerAdvice` that handles all Spring MVC exceptions and any `ErrorResponseException`, and renders an error response with a body (`spring-fw-webmvc-ann-rest-exceptions#page-title`).

You can extend an RFC 9457 response with non-standard fields by inserting them into the `properties` map of `ProblemDetail`, or by extending `ProblemDetail` to add dedicated properties (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-non-standard`).

In Spring Boot, the `spring.mvc.problemdetails.enabled` property autoconfigures a `ResponseEntityExceptionHandler` that handles built-in exceptions with problem details (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-non-standard`).

## Long-running operations and webhooks
<!-- bullets: 7.5.f -->

The `202` (Accepted) status code indicates that the request has been accepted for processing, but the processing has not been completed (`rfc9110#section-15.3.3`).

A request answered with `202` might or might not eventually be acted upon, as it might be disallowed when processing actually takes place (`rfc9110#section-15.3.3`).

HTTP has no facility for re-sending a status code from an asynchronous operation (`rfc9110#section-15.3.3`).

A `202` lets a server accept a request for some other process without requiring that the user agent's connection persist until the process is completed (`rfc9110#section-15.3.3`).

The representation sent with `202` ought to describe the request's current status and point to a status monitor that can estimate when the request will be fulfilled (`rfc9110#section-15.3.3`).

In OpenAPI, the `webhooks` field holds incoming webhooks that the API may send and that the API consumer MAY choose to implement (`openapi-spec#x4-1-1-fixed-fields`).

:::judgement{source="Standard Webhooks, Standard Webhooks specification" ref="standard-webhooks-spec#untitled"}
According to the Standard Webhooks specification, the most common way to verify the authenticity of webhooks is an HMAC signature with a pre-shared secret key, and a common alternative is an asymmetric signature. The specification signs the message ID, the timestamp and the body, concatenated and delimited by full-stops as `msg_id.timestamp.payload`. The ID, the timestamp and the signature travel in the `webhook-id`, `webhook-timestamp` and `webhook-signature` headers of the HTTP POST request, and the payload is the body. The signature header is a space-delimited list so that secrets can be rotated with zero downtime.
:::

:::judgement{source="Standard Webhooks, Standard Webhooks specification" ref="standard-webhooks-spec#untitled"}
According to the same specification, a consumer verifying a symmetric signature should compare it in constant time, should check that `webhook-timestamp` is within some tolerance of the current time to prevent replay attacks, and should use `webhook-id` as an idempotency key so that the same webhook is not processed twice.
:::

:::judgement{source="Standard Webhooks, Standard Webhooks specification" ref="standard-webhooks-spec#untitled"}
According to the same specification, the producer retries a failed delivery until a successful attempt or until delivery appears impossible. It recommends a retry schedule spanning multiple days with an exponential backoff and some random jitter. A delivery is successful when the response has a `2xx` status code, and a `410 Gone` response tells the sender to disable the endpoint. The specification recommends a request timeout between 15 and 30 seconds.
:::

## Rate limiting seen by the client
<!-- bullets: 7.5.g -->

The `429` status code indicates that the user has sent too many requests in a given amount of time (`rfc6585#section-4`).

A `429` response SHOULD include details explaining the condition, and MAY include a `Retry-After` header indicating how long to wait before making a new request (`rfc6585#section-4`).

RFC 6585 does not define how the origin server identifies the user or how it counts requests (`rfc6585#section-4`).

Responses with the `429` status code MUST NOT be stored by a cache (`rfc6585#section-4`).

Servers send the `Retry-After` header field to indicate how long the user agent ought to wait before making a follow-up request (`rfc9110#section-10.2.3`).

The `Retry-After` value can be either an HTTP-date or a number of seconds to delay after receiving the response (`rfc9110#section-10.2.3`).

A `delay-seconds` value is a non-negative decimal integer, representing time in seconds (`rfc9110#section-10.2.3`).

The IETF RateLimit draft defines `RateLimit-Policy`, a quota policy defined by the server that client requests will consume, and `RateLimit`, the quota currently available under a specific policy (`ietf-httpapi-ratelimit-headers#content`).

In a quota policy item the `q` parameter is REQUIRED and indicates the quota allocated by the policy, measured in quota units (`ietf-httpapi-ratelimit-headers#content`).

The default quota unit of a quota policy item is `requests` (`ietf-httpapi-ratelimit-headers#content`).

In a service limit item the `r` parameter is REQUIRED and conveys the available quota under the identified policy (`ietf-httpapi-ratelimit-headers#content`).

In a service limit item the `t` parameter conveys the effective window, the time within which the client can use no more than the available quota (`ietf-httpapi-ratelimit-headers#content`).

Clients MUST NOT assume that a positive available quota is a guarantee that further requests will be served (`ietf-httpapi-ratelimit-headers#content`).

The client MUST NOT assume that all its service limit will be fully restored after the time indicated by the effective window parameter (`ietf-httpapi-ratelimit-headers#content`).

The server MAY arbitrarily alter the available quota and effective window between subsequent requests (`ietf-httpapi-ratelimit-headers#content`).

If a response contains both `Retry-After` and `RateLimit`, the `Retry-After` value SHOULD NOT reference a point in time earlier than the end of the effective window (`ietf-httpapi-ratelimit-headers#content`).

The draft says that conveyed quota hints do not imply any service guarantee, and that the server is free to throttle clients that adhere to its recommended limits under certain circumstances (`ietf-httpapi-ratelimit-headers#content`).

## OpenAPI descriptions
<!-- bullets: 7.5.h -->

The OpenAPI Specification defines a standard, language-agnostic interface to HTTP APIs which lets humans and computers understand the capabilities of the service without access to source code, documentation or network traffic inspection (`openapi-spec#x2-introduction`).

An OpenAPI Description can be used by documentation generation tools to display the API and by code generation tools to generate servers and clients in various programming languages (`openapi-spec#x2-introduction`).

In an OpenAPI document the `openapi` field and the `info` field are REQUIRED, and at least one of `components`, `paths` or `webhooks` MUST be present (`openapi-spec#x4-1-1-fixed-fields`).

The `openapi` field holds the version number of the OpenAPI Specification that the document uses, and it is not related to the `info.version` string (`openapi-spec#x4-1-1-fixed-fields`).

If the `servers` field is not provided or is an empty array, the default is a single Server Object with a `url` value of `/` (`openapi-spec#x4-1-1-fixed-fields`).

A Path Item Object has one Operation Object field for each of the methods `get`, `put`, `post`, `delete`, `options`, `head`, `patch`, `trace` and `query` (`openapi-spec#x4-9-1-fixed-fields`).

The `operationId` of an operation MUST be unique among all operations described in the API, and its value is case-sensitive (`openapi-spec#x4-10-1-fixed-fields`).

For `GET` and `DELETE`, where the HTTP specification discourages message content, `requestBody` is permitted but has no well-defined semantics and SHOULD be avoided if possible (`openapi-spec#x4-10-1-fixed-fields`).

The `deprecated` field declares an operation to be deprecated, and consumers SHOULD refrain from using it (`openapi-spec#x4-10-1-fixed-fields`).

A unique parameter is defined by a combination of a name and a location (`openapi-spec#x4-10-1-fixed-fields`).

OpenAPI defines five parameter locations in the `in` field: `path`, `query`, `querystring`, `header` and `cookie` (`openapi-spec#x4-12-1-parameter-locations`).

The `querystring` location treats the entire URL query string as a value that MUST be specified using the `content` field (`openapi-spec#x4-12-1-parameter-locations`).

:::judgement{source="OpenAPI Initiative, OpenAPI best practices" ref="openapi-learn-best-practices#use-a-design-first-approach"}
According to the OpenAPI Initiative, in the code-first approach the API is implemented first and its description is created from the code, while in the design-first approach the API description is written first and the code follows. The OpenAPI Initiative says that, in its opinion, the importance of design-first cannot be stressed strongly enough. Its reason is that more APIs can be created in code than OpenAPI can describe, so an API built first in code may have to be changed, or its description twisted, to fit what OpenAPI can express.
:::

## Key points

- A method is idempotent when multiple identical requests have the same intended effect on the server as a single one, and a client SHOULD NOT automatically retry a non-idempotent request without a way to know it is safe (`rfc9110#section-9.2.2`).
- An idempotency key is a unique value generated by the client, sent in the `Idempotency-Key` header, which the resource uses to recognize retries of the same request (`ietf-httpapi-idempotency-key#content`).
- `If-Match` makes a state-changing request conditional on a matching entity tag, and a false condition means the method is not performed and a `412` MAY be returned (`rfc9110#section-13.1.1`).
- `428` means the server requires the request to be conditional, to avoid the lost update problem (`rfc6585#section-3`).
- A `Link` header field serialises one or more links into HTTP headers (`rfc8288#section-3`).
- A problem details object is JSON with the `application/problem+json` media type, and clients MUST ignore extension members they do not recognize (`rfc9457#section-3`; `rfc9457#section-3.2`).
- `ProblemDetail` represents an RFC 9457 problem detail in Spring Framework, and `ResponseEntityExceptionHandler` renders error responses for Spring MVC exceptions (`spring-fw-webmvc-ann-rest-exceptions#page-title`).
- `202` means the request was accepted for processing, but the processing has not been completed (`rfc9110#section-15.3.3`).
- `429` means too many requests in a given amount of time, and `Retry-After` is an HTTP-date or a number of seconds (`rfc6585#section-4`; `rfc9110#section-10.2.3`).
- A positive available quota in `RateLimit` is not a guarantee that further requests will be served (`ietf-httpapi-ratelimit-headers#content`).
- An OpenAPI document needs `openapi` and `info`, and at least one of `components`, `paths` or `webhooks` (`openapi-spec#x4-1-1-fixed-fields`).

# Refactoring legacy code and reviewing AI-generated changes

## Resource leaks and exception handling
<!-- bullets: 11.2.a -->

An `AutoCloseable` object may hold resources, such as file or socket handles, until it is closed (`javadoc-autocloseable#interface-autocloseable`).

The `close()` method of an `AutoCloseable` object is called automatically when exiting a try-with-resources block for which the object has been declared in the resource specification header (`javadoc-autocloseable#interface-autocloseable`).

Try-with-resources ensures prompt release, which avoids the resource exhaustion exceptions and errors that may otherwise occur (`javadoc-autocloseable#interface-autocloseable`).

For facilities such as `Stream` that support both I/O-based and non-I/O-based forms, try-with-resources blocks are in general unnecessary with the non-I/O-based forms (`javadoc-autocloseable#interface-autocloseable`).

Over time, a throwable can suppress other throwables from being propagated (`javadoc-throwable#class-throwable`).

The snippet calls `close()` by hand after a query that throws, and then runs the same query inside a try-with-resources block whose `close()` also throws.

```java snippet=m11-l02/ResourceLeak.java
public class ResourceLeak {
    static class Connection implements AutoCloseable {
        private final String name;

        Connection(String name) {
            this.name = name;
            System.out.println("open " + name);
        }

        void query() {
            throw new IllegalStateException("query failed on " + name);
        }

        @Override
        public void close() {
            System.out.println("close " + name);
            throw new IllegalArgumentException("close failed on " + name);
        }
    }

    public static void main(String[] args) {
        try {
            Connection leaked = new Connection("manual");
            leaked.query();
            leaked.close();
        } catch (IllegalStateException e) {
            System.out.println("manual: " + e.getMessage());
        }

        try (Connection pooled = new Connection("resource")) {
            pooled.query();
        } catch (IllegalStateException e) {
            System.out.println("resource: " + e.getMessage());
            System.out.println("suppressed: " + e.getSuppressed()[0].getMessage());
        }
    }
}
```

The snippet prints `open manual` and `manual: query failed on manual`, and never prints `close manual`, because the exception skips the `close()` call.

It prints `close resource` for the try-with-resources block, because the block closes the resource when the body throws.

It prints `resource: query failed on resource` for the exception that reaches the `catch` clause, and `suppressed: close failed on resource` for the exception from `close()`.

The `Throwable` class is the superclass of all errors and exceptions in the Java language (`javadoc-throwable#class-throwable`).

For compile-time checking, `Throwable` and any subclass that is not also a subclass of `RuntimeException` or `Error` are regarded as checked exceptions (`javadoc-throwable#class-throwable`).

A throwable contains a snapshot of the execution stack of its thread at the time it was created (`javadoc-throwable#class-throwable`).

A throwable can also contain a cause: another throwable that caused it to be constructed (`javadoc-throwable#class-throwable`).

A cause can be associated with a throwable through a constructor that takes the cause as an argument, or through the `initCause(Throwable)` method (`javadoc-throwable#class-throwable`).

Letting the throwable of a lower layer propagate outward would be bad design, because it is generally unrelated to the abstraction of the upper layer (`javadoc-throwable#class-throwable`).

Letting a checked exception of the lower layer propagate would tie the API of the upper layer to the details of its implementation (`javadoc-throwable#class-throwable`).

A wrapped exception, one that contains a cause, lets the upper layer communicate the details of a failure to its caller without those shortcomings (`javadoc-throwable#class-throwable`).

The snippet catches an `IOException` twice and rethrows an `IllegalStateException`, once without the cause and once with it.

```java snippet=m11-l02/ExceptionCause.java
import java.io.IOException;

public class ExceptionCause {
    static void load() throws IOException {
        throw new IOException("disk full");
    }

    static void swallowsCause() {
        try {
            load();
        } catch (IOException e) {
            throw new IllegalStateException("load failed");
        }
    }

    static void keepsCause() {
        try {
            load();
        } catch (IOException e) {
            throw new IllegalStateException("load failed", e);
        }
    }

    static String describe(Throwable cause) {
        return cause == null ? "no cause" : cause.getMessage();
    }

    public static void main(String[] args) {
        try {
            swallowsCause();
        } catch (IllegalStateException e) {
            System.out.println("swallowed: " + describe(e.getCause()));
        }
        try {
            keepsCause();
        } catch (IllegalStateException e) {
            System.out.println("kept: " + describe(e.getCause()));
        }
    }
}
```

The snippet prints `swallowed: no cause`, because the exception thrown without the cause has no cause.

It prints `kept: disk full`, the message of the `IOException`, because the cause was passed to the constructor.

## Concurrency errors
<!-- bullets: 11.2.a -->

The results of a write by one thread are guaranteed to be visible to a read by another thread only if the write operation happens-before the read operation (`javadoc-concurrent-package#MemoryVisibility`).

The `synchronized` and `volatile` constructs, as well as `Thread.start()` and `Thread.join()`, can form happens-before relationships (`javadoc-concurrent-package#MemoryVisibility`).

An unlock of a monitor happens-before every subsequent lock of that same monitor (`javadoc-concurrent-package#MemoryVisibility`).

A write to a `volatile` field happens-before every subsequent read of that same field (`javadoc-concurrent-package#MemoryVisibility`).

A call to `start` on a thread happens-before any action in the started thread (`javadoc-concurrent-package#MemoryVisibility`).

All actions in a thread happen-before any other thread successfully returns from a `join` on that thread (`javadoc-concurrent-package#MemoryVisibility`).

Actions in a thread before it places an object into a concurrent collection happen-before the actions that follow the access or removal of that element in another thread (`javadoc-concurrent-package#MemoryVisibility`).

A program that contains two conflicting accesses not ordered by a happens-before relationship is said to contain a data race (`jls-17#jls-17.4.5`).

Writes in one thread that are in a data race with reads in another thread may appear to occur out of order to those reads (`jls-17#jls-17.4.5`).

A program is correctly synchronized if and only if all sequentially consistent executions are free of data races (`jls-17#jls-17.4.5`).

The snippet runs two threads that both insert the same key into a `ConcurrentHashMap`, once with a `containsKey` check followed by `put`, once with `putIfAbsent`. A barrier makes both threads reach the insert together. It then reads a value written by a thread that was joined.

```java snippet=m11-l02/ConcurrencyChecks.java
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CyclicBarrier;
import java.util.concurrent.atomic.AtomicInteger;

public class ConcurrencyChecks {
    interface Insert {
        boolean insertIfAbsent(Map<String, String> map, CyclicBarrier barrier) throws Exception;
    }

    static int inserts(Insert strategy) throws Exception {
        Map<String, String> map = new ConcurrentHashMap<>();
        CyclicBarrier barrier = new CyclicBarrier(2);
        AtomicInteger inserted = new AtomicInteger();
        Runnable task = () -> {
            try {
                if (strategy.insertIfAbsent(map, barrier)) {
                    inserted.incrementAndGet();
                }
            } catch (Exception e) {
                throw new IllegalStateException(e);
            }
        };
        Thread first = new Thread(task);
        Thread second = new Thread(task);
        first.start();
        second.start();
        first.join();
        second.join();
        return inserted.get();
    }

    public static void main(String[] args) throws Exception {
        System.out.println("check then act: " + inserts((map, barrier) -> {
            boolean absent = !map.containsKey("key");
            barrier.await();
            if (absent) {
                map.put("key", "value");
            }
            return absent;
        }));
        System.out.println("atomic insert: " + inserts((map, barrier) -> {
            barrier.await();
            return map.putIfAbsent("key", "value") == null;
        }));

        int[] box = new int[1];
        Thread writer = new Thread(() -> box[0] = 42);
        writer.start();
        writer.join();
        System.out.println("after join: " + box[0]);
    }
}
```

The snippet prints `check then act: 2`, because both threads saw the key absent before either one inserted it.

It prints `atomic insert: 1` for `putIfAbsent`, because only one thread inserts the key.

It prints `after join: 42`, because the write of the joined thread is visible to the thread that joined it.

## Code smells and what a review looks for
<!-- bullets: 11.2.a -->

:::judgement{source="Martin Fowler, CodeSmell, martinfowler.com" ref="fowler-code-smell#banner"}
According to Martin Fowler, a code smell is a surface indication that usually corresponds to a deeper problem in the system. He writes that smells do not always indicate a problem: they are often an indicator of a problem rather than the problem itself.
:::

:::judgement{source="Google, Engineering Practices: What to look for in a code review" ref="google-eng-practices-looking-for#design"}
According to Google's engineering practices, the most important thing to cover in a review is the overall design of the change: whether the interactions of the pieces of code make sense and whether the change belongs in the codebase or in a library.
:::

:::judgement{source="Google, Engineering Practices: What to look for in a code review" ref="google-eng-practices-looking-for#complexity"}
According to the same page, "too complex" usually means "can't be understood quickly by code readers", and over-engineering is a particular type of complexity that reviewers should watch for especially.
:::

## Money, overflow and time
<!-- bullets: 11.2.b -->

`BigDecimal` is an immutable, arbitrary-precision signed decimal number (`javadoc-bigdecimal#class-bigdecimal`).

If no rounding mode is specified and the exact result cannot be represented, `BigDecimal` throws an `ArithmeticException` (`javadoc-bigdecimal#class-bigdecimal`).

If the quotient of a division has a nonterminating decimal expansion and the operation is specified to return an exact result, `BigDecimal` throws an `ArithmeticException` (`javadoc-bigdecimal#class-bigdecimal`).

The `equals` method of `BigDecimal` requires both the numerical value and the representation to be the same (`javadoc-bigdecimal#class-bigdecimal`).

:::esquema{kind=tabla title="Preferred scale of the result of a `BigDecimal` operation"}
| Operation | Preferred scale of the result | Source |
|---|---|---|
| Add | `max(addend.scale(), augend.scale())` | `javadoc-bigdecimal#class-bigdecimal` |
| Subtract | `max(minuend.scale(), subtrahend.scale())` | `javadoc-bigdecimal#class-bigdecimal` |
| Multiply | `multiplier.scale() + multiplicand.scale()` | `javadoc-bigdecimal#class-bigdecimal` |
| Divide | `dividend.scale() - divisor.scale()` | `javadoc-bigdecimal#class-bigdecimal` |
:::

The snippet adds `0.1` and `0.2` as `double` and as `BigDecimal`, multiplies two `BigDecimal` values, divides one by three exactly, and splits `100.00` into three shares rounded to two places.

```java snippet=m11-l02/MoneyMath.java
import java.math.BigDecimal;
import java.math.RoundingMode;

public class MoneyMath {
    public static void main(String[] args) {
        System.out.println(0.1 + 0.2);
        System.out.println(new BigDecimal("0.1").add(new BigDecimal("0.2")));
        System.out.println(new BigDecimal("1.10").multiply(new BigDecimal("2.0")));
        try {
            BigDecimal.ONE.divide(new BigDecimal("3"));
        } catch (ArithmeticException e) {
            System.out.println(e.getMessage());
        }
        BigDecimal share = new BigDecimal("100.00").divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP);
        System.out.println(share);
        System.out.println(share.multiply(new BigDecimal("3")));
    }
}
```

The snippet prints `0.30000000000000004` for `0.1 + 0.2` as `double`.

It prints `0.3` for the sum of `BigDecimal` values built from the strings `"0.1"` and `"0.2"`.

It prints `2.200` for `1.10` times `2.0`, because the scales 2 and 1 add up to 3.

It prints `Non-terminating decimal expansion; no exact representable decimal result.` for the exact division of 1 by 3.

It prints `33.33` for one share of `100.00` divided by 3 with scale 2 and `HALF_UP`, and `99.99` for the three shares together, one cent short.

`Math.addExact(int, int)` returns the sum of its arguments and throws an exception if the result overflows an `int` (`javadoc-math#addExact(int,int)`).

`Math.addExact(int, int)` throws `ArithmeticException` if the result overflows an `int` (`javadoc-math#addExact(int,int)`).

The snippet adds 1 to `Integer.MAX_VALUE` with `+` and with `Math.addExact`, and multiplies 1,000,000 by 5,000 as `int` and as `long`.

```java snippet=m11-l02/OverflowCheck.java
public class OverflowCheck {
    public static void main(String[] args) {
        int top = Integer.MAX_VALUE;
        System.out.println(top + 1);
        try {
            Math.addExact(top, 1);
        } catch (ArithmeticException e) {
            System.out.println(e.getMessage());
        }
        long wrong = 1_000_000 * 5_000;
        long right = 1_000_000L * 5_000;
        System.out.println(wrong);
        System.out.println(right);
    }
}
```

The snippet prints `-2147483648` for `Integer.MAX_VALUE + 1`.

It prints `integer overflow` for the `ArithmeticException` from `Math.addExact`.

It prints `705032704` for `1_000_000 * 5_000`, because the product is computed as `int` before it is assigned to a `long`.

It prints `5000000000` for `1_000_000L * 5_000`.

`ZonedDateTime` is an immutable representation of a date-time with a time-zone (`javadoc-zoneddatetime#class-zoneddatetime`).

Obtaining the offset for an instant is simple, because there is exactly one valid offset for each instant (`javadoc-zoneddatetime#class-zoneddatetime`).

In a gap, there are local date-time values with no valid offset (`javadoc-zoneddatetime#class-zoneddatetime`).

In an overlap, there are local date-time values with two valid offsets (`javadoc-zoneddatetime#class-zoneddatetime`).

If a local date-time falls in the middle of a gap, the zoned date-time has a local date-time shifted forwards by the length of the gap, in the later offset (`javadoc-zoneddatetime#class-zoneddatetime`).

If a local date-time falls in the middle of an overlap, the previous offset is retained (`javadoc-zoneddatetime#class-zoneddatetime`).

`withEarlierOffsetAtOverlap()` and `withLaterOffsetAtOverlap()` help manage the case of an overlap (`javadoc-zoneddatetime#class-zoneddatetime`).

The snippet builds `Europe/Paris` date-times for the spring gap of 29 March 2026 and the autumn overlap of 25 October 2026. It adds one day and 24 hours to noon on 28 March 2026.

```java snippet=m11-l02/ZoneTransitions.java
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class ZoneTransitions {
    public static void main(String[] args) {
        ZoneId paris = ZoneId.of("Europe/Paris");

        System.out.println(ZonedDateTime.of(LocalDateTime.of(2026, 3, 29, 2, 30), paris));

        ZonedDateTime overlap = ZonedDateTime.of(LocalDateTime.of(2026, 10, 25, 2, 30), paris);
        System.out.println(overlap);
        System.out.println(overlap.withLaterOffsetAtOverlap());

        ZonedDateTime saturday = ZonedDateTime.of(LocalDateTime.of(2026, 3, 28, 12, 0), paris);
        System.out.println(saturday.plusDays(1));
        System.out.println(saturday.plusHours(24));
    }
}
```

The snippet prints `2026-03-29T03:30+02:00[Europe/Paris]` for 02:30 on 29 March 2026, a time inside the gap.

It prints `2026-10-25T02:30+02:00[Europe/Paris]` for 02:30 on 25 October 2026, a time inside the overlap, and `2026-10-25T02:30+01:00[Europe/Paris]` after `withLaterOffsetAtOverlap()`.

It prints `2026-03-29T12:00+02:00[Europe/Paris]` for `plusDays(1)` and `2026-03-29T13:00+02:00[Europe/Paris]` for `plusHours(24)` on noon of 28 March 2026.

The primary purpose of the `Clock` abstraction is to allow alternate clocks to be plugged in as and when required (`javadoc-clock#class-clock`).

Applications that use an object to obtain the current time, rather than a static method, can simplify testing (`javadoc-clock#class-clock`).

Best practice for applications is to pass a `Clock` into any method that requires the current instant and time-zone (`javadoc-clock#class-clock`).

Passing a `Clock` allows an alternative clock, such as fixed or offset, to be used during testing (`javadoc-clock#class-clock`).

All implementations of `Clock` must be thread-safe (`javadoc-clock#class-clock`).

The snippet checks a token that expires after 15 minutes against a fixed clock at the boundary and one second later. It then reads the date of one instant through a `Clock` in UTC and one in `Asia/Tokyo`.

```java snippet=m11-l02/FixedClock.java
import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.time.LocalDate;
import java.time.ZoneId;
import java.time.ZoneOffset;

public class FixedClock {
    static boolean expired(Instant issuedAt, Clock clock) {
        return issuedAt.plus(Duration.ofMinutes(15)).isBefore(clock.instant());
    }

    public static void main(String[] args) {
        Instant issuedAt = Instant.parse("2026-01-01T00:00:00Z");
        Clock atBoundary = Clock.fixed(Instant.parse("2026-01-01T00:15:00Z"), ZoneOffset.UTC);
        Clock aSecondLater = Clock.offset(atBoundary, Duration.ofSeconds(1));
        System.out.println(expired(issuedAt, atBoundary));
        System.out.println(expired(issuedAt, aSecondLater));

        Instant lateEvening = Instant.parse("2026-01-01T23:30:00Z");
        System.out.println(LocalDate.now(Clock.fixed(lateEvening, ZoneOffset.UTC)));
        System.out.println(LocalDate.now(Clock.fixed(lateEvening, ZoneId.of("Asia/Tokyo"))));
    }
}
```

The snippet prints `false` when the fixed clock stands exactly 15 minutes after issue, and `true` one second later.

It prints `2026-01-01` for the instant `2026-01-01T23:30:00Z` through a UTC clock, and `2026-01-02` through an `Asia/Tokyo` clock.

## Transaction leaks
<!-- bullets: 11.2.b -->

The `@Transactional` annotation is merely metadata that runtime infrastructure consumes to configure beans with transactional behavior (`spring-fw-tx-declarative-annotations#using-transactional`).

The mere presence of the `@Transactional` annotation is not enough to activate the transactional behavior (`spring-fw-tx-declarative-annotations#using-transactional`).

In proxy mode, which is the default, only external method calls coming in through the proxy are intercepted (`spring-fw-tx-declarative-annotations#using-transactional`).

Self-invocation does not lead to an actual transaction at runtime in proxy mode, even if the invoked method is marked with `@Transactional` (`spring-fw-tx-declarative-annotations#using-transactional`).

The proxy must be fully initialized to provide the expected behavior, so the transactional feature should not be relied on in initialization code such as a `@PostConstruct` method (`spring-fw-tx-declarative-annotations#using-transactional`).

AspectJ mode is an option if self-invocations are expected to be wrapped with transactions as well (`spring-fw-tx-declarative-annotations#using-transactional`).

Interface-declared annotations are not recognized by the weaving infrastructure in AspectJ mode, because Java annotations are not inherited from interfaces (`spring-fw-tx-declarative-annotations#using-transactional`).

Transaction annotations may be silently ignored, and the code might appear to work until a rollback scenario is tested (`spring-fw-tx-declarative-annotations#using-transactional`).

`DataSourceUtils.getConnection` returns the connection already synchronized to an existing transaction (`spring-fw-tx-tx-resource-synchronization#tx-resource-synchronization-low`).

Otherwise, `DataSourceUtils.getConnection` creates a new connection, optionally synchronizes it to any existing transaction, and makes it available for reuse in that same transaction (`spring-fw-tx-tx-resource-synchronization#tx-resource-synchronization-low`).

## Key points

- A resource closed by hand is skipped when an earlier statement throws; try-with-resources closes it, and an exception from `close()` becomes a suppressed exception.
- A cause passed to the constructor of a wrapping exception is kept; leaving it out loses the original failure.
- A write is guaranteed to be visible to a read in another thread only if it happens-before the read; `volatile`, monitors, `start`, `join` and concurrent collections can form such edges.
- A check followed by an insert is two steps even on a concurrent map; `putIfAbsent` is one.
- `BigDecimal` division without a rounding rule throws when the quotient does not terminate, and `equals` compares scale as well as value.
- `int` arithmetic overflows silently with `+` and `*`; `Math.addExact` throws `ArithmeticException`.
- A local date-time in a gap moves forward by the length of the gap, and one in an overlap keeps the previous offset.
- Passing a `Clock` makes time-dependent code testable with fixed or offset clocks.
- In proxy mode, a self-invoked `@Transactional` method starts no transaction, and the proxy is not ready in `@PostConstruct`.

# Requirements — Curset, the multi-course web platform (today TradeSchool)

Version 1.0 · 4 October 2026 · requirements, not design. Web only (backend + SPA). The Android app is out of scope: it is the crypto-futures course and will stay that.

## 1. Goal

The web goes from one course (`crypto-futures`) to several, on unrelated subjects: the two new courses prepare candidates for Spanish civil-service exams (oposiciones). "TradeSchool" therefore stops describing the web: the platform is renamed **Curset** (section 2). Users choose which courses are active for them and, among the active ones, which one they are viewing. Everything that is "the course's" today (lessons, glossary, exams, progress, PDF) becomes "the selected course's". The new courses exist only in Spanish, so a course may not be available in the user's language and the web must handle that without an empty screen. Nothing changes in what a course teaches or in how exercises are generated, graded or measured.

## 2. Platform name

- R2.1 The platform is called **Curset**: one word, from "curso", identical in Spanish and English, naming no subject. This document fixes where it appears and what does not change.
- R2.2 It appears in: the header wordmark and the auth card, the browser tab title, settings and sign-up copy, the "no course" page, the PDF footer and the PDF filename (`curset-<slug>-<lang>-<date>.pdf`), the README and user-facing docs.
- R2.3 It does not change: internal identifiers (packages, Python and TypeScript module names, tables, cookies, environment variables, script names), slugs, i18n keys, API URLs. Renaming code is a separate change, if ever, and does not gate this version.
- R2.4 "TradeSchool" remains the Android app's name and may remain the title or subtitle of the `crypto-futures` course inside the web; it is a course name, not a platform name.
- R2.5 Domain and repository: outside this document. If they change, old URLs redirect.
- R2.6 Written "Curset", capital C, in all copy; the wordmark's case is decided by the identity work (2a). Never translated or inflected.

### 2a. Visual identity (generated by Claude Code)

- R2a.1 The identity is generated inside the repository as SVG files, in its own Claude Code round, from this document. No external images, no non-free typefaces, nothing resembling an existing brand. Typefaces are free (Google Fonts or OFL) and declared by name in a single identity file.
- R2a.2 Platform pieces: mark (symbol only), wordmark (name), lockup (symbol + name, horizontal and stacked), favicon (16/32/180/512 and SVG), and a monochrome variant of each. Every piece in light and dark variants; the mark works in one colour.
- R2a.3 Per-course pieces: each course declares in its `course.yaml` a `glyph` (the name of an SVG under `content/<slug>/identity/`) and an accent `color`. The glyph is a simple stroke symbol, legible at 24 px, representing the subject without text: a candlestick for `crypto-futures`; a symbol of its own for each oposiciones course once its syllabus exists. Glyphs share stroke weight, bounding box and corner radius with the platform mark so the dropdown and settings read as one family.
- R2a.4 Where each piece appears: lockup in the header and the auth card; mark alone as favicon and in the browser tab; glyph + course title in the dropdown, in settings, at sign-up and in the course header; platform mark on the PDF cover with the course glyph beside the course title; PDF footer with the monochrome wordmark.
- R2a.5 Colour: one ink and one paper for the platform, one accent per course. Course accents have similar lightness so no course looks like "the main one", and each passes 4.5:1 against paper and against ink as text, or is used only as a fill with ink text on top. The existing light, dark and OLED themes receive the colours through tokens; no SVG carries fixed colours except the monochrome variants, which use `currentColor`.
- R2a.6 CI checks: every SVG is valid, has a `viewBox`, no `<script>`, no external references, and is under 20 KB; favicon PNGs are generated from the SVG and never hand-edited; the glyph each course declares exists; each accent's contrast is tested against ink and paper.
- R2a.7 Deliverables of that round: the SVGs, the identity file (name, typefaces, colour tokens), a dev-gallery page (`/dev/identity`) showing every piece in the three themes, and a ten-line decisions doc in `docs/`. Rejected directions are not kept.

## 3. What a course is

- R3.1 A course is a complete, independent unit of content: its own `course.yaml`, language trees, figures, exercises, glossary and figure/prose coupling. Nothing is shared between courses: no glossary, no lessons, no exercises.
- R3.2 Identity: a permanent `slug`, chosen once and never renamed, in the same stable-identifier namespace modules, lessons and glossary already use. `crypto-futures` exists today. New courses get their slug when their `course.yaml` is created; their syllabi are defined in a separate requirements document.
- R3.3 Each course declares title, subtitle and summary per language, the list of **available languages** (`languages: [es]` or `[es, en]`) and a status (`draft` / `published`). A `draft` course exists for the team (it can be verified) but is not offered to users.
- R3.4 A course's internal identifiers (m01, m01-l1, g-funding, fig-…) are unique only inside that course. Every reference to a module, lesson, term or figure implies its course.
- R3.5 Authoring rules apply per course and per the languages it declares: never-coins in glossary and summaries, no invented vocabulary (`CLAUDE.md`), the style guide `docs/prose-voice.md`, its own goldens and fingerprints. ES/EN parity (counts, lists, glossary) is required only of two-language courses; a Spanish-only course has no `en/` tree and no test may expect one.
- R3.6 All courses live in the same repository, `content/<slug>/…`, with the same structure. The pipeline (registry, checks, export, PDF) is common to all courses; there are no per-course branches.
- R3.7 A course declares which exercise kinds it uses. The oposiciones courses use only multiple-choice test questions, as in the official exam (the five existing quiz sub-kinds), with no generated calculations or charts. A course without figures has no `figure-coupling.yaml`, no `figures.tsv` and no generation fingerprints, and every pipeline step that works on figures or generators (PDF figure capture, figure/prose coupling, generation goldens, numeric stability) skips that course explicitly and records it as "no figures", never as a failure or an empty result. Guards that apply to any course (never-coins, block inventory, list shape, answer bias, cross-references, exercise/answer-key bijection in the PDF) apply to all.
- R3.8 The PDF of a course without figures has no capture phase and its generation time reflects that; the generation report lists no figures.

## 4. Course language vs. user language

- R4.1 The interface language remains the account's (ES ↔ EN), as today.
- R4.2 Each course is read in a **reading language** chosen among those the course declares. If the account language is available it is the default reading language. If not, the course is read in its only language (or the first it declares), and the web says so.
- R4.3 The header's ES ↔ EN switch keeps changing the account language and, if the course being viewed has that language, its reading language too (as today). If the course does not have it, the interface changes and the reading language stays where it was; the course header says so ("Spanish only").
- R4.3b In addition, a course with two or more languages has its own reading-language selector in the course header, to read it in a language other than the interface's. The choice is remembered per user and per course.
- R4.4 A single-language course shows no reading-language selector. The catalogue, settings and the course header show which languages a course is available in ("Spanish only" when the account is in English).
- R4.5 Everything that depends on the content language (lessons, glossary, exams, summaries, PDF, theory export) uses the course's reading language. Everything that is interface (menus, tabs, the "no course" page, settings, answer labels) uses the account language. If a Spanish-only course has generated answer labels, they must exist in Spanish; interface i18n keys still require both languages.
- R4.6 Requesting a course in a language it does not declare (`?lang=en` on a Spanish-only course, PDF URL, export) returns a clear error naming the available languages, never the other language's content and never an empty response.
- R4.7 Progress, attempts and exams do not depend on the reading language (already true).

## 5. Active courses (settings)

- R5.1 Settings has a "Courses" section listing published courses in alphabetical order by title in the account language, each with title, summary, available languages and an enable/disable switch.
- R5.2 A disabled course disappears from navigation: not in the dropdown, no lessons, glossary, exams or progress shown. Nothing is deleted: its progress, attempts and exams are kept and return when re-enabled. An exam in progress is kept and resumed on re-enable; no warning before disabling.
- R5.3 Activation is per user and stored server-side with the account.
- R5.4 At sign-up, after username and password, the user is asked which courses interest them: the same list as in settings, with checkboxes, none pre-checked, and it is possible to continue with none. Checked courses become active. The screen is shown even when only one course is published.
- R5.5 Existing users keep `crypto-futures` active on migration, with no action needed.
- R5.6 If the user disables the course they are viewing, the web moves to the next active course in alphabetical order; if none remains, to the "no course" state (section 7).
- R5.7 A `draft` course appears neither in settings nor at sign-up.

## 6. Course selector

- R6.1 The Course and Exams tabs have a dropdown of active courses, alphabetical, in the header. It shows the current course; choosing another reloads the tab with that course.
- R6.2 Glossary and Progress have no dropdown of their own: they follow the selected course. There is exactly one selected course for the whole web at any moment.
- R6.3 With a single active course the dropdown is not shown; the course title takes its place.
- R6.4 The selected course is remembered server-side. On entry the web returns to the last selected course if still active; otherwise to the first active course alphabetically.
- R6.5 Switching course touches no progress and no state of any course.
- R6.6 The URL always says which course is being viewed (`/courses/{slug}/…`, which already exists). The dropdown changes the URL; entering an active course by URL selects it; entering a disabled or non-existent course leads to the "no course" state with a notice of what happened and, if the course exists but is disabled, a shortcut to enable it.

## 7. The "no course" state

- R7.1 If no course is active, the four tabs (Course, Glossary, Exams, Progress) each show a default page of their own, not an error and not an empty screen.
- R7.2 All four say the same in one sentence: a course needs to be enabled, with a button that goes straight to the Courses section in settings.
- R7.3 Each adds one line on what will be there once a course is enabled (Course: modules and lessons; Glossary: the course's terms; Exams: per-block and global exams; Progress: your progress and your failures). Nothing more.
- R7.4 The default page respects theme, account language and accessibility, and the button is the only interactive element.
- R7.5 It is also shown if every active course has ceased to exist (a course withdrawn from the catalogue). Their progress is not deleted.

## 8. Per-tab behaviour with a selected course

- R8.1 Course: the block/module/lesson tree of the selected course, in its reading language, with reading-time estimates and Export PDF. The PDF is named with the slug and the reading language (already so).
- R8.2 Glossary: only the selected course's terms, in its reading language, ordered as today. Term and lesson-reference popovers resolve inside the course.
- R8.3 Exams: global and per-block exams of the selected course. Sessions belong to a course; the past-exams list shows only that course's.
- R8.4 Progress: everything in `/stats` computed only from the selected course's attempts, including "where everyone struggles" (aggregated within the course). No cross-course aggregate view.
- R8.5 The three honesty rules of progress (fractions below ten, no ranking with fewer than three exercises, no aggregate with fewer than three people) apply per course.

### 8a. Reporting a wrong question

- R8a.1 Every multiple-choice exercise carries, under the prompt, a discreet "Report this question" link. In practice it is shown once the exercise has been answered (never before: the link must not be a way to ask for the answer) and in the review of a submitted exam. It is not shown during an exam in progress nor in the PDF.
- R8a.2 It opens a box with one free-text field ("What is wrong?", 20 to 1,000 characters, required) and a send button. Nothing else: no categories, ratings or attachments.
- R8a.3 The report is sent by email through the mail server the repository already has, to an address set by environment variable. Besides the user's text, the email carries: course (slug), module and lesson, exercise id and variant id, seed, reading language, the user's answer and the correct answer as they were shown, username, date and time, and a direct link to the exercise inside its lesson. All of that is filled in by the server; the client sends only the text and the attempt id.
- R8a.4 Besides the email, the report is stored server-side (its own table, same fields) so it does not depend on the email arriving and can be listed. An email failure does not fail the report: it is stored and retried.
- R8a.5 After sending, the box closes and a one-sentence confirmation appears. The user gets no reply and sees no report status; there is no report history for the user.
- R8a.6 Limits: 10 reports per user per day, and one report per attempt. Past the limit the link stays visible and sending returns a clear notice.
- R8a.7 Reporting touches neither the attempt, nor progress, nor statistics; reports live in their own lane, like exams.
- R8a.8 A report on an exercise of a Spanish-only course arrives with the texts in Spanish even if the account is in English: what the user saw is what is sent.

## 9. Backend and SPA

- R9.1 The content registry loads every course under `content/` at startup and fails, naming the course, if one does not validate. `draft` courses are loaded (for verification) but not served to users.
- R9.2 The API is already course-scoped (`/api/courses/{slug}/…`). Add `GET /api/courses`: the catalogue of published courses with slug, titles, summaries and available languages. And per user, `GET/PUT /api/me/courses`: active courses, selected course and reading language per course.
- R9.3 The unscoped aliases (`/api/course`, `/api/glossary`, …) are removed in this version, as the README already announces. Old page-URL redirects (`/glossary` → `/courses/crypto-futures/glossary`) stay.
- R9.4 SPA routes stop carrying the literal slug and take a `:course` parameter, validated against the catalogue; an inactive or unknown slug falls into R6.6.
- R9.5 Reports and goldens per course: `glossary-links`, `lesson-refs`, `figures.tsv`, `exercise-mode.tsv`, fingerprints and the list-shape test live inside each course and only for the languages it declares. A change in one course cannot move another course's golden.
- R9.6 Theory export, PDF and printed exercises are already per course; they accept only the course's languages (R4.6).
- R9.7 The Android bundle and contract exports keep existing only for `crypto-futures`. No other course is exported to a bundle, and the tool refuses if asked.

## 10. What does not change

- How exercises are generated, graded and scored; what the client reveals and when.
- Progress and exam rules.
- Content authoring rules (never-coins, no invented vocabulary, style); parity only where there are two languages.
- Accounts, themes, interface language.
- The Android app and its `crypto-futures` bundle.

## 11. Decisions taken

1. Syllabi and slugs of the new courses: a separate requirements document.
2. Independent glossary per course; the new courses are on another subject.
3. Android out of scope; crypto only, never multi-course.
4. Disabling a course with an exam in progress: kept and resumed on re-enable, no warning.
5. Courses of interest chosen at sign-up; none by default; the screen is shown even with a single published course.
6. Alphabetical order in dropdown and settings.
7. One repository for all courses.
8. New courses in Spanish only; reading language chosen among the course's available ones (section 4).
9. ES ↔ EN switch: changes the account and, if the course has the language, the reading language; otherwise the reading language stays.
10. The web is called Curset; TradeSchool stays for Android and the crypto course.
11. One pipeline for all courses; oposiciones courses are test-only, no figures or calculations, and the pipeline skips those steps per course (R3.7).
12. "Report this question" link on every multiple-choice exercise, free text, emailed and stored server-side (section 8a).

## 12. Still open

Nothing blocking. Syllabi and slugs of the oposiciones courses arrive in their own document, and with them their glyphs and accents (R2a.3).

## 13. Acceptance criteria

- With two active courses, switching in Course also switches Glossary, Exams and Progress, and the URL reflects it.
- With one active course, there is no dropdown.
- With no active course, the four tabs show their default page and the button leads to settings.
- An English account with a Spanish-only course reads it in Spanish, sees the "Spanish only" notice and keeps the interface in English.
- Switching the interface to English while reading a Spanish-only course leaves the reading in Spanish, with the notice, and the interface in English.
- Requesting a course in a language it does not declare returns an error naming the available ones.
- Disabling and re-enabling a course returns its progress, attempts and exams intact.
- An attempt, an exam or a statistic never appears in a course other than its own.
- Sign-up asks for courses of interest, also with a single published course, and continues with none checked.
- An answered exercise shows "Report this question"; the same exercise unanswered, an exam in progress and the PDF do not. A sent report arrives by email with every field in R8a.3 and is stored even if the email fails.
- No user-visible text says "TradeSchool" except where it names the crypto course or the Android app; header, browser tab, sign-up, settings, the "no course" page and the PDF say Curset.
- A course without figures passes the whole pipeline, generates its PDF without a capture phase, and reports say "no figures" where applicable.
- All current tests stay green with `crypto-futures` as the only published course, and the Android bundle exports and verifies exactly as today.

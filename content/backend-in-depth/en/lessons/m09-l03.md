# Multi-tenant architecture and data isolation

## Schema per tenant
<!-- bullets: 9.3.a -->

To create a schema, use the CREATE SCHEMA command (`pg-ddl-schemas#DDL-SCHEMAS-CREATE`).

To create or access objects in a schema, write a qualified name consisting of the schema name and table name separated by a dot (`pg-ddl-schemas#DDL-SCHEMAS-CREATE`).

Often you will want to create a schema owned by someone else, since this is one of the ways to restrict the activities of your users to well-defined namespaces (`pg-ddl-schemas#DDL-SCHEMAS-CREATE`).

Schema names beginning with pg_ are reserved for system purposes and cannot be created by users (`pg-ddl-schemas#DDL-SCHEMAS-CREATE`).

By default, users cannot access any objects in schemas they do not own (`pg-ddl-schemas#DDL-SCHEMAS-PRIV`).

To allow that, the owner of the schema must grant the USAGE privilege on the schema (`pg-ddl-schemas#DDL-SCHEMAS-PRIV`).

By default, everyone has the USAGE privilege on the schema public (`pg-ddl-schemas#DDL-SCHEMAS-PRIV`).

To create objects in someone else's schema, the CREATE privilege on the schema needs to be granted (`pg-ddl-schemas#DDL-SCHEMAS-PRIV`).

A secure schema usage pattern prevents untrusted users from changing the behavior of other users' queries (`pg-ddl-schemas#DDL-SCHEMAS-PATTERNS`).

One usage pattern is to constrain ordinary users to user-private schemas (`pg-ddl-schemas#DDL-SCHEMAS-PATTERNS`).

In PostgreSQL 15 and later, the default configuration supports the pattern of user-private schemas (`pg-ddl-schemas#DDL-SCHEMAS-PATTERNS`).

Keeping the default search path and granting privileges to create in the public schema is never a secure pattern (`pg-ddl-schemas#DDL-SCHEMAS-PATTERNS`).

For any pattern, to install shared applications, put them into separate schemas (`pg-ddl-schemas#DDL-SCHEMAS-PATTERNS`).

## Database per tenant
<!-- bullets: 9.3.a -->

:::judgement{source="Microsoft, Azure SQL Database documentation, multitenant SaaS database tenancy patterns" ref="azure-saas-tenancy-patterns#d-multitenant-app-with-database-per-tenant"}
According to the Azure SQL Database documentation, the database-per-tenant pattern uses a multitenant application with many databases, all of them single-tenant databases, and provisions a new database for each new tenant. The application tier is scaled up vertically or out horizontally based on the workload, independently of the number or scale of the individual databases.
:::

:::judgement{source="Microsoft, Azure SQL Database documentation, multitenant SaaS database tenancy patterns" ref="azure-saas-tenancy-patterns#e-multitenant-app-with-multitenant-databases"}
According to the same documentation, the alternative is to store many tenants in a multitenant database, whose schema must have one or more tenant identifier columns so that the data of any given tenant can be retrieved selectively. In that pattern, static code and reference data is stored only once and shared by all tenants.
:::

## Shared tables with row-level security
<!-- bullets: 9.3.a -->

Tables can have row security policies that restrict, on a per-user basis, which rows can be returned by normal queries or inserted, updated, or deleted by data modification commands (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

By default, tables do not have any policies, so that if a user has access privileges to a table according to the SQL privilege system, all rows within it are equally available for querying or updating (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

When row security is enabled on a table, all normal access to the table for selecting rows or modifying rows must be allowed by a row security policy (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

If no policy exists for the table, a default-deny policy is used, meaning that no rows are visible or can be modified (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

Operations that apply to the whole table, such as TRUNCATE and REFERENCES, are not subject to row security (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

Superusers and roles with the BYPASSRLS attribute always bypass the row security system when accessing a table (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with ALTER TABLE ... FORCE ROW LEVEL SECURITY (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

Enabling and disabling row security, as well as adding policies to a table, is always the privilege of the table owner only (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

Policy expressions are run as part of the query and with the privileges of the user running the query, although security-definer functions can be used to access data not available to the calling user (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

```sql
CREATE TABLE accounts (manager text, company text, contact_email text);
ALTER TABLE accounts ENABLE ROW LEVEL SECURITY;
CREATE POLICY account_managers ON accounts TO managers
USING (manager = current_user);
```

The `account_managers` policy allows only members of the managers role to access rows, and only rows of their accounts (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

The policy above implicitly provides a WITH CHECK clause identical to its USING clause (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

## Policies: USING, WITH CHECK and combining
<!-- bullets: 9.3.a -->

Existing table rows are checked against the expression specified in USING, while new rows that would be created via INSERT or UPDATE are checked against the expression specified in WITH CHECK (`pg-sql-createpolicy#id-1.9.3.75.5`).

When a USING expression returns true for a given row then that row is visible to the user, while if false or null is returned then the row is not visible (`pg-sql-createpolicy#id-1.9.3.75.5`).

Typically, no error occurs when a row is not visible (`pg-sql-createpolicy#id-1.9.3.75.5`).

When a WITH CHECK expression returns true for a row then that row is inserted or updated, while if false or null is returned then an error occurs (`pg-sql-createpolicy#id-1.9.3.75.5`).

For policies that can have both USING and WITH CHECK expressions (ALL and UPDATE), if no WITH CHECK expression is defined, then the USING expression will be used both to determine which rows are visible and which new rows will be allowed to be added (`pg-sql-createpolicy#id-1.9.3.75.5`).

The default for newly created policies is that they apply for all commands and roles, unless otherwise specified (`pg-sql-createpolicy#id-1.9.3.75.5`).

If row-level security is enabled for a table, but no applicable policies exist, a “default deny” policy is assumed, so that no rows will be visible or updatable (`pg-sql-createpolicy#id-1.9.3.75.5`).

When multiple policies apply to a given query, they are combined using either OR (for permissive policies, which are the default) or using AND (for restrictive policies) (`pg-ddl-rowsecurity#DDL-ROWSECURITY`).

All the PERMISSIVE policy expressions are combined using OR, all the RESTRICTIVE policy expressions are combined using AND, and the results are combined using AND (`pg-sql-createpolicy#id-1.9.3.75.6.4`).

If there are no PERMISSIVE policies, then access is denied (`pg-sql-createpolicy#id-1.9.3.75.6.4`).

## Per-tenant quotas in Kafka
<!-- bullets: 9.3.b -->

Kafka cluster has the ability to enforce quotas on requests to control the broker resources used by clients (`kafka-design#quotas`).

:::esquema{kind=tabla title="Client quotas enforced by Kafka brokers"}
| Quota | What it defines | Source |
|---|---|---|
| Network bandwidth quotas | Byte-rate thresholds | `kafka-design#quotas` |
| Request rate quotas | CPU utilization thresholds as a percentage of network and I/O threads | `kafka-design#quotas` |
:::

Producers and consumers can monopolize broker resources, cause network saturation and generally DOS other clients and the brokers themselves, and quotas protect against this, all the more in large multi-tenant clusters where a small set of badly behaved clients can degrade user experience for the well behaved ones (`kafka-design#why-are-quotas-necessary`).

Quotas can be applied to (user, client-id), user or client-id groups (`kafka-design#client-groups`).

For a given connection, the most specific quota matching the connection is applied (`kafka-design#client-groups`).

All connections of a quota group share the quota configured for the group (`kafka-design#client-groups`).

By default, each unique client group receives a fixed quota as configured by the cluster (`kafka-design#enforcement`).

This quota is defined on a per-broker basis (`kafka-design#enforcement`).

Kafka decided that defining these quotas per broker is much better than having a fixed cluster wide bandwidth per client because that would require a mechanism to share client quota usage among all the brokers (`kafka-design#enforcement`).

When a broker detects a quota violation, it first computes the amount of delay needed to bring the violating client under its quota and returns a response with the delay immediately (`kafka-design#enforcement`).

Then, the broker mutes the channel to the client, not to process requests from the client anymore, until the delay is over (`kafka-design#enforcement`).

Byte-rate and thread utilization are measured over multiple small windows in order to detect and correct quota violations quickly (`kafka-design#enforcement`).

The snippet assumes a per-broker quota of 10 MB/s, 3 brokers and 4 producer instances in the same quota group, with the load spread evenly.

```java snippet=m09-l03/QuotaShare.java
import java.util.Locale;

public class QuotaShare {
    public static void main(String[] args) {
        double perBrokerQuota = 10.0;
        int brokers = 3;
        int producerInstances = 4;

        double clusterCeiling = perBrokerQuota * brokers;
        System.out.println(String.format(Locale.ROOT, "per-broker quota MB/s: %.1f", perBrokerQuota));
        System.out.println(String.format(Locale.ROOT, "cluster-wide ceiling MB/s: %.1f", clusterCeiling));
        System.out.println(String.format(Locale.ROOT, "share per producer instance at the ceiling MB/s: %.1f", clusterCeiling / producerInstances));
        System.out.println(String.format(Locale.ROOT, "share per producer instance on one broker MB/s: %.1f", perBrokerQuota / producerInstances));
    }
}
```

The quota is defined per broker, so the snippet prints `per-broker quota MB/s: 10.0`.

Across 3 brokers a client can use 30 MB/s before it is throttled, so the snippet prints `cluster-wide ceiling MB/s: 30.0`.

Shared by 4 producer instances at that ceiling, each instance gets 7.5 MB/s, so the snippet prints `share per producer instance at the ceiling MB/s: 7.5`.

On a single broker each of the 4 instances gets 2.5 MB/s of the 10 MB/s quota, so the snippet prints `share per producer instance on one broker MB/s: 2.5`.

Use a Redis rate limiter when you need to enforce per-user, per-API, or per-tenant request quotas consistently across distributed service instances (`redis-rate-limiter#when-to-use-a-redis-rate-limiter`).

## Bulkheads and resource limits
<!-- bullets: 9.3.b -->

Resilience4j provides two implementations of a bulkhead pattern that can be used to limit the number of concurrent executions (`resilience4j-bulkhead#introduction`).

A SemaphoreBulkhead uses Semaphores (`resilience4j-bulkhead#introduction`).

A FixedThreadPoolBulkhead uses a bounded queue and a fixed thread pool (`resilience4j-bulkhead#introduction`).

The SemaphoreBulkhead, unlike Hystrix, does not provide a “shadow” thread pool option (`resilience4j-bulkhead#introduction`).

With the SemaphoreBulkhead it is up to the client to ensure correct thread pool sizing that will be consistent with bulkhead configuration (`resilience4j-bulkhead#introduction`).

Both cpu and memory limits are applied by the kubelet (and container runtime), and are ultimately enforced by the kernel (`k8s-resource-management#requests-and-limits`).

cpu limits are enforced by CPU throttling (`k8s-resource-management#requests-and-limits`).

Containers may not use more CPU than is specified in their cpu limit (`k8s-resource-management#requests-and-limits`).

memory limits are enforced by the kernel with out of memory (OOM) kills (`k8s-resource-management#requests-and-limits`).

A container may use more memory than its memory limit, but if it does, it may get killed (`k8s-resource-management#requests-and-limits`).

Kubernetes assigns every Pod a QoS class based on the resource requests and limits of its component Containers (`k8s-qos#quality-of-service-classes`).

The possible QoS classes are Guaranteed, Burstable, and BestEffort (`k8s-qos#quality-of-service-classes`).

When a Node runs out of resources, Kubernetes will first evict BestEffort Pods running on that Node, followed by Burstable and finally Guaranteed Pods (`k8s-qos#quality-of-service-classes`).

## Per-customer limits under overload
<!-- bullets: 9.3.b -->

:::judgement{source="Google, Site Reliability Engineering, chapter on handling overload" ref="sre-book-handling-overload#per-customer-limits-K7sAuk"}
According to Google's Site Reliability Engineering book, when global overload does occur, it is vital that the service only delivers error responses to misbehaving customers, while other customers remain unaffected. Service owners provision their capacity based on the negotiated usage with their customers and define per-customer quotas according to these agreements. In the book's example, a backend service with 10,000 CPUs allocated worldwide has limits of 4,000 CPU seconds per second for Gmail, 4,000 for Calendar, 3,000 for Android, 2,000 for Google+, and 500 for every other user. The book notes that these numbers may add up to more than the 10,000 CPUs allocated, because the service owner relies on the fact that it is unlikely for all customers to hit their resource limits simultaneously.
:::

```java snippet=m09-l03/Oversubscription.java
import java.util.Locale;
import java.util.Map;

public class Oversubscription {
    public static void main(String[] args) {
        long capacityCpuSeconds = 10_000;
        Map<String, Long> limits = new java.util.LinkedHashMap<>();
        limits.put("Gmail", 4_000L);
        limits.put("Calendar", 4_000L);
        limits.put("Android", 3_000L);
        limits.put("Google+", 2_000L);
        limits.put("Every other user", 500L);

        long sum = limits.values().stream().mapToLong(Long::longValue).sum();
        System.out.println("capacity CPU seconds per second: " + capacityCpuSeconds);
        System.out.println("sum of per-customer limits: " + sum);
        System.out.println(String.format(Locale.ROOT, "limits as a share of capacity: %.2f", (double) sum / capacityCpuSeconds));
        System.out.println("limits add up to more than capacity: " + (sum > capacityCpuSeconds));
    }
}
```

The 10,000 CPUs of the example give a capacity of 10000 CPU seconds per second, so the snippet prints `capacity CPU seconds per second: 10000`.

The five limits add up to 13500 CPU seconds per second, so the snippet prints `sum of per-customer limits: 13500`.

The 13500 limits are 1.35 times the 10000 capacity, so the snippet prints `limits as a share of capacity: 1.35`.

Because 13500 is greater than 10000, the snippet prints `limits add up to more than capacity: true`.

## Key points

- A PostgreSQL schema is created with `CREATE SCHEMA`, and users cannot access objects in schemas they do not own unless the owner grants the `USAGE` privilege.
- In PostgreSQL 15 and later, the default configuration supports the pattern of user-private schemas, and keeping the default search path with create privileges on the public schema is never a secure pattern.
- With row security enabled and no policy, a default-deny policy applies and no rows are visible or can be modified.
- Existing rows are checked against `USING` and new rows against `WITH CHECK`; permissive policies are combined with OR and restrictive ones with AND.
- Superusers and roles with `BYPASSRLS` bypass row security, and table owners do too unless they use `FORCE ROW LEVEL SECURITY`.
- Kafka quotas are network bandwidth quotas (byte-rate thresholds) and request rate quotas (CPU utilization thresholds), applied to the most specific matching group and defined per broker.
- With a per-broker quota of 10 MB/s across 3 brokers, a client can use 30 MB/s before it is throttled.
- Resilience4j offers `SemaphoreBulkhead` and `FixedThreadPoolBulkhead`.
- Kubernetes enforces cpu limits by throttling and memory limits with OOM kills, and evicts BestEffort Pods first, then Burstable and finally Guaranteed Pods.

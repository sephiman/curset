# Fundamentals of distributed systems

## CAP: what the theorem rules out
<!-- bullets: 8.1.a -->

The CAP Theorem was introduced as a trade-off between consistency, availability, and partition tolerance (`paper-gilbert-lynch-cap#p2`).

In a network subject to communication failures, it is impossible for any web service to implement an atomic read/write shared memory that guarantees a response to every request (`paper-gilbert-lynch-cap#p3`).

A web service is atomic if, for every operation, there is a single instant in between the request and the response at which the operation appears to occur (`paper-gilbert-lynch-cap#p2`).

Since no coordination among the servers is required, trivial services do not fall within the scope of the CAP Theorem (`paper-gilbert-lynch-cap#p2`).

Availability is a classic liveness property: it states that eventually, every request receives a response (`paper-gilbert-lynch-cap#p3`).

Consistency requirements are almost always safety properties (`paper-gilbert-lynch-cap#p3`).

The trade-off between consistency and availability in a partition-prone system is a particular example of the more general trade-off between safety and liveness in an unreliable system (`paper-gilbert-lynch-cap#p3`).

If communication is asynchronous and the message delay from one server to another is large enough that the receiver believes the system to be partitioned, the receiver may return an incorrect response despite the lack of partitions (`paper-gilbert-lynch-cap#p3`).

## PACELC: the trade-off when nothing has failed
<!-- bullets: 8.1.a -->

CAP does not constrain any system capabilities during normal operation (`paper-abadi-pacelc#p1`).

As soon as a distributed database system replicates data, a tradeoff between consistency and latency arises (`paper-abadi-pacelc#p3`).

For data replication over a WAN, there is no way around the consistency/latency tradeoff (`paper-abadi-pacelc#p4`).

## Consistency models in real systems
<!-- bullets: 8.1.b -->

Linearizability provides the illusion that each operation applied by concurrent processes takes effect instantaneously at some point between its invocation and its response (`etcd-api-guarantees#linearizability`).

etcd ensures strict serializability for all KV API calls, and linearizability for all other operations by default (`etcd-api-guarantees#kv-apis`; `etcd-api-guarantees#linearizability`).

Linearizable requests in etcd must go through the Raft consensus process (`etcd-api-guarantees#linearizability`).

To obtain lower latencies and higher throughput for read requests, etcd clients can configure a request's consistency mode to serializable, which may access stale data with respect to quorum (`etcd-api-guarantees#linearizability`).

Write operations in ZooKeeper are linearizable (`zk-internals#sc_consistency`).

Read operations in ZooKeeper are not linearizable since they can return potentially stale data (`zk-internals#sc_consistency`).

A read in ZooKeeper is not a quorum operation, and a server responds immediately to a client that is performing a read (`zk-internals#sc_consistency`).

Reads in ZooKeeper are sequentially consistent, because read operations will appear to take effect in some sequential order that furthermore respects the order of each client's operations (`zk-internals#sc_consistency`).

Issuing a sync before a read does not strictly guarantee up-to-date data, because sync is not currently a quorum operation (`zk-internals#sc_consistency`).

The stronger guarantee of linearizability is provided in ZooKeeper if an actual quorum operation, such as a write, is performed before a read (`zk-internals#sc_consistency`).

The consistency guarantees of ZooKeeper lie between sequential consistency and linearizability (`zk-internals#sc_consistency`).

ZooKeeper guarantees that updates from a client will be applied in the order that they were sent (`zk-over#Guarantees`).

ZooKeeper guarantees that a client sees the same view of the service regardless of the server that it connects to (`zk-over#Guarantees`).

Dynamo shows that an eventually-consistent storage system can be used in production applications (`paper-dynamo#p2`).

Dynamo provides eventual consistency, which allows for updates to be propagated to all replicas asynchronously (`paper-dynamo#p6`).

:::esquema{kind=tabla title="Reads and writes in etcd and ZooKeeper"}
| System and operation | Guarantee | Source |
|---|---|---|
| etcd, default operations | Linearizable | `etcd-api-guarantees#linearizability` |
| etcd, serializable read | May access stale data with respect to quorum | `etcd-api-guarantees#linearizability` |
| ZooKeeper, writes | Linearizable | `zk-internals#sc_consistency` |
| ZooKeeper, reads | Sequentially consistent, not linearizable | `zk-internals#sc_consistency` |
:::

:::judgement{source="Jepsen, Consistency Models, by Kyle Kingsbury" ref="jepsen-consistency#models"}
According to Kyle Kingsbury's Jepsen consistency map, a consistency model is a safety property which declares what a system can do, and formally it defines a set of histories that a system can legally execute.
:::

## Time: physical clocks and logical order
<!-- bullets: 8.1.c -->

The Network Time Protocol (NTP) is widely used to synchronize computer clocks in the Internet (`rfc5905#top`).

In NTP, primary servers are assigned stratum one, and secondary servers at each lower level are assigned stratum numbers one greater than the preceding level (`rfc5905#top`).

As the NTP stratum number increases, its accuracy degrades depending on the particular network path and system clock stability (`rfc5905#top`).

:::esquema{kind=tabla title="Stratum values in an NTPv4 packet"}
| Stratum value | Meaning | Source |
|---|---|---|
| 0 | Unspecified or invalid | `rfc5905#top` |
| 1 | Primary server, for example one equipped with a GPS receiver | `rfc5905#top` |
| 2 to 15 | Secondary server, reached via NTP | `rfc5905#top` |
| 16 | Unsynchronized | `rfc5905#top` |
:::

NTPv4 extends the potential accuracy to the tens of microseconds with modern workstations and fast LANs (`rfc5905#top`).

In a distributed system, it is sometimes impossible to say that one of two events occurred first (`paper-lamport-time-clocks#p1`).

The "happened before" relation is therefore only a partial ordering of the events in the system (`paper-lamport-time-clocks#p1`).

Lamport gives a distributed algorithm for synchronizing a system of logical clocks that can be used to totally order the events (`paper-lamport-time-clocks#p1`).

In Lamport’s logical clocks, each process increments its clock between any two successive events (`paper-lamport-time-clocks-columns#p6`).

Without physical time, there is no way to distinguish a failed process from one which is just pausing between events (`paper-lamport-time-clocks#p5`).

Dynamo uses vector clocks to capture causality between different versions of the same object (`paper-dynamo#p6`).

A vector clock in Dynamo is effectively a list of (node, counter) pairs (`paper-dynamo-columns#p12`).

If the counters on the first object’s clock are less-than-or-equal to all of the nodes in the second clock, then the first is an ancestor of the second and can be forgotten (`paper-dynamo-columns#p12`).

Otherwise, the two changes are considered to be in conflict and require reconciliation (`paper-dynamo-columns#p12`).

## Key points

- The CAP Theorem says that in a network subject to communication failures, no web service can implement an atomic read/write shared memory that guarantees a response to every request.
- Consistency is almost always a safety property, and availability is a liveness property.
- CAP does not constrain any system capabilities during normal operation, and replicating data brings a consistency/latency tradeoff as soon as it starts.
- etcd ensures strict serializability for all KV API calls and linearizability for all other operations by default, and a serializable read may return stale data with respect to quorum.
- ZooKeeper writes are linearizable, and its reads are sequentially consistent but not linearizable.
- In NTP, a primary server has stratum one, and accuracy degrades as the stratum number increases.
- The happened-before relation is only a partial ordering of events, and logical clocks can extend it to a total ordering.

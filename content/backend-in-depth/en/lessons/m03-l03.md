# Project Loom: virtual threads, structured concurrency and scoped values

## Virtual threads and platform threads
<!-- bullets: 3.3.a -->

Virtual threads are lightweight threads that dramatically reduce the effort of writing, maintaining, and observing high-throughput concurrent applications (`jep-444#Summary`).

Platform threads are typically mapped 1:1 to kernel threads scheduled by the operating system (`javadoc-thread#platform-threads`).

Platform threads will usually have a large stack and other resources that are maintained by the operating system (`javadoc-thread#platform-threads`).

Virtual threads are typically user-mode threads scheduled by the Java runtime rather than the operating system (`javadoc-thread#virtual-threads`).

A single Java virtual machine may support millions of virtual threads (`javadoc-thread#virtual-threads`).

Virtual threads are suitable for executing tasks that spend most of the time blocked, often waiting for I/O operations to complete (`javadoc-thread#virtual-threads`).

Virtual threads are not intended for long running CPU intensive operations (`javadoc-thread#virtual-threads`).

Virtual threads do not have a thread name by default (`javadoc-thread#virtual-threads`).

Virtual threads are daemon threads and so do not prevent the shutdown sequence from beginning (`javadoc-thread#virtual-threads`).

Virtual threads have a fixed thread priority that cannot be changed (`javadoc-thread#virtual-threads`).

Platform threads get an automatically generated thread name by default (`javadoc-thread#platform-threads`).

```java snippet=m03-l03/VirtualThreadFacts.java
public class VirtualThreadFacts {
    public static void main(String[] args) throws InterruptedException {
        Thread virtual = Thread.ofVirtual().unstarted(() -> {});
        Thread platform = Thread.ofPlatform().unstarted(() -> {});
        System.out.println("virtual-thread virtual=" + virtual.isVirtual());
        System.out.println("virtual-thread name=[" + virtual.getName() + "]");
        System.out.println("virtual-thread daemon=" + virtual.isDaemon());
        System.out.println("platform-thread virtual=" + platform.isVirtual());
        System.out.println("platform-thread daemon=" + platform.isDaemon());
        Thread.ofVirtual().start(() ->
            System.out.println("current-thread inside virtual=" + Thread.currentThread().isVirtual())).join();
    }
}
```

The snippet prints `virtual-thread name=[]`: an unstarted virtual thread has the empty name.

The snippet prints `virtual-thread daemon=true` for the virtual thread and `platform-thread daemon=false` for the platform thread.

Inside the virtual thread, `Thread.currentThread().isVirtual()` makes the snippet print `current-thread inside virtual=true`.

:::esquema{kind=tabla title="Platform threads and virtual threads"}
| Aspect | Platform thread | Virtual thread | Source |
|---|---|---|---|
| Scheduled by | The operating system, typically mapped 1:1 to kernel threads | The Java runtime, as user-mode threads | `javadoc-thread#platform-threads`; `javadoc-thread#virtual-threads` |
| Default name | Automatically generated | None, `getName` returns the empty string | `javadoc-thread#platform-threads`; `javadoc-thread#virtual-threads` |
| Daemon status | Designated daemon or non-daemon | Always daemon | `javadoc-thread#platform-threads`; `javadoc-thread#virtual-threads` |
:::

Platform threads are scheduled by the operating system, while virtual threads are scheduled by the Java runtime (`javadoc-thread#platform-threads`; `javadoc-thread#virtual-threads`).

Platform threads get a generated name by default, while a virtual thread's getName method returns the empty string if no name is set (`javadoc-thread#platform-threads`; `javadoc-thread#virtual-threads`).

Platform threads are designated daemon or non-daemon, while virtual threads are always daemon threads (`javadoc-thread#platform-threads`; `javadoc-thread#virtual-threads`).

## Scheduling, carriers and unmounting
<!-- bullets: 3.3.a -->

For virtual threads, the JDK has its own scheduler, while for platform threads it relies on the scheduler in the OS (`jep-444#Scheduling-virtual-threads`).

The JDK's virtual thread scheduler is a work-stealing ForkJoinPool that operates in FIFO mode (`jep-444#Scheduling-virtual-threads`).

By default the parallelism of the scheduler is equal to the number of available processors, and the system property `jdk.virtualThreadScheduler.parallelism` tunes it (`jep-444#Scheduling-virtual-threads`).

The scheduler's ForkJoinPool is distinct from the common pool, which operates in LIFO mode (`jep-444#Scheduling-virtual-threads`).

The platform thread to which the scheduler assigns a virtual thread is called the virtual thread's carrier (`jep-444#Scheduling-virtual-threads`).

A virtual thread can be scheduled on different carriers over the course of its lifetime (`jep-444#Scheduling-virtual-threads`).

The value returned by `Thread.currentThread()` is always the virtual thread itself (`jep-444#Scheduling-virtual-threads`).

Thread-local variables of the carrier are unavailable to the virtual thread, and vice-versa (`jep-444#Scheduling-virtual-threads`).

The scheduler does not currently implement time sharing for virtual threads (`jep-444#Scheduling-virtual-threads`).

Virtual threads do not require or expect application code to explicitly hand control back to the scheduler, so they are not cooperative (`jep-444#Executing-virtual-threads`).

Typically, a virtual thread will unmount when it blocks on I/O or some other blocking operation in the JDK, such as `BlockingQueue.take()` (`jep-444#Executing-virtual-threads`).

Some blocking operations in the JDK do not unmount the virtual thread, and thus block both its carrier and the underlying OS thread (`jep-444#Executing-virtual-threads`).

The implementations of these blocking operations compensate for the capture of the OS thread by temporarily expanding the parallelism of the scheduler (`jep-444#Executing-virtual-threads`).

The maximum number of platform threads available to the scheduler can be tuned with the system property `jdk.virtualThreadScheduler.maxPoolSize` (`jep-444#Executing-virtual-threads`).

## Virtual threads and the asynchronous style
<!-- bullets: 3.3.a -->

The asynchronous style employs a separate set of I/O methods that do not wait for I/O operations to complete but rather, later on, signal their completion to a callback (`jep-444#Improving-scalability-with-the-asynchronous-style`).

Without a dedicated thread, developers must break down their request-handling logic into small stages, typically written as lambda expressions, and then compose them into a sequential pipeline with an API such as `CompletableFuture` (`jep-444#Improving-scalability-with-the-asynchronous-style`).

Developers who write asynchronous pipelines forsake the language's basic sequential composition operators, such as loops and try/catch blocks (`jep-444#Improving-scalability-with-the-asynchronous-style`).

In the asynchronous style, stack traces provide no usable context (`jep-444#Improving-scalability-with-the-asynchronous-style`).

In the asynchronous style, debuggers cannot step through request-handling logic (`jep-444#Improving-scalability-with-the-asynchronous-style`).

In the asynchronous style, profilers cannot associate an operation's cost with its caller (`jep-444#Improving-scalability-with-the-asynchronous-style`).

Java debuggers can step through virtual threads, show call stacks, and inspect variables in stack frames (`jep-444#Observing-virtual-threads`).

JDK Flight Recorder can associate events from application code, such as object allocation and I/O operations, with the correct virtual thread (`jep-444#Observing-virtual-threads`).

Virtual threads are instances of `java.lang.Thread` (`jep-444#Observing-virtual-threads`).

A thread pool, like any resource pool, is intended to share expensive resources, but virtual threads are not expensive so there is never a need to pool them (`jep-444#Do-not-pool-virtual-threads`).

To limit concurrent access to a limited resource, the JEP says to use constructs specifically designed for that purpose, such as semaphores, instead of pooling virtual threads (`jep-444#Do-not-pool-virtual-threads`).

Do not be tempted to pool virtual threads in order to limit concurrency (`jep-444#Do-not-pool-virtual-threads`).

Creating an expensive resource for every virtual thread may degrade performance significantly (`jep-444#Do-not-pool-virtual-threads`).

The JDK's traditional thread dump, obtained with `jstack` or `jcmd`, presents a flat list of threads (`jep-444#Observing-virtual-threads`).

The JDK will not extend traditional thread dumps to include virtual threads (`jep-444#Observing-virtual-threads`).

`jcmd` can emit the new thread dump in JSON format in addition to plain text (`jep-444#Observing-virtual-threads`).

```bash
jcmd <pid> Thread.dump_to_file -format=json <file>
```

The new thread dump format does not include object addresses, locks, JNI statistics, heap statistics, and other information that appears in traditional thread dumps (`jep-444#Observing-virtual-threads`).

Generating a new thread dump does not pause the application (`jep-444#Observing-virtual-threads`).

Virtual threads are invisible to the OS, which is unaware of their existence (`jep-444#Observing-virtual-threads`).

## Pinning before and after JEP 491
<!-- bullets: 3.3.b -->

A virtual thread cannot be unmounted during blocking operations because it is pinned to its carrier when it executes code inside a synchronized block or method (`jep-444#Executing-virtual-threads`).

A virtual thread is also pinned to its carrier when it executes a native method or a foreign function (`jep-444#Executing-virtual-threads`).

Pinning does not make an application incorrect, but it might hinder its scalability (`jep-444#Executing-virtual-threads`).

If a virtual thread performs a blocking operation such as I/O or `BlockingQueue.take()` while it is pinned, its carrier and the underlying OS thread are blocked for the duration of the operation (`jep-444#Executing-virtual-threads`).

The scheduler does not compensate for pinning by expanding its parallelism (`jep-444#Executing-virtual-threads`).

JEP 444 advises revising `synchronized` blocks or methods that run frequently and guard potentially long I/O operations to use `ReentrantLock` instead (`jep-444#Executing-virtual-threads`).

There is no need to replace `synchronized` blocks and methods that are used infrequently or that guard in-memory operations (`jep-444#Executing-virtual-threads`).

JEP 491, Synchronize Virtual Threads without Pinning, was delivered in Java 24 (`jep-491#main`).

JEP 491 arranges for virtual threads that block in synchronized methods and statements to release their underlying platform threads for use by other virtual threads (`jep-491#Summary`).

JEP 491 eliminates nearly all cases of virtual threads being pinned to platform threads (`jep-491#Summary`).

Without JEP 491, a virtual thread cannot unmount when it runs code inside a synchronized method (`jep-491#Virtual-threads-are-pinned-in-synchronized-methods`).

Before Java 24, when a virtual thread invokes a synchronized instance method and the monitor is held by another thread, the virtual thread blocks in the JVM until the carrier acquires the monitor (`jep-491#More-pinning`).

The pinning described for synchronized instance methods applies, with appropriate changes, to synchronized static methods and to synchronized statements (`jep-491#More-pinning`).

A virtual thread that calls native code, which calls back to Java code that performs a blocking operation or blocks on a monitor, will be pinned (`jep-491#Diagnosing-remaining-cases-of-pinning`).

JEP 491 retains the `jdk.VirtualThreadPinned` JFR event for other pinning situations (`jep-491#Diagnosing-remaining-cases-of-pinning`).

:::esquema{kind=tabla title="Pinning in Java 21 and in Java 24 and later"}
| Situation | Java 21 (JEP 444) | Java 24 and later (JEP 491) | Source |
|---|---|---|---|
| Virtual thread blocks inside `synchronized` | Pinned to its carrier | Releases its underlying platform thread | `jep-444#Executing-virtual-threads`; `jep-491#Summary` |
| Virtual thread runs a native method or foreign function | Pinned to its carrier | Still pinned when native code calls back into blocking Java code | `jep-444#Executing-virtual-threads`; `jep-491#Diagnosing-remaining-cases-of-pinning` |
| Frequent, long-lived pinning | Revise `synchronized` to use `ReentrantLock` | Migration to `ReentrantLock` is no longer necessary | `jep-444#Executing-virtual-threads`; `jep-491#Choosing-between-synchronized-and-java-util-concurrent-locks` |
:::

In Java 21 a virtual thread blocking inside synchronized is pinned to its carrier, and since Java 24 it releases its underlying platform thread (`jep-444#Executing-virtual-threads`; `jep-491#Summary`).

In Java 21 a native method pins the virtual thread, and from Java 24 native code that calls back into blocking Java code still pins it (`jep-444#Executing-virtual-threads`; `jep-491#Diagnosing-remaining-cases-of-pinning`).

In Java 21 frequent, long-lived pinning is solved by revising synchronized to use ReentrantLock, and from Java 24 such migration is no longer necessary (`jep-444#Executing-virtual-threads`; `jep-491#Choosing-between-synchronized-and-java-util-concurrent-locks`).

Once the synchronized keyword no longer pins virtual threads, you can choose between synchronized and the APIs in the `java.util.concurrent.locks` package based solely upon which best solves the problem at hand (`jep-491#Choosing-between-synchronized-and-java-util-concurrent-locks`).

Once the synchronized keyword no longer pins virtual threads, migrating code from synchronized to `ReentrantLock` is no longer necessary (`jep-491#Choosing-between-synchronized-and-java-util-concurrent-locks`).

Code that has been migrated to use `ReentrantLock` need not be reverted to synchronized (`jep-491#Choosing-between-synchronized-and-java-util-concurrent-locks`).

The `ReentrantLock` API behaves the same as synchronized (`jep-491#Choosing-between-synchronized-and-java-util-concurrent-locks`).

The `java.util.concurrent.locks` APIs should generally be used with the try-finally construct in order to ensure that locks are released appropriately (`jep-491#Choosing-between-synchronized-and-java-util-concurrent-locks`).

For new code, JEP 491 agrees with Java Concurrency in Practice §13.4: use synchronized where practical, since it is more convenient and less error prone, and use `ReentrantLock` and the other APIs in `java.util.concurrent.locks` when more flexibility is required (`jep-491#Choosing-between-synchronized-and-java-util-concurrent-locks`).

JEP 491 advises reducing the potential for contention by narrowing the scope of locks and avoiding, where possible, doing I/O or other blocking operations while holding locks (`jep-491#Choosing-between-synchronized-and-java-util-concurrent-locks`).

## Limiting concurrency and sizing connection pools
<!-- bullets: 3.3.b -->

Conceptually, a semaphore maintains a set of permits (`javadoc-semaphore#class-semaphore`).

Each `acquire()` blocks if necessary until a permit is available, and then takes it (`javadoc-semaphore#class-semaphore`).

Each `release()` adds a permit, potentially releasing a blocking acquirer (`javadoc-semaphore#class-semaphore`).

Semaphores are often used to restrict the number of threads that can access some physical or logical resource (`javadoc-semaphore#class-semaphore`).

```java snippet=m03-l03/SemaphoreLimit.java
import java.util.concurrent.Semaphore;

public class SemaphoreLimit {
    public static void main(String[] args) {
        Semaphore permits = new Semaphore(2);
        System.out.println("available=" + permits.availablePermits());
        System.out.println("first=" + permits.tryAcquire());
        System.out.println("second=" + permits.tryAcquire());
        System.out.println("third=" + permits.tryAcquire());
        permits.release();
        System.out.println("after release available=" + permits.availablePermits());
    }
}
```

With two permits, the first two `tryAcquire()` calls print `first=true` and `second=true` and the third prints `third=false`.

After one `release()`, `availablePermits()` prints `1`.

HikariCP's pool sizing page recommends a small pool of a few dozen connections at most, with the rest of the application threads blocked on the pool awaiting connections (`hikaricp-pool-sizing#axiom-you-want-a-small-pool-saturated-with-threads-waiting-for-connections`).

A properly tuned pool is set right at the limit of the number of queries the database is capable of processing simultaneously, which is rarely much more than CPU cores * 2 (`hikaricp-pool-sizing#axiom-you-want-a-small-pool-saturated-with-threads-waiting-for-connections`).

For optimal throughput the number of active connections should be somewhere near `((core_count * 2) + effective_spindle_count)` (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

Core count should not include HT threads, even if hyperthreading is enabled (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

Effective spindle count is zero if the active data set is fully cached, and approaches the actual number of spindles as the cache hit rate falls (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

There has been no analysis so far of how well the formula works with SSDs (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

For a 4-core i7 server with one hard disk, the page computes a pool of 9 = ((4 * 2) + 1) (`hikaricp-pool-sizing#connections--core_count--2--effective_spindle_count`).

## Structured concurrency and the state of the API in Java 25
<!-- bullets: 3.3.c -->

Structured concurrency treats groups of related tasks running in different threads as single units of work, thereby streamlining error handling and cancellation, improving reliability, and enhancing observability (`jep-505#Summary`).

Programs can only use `StructuredTaskScope` when preview features are enabled (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

Compiling with `javac --release 25 --enable-preview Main.java` and running with `java --enable-preview Main` enables the `StructuredTaskScope` API (`jep-505#StructuredTaskScope-is-a-preview-API-disabled-by-default`).

```bash
javac --release 25 --enable-preview Main.java
java --enable-preview Main
```

Structured concurrency incubated in JDK 19 via JEP 428 and JDK 20 via JEP 437 (`jep-505#History`).

The zero-parameter `open` factory method creates a `StructuredTaskScope` that waits for all subtasks to succeed or any subtask to fail (`jep-505#History`).

Other policies and outcomes can be implemented by providing an appropriate `Joiner` to one of the richer `open` factory methods (`jep-505#History`).

In JDK 26, `Joiner::allSuccessfulOrThrow()` returns a list of results rather than a stream of subtasks (`jep-525#History`).

In JDK 26, a new method `onTimeout()` in the `Joiner` interface allows implementations to return a result when a timeout expires (`jep-525#History`).

In JDK 27, the `StructuredTaskScope` and `Joiner` interfaces have a third type parameter, `R_X`, for the type of the exception that `join()` can throw (`jep-533#History`).

:::esquema{kind=tabla title="How the structured concurrency API changed between previews"}
| JDK | JEP | Change | Source |
|---|---|---|---|
| 21 | 453 | The `fork` method returns a `Subtask` rather than a `Future` | `jep-505#History` |
| 25 | 505 | A `StructuredTaskScope` is opened via static factory methods rather than public constructors | `jep-505#History` |
| 26 | 525 | `Joiner::anySuccessfulResultOrThrow()` is renamed `anySuccessfulOrThrow()` | `jep-525#History` |
| 27 | 533 | The `Joiner` factory method `awaitAll()` is removed | `jep-533#History` |
:::

`StructuredTaskScope` defines the static method `open` to open a new scope and the `close` method to close it (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

Forking a subtask starts a new `Thread` to run the subtask (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

The thread executing the task does not continue beyond the `close` method until all threads started to execute subtasks have finished (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

The `fork`, `join` and `close` methods may only be invoked by the owner thread, the thread that opened the `StructuredTaskScope` (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

The `fork` method may not be called after `join` (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

The `join` method may only be invoked once (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

The `close` method throws an exception after closing if the owner did not invoke the `join` method after forking subtasks (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

If one subtask fails in the default scope, the other subtask is cancelled, which interrupts the thread executing it (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

If one subtask fails in the default scope, `join` throws `StructuredTaskScope.FailedException` with the exception from the failed subtask as the cause (`javadoc-structuredtaskscope#interface-structuredtaskscope-t-r`).

If all subtasks succeed in the default scope, `join()` completes normally and returns `null` (`jep-505#Joiners`).

A `Joiner` handles subtask completion and produces the outcome for the `join` method (`javadoc-structuredtaskscope#joiners-heading`).

Depending on the `Joiner`, `join` may return a result, a stream of elements, or some other object (`javadoc-structuredtaskscope#joiners-heading`).

Cancelling the scope prevents new threads from being started to execute further subtasks (`javadoc-structuredtaskscope#joiners-heading`).

Cancelling the scope interrupts the threads executing subtasks that have not completed (`javadoc-structuredtaskscope#joiners-heading`).

Cancelling the scope causes the `join` method to wake up with the outcome, a result or an exception (`javadoc-structuredtaskscope#joiners-heading`).

:::esquema{kind=tabla title="Joiner factory methods in Java 25"}
| Factory method | Behaviour | Source |
|---|---|---|
| `allSuccessfulOrThrow()` | Yields a stream of the completed subtasks when all succeed; cancels the scope and makes `join` throw if any subtask fails | `javadoc-structuredtaskscope-joiner#interface-structuredtaskscope-joiner-t-r` |
| `anySuccessfulResultOrThrow()` | Yields the result of the first subtask to succeed; makes `join` throw if all subtasks fail | `javadoc-structuredtaskscope-joiner#interface-structuredtaskscope-joiner-t-r` |
| `awaitAllSuccessfulOrThrow()` | Waits for all successful subtasks; cancels the scope and makes `join` throw if any subtask fails | `javadoc-structuredtaskscope-joiner#interface-structuredtaskscope-joiner-t-r` |
| `awaitAll()` | Waits for all subtasks; does not cancel the scope or make `join` throw | `javadoc-structuredtaskscope-joiner#interface-structuredtaskscope-joiner-t-r` |
| `allUntil(Predicate)` | Yields a stream of all subtasks; a predicate decides whether the scope continues or is cancelled | `javadoc-structuredtaskscope-joiner#interface-structuredtaskscope-joiner-t-r` |
:::

The `onFork(Subtask)` method of a custom `Joiner` is invoked when subtasks are forked (`javadoc-structuredtaskscope-joiner#interface-structuredtaskscope-joiner-t-r`).

The `onComplete(Subtask)` method of a custom `Joiner` is invoked when subtasks complete with a result or exception (`javadoc-structuredtaskscope-joiner#interface-structuredtaskscope-joiner-t-r`).

Implementations of `Joiner` must be thread safe (`javadoc-structuredtaskscope-joiner#interface-structuredtaskscope-joiner-t-r`).

Each `StructuredTaskScope` needs a new `Joiner`, and a `Joiner` must not be shared with other scopes or reused after its scope is closed (`jep-505#Joiners`).

If a scope's owner thread is interrupted before or while joining, `join()` throws an exception because there is no point in continuing (`jep-505#Cancellation`).

The try-with-resources statement then cancels the scope, which cancels all the subtasks and waits for them to terminate (`jep-505#Cancellation`).

Subtasks must be coded so that they finish as soon as possible when interrupted (`jep-505#Cancellation`).

Subtasks that do not respond to interrupts may delay the closing of a scope indefinitely (`jep-505#Cancellation`).

The `close` method always waits for threads executing subtasks to finish, even if the scope is cancelled (`jep-505#Cancellation`).

Attempts to call a `fork` method from a thread that is not the scope's owner fail with an exception (`jep-505#Structured-use-is-enforced`).

Using a scope outside of a try-with-resources block and returning without calling `close()`, or without maintaining the proper nesting of `close()` calls, may cause the scope's methods to throw a `StructureViolationException` (`jep-505#Structured-use-is-enforced`).

`StructuredTaskScope` does not implement the `ExecutorService` or `Executor` interfaces (`jep-505#Structured-use-is-enforced`).

## Scoped values
<!-- bullets: 3.3.d -->

Scoped values were delivered as a final feature in Java 25 by JEP 506 (`jep-506#main`).

Scoped values enable a method to share immutable data both with its callees within a thread, and with child threads (`jep-506#Summary`).

Scoped values are easier to reason about than thread-local variables (`jep-506#Summary`).

Scoped values have lower space and time costs than thread-local variables, especially when used together with virtual threads and structured concurrency (`jep-506#Summary`).

Each thread that accesses a thread-local variable via its `get` or `set` method has its own, independently initialized copy of the variable (`javadoc-threadlocal#class-threadlocal-t`).

Every thread-local variable is mutable: any code that can call its `get` method can call its `set` method at any time (`jep-506#Problems-with-thread-local-variables`).

Once a thread's copy of a thread-local variable is set via `set`, the value is retained for the lifetime of the thread, or until code in the thread calls the `remove` method (`jep-506#Problems-with-thread-local-variables`).

If a thread pool is used, the value of a thread-local variable set in one task could, if not properly cleared, accidentally leak into an unrelated task (`jep-506#Problems-with-thread-local-variables`).

When a child thread inherits thread-local variables, it has to allocate storage for every thread-local variable previously written in the parent thread (`jep-506#Problems-with-thread-local-variables`).

A `ScopedValue` is a value that may be safely and efficiently shared to methods without using method parameters (`javadoc-scopedvalue#class-scopedvalue-t`).

In effect, a `ScopedValue` is an implicit method parameter (`javadoc-scopedvalue#class-scopedvalue-t`).

A `ScopedValue` object reverts to being unbound when the original method completes normally or with an exception (`javadoc-scopedvalue#class-scopedvalue-t`).

A `ScopedValue` binding to a value is per-thread (`javadoc-scopedvalue#bindings-are-per-thread-heading`).

```java snippet=m03-l03/ScopedValueBinding.java
public class ScopedValueBinding {
    private static final ScopedValue<String> NAME = ScopedValue.newInstance();

    static void show(String label) {
        System.out.println(label + " bound=" + NAME.isBound() + (NAME.isBound() ? " value=" + NAME.get() : ""));
    }

    public static void main(String[] args) throws InterruptedException {
        show("before");
        ScopedValue.where(NAME, "duke").run(() -> {
            show("inside");
            ScopedValue.where(NAME, "nested").run(() -> show("rebound"));
            show("after-rebound");
        });
        show("after");
        Thread other = new Thread(() -> ScopedValue.where(NAME, "duke2").run(() -> show("other thread")));
        ScopedValue.where(NAME, "duke1").run(() -> {
            other.start();
            try { other.join(); } catch (InterruptedException e) { throw new RuntimeException(e); }
            show("main thread");
        });
    }
}
```

Outside any `run`, the snippet prints `before bound=false`.

Inside `ScopedValue.where(NAME, "duke").run(...)`, the snippet prints `inside bound=true value=duke`.

A nested binding prints `rebound bound=true value=nested`.

After the nested `run` completes, the snippet prints `after-rebound bound=true value=duke`.

After the outer `run` completes, the snippet prints `after bound=false`.

A second thread that binds `NAME` to `duke2` prints `other thread bound=true value=duke2`, and the main thread still prints `main thread bound=true value=duke1`.

Scoped values in the parent thread are automatically inherited by child threads created with `StructuredTaskScope` (`jep-506#Inheriting-scoped-values`).

Code in a child thread can use bindings established for a scoped value in the parent thread with minimal overhead (`jep-506#Inheriting-scoped-values`).

Unlike with thread-local variables, there is no copying of a parent thread's scoped value bindings to the child thread (`jep-506#Inheriting-scoped-values`).

Legacy thread management classes such as `ForkJoinPool` do not support inheritance of scoped values (`jep-506#Inheriting-scoped-values`).

JEP 506 advises migration to scoped values when the purpose of a thread-local variable aligns with the goal of a scoped value: one-way transmission of unchanging data (`jep-506#Migrating-to-scoped-values`).

If a codebase uses thread-local variables in a two-way fashion or in a completely unstructured fashion, migration to scoped values is not an option (`jep-506#Migrating-to-scoped-values`).

Caching objects that are expensive to create and use is a scenario that favors thread-local variables (`jep-506#Migrating-to-scoped-values`).

## Key points

- Virtual threads are user-mode threads scheduled by the Java runtime and mounted on carrier platform threads by a work-stealing `ForkJoinPool` in FIFO mode.
- Virtual threads are daemon threads, have no name by default and are not intended for long running CPU intensive operations.
- Virtual threads do not need pooling; use a semaphore to limit concurrent access to a limited resource.
- Java 21 pins a virtual thread that blocks inside `synchronized` or runs native code; Java 24 (JEP 491) releases the platform thread when it blocks in `synchronized`.
- HikariCP's page sizes a pool near `((core_count * 2) + effective_spindle_count)`: 9 for a 4-core server with one hard disk.
- `StructuredTaskScope` is a preview API in Java 25; a new `Joiner` is created for each scope and the scope owner calls `fork`, `join` and `close`.
- `anySuccessfulResultOrThrow()` and `awaitAll()` are two of the `Joiner` factory methods of Java 25; the API changed in JDK 21, 25, 26 and 27.
- Subtasks must finish when interrupted, because `close` always waits for them.
- A `ScopedValue` binding is per-thread, lasts for one method call and is inherited by child threads created with `StructuredTaskScope`.
- JEP 506 advises scoped values for one-way transmission of unchanging data, not for two-way or unstructured use of thread-local variables.

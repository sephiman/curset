# Interoperability and migration from Java

## Static methods and overloads for Java callers
<!-- bullets: 4.5.a -->

Kotlin represents package-level functions as static methods (`kotlin-docs-java-to-kotlin-interop#static-methods`).

The `@JvmStatic` annotation generates static methods for functions defined in named objects or companion objects (`kotlin-docs-java-to-kotlin-interop#static-methods`).

If you use `@JvmStatic` on a function in a companion object, the compiler generates both a static method in the enclosing class and an instance method in the companion object (`kotlin-docs-java-to-kotlin-interop#static-methods`).

For a named object, `@JvmStatic` turns the function into a static method of the object's class but doesn't generate a separate instance method (`kotlin-docs-java-to-kotlin-interop#static-methods`).

A function in an interface's companion object annotated with `@JvmStatic` compiles to a static method in the interface (`kotlin-docs-java-to-kotlin-interop#static-methods`).

Normally, a Kotlin function with default parameter values is visible in Java only as a full signature, with all parameters present (`kotlin-docs-java-to-kotlin-interop#overloads-generation`).

The `@IntroducedAt` annotation or the `@JvmOverloads` annotation generates overloads for optional parameters (`kotlin-docs-java-to-kotlin-interop#overloads-generation`).

The `@IntroducedAt` annotation is Experimental (`kotlin-docs-java-to-kotlin-interop#overloads-generation`).

The `@JvmOverloads` annotation also works for constructors, static methods, and so on (`kotlin-docs-java-to-kotlin-interop#overloads-generation`).

The `@JvmOverloads` annotation can't be used on abstract methods, including methods defined in interfaces (`kotlin-docs-java-to-kotlin-interop#overloads-generation`).

For every parameter with a default value, `@JvmOverloads` generates one additional overload, which has this parameter and all parameters to the right of it in the parameter list removed (`kotlin-docs-java-to-kotlin-interop#overloads-generation`).

If a class has default values for all constructor parameters, a public constructor with no arguments is generated for it, even if the `@JvmOverloads` annotation is not specified (`kotlin-docs-java-to-kotlin-interop#overloads-generation`).

The snippet declares a companion object with one `@JvmStatic` function and one plain function, a class whose constructor has `@JvmOverloads` and a default value for `radius`, and two functions of which one has `@Throws(IOException::class)`. It then reads the compiled classes through reflection.

```kotlin snippet=m04-l05/JvmInterop.kt
import java.io.IOException
import java.lang.reflect.Modifier

class Greeter {
    companion object {
        @JvmStatic fun callStatic() {}
        fun callNonStatic() {}
    }
}

class Circle @JvmOverloads constructor(centerX: Int, centerY: Int, radius: Double = 1.0)

class Files {
    @Throws(IOException::class)
    fun declared() {}

    fun undeclared() {}
}

fun names(methods: Array<java.lang.reflect.Method>): List<String> =
    methods.filter { !it.isSynthetic }.map { it.name }.sorted()

fun main() {
    val staticOnGreeter = Greeter::class.java.declaredMethods.filter { Modifier.isStatic(it.modifiers) }
    println("static methods of Greeter: " + names(staticOnGreeter.toTypedArray()))
    println("methods of Greeter.Companion: " + names(Greeter.Companion::class.java.declaredMethods))
    val arities = Circle::class.java.constructors.filter { !it.isSynthetic }.map { it.parameterCount }.sorted()
    println("Circle constructor parameter counts: $arities")
    println("declared throws: " + Files::class.java.getDeclaredMethod("declared").exceptionTypes.map { it.simpleName })
    println("undeclared throws: " + Files::class.java.getDeclaredMethod("undeclared").exceptionTypes.map { it.simpleName })
}
```

The snippet prints `static methods of Greeter: [callStatic]` and `methods of Greeter.Companion: [callNonStatic, callStatic]`, so the `@JvmStatic` function exists as a static method of the enclosing class and as a method of the companion object, and the plain function only in the companion object.

The snippet prints `Circle constructor parameter counts: [2, 3]`, one constructor with three parameters and the generated overload without `radius`.

## Exceptions across the boundary
<!-- bullets: 4.5.a -->

Kotlin does not have checked exceptions, so normally the Java signatures of Kotlin functions do not declare exceptions thrown (`kotlin-docs-java-to-kotlin-interop#checked-exceptions`).

A Java caller that catches `IOException` from a Kotlin function without `@Throws` gets an error message from the Java compiler, because the function does not declare `IOException` (`kotlin-docs-java-to-kotlin-interop#checked-exceptions`).

To work around this problem, use the `@Throws` annotation in Kotlin (`kotlin-docs-java-to-kotlin-interop#checked-exceptions`).

The snippet prints `declared throws: [IOException]` for the function annotated with `@Throws(IOException::class)` and `undeclared throws: []` for the other.

In Kotlin, all exceptions are unchecked, meaning that the compiler does not force you to catch any of them (`kotlin-docs-java-interop#checked-exceptions`).

When you call a Java method that declares a checked exception, Kotlin does not force you to do anything (`kotlin-docs-java-interop#checked-exceptions`).

Since Kotlin treats all exceptions as unchecked, it can lead to complications when such exceptions are called from languages that distinguish between checked and unchecked exceptions (`kotlin-docs-exceptions#exception-interoperability-with-java-swift-and-objective-c`).

The `@Throws` annotation alerts callers about possible exceptions (`kotlin-docs-exceptions#exception-interoperability-with-java-swift-and-objective-c`).

## Migrating a Java code base to Kotlin
<!-- bullets: 4.5.b -->

:::judgement{source="JetBrains, Kotlin documentation, Adding Kotlin to a Java project tutorial" ref="kotlin-docs-mixing-java-kotlin#mixing-java-kotlin-intellij.md"}
According to the Kotlin documentation, Kotlin is fully interoperable with Java, so you can gradually introduce it into your existing Java projects without having to rewrite everything.
:::

:::judgement{source="JetBrains, Kotlin documentation, Adding Kotlin to a Java project tutorial" ref="kotlin-docs-mixing-java-kotlin#project-structure"}
According to the Kotlin documentation, the Kotlin plugin automatically recognizes both `src/main/java` and `src/test/java`, so you can keep `.kt` and `.java` files in the same directories.
:::

:::judgement{source="JetBrains, Kotlin documentation, Adding Kotlin to a Java project tutorial" ref="kotlin-docs-mixing-java-kotlin#convert-java-files-to-kotlin"}
According to the Kotlin documentation, the Java to Kotlin converter (J2K) bundled with the Kotlin plugin does a pretty decent job of converting most boilerplate code, but it is not fool-proof and some manual tweaking is sometimes required.
:::

:::judgement{source="JetBrains, Kotlin documentation, Adding Kotlin to a Java project tutorial" ref="kotlin-docs-mixing-java-kotlin#explore-compiler-plugins"}
According to the Kotlin documentation, a project that uses Spring or JPA can use the `all-open`, `kotlin-spring`, `no-arg` and `kotlin-jpa` compiler plugins to adapt Kotlin's language features to framework expectations.
:::

## Key points

- The `@JvmStatic` annotation generates static methods for functions in named objects and companion objects.
- For a function in a companion object, `@JvmStatic` generates a static method in the enclosing class and an instance method in the companion object.
- The `@JvmOverloads` annotation generates one additional overload for every parameter with a default value, and it can't be used on abstract methods.
- In the snippet, `Circle` has constructors with two and three parameters.
- Kotlin does not have checked exceptions, so Java signatures of Kotlin functions normally do not declare exceptions.
- The `@Throws` annotation in Kotlin makes the Java signature declare the exception, as the snippet shows.
- In Kotlin, calling a Java method that declares a checked exception does not force you to do anything.

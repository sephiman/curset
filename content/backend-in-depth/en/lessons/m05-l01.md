# IoC container and bean lifecycle

## Bean definitions, containers and scopes
<!-- bullets: 5.1.a -->

A Spring container keeps a description of each bean, called a bean definition, and builds the objects from those descriptions. The `ApplicationContext` is the container you normally use. A scope decides how many instances one definition produces. A singleton is built when the container starts, so a wiring mistake shows up at start-up and not on the first request.

A Spring IoC container manages one or more beans, created with the configuration metadata that you supply to the container (`spring-fw-beans-definition#bean-overview`).

Within the container, bean definitions are represented as `BeanDefinition` objects (`spring-fw-beans-definition#bean-overview`).

A `BeanDefinition` includes bean behavioral configuration elements, which state how the bean should behave in the container, such as scope and lifecycle callbacks (`spring-fw-beans-definition#bean-overview`).

A `BeanDefinition` also holds references to other beans that the bean needs, and these references are called collaborators or dependencies (`spring-fw-beans-definition#bean-overview`).

The `BeanFactory` API provides the underlying basis for Spring's IoC functionality, and its `DefaultListableBeanFactory` implementation is a key delegate within the higher-level `GenericApplicationContext` container (`spring-fw-beans-beanfactory#the-beanfactory-api`).

The core `BeanFactory` API and `DefaultListableBeanFactory` make no assumptions about the configuration format or the component annotations used (`spring-fw-beans-beanfactory#the-beanfactory-api`).

Those flavors come in through extensions such as `XmlBeanDefinitionReader` and `AutowiredAnnotationBeanPostProcessor`, which operate on shared `BeanDefinition` objects as the core metadata representation (`spring-fw-beans-beanfactory#the-beanfactory-api`).

Bean overriding occurs when a bean is registered using an identifier that is already allocated (`spring-fw-beans-definition#beans-definition-overriding`).

By default, the container logs every attempt to override a bean at INFO level (`spring-fw-beans-definition#beans-definition-overriding`).

Setting the `allowBeanDefinitionOverriding` flag to false on the `ApplicationContext` before it is refreshed makes the container throw an exception if bean overriding is used (`spring-fw-beans-definition#beans-definition-overriding`).

With Java configuration, a corresponding `@Bean` method always silently overrides a scanned bean class with the same component name, as long as the return type of the `@Bean` method matches that bean class (`spring-fw-beans-definition#beans-definition-overriding`).

You should use an `ApplicationContext` unless you have a good reason for not doing so (`spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory`).

An `ApplicationContext` includes all the functionality of a `BeanFactory`, so it is generally recommended over a plain `BeanFactory` (`spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory`).

With only a plain `DefaultListableBeanFactory`, bean post-processors do not get detected and activated by default (`spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory`).

```java snippet=m05-l01/FactoryVsContext.java
import java.util.ArrayList;
import java.util.List;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.beans.factory.support.DefaultListableBeanFactory;
import org.springframework.beans.factory.support.RootBeanDefinition;
import org.springframework.context.support.GenericApplicationContext;

public class FactoryVsContext {
    static final List<String> seen = new ArrayList<>();

    static class Recorder implements BeanPostProcessor {
        @Override
        public Object postProcessBeforeInitialization(Object bean, String beanName) {
            seen.add(beanName);
            return bean;
        }
    }

    static class Widget {}

    public static void main(String[] args) {
        var factory = new DefaultListableBeanFactory();
        factory.registerBeanDefinition("recorder", new RootBeanDefinition(Recorder.class));
        factory.registerBeanDefinition("widget", new RootBeanDefinition(Widget.class));
        factory.getBean("widget");
        System.out.println("plain factory processed: " + seen);

        seen.clear();
        try (var context = new GenericApplicationContext()) {
            context.registerBeanDefinition("recorder", new RootBeanDefinition(Recorder.class));
            context.registerBeanDefinition("widget", new RootBeanDefinition(Widget.class));
            context.refresh();
            System.out.println("application context processed: " + seen);
        }
    }
}
```

In `FactoryVsContext`, the plain factory prints `plain factory processed: []` and the `GenericApplicationContext` prints `application context processed: [widget]`: the post-processor registered in the factory processed no bean, and the one in the context processed `widget`.

The Spring Framework supports six scopes, four of which are available only with a web-aware `ApplicationContext` (`spring-fw-beans-factory-scopes#bean-scopes`).

The `singleton` scope is the default and gives a single object instance for each Spring IoC container (`spring-fw-beans-factory-scopes#bean-scopes`).

The `prototype` scope gives any number of object instances for a single bean definition (`spring-fw-beans-factory-scopes#bean-scopes`).

The scope of the Spring singleton is best described as being per-container and per-bean (`spring-fw-beans-factory-scopes#beans-factory-scopes-singleton`).

The Gang of Four singleton hard-codes the scope of an object, so that one and only one instance of a class is created per `ClassLoader` (`spring-fw-beans-factory-scopes#beans-factory-scopes-singleton`).

The prototype scope creates a new bean instance every time a request for that specific bean is made (`spring-fw-beans-factory-scopes#beans-factory-scopes-prototype`).

If you dependency-inject a prototype-scoped bean into a singleton-scoped bean, a new prototype bean is instantiated and then injected into the singleton bean, and that prototype instance is the sole instance ever supplied to the singleton-scoped bean (`spring-fw-beans-factory-scopes#beans-factory-scopes-sing-prot-interaction`).

By default, `ApplicationContext` implementations eagerly create and configure all singleton beans as part of the initialization process (`spring-fw-beans-factory-lazy-init#page-title`).

```java snippet=m05-l01/ScopeIdentity.java
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Scope;

public class ScopeIdentity {
    static int created;

    static class Counter {
        final int number = ++created;
    }

    @Configuration
    static class Config {
        @Bean
        Counter shared() {
            return new Counter();
        }

        @Bean
        @Scope("prototype")
        Counter fresh() {
            return new Counter();
        }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            System.out.println("created after refresh: " + created);
            System.out.println("same singleton: " + (context.getBean("shared") == context.getBean("shared")));
            System.out.println("same prototype: " + (context.getBean("fresh") == context.getBean("fresh")));
            System.out.println("created after four lookups: " + created);
        }
    }
}
```

In `ScopeIdentity`, `created after refresh: 1` shows that the singleton exists and the prototype does not. It then prints `same singleton: true` and `same prototype: false`, and `created after four lookups: 3`, because each of the two prototype lookups created a new instance.

Singleton-scoped beans that are set to be pre-instantiated, which is the default, are created when the container is created (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

`ApplicationContext` implementations pre-instantiate singleton beans by default, so that you discover configuration issues when the `ApplicationContext` is created, not later (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

The container validates the configuration of each bean as the container is created, but the bean properties are not set until the bean is actually created (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

Without circular dependencies, each collaborating bean is totally configured before it is injected into the dependent bean (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

## Lifecycle callbacks and post-processors
<!-- bullets: 5.1.b -->

A bean goes through fixed steps between its creation and its removal. The container creates the object, sets its dependencies, runs the initialization callbacks and, when the container is destroyed, the destruction callbacks. A `BeanPostProcessor` gets a turn before and after initialization, which is how Spring can wrap a bean with a proxy. A prototype bean gets no configured destruction callback from the container, so whoever asked for it must release what it holds.

The bean is instantiated (if it is not a pre-instantiated singleton), its dependencies are set, and the relevant lifecycle methods, such as a configured init method or the `InitializingBean` callback method, are invoked (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

The container calls `afterPropertiesSet()` for `InitializingBean` and `destroy()` for `DisposableBean`, so the bean can act on initialization and destruction (`spring-fw-beans-factory-nature#beans-factory-lifecycle`).

The JSR-250 `@PostConstruct` and `@PreDestroy` annotations are generally considered best practice for receiving lifecycle callbacks in a modern Spring application (`spring-fw-beans-factory-nature#beans-factory-lifecycle`).

Internally, the Spring Framework uses `BeanPostProcessor` implementations to process any callback interfaces it can find and call the appropriate methods (`spring-fw-beans-factory-nature#beans-factory-lifecycle`).

`InitializingBean` lets a bean perform initialization work after the container has set all necessary properties on the bean (`spring-fw-beans-factory-nature#beans-factory-lifecycle-initializingbean`).

The documentation recommends against `InitializingBean`, because it unnecessarily couples the code to Spring (`spring-fw-beans-factory-nature#beans-factory-lifecycle-initializingbean`).

`@PostConstruct` and initialization methods in general are executed within the container's singleton creation lock (`spring-fw-beans-factory-nature#beans-factory-lifecycle-initializingbean`).

Implementing `DisposableBean` lets a bean get a callback when the container that contains it is destroyed (`spring-fw-beans-factory-nature#beans-factory-lifecycle-disposablebean`).

Spring supports inference of destroy methods, detecting a public `close` or `shutdown` method (`spring-fw-beans-factory-nature#beans-factory-lifecycle-disposablebean`).

The container guarantees that a configured initialization callback is called immediately after a bean is supplied with all dependencies (`spring-fw-beans-factory-nature#beans-factory-lifecycle-default-init-destroy-methods`).

The initialization callback is called on the raw bean reference, so AOP interceptors are not yet applied to the bean (`spring-fw-beans-factory-nature#beans-factory-lifecycle-default-init-destroy-methods`).

In a non-web application, you register a shutdown hook with the JVM by calling `registerShutdownHook()` on `ConfigurableApplicationContext`, which calls the destroy methods on your singleton beans (`spring-fw-beans-factory-nature#beans-factory-shutdown`).

Spring's web-based `ApplicationContext` implementations already have code in place to shut down the container gracefully when the web application is shut down (`spring-fw-beans-factory-nature#beans-factory-shutdown`).

As of Spring 2.5, a bean has three options for lifecycle behavior: the `InitializingBean` and `DisposableBean` interfaces, custom `init()` and `destroy()` methods, and the `@PostConstruct` and `@PreDestroy` annotations (`spring-fw-beans-factory-nature#beans-factory-lifecycle-combined-effects`).

If the same method name is configured for more than one lifecycle mechanism, that method is run once (`spring-fw-beans-factory-nature#beans-factory-lifecycle-combined-effects`).

With different initialization methods, the order is the `@PostConstruct` methods, then `afterPropertiesSet()` of `InitializingBean`, then a custom configured `init()` method (`spring-fw-beans-factory-nature#beans-factory-lifecycle-combined-effects`).

Destroy methods are called in the same order: the `@PreDestroy` methods, then `destroy()` of `DisposableBean`, then a custom configured destroy method (`spring-fw-beans-factory-nature#beans-factory-lifecycle-combined-effects`).

```java snippet=m05-l01/LifecycleOrder.java
import org.springframework.beans.factory.DisposableBean;
import org.springframework.beans.factory.InitializingBean;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class LifecycleOrder {
    static class Resource implements InitializingBean, DisposableBean {
        Resource() { System.out.println("constructor"); }
        @Autowired void setName(String name) { System.out.println("injection"); }
        @Override public void afterPropertiesSet() { System.out.println("after properties set"); }
        void init() { System.out.println("custom init"); }
        @Override public void destroy() { System.out.println("disposable destroy"); }
        void release() { System.out.println("custom release"); }
    }
    static class Tracer implements BeanPostProcessor {
        @Override public Object postProcessBeforeInitialization(Object bean, String name) {
            if (bean instanceof Resource) System.out.println("post-processor before");
            return bean;
        }
        @Override public Object postProcessAfterInitialization(Object bean, String name) {
            if (bean instanceof Resource) System.out.println("post-processor after");
            return bean;
        }
    }
    @Configuration
    static class Config {
        @Bean static Tracer tracer() { return new Tracer(); }
        @Bean String name() { return "resource"; }
        @Bean(initMethod = "init", destroyMethod = "release") Resource resource() { return new Resource(); }
    }
    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            System.out.println("context ready");
        }
    }
}
```

:::diagram{kind="flow" caption="The steps of a singleton bean from instantiation to destruction"}
description: The container instantiates the bean, sets its dependencies, calls the post-processor before initialization, runs the initialization callbacks, calls the post-processor after initialization, and runs the destruction callbacks when the container is destroyed.
create: Instantiate the bean
inject: Set its dependencies
before: BeanPostProcessor before initialization
init: Initialization callbacks
after: BeanPostProcessor after initialization
destroy: Destruction callbacks
create -> inject
inject -> before
before -> init
init -> after
after -> destroy: container destroyed
:::

For a prototype bean, initialization callbacks are called, but configured destruction callbacks are not (`spring-fw-beans-factory-scopes#beans-factory-scopes-prototype`).

The client code must clean up prototype-scoped objects and release the expensive resources that they hold (`spring-fw-beans-factory-scopes#beans-factory-scopes-prototype`).

`BeanPostProcessor` instances operate on bean instances: the container instantiates a bean instance and then they do their work (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

For each bean instance, the post-processor gets a callback both before the initialization methods are called and after any bean initialization callbacks (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

A bean post-processor typically checks for callback interfaces, or it may wrap a bean with a proxy (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

An `ApplicationContext` automatically detects any beans in the configuration metadata that implement the `BeanPostProcessor` interface (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

You can set the `order` property of a `BeanPostProcessor` only if it implements the `Ordered` interface (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

`BeanPostProcessor` instances added programmatically do not respect the `Ordered` interface (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

`BeanPostProcessor` instances registered programmatically are always processed before those registered through auto-detection, regardless of any explicit ordering (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

Because AOP auto-proxying is implemented as a `BeanPostProcessor` itself, neither `BeanPostProcessor` instances nor the beans they directly reference are eligible for auto-proxying (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

To change the bean definition itself, you use a `BeanFactoryPostProcessor` (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

A `BeanFactoryPostProcessor` can read the configuration metadata and potentially change it before the container instantiates any beans other than `BeanFactoryPostProcessor` instances (`spring-fw-beans-factory-extension#beans-factory-extension-factory-postprocessors`).

Working with bean instances inside a `BeanFactoryPostProcessor` causes premature bean instantiation, which may bypass bean post processing (`spring-fw-beans-factory-extension#beans-factory-extension-factory-postprocessors`).

A `@Bean` method that returns a `BeanFactoryPostProcessor` in a `@Configuration` class should be declared `static`, to avoid lifecycle conflicts with annotation processing such as `@Autowired`, `@Value` and `@PostConstruct` in the configuration class (`spring-fw-beans-factory-extension#beans-factory-extension-factory-postprocessors`).

The `@Autowired`, `@Inject`, `@Value` and `@Resource` annotations are handled by Spring `BeanPostProcessor` implementations, so you cannot apply them within your own `BeanPostProcessor` or `BeanFactoryPostProcessor` types (`spring-fw-beans-annotation-config-autowired#page-title`).

## Injection, circular dependencies and candidate selection
<!-- bullets: 5.1.c -->

Injection is how a bean receives its collaborators. Constructor injection fixes them when the object is created, so the object can be immutable and never holds a missing required dependency. Setter injection suits optional dependencies. When two beans each need the other through their constructors, the container cannot build either of them. When several beans qualify for one injection point, `@Primary` and `@Qualifier` tell the container which to choose.

Constructor-based DI is accomplished by the container invoking a constructor with a number of arguments, each representing a dependency (`spring-fw-beans-dependencies-factory-collaborators#beans-constructor-injection`).

Setter-based DI is accomplished by the container calling setter methods on your beans after invoking a no-argument constructor or a no-argument static factory method (`spring-fw-beans-dependencies-factory-collaborators#beans-setter-injection`).

The `ApplicationContext` also supports setter-based DI after some dependencies have already been injected through the constructor (`spring-fw-beans-dependencies-factory-collaborators#beans-setter-injection`).

The Spring team generally advocates constructor injection, as it lets you implement application components as immutable objects and ensures that required dependencies are not null (`spring-fw-beans-dependencies-factory-collaborators#beans-setter-injection`).

Setter injection should primarily be used for optional dependencies that can be assigned reasonable default values within the class (`spring-fw-beans-dependencies-factory-collaborators#beans-setter-injection`).

An `@Autowired` annotation on a constructor is not necessary if the target bean defines only one constructor (`spring-fw-beans-annotation-config-autowired#page-title`).

The default behavior is to treat annotated methods and fields as indicating required dependencies (`spring-fw-beans-annotation-config-autowired#page-title`).

A non-required field is not populated at all when its dependency is not available, which leaves its default value in place (`spring-fw-beans-annotation-config-autowired#page-title`).

A non-required method is not called at all if its dependency is not available (`spring-fw-beans-annotation-config-autowired#page-title`).

By default, autowiring fails when no matching candidate beans are available for a given injection point (`spring-fw-beans-annotation-config-autowired#page-title`).

Adding `@Autowired` to a field or method that expects an array of a type provides all beans of that type from the `ApplicationContext` (`spring-fw-beans-annotation-config-autowired#page-title`).

A typed `Map` can be autowired as long as the expected key type is `String`: the values are all beans of the expected type, and the keys are the bean names (`spring-fw-beans-annotation-config-autowired#page-title`).

`@Order` values may influence priorities at injection points, but they do not influence singleton startup order, which is determined by dependency relationships and `@DependsOn` declarations (`spring-fw-beans-annotation-config-autowired#page-title`).

`@Autowired` also considers self references for injection, but self injection is a fallback mechanism: regular dependencies on other components always have precedence, and self references always end up with the lowest precedence (`spring-fw-beans-annotation-config-autowired#page-title`).

If you use predominantly constructor injection, it is possible to create an unresolvable circular dependency scenario (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

If classes A and B are injected into each other through constructors, the container detects the circular reference at runtime and throws a `BeanCurrentlyInCreationException` (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

A circular dependency between bean A and bean B forces one of the beans to be injected into the other prior to being fully initialized itself (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

Although it is not recommended, you can configure circular dependencies with setter injection (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

```java snippet=m05-l01/CircularInjection.java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class CircularInjection {
    static class A { B b; A() {} A(B b) { this.b = b; } @Autowired void setB(B b) { this.b = b; } }
    static class B { A a; B() {} B(A a) { this.a = a; } @Autowired void setA(A a) { this.a = a; } }

    @Configuration
    static class ByConstructor {
        @Bean A a(B b) { return new A(b); }
        @Bean B b(A a) { return new B(a); }
    }

    @Configuration
    static class BySetter {
        @Bean A a() { return new A(); }
        @Bean B b() { return new B(); }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(ByConstructor.class)) {
            System.out.println("constructor injection started");
        } catch (RuntimeException failure) {
            Throwable root = failure;
            while (root.getCause() != null) root = root.getCause();
            System.out.println("constructor injection failed with " + root.getClass().getSimpleName());
        }
        try (var context = new AnnotationConfigApplicationContext(BySetter.class)) {
            var a = context.getBean(A.class);
            System.out.println("setter injection closes the cycle: " + (a.b.a == a));
        }
    }
}
```

In `CircularInjection`, the two beans that take each other through constructors end in `constructor injection failed with BeanCurrentlyInCreationException`, and the two that take each other through setters end in `setter injection closes the cycle: true`.

`@Primary` indicates that a particular bean should be given preference when multiple beans are candidates to be autowired to a single-valued dependency (`spring-fw-beans-annotation-config-autowired-primary#page-title`).

If exactly one primary bean exists among the candidates, it becomes the autowired value (`spring-fw-beans-annotation-config-autowired-primary#page-title`).

As of 6.2, the `@Fallback` annotation demarcates any beans other than the regular ones to be injected (`spring-fw-beans-annotation-config-autowired-primary#page-title`).

`@Qualifier` associates qualifier values with specific arguments, narrowing the set of type matches so that a specific bean is chosen for each argument (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

Qualifier values do not semantically express a reference to a unique bean id (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

Qualifiers do not have to be unique, and they constitute filtering criteria (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

With no qualifier, primary marker or fallback marker, Spring matches the injection point name against the target bean names and chooses the same-named candidate (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

Since version 6.1, matching by parameter name requires the `-parameters` Java compiler flag to be present (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

```java snippet=m05-l01/CandidateSelection.java
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;

public class CandidateSelection {
    interface Notifier { String name(); }

    record Named(String name) implements Notifier {}

    record Consumer(String label, Notifier notifier) {}

    @Configuration
    static class Config {
        @Bean @Primary Notifier email() { return new Named("email"); }
        @Bean Notifier sms() { return new Named("sms"); }
        @Bean Consumer byPrimary(Notifier notifier) { return new Consumer("byPrimary", notifier); }
        @Bean Consumer byQualifier(@Qualifier("sms") Notifier notifier) { return new Consumer("byQualifier", notifier); }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            context.getBeansOfType(Consumer.class).values().stream()
                .sorted(java.util.Comparator.comparing(Consumer::label))
                .forEach(c -> System.out.println(c.label() + " -> " + c.notifier().name()));
        }
    }
}
```

`CandidateSelection` prints `byPrimary -> email` and `byQualifier -> sms`: the unqualified injection point received the `@Primary` bean, and the `@Qualifier("sms")` injection point received the other one.

A lazy-initialized bean tells the IoC container to create a bean instance when it is first requested, rather than at startup (`spring-fw-beans-factory-lazy-init#page-title`).

When a lazy-initialized bean is a dependency of a singleton bean that is not lazy-initialized, the `ApplicationContext` creates the lazy-initialized bean at startup (`spring-fw-beans-factory-lazy-init#page-title`).

You can control lazy initialization for a set of beans with the `@Lazy` annotation on a `@Configuration` class (`spring-fw-beans-factory-lazy-init#page-title`).

## Configuration classes, conditions and profiles
<!-- bullets: 5.1.d -->

A `@Configuration` class is a source of bean definitions written in Java. In full mode a call from one `@Bean` method to another goes through the container, so it returns the managed bean. In lite mode the same call is a plain Java call and creates a new object. `@Conditional` and `@Profile` decide whether a definition is registered at all, which lets one code base register different beans in different environments.

Annotating a class with `@Configuration` indicates that its primary purpose is as a source of bean definitions (`spring-fw-beans-java-basic-concepts#page-title`).

`@Configuration` classes let inter-bean dependencies be defined by calling other `@Bean` methods in the same class (`spring-fw-beans-java-basic-concepts#page-title`).

`@Bean` methods are normally declared within `@Configuration` classes, so that full configuration class processing applies and cross-method references are redirected to the container's lifecycle management (`spring-fw-beans-java-basic-concepts#page-title`).

This prevents the same `@Bean` method from accidentally being invoked through a regular Java method call (`spring-fw-beans-java-basic-concepts#page-title`).

`@Bean` methods in a class without `@Configuration`, or in a class with `@Configuration(proxyBeanMethods=false)`, are processed in lite mode (`spring-fw-beans-java-basic-concepts#page-title`).

In lite mode, a Java call to a `@Bean` method is not intercepted by the container and creates a new instance every time (`spring-fw-beans-java-basic-concepts#page-title`).

In lite mode, no CGLIB subclassing has to be applied at runtime, which reduces the overhead and the footprint (`spring-fw-beans-java-basic-concepts#page-title`).

```java snippet=m05-l01/ConfigurationModes.java
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class ConfigurationModes {
    static int engines;

    static class Engine { Engine() { engines++; } }
    static class Car { Car(Engine engine) {} }

    @Configuration
    static class Full {
        @Bean Engine engine() { return new Engine(); }
        @Bean Car car() { return new Car(engine()); }
    }

    @Configuration(proxyBeanMethods = false)
    static class Lite {
        @Bean Engine engine() { return new Engine(); }
        @Bean Car car() { return new Car(engine()); }
    }

    static void run(Class<?> configuration) {
        engines = 0;
        try (var context = new AnnotationConfigApplicationContext(configuration)) {
            boolean subclass = context.getBean(configuration).getClass() != configuration;
            System.out.println(configuration.getSimpleName() + ": engines=" + engines + ", subclassed=" + subclass);
        }
    }

    public static void main(String[] args) {
        run(Full.class);
        run(Lite.class);
    }
}
```

`ConfigurationModes` prints `Full: engines=1, subclassed=true` and `Lite: engines=2, subclassed=false`: in lite mode the direct call to `engine()` created a second `Engine` next to the managed bean, and the configuration class was not subclassed.

`@Bean` methods on classes without runtime proxying are not meant to declare inter-bean dependencies at all (`spring-fw-beans-java-basic-concepts#page-title`).

Bean definition profiles provide a mechanism in the core container that allows for registration of different beans in different environments (`spring-fw-beans-environment#beans-definition-profiles`).

The `@Profile` annotation is implemented by using a much more flexible annotation called `@Conditional` (`spring-fw-beans-java-composing#beans-java-conditional`).

`@Conditional` indicates specific `Condition` implementations that should be consulted before a `@Bean` is registered (`spring-fw-beans-java-composing#beans-java-conditional`).

A `@Conditional` annotation on an enclosing `@Configuration` class is applied to a nested `@Configuration` class only if the nested class is reached through the parser's recursion from its enclosing class, or via `@Import` (`spring-fw-beans-java-composing#beans-java-conditional`).

A nested class discovered independently, for example via `@ComponentScan`, is processed using only its own `@Conditional` annotations (`spring-fw-beans-java-composing#beans-java-conditional`).

The `@Profile` annotation lets you indicate that a component is eligible for registration when one or more specified profiles are active (`spring-fw-beans-environment#beans-definition-profiles-java`).

The default profile represents the profile that is enabled if no profile is active (`spring-fw-beans-environment#beans-definition-profiles-default`).

If any profile is enabled, the default profile does not apply (`spring-fw-beans-environment#beans-definition-profiles-default`).

The name of the default profile is `default`, and you can change it with `setDefaultProfiles()` on the `Environment` or with the `spring.profiles.default` property (`spring-fw-beans-environment#beans-definition-profiles-default`).

You can activate profiles declaratively through the `spring.profiles.active` property, set through system environment variables, JVM system properties, servlet context parameters in `web.xml`, or an entry in JNDI (`spring-fw-beans-environment#beans-definition-profiles-enable`).

You can activate multiple profiles at once (`spring-fw-beans-environment#beans-definition-profiles-enable`).

In integration tests, active profiles can be declared by using the `@ActiveProfiles` annotation in the `spring-test` module (`spring-fw-beans-environment#beans-definition-profiles-enable`).

```java snippet=m05-l01/ProfileSelection.java
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Profile;

public class ProfileSelection {
    @Configuration
    static class Config {
        @Bean @Profile("default") String store() { return "embedded"; }
        @Bean @Profile("cloud") String managedStore() { return "managed"; }
    }

    static void run(String... profiles) {
        try (var context = new AnnotationConfigApplicationContext()) {
            context.getEnvironment().setActiveProfiles(profiles);
            context.register(Config.class);
            context.refresh();
            System.out.println(profiles.length + " active profiles -> " + context.getBeansOfType(String.class).values());
        }
    }

    public static void main(String[] args) {
        run();
        run("cloud");
    }
}
```

`ProfileSelection` prints `0 active profiles -> [embedded]` and `1 active profiles -> [managed]`: the bean marked `@Profile("default")` was registered with no active profile and was not registered once `cloud` was active.

## Key points

- Within the container, bean definitions are represented as `BeanDefinition` objects, which include scope, lifecycle callbacks and references to collaborators.
- An `ApplicationContext` includes all the functionality of a `BeanFactory`; a plain `DefaultListableBeanFactory` does not detect bean post-processors by default.
- `singleton` is the default scope, per container and per bean. `prototype` creates a new instance for each request, and its configured destruction callbacks are not called.
- `@PostConstruct` runs first, then `afterPropertiesSet()`, then a custom `init()` method; destruction follows the same order.
- A singleton is created when the container is created, a prototype on each lookup, and a prototype injected into a singleton is supplied once.
- A bean is instantiated, its dependencies are set, then the initialization callbacks run, with the `BeanPostProcessor` called before and after them.
- Programmatically registered `BeanPostProcessor` instances ignore `Ordered` and are processed before auto-detected ones.
- Constructor injection can produce an unresolvable circular dependency, reported as a `BeanCurrentlyInCreationException`.
- Constructor injection suits required dependencies and setter injection optional ones; setter injection can close a cycle that constructor injection cannot.
- `@Primary` gives preference to one candidate; `@Qualifier` values narrow the type matches and need not be unique.
- Since 6.1, matching an injection point name to a bean name requires the `-parameters` compiler flag.
- In lite mode, calls between `@Bean` methods are plain Java calls and create a new instance every time.
- The default profile applies only when no profile is active.
- A nested class discovered by `@ComponentScan` is processed using only its own `@Conditional` annotations.

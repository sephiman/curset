# Stability, resilience and traffic control

## Circuit breaker states
<!-- bullets: 8.4.a -->

A Resilience4j `CircuitBreaker` is implemented via a finite state machine with three normal states, `CLOSED`, `OPEN` and `HALF_OPEN`, and three special states, `METRICS_ONLY`, `DISABLED` and `FORCED_OPEN` (`resilience4j-circuitbreaker#introduction`).

The state of the `CircuitBreaker` changes from `CLOSED` to `OPEN` when the failure rate is equal or greater than a configurable threshold (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

The `CircuitBreaker` also changes from `CLOSED` to `OPEN` when the percentage of slow calls is equal or greater than a configurable threshold (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

By default all exceptions count as a failure (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

The failure rate and slow call rate can only be calculated if a minimum number of calls were recorded (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

If the minimum number of required calls is 10 and only 9 calls have been evaluated, the `CircuitBreaker` does not trip open even if all 9 calls have failed (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

The `CircuitBreaker` rejects calls with a `CallNotPermittedException` when it is `OPEN` (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

After a wait time duration has elapsed, the `CircuitBreaker` changes from `OPEN` to `HALF_OPEN` and permits a configurable number of calls to see if the backend is still unavailable or has become available again (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

In `HALF_OPEN`, further calls are rejected with a `CallNotPermittedException` until all permitted calls have completed (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

If the failure rate or slow call rate is then equal or greater than the configured threshold, the state changes back to `OPEN` (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

If the failure rate and slow call rate are below the threshold, the state changes back to `CLOSED` (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

`METRICS_ONLY` and `DISABLED` always allow access, and `FORCED_OPEN` always denies access (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

:::esquema{kind=tabla title="CircuitBreaker transitions"}
| From | To | When | Source |
|---|---|---|---|
| `CLOSED` | `OPEN` | The failure rate or slow call rate is equal or greater than its threshold | `resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds` |
| `OPEN` | `HALF_OPEN` | A wait time duration has elapsed | `resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds` |
| `HALF_OPEN` | `OPEN` | The failure rate or slow call rate is equal or greater than the threshold | `resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds` |
| `HALF_OPEN` | `CLOSED` | The failure rate and slow call rate are below the threshold | `resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds` |
:::

## Sliding windows, thresholds and fallbacks
<!-- bullets: 8.4.a -->

The `CircuitBreaker` uses a sliding window to store and aggregate the outcome of calls (`resilience4j-circuitbreaker#introduction`).

The count-based sliding window aggregates the outcome of the last N calls, and the time-based sliding window aggregates the outcome of the calls of the last N seconds (`resilience4j-circuitbreaker#introduction`).

The count-based sliding window is implemented with a circular array of N measurements (`resilience4j-circuitbreaker#count-based-sliding-window`).

The time-based sliding window is implemented with a circular array of N partial aggregations, called buckets (`resilience4j-circuitbreaker#time-based-sliding-window`).

The time to retrieve a snapshot of a sliding window is constant, O(1), since the snapshot is pre-aggregated (`resilience4j-circuitbreaker#count-based-sliding-window`).

:::esquema{kind=tabla title="Default values of the CircuitBreakerConfig in Resilience4j"}
| Config property | Default | Source |
|---|---|---|
| `failureRateThreshold` | 50 | `resilience4j-circuitbreaker#create-and-configure-a-circuitbreaker` |
| `slowCallRateThreshold` | 100 | `resilience4j-circuitbreaker#create-and-configure-a-circuitbreaker` |
| `slowCallDurationThreshold` | 60000 ms | `resilience4j-circuitbreaker#create-and-configure-a-circuitbreaker` |
| `permittedNumberOfCallsInHalfOpenState` | 10 | `resilience4j-circuitbreaker#create-and-configure-a-circuitbreaker` |
| `slidingWindowType` | `COUNT_BASED` | `resilience4j-circuitbreaker#create-and-configure-a-circuitbreaker` |
| `slidingWindowSize` | 100 | `resilience4j-circuitbreaker#create-and-configure-a-circuitbreaker` |
| `minimumNumberOfCalls` | 100 | `resilience4j-circuitbreaker#create-and-configure-a-circuitbreaker` |
| `waitDurationInOpenState` | 60000 ms | `resilience4j-circuitbreaker#create-and-configure-a-circuitbreaker` |
:::

The sliding window does not mean that only 15 calls are allowed to run concurrently when its size is 15 (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

If 20 concurrent threads ask for permission to execute a function and the `CircuitBreaker` is closed, all threads are allowed to invoke the function (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

The `CircuitBreaker` does not synchronize the function call (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

To restrict the number of concurrent threads, a `Bulkhead` is used, and a `Bulkhead` can be combined with a `CircuitBreaker` (`resilience4j-circuitbreaker#failure-rate-and-slow-call-rate-thresholds`).

Any `Callable`, `Supplier`, `Runnable`, `Consumer` or `CompletionStage`, among others, can be decorated with a `CircuitBreaker` (`resilience4j-circuitbreaker#decorate-and-execute-a-functional-interface`).

A decorated function invoked with `Try.of` allows chaining further functions with `map`, `flatMap`, `filter`, `recover` or `andThen` (`resilience4j-circuitbreaker#decorate-and-execute-a-functional-interface`).

The chained functions are only invoked if the `CircuitBreaker` is `CLOSED` or `HALF_OPEN` (`resilience4j-circuitbreaker#decorate-and-execute-a-functional-interface`).

## Retries with exponential backoff and jitter
<!-- bullets: 8.4.b -->

In Resilience4j, `maxAttempts` defaults to 3 and counts the initial call as the first attempt (`resilience4j-retry#create-and-configure-retry`).

In Resilience4j, `waitDuration` defaults to 500 ms as a fixed wait duration between retry attempts (`resilience4j-retry#create-and-configure-retry`).

By default the wait duration of a Resilience4j `Retry` remains constant (`resilience4j-retry#create-and-configure-retry`).

An `IntervalFunction` calculates the wait duration for every attempt instead of a fixed wait duration (`resilience4j-retry#use-a-custom-intervalfunction`).

Resilience4j provides several factory methods to simplify the creation of an `IntervalFunction` (`resilience4j-retry#use-a-custom-intervalfunction`).

An `intervalBiFunction` used together with `intervalFunction` throws an `IllegalStateException` (`resilience4j-retry#create-and-configure-retry`).

If provided, the Kafka client backoff increases exponentially for each failed request, up to `retry.backoff.max.ms` (`kafka-producer-configs#retry.backoff.max.ms`).

To prevent all clients from being synchronized upon retry, Kafka applies a randomized jitter with a factor of 0.2 to the backoff, so it falls within a range between 20% below and 20% above the computed value (`kafka-producer-configs#retry.backoff.max.ms`).

The default of `retry.backoff.max.ms` is 1000 (1 second) (`kafka-producer-configs#retry.backoff.max.ms`).

If `retry.backoff.ms` is higher than `retry.backoff.max.ms`, `retry.backoff.max.ms` is used as a constant backoff from the beginning, without any exponential increase (`kafka-producer-configs#retry.backoff.max.ms`).

By default, Spring's `ExponentialBackOff` retries indefinitely, and giving up after some number of retry attempts requires calculating the `maxElapsedTime` (`spring-kafka-error-handling#exp-backoff`).

Since version 2.7.3, Spring for Apache Kafka provides `ExponentialBackOffWithMaxRetries`, which receives the `maxRetries` property and automatically calculates the `maxElapsedTime` (`spring-kafka-error-handling#exp-backoff`).

```java snippet=m08-l04/BackoffSchedule.java
public class BackoffSchedule {
    static long next(long wait, double multiplier, long max) {
        return Math.min(Math.round(wait * multiplier), max);
    }

    public static void main(String[] args) {
        long wait = 1_000;
        StringBuilder waits = new StringBuilder();
        for (int retry = 1; retry <= 6; retry++) {
            if (retry > 1) {
                waits.append(", ");
            }
            waits.append(wait);
            wait = next(wait, 2.0, 10_000);
        }
        System.out.println(waits);
        System.out.println(Math.round(10_000 * 0.8) + " to " + Math.round(10_000 * 1.2));
    }
}
```

The program prints the waits 1000, 2000, 4000, 8000, 10000 and 10000 milliseconds for six retries of a capped exponential backoff with an initial wait of 1000 ms, a multiplier of 2 and a maximum of 10000 ms.

The program prints 8000 to 12000 as the range of a jitter factor of 0.2 around a computed wait of 10000 ms.

:::judgement{source="Marc Brooker, Exponential Backoff And Jitter, AWS Architecture Blog" ref="aws-exponential-backoff-jitter#adding-backoff"}
According to Marc Brooker, capped exponential backoff means that clients multiply their backoff by a constant after each attempt, up to some maximum value. In his simulation of contending clients, backoff helped a small amount but did not solve the problem, because there were still clusters of calls.
:::

:::judgement{source="Marc Brooker, Exponential Backoff And Jitter, AWS Architecture Blog" ref="aws-exponential-backoff-jitter#adding-jitter"}
According to Marc Brooker, the solution is not to remove backoff but to add jitter, which spreads out the spikes to an approximately constant rate. With 100 contending clients, jitter reduced the call count by more than half, and he considers jittered backoff a standard approach for remote clients.
:::

:::judgement{source="Marc Brooker, Exponential Backoff And Jitter, AWS Architecture Blog" ref="aws-exponential-backoff-jitter#adding-jitter"}
According to Marc Brooker, "Full Jitter" is the algorithm that adds jitter to the backoff, "Equal Jitter" always keeps some of the backoff and jitters by a smaller amount, and "Decorrelated Jitter" increases the maximum jitter based on the last random value. In his simulation, "Full Jitter" and "Equal Jitter" made about the same number of calls, "Decorrelated Jitter" made more, and "Equal Jitter" took much longer than "Full Jitter".
:::

:::judgement{source="AWS, aws-arch-backoff-simulator (source code of the AWS Architecture Blog post Exponential Backoff And Jitter)" ref="aws-arch-backoff-simulator#top"}
According to the simulator code that AWS published for the post, the capped exponential value is the smaller of the cap and `2^n * base`, and the "Full Jitter" backoff is a uniform random value between 0 and that capped value. In that code the client increments its attempt counter before it computes the backoff, so the first retry uses `n = 1`.
:::

## Bulkheads
<!-- bullets: 8.4.c -->

Resilience4j provides two bulkhead implementations that limit the number of concurrent executions, a `SemaphoreBulkhead` which uses semaphores and a `FixedThreadPoolBulkhead` which uses a bounded queue and a fixed thread pool (`resilience4j-bulkhead#introduction`).

With the `SemaphoreBulkhead`, it is up to the client to ensure a thread pool size that is consistent with the bulkhead configuration (`resilience4j-bulkhead#introduction`).

The default `queueCapacity` of a `ThreadPoolBulkhead` is 100, and its default `keepAliveDuration` is 20 ms (`resilience4j-bulkhead#create-and-configure-a-threadpoolbulkhead`).

## Rate limiting and quotas
<!-- bullets: 8.4.c -->

Resilience4j's `RateLimiter` splits all nanoseconds from the start of epoch into cycles, each with a duration configured by `limitRefreshPeriod` (`resilience4j-ratelimiter#internals`).

At the start of each cycle, the `RateLimiter` sets the number of active permissions to `limitForPeriod` (`resilience4j-ratelimiter#internals`).

The default implementation of `RateLimiter` is `AtomicRateLimiter`, which manages its state via an `AtomicReference` (`resilience4j-ratelimiter#internals`).

A Redis rate limiter is a single shared store that every service instance queries on every request, returning an allow or deny decision (`redis-rate-limiter#how-redis-supports-the-solution`).

`INCR` and `EXPIRE` give atomic fixed-window counters with automatic time-window cleanup (`redis-rate-limiter#how-redis-supports-the-solution`).

Hashes, sorted sets and strings cover the data shapes needed for sliding window and token bucket algorithms (`redis-rate-limiter#how-redis-supports-the-solution`).

Lua scripting with `EVAL` keeps the read-decide-update cycle atomic, so concurrent requests cannot double-spend tokens or lose counter updates (`redis-rate-limiter#how-redis-supports-the-solution`).

A Redis solution can run fixed window, sliding window and token bucket algorithms on a single Redis deployment (`redis-rate-limiter#what-you-can-expect-from-a-redis-solution`).

The token buckets of the RFC 2697 meter are initially, at time 0, full (`rfc2697#section-3`).

The maximum size of the RFC 2697 token bucket C is CBS (`rfc2697#section-3`).

In the RFC 2697 meter, the token count Tc is incremented by one CIR times per second while Tc is less than CBS (`rfc2697#section-3`).

In a Redis token bucket rate limiter, tokens accumulate over time up to a maximum capacity, and each request consumes one token (`redis-ratelimiting-algorithms#how-it-works-3`).

In a Redis token bucket rate limiter, requests are denied when the bucket is empty, until more tokens refill (`redis-ratelimiting-algorithms#how-it-works-3`).

On each new attempt, a Redis sliding window log removes the entries older than the window, counts what is left, and adds the new entry if the count is below the limit (`redis-ratelimiting-algorithms#how-it-works-1`).

The `RateLimit-Policy` header field of the IETF HTTP API draft is a quota policy, defined by the server, that client HTTP requests will consume (`ietf-httpapi-ratelimit-headers#content`).

The `RateLimit` header field of the IETF HTTP API draft is the quota currently available under a specific policy (`ietf-httpapi-ratelimit-headers#content`).

Network bandwidth quotas in Kafka define byte-rate thresholds, and request rate quotas define CPU utilization thresholds as a percentage of network and I/O threads (`kafka-design#quotas`).

In Kafka, each unique client group receives a fixed quota as configured by the cluster, and the quota is defined on a per-broker basis (`kafka-design#enforcement`).

When a Kafka broker detects a quota violation, it first computes the delay needed to bring the violating client under its quota and returns a response with the delay immediately (`kafka-design#enforcement`).

The Kafka broker then mutes the channel to the client until the delay is over (`kafka-design#enforcement`).

Kafka measures byte-rate and thread utilization over multiple small windows, for example 30 windows of 1 second each, to detect and correct quota violations quickly (`kafka-design#enforcement`).

Large measurement windows in Kafka lead to large bursts of traffic followed by long delays (`kafka-design#enforcement`).

:::judgement{source="Google, Site Reliability Engineering, chapter 21, Handling Overload" ref="sre-book-handling-overload#per-customer-limits-K7sAuk"}
According to the Google SRE book, when global overload occurs it is vital that the service only delivers error responses to misbehaving customers while other customers remain unaffected, so service owners define per-customer quotas according to negotiated usage.
:::

:::judgement{source="Google, Site Reliability Engineering, chapter 21, Handling Overload" ref="sre-book-handling-overload#client-side-throttling-a7sYUg"}
According to the Google SRE book, when a client detects that a significant portion of its recent requests have been rejected due to out-of-quota errors, it starts self-regulating and caps its outgoing traffic, so that requests above the cap fail locally without reaching the network. The book calls this client-side throttling.
:::

## Load shedding and criticality
<!-- bullets: 8.4.c -->

:::judgement{source="Google, Site Reliability Engineering, chapter 22, Addressing Cascading Failures" ref="sre-book-cascading-failures#xref_cascading-failure_load-shed-graceful-degredation"}
According to the Google SRE book, load shedding drops some proportion of load by dropping traffic as the server approaches overload conditions, with the goal of keeping the server from running out of RAM, failing health checks or serving with extremely high latency, while still doing as much useful work as it can.
:::

:::judgement{source="Google, Site Reliability Engineering, chapter 22, Addressing Cascading Failures" ref="sre-book-cascading-failures#xref_cascading-failure_load-shed-graceful-degredation"}
According to the Google SRE book, graceful degradation takes load shedding one step further by reducing the amount of work to be performed, for example by decreasing the quality of responses, and it should not trigger very often.
:::

:::judgement{source="Google, Site Reliability Engineering, chapter 21, Handling Overload" ref="sre-book-handling-overload#criticality-00sDCK"}
According to the Google SRE book, each request to a backend carries one of four criticality values, CRITICAL_PLUS, CRITICAL, SHEDDABLE_PLUS and SHEDDABLE, and an overloaded task rejects requests of lower criticalities sooner.
:::

## Timeouts and deadline propagation
<!-- bullets: 8.4.c -->

A Resilience4j `TimeLimiterConfig` configures the timeout duration and whether cancel should be called on the running future (`resilience4j-timeout#create-and-configure-timelimiter`).

A deadline specifies a point in time past which a client is unwilling to wait for a response from a server (`grpc-deadlines#overview`).

A timeout is the maximum duration of time that a call can take, and it can be converted to a deadline by adding the timeout to the current time when the application starts a call (`grpc-deadlines#overview`).

When a gRPC server also acts as a client, it should honor the deadline set by the original client (`grpc-deadlines#deadline-propagation`).

Automatic propagation of the deadline from an incoming RPC to an outgoing one is enabled by default in Java and Go, and needs to be explicitly enabled in C++ (`grpc-deadlines#deadline-propagation`).

Propagating a deadline as-is to a server can be problematic, because the clocks on the two servers might not be synchronized (`grpc-deadlines#deadline-propagation`).

gRPC converts the deadline to a timeout from which the already elapsed time is deducted, which shields the system from clock skew (`grpc-deadlines#deadline-propagation`).

:::judgement{source="Google, Site Reliability Engineering, chapter 22, Addressing Cascading Failures" ref="sre-book-cascading-failures#deadline-propagation-1"}
According to the Google SRE book, with deadline propagation a deadline is set high in the stack and the tree of RPCs from an initial request all have the same absolute deadline. In its example, if server A selects a 30-second deadline and processes the request for 7 seconds before sending an RPC to server B, the RPC from A to B has a 23-second deadline.
:::

## Backpressure
<!-- bullets: 8.4.c -->

A back pressure warning for a Flink task means that it is producing data faster than the downstream operators can consume (`flink-back-pressure#back-pressure`).

In Flink, records flow downstream and back pressure is propagated in the opposite direction, up the stream (`flink-back-pressure#back-pressure`).

In a Flink Source to Sink job, a warning for Source means that Sink is consuming data slower than Source is producing (`flink-back-pressure#back-pressure`).

Requests from a throttled Kafka client are effectively blocked from both sides, the broker and the client (`kafka-design#enforcement`).

Even with older Kafka client implementations that do not respect the delay response, the back pressure applied by the broker via muting its socket channel can still handle the throttling of badly behaving clients (`kafka-design#enforcement`).

## Key points

- A Resilience4j `CircuitBreaker` goes from `CLOSED` to `OPEN` when the failure rate or slow call rate reaches its threshold, and from `OPEN` to `HALF_OPEN` after a wait time duration.
- The `CircuitBreaker` cannot calculate a failure rate before the minimum number of calls is recorded.
- A `CircuitBreaker` sliding window does not limit concurrent calls, and a `Bulkhead` does.
- The default wait of a Resilience4j `Retry` is a constant 500 ms, and an `IntervalFunction` replaces it.
- Kafka applies a randomized jitter with a factor of 0.2 to the exponential backoff, so the wait falls between 20% below and 20% above the computed value.
- A Resilience4j `RateLimiter` refreshes the number of permissions at the start of each cycle.
- A Kafka quota is defined per broker, and a violating client receives a delay in the response.
- A gRPC deadline is converted to a timeout with the elapsed time deducted, which shields the system from clock skew.
- Flink back pressure propagates up the stream, from a slow consumer to its producers.

# Networking fundamentals for backend engineers

## Connection set-up and teardown
<!-- bullets: 7.1.a -->

The "three-way handshake" is the procedure used to establish a TCP connection (`rfc9293#section-3.5`).

The principal reason for the three-way handshake is to prevent old duplicate connection initiations from causing confusion (`rfc9293#section-3.5`).

In the basic handshake example, the second peer sends a SYN and acknowledges the SYN it received from the first peer (`rfc9293#section-3.5`).

An ACK does not occupy sequence number space (`rfc9293#section-3.5`).

A TCP implementation must support simultaneous open attempts (`rfc9293#section-3.5`).

The user who closes may continue to receive until the TCP receiver is told that the remote peer has closed also (`rfc9293#section-3.6`).

A TCP endpoint receiving a FIN will ACK it but not send its own FIN until its user has closed the connection also (`rfc9293#section-3.6`).

If an unsolicited FIN arrives from the network, the receiving TCP endpoint can ACK it and tell the user that the connection is closing (`rfc9293#section-3.6`).

A TCP connection may terminate in two ways, the normal close sequence using a FIN handshake and an abort in which one or more RST segments are sent and the connection state is immediately discarded (`rfc9293#section-3.6`).

:::esquema{kind=tabla title="Four TCP states in RFC 9293"}
| State | Meaning | Source |
|---|---|---|
| `LISTEN` | Waiting for a connection request from any remote TCP peer and port | `rfc9293#section-3.3.2` |
| `FIN-WAIT-2` | Waiting for a connection termination request from the remote TCP peer | `rfc9293#section-3.3.2` |
| `CLOSE-WAIT` | Waiting for a connection termination request from the local user | `rfc9293#section-3.3.2` |
| `TIME-WAIT` | Waiting for enough time to pass to be sure the remote TCP peer received the acknowledgment of its connection termination request, and to avoid new connections being impacted by delayed segments from previous connections | `rfc9293#section-3.3.2` |
:::

## Flow control and congestion control
<!-- bullets: 7.1.a -->

The window sent in each segment indicates the range of sequence numbers the data receiver is currently prepared to accept (`rfc9293#section-3.8.6`).

Indicating a small window may restrict the transmission of data to the point of introducing a round-trip delay between each new segment transmitted (`rfc9293#section-3.8.6`).

A TCP receiver should not shrink the window, that is, move the right window edge to the left (`rfc9293#section-3.8.6`).

The congestion window (cwnd) is a sender-side limit on the amount of data the sender can transmit into the network before receiving an acknowledgment, while the receiver's advertised window (rwnd) is a receiver-side limit on the amount of outstanding data (`rfc5681#section-3.1`).

The minimum of cwnd and rwnd governs data transmission (`rfc5681#section-3.1`).

The slow start threshold (ssthresh) is used to determine whether the slow start or congestion avoidance algorithm is used to control data transmission (`rfc5681#section-3.1`).

The slow start algorithm is used when cwnd is below ssthresh, and the congestion avoidance algorithm is used when cwnd is above ssthresh (`rfc5681#section-3.1`).

When SMSS is at most 1095 bytes, the initial window IW is at most 4 * SMSS bytes and at most 4 segments (`rfc5681#section-3.1`).

During slow start, a TCP increments cwnd by at most SMSS bytes for each ACK received that cumulatively acknowledges new data (`rfc5681#section-3.1`).

During congestion avoidance, cwnd is incremented by roughly 1 full-sized segment per round-trip time (RTT) (`rfc5681#section-3.1`).

Upon a timeout, cwnd must be set to no more than the loss window, which equals 1 full-sized segment regardless of the value of IW (`rfc5681#section-3.1`).

The fast retransmit algorithm uses the arrival of 3 duplicate ACKs as an indication that a segment has been lost (`rfc5681#section-3.2`).

After receiving 3 duplicate ACKs, TCP retransmits what appears to be the missing segment without waiting for the retransmission timer to expire (`rfc5681#section-3.2`).

After fast retransmit, the fast recovery algorithm governs the transmission of new data until a non-duplicate ACK arrives (`rfc5681#section-3.2`).

## Keep-alive and head-of-line blocking
<!-- bullets: 7.1.a -->

Implementers may include keep-alives in their TCP implementations, although this practice is not universally accepted (`rfc9293#section-3.8.4`).

To confirm that an idle connection is still active, a keep-alive implementation sends a probe segment designed to elicit a response from the TCP peer (`rfc9293#section-3.8.4`).

If keep-alives are included, the application must be able to turn them on or off for each TCP connection, and they must default to off (`rfc9293#section-3.8.4`).

The keep-alive interval must be configurable and must default to no less than two hours (`rfc9293#section-3.8.4`).

ACK segments that contain no data are not reliably transmitted by TCP (`rfc9293#section-3.8.4`).

A keep-alive mechanism must not interpret failure to respond to any specific probe as a dead connection (`rfc9293#section-3.8.4`).

An implementation should send a keep-alive segment with no data, but may be configurable to send one containing one garbage octet (`rfc9293#section-3.8.4`).

HTTP/1.1 added request pipelining, but this only partially addressed request concurrency and still suffers from application-layer head-of-line blocking (`rfc9113#section-1`).

HTTP/1.0 and HTTP/1.1 clients use multiple connections to a server to make concurrent requests (`rfc9113#section-1`).

HTTP/2 does not address TCP head-of-line blocking (`rfc9113#section-1`).

## DNS resolution and TTL
<!-- bullets: 7.1.b -->

A user does not generate DNS queries directly but makes a request to a resolver, which sends one or more queries to name servers and deals with the error conditions and referrals that result (`rfc1034#section-3.7`).

In the Internet, DNS queries are carried in UDP datagrams or over TCP connections (`rfc1034#section-3.7`).

The response by the name server either answers the question posed in the query, refers the requester to another set of name servers, or signals some error condition (`rfc1034#section-3.7`).

The first step of the resolver algorithm is to see if the answer is in local information, and if so return it to the client (`rfc1034#section-5.3.3`).

If the data is in the cache, it is assumed to be good enough for normal use (`rfc1034#section-5.3.3`).

The data is entered in the cache for future use if its TTL is greater than zero (`rfc1034#section-5.3.3`).

Negative answers have a time to live (TTL) like normal answers (`rfc2308#section-5`).

The TTL of a negative answer is carried by the SOA record of the zone in the authority section of the reply (`rfc2308#section-5`).

The authoritative server takes the TTL of that SOA record from the minimum of the SOA.MINIMUM field and the SOA's TTL (`rfc2308#section-5`).

The DNS protocol supports caching negative responses for up to 68 years (`rfc2308#section-5`).

## DNS caches in the JVM and service discovery in Kubernetes
<!-- bullets: 7.1.b -->

The InetAddress class has a cache to store successful as well as unsuccessful host name resolutions (`javadoc-java-net-inetaddress#inetaddress-caching-heading`).

The result of an unsuccessful host name resolution is cached for a very short period of time (10 seconds) to improve performance (`javadoc-java-net-inetaddress#inetaddress-caching-heading`).

The default setting of networkaddress.cache.ttl is to cache successful lookups for an implementation specific period of time (`javadoc-java-net-inetaddress#inetaddress-caching-heading`).

A networkaddress.cache.ttl value of -1 indicates "cache forever" (`javadoc-java-net-inetaddress#inetaddress-caching-heading`).

In the java.net address cache, a networkaddress.cache.ttl value of 0 means no caching (`java-net-properties#address-cache-heading`).

A name is considered stale if the TTL has expired and an attempt to lookup the host name again was not successful (`javadoc-java-net-inetaddress#inetaddress-caching-heading`).

The three networkaddress.cache properties are security properties, so they are not set by the -D option or the System.setProperty() API (`java-net-properties#address-cache-heading`).

A headless Service is created by explicitly specifying "None" for the cluster IP address (.spec.clusterIP) (`k8s-service#headless-services`).

The string value None is a special case and is not the same as leaving the .spec.clusterIP field unset (`k8s-service#headless-services`).

For a headless Service, a cluster IP is not allocated, kube-proxy does not handle the Service, and the platform does no load balancing or proxying (`k8s-service#headless-services`).

A headless Service reports the endpoint IP addresses of the individual pods via internal DNS records, served through the cluster's DNS service (`k8s-service#headless-services`).

SRV records are created for named ports that are part of normal or headless services (`k8s-dns-service-pod#srv-records`).

For a headless Service, an SRV record resolves to multiple answers, one for each Pod that is backing the Service (`k8s-dns-service-pod#srv-records`).

With the ClusterFirst DNS policy, any DNS query that does not match the configured cluster domain suffix is forwarded to an upstream nameserver by the DNS server (`k8s-dns-service-pod#pod-s-dns-policy`).

Pods running with hostNetwork and ClusterFirst fall back to the behavior of the Default DNS policy (`k8s-dns-service-pod#pod-s-dns-policy`).

## The TLS 1.3 handshake
<!-- bullets: 7.1.c -->

The TLS handshake protocol allows peers to negotiate a protocol version, select cryptographic algorithms, optionally authenticate each other, and establish shared secret keying material (`rfc8446#section-2`).

Once the handshake is complete, the peers use the established keys to protect the application-layer traffic (`rfc8446#section-2`).

TLS supports three basic key exchange modes: (EC)DHE, PSK-only and PSK with (EC)DHE (`rfc8446#section-2`).

In the Key Exchange phase, the peers establish shared keying material and select the cryptographic parameters, and everything after this phase is encrypted (`rfc8446#section-2`).

In the Authentication phase, the server and optionally the client are authenticated, with key confirmation and handshake integrity (`rfc8446#section-2`).

When client and server share a PSK, TLS 1.3 allows the client to send data on the first flight, called early data (`rfc8446#section-2.3`).

0-RTT data is not forward secret, as it is encrypted solely under keys derived using the offered PSK (`rfc8446#section-2.3`).

There are no guarantees of non-replay between connections for 0-RTT data (`rfc8446#section-2.3`).

0-RTT data cannot be duplicated within a connection (`rfc8446#section-2.3`).

## Certificates, chain of trust and mutual TLS
<!-- bullets: 7.1.c -->

The server must send a Certificate message whenever the agreed-upon key exchange method uses certificates for authentication (`rfc8446#section-4.4.2`).

Each certificate in the chain after the sender's certificate should directly certify the one immediately preceding it (`rfc8446#section-4.4.2`).

A certificate that specifies a trust anchor may be omitted from the chain, provided that supported peers are known to possess any omitted certificates (`rfc8446#section-4.4.2`).

The CertificateVerify message provides explicit proof that an endpoint possesses the private key corresponding to its certificate (`rfc8446#section-4.4.3`).

A server that is authenticating with a certificate may optionally request a certificate from the client (`rfc8446#section-4.3.2`).

The client must send a Certificate message if and only if the server has requested client authentication via a CertificateRequest message (`rfc8446#section-4.4.2`).

If the server requests client authentication but no suitable certificate is available, the client must send a Certificate message containing no certificates (`rfc8446#section-4.4.2`).

Servers that are authenticating with a PSK must not send the CertificateRequest message in the main handshake (`rfc8446#section-4.3.2`).

The certificate_authorities extension indicates the certificate authorities which an endpoint supports and which should be used by the receiving endpoint to guide certificate selection (`rfc8446#section-4.2.4`).

## SNI and ALPN
<!-- bullets: 7.1.c -->

TLS does not provide a mechanism for a client to tell a server the name of the server it is contacting (`rfc6066#section-3`).

Providing the server name facilitates secure connections to servers that host multiple virtual servers at a single underlying network address (`rfc6066#section-3`).

Clients may include an extension of type "server_name", Server Name Indication (SNI), in the extended client hello (`rfc6066#section-3`).

The ServerNameList must not contain more than one name of the same name_type (`rfc6066#section-3`).

The only server names supported are DNS hostnames (`rfc6066#section-3`).

The client may include the Application-Layer Protocol Negotiation (ALPN) extension, application_layer_protocol_negotiation, in its ClientHello message (`rfc7301#section-3.1`).

The ProtocolNameList contains the list of protocols advertised by the client, in descending order of preference (`rfc7301#section-3.1`).

In the ServerHello, the ProtocolNameList must contain exactly one ProtocolName (`rfc7301#section-3.1`).

The server should select the most highly preferred protocol that it supports and that is also advertised by the client (`rfc7301#section-3.2`).

If the server supports no protocols that the client advertises, it must respond with a fatal no_application_protocol alert (`rfc7301#section-3.2`).

The server must not respond with a selected protocol and subsequently use a different protocol for application data exchange (`rfc7301#section-3.2`).

## Connect and read timeouts
<!-- bullets: 7.1.d -->

Spring Boot's HTTP clients share common settings, including connection timeouts and read timeouts (`spring-boot-io-rest-client#io.rest-client.global-configuration`).

The same configuration can be applied to all auto-configured clients with the spring.http.clients properties (`spring-boot-io-rest-client#io.rest-client.global-configuration`).

If no request factory is specified when the RestClient is built, it uses the Apache or Jetty HttpClient if they are available on the classpath (`spring-fw-integration-rest-clients#rest-request-factories`).

Otherwise, if the java.net.http module is loaded, RestClient uses Java's HttpClient (`spring-fw-integration-rest-clients#rest-request-factories`).

HttpClient.connectTimeout() returns an Optional containing the connect timeout duration for the client (`javadoc-java-net-http-httpclient#connectTimeout()`).

If the connect timeout duration was not set in the client's builder, the Optional is empty (`javadoc-java-net-http-httpclient#connectTimeout()`).

HttpRequest.timeout() returns an Optional containing the request's timeout duration, which is empty if the request's builder did not set it (`javadoc-java-net-http-httprequest#timeout()`).

```java snippet=m07-l01/Timeouts.java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.time.Duration;
import java.util.Optional;

public class Timeouts {
    static String shown(Optional<Duration> timeout) {
        return timeout.map(Duration::toString).orElse("none");
    }

    public static void main(String[] args) {
        URI uri = URI.create("http://localhost/");
        System.out.println(shown(HttpClient.newHttpClient().connectTimeout()));
        System.out.println(shown(HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(2)).build().connectTimeout()));
        System.out.println(shown(HttpRequest.newBuilder(uri).build().timeout()));
        System.out.println(shown(HttpRequest.newBuilder(uri).timeout(Duration.ofSeconds(1)).build().timeout()));
    }
}
```

A client built without a connect timeout has an empty `Optional` as `connectTimeout()`, so the snippet prints `none`.

A client built with `connectTimeout(Duration.ofSeconds(2))` has `Optional[PT2S]` as its connect timeout, so the snippet prints `PT2S`.

A request built with `timeout(Duration.ofSeconds(1))` has `Optional[PT1S]` as its `timeout()`, so the snippet prints `PT1S`.

With a positive SO_TIMEOUT, a read() call on the InputStream of a Socket blocks for only that many milliseconds (`javadoc-java-net-socket#setSoTimeout(int)`).

If the timeout expires, a java.net.SocketTimeoutException is raised, though the Socket is still valid (`javadoc-java-net-socket#setSoTimeout(int)`).

A socket timeout of zero is interpreted as an infinite timeout (`javadoc-java-net-socket#setSoTimeout(int)`).

The SO_TIMEOUT option must be enabled prior to entering the blocking operation to have effect (`javadoc-java-net-socket#setSoTimeout(int)`).

Socket.setSoTimeout throws IllegalArgumentException if the timeout is negative (`javadoc-java-net-socket#setSoTimeout(int)`).

Socket.setKeepAlive(boolean) enables or disables SO_KEEPALIVE (`javadoc-java-net-socket#setKeepAlive(boolean)`).

## Connection pools and stale connections
<!-- bullets: 7.1.d -->

HTTP/1.1 defaults to the use of persistent connections, allowing multiple requests and responses to be carried over a single connection (`rfc9112#section-9.3`).

A client must read the entire response message body if it intends to reuse the same connection for a subsequent request (`rfc9112#section-9.3`).

Servers will usually have some timeout value beyond which they will no longer maintain an inactive connection (`rfc9112#section-9.5`).

A client, server or proxy may close the transport connection at any time (`rfc9112#section-9.5`).

A client might have started to send a new request at the same time that the server has decided to close the idle connection (`rfc9112#section-9.5`).

Implementations ought to anticipate the need to recover from asynchronous close events (`rfc9112#section-9.3.1`).

Implementations should constantly monitor open connections for a received closure signal and respond to it as appropriate (`rfc9112#section-9.5`).

A client or server that wishes to time out should issue a graceful close on the connection (`rfc9112#section-9.5`).

## Key points

- The three-way handshake prevents old duplicate connection initiations from causing confusion.
- A TCP endpoint that receives a FIN ACKs it and sends its own FIN only when its user has closed the connection.
- `TIME-WAIT` waits so that the peer's acknowledgment arrives and delayed segments do not affect new connections.
- The minimum of `cwnd` and `rwnd` governs data transmission, and `ssthresh` selects slow start or congestion avoidance.
- Three duplicate ACKs trigger a fast retransmit without waiting for the retransmission timer.
- Keep-alives must default to off, with an interval that defaults to no less than two hours.
- HTTP/2 does not address TCP head-of-line blocking.
- A negative DNS answer is cached for the TTL taken from the minimum of `SOA.MINIMUM` and the SOA's TTL.
- The JDK caches unsuccessful host name resolutions for 10 seconds, and `networkaddress.cache.ttl` of -1 means cache forever.
- A headless Service has `.spec.clusterIP` set to `None` and publishes the Pod addresses through DNS.
- In TLS 1.3 the client sends a Certificate message if and only if the server sent a CertificateRequest.
- 0-RTT data is not forward secret and has no guarantee of non-replay between connections.
- SNI carries the server name in a `server_name` extension, and ALPN lets the server select one protocol from the client's list.
- `HttpClient.connectTimeout()` and `HttpRequest.timeout()` return an empty `Optional` when the builder did not set them.
- An expired socket read timeout raises `SocketTimeoutException` and leaves the socket valid.
- A client, server or proxy may close the transport connection at any time, and implementations ought to anticipate the need to recover from asynchronous close events.

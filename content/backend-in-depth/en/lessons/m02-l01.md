# Complexity and Java collections internals

## Asymptotic notation and amortised cost
<!-- bullets: 2.1.a -->

The running time of an operation is the number of computer instructions performed during the operation (`ods-1-3-mathematical-background#SECTION00433000000000000000`).

Exact running times vary from computer to computer and even from run to run on one computer (`ods-1-3-mathematical-background#SECTION00433000000000000000`).

Big-oh notation replaces the exact running time with a simpler function (`ods-1-3-mathematical-background#SECTION00433000000000000000`).

A binary counter increment takes Θ(log n) time in the worst case when the counter holds an integer between 0 and n (`erickson-amortized-analysis#p1`).

Charging that worst case to every call gives an upper bound of O(n log n) on the total running time of n increments (`erickson-amortized-analysis#p2`).

The total running time of n increments from zero is only Θ(n) (`erickson-amortized-analysis#p2`).

The number of bit flips in n increments is exactly 2n minus the number of 1 bits in the binary representation of n (`erickson-amortized-analysis#p2`).

The snippet runs 1,000 increments on a counter of 64 bits and counts every bit that changes.

```java snippet=m02-l01/BinaryCounter.java
public class BinaryCounter {
    public static void main(String[] args) {
        boolean[] bits = new boolean[64];
        int n = 1000;
        long totalFlips = 0;
        long mostFlipsInOneIncrement = 0;
        for (int step = 1; step <= n; step++) {
            long flips = 0;
            int i = 0;
            while (bits[i]) {
                bits[i] = false;
                flips++;
                i++;
            }
            bits[i] = true;
            flips++;
            totalFlips += flips;
            mostFlipsInOneIncrement = Math.max(mostFlipsInOneIncrement, flips);
        }
        System.out.println("total flips " + totalFlips);
        System.out.println("most flips in one increment " + mostFlipsInOneIncrement);
        System.out.println("2n minus ones " + (2L * n - Integer.bitCount(n)));
    }
}
```

The snippet prints `total flips 1994`, which is 2 × 1000 minus the 6 one-bits of 1000.

It prints `2n minus ones 1994` for the formula, the same value as the counted flips.

It prints `most flips in one increment 10`, so no single increment among the first 1,000 changes more than 10 bits.

Amortization averages over a sequence of operations, and no probability is involved (`erickson-amortized-analysis#p2`).

The worst-case cost of `Increment` is O(log n), but its amortized cost is only O(1) (`erickson-amortized-analysis#p2`).

In the summation method, T(n) is the worst-case running time for a sequence of n operations and the amortized time for each operation is T(n)/n (`erickson-amortized-analysis#p2`).

In the potential method, the amortized cost of an operation is its actual cost plus the change in potential (`erickson-amortized-analysis#p4`).

Amortized time bounds are not unique (`erickson-amortized-analysis#p7`).

A lower expected or amortized running time than the worst case is often possible (`ods-1-5-correctness-time-comple#SECTION00450020000000000000`).

`ArrayList.add` runs in amortized constant time, so adding n elements requires O(n) time (`javadoc-arraylist#class-arraylist-e`).

The capacity of an `ArrayList` is the size of the array used to store the elements, and it is always at least as large as the list size (`javadoc-arraylist#class-arraylist-e`).

The growth policy of `ArrayList` is not specified beyond constant amortized time for adding an element (`javadoc-arraylist#class-arraylist-e`).

The snippet doubles a backing array each time it is full and counts the elements copied while adding 1,000,000 values.

```java snippet=m02-l01/DoublingArray.java
public class DoublingArray {
    public static void main(String[] args) {
        int n = 1_000_000;
        int[] backing = new int[1];
        int size = 0;
        long copies = 0;
        for (int value = 0; value < n; value++) {
            if (size == backing.length) {
                int[] bigger = new int[backing.length * 2];
                for (int i = 0; i < size; i++) {
                    bigger[i] = backing[i];
                }
                copies += size;
                backing = bigger;
            }
            backing[size++] = value;
        }
        System.out.println("adds " + n);
        System.out.println("element copies " + copies);
        System.out.println("copies below 2n " + (copies < 2L * n));
    }
}
```

The snippet prints `element copies 1048575` for 1,000,000 adds and `copies below 2n true`, so the copying costs fewer than two element copies per add.

## Structure and cost of the collections
<!-- bullets: 2.1.b -->

:::esquema{kind=tabla title="Structure of each collection according to its Javadoc"}
| Class | Structure | Citation |
| --- | --- | --- |
| `ArrayList` | Resizable-array implementation of the `List` interface | `javadoc-arraylist#class-arraylist-e` |
| `LinkedList` | Doubly-linked list implementation of the `List` and `Deque` interfaces | `javadoc-linkedlist#class-linkedlist-e` |
| `ArrayDeque` | Resizable-array implementation of the `Deque` interface | `javadoc-arraydeque#class-arraydeque-e` |
| `HashMap` | Hash table based implementation of the `Map` interface | `javadoc-hashmap#class-hashmap-k-v` |
| `LinkedHashMap` | Hash table and linked list implementation of the `Map` interface | `javadoc-linkedhashmap#class-linkedhashmap-k-v` |
| `TreeMap` | A Red-Black tree based `NavigableMap` implementation | `javadoc-treemap#class-treemap-k-v` |
| `PriorityQueue` | An unbounded priority queue based on a priority heap | `javadoc-priorityqueue#class-priorityqueue-e` |
:::

`ArrayList` runs `size`, `isEmpty`, `get` and `set` in constant time (`javadoc-arraylist#class-arraylist-e`).

An indexed `LinkedList` operation traverses the list from the beginning or the end, whichever is closer to the index (`javadoc-linkedlist#class-linkedlist-e`).

Array deques have no capacity restrictions and grow as necessary (`javadoc-arraydeque#class-arraydeque-e`).

`ArrayDeque` prohibits null elements (`javadoc-arraydeque#class-arraydeque-e`).

`ArrayDeque` is likely to be faster than `Stack` when used as a stack, and faster than `LinkedList` when used as a queue (`javadoc-arraydeque#class-arraydeque-e`).

`ArrayDeque` is not thread-safe (`javadoc-arraydeque#class-arraydeque-e`).

Most `ArrayDeque` operations run in amortized constant time (`javadoc-arraydeque#class-arraydeque-e`).

`HashMap` provides constant-time `get` and `put`, assuming the hash function disperses the elements properly among the buckets (`javadoc-hashmap#class-hashmap-k-v`).

Iteration over `HashMap` collection views requires time proportional to the capacity plus the size (`javadoc-hashmap#class-hashmap-k-v`).

`HashMap` makes no guarantees as to the order of the map (`javadoc-hashmap#class-hashmap-k-v`).

`HashMap` permits null values and the null key (`javadoc-hashmap#class-hashmap-k-v`).

The load factor is a measure of how full the hash table is allowed to get before its capacity is automatically increased (`javadoc-hashmap#class-hashmap-k-v`).

When the entries exceed the product of the load factor and the current capacity, the table is rehashed to approximately twice the number of buckets (`javadoc-hashmap#class-hashmap-k-v`).

The default load factor of .75 offers a good tradeoff between time and space costs (`javadoc-hashmap#class-hashmap-k-v`).

Higher load factors decrease the space overhead but increase the lookup cost (`javadoc-hashmap#class-hashmap-k-v`).

If the initial capacity is greater than the maximum number of entries divided by the load factor, no rehash operations will ever occur (`javadoc-hashmap#class-hashmap-k-v`).

Many keys with the same `hashCode()` slow down any hash table, and when keys are `Comparable`, `HashMap` may use comparison order among keys to break ties (`javadoc-hashmap#class-hashmap-k-v`).

In a chained hash table, each entry holds a linked list of all the items that hash to it (`erickson-hashing#p4`).

Open addressing resolves collisions by looking elsewhere in the table instead of building secondary data structures (`erickson-hashing#p12`).

`LinkedHashMap` differs from `HashMap` in that it maintains a doubly-linked list running through all of its entries (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

That linked list defines the encounter order, which is normally the order in which keys were inserted (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Encounter order is not affected if a key is re-inserted with `put` (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

A special constructor creates a `LinkedHashMap` ordered by last access, from least-recently accessed to most-recently (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

An access-ordered map is well-suited to building LRU caches (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

In access-ordered linked hash maps, merely querying the map with `get` is a structural modification (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

`put` and `putAll` invoke `removeEldestEntry` after inserting a new entry (`javadoc-linkedhashmap#removeEldestEntry(java.util.Map.Entry)`).

Iteration over the collection views of a `LinkedHashMap` requires time proportional to the size of the map, regardless of its capacity (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Like `HashMap`, `LinkedHashMap` provides constant-time performance for the basic operations (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The snippet builds an insertion-ordered map, an access-ordered map and a cache of two entries that overrides `removeEldestEntry`, and prints the keys of each.

```java snippet=m02-l01/MapOrder.java
import java.util.LinkedHashMap;
import java.util.Map;

public class MapOrder {
    static class Lru<K, V> extends LinkedHashMap<K, V> {
        private final int limit;

        Lru(int limit) {
            super(16, 0.75f, true);
            this.limit = limit;
        }

        @Override
        protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
            return size() > limit;
        }
    }

    public static void main(String[] args) {
        Map<String, Integer> insertion = new LinkedHashMap<>();
        insertion.put("a", 1);
        insertion.put("b", 2);
        insertion.put("c", 3);
        insertion.put("a", 10);
        System.out.println(insertion.keySet());

        Map<String, Integer> access = new LinkedHashMap<>(16, 0.75f, true);
        access.put("a", 1);
        access.put("b", 2);
        access.put("c", 3);
        access.get("a");
        System.out.println(access.keySet());

        Lru<String, Integer> lru = new Lru<>(2);
        lru.put("a", 1);
        lru.put("b", 2);
        lru.get("a");
        lru.put("c", 3);
        System.out.println(lru.keySet());
    }
}
```

The snippet prints `[a, b, c]` for the insertion-ordered map, because the second `put` of `a` does not change the order.

It prints `[b, c, a]` for the access-ordered map, because `get("a")` moves `a` to the end.

It prints `[a, c]` for the cache, because `get("a")` made `b` the eldest entry and the third `put` removed it.

`TreeMap` provides guaranteed log(n) time cost for `containsKey`, `get`, `put` and `remove` (`javadoc-treemap#class-treemap-k-v`).

A `TreeMap` is sorted by the natural ordering of its keys or by a `Comparator` given at creation (`javadoc-treemap#class-treemap-k-v`).

The `putFirst` and `putLast` methods of `TreeMap` throw `UnsupportedOperationException` (`javadoc-treemap#class-treemap-k-v`).

The head of a `PriorityQueue` is the least element with respect to the specified ordering (`javadoc-priorityqueue#class-priorityqueue-e`).

A `PriorityQueue` does not permit null elements (`javadoc-priorityqueue#class-priorityqueue-e`).

`PriorityQueue` takes O(log(n)) time for `offer`, `poll`, `remove()` and `add`, linear time for `remove(Object)` and `contains(Object)`, and constant time for `peek`, `element` and `size` (`javadoc-priorityqueue#class-priorityqueue-e`).

The iterator of a `PriorityQueue` is not guaranteed to traverse the elements in any particular order (`javadoc-priorityqueue#class-priorityqueue-e`).

The snippet adds `null` to an `ArrayDeque`, calls `putFirst` on a `TreeMap`, and offers five values to a `PriorityQueue` before polling them all.

```java snippet=m02-l01/CollectionContracts.java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.List;
import java.util.PriorityQueue;
import java.util.TreeMap;

public class CollectionContracts {
    public static void main(String[] args) {
        try {
            new ArrayDeque<String>().addLast(null);
        } catch (NullPointerException e) {
            System.out.println("ArrayDeque rejects null");
        }

        try {
            new TreeMap<String, Integer>().putFirst("a", 1);
        } catch (UnsupportedOperationException e) {
            System.out.println("TreeMap.putFirst throws UnsupportedOperationException");
        }

        PriorityQueue<Integer> queue = new PriorityQueue<>();
        for (int value : new int[] {5, 1, 4, 2, 3}) {
            queue.offer(value);
        }
        List<Integer> polled = new ArrayList<>();
        while (!queue.isEmpty()) {
            polled.add(queue.poll());
        }
        System.out.println(polled);

        PriorityQueue<Integer> reversed = new PriorityQueue<>((x, y) -> Integer.compare(y, x));
        reversed.addAll(List.of(5, 1, 4, 2, 3));
        System.out.println(reversed.poll());
    }
}
```

The snippet prints `ArrayDeque rejects null` because `addLast(null)` throws a `NullPointerException`.

The snippet prints `TreeMap.putFirst throws UnsupportedOperationException`.

The snippet offers 5, 1, 4, 2 and 3 and prints `[1, 2, 3, 4, 5]` for the values returned by repeated `poll`.

## The `equals`, `hashCode` and `compareTo` contracts
<!-- bullets: 2.1.c -->

:::esquema{kind=tabla title="Contract of `equals` on non-null references"}
| Property | Rule | Citation |
| --- | --- | --- |
| Reflexive | `x.equals(x)` should return `true` | `javadoc-object#equals(java.lang.Object)` |
| Symmetric | `x.equals(y)` should return `true` if and only if `y.equals(x)` returns `true` | `javadoc-object#equals(java.lang.Object)` |
| Transitive | If `x.equals(y)` and `y.equals(z)` return `true`, then `x.equals(z)` should return `true` | `javadoc-object#equals(java.lang.Object)` |
| Consistent | Multiple invocations of `x.equals(y)` consistently return `true` or consistently return `false`, provided no information used in the comparison is modified | `javadoc-object#equals(java.lang.Object)` |
| Null | `x.equals(null)` should return `false` | `javadoc-object#equals(java.lang.Object)` |
:::

`Object.equals` returns `true` if and only if `x` and `y` refer to the same object (`javadoc-object#equals(java.lang.Object)`).

Overriding `equals` generally requires overriding `hashCode`, so that equal objects have equal hash codes (`javadoc-object#equals(java.lang.Object)`).

If two objects are equal according to `equals`, calling `hashCode` on each must produce the same integer result (`javadoc-object#hashCode()`).

Unequal objects are not required to produce distinct hash codes (`javadoc-object#hashCode()`).

The integer from `hashCode` need not stay the same from one execution of an application to another (`javadoc-object#hashCode()`).

More distinct hash codes for unequal objects may improve the performance of hash tables (`javadoc-object#hashCode()`).

The snippet defines a class with `equals` only, a subclass that adds `hashCode`, and compares `BigDecimal` values in a `HashSet` and a `TreeSet`.

```java snippet=m02-l01/EqualityContracts.java
import java.math.BigDecimal;
import java.util.HashSet;
import java.util.Objects;
import java.util.Set;
import java.util.TreeSet;

public class EqualityContracts {
    static class EqualsOnly {
        final int id;

        EqualsOnly(int id) {
            this.id = id;
        }

        @Override
        public boolean equals(Object other) {
            return other instanceof EqualsOnly that && that.id == id;
        }
    }

    static class EqualsAndHash extends EqualsOnly {
        EqualsAndHash(int id) {
            super(id);
        }

        @Override
        public int hashCode() {
            return Objects.hash(id);
        }
    }

    public static void main(String[] args) {
        System.out.println("equals: " + new EqualsOnly(7).equals(new EqualsOnly(7)));
        Set<EqualsOnly> broken = new HashSet<>();
        broken.add(new EqualsOnly(7));
        System.out.println("contains, equals only: " + broken.contains(new EqualsOnly(7)));

        Set<EqualsAndHash> working = new HashSet<>();
        working.add(new EqualsAndHash(7));
        System.out.println("contains, equals and hash code: " + working.contains(new EqualsAndHash(7)));

        BigDecimal four = new BigDecimal("4.0");
        BigDecimal fourPointZeroZero = new BigDecimal("4.00");
        System.out.println("decimal equals: " + four.equals(fourPointZeroZero));
        System.out.println("decimal compare: " + four.compareTo(fourPointZeroZero));

        Set<BigDecimal> hashed = new HashSet<>(Set.of(four, fourPointZeroZero));
        Set<BigDecimal> sorted = new TreeSet<>(Set.of(four, fourPointZeroZero));
        System.out.println("hashed size: " + hashed.size());
        System.out.println("sorted size: " + sorted.size());
    }
}
```

The snippet prints `equals: true` for two instances with the same id.

It prints `contains, equals only: false`, because a `HashSet` holding one instance does not find the equal instance without a matching `hashCode`.

It prints `contains, equals and hash code: true` once the class also overrides `hashCode`.

The implementor of `compareTo` must ensure `signum(x.compareTo(y)) == -signum(y.compareTo(x))` for all `x` and `y` (`javadoc-comparable#compareTo(java.lang.Object)`).

The implementor must also ensure that the `compareTo` relation is transitive (`javadoc-comparable#compareTo(java.lang.Object)`).

Making `(x.compareTo(y)==0) == (x.equals(y))` hold is strongly recommended but not strictly required (`javadoc-comparable#compareTo(java.lang.Object)`).

`e.compareTo(null)` should throw a `NullPointerException` even though `e.equals(null)` returns `false` (`javadoc-comparable#interface-comparable-t`).

`BigDecimal` has a natural ordering inconsistent with equals: it equates objects with equal numerical values and different representations, such as 4.0 and 4.00 (`javadoc-comparable#interface-comparable-t`).

If `!a.equals(b)` and `a.compareTo(b) == 0`, the second `add` to a sorted set without an explicit comparator returns `false` and the size does not increase (`javadoc-comparable#interface-comparable-t`).

The ordering of a `TreeMap` must be consistent with equals if the map is to correctly implement the `Map` interface (`javadoc-treemap#class-treemap-k-v`).

A sorted map performs all key comparisons with `compareTo` or `compare`, so two keys that compare as equal are equal to the map (`javadoc-treemap#class-treemap-k-v`).

The snippet prints `decimal equals: false` and `decimal compare: 0` for 4.0 and 4.00.

It prints `hashed size: 2` and `sorted size: 1` for a set built from both values.

## Key points

- Amortized cost averages the cost of a sequence of operations, so a counter increment has worst-case cost O(log n) and amortized cost O(1).
- `ArrayList.add` runs in amortized constant time, and the growth policy is not specified beyond that.
- `ArrayDeque` prohibits null, grows as needed and is not thread-safe.
- `HashMap` is rehashed to about twice the buckets when entries exceed the load factor times the capacity.
- Iterating a `HashMap` takes time proportional to capacity plus size; iterating a `LinkedHashMap` takes time proportional to size.
- An access-ordered `LinkedHashMap` moves an entry to the end on `get`, and `removeEldestEntry` can turn it into an LRU cache.
- `TreeMap` guarantees log(n) for `get` and `put`, and a `PriorityQueue` iterator does not traverse in priority order.
- Equal objects must have equal hash codes, but unequal objects need not have distinct ones.
- `BigDecimal` 4.0 and 4.00 are not `equals` but compare as 0, so a `HashSet` keeps both and a `TreeSet` keeps one.

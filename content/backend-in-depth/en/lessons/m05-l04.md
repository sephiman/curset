# Transaction management

## Transaction strategy and thread binding
<!-- bullets: 5.4.a -->

Spring puts every kind of transaction behind one object, the transaction manager. Application code asks for a transaction and does not depend on how the resource underneath handles it. The current transaction belongs to the thread that started it, so work moved to another thread runs outside it.

A transaction strategy is defined by a `TransactionManager`: the `PlatformTransactionManager` interface for imperative transaction management and the `ReactiveTransactionManager` interface for reactive transaction management (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

`PlatformTransactionManager` is primarily a service provider interface (SPI), although you can use it programmatically from your application code (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

Because `PlatformTransactionManager` is an interface, it can be easily mocked or stubbed as necessary (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

In all Spring transaction setups, application code does not need to change, and you can change how transactions are managed merely by changing configuration (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

The `TransactionException` that can be thrown by any of the `PlatformTransactionManager` methods is unchecked, which means that it extends the `java.lang.RuntimeException` class (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

The `getTransaction(..)` method returns a `TransactionStatus` object, depending on a `TransactionDefinition` parameter (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

The returned `TransactionStatus` might represent a new transaction or an existing transaction, if a matching transaction exists in the current call stack (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

A `TransactionStatus` is associated with a thread of execution (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

The combination of AOP with transactional metadata yields an AOP proxy that uses a `TransactionInterceptor` in conjunction with an appropriate `TransactionManager` implementation to drive transactions around method invocations (`spring-fw-tx-declarative-tx-decl-explained#page-title`).

`@Transactional` commonly works with thread-bound transactions managed by `PlatformTransactionManager`, exposing a transaction to all data access operations within the current execution thread (`spring-fw-tx-declarative-tx-decl-explained#page-title`).

A thread-bound transaction does not propagate to newly started threads within the method (`spring-fw-tx-declarative-tx-decl-explained#page-title`).

`TransactionSynchronizationManager` is the central delegate that manages resources and transaction synchronizations per thread (`spring-fw-javadoc-transactionsynchronizationmanager#class-transactionsynchronizationmanager`).

Resource management code is normally not supposed to bind resources to threads, as this is the responsibility of transaction managers (`spring-fw-javadoc-transactionsynchronizationmanager#class-transactionsynchronizationmanager`).

A transaction manager must activate and deactivate transaction synchronization through `initSynchronization()` and `clearSynchronization()`, which `AbstractPlatformTransactionManager` supports automatically (`spring-fw-javadoc-transactionsynchronizationmanager#class-transactionsynchronizationmanager`).

`isActualTransactionActive()` returns whether the current thread is associated with an actual transaction rather than just with active transaction synchronization (`spring-fw-javadoc-transactionsynchronizationmanager#isActualTransactionActive()`).

```java snippet=m05-l04/ThreadBinding.java
import org.springframework.transaction.*;
import org.springframework.transaction.support.*;

public class ThreadBinding {
    static class RecordingManager extends AbstractPlatformTransactionManager {
        protected Object doGetTransaction() { return new Object(); }
        protected void doBegin(Object tx, TransactionDefinition d) { }
        protected void doCommit(DefaultTransactionStatus s) { }
        protected void doRollback(DefaultTransactionStatus s) { }
    }

    static boolean activeInNewThread() throws InterruptedException {
        boolean[] seen = new boolean[1];
        Thread thread = new Thread(() -> seen[0] = TransactionSynchronizationManager.isActualTransactionActive());
        thread.start();
        thread.join();
        return seen[0];
    }

    public static void main(String[] args) {
        System.out.println("before: " + TransactionSynchronizationManager.isActualTransactionActive());
        new TransactionTemplate(new RecordingManager()).executeWithoutResult(status -> {
            System.out.println("inside, same thread: " + TransactionSynchronizationManager.isActualTransactionActive());
            try {
                System.out.println("inside, new thread: " + activeInNewThread());
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
        System.out.println("after: " + TransactionSynchronizationManager.isActualTransactionActive());
    }
}
```

The program prints `false` before the template runs, `true` inside the callback on the calling thread, `false` inside a thread started by the callback, and `false` after the template returns.

The preferred approach is to use Spring's highest-level template-based persistence integration APIs, or native ORM APIs with transaction-aware factory beans or proxies (`spring-fw-tx-tx-resource-synchronization#tx-resource-synchronization-high`).

Classes such as `DataSourceUtils` for JDBC, `EntityManagerFactoryUtils` for JPA and `SessionFactoryUtils` for Hibernate exist at a lower level (`spring-fw-tx-tx-resource-synchronization#tx-resource-synchronization-low`).

If an existing transaction already has a connection synchronized to it, `DataSourceUtils.getConnection` returns that instance (`spring-fw-tx-tx-resource-synchronization#tx-resource-synchronization-low`).

Otherwise, the call creates a new connection, which is optionally synchronized to any existing transaction and made available for subsequent reuse in that same transaction (`spring-fw-tx-tx-resource-synchronization#tx-resource-synchronization-low`).

The Spring Framework provides two means of programmatic transaction management: the `TransactionTemplate` or `TransactionalOperator`, and a `TransactionManager` implementation directly (`spring-fw-tx-programmatic-tm#page-title`).

The Spring team generally recommends the `TransactionTemplate` for programmatic transaction management in imperative flows and `TransactionalOperator` for reactive code (`spring-fw-tx-programmatic-tm#page-title`).

## Propagation
<!-- bullets: 5.4.b -->

Propagation settles what a transactional method does when it is called while a transaction is already running. It can run inside that transaction or start one of its own, and the choice decides which work commits or rolls back together.

Propagation lets you specify the behavior if a transactional method is run when a transaction context already exists: code can continue running in the existing transaction, which is the common case, or the existing transaction can be suspended and a new transaction created (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

Spring offers all of the transaction propagation options familiar from EJB CMT (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

:::esquema{kind=tabla title="Propagation behaviours of TransactionDefinition"}
| Behaviour | What it does | Source |
|---|---|---|
| `PROPAGATION_REQUIRED` | Supports a current transaction and creates a new one if none exists | `spring-fw-javadoc-transactiondefinition#PROPAGATION_REQUIRED` |
| `PROPAGATION_SUPPORTS` | Supports a current transaction and executes non-transactionally if none exists | `spring-fw-javadoc-transactiondefinition#PROPAGATION_SUPPORTS` |
| `PROPAGATION_MANDATORY` | Supports a current transaction and throws an exception if none exists | `spring-fw-javadoc-transactiondefinition#PROPAGATION_MANDATORY` |
| `PROPAGATION_REQUIRES_NEW` | Creates a new transaction, suspending the current transaction if one exists | `spring-fw-javadoc-transactiondefinition#PROPAGATION_REQUIRES_NEW` |
| `PROPAGATION_NOT_SUPPORTED` | Does not support a current transaction and always executes non-transactionally | `spring-fw-javadoc-transactiondefinition#PROPAGATION_NOT_SUPPORTED` |
| `PROPAGATION_NEVER` | Does not support a current transaction and throws an exception if one exists | `spring-fw-javadoc-transactiondefinition#PROPAGATION_NEVER` |
| `PROPAGATION_NESTED` | Executes within a nested transaction if a current transaction exists, behaving like `PROPAGATION_REQUIRED` otherwise | `spring-fw-javadoc-transactiondefinition#PROPAGATION_NESTED` |
:::

In Spring-managed transactions, you need to be aware of the difference between physical and logical transactions, and of how the propagation setting applies to this difference (`spring-fw-tx-declarative-tx-propagation#page-title`).

`PROPAGATION_REQUIRED` enforces a physical transaction, either locally for the current scope if no transaction exists yet or participating in an existing 'outer' transaction defined for a larger scope (`spring-fw-tx-declarative-tx-propagation#tx-propagation-required`).

By default, a participating transaction joins the characteristics of the outer scope, silently ignoring the local isolation level, timeout value, or read-only flag (`spring-fw-tx-declarative-tx-propagation#tx-propagation-required`).

Setting the `validateExistingTransaction` flag to `true` on the transaction manager makes it reject isolation level declarations when participating in an existing transaction with a different isolation level, and it also rejects read-only mismatches (`spring-fw-tx-declarative-tx-propagation#tx-propagation-required`).

When the propagation setting is `PROPAGATION_REQUIRED`, a logical transaction scope is created for each method upon which the setting is applied (`spring-fw-tx-declarative-tx-propagation#tx-propagation-required`).

In the case of standard `PROPAGATION_REQUIRED` behavior, all these scopes are mapped to the same physical transaction, so a rollback-only marker set in the inner transaction scope does affect the outer transaction's chance to actually commit (`spring-fw-tx-declarative-tx-propagation#tx-propagation-required`).

When an inner transaction scope silently sets the rollback-only marker and the outer caller still calls commit, an `UnexpectedRollbackException` is thrown, so that the caller of a transaction can never be misled to assume that a commit was performed when it really was not (`spring-fw-tx-declarative-tx-propagation#tx-propagation-required`).

`PROPAGATION_REQUIRES_NEW`, in contrast to `PROPAGATION_REQUIRED`, always uses an independent physical transaction for each affected transaction scope, never participating in an existing transaction for an outer scope (`spring-fw-tx-declarative-tx-propagation#tx-propagation-requires_new`).

The underlying resource transactions are different, so they can commit or roll back independently, with an outer transaction not affected by an inner transaction's rollback status and with an inner transaction's locks released immediately after its completion (`spring-fw-tx-declarative-tx-propagation#tx-propagation-requires_new`).

Such an independent inner transaction can also declare its own isolation level, timeout, and read-only settings and not inherit an outer transaction's characteristics (`spring-fw-tx-declarative-tx-propagation#tx-propagation-requires_new`).

The resources attached to the outer transaction remain bound there while the inner transaction acquires its own resources such as a new database connection (`spring-fw-tx-declarative-tx-propagation#tx-propagation-requires_new`).

The connection pool may be exhausted, and a deadlock can follow, if several threads have an active outer transaction and wait to acquire a new connection for their inner transaction (`spring-fw-tx-declarative-tx-propagation#tx-propagation-requires_new`).

You should not use `PROPAGATION_REQUIRES_NEW` unless your connection pool is appropriately sized, exceeding the number of concurrent threads by at least 1 (`spring-fw-tx-declarative-tx-propagation#tx-propagation-requires_new`).

Actual transaction suspension does not work out-of-the-box on all transaction managers, and this applies in particular to `JtaTransactionManager` (`spring-fw-javadoc-transactiondefinition#PROPAGATION_REQUIRES_NEW`).

```java snippet=m05-l04/RequiredVersusRequiresNew.java
import org.springframework.transaction.*;
import org.springframework.transaction.support.*;

public class RequiredVersusRequiresNew {
    static class RecordingManager extends AbstractPlatformTransactionManager {
        private final int[] current = {0};
        private int counter;
        protected Object doGetTransaction() { return current; }
        protected boolean isExistingTransaction(Object tx) { return current[0] != 0; }
        protected Object doSuspend(Object tx) { int outer = current[0]; current[0] = 0; return outer; }
        protected void doResume(Object tx, Object outer) { current[0] = (Integer) outer; }
        protected void doBegin(Object tx, TransactionDefinition d) { current[0] = ++counter; System.out.println("begin " + counter); }
        protected void doCommit(DefaultTransactionStatus s) { System.out.println("commit " + current[0]); current[0] = 0; }
        protected void doRollback(DefaultTransactionStatus s) { System.out.println("rollback " + current[0]); current[0] = 0; }
        protected void doSetRollbackOnly(DefaultTransactionStatus s) { }
    }

    static void inner(PlatformTransactionManager manager, int propagation) {
        TransactionTemplate template = new TransactionTemplate(manager);
        template.setPropagationBehavior(propagation);
        template.executeWithoutResult(status -> System.out.println("  inner runs, new transaction: " + status.isNewTransaction()));
    }

    static void run(PlatformTransactionManager manager, String name, int propagation) {
        System.out.println("-- inner " + name);
        new TransactionTemplate(manager).executeWithoutResult(outer -> inner(manager, propagation));
    }

    public static void main(String[] args) {
        PlatformTransactionManager manager = new RecordingManager();
        run(manager, "required", TransactionDefinition.PROPAGATION_REQUIRED);
        run(manager, "requires new", TransactionDefinition.PROPAGATION_REQUIRES_NEW);
    }
}
```

With `PROPAGATION_REQUIRED` for the inner scope the program prints `begin 1`, then `inner runs, new transaction: false`, then `commit 1`. With `PROPAGATION_REQUIRES_NEW` it prints `begin 2` and `begin 3`, then `inner runs, new transaction: true`, then `commit 3` and `commit 2`.

:::diagram{kind="flow" caption="With REQUIRES_NEW the inner transaction commits before the outer one"}
description: The outer transaction begins, the inner REQUIRES_NEW scope begins a second transaction, the inner transaction commits, then the outer transaction commits.
outer: outer transaction begins
inner: inner scope begins a new transaction
inner_commit: inner transaction commits
outer_commit: outer transaction commits
outer -> inner
inner -> inner_commit
inner_commit -> outer_commit
:::

```java snippet=m05-l04/InnerRollbackOnly.java
import org.springframework.transaction.*;
import org.springframework.transaction.support.*;

public class InnerRollbackOnly {
    static class Tx implements SmartTransactionObject {
        boolean rollbackOnly;
        public boolean isRollbackOnly() { return rollbackOnly; }
        public void flush() { }
    }
    static class RecordingManager extends AbstractPlatformTransactionManager {
        private Tx current;
        protected Object doGetTransaction() { return current == null ? new Tx() : current; }
        protected boolean isExistingTransaction(Object tx) { return current != null; }
        protected Object doSuspend(Object tx) { Tx outer = current; current = null; return outer; }
        protected void doResume(Object tx, Object outer) { current = (Tx) outer; }
        protected void doBegin(Object tx, TransactionDefinition d) { current = (Tx) tx; System.out.println("begin"); }
        protected void doCommit(DefaultTransactionStatus s) { System.out.println("commit"); current = null; }
        protected void doRollback(DefaultTransactionStatus s) { System.out.println("rollback"); current = null; }
        protected void doSetRollbackOnly(DefaultTransactionStatus s) { ((Tx) s.getTransaction()).rollbackOnly = true; }
    }
    static void run(PlatformTransactionManager manager, String name, int propagation) {
        System.out.println("-- inner " + name + " marks rollback-only");
        TransactionTemplate inner = new TransactionTemplate(manager);
        inner.setPropagationBehavior(propagation);
        try {
            new TransactionTemplate(manager).executeWithoutResult(
                outer -> inner.executeWithoutResult(status -> status.setRollbackOnly()));
            System.out.println("outer returned normally");
        } catch (UnexpectedRollbackException e) {
            System.out.println("outer failed: unexpected rollback");
        }
    }
    public static void main(String[] args) {
        PlatformTransactionManager manager = new RecordingManager();
        run(manager, "required", TransactionDefinition.PROPAGATION_REQUIRED);
        run(manager, "requires new", TransactionDefinition.PROPAGATION_REQUIRES_NEW);
    }
}
```

With `PROPAGATION_REQUIRED` the program prints `begin`, `rollback` and `outer failed: unexpected rollback` after the inner scope marks rollback-only. With `PROPAGATION_REQUIRES_NEW` it prints `begin`, `begin`, `rollback`, `commit` and `outer returned normally`.

`PROPAGATION_NESTED` uses a single physical transaction with multiple savepoints that it can roll back to (`spring-fw-tx-declarative-tx-propagation#tx-propagation-nested`).

Such partial rollbacks let an inner transaction scope trigger a rollback for its scope, with the outer transaction being able to continue the physical transaction despite some operations having been rolled back (`spring-fw-tx-declarative-tx-propagation#tx-propagation-nested`).

`PROPAGATION_NESTED` is typically mapped onto JDBC savepoints, so it works only with JDBC resource transactions (`spring-fw-tx-declarative-tx-propagation#tx-propagation-nested`).

For transaction managers with transaction synchronization, `PROPAGATION_SUPPORTS` is slightly different from no transaction at all, as it defines a transaction scope that synchronization might apply to (`spring-fw-javadoc-transactiondefinition#PROPAGATION_SUPPORTS`).

## Isolation, read-only and timeouts
<!-- bullets: 5.4.b -->

Isolation, read-only status and timeout are settings of a transaction. The isolation level and the timeout apply only when a new transaction starts.

The `@Transactional` annotation is metadata that specifies that an interface, class, or method must have transactional semantics (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

The default `propagation` setting of `@Transactional` is `PROPAGATION_REQUIRED` (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

The default isolation level of `@Transactional` is `ISOLATION_DEFAULT` (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

`ISOLATION_DEFAULT` uses the default isolation level of the underlying datastore (`spring-fw-javadoc-transactiondefinition#ISOLATION_DEFAULT`).

The transaction timeout defaults to the default timeout of the underlying transaction system, or to none if timeouts are not supported (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

The `isolation` attribute of `@Transactional` applies only to propagation values of `REQUIRED` or `REQUIRES_NEW` (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

The `timeout` attribute of `@Transactional` applies only to propagation values of `REQUIRED` or `REQUIRES_NEW` (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

The `readOnly` attribute of `@Transactional` selects a read-write versus read-only transaction and is only applicable to values of `REQUIRED` or `REQUIRES_NEW` (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

Isolation level and timeout settings are not applied unless an actual new transaction gets started (`spring-fw-javadoc-transactiondefinition#interface-transactiondefinition`).

The most derived location takes precedence when evaluating the transactional settings for a method (`spring-fw-tx-declarative-annotations#using-transactional`).

For declarative transactions, the transaction name is always the fully-qualified class name of the transactionally advised class, a dot and the method name (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

Isolation is the degree to which a transaction is isolated from the work of other transactions (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

Timeout is how long a transaction runs before timing out and being automatically rolled back by the underlying transaction infrastructure (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

A transaction manager that does not support timeouts throws an exception when given any timeout other than `TIMEOUT_DEFAULT` (`spring-fw-javadoc-transactiondefinition#getTimeout()`).

You can use a read-only transaction when your code reads but does not modify data (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

Read-only transactions can be a useful optimization in some cases, such as when you use Hibernate (`spring-fw-tx-strategies#understanding-the-spring-framework-transaction-abstraction`).

The read-only flag only serves as a hint for the actual transaction subsystem, and it does not necessarily cause failure of write access attempts (`spring-fw-javadoc-transactiondefinition#isReadOnly()`).

## Rollback rules
<!-- bullets: 5.4.c -->

A rollback rule tells the transaction infrastructure which exceptions turn a transaction into a rollback. Without a rule, an unchecked exception rolls back and a checked exception does not, and a rule changes that for the exception types it names.

By default, any `RuntimeException` or `Error` triggers rollback, and any checked `Exception` does not (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

The recommended way to roll back is to throw an `Exception` from code that is currently executing in the context of a transaction (`spring-fw-tx-declarative-rolling-back#page-title`).

In its default configuration, the transaction infrastructure marks a transaction for rollback only in the case of runtime, unchecked exceptions (`spring-fw-tx-declarative-rolling-back#page-title`).

`Error` instances also, by default, result in a rollback (`spring-fw-tx-declarative-rolling-back#page-title`).

Checked exceptions that are thrown from a transactional method do not result in a rollback in the default configuration (`spring-fw-tx-declarative-rolling-back#page-title`).

You can configure exactly which `Exception` types mark a transaction for rollback, including checked exceptions, by specifying rollback rules (`spring-fw-tx-declarative-rolling-back#page-title`).

Rollback rules determine if a transaction should be rolled back when a given exception is thrown, and the rules are based on exception types or exception patterns (`spring-fw-tx-declarative-rolling-back#page-title`).

With `@Transactional`, rollback rules may be configured via the `rollbackFor` and `noRollbackFor` attributes, and the `rollbackForClassName` and `noRollbackForClassName` attributes (`spring-fw-tx-declarative-rolling-back#page-title`).

```java snippet=m05-l04/RollbackRules.java
import java.io.IOException;
import org.springframework.context.annotation.*;
import org.springframework.transaction.*;
import org.springframework.transaction.annotation.*;
import org.springframework.transaction.support.*;

public class RollbackRules {
    static class RecordingManager extends AbstractPlatformTransactionManager {
        protected Object doGetTransaction() { return new Object(); }
        protected void doBegin(Object tx, TransactionDefinition d) { }
        protected void doCommit(DefaultTransactionStatus s) { System.out.println("  commit"); }
        protected void doRollback(DefaultTransactionStatus s) { System.out.println("  rollback"); }
    }
    public static class Ledger {
        @Transactional public void unchecked() { throw new IllegalStateException(); }
        @Transactional public void checked() throws IOException { throw new IOException(); }
        @Transactional(rollbackFor = IOException.class) public void checkedWithRule() throws IOException { throw new IOException(); }
        @Transactional(noRollbackFor = IllegalStateException.class) public void uncheckedWithRule() { throw new IllegalStateException(); }
    }
    @Configuration @EnableTransactionManagement
    static class Config {
        @Bean Ledger ledger() { return new Ledger(); }
        @Bean PlatformTransactionManager transactionManager() { return new RecordingManager(); }
    }
    interface Call { void run() throws Exception; }
    static void call(String name, Call call) {
        System.out.println(name);
        try { call.run(); } catch (Exception e) { System.out.println("  thrown " + (e instanceof RuntimeException ? "unchecked" : "checked") + " exception"); }
    }
    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            Ledger ledger = context.getBean(Ledger.class);
            call("unchecked", ledger::unchecked);
            call("checked", ledger::checked);
            call("checked, with a rollback rule", ledger::checkedWithRule);
            call("unchecked, with a no-rollback rule", ledger::uncheckedWithRule);
        }
    }
}
```

The program prints `rollback` and then `thrown unchecked exception` for the unchecked exception. It prints `commit` and then `thrown checked exception` for the checked exception, `rollback` and `thrown checked exception` when `rollbackFor = IOException.class` is set, and `commit` and `thrown unchecked exception` when `noRollbackFor = IllegalStateException.class` is set.

Given a configured exception type C, a thrown exception of type T is a match if T is equal to C or a subclass of C (`spring-fw-tx-declarative-rolling-back#page-title`).

A pattern can be a fully qualified class name or a substring of one, with no wildcard support at present (`spring-fw-tx-declarative-rolling-back#page-title`).

A thrown exception is a match for a pattern-based rule if the name of the thrown exception contains the exception pattern configured for the rule (`spring-fw-tx-declarative-rolling-back#page-title`).

When the infrastructure consults the configured rollback rules, the strongest matching rule wins (`spring-fw-tx-declarative-rolling-back#page-title`).

Transaction-specific rollback rules override the default behavior but retain the chosen default for unspecified exceptions (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

As of 6.2, you can globally change the default rollback behavior, for example through `@EnableTransactionManagement(rollbackOn=ALL_EXCEPTIONS)` (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

The `ALL_EXCEPTIONS` setting leads to a rollback for all exceptions raised within a transaction, including any checked exception (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

The documentation advises switching to `ALL_EXCEPTIONS` unless you rely on EJB-style business exceptions with commit behavior, and also for Kotlin-based applications, where checked exceptions are not enforced at all (`spring-fw-tx-declarative-annotations#transaction-declarative-attransactional-settings`).

As of 6.1, a `CompletableFuture` or `Future` return value that was exceptionally completed at the time of being returned triggers a rollback (`spring-fw-tx-declarative-rolling-back#page-title`).

## Transaction-bound events
<!-- bullets: 5.4.d -->

An event listener can wait for the outcome of the transaction in which the event was published, so that it acts only after a commit or only after a rollback. A listener bound to a phase is not invoked at all when no transaction is running, unless it is told otherwise.

As of Spring 4.2, the listener of an event can be bound to a phase of the transaction (`spring-fw-tx-event#page-title`).

If you need to bind a listener to the transaction, use `@TransactionalEventListener`, and the listener is bound to the commit phase of the transaction by default (`spring-fw-tx-event#page-title`).

The valid phases are `BEFORE_COMMIT`, `AFTER_COMMIT` (default), `AFTER_ROLLBACK`, and `AFTER_COMPLETION` (`spring-fw-tx-event#page-title`).

`AFTER_COMPLETION` aggregates the transaction completion, be it a commit or a rollback (`spring-fw-tx-event#page-title`).

If no transaction is running, the listener is not invoked at all, since the required semantics cannot be honored (`spring-fw-tx-event#page-title`).

You can override that behavior by setting the `fallbackExecution` attribute of the annotation to `true` (`spring-fw-tx-event#page-title`).

```java snippet=m05-l04/AfterCommitListener.java
import org.springframework.context.annotation.*;
import org.springframework.transaction.*;
import org.springframework.transaction.annotation.*;
import org.springframework.transaction.event.*;
import org.springframework.transaction.support.*;
public class AfterCommitListener {
    static class RecordingManager extends AbstractPlatformTransactionManager {
        protected Object doGetTransaction() { return new Object(); }
        protected void doBegin(Object tx, TransactionDefinition d) { }
        protected void doCommit(DefaultTransactionStatus s) { System.out.println("  commit"); }
        protected void doRollback(DefaultTransactionStatus s) { System.out.println("  rollback"); }
    }
    public static class Listeners {
        @TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)
        public void beforeCommit(String event) { System.out.println("  before commit: " + event); }
        @TransactionalEventListener
        public void afterCommit(String event) { System.out.println("  after commit: " + event); }
        @TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
        public void afterRollback(String event) { System.out.println("  after rollback: " + event); }
        @TransactionalEventListener(fallbackExecution = true)
        public void afterCommitOrNoTransaction(String event) { System.out.println("  fallback: " + event); }
    }
    @Configuration @EnableTransactionManagement
    static class Config {
        @Bean Listeners listeners() { return new Listeners(); }
        @Bean PlatformTransactionManager transactionManager() { return new RecordingManager(); }
    }
    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            TransactionTemplate template = new TransactionTemplate(context.getBean(PlatformTransactionManager.class));
            System.out.println("no transaction");
            context.publishEvent("A");
            System.out.println("commit");
            template.executeWithoutResult(status -> context.publishEvent("B"));
            System.out.println("rollback");
            template.executeWithoutResult(status -> { context.publishEvent("C"); status.setRollbackOnly(); });
        }
    }
}
```

For event `A`, published with no transaction, the program prints only `fallback: A` after its `no transaction` label. For event `B`, published in a transaction that commits, it prints `before commit: B`, `commit`, `after commit: B` and `fallback: B`. For event `C`, published in a transaction marked rollback-only, it prints `rollback` and `after rollback: C`.

:::diagram{kind="flow" caption="Order of the listener phases around a commit"}
description: A BEFORE_COMMIT listener runs, the transaction commits, then the AFTER_COMMIT listener runs.
before: BEFORE_COMMIT listener runs
commit: transaction commits
after: AFTER_COMMIT listener runs
before -> commit
commit -> after
:::

## Asynchronous execution and reactive code
<!-- bullets: 5.4.d -->

Code that hands work to a task executor leaves the transaction behind, and reactive transactions use the Reactor context instead of thread-local attributes. Which kind of transaction manager applies depends on the return type of the method.

The `TransactionInterceptor` provides transaction management for imperative and reactive programming models (`spring-fw-tx-declarative-tx-decl-explained#page-title`).

The interceptor detects the desired flavor of transaction management by inspecting the method return type (`spring-fw-tx-declarative-tx-decl-explained#page-title`).

Methods returning a reactive type such as `Publisher` or Kotlin `Flow` qualify for reactive transaction management, and all other return types including `void` use the code path for imperative transaction management (`spring-fw-tx-declarative-tx-decl-explained#page-title`).

Imperative transactions require a `PlatformTransactionManager`, while reactive transactions use `ReactiveTransactionManager` implementations (`spring-fw-tx-declarative-tx-decl-explained#page-title`).

A reactive transaction managed by `ReactiveTransactionManager` uses the Reactor context instead of thread-local attributes (`spring-fw-tx-declarative-tx-decl-explained#page-title`).

All participating data access operations need to execute within the same Reactor context in the same reactive pipeline (`spring-fw-tx-declarative-tx-decl-explained#page-title`).

As of 6.1, `@TransactionalEventListener` can work with thread-bound transactions managed by `PlatformTransactionManager` as well as reactive transactions managed by `ReactiveTransactionManager` (`spring-fw-tx-event#page-title`).

For thread-bound transactions, listeners are guaranteed to see the current thread-bound transaction (`spring-fw-tx-event#page-title`).

Reactive transactions use the Reactor context instead of thread-local variables, so the transaction context needs to be included in the published event instance as the event source (`spring-fw-tx-event#page-title`).

With `@Async`, the caller returns immediately upon invocation, while the actual execution of the method occurs in a task that has been submitted to a Spring `TaskExecutor` (`spring-fw-async#scheduling-annotation-support-async`).

```java snippet=m05-l04/AsyncTransaction.java
import java.util.concurrent.CompletableFuture;
import org.springframework.context.annotation.*;
import org.springframework.scheduling.annotation.*;
import org.springframework.transaction.*;
import org.springframework.transaction.annotation.*;
import org.springframework.transaction.support.*;

public class AsyncTransaction {
    static class RecordingManager extends AbstractPlatformTransactionManager {
        protected Object doGetTransaction() { return new Object(); }
        protected void doBegin(Object tx, TransactionDefinition d) { }
        protected void doCommit(DefaultTransactionStatus s) { }
        protected void doRollback(DefaultTransactionStatus s) { }
    }
    public static class Worker {
        @Async public CompletableFuture<Boolean> transactionActive() {
            return CompletableFuture.completedFuture(TransactionSynchronizationManager.isActualTransactionActive());
        }
    }
    @Configuration @EnableAsync @EnableTransactionManagement
    static class Config {
        @Bean Worker worker() { return new Worker(); }
        @Bean PlatformTransactionManager transactionManager() { return new RecordingManager(); }
    }
    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            Worker worker = context.getBean(Worker.class);
            new TransactionTemplate(context.getBean(PlatformTransactionManager.class)).executeWithoutResult(status -> {
                System.out.println("caller: " + TransactionSynchronizationManager.isActualTransactionActive());
                System.out.println("async method: " + worker.transactionActive().join());
            });
        }
    }
}
```

The program prints `caller: true` for the code inside the template and `async method: false` for the `@Async` method called from it.

In the absence of an `Executor` bean in the context, Spring Boot auto-configures an `AsyncTaskExecutor` (`spring-boot-features-task-execution-and-scheduling#page-title`).

When virtual threads are enabled, using Java 21+ and `spring.threads.virtual.enabled` set to `true`, the auto-configured executor is a `SimpleAsyncTaskExecutor` that uses virtual threads (`spring-boot-features-task-execution-and-scheduling#page-title`).

Otherwise, the auto-configured executor is a `ThreadPoolTaskExecutor` with sensible defaults (`spring-boot-features-task-execution-and-scheduling#page-title`).

```java snippet=m05-l04/VirtualThreadExecutor.java
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executor;
import org.springframework.boot.WebApplicationType;
import org.springframework.boot.autoconfigure.task.TaskExecutionAutoConfiguration;
import org.springframework.boot.builder.SpringApplicationBuilder;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Import;

public class VirtualThreadExecutor {
    @Configuration @Import(TaskExecutionAutoConfiguration.class)
    static class Config { }

    static void show(String property) throws Exception {
        try (ConfigurableApplicationContext context = new SpringApplicationBuilder(Config.class)
                .web(WebApplicationType.NONE).bannerMode(org.springframework.boot.Banner.Mode.OFF)
                .properties("spring.threads.virtual.enabled=" + property, "logging.level.root=OFF").run()) {
            Executor executor = context.getBean("applicationTaskExecutor", Executor.class);
            CompletableFuture<Boolean> virtual = new CompletableFuture<>();
            executor.execute(() -> virtual.complete(Thread.currentThread().isVirtual()));
            System.out.println("virtual=" + property + ": " + executor.getClass().getSimpleName() + ", virtual thread " + virtual.get());
        }
    }

    public static void main(String[] args) throws Exception {
        show("true");
        show("false");
    }
}
```

The program prints `SimpleAsyncTaskExecutor, virtual thread true` when `spring.threads.virtual.enabled` is `true`, and `ThreadPoolTaskExecutor, virtual thread false` when it is `false`.

The auto-configured `AsyncTaskExecutor` is used for execution of asynchronous tasks using `@EnableAsync`, unless a bean of type `AsyncConfigurer` is defined (`spring-boot-features-task-execution-and-scheduling#page-title`).

By default, when a custom `Executor` bean is registered, the auto-configured `AsyncTaskExecutor` backs off, and the custom `Executor` is used for regular task execution via `@EnableAsync` (`spring-boot-features-task-execution-and-scheduling#page-title`).

## Key points

- A transaction strategy is a `TransactionManager`: `PlatformTransactionManager` for imperative code and `ReactiveTransactionManager` for reactive code.
- `TransactionException` is unchecked, and a `TransactionStatus` is associated with a thread of execution.
- A thread-bound transaction does not propagate to threads started within the method, and an `@Async` method runs in a task submitted to a `TaskExecutor`.
- `@Transactional` defaults to `PROPAGATION_REQUIRED`, `ISOLATION_DEFAULT` and the default timeout of the underlying transaction system.
- A participating `PROPAGATION_REQUIRED` scope shares the physical transaction of the outer scope, so an inner rollback-only marker makes the outer commit fail with `UnexpectedRollbackException`.
- `PROPAGATION_REQUIRES_NEW` uses an independent physical transaction and a new connection, which can exhaust a connection pool that is not sized for it.
- `PROPAGATION_NESTED` uses savepoints within one physical transaction and works only with JDBC resource transactions.
- The `isolation`, `timeout` and `readOnly` attributes apply only to propagation values of `REQUIRED` or `REQUIRES_NEW`.
- By default, a `RuntimeException` or an `Error` triggers rollback, and a checked `Exception` does not.
- `rollbackFor` matches the configured type and its subclasses; a pattern matches when the thrown exception's name contains it.
- As of 6.2, `@EnableTransactionManagement(rollbackOn=ALL_EXCEPTIONS)` rolls back for all exceptions, including checked ones.
- `@TransactionalEventListener` is bound to `AFTER_COMMIT` by default and is not invoked when no transaction is running, unless `fallbackExecution` is `true`.
- Reactive transactions carry the transaction context in the Reactor context, so it must be in the published event as the event source.
- With virtual threads enabled on Java 21+, Spring Boot auto-configures a `SimpleAsyncTaskExecutor` that uses virtual threads.

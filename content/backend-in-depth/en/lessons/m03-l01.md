# JVM internals, memory management and cloud efficiency

## Stack, heap, method area and Metaspace
<!-- bullets: 3.1.a -->

Each Java Virtual Machine thread has a private Java Virtual Machine stack, created at the same time as the thread (`jvms-2#jvms-2.5.2`).

A Java Virtual Machine stack stores frames (`jvms-2#jvms-2.5.2`).

If the computation in a thread requires a larger Java Virtual Machine stack than is permitted, the Java Virtual Machine throws a `StackOverflowError` (`jvms-2#jvms-2.5.2`).

The Java Virtual Machine has a heap that is shared among all Java Virtual Machine threads (`jvms-2#jvms-2.5.3`).

The heap is the run-time data area from which memory for all class instances and arrays is allocated (`jvms-2#jvms-2.5.3`).

Heap storage for objects is reclaimed by an automatic storage management system, known as a garbage collector (`jvms-2#jvms-2.5.3`).

If a computation requires more heap than can be made available by the automatic storage management system, the Java Virtual Machine throws an `OutOfMemoryError` (`jvms-2#jvms-2.5.3`).

The Java Virtual Machine has a method area that is shared among all Java Virtual Machine threads (`jvms-2#jvms-2.5.4`).

The method area stores per-class structures such as the run-time constant pool, field and method data, and the code for methods and constructors (`jvms-2#jvms-2.5.4`).

A run-time constant pool is a per-class or per-interface run-time representation of the `constant_pool` table in a class file (`jvms-2#jvms-2.5.5`).

Each run-time constant pool is allocated from the method area of the Java Virtual Machine (`jvms-2#jvms-2.5.5`).

Java class metadata is allocated in native memory, referred to as Metaspace (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

`-XX:MaxMetaspaceSize` sets the maximum amount of native memory that can be allocated for class metadata (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

By default, the size of Metaspace is not limited (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

If the Metaspace for class metadata is exhausted, the JVM throws a `java.lang.OutOfMemoryError` with the detail message `Metaspace` (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

The initial and maximum size of the Java heap space can be configured using the `-Xms` and `-Xmx` options (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

The `-XX:MaxHeapSize` option is equivalent to `-Xmx` (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

The snippet recurses without a limit, and then allocates an `int` array of `Integer.MAX_VALUE` elements.

```java snippet=m03-l01/MemoryAreaErrors.java
public class MemoryAreaErrors {
    static int depth = 0;

    static void recurse() {
        depth++;
        recurse();
    }

    public static void main(String[] args) {
        try {
            recurse();
        } catch (StackOverflowError e) {
            System.out.println("StackOverflowError after recursing: " + (depth > 1000));
        }
        try {
            int[] tooLarge = new int[Integer.MAX_VALUE];
            System.out.println(tooLarge.length);
        } catch (OutOfMemoryError e) {
            System.out.println("OutOfMemoryError: " + e.getMessage());
        }
    }
}
```

The snippet prints `StackOverflowError after recursing: true`, because the unbounded recursion needs a larger stack than the thread is permitted.

It then prints `OutOfMemoryError: Requested array size exceeds VM limit`.

The detail message `Requested array size exceeds VM limit` indicates an attempt to allocate an array with a size larger than the VM implementation limit, irrespective of how much heap size is available (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

:::esquema{kind=tabla title="Run-time data areas in the Java Virtual Machine Specification"}
| Area | What the specification says | Source |
|---|---|---|
| Java Virtual Machine stack | Private to each thread and holds frames | `jvms-2#jvms-2.5.2` |
| Heap | Shared among all threads and the source of memory for all class instances and arrays | `jvms-2#jvms-2.5.3` |
| Method area | Shared among all threads and stores per-class structures | `jvms-2#jvms-2.5.4` |

## Allocation: TLABs and escape analysis
<!-- bullets: 3.1.a -->

Small objects are allocated in a Thread Local Area Buffer (TLAB) (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

A TLAB is a small memory area where new objects are allocated (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

Once a TLAB is full, the thread gets a new one (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

Larger objects are allocated outside a TLAB (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The `jdk.ObjectAllocationInNewTLAB` and `jdk.ObjectAllocationOutsideTLAB` events provide information about the allocation of temporary objects (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The `jdk.ThreadAllocationStatistics` event provides information about the allocations per thread (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

`-XX:+UseTLAB` enables the use of thread-local allocation blocks (TLABs) in the young generation space (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

`-XX:-UseTLAB` disables the use of TLABs (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

If `-XX:TLABSize` is set to 0, the JVM selects the initial size of a TLAB automatically (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

`-XX:+DoEscapeAnalysis` enables the use of escape analysis (`jdk-tool-java#advanced-jit-compiler-options-for-java`).

`-XX:-DoEscapeAnalysis` disables the use of escape analysis (`jdk-tool-java#advanced-jit-compiler-options-for-java`).

## Heap size in a container
<!-- bullets: 3.1.a 3.1.d -->

`-XX:MaxRAM` sets the maximum amount of memory that the JVM may use for the Java heap before applying ergonomics heuristics (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

The maximum amount of available memory to the JVM process is the minimum of the machine's physical memory and any constraints set by the environment, such as a container (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

The default value of `-XX:MaxRAMPercentage` is 25 percent (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

The default value of `-XX:MinRAMPercentage` is 50 percent (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

For `-XX:MinRAMPercentage`, a small heap is a heap of approximately 125 MB (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

For server deployments, the options `-XX:InitialHeapSize` and `-XX:MaxHeapSize` are often set to the same value (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

The Java heap size can be minimized by lowering `-XX:MaxHeapFreeRatio`, whose default is 70%, and `-XX:MinHeapFreeRatio`, whose default is 40% (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

## How G1 lays out and collects the heap
<!-- bullets: 3.1.b -->

G1 partitions the heap into a set of equally sized heap regions (`jdk-gctuning-g1#JSGCT-GUID-15921907-B297-43A4-8C48-DC88035BC7CF`).

A G1 region is the unit of memory allocation and memory reclamation (`jdk-gctuning-g1#JSGCT-GUID-15921907-B297-43A4-8C48-DC88035BC7CF`).

The regions of the young generation in G1 are typically laid out in a noncontiguous pattern in memory (`jdk-gctuning-g1#JSGCT-GUID-15921907-B297-43A4-8C48-DC88035BC7CF`).

Old generation regions in G1 may be humongous, for objects that span multiple regions (`jdk-gctuning-g1#JSGCT-GUID-15921907-B297-43A4-8C48-DC88035BC7CF`).

An application always allocates into eden regions, with the exception of humongous objects that are directly allocated as belonging to the old generation (`jdk-gctuning-g1#JSGCT-GUID-15921907-B297-43A4-8C48-DC88035BC7CF`).

G1 is a generational, incremental, parallel, mostly concurrent, stop-the-world, and evacuating garbage collector (`jdk-gctuning-g1#JSGCT-GUID-E9CB81BC-92E5-489E-8A2E-760691A41CDF`).

G1 reclaims space mostly by using evacuation, copying live objects found within selected memory areas into new memory areas and compacting them in the process (`jdk-gctuning-g1#JSGCT-GUID-E9CB81BC-92E5-489E-8A2E-760691A41CDF`).

G1 is not a real-time collector (`jdk-gctuning-g1#JSGCT-GUID-E9CB81BC-92E5-489E-8A2E-760691A41CDF`).

The G1 collector alternates between the Young-Only phase and the Space-Reclamation phase (`jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).

The Young-Only phase contains garbage collections that fill up the currently available memory with objects in the old generation gradually (`jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).

The transition between the Young-Only phase and the Space-Reclamation phase starts when the old generation occupancy reaches the Initiating Heap Occupancy threshold (`jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).

A Concurrent Start young collection starts the marking process in addition to performing a Normal young collection (`jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).

Marking finishes with two special stop-the-world pauses, Remark and Cleanup (`jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).

The Remark pause finalizes the marking itself, performs reference processing and class unloading, reclaims completely empty regions and cleans up internal data structures (`jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).

The Space-Reclamation phase consists of multiple young collections that, in addition to young generation regions, also evacuate live objects of sets of old generation regions (`jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).

The collections of the Space-Reclamation phase are also called Mixed collections (`jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).

If the application runs out of memory while gathering liveness information, G1 performs an in-place stop-the-world full heap compaction (`jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).

`-XX:InitiatingHeapOccupancyPercent` sets the percentage of the old generation occupancy at which G1 starts the first few concurrent marking cycles (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

The initiating value of `-XX:InitiatingHeapOccupancyPercent` is 45% by default (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

`-XX:MaxGCPauseMillis` sets a target for the maximum GC pause time, and it is a soft goal (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

For G1 the default maximum pause time target is 200 milliseconds (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

Parallel GC can compact and reclaim space in the old generation only as a whole (`jdk-gctuning-g1#JSGCT-GUID-98E80C82-24D8-41D4-BC39-B2583F04F1FF`).

G1 incrementally distributes the old generation work across multiple much shorter collections (`jdk-gctuning-g1#JSGCT-GUID-98E80C82-24D8-41D4-BC39-B2583F04F1FF`).

G1 performs part of the old generation Space-Reclamation concurrently (`jdk-gctuning-g1#JSGCT-GUID-98E80C82-24D8-41D4-BC39-B2583F04F1FF`).

G1 may exhibit higher overhead than the other collectors, affecting throughput due to its concurrent nature (`jdk-gctuning-g1#JSGCT-GUID-98E80C82-24D8-41D4-BC39-B2583F04F1FF`).

G1 can reclaim some kinds of humongous objects during any collection (`jdk-gctuning-g1#JSGCT-GUID-98E80C82-24D8-41D4-BC39-B2583F04F1FF`).

String deduplication is disabled by default, and `-XX:+UseStringDeduplication` enables it (`jdk-gctuning-g1#JSGCT-GUID-98E80C82-24D8-41D4-BC39-B2583F04F1FF`).

## Tuning G1 for latency or throughput
<!-- bullets: 3.1.b -->

To increase throughput, G1 can be given a larger maximum pause time by using `-XX:MaxGCPauseMillis` (`jdk-gctuning-g1-tuning#JSGCT-GUID-70E3F150-B68E-4787-BBF1-F91315AC9AB9`).

The generation sizing heuristics adapt the size of the young generation automatically, which directly determines the frequency of pauses (`jdk-gctuning-g1-tuning#JSGCT-GUID-70E3F150-B68E-4787-BBF1-F91315AC9AB9`).

Increasing the minimum young generation size with `-XX:G1NewSizePercent` forces G1 to use a larger young generation (`jdk-gctuning-g1-tuning#JSGCT-GUID-70E3F150-B68E-4787-BBF1-F91315AC9AB9`).

`-XX:G1RSetUpdatingPauseTimePercent` can be used to move work from concurrent operation into the garbage collection pause (`jdk-gctuning-g1-tuning#JSGCT-GUID-70E3F150-B68E-4787-BBF1-F91315AC9AB9`).

Concurrent refinement can be completely disabled with `-XX:-G1UseConcRefinement` (`jdk-gctuning-g1-tuning#JSGCT-GUID-70E3F150-B68E-4787-BBF1-F91315AC9AB9`).

Setting `-Xms` and `-Xmx` to the same value minimizes heap resizing work (`jdk-gctuning-g1-tuning#JSGCT-GUID-70E3F150-B68E-4787-BBF1-F91315AC9AB9`).

`-XX:+AlwaysPreTouch` moves the operating system work of backing virtual memory with physical memory to VM startup time (`jdk-gctuning-g1-tuning#JSGCT-GUID-70E3F150-B68E-4787-BBF1-F91315AC9AB9`).

Many collectors do most of their work in the background, so what matters is how long the application actually had to stop (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The sum of pauses is the total amount of time that the application was paused during a GC (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The `jfr` tool can print the `jdk.GCPhasePause` events that a flight recording contains (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

A recording taken to investigate garbage collection issues should not include the heap statistics, because that triggers extra old collections (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The bigger the Java heap, the longer the time between GCs (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

## ZGC and choosing a collector
<!-- bullets: 3.1.b -->

ZGC performs all expensive work concurrently, without stopping the execution of application threads for more than a millisecond (`jdk-gctuning-zgc#JSGCT-GUID-8637B158-4F35-4E2D-8E7B-9DAEF15BB3CD`).

ZGC pause times are independent of the heap size that is being used (`jdk-gctuning-zgc#JSGCT-GUID-8637B158-4F35-4E2D-8E7B-9DAEF15BB3CD`).

ZGC works well with heap sizes from a few hundred megabytes to 16TB (`jdk-gctuning-zgc#JSGCT-GUID-8637B158-4F35-4E2D-8E7B-9DAEF15BB3CD`).

ZGC dynamically adapts to the workload by resizing generations, scaling the number of GC threads, and adjusting tenuring thresholds (`jdk-gctuning-zgc#JSGCT-GUID-8637B158-4F35-4E2D-8E7B-9DAEF15BB3CD`).

The main tuning knob of ZGC is to increase the maximum heap size (`jdk-gctuning-zgc#JSGCT-GUID-8637B158-4F35-4E2D-8E7B-9DAEF15BB3CD`).

As of JDK 24 ZGC is a generational garbage collector (`jdk-gctuning-zgc#JSGCT-GUID-8637B158-4F35-4E2D-8E7B-9DAEF15BB3CD`).

The `ZGenerational` option has been removed (`jdk-gctuning-zgc#JSGCT-GUID-8637B158-4F35-4E2D-8E7B-9DAEF15BB3CD`).

JEP 439 extends ZGC to maintain separate generations for young and old objects (`jep-439#Summary`).

Separate generations allow ZGC to collect young objects, which tend to die young, more frequently (`jep-439#Summary`).

JEP 474 switches the default mode of ZGC to the generational mode and deprecates the non-generational mode (`jep-474#Summary`).

`-XX:ZUncommitDelay` sets the time that heap memory must have been unused before being uncommitted, and its default is 300 seconds (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

`-XX:+ZUncommit` enables uncommitting of unused heap memory when using ZGC, and it is enabled by default (`jdk-tool-java#advanced-garbage-collection-options-for-java`).

Unless the application has rather strict pause-time requirements, the guide advises running it first and allowing the VM to select a collector (`jdk-gctuning-collectors#JSGCT-GUID-414C9D95-297E-4EE3-B0D9-36F158A83393`).

For a small data set of up to approximately 100 MB, the guide suggests the serial collector with `-XX:+UseSerialGC` (`jdk-gctuning-collectors#JSGCT-GUID-414C9D95-297E-4EE3-B0D9-36F158A83393`).

When peak application performance is the first priority and pauses of one second or longer are acceptable, the guide suggests the parallel collector with `-XX:+UseParallelGC` (`jdk-gctuning-collectors#JSGCT-GUID-414C9D95-297E-4EE3-B0D9-36F158A83393`).

When response time is more important than overall throughput, the guide suggests the mostly concurrent collector with `-XX:+UseG1GC` (`jdk-gctuning-collectors#JSGCT-GUID-414C9D95-297E-4EE3-B0D9-36F158A83393`).

When response time is a high priority, the guide suggests a fully concurrent collector with `-XX:+UseZGC` (`jdk-gctuning-collectors#JSGCT-GUID-414C9D95-297E-4EE3-B0D9-36F158A83393`).

The collector guidelines are only a starting point, because performance depends on the size of the heap, the amount of live data and the number and speed of available processors (`jdk-gctuning-collectors#JSGCT-GUID-414C9D95-297E-4EE3-B0D9-36F158A83393`).

The snippet starts a child JVM for each of four collector options and prints the names of the garbage collector beans that each one reports.

```java snippet=m03-l01/CollectorNames.java
import java.lang.management.GarbageCollectorMXBean;
import java.lang.management.ManagementFactory;
import java.util.List;

public class CollectorNames {
    public static void main(String[] args) throws Exception {
        if (args.length > 0) {
            List<GarbageCollectorMXBean> beans = ManagementFactory.getGarbageCollectorMXBeans();
            beans.stream().map(GarbageCollectorMXBean::getName).sorted().forEach(System.out::println);
            return;
        }
        String java = ProcessHandle.current().info().command().orElseThrow();
        for (String flag : List.of("-XX:+UseSerialGC", "-XX:+UseParallelGC", "-XX:+UseG1GC", "-XX:+UseZGC")) {
            Process child = new ProcessBuilder(java, flag, "CollectorNames.java", "child")
                    .redirectErrorStream(true)
                    .start();
            String output = new String(child.getInputStream().readAllBytes()).strip().replace("\n", ", ");
            child.waitFor();
            System.out.println(flag + " -> " + output);
        }
    }
}
```

The snippet prints `-XX:+UseSerialGC -> Copy, MarkSweepCompact` and `-XX:+UseParallelGC -> PS MarkSweep, PS Scavenge`.

It prints `-XX:+UseG1GC -> G1 Concurrent GC, G1 Old Generation, G1 Young Generation`.

It prints `-XX:+UseZGC -> ZGC Major Cycles, ZGC Major Pauses, ZGC Minor Cycles, ZGC Minor Pauses`, so ZGC reports minor and major cycles.

## Diagnosing memory leaks
<!-- bullets: 3.1.c -->

An `OutOfMemoryError` indicates that the garbage collector cannot make space available to accommodate a new object, and the heap cannot be expanded further (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

A detail message is appended to the text of an `OutOfMemoryError` to help discover the cause (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

The detail message `Java heap space` indicates that an object could not be allocated in the Java heap (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

The `Java heap space` error does not necessarily imply a memory leak (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

The `Java heap space` problem can be a configuration issue, where the specified heap size or the default size is insufficient for the application (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

After a garbage collection, if the application spends more than approximately 98% of its time performing garbage collection and recovers less than 2% of the heap for the last five consecutive collections, a `java.lang.OutOfMemoryError` is thrown (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`).

A memory leak occurs when an application unintentionally holds references to Java objects or classes, preventing them from being garbage collected (`jdk-troubleshoot-memleaks#JSTGD-GUID-2A57EA14-3A39-4E6D-90FA-95788A9C3605`).

Before assuming a memory leak in the application, the memory pool for which the error is seen should be sized adequately (`jdk-troubleshoot-memleaks#JSTGD-GUID-2A57EA14-3A39-4E6D-90FA-95788A9C3605`).

To detect a memory leak, the live set is monitored, that is, the amount of Java heap space or Metaspace being used after a full garbage collection (`jdk-troubleshoot-memleaks#JSTGD-GUID-2A57EA14-3A39-4E6D-90FA-95788A9C3605`).

A live set that increases over time after the application has reached a stable state under a stable load could be a strong indication of a memory leak (`jdk-troubleshoot-memleaks#JSTGD-GUID-2A57EA14-3A39-4E6D-90FA-95788A9C3605`).

The live set can be monitored by using JConsole and JDK Mission Control, and the memory usage information can also be extracted from garbage collection logs (`jdk-troubleshoot-memleaks#JSTGD-GUID-2A57EA14-3A39-4E6D-90FA-95788A9C3605`).

To confirm native memory leaks, native tools such as `pmap` or PerfMon are used to compare periodically collected output (`jdk-troubleshoot-memleaks#JSTGD-GUID-2A57EA14-3A39-4E6D-90FA-95788A9C3605`).

Heap dumps are the most important data to troubleshoot memory leaks (`jdk-troubleshoot-memleaks#JSTGD-GUID-4B841E7E-C533-447B-B093-58CEE13B962A`).

Heap dumps can be collected using `jcmd`, `jmap`, JConsole tools, and the `-XX:+HeapDumpOnOutOfMemoryError` Java option (`jdk-troubleshoot-memleaks#JSTGD-GUID-4B841E7E-C533-447B-B093-58CEE13B962A`).

The `-XX:+HeapDumpOnOutOfMemoryError` option dumps the Java heap of a process when it fails with a `java.lang.OutOfMemoryError` (`jdk-troubleshoot-memleaks#JSTGD-GUID-4B841E7E-C533-447B-B093-58CEE13B962A`).

```bash
jcmd <process id/main class> GC.heap_dump filename=heapdump.dmp
jcmd <process id/main class> GC.class_histogram filename=Myheaphistogram
```

The `GC.heap_dump` command of `jcmd` generates a HPROF format dump of the Java heap (`jdk-tool-jcmd#commands-for-jcmd`).

`GC.heap_dump` requests a full GC unless the `-all` option is specified (`jdk-tool-jcmd#commands-for-jcmd`).

The `-all` option of `GC.heap_dump` dumps all objects, including unreachable objects, and it is false by default (`jdk-tool-jcmd#commands-for-jcmd`).

The `-gz` option of `GC.heap_dump` writes the heap dump in gzipped format when it is specified (`jdk-tool-jcmd#commands-for-jcmd`).

The impact of `GC.heap_dump` is high and depends on the Java heap size and content (`jdk-tool-jcmd#commands-for-jcmd`).

The `GC.class_histogram` command of `jcmd` provides statistics about the Java heap usage (`jdk-tool-jcmd#commands-for-jcmd`).

The output of a heap histogram shows the total size and instance count for each class type in the heap (`jdk-troubleshoot-memleaks#JSTGD-GUID-93A2C2F1-C22C-4E76-83B8-785D3DD869E9`).

If a sequence of histograms is obtained, for example every two minutes, a trend might be visible that leads to further analysis (`jdk-troubleshoot-memleaks#JSTGD-GUID-93A2C2F1-C22C-4E76-83B8-785D3DD869E9`).

The guide recommends `jcmd` instead of `jmap` for enhanced diagnostics and reduced performance overhead (`jdk-troubleshoot-memleaks#JSTGD-GUID-93A2C2F1-C22C-4E76-83B8-785D3DD869E9`).

There are many third-party tools available for heap dump analysis (`jdk-troubleshoot-memleaks#JSTGD-GUID-9F372CA9-E5C7-4098-A29E-D112B0877408`).

## Thread dumps and deadlocks
<!-- bullets: 3.1.c -->

A thread dump consists of the thread stack, including the thread state, for all Java threads in the virtual machine (`jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238`).

A thread dump does not terminate the application, which continues after the thread information is printed (`jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238`).

The `Thread.print` command of `jcmd` prints all threads with stack traces (`jdk-tool-jcmd#commands-for-jcmd`).

The `-l` option of `Thread.print` prints `java.util.concurrent` locks (`jdk-tool-jcmd#commands-for-jcmd`).

The `Thread.dump_to_file` command of `jcmd` dumps threads, with stack traces, to a file in plain text or JSON format (`jdk-tool-jcmd#commands-for-jcmd`).

The `NEW` thread state means that the thread has not yet started (`jdk-troubleshoot-tools#JSTGD-GUID-0110914C-4E91-4983-9CDB-412BC6C36AEA`).

The `RUNNABLE` thread state means that the thread is executing in the JVM (`jdk-troubleshoot-tools#JSTGD-GUID-0110914C-4E91-4983-9CDB-412BC6C36AEA`).

The `BLOCKED` thread state means that the thread is blocked, waiting for a monitor lock (`jdk-troubleshoot-tools#JSTGD-GUID-0110914C-4E91-4983-9CDB-412BC6C36AEA`).

The `WAITING` thread state means that the thread is waiting indefinitely for another thread to perform a particular action (`jdk-troubleshoot-tools#JSTGD-GUID-0110914C-4E91-4983-9CDB-412BC6C36AEA`).

The `TIMED_WAITING` thread state means that the thread is waiting for another thread to perform an action for up to a specified waiting time (`jdk-troubleshoot-tools#JSTGD-GUID-0110914C-4E91-4983-9CDB-412BC6C36AEA`).

The `TERMINATED` thread state means that the thread has exited (`jdk-troubleshoot-tools#JSTGD-GUID-0110914C-4E91-4983-9CDB-412BC6C36AEA`).

The snippet puts one thread in each of the `WAITING`, `TIMED_WAITING` and `BLOCKED` states and prints the states.

```java snippet=m03-l01/ThreadStates.java
import java.util.concurrent.CountDownLatch;

public class ThreadStates {
    static final Object monitor = new Object();

    static void awaitState(Thread thread, Thread.State wanted) throws InterruptedException {
        while (thread.getState() != wanted) {
            Thread.sleep(5);
        }
    }

    public static void main(String[] args) throws InterruptedException {
        CountDownLatch release = new CountDownLatch(1);
        Thread waiting = new Thread(() -> {
            try {
                release.await();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
        Thread sleeping = new Thread(() -> {
            try {
                Thread.sleep(60_000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
        Thread blocked = new Thread(() -> {
            synchronized (monitor) {
                System.out.println("blocked thread entered the monitor");
            }
        });
        System.out.println(blocked.getState());
        synchronized (monitor) {
            waiting.start();
            sleeping.start();
            blocked.start();
            awaitState(waiting, Thread.State.WAITING);
            awaitState(sleeping, Thread.State.TIMED_WAITING);
            awaitState(blocked, Thread.State.BLOCKED);
            System.out.println(waiting.getState());
            System.out.println(sleeping.getState());
            System.out.println(blocked.getState());
        }
        blocked.join();
        release.countDown();
        sleeping.interrupt();
        waiting.join();
        sleeping.join();
        System.out.println(waiting.getState());
    }
}
```

The snippet prints `NEW` for a thread that has not started, then `WAITING`, `TIMED_WAITING` and `BLOCKED` for the three threads, in that order.

It prints `blocked thread entered the monitor` once the main thread leaves the `synchronized` block, and ends with `TERMINATED` for the thread that was released.

If a deadlock is detected, it is printed along with the stack trace of the threads involved in the deadlock (`jdk-troubleshoot-hangs#JSTGD-GUID-5A88BA3D-D0FC-466F-B5B9-566ED0D62DF1`).

The default deadlock detection works with locks obtained using the `synchronized` keyword, as well as with locks obtained using the `java.util.concurrent` package (`jdk-troubleshoot-hangs#JSTGD-GUID-5A88BA3D-D0FC-466F-B5B9-566ED0D62DF1`).

If the Java VM flag `-XX:+PrintConcurrentLocks` is set, the stack trace also shows a list of lock owners (`jdk-troubleshoot-hangs#JSTGD-GUID-5A88BA3D-D0FC-466F-B5B9-566ED0D62DF1`).

If the thread dump is printed and no deadlocks are found, the issue might be a bug in which a thread is waiting for a monitor that is never notified (`jdk-troubleshoot-hangs#JSTGD-GUID-8B8DE8E0-D7E3-48A9-96EB-77BC1128100D`).

## Start-up time and footprint: AppCDS and the AOT cache
<!-- bullets: 3.1.d -->

Application Class Data Sharing stores classes used by your applications in an archive file (`jdk-tool-java#application-class-data-sharing`).

AppCDS can improve the start-up time of applications, because the stored classes can be loaded very quickly compared to classes stored in a JAR file (`jdk-tool-java#application-class-data-sharing`).

AppCDS can reduce the runtime memory footprint by sharing parts of these classes across multiple processes (`jdk-tool-java#application-class-data-sharing`).

Classes in the CDS archive are stored in an optimized format that is about 2 to 5 times larger than classes stored in JAR files or the JDK runtime image (`jdk-tool-java#application-class-data-sharing`).

It is a good idea to archive only those classes that are actually used by the application (`jdk-tool-java#application-class-data-sharing`).

JEP 350 extends application class-data sharing to allow the dynamic archiving of classes at the end of Java application execution (`jep-350#Summary`).

The AOT cache is a container, introduced in JDK 24, for storing artifacts produced by AOT optimizations (`jdk-tool-java#ahead-of-time-cache`).

An AOT cache is specific to a particular application, a particular JDK release, and a particular OS and CPU architecture (`jdk-tool-java#ahead-of-time-cache`).

If the application, the JDK release, or the OS and CPU architecture changes, the AOT cache must be recreated (`jdk-tool-java#ahead-of-time-cache`).

The deployment of the AOT cache is divided into three phases, Training, Assembly and Production (`jdk-tool-java#ahead-of-time-cache`).

In the Training phase the application runs with a representative work-load, and the gathered data are saved in an AOT Configuration file (`jdk-tool-java#ahead-of-time-cache`).

`-XX:AOTMode=record` executes the application in the training phase (`jdk-tool-java#ahead-of-time-cache`).

`-XX:AOTMode=create` performs the Assembly phase (`jdk-tool-java#ahead-of-time-cache`).

In the `create` mode the application itself is not executed (`jdk-tool-java#ahead-of-time-cache`).

`-XX:AOTMode=on` executes the application in the Production phase (`jdk-tool-java#ahead-of-time-cache`).

`-XX:AOTMode=auto` is the default and takes effect if no `-XX:AOTMode` option is present (`jdk-tool-java#ahead-of-time-cache`).

`-XX:AOTMode=off` means that no AOT cache is used and the other AOT command line options are ignored (`jdk-tool-java#ahead-of-time-cache`).

If the AOT cache fails to load and `AOTMode` was originally `auto`, the JVM continues execution without using the AOT cache (`jdk-tool-java#ahead-of-time-cache`).

If the AOT cache fails to load and `AOTMode` is `on`, the JVM prints an error message and exits immediately (`jdk-tool-java#ahead-of-time-cache`).

JEP 483 extends the HotSpot JVM to support an ahead-of-time cache that can store classes after reading, parsing, loading, and linking them (`jep-483#Description`).

Creating an AOT cache with JEP 483 takes two steps, a training run and a second run that creates the cache (`jep-483#Description`).

With JEP 483, if the cache file is unusable or does not exist, HotSpot issues a warning message and continues (`jep-483#Description`).

JEP 483 reports that Spring PetClinic 3.2.0 loads and links about 21,000 classes at startup (`jep-483#Description`).

JEP 483 reports that Spring PetClinic starts in 4.486 seconds on JDK 23 and in 2.604 seconds on JDK 24 when using an AOT cache, an improvement of 42% (`jep-483#Description`).

JEP 514 adds the `-XX:AOTCacheOutput` option, which, when used alone, makes the launcher run a training run and then create the AOT cache (`jep-514#Description`).

With JEP 514 a production run that uses the AOT cache is started with `-XX:AOTCache` (`jep-514#Description`).

JEP 515 extends the AOT cache to collect method profiles during training runs (`jep-515#Description`).

With cached profiles, production runs of the application are both faster to start and faster to achieve peak performance (`jep-515#Description`).

Profiles cached during training runs do not prevent additional profiling during production runs (`jep-515#Description`).

The net effect of cached profiles is that the JIT runs earlier and with more accuracy (`jep-515#Description`).

## Spring AOT and GraalVM Native Image
<!-- bullets: 3.1.d -->

Spring's support for AOT optimizations inspects an `ApplicationContext` at build time and applies decisions and discovery logic that usually happens at runtime (`spring-fw-aot#aot.introduction`).

Spring AOT requires that the classpath is fixed and fully defined at build time (`spring-fw-aot#aot.introduction`).

Spring AOT requires that the beans defined in the application cannot change at runtime (`spring-fw-aot#aot.introduction`).

With Spring AOT, `@Profile`, in particular profile-specific configuration, needs to be chosen at build time and is automatically enabled at runtime when AOT is enabled (`spring-fw-aot#aot.introduction`).

With Spring AOT, environment properties that impact the presence of a bean (`@Conditional`) are only considered at build time (`spring-fw-aot#aot.introduction`).

With Spring AOT, bean definitions with instance suppliers, such as lambdas or method references, cannot be transformed ahead of time (`spring-fw-aot#aot.introduction`).

A Spring AOT processed application typically generates Java source code, bytecode, usually for dynamic proxies, and `RuntimeHints` for the use of reflection, resource loading, serialization, and JDK proxies (`spring-fw-aot#aot.introduction`).

AOT is a mandatory step to transform a Spring application to a native executable (`spring-fw-aot#aot.running`).

AOT optimizations can be used on the JVM by setting the `spring.aot.enabled` system property to true (`spring-fw-aot#aot.running`).

The AOT cache and Spring's AOT can be combined to further improve start-up time (`spring-boot-aot#page-title`).

GraalVM Native Image performs static analysis of the application at build time from the main entry point (`spring-boot-native-intro#packaging.native-image.introducing-graalvm-native-images.key-differences-with-jvm-deployments`).

In a native image, code that cannot be reached when the image is created is removed and is not part of the executable (`spring-boot-native-intro#packaging.native-image.introducing-graalvm-native-images.key-differences-with-jvm-deployments`).

GraalVM is not directly aware of dynamic elements of the code and must be told about reflection, resources, serialization, and dynamic proxies (`spring-boot-native-intro#packaging.native-image.introducing-graalvm-native-images.key-differences-with-jvm-deployments`).

In a native image, there is no lazy class loading, and everything shipped in the executable is loaded in memory on startup (`spring-boot-native-intro#packaging.native-image.introducing-graalvm-native-images.key-differences-with-jvm-deployments`).

Static analysis determines which program elements, such as classes, methods and fields, are used by an application (`graalvm-native-image-basics#static-analysis`).

Only reachable elements are included in the final image (`graalvm-native-image-basics#static-analysis`).

Once a native image is built, no new elements can be added at run time, for example through class loading, which is called the closed-world assumption (`graalvm-native-image-basics#static-analysis`).

If a class is initialized at build time, its static fields are saved in the produced binary (`graalvm-native-image-basics#build-time-vs-run-time`).

The `--initialize-at-build-time=<class>` option of the `native-image` builder triggers class initialization at build time (`graalvm-native-image-basics#build-time-vs-run-time`).

Build-time class initialization is an expert feature, and not all classes are suitable for it (`graalvm-native-image-basics#build-time-vs-run-time`).

:::esquema{kind=tabla title="What each start-up option fixes ahead of time"}
| Option | What is prepared ahead of time | Source |
|---|---|---|
| AppCDS | Classes used by the application, stored in an archive file | `jdk-tool-java#application-class-data-sharing` |
| AOT cache | Classes and method profiles gathered in a training run, specific to the application, JDK release, and OS and CPU architecture | `jdk-tool-java#ahead-of-time-cache`; `jep-515#Description` |
| Spring AOT | Build-time inspection of an `ApplicationContext`, with a classpath and a set of beans fixed at build time | `spring-fw-aot#aot.introduction` |
| GraalVM Native Image | Only the elements reachable by static analysis, with no new elements added at run time | `graalvm-native-image-basics#static-analysis` |
:::

## Key points

- The Java Virtual Machine stack is private to each thread and holds frames, while the heap and the method area are shared among all threads (`jvms-2#jvms-2.5.2`; `jvms-2#jvms-2.5.3`; `jvms-2#jvms-2.5.4`).
- Class metadata lives in native memory called Metaspace, and its size is not limited by default (`jdk-troubleshoot-memleaks#JSTGD-GUID-19F6D28E-75A1-4480-9879-D0932B2F305B`; `jdk-tool-java#advanced-garbage-collection-options-for-java`).
- Unbounded recursion ends in a `StackOverflowError`, and an array larger than the VM limit ends in an `OutOfMemoryError` whatever the heap size.
- Small objects are allocated in a TLAB, and larger objects are allocated outside one (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).
- G1 splits the heap into equally sized regions and alternates between a Young-Only phase and a Space-Reclamation phase (`jdk-gctuning-g1#JSGCT-GUID-15921907-B297-43A4-8C48-DC88035BC7CF`; `jdk-gctuning-g1#JSGCT-GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180`).
- For G1, `-XX:MaxGCPauseMillis` is a soft pause target that defaults to 200 milliseconds, and raising it favours throughput (`jdk-tool-java#advanced-garbage-collection-options-for-java`; `jdk-gctuning-g1-tuning#JSGCT-GUID-70E3F150-B68E-4787-BBF1-F91315AC9AB9`).
- ZGC has pause times independent of the heap size and, as of JDK 24, is only generational (`jdk-gctuning-zgc#JSGCT-GUID-8637B158-4F35-4E2D-8E7B-9DAEF15BB3CD`).
- A memory leak shows as a live set that keeps growing under a stable load, and a heap dump is the most important data to troubleshoot it (`jdk-troubleshoot-memleaks#JSTGD-GUID-2A57EA14-3A39-4E6D-90FA-95788A9C3605`; `jdk-troubleshoot-memleaks#JSTGD-GUID-4B841E7E-C533-447B-B093-58CEE13B962A`).
- A thread dump shows each thread's state and does not stop the application, and the default deadlock detection covers `synchronized` and `java.util.concurrent` locks (`jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238`; `jdk-troubleshoot-hangs#JSTGD-GUID-5A88BA3D-D0FC-466F-B5B9-566ED0D62DF1`).
- An AOT cache is specific to the application, the JDK release, and the OS and CPU architecture, and it is built in a training, an assembly and a production phase (`jdk-tool-java#ahead-of-time-cache`).
- Spring AOT requires a classpath fixed at build time, and a native image keeps only the elements reachable by static analysis (`spring-fw-aot#aot.introduction`; `graalvm-native-image-basics#static-analysis`).

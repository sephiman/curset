# Spring Boot auto-configuration

## Discovery, ordering and the condition report
<!-- bullets: 5.2.a -->

Auto-configuration is how Spring Boot builds the beans a typical application needs from what is on its classpath. Each candidate is an ordinary configuration class guarded by conditions. Boot applies it only when its classes are present, and it backs off when you declare the bean yourself. A report lists every decision, which is where you look when a bean is missing or unexpected.

Spring Boot auto-configuration attempts to automatically configure your Spring application based on the jar dependencies that you have added (`spring-boot-using-auto-configuration#page-title`).

You opt in to auto-configuration by adding `@EnableAutoConfiguration` or `@SpringBootApplication` to one of your `@Configuration` classes (`spring-boot-using-auto-configuration#page-title`).

You should only ever add one `@SpringBootApplication` or `@EnableAutoConfiguration` annotation (`spring-boot-using-auto-configuration#page-title`).

The documentation generally recommends adding one or the other to your primary `@Configuration` class only (`spring-boot-using-auto-configuration#page-title`).

Auto-configuration is non-invasive, and at any point you can define your own configuration to replace specific parts of it (`spring-boot-using-auto-configuration#using.auto-configuration.replacing`).

If you add your own `DataSource` bean, the default embedded database support backs away (`spring-boot-using-auto-configuration#using.auto-configuration.replacing`).

You can use the `exclude` attribute of `@SpringBootApplication` to disable specific auto-configuration classes, and `excludeName` with the fully qualified name if the class is not on the classpath (`spring-boot-using-auto-configuration#using.auto-configuration.disabling-specific`).

You can also control the list of excluded auto-configuration classes with the `spring.autoconfigure.exclude` property (`spring-boot-using-auto-configuration#using.auto-configuration.disabling-specific`).

The only aspect of an auto-configuration class that is considered public API is its name, which can be used for disabling it; the contents, such as nested configuration classes or bean methods, are for internal use only (`spring-boot-using-auto-configuration#using.auto-configuration.disabling-specific`).

Auto-configuration packages are the packages that various auto-configured features look in by default when scanning for things such as entities and Spring Data repositories (`spring-boot-using-auto-configuration#using.auto-configuration.packages`).

The `@EnableAutoConfiguration` annotation, directly or through `@SpringBootApplication`, determines the default auto-configuration package (`spring-boot-using-auto-configuration#using.auto-configuration.packages`).

Classes that implement auto-configuration are annotated with `@AutoConfiguration`, which is meta-annotated with `@Configuration`, so auto-configurations are standard `@Configuration` classes (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.understanding-auto-configured-beans`).

Auto-configuration classes usually use the `@ConditionalOnClass` and `@ConditionalOnMissingBean` annotations (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.understanding-auto-configured-beans`).

This ensures that auto-configuration applies only when relevant classes are found and when you have not declared your own `@Configuration` (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.understanding-auto-configured-beans`).

When `@ConditionalOnMissingBean` is placed on a `@Bean` method, the target type defaults to the return type of the method (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.bean-conditions`).

Bean conditions are evaluated based on what has been processed so far, so the documentation recommends using `@ConditionalOnBean` and `@ConditionalOnMissingBean` only on auto-configuration classes, which are guaranteed to load after any user-defined bean definitions have been added (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.bean-conditions`).

Bean condition evaluation can only rely on the type information available in the method signature, so a `@Bean` method should provide as much type information as possible in its return type (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.bean-conditions`).

```java snippet=m05-l02/BackOff.java
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class BackOff {
    record Greeter(String origin) {}

    @Configuration
    static class UserConfig {
        @Bean Greeter userGreeter() { return new Greeter("user"); }
    }

    @Configuration
    static class DefaultConfig {
        @Bean @ConditionalOnMissingBean Greeter defaultGreeter() { return new Greeter("default"); }
    }

    static void run(Class<?>... configurations) {
        try (var context = new AnnotationConfigApplicationContext(configurations)) {
            System.out.println(context.getBeansOfType(Greeter.class).values().stream().map(Greeter::origin).toList());
        }
    }

    public static void main(String[] args) {
        run(DefaultConfig.class);
        run(UserConfig.class, DefaultConfig.class);
    }
}
```

The program prints `[default]` for the context with only the default configuration, and `[user]` once `UserConfig` is registered first: the default `Greeter` backed off.

Spring Boot checks for the presence of a `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` file within your published jar (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

Auto-configurations must be loaded only by being named in the imports file (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

To apply a configuration in a specific order, use the `before`, `beforeName`, `after` and `afterName` attributes of `@AutoConfiguration`, or the dedicated `@AutoConfigureBefore` and `@AutoConfigureAfter` annotations (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

`@AutoConfigureOrder` has the same semantic as the regular `@Order` annotation but provides a dedicated order for auto-configuration classes (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

The order in which auto-configuration classes are applied only affects the order in which their beans are defined (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

The order in which those beans are subsequently created is unaffected and is determined by each bean's dependencies and any `@DependsOn` relationships (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

```java snippet=m05-l02/AutoOrdering.java
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.EnableAutoConfiguration;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;

public class AutoOrdering {
    @AutoConfiguration(after = Zeta.class)
    public static class Alpha {
        @Bean String alphaBean() { return "alpha"; }
    }

    @AutoConfiguration
    public static class Zeta {
        @Bean String zetaBean() { return "zeta"; }
    }

    public static void main(String[] args) throws Exception {
        Path root = Files.createTempDirectory("order");
        Path file = root.resolve("META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports");
        Files.createDirectories(file.getParent());
        Files.writeString(file, "AutoOrdering$Alpha\nAutoOrdering$Zeta\n");
        var loader = new URLClassLoader(new URL[] {root.toUri().toURL()}, AutoOrdering.class.getClassLoader());
        try (var context = new AnnotationConfigApplicationContext()) {
            context.setClassLoader(loader);
            context.register(EnableAuto.class);
            context.refresh();
            System.out.println(List.of(context.getBeanDefinitionNames()).stream().filter(n -> n.endsWith("Bean")).map(n -> n.replace("Bean", "")).toList());
        }
    }

    @EnableAutoConfiguration
    public static class EnableAuto {}
}
```

The program prints `[zeta, alpha]`: the imports file lists `Alpha` first, and `@AutoConfiguration(after = Zeta.class)` made `Zeta` define its bean before it.

:::diagram{kind="flow" caption="From the imports file to bean creation"}
description: The imports file names the auto-configuration classes, the before and after attributes order them, their beans are defined in that order, and the beans are created according to their dependencies.
imports: Imports file names the classes
order: Classes ordered by before and after
define: Bean definitions added in that order
create: Beans created by dependencies and DependsOn
imports -> order
order -> define
define -> create: order of creation is unaffected
:::

A `ConditionEvaluationReport` is available in any Spring Boot `ApplicationContext` (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

You can see the report if you enable `DEBUG` logging output (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

With the actuator, a `conditions` endpoint renders the report in JSON (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

Adding `--debug` to the command line or the system property `-Ddebug` logs all the auto-configuration decisions that were made in your app on the console (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

Classes annotated with `@ConfigurationProperties`, such as `ServerProperties`, show the available external configuration options (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

```java snippet=m05-l02/ConditionReport.java
import java.util.TreeMap;
import org.springframework.boot.autoconfigure.condition.ConditionEvaluationReport;
import org.springframework.boot.autoconfigure.condition.ConditionalOnClass;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class ConditionReport {
    record Greeter() {}

    @Configuration
    static class UserConfig {
        @Bean Greeter userGreeter() { return new Greeter(); }
    }

    @Configuration
    static class DefaultConfig {
        @Bean @ConditionalOnMissingBean Greeter defaultGreeter() { return new Greeter(); }
        @Bean @ConditionalOnClass(name = "com.acme.Missing") String missingClass() { return "never"; }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext()) {
            var report = ConditionEvaluationReport.get(context.getDefaultListableBeanFactory());
            context.register(UserConfig.class, DefaultConfig.class);
            context.refresh();
            new TreeMap<>(report.getConditionAndOutcomesBySource()).forEach(
                (source, outcomes) -> System.out.println(source + " fullMatch=" + outcomes.isFullMatch()));
        }
    }
}
```

The program prints `ConditionReport$DefaultConfig#defaultGreeter fullMatch=false` and `ConditionReport$DefaultConfig#missingClass fullMatch=false`: the report records the outcome of each conditional `@Bean` method, and neither matched.

## Starters and externalised configuration
<!-- bullets: 5.2.b -->

Configuration values reach the application through the `Environment`. `@ConfigurationProperties` binds a group of them into a typed object, and it accepts several spellings of one property name. When the same property is set in several places, the order of the property sources decides which value wins. A starter is a dependency descriptor that brings in the libraries for one kind of application.

Starters are a set of convenient dependency descriptors that you can include in your application (`spring-boot-using-build-systems#using.build-systems.starters`).

To use Spring and JPA for database access, include the `spring-boot-starter-data-jpa` dependency in your project (`spring-boot-using-build-systems#using.build-systems.starters`).

All official starters follow the naming pattern `spring-boot-starter-*`, where `*` is a particular type of application (`spring-boot-using-build-systems#using.build-systems.starters`).

Third-party starters should not start with `spring-boot`, as it is reserved for official Spring Boot artifacts (`spring-boot-using-build-systems#using.build-systems.starters`).

A third-party starter typically starts with the name of the project (`spring-boot-using-build-systems#using.build-systems.starters`).

Spring Boot lets you externalize your configuration so that you can work with the same application code in different environments (`spring-boot-features-external-config#page-title`).

Property values can be injected into your beans with `@Value`, accessed through the `Environment` abstraction, or bound to structured objects through `@ConfigurationProperties` (`spring-boot-features-external-config#page-title`).

`@ConfigurationProperties` lets strongly typed beans govern and validate the configuration of your application (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties`).

Spring Boot uses relaxed rules for binding `Environment` properties to `@ConfigurationProperties` beans, so the property name and the bean property name do not need to match exactly (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding`).

A dash-separated property such as `context-path` binds to `contextPath`, and a capitalized property such as `PORT` binds to `port` (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding`).

:::esquema{kind=tabla title="Relaxed binding of one property"}
| Property | Note | Citation |
| --- | --- | --- |
| `my.main-project.person.first-name` | Kebab case, which is recommended for use in `.properties` and YAML files | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding` |
| `my.main-project.person.firstName` | Standard camel case syntax | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding` |
| `my.main-project.person.first_name` | Underscore notation, which is an alternative format for use in `.properties` and YAML files | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding` |
| `MY_MAINPROJECT_PERSON_FIRSTNAME` | Upper case format, which is recommended when using system environment variables | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding` |
:::

The prefix value of the `@ConfigurationProperties` annotation must be in kebab case (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding`).

The documentation recommends that properties are stored in lower-case kebab format when possible, such as `my.person.first-name=Rod` (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding`).

```java snippet=m05-l02/RelaxedBinding.java
import java.util.Map;
import org.springframework.boot.context.properties.bind.Bindable;
import org.springframework.boot.context.properties.bind.Binder;
import org.springframework.boot.context.properties.source.ConfigurationPropertySources;
import org.springframework.boot.context.properties.source.MapConfigurationPropertySource;
import org.springframework.core.env.SystemEnvironmentPropertySource;

public class RelaxedBinding {
    public static class Person {
        private String firstName;
        public String getFirstName() { return firstName; }
        public void setFirstName(String firstName) { this.firstName = firstName; }
    }

    static void bind(String label, Binder binder) {
        var bound = binder.bind("my.main-project.person", Bindable.of(Person.class));
        System.out.println(label + " -> " + bound.map(Person::getFirstName).orElse("unbound"));
    }

    public static void main(String[] args) {
        var spellings = Map.of("kebab case", "first-name", "camel case", "firstName", "underscore", "first_name");
        for (var spelling : new java.util.TreeMap<>(spellings).entrySet()) {
            var source = new MapConfigurationPropertySource(Map.of("my.main-project.person." + spelling.getValue(), "Rod"));
            bind(spelling.getKey(), new Binder(source));
        }
        var env = new SystemEnvironmentPropertySource("systemEnvironment", Map.of("MY_MAINPROJECT_PERSON_FIRSTNAME", "Rod"));
        bind("environment variable", new Binder(ConfigurationPropertySources.from(env)));
    }
}
```

The program prints `Rod` for each of the four spellings, in the order `camel case`, `kebab case`, `underscore` and `environment variable`: `firstName`, `first-name`, `first_name` and `MY_MAINPROJECT_PERSON_FIRSTNAME` all bound to the `firstName` property of `Person`.

You can enable `@ConfigurationProperties` types class by class with `@EnableConfigurationProperties`, or enable configuration property scanning with `@ConfigurationPropertiesScan` (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.enabling-annotated-types`).

Classes that are not suitable for scanning, for example when you develop your own auto-configuration or want to enable them conditionally, are listed with `@EnableConfigurationProperties` (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.enabling-annotated-types`).

A single parameterized constructor implies that constructor binding is used, and to opt out the constructor must be annotated with `@Autowired` or made private (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.constructor-binding`).

You cannot use constructor binding with beans that are created by the regular Spring mechanisms, such as `@Component` beans, `@Bean` methods or beans loaded by `@Import` (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.constructor-binding`).

To use constructor binding the class must be compiled with `-parameters` (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.constructor-binding`).

Spring Boot attempts to validate `@ConfigurationProperties` classes whenever they are annotated with Spring's `@Validated` annotation (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.validation`).

To cascade validation to nested properties, the associated field must be annotated with `@Valid` (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.validation`).

The `@Value` annotation is a core container feature, and it does not provide the same features as type-safe configuration properties (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.vs-value-annotation`).

:::esquema{kind=tabla title="@ConfigurationProperties and @Value"}
| Feature | @ConfigurationProperties | @Value | Citation |
| --- | --- | --- | --- |
| Relaxed binding | Yes | Limited | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.vs-value-annotation` |
| Meta-data support | Yes | No | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.vs-value-annotation` |
| SpEL evaluation | No | Yes | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.vs-value-annotation` |
:::

If you do use `@Value`, the documentation recommends referring to property names in their canonical form, kebab-case using only lowercase letters (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.vs-value-annotation`).

Spring Boot uses a very particular `PropertySource` order, and later property sources can override the values defined in earlier ones (`spring-boot-features-external-config#page-title`).

Among the sources, config data such as `application.properties` files is considered first, then `random.*` properties, then OS environment variables, then Java System properties, then JNDI attributes (`spring-boot-features-external-config#page-title`).

Default properties, specified by setting `SpringApplication.setDefaultProperties(Map)`, are the first source in that order (`spring-boot-features-external-config#page-title`).

After `ServletContext` and `ServletConfig` init parameters and `SPRING_APPLICATION_JSON`, command line arguments are considered (`spring-boot-features-external-config#page-title`).

```java snippet=m05-l02/Precedence.java
import java.util.Map;
import org.springframework.boot.Banner;
import org.springframework.boot.WebApplicationType;
import org.springframework.boot.builder.SpringApplicationBuilder;
import org.springframework.context.annotation.Configuration;

public class Precedence {
    @Configuration
    static class Config {}

    static void run(String... args) {
        var context = new SpringApplicationBuilder(Config.class)
            .web(WebApplicationType.NONE)
            .bannerMode(Banner.Mode.OFF)
            .logStartupInfo(false)
            .properties(Map.of("acme.name", "default"))
            .run(args);
        System.out.println((args.length == 0 ? "no arguments" : "command line argument") + " -> " + context.getEnvironment().getProperty("acme.name"));
        context.close();
    }

    public static void main(String[] args) {
        run();
        System.setProperty("acme.name", "system");
        run();
        run("--acme.name=cli");
    }
}
```

The program prints `no arguments -> default`, then `no arguments -> system` once the system property `acme.name` is set, then `command line argument -> cli` for the argument `--acme.name=cli`: each later source overrode the earlier one.

Config data files are considered in this order: application properties inside your jar, profile-specific properties inside your jar, application properties outside your jar, profile-specific properties outside your jar (`spring-boot-features-external-config#page-title`).

If configuration files in both `.properties` and YAML format are in the same location, `.properties` takes precedence (`spring-boot-features-external-config#page-title`).

Spring Boot also attempts to load profile-specific files named `application-{profile}`, and they always override the non-specific ones (`spring-boot-features-external-config#features.external-config.files.profile-specific`).

If several profiles are specified, a last-wins strategy applies (`spring-boot-features-external-config#features.external-config.files.profile-specific`).

If no profiles are explicitly activated, properties from `application-default` are considered (`spring-boot-features-external-config#features.external-config.files.profile-specific`).

Spring Boot automatically finds and loads `application.properties` and `application.yaml` files from locations on the classpath and in the current directory when your application starts (`spring-boot-features-external-config#features.external-config.files`).

The list of default locations is ordered by precedence, with values from lower items overriding earlier ones (`spring-boot-features-external-config#features.external-config.files`).

You can switch to another file name than `application` by specifying a `spring.config.name` environment property (`spring-boot-features-external-config#features.external-config.files`).

The `spring.config.location` environment property accepts a comma-separated list of one or more locations to check (`spring-boot-features-external-config#features.external-config.files`).

Locations configured by using `spring.config.location` replace the default locations (`spring-boot-features-external-config#features.external-config.files`).

To add locations rather than replace the default ones, use `spring.config.additional-location`; properties loaded from additional locations can override those in the default locations (`spring-boot-features-external-config#features.external-config.files`).

The `spring.config.name`, `spring.config.location` and `spring.config.additional-location` properties are used very early to determine which files have to be loaded (`spring-boot-features-external-config#features.external-config.files`).

They must be defined as an environment property, typically an OS environment variable, a system property or a command-line argument (`spring-boot-features-external-config#features.external-config.files`).

Use the prefix `optional:` if the locations are optional and you do not mind if they do not exist (`spring-boot-features-external-config#features.external-config.files`).

## Writing an auto-configuration and a starter
<!-- bullets: 5.2.c -->

To write an auto-configuration, you put its class name in a file inside the jar and guard the class with conditions, so that users can override its beans. A starter packages it, either as one module or as an auto-configuration module plus a starter module that brings in the dependencies. Tests build a small context for each combination of user configuration and conditions.

The imports file should list your configuration classes, with one class name per line (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

You can add comments to the imports file using the `#` character (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

If an auto-configuration class is not a top-level class, its class name should use `$` to separate it from its containing class (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

```java snippet=m05-l02/ImportsFile.java
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Files;
import java.nio.file.Path;
import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.context.annotation.ImportCandidates;

public class ImportsFile {
    public static void main(String[] args) throws Exception {
        Path root = Files.createTempDirectory("imports");
        Path file = root.resolve("META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports");
        Files.createDirectories(file.getParent());
        Files.writeString(file, "# first\ncom.acme.FirstAutoConfiguration\ncom.acme.Outer$InnerAutoConfiguration\n");
        try (var loader = new URLClassLoader(new URL[] {root.toUri().toURL()}, null)) {
            var candidates = ImportCandidates.load(AutoConfiguration.class, loader).getCandidates();
            System.out.println(candidates.size() + " candidates");
            System.out.println("comment listed: " + candidates.contains("# first"));
            System.out.println("nested name kept: " + candidates.contains("com.acme.Outer$InnerAutoConfiguration"));
        }
    }
}
```

The program prints `2 candidates`, `comment listed: false` and `nested name kept: true` for a file that holds a `# first` comment line, `com.acme.FirstAutoConfiguration` and `com.acme.Outer$InnerAutoConfiguration`: the comment is not a candidate, and the nested class name keeps its `$`.

To deprecate an auto-configuration class and offer an alternative, you create a `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.replacements` file indicating the link between the old class and the new one (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates.deprecating`).

The `AutoConfiguration.imports` file should also be updated to reference only the replacement class (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates.deprecating`).

Auto-configurations should be defined in a specific package space and must never be the target of component scanning (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

Auto-configuration classes should not enable component scanning to find additional components, and specific `@Import` annotations should be used instead (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

You almost always want to include one or more `@Conditional` annotations on your auto-configuration class (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations`).

`@ConditionalOnMissingBean` is a common example used to allow developers to override auto-configuration if they are not happy with your defaults (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations`).

`@ConditionalOnClass` and `@ConditionalOnMissingClass` let `@Configuration` classes be included based on the presence or absence of specific classes (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.class-conditions`).

Because annotation metadata is parsed by using ASM, you can use the `value` attribute to refer to the real class, even though that class might not appear on the running application classpath (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.class-conditions`).

This does not apply the same way to `@Bean` methods, because before the condition on the method applies, the JVM will have loaded the return type and potentially processed method references that fail if the class is not present (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.class-conditions`).

To handle this scenario, a separate `@Configuration` class can be used to isolate the condition (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.class-conditions`).

If you use `@ConditionalOnClass` or `@ConditionalOnMissingClass` as part of a meta-annotation, you must use `name`, because referring to the class is not handled in that case (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.class-conditions`).

`@ConditionalOnProperty` lets configuration be included based on a Spring `Environment` property, and by default any property that exists and is not equal to `false` is matched (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.property-conditions`).

If multiple names are given in the `name` attribute, all of the properties have to pass the test for the condition to match (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations.property-conditions`).

```java snippet=m05-l02/PropertyCondition.java
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class PropertyCondition {
    @Configuration
    static class Config {
        @Bean @ConditionalOnProperty(prefix = "acme", name = "feature") String feature() { return "on"; }
    }

    static void run(String value) {
        try (var context = new AnnotationConfigApplicationContext()) {
            if (value != null) System.setProperty("acme.feature", value);
            context.register(Config.class);
            context.refresh();
            System.out.println(value + " -> " + (context.getBeansOfType(String.class).isEmpty() ? "off" : "on"));
        } finally {
            System.clearProperty("acme.feature");
        }
    }

    public static void main(String[] args) {
        run(null);
        run("false");
        run("true");
        run("0");
    }
}
```

The program prints `null -> off` and `false -> off`, then `true -> on` and `0 -> on`: with no `havingValue`, the bean was registered for a property set to any value other than `false`, and not for an absent one.

Spring Boot includes `@Conditional` annotations in six groups: class, bean, property, resource, web application and SpEL expression conditions (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations`).

If you only have one module that combines the auto-configuration and the starter, you name it after the starter, such as `acme-spring-boot-starter` (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter.naming`).

If you provide configuration keys, you use a unique namespace for them, and you do not include your keys in the namespaces that Spring Boot uses, such as `server`, `management` and `spring` (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter.configuration-keys`).

If you use the same namespace, Spring Boot may modify it in the future in ways that break your modules (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter.configuration-keys`).

You should mark the dependencies to the library as optional so that you can include the autoconfigure module in your projects more easily (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter.autoconfigure-module`).

Spring Boot uses an annotation processor to collect the conditions on auto-configurations in the `META-INF/spring-autoconfigure-metadata.properties` file, which, if present, is used to eagerly filter auto-configurations that do not match, improving startup time (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter.autoconfigure-module`).

The starter is really an empty jar whose only purpose is to provide the necessary dependencies to work with the library (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter.starter-module`).

A starter must reference the core Spring Boot starter, `spring-boot-starter`, directly or indirectly (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter.starter-module`).

A typical Spring Boot starter contains code to auto-configure and customize the infrastructure of a given technology (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

To make the starter easily extensible, a number of configuration keys in a dedicated namespace can be exposed to the environment (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

A starter can have one module with the auto-configuration code and any API to use the feature, and a second module that provides a dependency to the other starters required, to the first module, and potentially additional dependencies (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

This separation in two modules is in no way necessary (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

If the technology has several flavors, options or optional features, it is better to separate the auto-configuration, as you can clearly express the fact that some features are optional (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

If the auto-configuration is relatively straightforward and does not have optional features, merging the two modules in the starter is definitely an option (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

A separate test-scoped starter can offer test-specific auto-configurations, for example to replace external dependencies with in-memory alternatives (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

An auto-configuration can be affected by many factors: user configuration, condition evaluation and others (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

Each test should create a well defined `ApplicationContext` that represents a combination of those customizations (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

`ApplicationContextRunner` does not work when running the tests in a native image (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

If multiple auto-configurations have to be defined, there is no need to order their declarations, as they are invoked in the exact same order as when running the application (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

The runner can also display the `ConditionEvaluationReport`, which can be printed at `INFO` or `DEBUG` level (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

## Key points

- Auto-configuration is opt-in through `@EnableAutoConfiguration` or `@SpringBootApplication`, added once, on the primary `@Configuration` class.
- Auto-configuration classes are `@Configuration` classes loaded only by being named in the `AutoConfiguration.imports` file, never by component scanning.
- Ordering auto-configurations affects only the order in which beans are defined; bean creation order follows dependencies and `@DependsOn`.
- The `ConditionEvaluationReport` shows the auto-configuration decisions: with `DEBUG` logging, `--debug`, or the `conditions` endpoint.
- Your own configuration makes auto-configuration back off: a bean condition such as `@ConditionalOnMissingBean` is evaluated against what has been processed so far.
- Specific auto-configuration classes are disabled with `exclude`, `excludeName` or `spring.autoconfigure.exclude`.
- All official starters follow the naming pattern `spring-boot-starter-*`; a third-party starter typically starts with the name of the project.
- Kebab case is the recommended format for property names in `.properties` and YAML files, and the prefix of `@ConfigurationProperties` must be in kebab case.
- `@ConfigurationProperties` binds the spellings `first-name`, `firstName`, `first_name` and `MY_MAINPROJECT_PERSON_FIRSTNAME` of one property.
- Later property sources override earlier ones; command line arguments come after OS environment variables and Java System properties.
- `spring.config.location` replaces the default locations, and `spring.config.additional-location` adds to them.
- `@ConditionalOnProperty` matches by default any property that exists and is not equal to `false`.
- `@ConditionalOnClass` on a `@Bean` method can fail when the class is absent, so it is isolated in a separate `@Configuration` class.
- Splitting a starter into an auto-configuration module and a starter module is not necessary.
- Each auto-configuration test should create a well defined `ApplicationContext`.

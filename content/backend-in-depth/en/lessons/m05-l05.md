# Web layer

## The request path through Spring MVC
<!-- bullets: 5.5.a -->

In the Servlet API, you can add a `jakarta.servlet.Filter` to apply interception-style logic before and after the rest of the processing chain of filters and the target Servlet (`spring-fw-webmvc-filters#page-title`).

`OncePerRequestFilter` extends `GenericFilterBean` and supports a single invocation at the start of a request, during the REQUEST dispatch phase, and ignores further handling via FORWARD dispatches (`spring-fw-webmvc-filters#page-title`).

In a Spring Boot application, you can declare `Filter` instances as beans and Boot will have them configured (`spring-fw-webmvc-filters#page-title`).

Spring MVC is designed around the front controller pattern, where a central Servlet, the `DispatcherServlet`, provides a shared algorithm for request processing, while actual work is performed by configurable delegate components (`spring-fw-webmvc-dispatcher#page-title`).

The `DispatcherServlet` delegates to special beans to process requests and render the appropriate responses (`spring-fw-webmvc-dispatcher-special-beans#page-title`).

A `HandlerMapping` maps a request to a handler along with a list of interceptors for pre- and post-processing (`spring-fw-webmvc-dispatcher-special-beans#page-title`).

The two main `HandlerMapping` implementations are `RequestMappingHandlerMapping`, which supports `@RequestMapping` annotated methods, and `SimpleUrlHandlerMapping`, which maintains explicit registrations of URI path patterns to handlers (`spring-fw-webmvc-dispatcher-special-beans#page-title`).

A `HandlerAdapter` helps the `DispatcherServlet` to invoke a handler mapped to a request, regardless of how the handler is actually invoked (`spring-fw-webmvc-dispatcher-special-beans#page-title`).

If a handler is found, the execution chain associated with the handler (preprocessors, postprocessors, and controllers) is run to prepare a model for rendering (`spring-fw-webmvc-dispatcher-sequence#page-title`).

The `HandlerExceptionResolver` beans declared in the `WebApplicationContext` are used to resolve exceptions thrown during request processing (`spring-fw-webmvc-dispatcher-sequence#page-title`).

Interceptors are not ideally suited as a security layer due to the potential for a mismatch with annotated controller path matching (`spring-fw-webmvc-handlermapping-interceptor#page-title`).

`java.util.Optional` is supported as a method argument in combination with annotations that have a `required` attribute, such as `@RequestParam` and `@RequestHeader`, and is equivalent to `required=false` (`spring-fw-webmvc-controller-ann-arguments#page-title`).

Reactive types are not supported for any controller method arguments (`spring-fw-webmvc-controller-ann-arguments#page-title`).

A `jakarta.servlet.http.HttpSession` argument enforces the presence of a session (`spring-fw-webmvc-controller-ann-arguments#page-title`).

Spring MVC uses the `HttpMessageConverter` interface to convert HTTP requests and responses (`spring-boot-web-servlet#web.servlet.spring-mvc.message-converters`).

Any `HttpMessageConverter` bean that is present in the context is added to the list of converters (`spring-boot-web-servlet#web.servlet.spring-mvc.message-converters`).

By default, Spring MVC encodes strings in UTF-8 (`spring-boot-web-servlet#web.servlet.spring-mvc.message-converters`).

You can configure the `HttpMessageConverter` instances to use by overriding `configureMessageConverters()` (`spring-fw-webmvc-message-converters#page-title`).

## Validation, controller advice and the error model
<!-- bullets: 5.5.b -->

To be eligible for Spring-driven method validation, target classes need to be annotated with Spring’s `@Validated` annotation (`spring-fw-validation-beanvalidation#validation-beanvalidation-spring-method`).

Method validation relies on AOP proxies around the target classes, either JDK dynamic proxies for methods on interfaces or CGLIB proxies (`spring-fw-validation-beanvalidation#validation-beanvalidation-spring-method`).

Spring MVC and WebFlux have built-in support for the same underlying method validation but without the need for AOP (`spring-fw-validation-beanvalidation#validation-beanvalidation-spring-method`).

`@ExceptionHandler`, `@InitBinder` and `@ModelAttribute` methods apply only to the `@Controller` class, or class hierarchy, in which they are declared (`spring-fw-webmvc-controller-advice#page-title`).

If they are declared in an `@ControllerAdvice` or `@RestControllerAdvice` class, they apply to any controller (`spring-fw-webmvc-controller-advice#page-title`).

`@RestControllerAdvice` is a shortcut annotation that combines `@ControllerAdvice` with `@ResponseBody` (`spring-fw-webmvc-controller-advice#page-title`).

By default, both `@ControllerAdvice` and `@RestControllerAdvice` apply to any controller, including `@Controller` and `@RestController` (`spring-fw-webmvc-controller-advice#page-title`).

Global `@ExceptionHandler` methods, from an `@ControllerAdvice`, are applied after local ones, from the `@Controller` (`spring-fw-webmvc-controller-advice#page-title`).

Global `@ModelAttribute` and `@InitBinder` methods are applied before local ones (`spring-fw-webmvc-controller-advice#page-title`).

When multiple exception methods match, a root exception match is generally preferred to a cause exception match (`spring-fw-webmvc-exceptionhandler#mvc-ann-exceptionhandler-exc`).

`ExceptionDepthComparator` sorts matching exceptions based on their depth from the thrown exception type (`spring-fw-webmvc-exceptionhandler#mvc-ann-exceptionhandler-exc`).

Since Spring Framework 5.3, an exception handler can match at arbitrary cause levels, whereas previously only an immediate cause was considered (`spring-fw-webmvc-exceptionhandler#mvc-ann-exceptionhandler-exc`).

You can return `ProblemDetail` or `ErrorResponse` from any `@ExceptionHandler` or from any `@RequestMapping` method to render an RFC 9457 response (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-render`).

The `status` property of `ProblemDetail` determines the HTTP status (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-render`).

The `instance` property of `ProblemDetail` is set from the current URL path, if not already set (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-render`).

To enable RFC 9457 responses for Spring MVC exceptions and for any `ErrorResponseException`, extend `ResponseEntityExceptionHandler` and declare it as an `@ControllerAdvice` in Spring configuration (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-render`).

By default, Spring Boot provides an `/error` mapping that handles all errors in a sensible way, and it is registered as a “global” error page in the servlet container (`spring-boot-web-servlet#web.servlet.spring-mvc.error-handling`).

Spring Boot enables RFC 9457 Problem Details support by setting `spring.mvc.problemdetails.enabled` to `true` (`spring-boot-web-servlet#web.servlet.spring-mvc.error-handling`).

To replace the default error behavior completely, you can implement `ErrorController` and register a bean definition of that type (`spring-boot-web-servlet#web.servlet.spring-mvc.error-handling`).

## Spring MVC, WebFlux and virtual threads
<!-- bullets: 5.5.c -->

In Spring MVC, and servlet applications in general, it is assumed that applications can block the current thread, for example for remote calls (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

For this reason, servlet containers use a large thread pool to absorb potential blocking during request handling (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

In Spring WebFlux, and non-blocking servers in general, it is assumed that applications do not block (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

Non-blocking servers use a small, fixed-size thread pool, called event loop workers, to handle requests (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

Never blocking the current thread and relying on callbacks means that you do not need extra threads, as there are no blocking calls to absorb (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

Reactive and non-blocking generally do not make applications run faster (`spring-fw-webflux-new-framework#webflux-performance`).

It requires more work to do things the non-blocking way, and that can slightly increase the required processing time (`spring-fw-webflux-new-framework#webflux-performance`).

The key expected benefit of reactive and non-blocking is the ability to scale with a small, fixed number of threads and less memory (`spring-fw-webflux-new-framework#webflux-performance`).

To observe those benefits, you need to have some latency, including a mix of slow and unpredictable network I/O (`spring-fw-webflux-new-framework#webflux-performance`).

If you have a Spring MVC application that works fine, there is no need to change (`spring-fw-webflux-new-framework#webflux-framework-choice`).

If you have blocking persistence APIs (JPA, JDBC) or networking APIs to use, Spring MVC is the best choice for common architectures at least (`spring-fw-webflux-new-framework#webflux-framework-choice`).

Reactive Streams is a small spec, also adopted in Java 9, that defines the interaction between asynchronous components with back pressure (`spring-fw-webflux-new-framework#webflux-why-reactive`).

If a publisher cannot slow down, it has to decide whether to buffer, drop, or fail (`spring-fw-webflux-new-framework#webflux-why-reactive`).

Virtual threads are lightweight threads that dramatically reduce the effort of writing, maintaining, and observing high-throughput concurrent applications (`jep-444#Summary`).

In the absence of an `Executor` bean in the context, Spring Boot auto-configures an `AsyncTaskExecutor` (`spring-boot-features-task-execution-and-scheduling#page-title`).

When virtual threads are enabled, using Java 21+ and `spring.threads.virtual.enabled` set to `true`, the auto-configured executor is a `SimpleAsyncTaskExecutor` that uses virtual threads (`spring-boot-features-task-execution-and-scheduling#page-title`).

Otherwise, the auto-configured executor is a `ThreadPoolTaskExecutor` with sensible defaults (`spring-boot-features-task-execution-and-scheduling#page-title`).

The `SimpleAsyncTaskScheduler` that uses virtual threads will ignore any pooling related properties (`spring-boot-features-task-execution-and-scheduling#page-title`).

## HTTP clients
<!-- bullets: 5.5.d -->

If you are not using Spring WebFlux or Project Reactor in your application, Spring Boot recommends that you use `RestClient` to call remote REST services (`spring-boot-io-rest-client#io.rest-client.restclient`).

Spring Boot creates and pre-configures a prototype `RestClient.Builder` bean (`spring-boot-io-rest-client#io.rest-client.restclient`).

Once created, a `RestClient` is safe to use in multiple threads (`spring-fw-integration-rest-clients#_create_a_restclient`).

To execute the HTTP request, `RestClient` uses a client HTTP library (`spring-fw-integration-rest-clients#rest-request-factories`).

If no request factory is specified when the `RestClient` was built, it will use the Apache or Jetty `HttpClient` if they are available on the classpath (`spring-fw-integration-rest-clients#rest-request-factories`).

Otherwise, if the `java.net.http` module is loaded, the `RestClient` uses Java’s `HttpClient` (`spring-fw-integration-rest-clients#rest-request-factories`).

Finally, the `RestClient` resorts to the simple default (`spring-fw-integration-rest-clients#rest-request-factories`).

The `SimpleClientHttpRequestFactory` may raise an exception when accessing the status of a response that represents an error, for example `401` (`spring-fw-integration-rest-clients#rest-request-factories`).

`WebClient` is a non-blocking, reactive client to perform HTTP requests (`spring-fw-integration-rest-clients#rest-webclient`).

Regardless of the underlying technology being used, all HTTP clients have common settings that can be configured (`spring-boot-io-rest-client#io.rest-client.global-configuration`).

When `spring.http.clients.cookie-handling` is not set, the default cookie handling of the underlying HTTP client library is used (`spring-boot-io-rest-client#io.rest-client.global-configuration`).

You can use the `spring.http.clients.imperative.factory` property to pick a specific factory if the auto-detected HTTP client does not meet your needs (`spring-boot-io-rest-client#io.rest-client.clienthttprequestfactory.configuration`).

You can define an HTTP Service as a Java interface with `@HttpExchange` methods, and use `HttpServiceProxyFactory` to create a client proxy from it for remote access over HTTP via `RestClient`, `WebClient`, or `RestTemplate` (`spring-fw-integration-rest-clients#rest-http-service-client`).

On the server side, an `@Controller` class can implement the same interface to handle requests with `@HttpExchange` controller methods (`spring-fw-integration-rest-clients#rest-http-service-client`).

HTTP Service interfaces define a service contract by using methods annotated with `@HttpExchange`, or more typically the method specific variants such as `@GetExchange` and `@PostExchange` (`spring-boot-io-rest-client#io.rest-client.httpservice`).

Configuration properties for HTTP Services can be specified under `spring.http.serviceclient.<group-name>` (`spring-boot-io-rest-client#io.rest-client.httpservice.properties`).

## Key points

- The `DispatcherServlet` is the front controller of Spring MVC and delegates to special beans such as `HandlerMapping` and `HandlerAdapter`.
- Interceptors are not ideally suited as a security layer.
- Spring MVC uses `HttpMessageConverter` to convert HTTP requests and responses, and strings are encoded in UTF-8 by default.
- Global `@ExceptionHandler` methods from an `@ControllerAdvice` are applied after local ones, while global `@ModelAttribute` and `@InitBinder` methods are applied before local ones.
- A `ProblemDetail` returned from an exception handler renders an RFC 9457 response.
- Servlet containers use a large thread pool because Spring MVC assumes blocking, and non-blocking servers use a small, fixed-size pool.
- Reactive and non-blocking generally do not make applications run faster; the key expected benefit is scaling with a small, fixed number of threads and less memory.
- With virtual threads enabled, Spring Boot auto-configures a `SimpleAsyncTaskExecutor` that uses virtual threads.
- A `RestClient` without a request factory uses the Apache or Jetty `HttpClient`, then Java’s `HttpClient`, then the simple default.
- An HTTP Service is a Java interface with `@HttpExchange` methods, turned into a client proxy by `HttpServiceProxyFactory`.

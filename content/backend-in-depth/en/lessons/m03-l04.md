# Profiling, benchmarking and measuring performance

## Flight Recorder and Mission Control
<!-- bullets: 3.4.a -->

Flight Recorder (JFR) is a profiling and event collection framework built into the JDK (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

Flight Recorder records data about JVM events as they occur, with a timestamp (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

The data is recorded as time-stamped data points called events (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

Flight recordings can be started when the application is started or while the application is running (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

:::esquema{kind=tabla title="Flight Recorder event categories"}
| Category | What it is | Source |
|---|---|---|
| Duration events | Occur at a particular duration with specific start time and stop time | `jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6` |
| Instant events | Occur instantly and get logged immediately, for example when a thread gets blocked | `jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6` |
| Sample events | Occur at regular intervals to check the overall health of the system | `jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6` |
| Custom events | User defined events created using JMC or APIs | `jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6` |
:::

The `default.jfc` template collects a predefined set of data with low overhead (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

The `profile.jfc` template provides more data than `default.jfc`, but with overhead and impact on performance (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

A time fixed recording is also known as a profiling recording that runs for a set amount of time, and then stops (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

A continuous recording is a recording that is always on and saves, for example, the last six hours of data (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

When the global buffer fills up, the oldest data is discarded (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

The data currently in the buffer is written to the specified file whenever you request a dump, or if the dump is triggered by a rule (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

A continuous recording with the default template has low overhead and gathers a lot of useful data (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

The default template of a continuous recording doesn't gather heap statistics or allocation profiling (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

For continuous recordings, you can specify the maximum size or maximum age of events you want to save (`jdk-troubleshoot-tools#JSTGD-GUID-88CC453C-0CED-45D6-9E93-28A03F3752F2`).

By default, synchronization events above 10 ms are collected (`jdk-troubleshoot-tools#JSTGD-GUID-88CC453C-0CED-45D6-9E93-28A03F3752F2`).

The overhead for recording a standard time fixed recording using the default settings is less than two percent for most applications (`jdk-troubleshoot-jfr#JSTGD-GUID-85F8E796-5FEC-451F-885D-2A4518A5FE68`).

Running with a standard continuous recording generally has no measurable performance effect (`jdk-troubleshoot-jfr#JSTGD-GUID-85F8E796-5FEC-451F-885D-2A4518A5FE68`).

Using Heap Statistics, which is disabled by default, can cause significant performance overhead (`jdk-troubleshoot-jfr#JSTGD-GUID-85F8E796-5FEC-451F-885D-2A4518A5FE68`).

Enabling Heap Statistics triggers an old garbage collection at the beginning and at the end of the test run (`jdk-troubleshoot-jfr#JSTGD-GUID-85F8E796-5FEC-451F-885D-2A4518A5FE68`).

The overhead of Flight Recorder differs depending on the application (`jdk-troubleshoot-jfr#JSTGD-GUID-85F8E796-5FEC-451F-885D-2A4518A5FE68`).

An event has a time stamp, duration and usually an application-specific payload (`jdk-jfr-api-package#package-jdk-jfr`).

To define a Flight Recorder event, extend `Event` and add fields that match the data types of the payload (`jdk-jfr-api-package#package-jdk-jfr`).

Flight Recorder can be controlled locally by using the `jcmd` command line tool or remotely by using the `FlightRecorderMXBean` interface (`jdk-jfr-api-package#package-jdk-jfr`).

The `threshold` setting specifies the duration below which an event is not recorded (`jdk-jfr-api-package#package-jdk-jfr`).

```java snippet=m03-l04/JfrEvents.java
import java.nio.file.Files;
import java.nio.file.Path;
import java.time.Duration;
import jdk.jfr.Event;
import jdk.jfr.Name;
import jdk.jfr.Recording;
import jdk.jfr.consumer.RecordingFile;

public class JfrEvents {
    @Name("demo.Order")
    static class OrderEvent extends Event {
        int orderId;
    }

    static long countRecorded(Duration threshold) throws Exception {
        Path file = Files.createTempFile("orders", ".jfr");
        try (Recording recording = new Recording()) {
            recording.enable("demo.Order").withThreshold(threshold);
            recording.start();
            for (int id = 1; id <= 3; id++) {
                OrderEvent event = new OrderEvent();
                event.begin();
                event.orderId = id;
                event.commit();
            }
            recording.stop();
            recording.dump(file);
        }
        long count = RecordingFile.readAllEvents(file).stream()
            .filter(event -> event.getEventType().getName().equals("demo.Order"))
            .count();
        Files.delete(file);
        return count;
    }

    public static void main(String[] args) throws Exception {
        System.out.println("threshold 0 ns: " + countRecorded(Duration.ZERO) + " events");
        System.out.println("threshold 1 h: " + countRecorded(Duration.ofHours(1)) + " events");
    }
}
```

The snippet commits three `OrderEvent` instances and prints `threshold 0 ns: 3 events` when the threshold is zero.

With a threshold of one hour the same three events are not recorded, and the snippet prints `threshold 1 h: 0 events`.

The `jfr` command filters, summarizes and outputs flight recording files into human readable format (`jdk-tool-jfr#description`).

Flight recording files are created and saved as binary formatted files (`jdk-tool-jfr#description`).

JDK Mission Control (JMC) is a production-time profiling and diagnostics tool (`jdk-troubleshoot-tools#JSTGD-GUID-47A98C88-95B1-4842-9B0D-67BBDB266214`).

JMC is not part of the regular JDK installation (`jdk-troubleshoot-tools#JSTGD-GUID-47A98C88-95B1-4842-9B0D-67BBDB266214`).

JMC is an advanced set of tools for managing, monitoring, profiling, and troubleshooting Java applications (`jmc-docs#jdk-mission-control`).

Flight Recorder together with JMC creates a toolchain to continuously collect low-level and detailed runtime information enabling after-the-fact incident analysis (`jdk-troubleshoot-tools#JSTGD-GUID-D38849B6-61C7-4ED6-A395-EA4BC32A9FD6`).

## Profiling with async-profiler
<!-- bullets: 3.4.b -->

Async-profiler is a low overhead sampling profiler for Java that does not suffer from the Safepoint bias problem (`async-profiler-readme#async-profiler`).

Async-profiler features a HotSpot-specific API to collect stack traces and to track memory allocations (`async-profiler-readme#async-profiler`).

The profiler works with OpenJDK and other Java runtimes based on the HotSpot JVM (`async-profiler-readme#async-profiler`).

Unlike traditional Java profilers, async-profiler monitors non-Java threads, such as GC and JIT compiler threads, and shows native and kernel frames in stack traces (`async-profiler-readme#async-profiler`).

:::esquema{kind=tabla title="What async-profiler can profile"}
| Target | Source |
|---|---|
| CPU time | `async-profiler-readme#async-profiler` |
| Allocations in Java Heap | `async-profiler-readme#async-profiler` |
| Native memory allocations and leaks | `async-profiler-readme#async-profiler` |
| Contended locks | `async-profiler-readme#async-profiler` |
| Hardware and software performance counters like cache misses, page faults and context switches | `async-profiler-readme#async-profiler` |
:::

In a typical use case, profiling a Java application is just a matter of running `asprof` with the PID of a running Java process (`async-profiler-readme#quick-start`).

```bash
asprof -d 30 -f flamegraph.html <PID>
```

This command runs the profiler for 30 seconds and saves results to `flamegraph.html` as an interactive Flame Graph that can be viewed in a browser (`async-profiler-readme#quick-start`).

## Microbenchmarks with JMH
<!-- bullets: 3.4.c -->

Users annotate methods with `@Benchmark`, and then JMH produces the generated code to run this particular benchmark as reliably as possible (`jmh-sample-helloworld#_R_7lcpala9lik5_`).

Method names are non-essential for JMH, and it only matters that the methods are marked with `@Benchmark` (`jmh-sample-helloworld#_R_7lcpala9lik5_`).

A benchmark that measures nothing shows the overheads the infrastructure bears on the code you measure in the method (`jmh-sample-helloworld#_R_7lcpala9lik5_`).

A `baseline` measurement gives something to compare against the infrastructure overheads (`jmh-sample-helloworld#_R_7lcpala9lik5_`).

Dead-Code Elimination (DCE) happens because compilers are smart enough to deduce some computations are redundant and eliminate them completely (`jmh-sample-deadcode#_R_7lcpala9lik5_`).

If the eliminated part was the benchmarked code, the benchmark is in trouble (`jmh-sample-deadcode#_R_7lcpala9lik5_`).

Returning the result of the computation asks JMH to deal with the result to limit dead-code elimination (`jmh-sample-deadcode#_R_7lcpala9lik5_`).

Returned results are implicitly consumed by `Blackhole`s (`jmh-sample-deadcode#_R_7lcpala9lik5_`).

In `measureWrong()` the result is not used and the entire computation is optimized away (`jmh-sample-deadcode#_R_7lcpala9lik5_`).

If a benchmark is only producing a single result, it is more readable to use the implicit return than an explicit `Blackhole` (`jmh-sample-blackhole#_R_7lcpala9lik5_`).

Option A for a benchmark with multiple results is to merge multiple results into one and return it (`jmh-sample-blackhole#_R_7lcpala9lik5_`).

Merging results is OK when the computation is relatively heavyweight, and merging the results does not offset the results much (`jmh-sample-blackhole#_R_7lcpala9lik5_`).

Option B is to use explicit `Blackhole` objects and sink the values there (`jmh-sample-blackhole#_R_7lcpala9lik5_`).

`Blackhole` is just another `@State` object, bundled with JMH (`jmh-sample-blackhole#_R_7lcpala9lik5_`).

In the Blackholes sample, `measureWrong()` runs on par with `baseline()` because the redundant computation is optimized out (`jmh-sample-blackhole#_R_7lcpala9lik5_`).

Constant-folding is the flip side of dead-code elimination (`jmh-sample-constantfold#_R_7lcpala9lik5_`).

If the JVM realizes the result of the computation is the same no matter what, it can cleverly optimize it (`jmh-sample-constantfold#_R_7lcpala9lik5_`).

Constant folding can move the computation outside of the internal JMH loop (`jmh-sample-constantfold#_R_7lcpala9lik5_`).

Constant folding can be prevented by always reading the inputs from non-final instance fields of `@State` objects, computing the result based on those values, and following the rules to prevent DCE (`jmh-sample-constantfold#_R_7lcpala9lik5_`).

A computation whose source is predictable is foldable, and so a measurement based on it is wrong (`jmh-sample-constantfold#_R_7lcpala9lik5_`).

JVMs are notoriously good at profile-guided optimizations (`jmh-sample-forking#_R_7lcpala9lik5_`).

Different tests can mix their profiles together, and then render the "uniformly bad" code for every test (`jmh-sample-forking#_R_7lcpala9lik5_`).

Forking each test, that is running it in a separate process, can help to evade the mixing of profiles (`jmh-sample-forking#_R_7lcpala9lik5_`).

JMH will fork the tests by default (`jmh-sample-forking#_R_7lcpala9lik5_`).

`@Fork(0)` helps to run in the same JVM (`jmh-sample-forking#_R_7lcpala9lik5_`).

:::esquema{kind=tabla title="JMH pitfalls and what the samples say against them"}
| Pitfall | Remedy in the JMH samples | Source |
|---|---|---|
| Dead-code elimination | Return the result of the computation, or sink values into a `Blackhole` | `jmh-sample-deadcode#_R_7lcpala9lik5_`; `jmh-sample-blackhole#_R_7lcpala9lik5_` |
| Constant folding | Read inputs from non-final instance fields of `@State` objects | `jmh-sample-constantfold#_R_7lcpala9lik5_` |
| Mixed profiles across tests | Fork each test into a separate process | `jmh-sample-forking#_R_7lcpala9lik5_` |
:::

Against dead-code elimination, return the result of the computation or sink values into a Blackhole (`jmh-sample-deadcode#_R_7lcpala9lik5_`; `jmh-sample-blackhole#_R_7lcpala9lik5_`).

## Measuring latency and coordinated omission
<!-- bullets: 3.4.d -->

HdrHistogram supports the recording and analyzing of sampled data value counts across a configurable integer value range with configurable value precision within the range (`hdrhistogram-readme#untitled`).

Value precision is expressed as the number of significant digits in the value recording (`hdrhistogram-readme#untitled`).

HdrHistogram is designed for recording histograms of value measurements in latency and performance sensitive applications (`hdrhistogram-readme#untitled`).

A Histogram's memory footprint is constant, with no allocation operations involved in recording data values or in iterating through them (`hdrhistogram-readme#untitled`).

The memory footprint is fixed regardless of the number of data value samples recorded, and depends solely on the dynamic range and precision chosen (`hdrhistogram-readme#untitled`).

The amount of work involved in recording a sample is constant, so that no iteration or searching is ever involved in recording data values (`hdrhistogram-readme#untitled`).

Analysis of recorded values can include computing, examining, and reporting of distribution by percentiles, linear or logarithmic value buckets, mean and standard deviation (`hdrhistogram-readme#untitled`).

Kept in high resolution, the recorded data allows accurate post-recording analysis, whether calculating or plotting arbitrary percentiles or deriving mean and standard deviation values (`hdrhistogram-readme#untitled`).

wrk's model computes the latency for a given request as the time from the sending of the first byte of the request to the time the complete response was received (`wrk2-readme#acknowledgements`).

wrk's model exhibits a strong Coordinated Omission effect, through which most of the high latency artifacts exhibited by the measured server will be ignored (`wrk2-readme#acknowledgements`).

Since each connection only begins to send a request after receiving a response, high latency responses result in the load generator coordinating with the server to avoid measurement during high latency periods (`wrk2-readme#acknowledgements`).

HdrHistogram includes a simple way to compensate for Coordinated Omission when a known expected interval between measurements exists (`wrk2-readme#acknowledgements`).

Some completely asynchronous load generators can avoid Coordinated Omission by sending requests without waiting for previous responses to arrive (`wrk2-readme#acknowledgements`).

The asynchronous technique is normally only effective with non-blocking protocols or single-request-per-connection workloads (`wrk2-readme#acknowledgements`).

wrk2 measures response latency from the time the transmission should have occurred according to the constant throughput configured for the run (`wrk2-readme#acknowledgements`).

wrk2 is wrk modified to produce a constant throughput load, and accurate latency details to the high 9s (`wrk2-readme#wrk2`).

wrk2 takes a throughput argument, in total requests per second, via the `--rate` or `-R` parameters, with a default of 1000 (`wrk2-readme#wrk2`).

wrk2 replaces wrk's individual request sample buffers with HdrHistograms (`wrk2-readme#wrk2`).

In wrk2's constant-throughput implementation, measured latencies are only accurate to a +/- ~1 msec granularity, due to OS sleep time behavior (`wrk2-readme#wrk2`).

wrk2 reports its uncorrected latency histogram with the `--u_latency` flag (`wrk2-readme#acknowledgements`).

`recordValueWithExpectedInterval()` records a corrected histogram value, for scenarios where response times may exceed the expected interval between issuing requests (`hdrhistogram-readme#corrected-vs-raw-value-recording-calls`).

When a recorded value exceeds `expectedIntervalBetweenValueSamples`, the histogram data reflects additional values, linearly decreasing in steps of `expectedIntervalBetweenValueSamples`, down to the last value that would still be higher than it (`hdrhistogram-readme#corrected-vs-raw-value-recording-calls`).

In the README's example, the raw data histogram would show ~99.99% of results at 1 msec or below, which is obviously "not right" (`hdrhistogram-readme#corrected-vs-raw-value-recording-calls`).

In the README's example, the histogram corrected with an `expectedIntervalBetweenValueSamples` of 10 msec shows only ~50% of results at 1 msec or below (`hdrhistogram-readme#corrected-vs-raw-value-recording-calls`).

Data sets recorded with and without `expectedIntervalBetweenValueSamples` differ only if at least one value recorded with `recordValue` was greater than its associated `expectedIntervalBetweenValueSamples` (`hdrhistogram-readme#corrected-vs-raw-value-recording-calls`).

`copyCorrectedForCoordinatedOmission` is a post-correction method, as opposed to the at-recording correction method `recordValueWithExpectedInterval` (`hdrhistogram-javadoc#copyCorrectedForCoordinatedOmission-long-`).

The post-correction and the at-recording methods are mutually exclusive, and only one of the two should be used on a given data set to correct for the same coordinated omission issue (`hdrhistogram-javadoc#copyCorrectedForCoordinatedOmission-long-`).

In the README's example, response time samples are taken once every 10 msec (`hdrhistogram-readme#corrected-vs-raw-value-recording-calls`).

In the README's example, the system behaves perfectly for 100 seconds with 10,000 samples of 1 msec each, and then encounters a 100 sec pause during which only a single sample is recorded, with a 100 second value (`hdrhistogram-readme#corrected-vs-raw-value-recording-calls`).

```java snippet=m03-l04/CoordinatedOmission.java
import java.util.Locale;

public class CoordinatedOmission {
    public static void main(String[] args) {
        long intervalMs = 10;
        long goodSamples = 10_000;
        long pauseMs = 100_000;

        long rawSamples = goodSamples + 1;
        double rawPercentAtOneMs = 100.0 * goodSamples / rawSamples;
        System.out.println("raw samples=" + rawSamples);
        System.out.println(String.format(Locale.ROOT, "raw percent at or below 1 ms=%.2f", rawPercentAtOneMs));

        long addedSamples = 0;
        for (long value = pauseMs - intervalMs; value > intervalMs; value -= intervalMs) {
            addedSamples++;
        }
        long correctedSamples = rawSamples + addedSamples;
        double correctedPercentAtOneMs = 100.0 * goodSamples / correctedSamples;
        System.out.println("added samples=" + addedSamples);
        System.out.println("corrected samples=" + correctedSamples);
        System.out.println(String.format(Locale.ROOT, "corrected percent at or below 1 ms=%.2f", correctedPercentAtOneMs));
    }
}
```

The raw histogram holds 10,001 samples, and the snippet prints `raw percent at or below 1 ms=99.99`.

Following the correction rule from 99,990 msec down to 20 msec in steps of 10 msec adds 9,998 samples, and the snippet prints `added samples=9998`.

The corrected histogram holds 19,999 samples, and the snippet prints `corrected percent at or below 1 ms=50.00`.

## Method: hypothesis, measurement and test
<!-- bullets: 3.4.e -->

:::judgement{source="Google, Site Reliability Engineering, ch. 12" ref="sre-book-effective-troubleshooting#theory-Nbsviy"}
According to the Site Reliability Engineering book, the troubleshooting process can be thought of as an application of the hypothetico-deductive method: given a set of observations about a system and a theoretical basis for understanding system behavior, we iteratively hypothesize potential causes for the failure and try to test those hypotheses. The book offers two ways to test a hypothesis: compare the observed state of the system against the theories to find confirming or disconfirming evidence, or actively treat the system by changing it in a controlled way and observe the results.
:::

:::judgement{source="Google, Site Reliability Engineering, ch. 12" ref="sre-book-effective-troubleshooting#test-and-treat-EvsWceuj"}
According to the same chapter, an ideal test has mutually exclusive alternatives, so that it can rule one group of hypotheses in and rule another set out. It adds that active tests may have side effects that change future test results: turning on verbose logging might make a latency problem even worse and confuse the results. It advises taking clear notes of what ideas you had, which tests you ran, and the results you saw.
:::

## Key points

- Flight Recorder records time-stamped events; a continuous recording is always on and discards the oldest data when the global buffer fills.
- A standard time fixed recording with default settings costs less than two percent for most applications, and Heap Statistics, which is disabled by default, can cause significant overhead.
- The `threshold` setting of a Flight Recorder event is the duration below which the event is not recorded; the snippet records three events at a threshold of zero and none at one hour.
- JMC is a production-time profiling and diagnostics tool that is not part of the regular JDK installation.
- Async-profiler is a sampling profiler that does not suffer from the Safepoint bias problem and shows native and kernel frames in stack traces.
- JMH samples guard against dead-code elimination by returning results or using a `Blackhole`, against constant folding by reading inputs from non-final `@State` fields, and against mixed profiles by forking tests.
- JMH forks the tests by default.
- wrk's latency model exhibits Coordinated Omission; wrk2 measures from the time the transmission should have occurred under a constant throughput.
- An `HdrHistogram` `Histogram` has a fixed memory footprint and a constant cost to record a sample.
- In the README's example, correcting for an expected interval of 10 msec moves the share of results at 1 msec or below from about 99.99% to about 50%.

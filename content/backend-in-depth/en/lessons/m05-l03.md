# AOP and proxies

## Two kinds of proxy
<!-- bullets: 5.3.a -->

When advice applies to a Spring bean, callers do not receive the plain object. They receive a stand-in that runs the advice and then forwards the call to the real object. Spring builds that stand-in in one of two ways, and the way decides which methods it can advise.

Spring AOP is proxy-based (`spring-fw-aop-pfb#page-title`).

Advice is action taken by an aspect at a particular join point (`spring-fw-aop-introduction-defn#page-title`).

In Spring AOP, a join point always represents a method execution (`spring-fw-aop-introduction-defn#page-title`).

An AOP proxy is an object created by the AOP framework in order to implement the aspect contracts, and in the Spring Framework it is a JDK dynamic proxy or a CGLIB proxy (`spring-fw-aop-introduction-defn#page-title`).

Method calls on a reference to the proxy are calls on the proxy, and the proxy can delegate to all of the interceptors (advice) that are relevant to that method call (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

JDK dynamic proxies are built into the JDK, whereas CGLIB is a common open-source class definition library, repackaged into spring-core (`spring-fw-aop-proxying#proxying-mechanisms`).

Spring AOP defaults to using standard JDK dynamic proxies for AOP proxies (`spring-fw-aop-pfb#page-title`).

Spring AOP can also use CGLIB proxies, which are necessary to proxy classes rather than interfaces (`spring-fw-aop-pfb#page-title`).

If the target object implements at least one interface, a JDK dynamic proxy is used, and all of the interfaces implemented by the target type are proxied (`spring-fw-aop-proxying#proxying-mechanisms`).

If the target object does not implement any interfaces, a CGLIB proxy is created, which is a runtime-generated subclass of the target type (`spring-fw-aop-proxying#proxying-mechanisms`).

You can force the use of CGLIB proxying, for example to proxy every method defined for the target object, not only those implemented by its interfaces (`spring-fw-aop-proxying#proxying-mechanisms`).

```java snippet=m05-l03/ProxyTypes.java
import org.springframework.aop.framework.ProxyFactory;
import org.springframework.aop.support.AopUtils;

public class ProxyTypes {
    public interface Greeter { String greet(); }

    public static class EnglishGreeter implements Greeter {
        public String greet() { return "hello"; }
    }

    public static class Plain {
        public String name() { return "plain"; }
    }

    private static String kind(Object proxy) {
        if (AopUtils.isJdkDynamicProxy(proxy)) return "JDK dynamic proxy";
        return AopUtils.isCglibProxy(proxy) ? "CGLIB proxy" : "not a proxy";
    }

    public static void main(String[] args) {
        Object withInterface = new ProxyFactory(new EnglishGreeter()).getProxy();
        Object withoutInterface = new ProxyFactory(new Plain()).getProxy();
        ProxyFactory forced = new ProxyFactory(new EnglishGreeter());
        forced.setProxyTargetClass(true);
        Object forcedProxy = forced.getProxy();

        System.out.println("interface target: " + kind(withInterface));
        System.out.println("no interface: " + kind(withoutInterface));
        System.out.println("forced class proxy: " + kind(forcedProxy));
        System.out.println("forced proxy extends the target class: " + (forcedProxy instanceof EnglishGreeter));
        System.out.println("interface proxy extends the target class: " + (withInterface instanceof EnglishGreeter));
    }
}
```

The program prints `JDK dynamic proxy` for the target that implements `Greeter` and `CGLIB proxy` for the target with no interface. After `setProxyTargetClass(true)` the `Greeter` target gets a CGLIB proxy, and the program prints `true` for whether that proxy extends the target class and `false` for the JDK proxy.

`@EnableAspectJAutoProxy`, `@EnableTransactionManagement` and related configuration annotations offer a corresponding `proxyTargetClass` attribute (`spring-fw-aop-proxying#aop-forcing-proxy-types`).

The core framework suggests interface-based proxies by default, but Spring Boot may, depending on configuration properties, enable class-based proxies by default (`spring-fw-aop-proxying#aop-forcing-proxy-types`).

As of 7.0, `@Proxyable` on a `@Bean` method or `@Component` class forces a specific proxy type, with `@Proxyable(INTERFACES)` or `@Proxyable(TARGET_CLASS)` overriding any globally configured default (`spring-fw-aop-proxying#aop-forcing-proxy-types`).

## Self-invocation
<!-- bullets: 5.3.a -->

A proxy only sees the calls that arrive through it. When the real object calls one of its own methods, the call stays inside the object and the advice for that second method does not run.

Once the call has reached the target object, any method calls it makes on itself, such as `this.bar()` or `this.foo()`, are invoked against the `this` reference and not the proxy (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

Self invocation via an explicit or implicit `this` reference bypasses the advice (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

```java snippet=m05-l03/SelfInvocation.java
import org.aopalliance.intercept.MethodInterceptor;
import org.springframework.aop.framework.ProxyFactory;

public class SelfInvocation {
    public interface Pojo { void foo(); void bar(); }

    public static class SimplePojo implements Pojo {
        public void foo() { System.out.println("foo runs"); this.bar(); }
        public void bar() { System.out.println("bar runs"); }
    }

    public static void main(String[] args) {
        MethodInterceptor advice = invocation -> {
            System.out.println("advice before " + invocation.getMethod().getName());
            return invocation.proceed();
        };
        ProxyFactory factory = new ProxyFactory(new SimplePojo());
        factory.addAdvice(advice);
        Pojo proxy = (Pojo) factory.getProxy();

        System.out.println("-- foo() through the proxy");
        proxy.foo();
        System.out.println("-- bar() through the proxy");
        proxy.bar();
    }
}
```

The program prints `advice before foo`, `foo runs` and `bar runs` for the call to `foo()`, with no `advice before bar` line. It prints `advice before bar` only for the direct call to `bar()` on the proxy.

:::diagram{kind="flow" caption="A call to foo() reaches the advice; the call to bar() inside foo() does not"}
description: The caller invokes foo() on the proxy, the advice runs, foo() runs on the target, and the this.bar() call made inside foo() runs without advice.
call: caller invokes foo() on the proxy
advice: advice runs before foo
foo: foo runs on the target
bar: this.bar() runs on the target, no advice
call -> advice
advice -> foo
foo -> bar
:::

The best approach is to refactor your code so that the self invocation does not happen (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

An alternative approach is to make use of self injection, and invoke methods on the proxy via the self reference instead of via `this` (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

`AopContext.currentProxy()` totally couples your code to Spring AOP, and the documentation highly discourages it (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

`AopContext.currentProxy()` also requires that the `ProxyFactory` is configured to expose the proxy (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

Spring's AOP framework does not expose proxies by default, as there is a performance cost in doing so (`spring-fw-javadoc-aopcontext#class-aopcontext`).

`AopContext.currentProxy()` throws an `IllegalStateException` if the proxy cannot be found, because the method was invoked outside an AOP invocation context or because the AOP framework has not been configured to expose the proxy (`spring-fw-javadoc-aopcontext#currentProxy()`).

```java snippet=m05-l03/ExposedProxy.java
import org.aopalliance.intercept.MethodInterceptor;
import org.springframework.aop.framework.AopContext;
import org.springframework.aop.framework.ProxyFactory;

public class ExposedProxy {
    public interface Pojo { void foo(); void bar(); }

    public static class SimplePojo implements Pojo {
        public void foo() { ((Pojo) AopContext.currentProxy()).bar(); }
        public void bar() { System.out.println("bar runs"); }
    }

    private static void call(boolean exposeProxy) {
        ProxyFactory factory = new ProxyFactory(new SimplePojo());
        factory.addAdvice((MethodInterceptor) invocation -> {
            System.out.println("advice before " + invocation.getMethod().getName());
            return invocation.proceed();
        });
        factory.setExposeProxy(exposeProxy);
        try {
            ((Pojo) factory.getProxy()).foo();
        } catch (IllegalStateException e) {
            System.out.println("proxy not exposed: illegal state");
        }
    }

    public static void main(String[] args) {
        call(true);
        call(false);
    }
}
```

With the proxy exposed, the program prints `advice before foo`, `advice before bar` and `bar runs`, so the call through `AopContext.currentProxy()` is advised. With `setExposeProxy(false)` it prints `advice before foo` and then `proxy not exposed: illegal state`, the line written by the handler of the `IllegalStateException`.

Weaving links aspects with other application types or objects to create an advised object (`spring-fw-aop-introduction-defn#page-title`).

Spring AOP, like other pure Java AOP frameworks, performs weaving at runtime (`spring-fw-aop-introduction-defn#page-title`).

AspectJ compile-time weaving and load-time weaving do not have the self-invocation issue because they apply advice within the bytecode instead of via a proxy (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

## Limits of proxies
<!-- bullets: 5.3.b -->

A class-based proxy works by extending the target class, so a method that a subclass cannot override is a method the proxy cannot advise. An interface-based proxy sees only the methods of the interface. A proxy also has to be fully built before it behaves as expected, which rules out relying on it in code that runs while the bean is being initialized.

`final` classes cannot be proxied, because they cannot be extended (`spring-fw-aop-proxying#proxying-mechanisms`).

`final` methods cannot be advised, because they cannot be overridden (`spring-fw-aop-proxying#proxying-mechanisms`).

`private` methods cannot be advised, because they cannot be overridden (`spring-fw-aop-proxying#proxying-mechanisms`).

Methods that are not visible, for example package-private methods in a parent class from a different package, cannot be advised because they are effectively private (`spring-fw-aop-proxying#proxying-mechanisms`).

```java snippet=m05-l03/FinalMethod.java
import org.aopalliance.intercept.MethodInterceptor;
import org.springframework.aop.framework.ProxyFactory;

public class FinalMethod {
    public static class Account {
        public String open() { return "open"; }
        public final String close() { return "close"; }
    }

    public static void main(String[] args) {
        ProxyFactory factory = new ProxyFactory(new Account());
        factory.setProxyTargetClass(true);
        factory.addAdvice((MethodInterceptor) invocation -> {
            System.out.println("advice before " + invocation.getMethod().getName());
            return invocation.proceed();
        });
        Account proxy = (Account) factory.getProxy();
        proxy.open();
        proxy.close();
        System.out.println("done");
    }
}
```

The program prints `advice before open` and `done`: the call to the `final` method `close()` on the CGLIB proxy produces no advice line.

:::esquema{kind=tabla title="What a proxy cannot advise"}
| Case | Why | Source |
|---|---|---|
| `final` class | It cannot be extended, so it cannot be proxied | `spring-fw-aop-proxying#proxying-mechanisms` |
| `final` method | It cannot be overridden | `spring-fw-aop-proxying#proxying-mechanisms` |
| `private` method | It cannot be overridden | `spring-fw-aop-proxying#proxying-mechanisms` |
| Package-private method of a parent class in another package | It is effectively private | `spring-fw-aop-proxying#proxying-mechanisms` |
| Method called through `this` | The call is invoked against the `this` reference and not the proxy | `spring-fw-aop-proxying#aop-understanding-aop-proxies` |
| Non-public method of an interface-based proxy | Transactional methods in interface-based proxies must always be public and defined in the proxied interface | `spring-fw-tx-declarative-annotations#using-transactional` |
:::

The constructor of your proxied object is not called twice, since the CGLIB proxy instance is created through Objenesis (`spring-fw-aop-proxying#proxying-mechanisms`).

If your JVM does not allow for constructor bypassing, you might see double invocations and corresponding debug log entries from Spring's AOP support (`spring-fw-aop-proxying#proxying-mechanisms`).

You cannot create a CGLIB proxy for a class from the `java.lang` package when deploying on the module path (`spring-fw-aop-proxying#proxying-mechanisms`).

The proxy must be fully initialized to provide the expected behavior, so you should not rely on `@Transactional` in your initialization code (`spring-fw-tx-declarative-annotations#using-transactional`).

The `@Transactional` annotation is typically used on methods with public visibility (`spring-fw-tx-declarative-annotations#using-transactional`).

As of 6.0, protected or package-visible methods can also be made transactional for class-based proxies by default (`spring-fw-tx-declarative-annotations#using-transactional`).

A class-level `@Transactional` annotation does not apply to ancestor classes up the class hierarchy (`spring-fw-tx-declarative-annotations#using-transactional`).

The Spring team recommends that you annotate methods of concrete classes with `@Transactional`, rather than relying on annotated methods in interfaces (`spring-fw-tx-declarative-annotations#using-transactional`).

## Proxy-based annotations
<!-- bullets: 5.3.c -->

`@Transactional`, `@Async`, `@Cacheable` and `@Retryable` each wrap a method call in an extra step. Spring AOP applies each of them as an interceptor.

Spring AOP applies interceptors in a specific order when multiple annotations such as `@Retryable`, `@Transactional`, `@Cacheable` and `@Async` are present on the same method (`spring-fw-resilience#resilience-annotations-retryable-combining`).

In proxy mode, which is the default, only external method calls coming in through the proxy are intercepted (`spring-fw-tx-declarative-annotations#using-transactional`).

The mere presence of the `@Transactional` annotation is not enough to activate the transactional behavior (`spring-fw-tx-declarative-annotations#using-transactional`).

You make the bean instance transactional through an `@EnableTransactionManagement` annotation in a `@Configuration` class (`spring-fw-tx-declarative-annotations#using-transactional`).

Self-invocation does not lead to an actual transaction at runtime even if the invoked method is marked with `@Transactional` (`spring-fw-tx-declarative-annotations#using-transactional`).

Consider using AspectJ mode if you expect self-invocations to be wrapped with transactions as well (`spring-fw-tx-declarative-annotations#using-transactional`).

If `proxy-target-class` is false or omitted, standard JDK interface-based proxies are created for classes annotated with `@Transactional`, and if it is true, class-based proxies are created (`spring-fw-tx-declarative-annotations#using-transactional`).

```java snippet=m05-l03/TransactionalSelfInvocation.java
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.transaction.*;
import org.springframework.transaction.annotation.*;
import org.springframework.transaction.support.*;

public class TransactionalSelfInvocation {
    static class RecordingManager extends AbstractPlatformTransactionManager {
        protected Object doGetTransaction() { return new Object(); }
        protected void doBegin(Object tx, TransactionDefinition d) { System.out.println("begin"); }
        protected void doCommit(DefaultTransactionStatus s) { System.out.println("commit"); }
        protected void doRollback(DefaultTransactionStatus s) { System.out.println("rollback"); }
    }

    public static class Orders {
        public void placeOrder() { System.out.println("place order"); this.audit(); }
        @Transactional(propagation = Propagation.REQUIRES_NEW)
        public void audit() { System.out.println("audit"); }
    }

    @Configuration @EnableTransactionManagement
    static class Config {
        @Bean Orders orders() { return new Orders(); }
        @Bean PlatformTransactionManager transactionManager() { return new RecordingManager(); }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            Orders orders = context.getBean(Orders.class);
            System.out.println("-- self-invocation");
            orders.placeOrder();
            System.out.println("-- through the proxy");
            orders.audit();
        }
    }
}
```

For the first call the program prints `place order` and `audit` with no `begin` or `commit` line, because `audit()` was reached through `this`. For the second call it prints `begin`, `audit` and `commit`.

`@Async` makes the caller return immediately, while the actual execution of the method occurs in a task submitted to a Spring `TaskExecutor` (`spring-fw-async#scheduling-annotation-support-async`).

A method that returns a value can be invoked asynchronously only if it has a `Future`-typed return value (`spring-fw-async#scheduling-annotation-support-async`).

`@Async` methods may declare `CompletableFuture` as a return type as well as a regular `Future` (`spring-fw-async#scheduling-annotation-support-async`).

You can not use `@Async` in conjunction with lifecycle callbacks such as `@PostConstruct` (`spring-fw-async#scheduling-annotation-support-async`).

To initialize a Spring bean asynchronously, you currently have to use a separate initializing Spring bean that then invokes the `@Async` method on the target (`spring-fw-async#scheduling-annotation-support-async`).

`@Cacheable` demarcates methods for which the result is stored in the cache, so that later invocations with the same arguments return the cached value without invoking the method (`spring-fw-cache-annotations#cache-annotations-cacheable`).

`@Retryable` specifies retry characteristics for an individual method, or for all proxy-invoked methods in a given class hierarchy when it is declared at the type level (`spring-fw-resilience#resilience-annotations-retryable`).

By default, the invocation is retried for any exception thrown, with at most 3 retry attempts after an initial failure and a delay of 1 second between attempts (`spring-fw-resilience#resilience-annotations-retryable`).

Total attempts are 1 initial attempt plus `maxRetries` attempts (`spring-fw-resilience#resilience-annotations-retryable`).

If `maxRetries` is set to 4, the `@Retryable` method is invoked at least once and at most 5 times (`spring-fw-resilience#resilience-annotations-retryable`).

If all attempts have failed and the retry policy has been exhausted, the last original exception from the target method is propagated to the caller (`spring-fw-resilience#resilience-annotations-retryable`).

## Ordering of proxy-based advice
<!-- bullets: 5.3.c -->

When several of these annotations sit on one method, their advice nests in layers. The outer layer runs first on the way in and last on the way out. Which annotation is the outer layer decides what a retry repeats.

When `@Async` is combined with `@Retryable`, the async advice is applied outermost, so all retry attempts run on the async executor thread (`spring-fw-async#scheduling-annotation-support-async`).

When `@Cacheable` is combined with `@Retryable`, the retry advice is applied outermost, so each retry attempt checks the cache before invoking the method (`spring-fw-cache-annotations#cache-annotations-cacheable`).

When `@Transactional` is combined with `@Retryable`, the retry advice is applied outermost, so each retry attempt runs in its own transaction (`spring-fw-tx-declarative-annotations#using-transactional`).

```java snippet=m05-l03/RetryInsideTransaction.java
import java.util.concurrent.atomic.AtomicInteger;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.resilience.annotation.EnableResilientMethods;
import org.springframework.resilience.annotation.Retryable;
import org.springframework.transaction.*;
import org.springframework.transaction.annotation.*;
import org.springframework.transaction.support.*;

public class RetryInsideTransaction {
    static class RecordingManager extends AbstractPlatformTransactionManager {
        protected Object doGetTransaction() { return new Object(); }
        protected void doBegin(Object tx, TransactionDefinition d) { System.out.println("begin"); }
        protected void doCommit(DefaultTransactionStatus s) { System.out.println("commit"); }
        protected void doRollback(DefaultTransactionStatus s) { System.out.println("rollback"); }
    }

    public static class Payments {
        private final AtomicInteger attempts = new AtomicInteger();
        @Retryable(maxRetries = 2, delay = 0)
        @Transactional
        public void charge() {
            System.out.println("attempt " + attempts.incrementAndGet());
            if (attempts.get() < 3) throw new IllegalStateException("try again");
        }
    }
    @Configuration @EnableTransactionManagement @EnableResilientMethods
    static class Config {
        @Bean Payments payments() { return new Payments(); }
        @Bean PlatformTransactionManager transactionManager() { return new RecordingManager(); }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            context.getBean(Payments.class).charge();
        }
    }
}
```

The program prints `begin`, `attempt 1` and `rollback`, then the same three lines for attempt 2, and `begin`, `attempt 3` and `commit` for the third attempt.

:::diagram{kind="flow" caption="With retry outermost, each attempt gets its own transaction"}
description: The retry advice calls the method; each failed attempt is rolled back and the next attempt begins a new transaction; the third attempt commits.
begin1: begin, attempt 1
rollback1: attempt 1 fails, rollback
begin2: begin, attempt 2
rollback2: attempt 2 fails, rollback
begin3: begin, attempt 3
commit3: attempt 3 succeeds, commit
begin1 -> rollback1
rollback1 -> begin2
begin2 -> rollback2
rollback2 -> begin3
begin3 -> commit3
:::

Both the retry and the async post-processors are plain `Ordered` bean post-processors, so you can change their relative ordering by setting the `order` attribute on `@EnableResilientMethods` and/or `@EnableAsync` (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

With the reversed order, in which retry is outermost and async innermost, exceptions thrown during asynchronous execution are not retried, because the retry interceptor only sees the `Future` handle (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

Such an arrangement only retries synchronous submission failures, such as a rejected task submission, and is rarely desirable in practice (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

The technique of changing the order attribute does not apply to `@Transactional` or `@Cacheable` (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

The advisors of `@Transactional` and `@Cacheable` are registered through Spring's shared `InfrastructureAdvisorAutoProxyCreator`, whose own post-processor order is fixed at `Ordered.HIGHEST_PRECEDENCE` (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

Retry advice is always applied outside `@Transactional` and `@Cacheable`, regardless of the order configured on `@EnableResilientMethods` (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

The `order` attribute of `@EnableTransactionManagement` defaults to `Ordered.LOWEST_PRECEDENCE`, and no specified ordering means that the AOP subsystem determines the order of the advice (`spring-fw-tx-declarative-annotations#using-transactional`).

Spring AOP follows the same precedence rules as AspectJ to determine the order of advice execution (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

When two pieces of advice defined in different aspects both need to run at the same join point, unless you specify otherwise, the order of execution is undefined (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

You control the order by implementing the `org.springframework.core.Ordered` interface in the aspect class or annotating it with the `@Order` annotation (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

Given two aspects, the aspect returning the lower value from `Ordered.getOrder()`, or the annotation value, has the higher precedence (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

```java snippet=m05-l03/AdviceOrder.java
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;
import org.springframework.core.annotation.Order;

public class AdviceOrder {
    public static class Service { public void work() { System.out.println("work"); } }

    public abstract static class Traced {
        @Around("execution(* AdviceOrder.Service.work(..))")
        public Object around(ProceedingJoinPoint pjp) throws Throwable {
            System.out.println(getClass().getSimpleName() + " in");
            Object result = pjp.proceed();
            System.out.println(getClass().getSimpleName() + " out");
            return result;
        }
    }

    @Aspect @Order(2) public static class Second extends Traced { }
    @Aspect @Order(1) public static class First extends Traced { }

    @Configuration @EnableAspectJAutoProxy
    static class Config {
        @Bean Service service() { return new Service(); }
        @Bean Second second() { return new Second(); }
        @Bean First first() { return new First(); }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            context.getBean(Service.class).work();
        }
    }
}
```

The program prints `First in`, `Second in`, `work`, `Second out`, `First out`, so the aspect with `@Order(1)` wraps the aspect with `@Order(2)`.

Advice methods defined in the same `@Aspect` class are assigned precedence by advice type, from highest to lowest: `@Around`, `@Before`, `@After`, `@AfterReturning`, `@AfterThrowing` (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

Two pieces of the same type of advice in the same `@Aspect` class have an undefined order, since there is no way to retrieve the source code declaration order through reflection for javac-compiled classes (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

## Key points

- Spring AOP is proxy-based. A target that implements an interface gets a JDK dynamic proxy by default; otherwise it gets a CGLIB proxy, a runtime-generated subclass.
- The core framework suggests interface-based proxies by default, and Spring Boot may enable class-based proxies by default.
- Self invocation through `this` bypasses the advice; refactoring so that it does not happen is the best, least-invasive approach.
- `AopContext.currentProxy()` works only when the proxy is exposed, which Spring AOP does not do by default.
- `final` classes, `final` methods and `private` methods cannot be proxied or advised by CGLIB.
- The proxy must be fully initialized, so `@Transactional` is not reliable in initialization code.
- `@Async` cannot be used with lifecycle callbacks such as `@PostConstruct`.
- A `@Retryable` method is invoked at most `maxRetries` plus one times.
- Retry advice is always applied outside `@Cacheable` and `@Transactional`; with `@Async`, the async advice is outermost by default, and the `order` attributes can change that.
- Two aspects without an order have an undefined order; the lower `@Order` value has the higher precedence.
- In one `@Aspect` class, precedence by advice type runs `@Around`, `@Before`, `@After`, `@AfterReturning`, `@AfterThrowing`.

# Design structures common in interviews

## LRU cache with a linked hash map
<!-- bullets: 2.6.a -->

A `LinkedHashMap` in access order keeps its entries from the least recently accessed to the most recently accessed, and the eldest entry is the first one in that order. Overriding `removeEldestEntry` deletes it when a new entry arrives, which makes the map well-suited to LRU caches.

A `LinkedHashMap` differs from a `HashMap` in that it maintains a doubly-linked list running through all of its entries (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The linked list defines the encounter order, which is normally the order in which keys were inserted into the map (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The encounter order is not affected if a key is re-inserted into the map with the `put` method (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

A special constructor creates a linked hash map whose encounter order is the order in which its entries were last accessed, from least-recently accessed to most-recently (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

An access-ordered linked hash map is well-suited to building LRU caches (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Invoking `put`, `putIfAbsent`, `get`, `getOrDefault`, `compute`, `computeIfAbsent`, `computeIfPresent` or `merge` results in an access to the corresponding entry (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The `putAll` method generates one entry access for each mapping in the specified map (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The constructor with an `accessOrder` flag creates an access-ordered map when the flag is true and an insertion-ordered map when it is false (`javadoc-linkedhashmap#<init>(int,float,boolean)`).

The replace methods result in an access of the entry only if the value is replaced (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

No methods other than those listed generate entry accesses (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Operations on the `keySet`, `values` and `entrySet` views do not affect the encounter order of the backing map (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Explicit-positioning methods such as `putFirst` or `lastEntry` do not generate entry accesses (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Since the eldest entry is the first entry in encounter order, programs can inspect and remove stale mappings through `firstEntry` and `pollFirstEntry` (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

In an access-ordered linked hash map, merely querying the map with `get` is a structural modification (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The iterators of the collection views are fail-fast: if the map is structurally modified after the iterator is created, in any way except through the iterator's own `remove` method, the iterator throws a `ConcurrentModificationException` (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

A `LinkedHashMap` is not synchronized, so a map that several threads access, with at least one of them modifying it structurally, must be synchronized externally (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Iteration over the collection views of a `LinkedHashMap` requires time proportional to the size of the map, regardless of its capacity (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The `removeEldestEntry` method is invoked by `put` and `putAll` after inserting a new entry into the map (`javadoc-linkedhashmap#removeEldestEntry(java.util.Map.Entry)`).

The default `removeEldestEntry` merely returns false, so the eldest element is never removed (`javadoc-linkedhashmap#removeEldestEntry(java.util.Map.Entry)`).

Overriding `removeEldestEntry` to return `size() > MAX_ENTRIES` lets the map grow up to MAX_ENTRIES entries and then delete the eldest entry each time a new entry is added (`javadoc-linkedhashmap#removeEldestEntry(java.util.Map.Entry)`).

Like `HashMap`, a `LinkedHashMap` provides constant-time performance for the basic operations, assuming the hash function disperses elements properly among the buckets (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

In a `LinkedHashSet`, the hash table finds the relevant list node in constant time and the list node is then deleted, also in constant time (`ods-3-2-dllist-doubly-linked-li#SECTION00622000000000000000`).

Linked list structures are well-suited to applications where references to list nodes can be obtained through external means (`ods-3-2-dllist-doubly-linked-li#SECTION00622000000000000000`).

The snippet subclasses `LinkedHashMap` with the access-order constructor and a capacity of 3. It puts a, b and c, reads a, and puts d. A second map keeps insertion order and puts a again.

```java snippet=m02-l06/LruCache.java
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(16, 0.75f, true);
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }

    public static void main(String[] args) {
        LruCache<String, Integer> cache = new LruCache<>(3);
        cache.put("a", 1);
        cache.put("b", 2);
        cache.put("c", 3);
        cache.get("a");
        cache.put("d", 4);
        System.out.println("access-ordered " + List.copyOf(cache.keySet()));

        Map<String, Integer> insertionOrdered = new LinkedHashMap<>();
        insertionOrdered.put("a", 1);
        insertionOrdered.put("b", 2);
        insertionOrdered.put("c", 3);
        insertionOrdered.put("a", 4);
        System.out.println("insertion-ordered " + List.copyOf(insertionOrdered.keySet()));
    }
}
```

The cache prints `access-ordered [c, a, d]`, because b is the eldest entry when d arrives.

The second map prints `insertion-ordered [a, b, c]`.

The next snippet walks the `keySet` of a map holding a, b and c and calls `get` on each key it visits, once for an access-ordered map and once for an insertion-ordered map.

```java snippet=m02-l06/AccessOrderIteration.java
import java.util.ConcurrentModificationException;
import java.util.LinkedHashMap;
import java.util.Map;

public class AccessOrderIteration {
    static String words(Exception e) {
        return e.getClass().getSimpleName().replace("Exception", "").replaceAll("([a-z])([A-Z])", "$1 $2").toLowerCase();
    }

    static String walkAndGet(boolean accessOrder) {
        Map<String, Integer> map = new LinkedHashMap<>(16, 0.75f, accessOrder);
        map.put("a", 1);
        map.put("b", 2);
        map.put("c", 3);
        StringBuilder visited = new StringBuilder();
        try {
            for (String key : map.keySet()) {
                visited.append(key);
                map.get(key);
            }
            return "visited " + visited;
        } catch (ConcurrentModificationException e) {
            return "visited " + visited + " then " + words(e);
        }
    }

    public static void main(String[] args) {
        System.out.println("access-ordered: " + walkAndGet(true));
        System.out.println("insertion-ordered: " + walkAndGet(false));
    }
}
```

The access-ordered map prints `access-ordered: visited a then concurrent modification`.

The insertion-ordered map prints `insertion-ordered: visited abc`.

## LFU eviction and an in-memory rate limiter
<!-- bullets: 2.6.a -->

An LFU cache evicts the entry used least often, and a rate limiter caps how many requests pass in a period. Redis documents an approximated LFU, and a token bucket is one way to limit requests.

Starting with Redis 4.0, the Least Frequently Used eviction mode is available (`redis-eviction#lfu-eviction`).

In Redis LFU mode, Redis tries to track the frequency of access of items, so the ones used rarely are evicted (`redis-eviction#lfu-eviction`).

The `allkeys-lfu` policy evicts any key using approximated LFU (`redis-eviction#lfu-eviction`).

The `volatile-lfu` policy evicts using approximated LFU among the keys with an expire set (`redis-eviction#lfu-eviction`).

Redis approximates LFU with a probabilistic counter, called a Morris counter, which estimates the access frequency using just a few bits per object (`redis-eviction#lfu-eviction`).

By default Redis decays the LFU counter every one minute (`redis-eviction#lfu-eviction`).

The LFU frequency counter is in the range 0-255 (`redis-eviction#lfu-eviction`).

In LFU mode, the keys used often have a higher chance of remaining in memory (`redis-eviction#lfu-eviction`).

By default Redis saturates the LFU counter at around one million requests (`redis-eviction#lfu-eviction`).

The LFU decay time is the number of minutes after which a counter is decayed when it is sampled and found to be older than that value, and a value of 0 means the counter is never decayed (`redis-eviction#lfu-eviction`).

The counter logarithm factor changes how many hits are needed to saturate the frequency counter, and the higher the factor, the more accesses are needed to reach the maximum (`redis-eviction#lfu-eviction`).

The Redis LRU algorithm approximates the least recently used keys by sampling a small number of keys at random and evicting the ones with the longest time since last access (`redis-eviction#apx-lru`).

Redis does not use a true LRU implementation because it costs more memory (`redis-eviction#apx-lru`).

A token bucket rate limiter allows controlled bursts of traffic while enforcing a steady average rate (`redis-ratelimiting-algorithms#how-it-works-3`).

In a token bucket rate limiter, each request consumes one token, and when the bucket is empty, requests are denied until more tokens refill (`redis-ratelimiting-algorithms#how-it-works-3`).

In a token bucket, tokens refill at a steady rate and the bucket has a maximum capacity, so tokens cannot accumulate beyond a set limit (`redis-ratelimiting-algorithms#how-it-works-3`).

The refill calculation of a token bucket uses floating-point math, which needs care to avoid drift (`redis-ratelimiting-algorithms#trade-offs-3`).

A fixed window rate limiter counts requests within discrete, non-overlapping time intervals (`redis-ratelimiting-algorithms#how-it-works`).

A fixed window rate limiter is susceptible to boundary bursts: a client can send 10 requests at second 9 and another 10 at second 11, which is 20 requests in 2 seconds, while staying within a limit of 10 per 10 seconds (`redis-ratelimiting-algorithms#trade-offs`).

A sliding window log rate limiter records the exact timestamp of every request, removes the entries older than the window on each new attempt, and counts what is left (`redis-ratelimiting-algorithms#how-it-works-1`).

A sliding window log eliminates the boundary-burst problem of fixed windows at the cost of higher memory usage (`redis-ratelimiting-algorithms#how-it-works-1`).

The memory of a sliding window log grows linearly with request volume, O(n) per client (`redis-ratelimiting-algorithms#trade-offs-1`).

The snippet keeps a token bucket in memory with a capacity of 3 and a refill of 1 token per second. It takes the time as an argument, so the output does not depend on a clock. It asks for 4 tokens at second 0, 2 at second 1 and 5 at second 100.

```java snippet=m02-l06/TokenBucketBurst.java
import java.util.ArrayList;
import java.util.List;

public class TokenBucketBurst {
    private final long capacity;
    private final long refillPerSecond;
    private long tokens;
    private long lastSecond;

    TokenBucketBurst(long capacity, long refillPerSecond) {
        this.capacity = capacity;
        this.refillPerSecond = refillPerSecond;
        this.tokens = capacity;
    }

    boolean tryAcquire(long second) {
        tokens = Math.min(capacity, tokens + (second - lastSecond) * refillPerSecond);
        lastSecond = second;
        if (tokens == 0) {
            return false;
        }
        tokens--;
        return true;
    }

    static List<Boolean> requests(TokenBucketBurst bucket, long second, int count) {
        List<Boolean> results = new ArrayList<>();
        for (int i = 0; i < count; i++) {
            results.add(bucket.tryAcquire(second));
        }
        return results;
    }

    public static void main(String[] args) {
        TokenBucketBurst bucket = new TokenBucketBurst(3, 1);
        System.out.println("at second 0: " + requests(bucket, 0, 4));
        System.out.println("at second 1: " + requests(bucket, 1, 2));
        System.out.println("at second 100: " + requests(bucket, 100, 5));
    }
}
```

At second 0 it prints `at second 0: [true, true, true, false]`, a burst up to the capacity followed by a denial.

At second 1 it prints `at second 1: [true, false]`, one refilled token.

At second 100 it prints `at second 100: [true, true, true, false, false]`, because the tokens stop at the capacity.

:::judgement{source="Vladimir Bukhtoyarov, Bucket4j README" ref="bucket4j-readme#top"}
According to Vladimir Bukhtoyarov, Bucket4j is a Java rate-limiting library based on the token-bucket algorithm. He writes that, besides clustered usage on top of back-ends, it supports local in-memory buckets, for cases where distributed synchronization is unnecessary.

## Iterator over nested structures
<!-- bullets: 2.6.a -->

An iterator hands out the elements of a collection one at a time. An iterator over nested lists keeps its position in the current inner list and moves to the next inner list when the current one runs out.

`Iterator` takes the place of `Enumeration` in the Java Collections Framework (`javadoc-iterator#interface-iterator-e`).

Iterators allow the caller to remove elements from the underlying collection during the iteration with well-defined semantics (`javadoc-iterator#interface-iterator-e`).

A recursive traversal of a binary tree can use more stack space than is available when the height of the tree is very large, causing a crash (`ods-6-1-binarytree-basic-binary#SECTION00912000000000000000`).

The maximum depth of the recursion is given by the height of the tree (`ods-6-1-binarytree-basic-binary#SECTION00912000000000000000`).

To traverse a binary tree without recursion, an algorithm can rely on where it came from to determine where it will go next (`ods-6-1-binarytree-basic-binary#SECTION00912000000000000000`).

`hasNext` returns true if the iteration has more elements, in other words if `next()` would return an element rather than throwing an exception (`javadoc-iterator#hasNext()`).

`next` throws a `NoSuchElementException` if the iteration has no more elements (`javadoc-iterator#next()`).

`remove` can be called only once per call to `next()` (`javadoc-iterator#remove()`).

The default implementation of `remove` throws an `UnsupportedOperationException` and performs no other action (`javadoc-iterator#remove()`).

`remove` throws an `IllegalStateException` if `next` has not yet been called, or if `remove` has already been called after the last call to `next` (`javadoc-iterator#remove()`).

The default implementation of `forEachRemaining` behaves as `while (hasNext()) action.accept(next());` (`javadoc-iterator#forEachRemaining(java.util.function.Consumer)`).

The snippet implements `Iterator<Integer>` over a list of lists. Its `hasNext` moves to the next inner list while the current one is exhausted, so empty inner lists are skipped. It keeps no recursion, only the position in the outer and the inner iterator.

```java snippet=m02-l06/NestedIterator.java
import java.util.ArrayList;
import java.util.Iterator;
import java.util.List;
import java.util.NoSuchElementException;

public class NestedIterator implements Iterator<Integer> {
    private final Iterator<List<Integer>> outer;
    private Iterator<Integer> inner = List.<Integer>of().iterator();

    NestedIterator(List<List<Integer>> nested) {
        this.outer = nested.iterator();
    }

    @Override
    public boolean hasNext() {
        while (!inner.hasNext() && outer.hasNext()) {
            inner = outer.next().iterator();
        }
        return inner.hasNext();
    }

    @Override
    public Integer next() {
        if (!hasNext()) {
            throw new NoSuchElementException();
        }
        return inner.next();
    }

    static List<Integer> drain(List<List<Integer>> nested) {
        List<Integer> values = new ArrayList<>();
        new NestedIterator(nested).forEachRemaining(values::add);
        return values;
    }

    public static void main(String[] args) {
        System.out.println("values " + drain(List.of(List.of(1, 2), List.of(), List.of(3), List.of())));
        System.out.println("values of two empty lists " + drain(List.of(List.of(), List.of())));
    }
}
```

The nested list `[[1, 2], [], [3], []]` yields `values [1, 2, 3]`.

Two empty inner lists yield `values of two empty lists []`.

The next snippet calls `remove` before `next`, after `next` and twice in a row on an `ArrayList` iterator, reads past the end after `forEachRemaining`, and calls `remove` on an iterator that does not override it.

```java snippet=m02-l06/IteratorContract.java
import java.util.ArrayList;
import java.util.Iterator;
import java.util.List;
import java.util.NoSuchElementException;

public class IteratorContract {
    static String words(Exception e) {
        return e.getClass().getSimpleName().replace("Exception", "").replaceAll("([a-z])([A-Z])", "$1 $2").toLowerCase();
    }

    static String outcome(Runnable action) {
        try {
            action.run();
            return "no exception";
        } catch (RuntimeException e) {
            return words(e);
        }
    }

    public static void main(String[] args) {
        List<Integer> values = new ArrayList<>(List.of(1, 2, 3));
        Iterator<Integer> iterator = values.iterator();
        System.out.println("remove before next: " + outcome(iterator::remove));
        iterator.next();
        System.out.println("remove after next: " + outcome(iterator::remove));
        System.out.println("remove twice: " + outcome(iterator::remove));
        System.out.println("values " + values);
        iterator.forEachRemaining(v -> { });
        System.out.println("next at the end: " + outcome(iterator::next));

        Iterator<Integer> withoutRemove = new Iterator<>() {
            public boolean hasNext() { return false; }
            public Integer next() { throw new NoSuchElementException(); }
        };
        System.out.println("default remove: " + outcome(withoutRemove::remove));
    }
}
```

The calls print `remove before next: illegal state`, `remove after next: no exception` and `remove twice: illegal state`.

The list is left as `values [2, 3]`.

Reading past the end prints `next at the end: no such element`, and the default `remove` prints `default remove: unsupported operation`.

## Running median with two heaps
<!-- bullets: 2.6.a -->

A priority queue gives its smallest element in constant time and takes logarithmic time to add an element or remove the head. Two of them, one ordered largest first and one ordered smallest first, give the median of a stream from their two heads.

The elements of a `PriorityQueue` are ordered according to their natural ordering, or by a `Comparator` provided at queue construction time (`javadoc-priorityqueue#class-priorityqueue-e`).

The head of a `PriorityQueue` is the least element with respect to the specified ordering (`javadoc-priorityqueue#class-priorityqueue-e`).

The `Iterator` of a `PriorityQueue` is not guaranteed to traverse the elements in any particular order (`javadoc-priorityqueue#class-priorityqueue-e`).

A `PriorityQueue` provides O(log(n)) time for `offer`, `poll`, `remove()` and `add` (`javadoc-priorityqueue#class-priorityqueue-e`).

A `PriorityQueue` provides linear time for `remove(Object)` and `contains(Object)` (`javadoc-priorityqueue#class-priorityqueue-e`).

A `PriorityQueue` provides constant time for `peek`, `element` and `size` (`javadoc-priorityqueue#class-priorityqueue-e`).

A binary heap stores the smallest value of the priority queue at position 0, the root (`ods-10-1-binaryheap-implicit-bi#SECTION001310000000000000000`).

A `PriorityQueue` is an unbounded priority queue based on a priority heap (`javadoc-priorityqueue#class-priorityqueue-e`).

A `PriorityQueue` does not permit null elements (`javadoc-priorityqueue#class-priorityqueue-e`).

If several elements of a `PriorityQueue` are tied for least value, the head is one of them and ties are broken arbitrarily (`javadoc-priorityqueue#class-priorityqueue-e`).

For ordered traversal of a `PriorityQueue`, the documentation suggests `Arrays.sort(pq.toArray())` (`javadoc-priorityqueue#class-priorityqueue-e`).

A `PriorityQueue` is not synchronized, and the documentation names `PriorityBlockingQueue` as the thread-safe class (`javadoc-priorityqueue#class-priorityqueue-e`).

`poll` retrieves and removes the head of the queue, or returns null if the queue is empty (`javadoc-priorityqueue#poll()`).

`peek` retrieves, but does not remove, the head of the queue, or returns null if the queue is empty (`javadoc-priorityqueue#peek()`).

Eytzinger's method represents a complete binary tree as an array by laying out the nodes in breadth-first order, with the root at position 0, its left child at position 1 and its right child at position 2 (`ods-10-1-binaryheap-implicit-bi#SECTION001310000000000000000`).

In a `BinaryHeap`, adding a value places it at the end of the array and repeatedly swaps it with its parent until it is no longer smaller than its parent (`ods-10-1-binaryheap-implicit-bi#SECTION001310000000000000000`).

In a `BinaryHeap`, removing the smallest value replaces the root with the last value and repeatedly swaps it with the smaller of its two children until it is the smallest of the three (`ods-10-1-binaryheap-implicit-bi#SECTION001310000000000000000`).

The first snippet adds 5, 1 and 3 to a `PriorityQueue`, prints the queue and then polls it empty.

```java snippet=m02-l06/PriorityQueueOrder.java
import java.util.ArrayList;
import java.util.List;
import java.util.PriorityQueue;

public class PriorityQueueOrder {
    public static void main(String[] args) {
        PriorityQueue<Integer> queue = new PriorityQueue<>();
        queue.add(5);
        queue.add(1);
        queue.add(3);
        System.out.println("queue as printed " + queue);

        List<Integer> polled = new ArrayList<>();
        while (!queue.isEmpty()) {
            polled.add(queue.poll());
        }
        System.out.println("queue polled " + polled);
    }
}
```

The queue prints as `queue as printed [1, 5, 3]`.

Polling returns the values as `queue polled [1, 3, 5]`.

The next snippet calls `peek` and `poll` on an empty queue and on a queue holding 5, 1 and 3, adds a null element, and sorts a copy of the array returned by `toArray`.

```java snippet=m02-l06/PriorityQueueBehaviour.java
import java.util.Arrays;
import java.util.PriorityQueue;

public class PriorityQueueBehaviour {
    public static void main(String[] args) {
        PriorityQueue<Integer> queue = new PriorityQueue<>();
        System.out.println("peek when empty: " + queue.peek());
        System.out.println("poll when empty: " + queue.poll());
        queue.add(5);
        queue.add(1);
        queue.add(3);
        System.out.println("peek leaves the head: " + queue.peek() + " of " + queue.size());
        System.out.println("poll removes the head: " + queue.poll() + " of " + queue.size());
        try {
            queue.add(null);
        } catch (NullPointerException e) {
            System.out.println("null element: null pointer");
        }
        Object[] ordered = queue.toArray();
        Arrays.sort(ordered);
        System.out.println("sorted copy " + Arrays.toString(ordered));
    }
}
```

The empty queue prints `peek when empty: null` and `poll when empty: null`.

On the queue with three elements, `peek` prints `peek leaves the head: 1 of 3` and `poll` prints `poll removes the head: 1 of 2`.

The null element prints `null element: null pointer`.

The sorted copy prints `sorted copy [3, 5]`.

The second snippet keeps the lower half of a stream in a `PriorityQueue` ordered largest first and the upper half in one ordered smallest first. After each value it moves one head across when needed so that the lower queue has the same size as the upper one or one element more, and it reads the median from the lower head when that queue is larger, or from the mean of the two heads when the sizes are equal.

```java snippet=m02-l06/RunningMedian.java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.PriorityQueue;

public class RunningMedian {
    private final PriorityQueue<Integer> lower = new PriorityQueue<>(Collections.reverseOrder());
    private final PriorityQueue<Integer> upper = new PriorityQueue<>();

    void add(int value) {
        if (lower.isEmpty() || value <= lower.peek()) {
            lower.add(value);
        } else {
            upper.add(value);
        }
        if (lower.size() > upper.size() + 1) {
            upper.add(lower.poll());
        } else if (upper.size() > lower.size()) {
            lower.add(upper.poll());
        }
    }

    double median() {
        return lower.size() > upper.size() ? lower.peek() : (lower.peek() + upper.peek()) / 2.0;
    }

    public static void main(String[] args) {
        RunningMedian stream = new RunningMedian();
        List<Double> medians = new ArrayList<>();
        for (int value : new int[] {5, 15, 1, 3}) {
            stream.add(value);
            medians.add(stream.median());
        }
        System.out.println("medians " + medians);
    }
}
```

For the stream 5, 15, 1, 3 it prints `medians [5.0, 10.0, 5.0, 4.0]`.

## Key points

- A `LinkedHashMap` keeps a doubly-linked list through its entries, and the access-order constructor makes it well-suited to LRU caches.
- Overriding `removeEldestEntry` to return `size() > MAX_ENTRIES` deletes the eldest entry after each `put` that passes the limit.
- Re-inserting a key with `put` does not change the encounter order of an insertion-ordered map.
- In an access-ordered `LinkedHashMap`, a `get` during iteration is a structural modification and the fail-fast iterator throws a `ConcurrentModificationException`, while the insertion-ordered map visits all keys.
- Of the cache snippet, the access-ordered map printed `[c, a, d]` and the insertion-ordered map printed `[a, b, c]`.
- An iterator over nested lists can skip empty inner lists in `hasNext` without recursion.
- `remove` is valid once per call to `next`, throws an `IllegalStateException` otherwise, and throws an `UnsupportedOperationException` where it is not overridden.
- A `PriorityQueue` has its least element at the head, but its iterator and `toString` do not follow the ordering, as `[1, 5, 3]` showed.
- A `PriorityQueue` takes O(log(n)) for `offer` and `poll`, linear time for `contains(Object)` and constant time for `peek`.
- `peek` and `poll` return null on an empty `PriorityQueue`, while adding a null element throws a `NullPointerException`.
- The two-heap snippet printed the medians `[5.0, 10.0, 5.0, 4.0]` for the stream 5, 15, 1, 3.
- Redis offers an approximated LFU eviction mode that evicts rarely used keys, with a decay period of one minute by default.
- A token bucket rate limiter denies requests when the bucket is empty, until more tokens refill, and its tokens stop at the capacity.
- A fixed window rate limiter is susceptible to boundary bursts, and a sliding window log avoids them at a memory cost that grows with request volume.

# Coroutines

## Suspending functions and continuations
<!-- bullets: 4.3.a -->

The most basic building block of coroutines is the suspending function (`kotlin-docs-coroutines-basics#suspending-functions`).

A suspending function allows a running operation to pause and resume later without affecting the structure of your code (`kotlin-docs-coroutines-basics#suspending-functions`).

To declare a suspending function, use the `suspend` keyword (`kotlin-docs-coroutines-basics#suspending-functions`).

You can only call a suspending function from another suspending function (`kotlin-docs-coroutines-basics#suspending-functions`).

To call suspending functions at the entry point of a Kotlin application, mark the `main()` function with the `suspend` keyword (`kotlin-docs-coroutines-basics#suspending-functions`).

While the `suspend` keyword is part of the core Kotlin language, most coroutine features are available through the `kotlinx.coroutines` library (`kotlin-docs-coroutines-basics#suspending-functions`).

A suspending function is different from non-suspending functions by potentially having zero or more suspension points (`kotlin-spec-coroutines#suspending-functions`).

Non-suspending functions may not call suspending functions directly, as they do not support suspension points (`kotlin-spec-coroutines#suspending-functions`).

Suspending functions may call non-suspending functions without any limitations; such calls do not create suspension points (`kotlin-spec-coroutines#suspending-functions`).

This restriction is also known as “function colouring” (`kotlin-spec-coroutines#suspending-functions`).

Suspending functions may pause only at suspension points, so they cannot be paused at an arbitrary execution point (`kotlin-spec-coroutines#suspending-functions`).

Constructors cannot be marked as suspending (`kotlin-spec-coroutines#suspending-functions`).

Property getters and setters cannot be marked as suspending (`kotlin-spec-coroutines#suspending-functions`).

Each suspendable function goes through a transformation from normally invoked function to continuation passing style (CPS) (`kotlin-spec-coroutines#continuation-passing-style`).

The CPS transformation generates a new function with an additional parameter of type `kotlin.coroutines.Continuation<T>` and the return type changed to `kotlin.Any?` (`kotlin-spec-coroutines#continuation-passing-style`).

The calling convention of such a function is different from regular functions, as a suspendable function may either suspend or return (`kotlin-spec-coroutines#continuation-passing-style`).

If the function returns a result, it is returned directly from the function as normal (`kotlin-spec-coroutines#continuation-passing-style`).

If the function suspends, it returns a special marker value, `COROUTINE_SUSPENDED`, to signal its suspended state (`kotlin-spec-coroutines#continuation-passing-style`).

Kotlin implements suspendable functions as state machines, since such implementation does not require specific runtime support (`kotlin-spec-coroutines#coroutine-state-machine`).

This dictates the explicit `suspend` marking (function colouring) of Kotlin coroutines: the compiler has to know which function can potentially suspend, to turn it into a state machine (`kotlin-spec-coroutines#coroutine-state-machine`).

Each suspendable lambda is compiled to a continuation class, with fields representing its local variables, and an integer field for current state in the state machine (`kotlin-spec-coroutines#coroutine-state-machine`).

`kotlin.coroutines.Continuation<T>` is the main supertype of all coroutines and represents the basis upon which the coroutine machinery is implemented (`kotlin-spec-coroutines#kotlin.coroutines.continuationt`).

Every suspending function is associated with a generated `Continuation` subtype, which handles the suspension implementation (`kotlin-spec-coroutines#kotlin.coroutines.continuationt`).

The return type of the suspending function becomes the type parameter `T` of the continuation (`kotlin-spec-coroutines#kotlin.coroutines.continuationt`).

The `resumeWith` function is used to propagate the results in between suspension points (`kotlin-spec-coroutines#kotlin.coroutines.continuationt`).

The `resumeWith` function is called with the result (or exception) of the last suspension point and resumes the coroutine execution (`kotlin-spec-coroutines#kotlin.coroutines.continuationt`).

The snippet uses only the standard library. A suspending function stores its continuation, the main function resumes it later, and reflection lists the parameters of the generated `greet` method.

```kotlin snippet=m04-l03/ContinuationDemo.kt
import kotlin.coroutines.Continuation
import kotlin.coroutines.EmptyCoroutineContext
import kotlin.coroutines.resume
import kotlin.coroutines.startCoroutine
import kotlin.coroutines.suspendCoroutine

var saved: Continuation<String>? = null

suspend fun awaitName(): String = suspendCoroutine { continuation -> saved = continuation }

suspend fun greet(): String {
    println("before suspension")
    val name = awaitName()
    println("after suspension")
    return "hello $name"
}

fun main() {
    val completion = Continuation<String>(EmptyCoroutineContext) { result ->
        println("result: ${result.getOrNull()}")
    }
    ::greet.startCoroutine(completion)
    println("main continues")
    saved?.resume("Kotlin")
    val generated = Class.forName("ContinuationDemoKt").declaredMethods.first { it.name == "greet" }
    println(generated.parameterTypes.map { it.simpleName })
    println(generated.returnType.simpleName)
}
```

The snippet prints `before suspension` and `main continues`, because `greet` suspends in `awaitName` and returns control to `main`.

After `saved?.resume("Kotlin")`, it prints `after suspension` and then `result: hello Kotlin`, from the completion continuation.

The generated `greet` method has the parameter types `[Continuation]` and the return type `Object`, as the CPS transformation adds a `Continuation` parameter and changes the return type to `Any?`.

## Structured concurrency, Job, SupervisorJob and cancellation
<!-- bullets: 4.3.b -->

Kotlin coroutines rely on a principle called structured concurrency to manage coroutines as groups (`kotlin-docs-coroutines-basics#coroutine-scope-and-structured-concurrency`).

According to this principle, coroutines form a tree hierarchy of parent and child tasks with linked lifecycles (`kotlin-docs-coroutines-basics#coroutine-scope-and-structured-concurrency`).

A parent coroutine waits for its children to complete before it finishes (`kotlin-docs-coroutines-basics#coroutine-scope-and-structured-concurrency`).

If the parent coroutine fails or gets canceled, all its child coroutines are recursively canceled too (`kotlin-docs-coroutines-basics#coroutine-scope-and-structured-concurrency`).

To maintain structured concurrency, new coroutines can only be launched in a `CoroutineScope` that defines and manages their lifecycle (`kotlin-docs-coroutines-basics#coroutine-scope-and-structured-concurrency`).

The `CoroutineScope` includes the coroutine context, which defines the dispatcher and other execution properties (`kotlin-docs-coroutines-basics#coroutine-scope-and-structured-concurrency`).

When you start a coroutine inside another coroutine, it automatically becomes a child of its parent scope (`kotlin-docs-coroutines-basics#coroutine-scope-and-structured-concurrency`).

`CoroutineScope.launch()` starts a new coroutine without blocking the rest of the scope, inside an existing coroutine scope (`kotlin-docs-coroutines-basics#coroutinescope-launch`).

The `CoroutineScope.launch()` function returns a `Job` handle (`kotlin-docs-coroutines-basics#coroutinescope-launch`).

`CoroutineScope.async()` starts a concurrent computation inside an existing coroutine scope and returns a `Deferred` handle that represents an eventual result (`kotlin-docs-coroutines-basics#coroutinescope-async`).

Use the `.await()` function to suspend the code until the result is ready (`kotlin-docs-coroutines-basics#coroutinescope-async`).

Since `async` is a `CoroutineScope` extension, the `coroutineScope` function provides the necessary scope (`kotlin-docs-composing-suspending-functions#structured-concurrency-with-async`).

If something goes wrong inside a function that starts `async` coroutines in a `coroutineScope` and it throws an exception, all the coroutines that were launched in its scope will be cancelled (`kotlin-docs-composing-suspending-functions#structured-concurrency-with-async`).

Coroutine builders come in two flavors: propagating exceptions automatically (`launch`) or exposing them to users (`async` and `produce`) (`kotlin-docs-exception-handling#exception-propagation`).

For a root coroutine, `launch` treats exceptions as uncaught exceptions, similar to Java's `Thread.uncaughtExceptionHandler` (`kotlin-docs-exception-handling#exception-propagation`).

For a root coroutine, `async` relies on the user to consume the final exception, for example via `await` or `receive` (`kotlin-docs-exception-handling#exception-propagation`).

`GlobalScope` is a delicate API that can backfire in non-trivial ways (`kotlin-docs-exception-handling#exception-propagation`).

A `SupervisorJob` is similar to a regular `Job` with the only exception that a failure or cancellation of a child does not propagate to the supervisor job or its other children (`kotlin-docs-exception-handling#supervision-job`).

Children of a supervisor job can fail independently of each other (`coroutines-api-supervisor-job#content`).

A failure of a child job that was created using `launch` can be handled via `CoroutineExceptionHandler` in the context (`coroutines-api-supervisor-job#content`).

A failure of a child job that was created using `async` can be handled via `Deferred.await` on the resulting deferred value (`coroutines-api-supervisor-job#content`).

If a parent job is specified, then the supervisor job becomes a child job of the parent and is cancelled when the parent fails or is cancelled (`coroutines-api-supervisor-job#content`).

All of the supervisor's children are cancelled in this case, too (`coroutines-api-supervisor-job#content`).

`supervisorScope` propagates the cancellation in one direction only and cancels all its children only if it failed itself (`kotlin-docs-exception-handling#supervision-scope`).

`supervisorScope` also waits for all children before completion just like `coroutineScope` does (`kotlin-docs-exception-handling#supervision-scope`).

In Kotlin, coroutine cancellation is cooperative (`kotlin-docs-cancellation-and-timeouts#cancellation-is-cooperative`).

Coroutines react to cancellation only when they cooperate by suspending or checking for cancellation explicitly (`kotlin-docs-cancellation-and-timeouts#cancellation-is-cooperative`).

Structured concurrency ensures that canceling a coroutine also cancels all of its children (`kotlin-docs-cancellation-and-timeouts#cancellation-propagation`).

Usually, a job is created in the active state (it is created and started) (`coroutines-api-job#job-states`).

Coroutine builders that provide an optional start parameter create a coroutine in the new state when this parameter is set to `CoroutineStart.LAZY` (`coroutines-api-job#job-states`).

Failure of an active job with an exception transitions the state to the cancelling state (`coroutines-api-job#job-states`).

A job can be cancelled at any time with the `cancel` function that forces it to transition to the cancelling state immediately (`coroutines-api-job#job-states`).

The job becomes cancelled when it finishes executing its work and all its children complete (`coroutines-api-job#job-states`).

Completion of an active coroutine's body or a call to `CompletableJob.complete` transitions the job to the completing state (`coroutines-api-job#job-states`).

For an outside observer, a completing job is still active, while internally it is waiting for its children (`coroutines-api-job#job-states`).

In the cancelling state, `isActive` is false, `isCompleted` is false and `isCancelled` is true (`coroutines-api-job#job-states`).

:::esquema{kind=tabla title="Job states"}
| State | isActive | isCompleted | isCancelled | Source |
|---|---|---|---|---|
| New (optional initial state) | false | false | false | `coroutines-api-job#job-states` |
| Active (default initial state) | true | false | false | `coroutines-api-job#job-states` |
| Completing (transient state) | true | false | false | `coroutines-api-job#job-states` |
| Cancelling (transient state) | false | false | true | `coroutines-api-job#job-states` |
| Cancelled (final state) | false | true | true | `coroutines-api-job#job-states` |
| Completed (final state) | false | true | false | `coroutines-api-job#job-states` |
:::

## Dispatchers, context switching and blocking calls
<!-- bullets: 4.3.c -->

The coroutine context includes a coroutine dispatcher that determines what thread or threads the corresponding coroutine uses for its execution (`kotlin-docs-coroutine-context-and-dispatchers#dispatchers-and-threads`).

The coroutine dispatcher can confine coroutine execution to a specific thread, dispatch it to a thread pool, or let it run unconfined (`kotlin-docs-coroutine-context-and-dispatchers#dispatchers-and-threads`).

When `launch { ... }` is used without parameters, it inherits the context (and thus dispatcher) from the `CoroutineScope` it is being launched from (`kotlin-docs-coroutine-context-and-dispatchers#dispatchers-and-threads`).

`Dispatchers.Default` uses a shared background pool of threads (`kotlin-docs-coroutine-context-and-dispatchers#dispatchers-and-threads`).

If the coroutine context doesn't include a dispatcher, coroutine builders use `Dispatchers.Default` (`kotlin-docs-coroutines-basics#coroutine-dispatchers`).

`Dispatchers.Default` is an ideal choice for CPU-intensive operations like data processing (`kotlin-docs-coroutines-basics#coroutine-dispatchers`).

`Dispatchers.IO` is designed for offloading blocking IO tasks to a shared pool of threads (`coroutines-api-dispatchers#properties`).

The default `Dispatchers.IO` pool size is 64 (`coroutines-api-dispatchers#properties`).

`Dispatchers.Main` is confined to the Main thread operating with UI objects (`coroutines-api-dispatchers#properties`).

`Dispatchers.Unconfined` is not confined to any specific thread (`coroutines-api-dispatchers#properties`).

A dedicated thread created by `newSingleThreadContext` is a very expensive resource (`kotlin-docs-coroutine-context-and-dispatchers#dispatchers-and-threads`).

Even though coroutines can suspend and resume on different threads, values written before the coroutine suspends are still guaranteed to be available within the same coroutine when it resumes (`kotlin-docs-coroutines-basics#coroutine-dispatchers`).

`withContext` calls the specified suspending block with an updated coroutine context, suspends until it completes, and returns the result (`coroutines-api-with-context#content`).

If you specify a different `CoroutineDispatcher` in `withContext`, extra dispatches are required: the block is scheduled on the new dispatcher, and once it finishes, execution returns to the original dispatcher (`kotlin-docs-coroutine-context-and-dispatchers#jumping-between-threads`).

It is incorrect to pass a `Job` element to `withContext`, unless it is `NonCancellable`, as this breaks structured concurrency (`coroutines-api-with-context#content`).

On the JVM, some blocking functions, such as `Thread.sleep()` or `BlockingQueue.take()`, can block the current thread (`kotlin-docs-cancellation-and-timeouts#interrupt-blocking-code-when-coroutines-are-canceled`).

When you call blocking functions from a coroutine, cancellation doesn't interrupt the thread (`kotlin-docs-cancellation-and-timeouts#interrupt-blocking-code-when-coroutines-are-canceled`).

To interrupt the thread when canceling a coroutine, wrap the blocking code in the `runInterruptible()` function (`kotlin-docs-cancellation-and-timeouts#interrupt-blocking-code-when-coroutines-are-canceled`).

## Flow, StateFlow, SharedFlow and backpressure
<!-- bullets: 4.3.d -->

To create a cold flow, use the `flow()` builder function (`kotlin-docs-flow#create-a-cold-flow`).

The `flow()` builder function returns a `Flow<T>`, but it doesn't start executing its block (`kotlin-docs-flow#create-a-cold-flow`).

A cold flow defines how to produce values, but it only starts producing values when you collect it (`kotlin-docs-flow#create-a-cold-flow`).

`flowOf()` creates a flow from provided values (`kotlin-docs-flow#create-a-cold-flow`).

`.asFlow()` converts an existing iterable, such as a range, into a flow (`kotlin-docs-flow#create-a-cold-flow`).

Intermediate operators apply operations to an upstream flow and return a new downstream flow (`kotlin-docs-flow#intermediate-flow-operators`).

Intermediate operators are cold, so the returned flow doesn't start processing values until it's collected, even when the upstream flow is hot (`kotlin-docs-flow#intermediate-flow-operators`).

Hot flows are shared streams that emit values independently of collectors (`kotlin-docs-flow#hot-flows`).

Hot flows keep emitting values even when no collector is active, and multiple collectors can collect the same emissions from an already active stream instead of starting a new execution (`kotlin-docs-flow#hot-flows`).

A collector of a hot flow is called a subscriber (`kotlin-docs-flow#hot-flows`).

`SharedFlow` broadcasts values to multiple subscribers (`kotlin-docs-flow#hot-flows`).

`StateFlow` is a specialized `SharedFlow` that always holds the latest state value (`kotlin-docs-flow#hot-flows`).

You can create a `SharedFlow` with the `MutableSharedFlow()` function (`kotlin-docs-flow#create-a-sharedflow`).

To set how many previous emissions a new subscriber receives, use the `replay` parameter in `MutableSharedFlow()` (`kotlin-docs-flow#create-a-sharedflow`).

Collecting a hot flow doesn't complete by itself, so you must cancel the collecting coroutines when you no longer need them (`kotlin-docs-flow#create-a-sharedflow`).

A shared flow keeps a specific number of the most recent values in its replay cache (`coroutines-api-shared-flow#replay-cache-and-buffer`).

Every new subscriber first gets the values from the replay cache and then gets new emitted values (`coroutines-api-shared-flow#replay-cache-and-buffer`).

Additional buffer capacity beyond replay can be reserved using the `extraBufferCapacity` parameter (`coroutines-api-shared-flow#replay-cache-and-buffer`).

A shared flow with a buffer can be configured with the `onBufferOverflow` parameter to avoid suspension of emitters on buffer overflow (`coroutines-api-shared-flow#replay-cache-and-buffer`).

In the absence of subscribers, only the most recent replay values are stored and the buffer overflow behavior is never triggered and has no effect (`coroutines-api-shared-flow#replay-cache-and-buffer`).

`StateFlow` is a hot flow that stores a single state value and emits updates when that value is replaced with a new one (`kotlin-docs-flow#create-a-stateflow`).

New `StateFlow` subscribers receive the current value as soon as they start collecting, and then receive new values each time the state updates (`kotlin-docs-flow#create-a-stateflow`).

To create a `StateFlow`, use the `MutableStateFlow()` function with an initial value (`kotlin-docs-flow#create-a-stateflow`).

State flow never completes (`coroutines-api-state-flow#content`).

Updates to the value of a state flow are always conflated, so a slow collector skips fast updates but always collects the most recently emitted value (`coroutines-api-state-flow#content`).

The current value of a state flow can be retrieved via the `value` property (`coroutines-api-state-flow#content`).

Normally, flows are sequential, which means that the code of all operators is executed in the same coroutine (`coroutines-api-flow-buffer#content`).

The `buffer` operator creates a separate coroutine during execution for the flow it applies to (`coroutines-api-flow-buffer#content`).

`buffer` buffers flow emissions via a channel of a specified capacity and runs the collector in a separate coroutine (`coroutines-api-flow-buffer#content`).

By default, the emitter is suspended when the buffer overflows, to let the collector catch up (`coroutines-api-flow-buffer#buffer-overflow`).

With the `DROP_OLDEST` strategy, the oldest value in the buffer is dropped and the latest emitted value is added to the buffer (`coroutines-api-flow-buffer#buffer-overflow`).

## Coroutines, JVM threads and virtual threads
<!-- bullets: 4.3.e -->

A thread is managed by the operating system (`kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads`).

When you create a thread, the operating system allocates memory for its stack and uses the kernel to switch between threads (`kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads`).

Each thread usually needs a few megabytes of memory, and typically the JVM can only handle a few thousand threads at once (`kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads`).

A coroutine isn't bound to a specific thread (`kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads`).

A coroutine can suspend on one thread and resume on another, so many coroutines can share the same thread pool (`kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads`).

When a coroutine suspends, the thread isn't blocked and remains free to run other tasks (`kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads`).

Coroutines are much lighter than threads and allow running millions of them in one process without exhausting system resources (`kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads`).

For 50,000 threads, memory can be up to 100 GB, compared to roughly 500 MB for the same number of coroutines (`kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads`).

JEP 444 introduces virtual threads to the Java Platform (`jep-444#Summary`).

Virtual threads are lightweight threads that dramatically reduce the effort of writing, maintaining, and observing high-throughput concurrent applications (`jep-444#Summary`).

:::esquema{kind=tabla title="Threads, coroutines and virtual threads"}
| Concept | What the sources state | Source |
|---|---|---|
| JVM thread | Managed by the operating system, which allocates memory for its stack | `kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads` |
| Kotlin coroutine | Not bound to a specific thread, and it can suspend on one thread and resume on another | `kotlin-docs-coroutines-basics#comparing-coroutines-and-jvm-threads` |
| Java virtual thread | A lightweight thread introduced to the Java Platform | `jep-444#Summary` |
:::

## Key points

- A suspending function can only be called from another suspending function, and a non-suspending function cannot call one directly.
- The compiler turns a suspendable function into continuation passing style, with an additional `Continuation<T>` parameter and the return type `Any?`, and implements it as a state machine.
- A parent coroutine waits for its children, and a failed or canceled parent cancels all of them recursively.
- `launch` returns a `Job`, `async` returns a `Deferred`, and for a root coroutine `launch` treats exceptions as uncaught while `async` relies on `await`.
- A failure of a child of a `SupervisorJob` does not propagate to the supervisor or its other children, and `supervisorScope` cancels its children only if it failed itself.
- Cancellation is cooperative, and a job in the cancelling state has `isActive` false, `isCompleted` false and `isCancelled` true.
- A dispatcher decides the threads of a coroutine, builders use `Dispatchers.Default` when the context has none, and `withContext` with a different dispatcher dispatches the block there and back.
- Cancellation does not interrupt a blocking JVM call unless the code is wrapped in `runInterruptible()`.
- A cold flow starts producing values only when collected, and a hot flow emits independently of collectors.
- A `StateFlow` holds the latest value, never completes and conflates updates, and a `SharedFlow` replays a configured number of values.
- The `buffer` operator runs the upstream in a separate coroutine, and by default the emitter is suspended on buffer overflow.
- A coroutine is not bound to a thread, and when it suspends the thread stays free.

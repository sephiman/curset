# Distributed transactions without 2PC

## The dual-write problem
<!-- bullets: 8.3.a -->

:::judgement{source="Chris Richardson, Pattern: Transactional outbox, microservices.io" ref="microservices-io-transactional-outbox#context"}
According to Chris Richardson, a service command typically needs to create, update or delete aggregates in the database and send messages or events to a message broker. He states that the command must atomically update the database and send messages to avoid data inconsistencies and bugs.
:::

:::judgement{source="Chris Richardson, Pattern: Transactional outbox, microservices.io" ref="microservices-io-transactional-outbox#context"}
According to Chris Richardson, without two-phase commit, sending a message in the middle of a transaction is not reliable, because there is no guarantee that the transaction will commit. He adds that if a service sends a message after committing the transaction, there is no guarantee that it will not crash before sending the message.
:::

:::judgement{source="Chris Richardson, Pattern: Transactional outbox, microservices.io" ref="microservices-io-transactional-outbox#forces"}
According to Chris Richardson, a traditional distributed transaction is not an option here, because the database or the message broker might not support two-phase commit, and it is often undesirable to couple the service to both.
:::

## The transactional outbox pattern
<!-- bullets: 8.3.b -->

:::judgement{source="Chris Richardson, Pattern: Transactional outbox, microservices.io" ref="microservices-io-transactional-outbox#solution"}
According to Chris Richardson, the service that sends the message first stores the message in the database as part of the transaction that updates the business entities, and a separate process, the message relay, then sends the messages to the message broker.
:::

:::judgement{source="Chris Richardson, Pattern: Transactional outbox, microservices.io" ref="microservices-io-transactional-outbox#result-context"}
According to Chris Richardson, the message relay might publish a message more than once, for example by crashing after publishing a message but before recording that it has done so, so a message consumer must be idempotent.
:::

The outbox pattern is a way to safely and reliably exchange data between multiple (micro) services (`debezium-outbox-event-router#dbz-doc-main`).

To implement the outbox pattern in a Debezium application, a connector is configured to capture changes in an outbox table and to apply the Debezium outbox event router single message transformation (`debezium-outbox-event-router#dbz-doc-main`).

A connector can capture changes in more than one outbox table only if each outbox table has the same structure (`debezium-outbox-event-router#dbz-doc-main`).

The outbox event router SMT is not compatible with the MongoDB connector (`debezium-outbox-event-router#dbz-doc-main`).

To configure a Debezium connector to support the outbox pattern, the `outbox.EventRouter` SMT is configured (`debezium-outbox-event-router#basic-outbox-configuration`).

The default outbox table has the columns `id`, `aggregatetype`, `aggregateid`, `type` and `payload` (`debezium-outbox-event-router#basic-outbox-table`).

:::esquema{kind=tabla title="Default outbox table columns of the Debezium outbox event router"}
| Column | Effect | Source |
|---|---|---|
| `id` | Contains the unique ID of the event, which is a header in an outbox message and can be used to remove duplicate messages | `debezium-outbox-event-router#basic-outbox-table` |
| `aggregatetype` | Contains a value that the SMT appends to the name of the topic to which the connector emits an outbox message | `debezium-outbox-event-router#basic-outbox-table` |
| `aggregateid` | Contains the event key, which the SMT uses as the key in the emitted outbox message | `debezium-outbox-event-router#basic-outbox-table` |
| `payload` | A representation of the outbox change event, in JSON by default | `debezium-outbox-event-router#basic-outbox-table` |
:::

The `aggregateid` value as the message key is important for maintaining correct order in Kafka partitions (`debezium-outbox-event-router#basic-outbox-table`).

By default, the Kafka message value is solely comprised of the payload value (`debezium-outbox-event-router#basic-outbox-table`).

In a default configuration, `route.by.field` is set to `aggregatetype` and `route.topic.replacement` is set to `outbox.event.${routedByValue}` (`debezium-outbox-event-router#basic-outbox-table`).

A record whose `aggregatetype` is `customers` is emitted to the `outbox.event.customers` topic (`debezium-outbox-event-router#basic-outbox-table`).

## Polling the outbox with SKIP LOCKED
<!-- bullets: 8.3.b -->

With `SKIP LOCKED`, any selected rows that cannot be immediately locked are skipped (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

To prevent an operation from waiting for other transactions to commit, `NOWAIT` or `SKIP LOCKED` is used (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

With `NOWAIT`, the statement reports an error, rather than waiting, if a selected row cannot be locked immediately (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

Skipping locked rows provides an inconsistent view of the data, so it is not suitable for general purpose work (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

Skipping locked rows can be used to avoid lock contention with multiple consumers accessing a queue-like table (`pg-sql-select#SQL-FOR-UPDATE-SHARE`).

```sql
SELECT id, aggregatetype, payload
FROM outbox
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
```

`FOR UPDATE` prevents the rows from being locked, modified or deleted by other transactions until the current transaction ends (`pg-explicit-locking#LOCKING-ROWS`).

Row-level locks are released at transaction end or during savepoint rollback (`pg-explicit-locking#LOCKING-ROWS`).

`SELECT FOR UPDATE` modifies the selected rows to mark them locked, and so results in disk writes (`pg-explicit-locking#LOCKING-ROWS`).

## Change data capture with Debezium
<!-- bullets: 8.3.b -->

PostgreSQL's logical decoding allows the extraction of the changes that were committed to the transaction log and their processing with the help of an output plug-in (`debezium-postgresql#postgresql-overview`).

`pgoutput` is the standard logical decoding output plug-in in PostgreSQL 10+ (`debezium-postgresql#postgresql-overview`).

`decoderbufs` is a decoding plug-in based on Protobuf and maintained by the Debezium community (`debezium-postgresql#postgresql-overview`).

The PostgreSQL connector produces a change event for every row-level insert, update and delete operation that was captured, and sends the records for each table to a separate Kafka topic (`debezium-postgresql#postgresql-overview`).

When it first connects to a database, the PostgreSQL connector performs a consistent snapshot of each of the database schemas (`debezium-postgresql#postgresql-overview`).

PostgreSQL normally purges write-ahead log segments after some period of time (`debezium-postgresql#postgresql-overview`).

The connector records the WAL position for each event (`debezium-postgresql#postgresql-overview`).

If the connector stops for any reason, upon restart it continues reading the WAL where it last left off (`debezium-postgresql#postgresql-overview`).

If the connector stops during a snapshot, it begins a new snapshot when it restarts (`debezium-postgresql#postgresql-overview`).

Logical decoding does not support DDL changes (`debezium-postgresql#postgresql-overview`).

The Kafka Connect process asynchronously writes the change event records in the same order in which they were generated to the appropriate Kafka topic (`debezium-postgresql#postgresql-streaming-changes`).

For the PostgreSQL connector, the LSN recorded in each change event is the offset (`debezium-postgresql#postgresql-streaming-changes`).

When the connector restarts, it asks the PostgreSQL server to send the events starting just after the last recorded position (`debezium-postgresql#postgresql-streaming-changes`).

:::esquema{kind=tabla title="Two ways to read an outbox table"}
| Reader | What the cited source says | Source |
|---|---|---|
| Polling with `SKIP LOCKED` | Skipped rows avoid lock contention with multiple consumers of a queue-like table | `pg-sql-select#SQL-FOR-UPDATE-SHARE` |
| Debezium change data capture | The connector continues reading the WAL where it last left off after a restart | `debezium-postgresql#postgresql-overview` |
:::

## Sagas: orchestration, choreography and compensating transactions
<!-- bullets: 8.3.c -->

:::judgement{source="Chris Richardson, Pattern: Saga, microservices.io" ref="microservices-io-saga#solution"}
According to Chris Richardson, a saga is a reliably coordinated sequence of local transactions. If a local transaction fails because it violates a business rule, the changes made by the completed steps are undone by compensating transactions.
:::

:::judgement{source="Chris Richardson, Pattern: Saga, microservices.io" ref="microservices-io-saga#solution"}
According to Chris Richardson, there are two ways of coordinating sagas. In choreography, each local transaction publishes domain events that trigger local transactions in other services. In orchestration, an orchestrator tells the participants what local transactions to execute.
:::

:::judgement{source="Chris Richardson, Pattern: Saga, microservices.io" ref="microservices-io-saga#resulting-context"}
According to Chris Richardson, a saga lacks automatic rollback, so a developer must design compensating transactions that explicitly undo earlier changes. He adds that it lacks isolation, so concurrent sagas can cause data anomalies and a developer must use countermeasures, which are design techniques that implement isolation.
:::

## Sagas and workflows in Axon Framework
<!-- bullets: 8.3.c -->

In Axon Framework, a saga coordinates a process through event handlers and persisted fields (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

Association values route events to the right saga instance (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

Flags, counters and deadline identifiers describe where the saga process is and what it should do next (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

:::esquema{kind=tabla title="Sagas and workflows in Axon Framework"}
| Concern | Saga | Workflow | Source |
|---|---|---|---|
| Compensation | Store enough state to decide which effects must be undone in later handlers | Express compensation around the relevant steps, preserving the same guards and failure handling | `axon-migration-sagas-to-workflows#sagas-and-workflows` |
| Timeouts | Schedule a deadline, store its identifier, handle expiry, and cancel it on success | Configure a timeout on the step and branch on its outcome | `axon-migration-sagas-to-workflows#sagas-and-workflows` |
| Retries | Persist an attempt counter and arrange the next attempt, often through a deadline | Configure a step retry policy and backoff, or model a business retry loop explicitly | `axon-migration-sagas-to-workflows#sagas-and-workflows` |
:::

In a workflow, the body must remain deterministic during replay, and commands, queries and external side effects go inside steps (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

Workflow primitives do not infer business intent or make external effects exactly once (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

A retry can repeat an external call, so a stable idempotency key is used when that call must tolerate repetition (`axon-migration-sagas-to-workflows#sagas-and-workflows`).

The consequence of token stealing in an Axon streaming event processor is that an event may be handled twice, or more (`axon-event-processors-streaming#_what_are_the_consequences_of_token_stealing`).

When an event handling task cannot be rolled back nor performed in an idempotent fashion, compensating actions are the way out (`axon-event-processors-streaming#_what_are_the_consequences_of_token_stealing`).

If a rollback is out of the question for an event handling task, Axon strongly recommends making the task idempotent (`axon-event-processors-streaming#_what_are_the_consequences_of_token_stealing`).

Axon recommends storing tokens and projections in the same database, so that a rollback ensures the change is not persisted (`axon-event-processors-streaming#_what_are_the_consequences_of_token_stealing`).

## Key points

- The Debezium outbox event router uses `aggregateid` as the message key, appends `aggregatetype` to the topic name, and carries `id` as a header.
- `SKIP LOCKED` skips rows that cannot be locked immediately, which avoids lock contention among consumers of a queue-like table but gives an inconsistent view of the data.
- After a restart, the Debezium PostgreSQL connector continues reading the WAL where it last left off.
- Logical decoding does not support DDL changes.
- In Axon Framework, a saga coordinates a process through event handlers and persisted fields, and association values route events to the right saga instance.
- In Axon Framework, a retry can repeat an external call, so a stable idempotency key is used when the call must tolerate repetition.
- When an event handling task cannot be rolled back nor made idempotent, compensating actions are the way out.

# Application architecture and modular evolution

## Architecture styles in the books
<!-- bullets: 1.3.a -->

Hexagonal architecture puts the application inside and connects it to everything outside through ports, with one adapter for each outside technology. The aim is to keep code that belongs inside the application from leaking into the outside parts. The same port can be served by several adapters, such as a test harness, a batch driver or an in-memory database.

:::judgement{source="Alistair Cockburn, Hexagonal (Ports & Adapters) Architecture" ref="cockburn-hexagonal-architecture#a195fd4ba8fc05c14272b6c02cb8dd80"}
According to Alistair Cockburn, the application communicates over ports with external agencies, and for each external device an adapter converts the port's API to the signals that device needs and back. According to him, a graphical user interface, an automated test harness, an SQL adapter and an in-memory mock database are adapters that fit such ports, and the intent is that the application can be driven by users, programs, tests or batch scripts and developed and tested in isolation from its run-time devices and databases.
:::

:::judgement{source="Alistair Cockburn, Hexagonal (Ports & Adapters) Architecture" ref="cockburn-hexagonal-architecture#a195fd4ba8fc05c14272b6c02cb8dd80"}
According to Alistair Cockburn, one of the great bugaboos of software applications has been the infiltration of business logic into the user interface code. He says such a system cannot neatly be tested with automated test suites, because part of the logic needing to be tested depends on oft-changing visual details such as field size and button placement. He states the rule to obey as: code pertaining to the inside part should not leak into the outside part.
:::

:::judgement{source="Alistair Cockburn, Hexagonal (Ports & Adapters) Architecture" ref="cockburn-hexagonal-architecture#a195fd4ba8fc05c14272b6c02cb8dd80"}
According to Alistair Cockburn, a port identifies a purposeful conversation, and there will typically be multiple adapters for any one port, for example a test harness, a batch driver, an http interface, a mock in-memory database or a real database. He says the hexagon is not a hexagon because the number six is important, but to give the people doing the drawing room to insert ports and adapters as they need.
:::

The snippet runs one `Discounter` against two adapters of a `RateSource` port, a constant rate and an in-memory table.

```java snippet=m01-l03/PortsAndAdapters.java
import java.util.Map;

public class PortsAndAdapters {
    interface RateSource {
        int percentFor(int amount);
    }

    static class Discounter {
        private final RateSource rates;

        Discounter(RateSource rates) {
            this.rates = rates;
        }

        int discount(int amount) {
            return amount * rates.percentFor(amount) / 100;
        }
    }

    public static void main(String[] args) {
        RateSource constantRate = amount -> 5;
        Map<Integer, Integer> table = Map.of(100, 5, 200, 5, 1000, 10);
        RateSource inMemoryTable = table::get;
        for (RateSource source : new RateSource[] {constantRate, inMemoryTable}) {
            Discounter application = new Discounter(source);
            System.out.println(application.discount(100) + " " + application.discount(200) + " " + application.discount(1000));
        }
    }
}
```

The program prints `5 10 50` with the constant rate and `5 10 100` with the in-memory table, and the `Discounter` class is the same in both runs.

## Modules and their boundaries in Spring Modulith
<!-- bullets: 1.3.b -->

Spring Modulith divides a Spring Boot application into application modules and checks that the modules stay out of each other's internals. A module exposes an API to the others and keeps the rest internal. Modules are meant to interact mainly through events.

In a Spring Boot application, an application module is a unit of functionality (`spring-modulith-fundamentals#modules`).

A module's API is made of the Spring bean instances it exposes to other modules and the application events it publishes, usually referred to as its provided interface (`spring-modulith-fundamentals#modules`).

A module's internal implementation components are not supposed to be accessed by other modules (`spring-modulith-fundamentals#modules`).

The main package is the one in which the main application class resides, and by default each direct sub-package of the main package is considered an application module package (`spring-modulith-fundamentals#modules.simple`).

By default, a module's base package is the API package and the only package that allows incoming dependencies from other modules (`spring-modulith-fundamentals#modules.named-interfaces`).

Any sub-package of a module's base package, such as `order.internal`, is considered an internal one, and code within it must not be referred to from other modules (`spring-modulith-fundamentals#modules.advanced`).

A public type in an internal package can still be referred to from other packages, and the Java compiler is not of much use to prevent these illegal references (`spring-modulith-fundamentals#modules.advanced`).

To expose an additional package to other modules, you annotate its `package-info.java` with `@NamedInterface` (`spring-modulith-fundamentals#modules.named-interfaces`).

With `@ApplicationModule(allowedDependencies = "order :: spi")` on the `inventory` module, its code may depend on the types in the `order.spi` named interface but not on `OrderManagement` (`spring-modulith-fundamentals#modules.named-interfaces`).

:::esquema{kind=tabla title="Module boundary declarations in Spring Modulith"}
| Declaration | What it states | Source |
|---|---|---|
| `@NamedInterface("spi")` on the `package-info.java` of `order.spi` | Code in other application modules is allowed to refer to the types of that package, and modules can name it in explicit dependency declarations | `spring-modulith-fundamentals#modules.named-interfaces` |
| `@ApplicationModule(allowedDependencies = "order")` on `inventory` | Code in `inventory` is only allowed to refer to code in the `order` module and to code not assigned to any module | `spring-modulith-fundamentals#modules.explicit-dependencies` |
| `@ApplicationModule(allowedDependencies = "order :: *")` on `inventory` | The module is allowed to refer to all explicitly declared named interfaces of `order` | `spring-modulith-fundamentals#modules.named-interfaces` |
| `@ApplicationModule(type = Type.OPEN)` on the `package-info.java` of `inventory` | Access to application module internal types from other modules is generally allowed | `spring-modulith-fundamentals#modules.open` |
:::

Open application modules are intended to be used primarily with code bases of existing projects gradually moving to the Spring Modulith recommended packaging structure (`spring-modulith-fundamentals#modules.open`).

In a fully-modularized application, using open application modules usually hints at sub-optimal modularization and packaging structures (`spring-modulith-fundamentals#modules.open`).

Calling `ApplicationModules.of(Application.class).verify()` rejects cycles at the module level, because the dependencies between modules have to form a directed acyclic graph (`spring-modulith-verification#page-title`).

The same verification rejects references to types that reside in application module internal packages, while dependencies into internals of open application modules are allowed (`spring-modulith-verification#page-title`).

Spring Modulith says that the primary means of interaction between application modules should be event publication and consumption (`spring-modulith-events#page-title`).

Spring Modulith provides `@ApplicationModuleListener` as a shortcut for the default way of integrating modules via events (`spring-modulith-events#aml`).

:::judgement{source="James Lewis and Martin Fowler, Microservices" ref="fowler-microservices#ComponentizationViaServices"}
According to James Lewis and Martin Fowler, remote calls are more expensive than in-process calls, so remote APIs need to be coarser-grained, which is often more awkward to use. They add that changing the allocation of responsibilities between components is harder when crossing process boundaries.
:::

:::judgement{source="James Lewis and Martin Fowler, Microservices" ref="fowler-microservices#SynchronousCallsConsideredHarmful"}
According to James Lewis and Martin Fowler, any time there are a number of synchronous calls between services, the downtime of the system becomes the product of the downtimes of the individual components.
:::

:::judgement{source="James Lewis and Martin Fowler, Microservices" ref="fowler-microservices#microservice-trade-offs"}
According to James Lewis and Martin Fowler, one reasonable argument is that you should not start with a microservices architecture, but begin with a monolith, keep it modular and split it into microservices once the monolith becomes a problem. They add that this advice is not ideal, since a good in-process interface is usually not a good service interface.
:::

:::judgement{source="Sam Newman, Building Microservices, 2nd edition, chapters 2 and 3"}
According to Sam Newman, chapter 2 of *Building Microservices* is titled "How to Model Microservices" and chapter 3 "Splitting the Monolith".
:::

## Architecture tests with ArchUnit
<!-- bullets: 1.3.c -->

An architecture test states a structural rule about packages and classes and evaluates it against the compiled classes. Layer and onion checks describe which part of the code may use which. Slice rules look for cycles between packages. A rule added to a grown project can be frozen, so that only new violations are reported.

ArchUnit offers a fluent, DSL-like API to express architectural rules such as "Services should only be accessed by Controllers" (`archunit-user-guide#_asserting_architectural_constraints`).

The entry point for specifying a rule is the class `ArchRuleDefinition` (`archunit-user-guide#_asserting_architectural_constraints`).

A rule of type `ArchRule` is evaluated against imported classes by calling `check(importedClasses)` (`archunit-user-guide#_asserting_architectural_constraints`).

The `ClassFileImporter` imports Java bytecode into Java code structures, for example with `importPackages("com.mycompany.myapp")` (`archunit-user-guide#_importing_classes`).

The JUnit support imports the classes named in `@AnalyzeClasses` and evaluates any rule annotated with `@ArchTest` against those classes (`archunit-user-guide#_using_junit`).

:::esquema{kind=tabla title="A layer check in ArchUnit"}
| Declaration | What it states | Source |
|---|---|---|
| `layer("Controller").definedBy("..controller..")` | The `Controller` layer is the classes in the `..controller..` package pattern | `archunit-user-guide#_layer_checks` |
| `whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")` | Only the `Controller` layer may access the `Service` layer | `archunit-user-guide#_layer_checks` |
| `whereLayer("Controller").mayNotBeAccessedByAnyLayer()` | No layer may access the `Controller` layer | `archunit-user-guide#_layer_checks` |
:::

The `Architectures` entry point provides a check for a layered architecture and for an onion architecture (`archunit-user-guide#_architectures`).

In an Onion Architecture, also known as Hexagonal Architecture or Ports and Adapters, domain packages and adapter packages can be defined (`archunit-user-guide#_onion_architecture`).

:::esquema{kind=tabla title="The onion check in ArchUnit"}
| Declaration | What it states | Source |
|---|---|---|
| `domainModels("com.myapp.domain.model..")` | The packages hold the domain entities | `archunit-user-guide#_onion_architecture` |
| `domainServices("com.myapp.domain.service..")` | The packages hold services that use the entities of the domain model packages | `archunit-user-guide#_onion_architecture` |
| `applicationServices("com.myapp.application..")` | The packages hold services and configuration to run the application and use cases | `archunit-user-guide#_onion_architecture` |
| `adapter("rest", "com.myapp.adapter.rest..")` | The package holds logic to connect to external systems or infrastructure | `archunit-user-guide#_onion_architecture` |
:::

In the onion check, the application packages can use the items of the domain package, but there must not be any dependency from the domain to the application packages (`archunit-user-guide#_onion_architecture`).

No adapter may depend on another adapter, and neither the domain nor the application packages may contain dependencies on any adapter package (`archunit-user-guide#_onion_architecture`).

Adapters can use both the items of the domain and the application packages (`archunit-user-guide#_onion_architecture`).

:::diagram{kind="structure" caption="Allowed dependency directions in the ArchUnit onion check"}
description: An adapter package may use the application packages and the domain packages, and the application packages may use the domain packages; no dependency points the other way.
adapter: adapter packages
application: application packages
domain: domain packages
adapter -> application: may use
adapter -> domain: may use
application -> domain: may use
:::

Slice rules sort classes into slices by package and make assertions on those slices (`archunit-user-guide#_slices`).

`SlicesRuleDefinition.slices().matching("..myapp.(*)..").should().beFreeOfCycles()` sorts classes by the first package after `myapp` and checks those slices for cyclic dependencies (`archunit-user-guide#_slices`).

`notDependOnEachOther()` checks that slices have no dependencies on each other (`archunit-user-guide#_slices`).

When rules are introduced in grown projects, there are often hundreds or even thousands of violations, way too many to fix immediately (`archunit-user-guide#_freezing_arch_rules`).

`FreezingArchRule` records all existing violations to a `ViolationStore`, and consecutive runs report only new violations and ignore known ones (`archunit-user-guide#_freezing_arch_rules`).

:::judgement{source="Building Evolutionary Architectures, authors' precis, section Fitness Functions" ref="bea-evolutionary-architecture-precis#fitness-functions"}
According to the authors of *Building Evolutionary Architectures*, an architectural fitness function provides an objective integrity assessment of some architectural characteristic or characteristics. According to them, fitness functions encompass existing engineering practices such as testing and metrics.
:::

:::judgement{source="Building Evolutionary Architectures, authors' precis, section Evolutionary Architecture" ref="bea-evolutionary-architecture-precis#evolutionary-architecture"}
According to the authors of *Building Evolutionary Architectures*, their framework is to identify the important dimensions, define fitness functions to ensure compliance, and use incremental change engineering practices such as deployment pipelines and other continuous delivery practices to automatically verify fitness.
:::

## Aggregates, value objects and domain events
<!-- bullets: 1.3.d -->

Spring Data treats the entities its repositories manage as aggregate roots. An aggregate root can publish domain events when it is saved or deleted. A record carries a fixed set of values and derives its equality from them.

Entities managed by Spring Data repositories are aggregate roots (`spring-data-commons-domain-events#page-title`).

In a Domain-Driven Design application, aggregate roots usually publish domain events (`spring-data-commons-domain-events#page-title`).

A method of an aggregate root annotated with `@DomainEvents` can return a single event instance or a collection, and it must not take any arguments (`spring-data-commons-domain-events#page-title`).

Spring Data calls that method every time `save(…)`, `saveAll(…)`, `delete(…)`, `deleteAll(…)`, `deleteAllInBatch(…)` or `deleteInBatch(…)` is called (`spring-data-commons-domain-events#page-title`).

`deleteById(…)` is absent from that list because an implementation might issue a query that deletes the instance, and then it never has access to the aggregate instance (`spring-data-commons-domain-events#page-title`).

After all events have been published, a method annotated with `@AfterDomainEventPublication` is called, and it can be used to clean the list of events to be published, among other uses (`spring-data-commons-domain-events#page-title`).

A record class is a shallowly immutable, transparent carrier for a fixed set of values, called the record components (`javadoc-record#class-record`).

The implicit declarations of `equals(Object)`, `hashCode()` and `toString()` are derived from all of the component fields (`javadoc-record#class-record`).

The primary reasons to provide an explicit declaration for the canonical constructor or the accessor methods are to validate constructor arguments, perform defensive copies on mutable components, or normalize groups of components (`javadoc-record#class-record`).

The snippet declares a `Money` record whose canonical constructor rejects a negative amount. It compares a record with a copy built from its components, and then builds a negative amount.

```java snippet=m01-l03/MoneyRecord.java
public class MoneyRecord {
    record Money(int cents, String currency) {
        Money {
            if (cents < 0) {
                throw new IllegalArgumentException("negative amount: " + cents);
            }
        }
    }

    public static void main(String[] args) {
        Money first = new Money(500, "EUR");
        Money copy = new Money(first.cents(), first.currency());
        System.out.println(first.equals(copy));
        System.out.println(first == copy);
        System.out.println(first);
        try {
            new Money(-1, "EUR");
        } catch (IllegalArgumentException rejected) {
            System.out.println(rejected.getMessage());
        }
    }
}
```

The program prints `true` for `equals` and `false` for `==` on the record and its copy.

Printing the record gives `Money[cents=500, currency=EUR]`, and the negative amount is rejected with the message `negative amount: -1`.

According to Vaughn Vernon, *Implementing Domain-Driven Design* treats value objects in chapter 6, domain events in chapter 8 and aggregates in chapter 10. According to Eric Evans, the building blocks of *Domain-Driven Design* are covered in part II.

## Domain events and transactions
<!-- bullets: 1.3.d -->

A domain event is published when the state transitions of an aggregate are done. Publishing it synchronously leaves the transactional semantics as they were, and triggered functionality can then fail the transaction. A listener decoupled from the transaction avoids that, but its event can be lost.

In the Spring Modulith example, `OrderManagement` uses Spring's `ApplicationEventPublisher` to publish a domain event once it has completed the state transitions on the primary aggregate (`spring-modulith-events#page-title`).

Event publication happens synchronously by default, so the transactional semantics of the overall arrangement stay the same as when the other module's bean is called directly (`spring-modulith-events#page-title`).

Triggered related functionality widens the transaction boundary and can cause the entire transaction to fail, even if the functionality that causes the error is not crucial (`spring-modulith-events#page-title`).

An `@Async` listener annotated with `@TransactionalEventListener` decouples the original transaction from the execution of the listener, which avoids the expansion of the original business transaction, but if the listener fails the event publication is lost, unless each listener implements its own safety net (`spring-modulith-events#page-title`).

The event publication registry writes an entry for each transactional event listener into an event publication log as part of the original business transaction (`spring-modulith-events#publication-registry`).

Each transactional event listener is wrapped into an aspect that marks its log entry as completed if the listener succeeds, and if the listener fails the entry stays untouched so that retry mechanisms can be deployed (`spring-modulith-events#publication-registry`).

The snippet uses Spring Framework's `ApplicationEventPublisher` and a recording transaction manager, without Spring Modulith. A `@Transactional` method publishes an `OrderCompleted` event to a plain `@EventListener` and to a `@TransactionalEventListener`.

```java snippet=m01-l03/OrderEvents.java
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.event.EventListener;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.TransactionDefinition;
import org.springframework.transaction.annotation.EnableTransactionManagement;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.event.TransactionalEventListener;
import org.springframework.transaction.support.AbstractPlatformTransactionManager;
import org.springframework.transaction.support.DefaultTransactionStatus;

public class OrderEvents {
    record OrderCompleted(long orderId) {}

    static class RecordingManager extends AbstractPlatformTransactionManager {
        protected Object doGetTransaction() { return new Object(); }
        protected void doBegin(Object tx, TransactionDefinition d) { System.out.println("begin"); }
        protected void doCommit(DefaultTransactionStatus s) { System.out.println("commit"); }
        protected void doRollback(DefaultTransactionStatus s) { System.out.println("rollback"); }
    }

    public static class OrderManagement {
        private final ApplicationEventPublisher events;
        OrderManagement(ApplicationEventPublisher events) { this.events = events; }

        @Transactional
        public void complete(long orderId) {
            System.out.println("publishing");
            events.publishEvent(new OrderCompleted(orderId));
            System.out.println("published");
        }
    }

    public static class InventoryManagement {
        @EventListener
        void immediately(OrderCompleted event) { System.out.println("listener, order " + event.orderId()); }

        @TransactionalEventListener
        void afterCommit(OrderCompleted event) { System.out.println("after-commit listener, order " + event.orderId()); }
    }

    @Configuration
    @EnableTransactionManagement
    static class Config {
        @Bean OrderManagement orders(ApplicationEventPublisher events) { return new OrderManagement(events); }
        @Bean InventoryManagement inventory() { return new InventoryManagement(); }
        @Bean PlatformTransactionManager transactionManager() { return new RecordingManager(); }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            context.getBean(OrderManagement.class).complete(7);
        }
    }
}
```

The program prints `begin`, `publishing`, `listener, order 7` and `published`, in that order, so the plain listener ran inside the `publishEvent` call.

`commit` follows, and `after-commit listener, order 7` comes last, after the commit.

:::diagram{kind="flow" caption="Output order of the OrderEvents program"}
description: begin, publishing, the plain listener, published, commit, and the after-commit listener last.
begin: begin
publishing: publishing
listener: listener, order 7
published: published
commit: commit
after: after-commit listener, order 7
begin -> publishing
publishing -> listener

published -> commit

## Key points

- A Spring Modulith module exposes its base package by default; `@NamedInterface` exposes more.
- `verify()` rejects module-level cycles and references to internal packages of other modules.
- Spring Modulith publishes events synchronously by default, which can widen the transaction boundary.
- ArchUnit evaluates an `ArchRule` against imported classes with `check(importedClasses)`.
- Layer rules in ArchUnit state which layer may access which, and slice rules check slices for cyclic dependencies.
- An onion check in ArchUnit forbids dependencies from the domain to the application packages and from either to an adapter.
- An aggregate root can publish events from a `@DomainEvents` method, called on `save(…)` and `delete(…)` calls.
- A record derives `equals`, `hashCode` and `toString` from all of its component fields.

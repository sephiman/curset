# Type system and null safety

## Nullable types, safe calls and the Elvis operator
<!-- bullets: 4.1.a -->

In Kotlin, the type system distinguishes between types that can hold null (nullable types) and those that cannot (non-nullable types) (`kotlin-docs-null-safety#nullable-types-and-non-nullable-types`).

To allow null values, declare a variable with a `?` sign right after the variable type (`kotlin-docs-null-safety#nullable-types-and-non-nullable-types`).

If you try accessing `length` directly on a variable declared as `String?`, the compiler reports an error (`kotlin-docs-null-safety#nullable-types-and-non-nullable-types`).

Instead of throwing an NPE, the safe call operator `?.` returns null if the object is null (`kotlin-docs-null-safety#safe-call-operator`).

The type of the expression `b?.length`, where `b` is a `String?`, is `Int?` (`kotlin-docs-null-safety#safe-call-operator`).

A chain of safe calls returns null if any of its properties are null (`kotlin-docs-null-safety#safe-call-operator`).

If one of the receivers in a safe call chain on the left side of an assignment is null, the assignment is skipped and the expression on the right is not evaluated at all (`kotlin-docs-null-safety#safe-call-operator`).

If the expression to the left of `?:` is not null, the Elvis operator returns it (`kotlin-docs-null-safety#elvis-operator`).

Otherwise, the Elvis operator returns the expression to the right (`kotlin-docs-null-safety#elvis-operator`).

The expression on the right-hand side of the Elvis operator is evaluated only if the left-hand side is null (`kotlin-docs-null-safety#elvis-operator`).

Since `throw` and `return` are expressions in Kotlin, you can also use them on the right-hand side of the Elvis operator (`kotlin-docs-null-safety#elvis-operator`).

The snippet applies the safe call and the Elvis operator to a `String?` that holds null and to one that holds a value.

```kotlin snippet=m04-l01/SafeCallAndElvis.kt
fun lengthOrZero(text: String?): Int = text?.length ?: 0

fun expensiveDefault(): Int {
    println("default evaluated")
    return -1
}

fun main() {
    val missing: String? = null
    val present: String? = "abc"
    println(missing?.length)
    println(lengthOrZero("Kotlin"))
    println(lengthOrZero(missing))
    println(present?.length ?: expensiveDefault())
    println(missing?.length ?: expensiveDefault())
}
```

The snippet prints `null` for the safe call `missing?.length` on a `String?` that holds null.

It prints `6` for `lengthOrZero("Kotlin")` and `0` for `lengthOrZero(missing)`.

When the left side is not null, `present?.length ?: expensiveDefault()` prints `3` and never prints `default evaluated`.

When the left side is null, `missing?.length ?: expensiveDefault()` prints `default evaluated` and then `-1`.

## Smart casts and lateinit
<!-- bullets: 4.1.a -->

The compiler tracks the type checks and explicit casts for immutable values and inserts implicit (safe) casts automatically (`kotlin-docs-typecasts#smart-casts`).

The compiler knows that a cast is safe if a negative check leads to a return (`kotlin-docs-typecasts#smart-casts`).

A property that is not convenient to initialize in the constructor, for example one set through dependency injection or inside the setup method of a unit test, is marked with the `lateinit` modifier (`kotlin-docs-properties#late-initialized-properties-and-variables`).

The `lateinit` modifier is used on `var` properties declared as top-level properties, local variables or properties inside the body of a class (`kotlin-docs-properties#late-initialized-properties-and-variables`).

A `lateinit` class property cannot be declared in the primary constructor (`kotlin-docs-properties#late-initialized-properties-and-variables`).

A `lateinit` property or variable must be non-nullable and must not be a primitive type (`kotlin-docs-properties#late-initialized-properties-and-variables`).

If you access a `lateinit` property before initializing it, Kotlin throws a specific exception that identifies the uninitialized property being accessed (`kotlin-docs-properties#late-initialized-properties-and-variables`).

To check whether a `lateinit` var has already been initialized, use the `isInitialized` property on the reference to that property (`kotlin-docs-properties#late-initialized-properties-and-variables`).

The snippet checks a value with `!is` and an early return, and reads a `lateinit` property before it is set.

```kotlin snippet=m04-l01/SmartCastAndLateinit.kt
class Report {
    lateinit var body: String
}

fun describe(data: Any): String {
    if (data !is String) return "not text"
    return "text of ${data.length} characters"
}

fun main() {
    println(describe("Kotlin"))
    println(describe(404))
    try {
        println(Report().body)
    } catch (e: UninitializedPropertyAccessException) {
        println(e.message)
    }
}
```

The snippet prints `text of 6 characters` for `describe("Kotlin")`, because `data` is a `String` after the negative check returns, and `not text` for `describe(404)`.

Reading the `lateinit` property `body` before it is set throws an `UninitializedPropertyAccessException` with the message `lateinit property body has not been initialized`.

## Platform types and nullability annotations
<!-- bullets: 4.1.b -->

Any reference in Java may be null, which makes Kotlin's requirements of strict null-safety impractical for objects coming from Java (`kotlin-docs-java-interop#null-safety-and-platform-types`).

Types of Java declarations are treated in Kotlin as non-denotable and called platform types (`kotlin-docs-java-interop#null-safety-and-platform-types`).

You can't write the non-denotable types in the code explicitly (`kotlin-docs-java-interop#null-safety-and-platform-types`).

When you call methods on variables of platform types, Kotlin does not issue nullability errors at compile time, but the call may fail at runtime (`kotlin-docs-java-interop#null-safety-and-platform-types`).

You can assign a value of a platform type to a variable of both nullable and non-nullable Kotlin types (`kotlin-docs-java-interop#null-safety-and-platform-types`).

If you assign a platform value to a variable of a non-nullable type and the value is actually null at runtime, Kotlin throws a `NullPointerException` (`kotlin-docs-java-interop#null-safety-and-platform-types`).

If you choose a non-nullable type, the compiler will emit an assertion upon assignment (`kotlin-docs-java-interop#null-safety-and-platform-types`).

The snippet assigns the result of the Java method `System.getProperty` for a missing property to a `String?` and then to a `String`.

```kotlin snippet=m04-l01/PlatformTypes.kt
fun main() {
    val fromJava = System.getProperty("curset.missing.property")
    val nullable: String? = fromJava
    println(nullable)
    try {
        val notNull: String = fromJava
        println(notNull)
    } catch (e: NullPointerException) {
        println("null pointer on assignment")
    }
}
```

Assigning the value to the `String?` prints `null`.

Assigning the same value to the `String` throws a `NullPointerException`, which the snippet catches and reports as `null pointer on assignment`.

In the notation for platform types, `T!` means "T or T?" (`kotlin-docs-java-interop#notation-for-platform-types`).

Java types that have nullability annotations are represented not as platform types, but as actual nullable or non-nullable Kotlin types (`kotlin-docs-java-interop#nullability-annotations`).

JSpecify is the only supported flavor that uses strict report level by default (`kotlin-docs-java-interop#nullability-annotations`).

:::esquema{kind=tabla title="Report levels of the nullability-annotations compiler option"}
| Report level | Effect | Source |
|---|---|---|
| `ignore` | Ignores nullability mismatches | `kotlin-docs-java-interop#nullability-annotations` |
| `warn` | Reports warnings | `kotlin-docs-java-interop#nullability-annotations` |
| `strict` | Reports errors | `kotlin-docs-java-interop#nullability-annotations` |
:::

In JSpecify, `@NullMarked` marks all types within a scope, for example a class or package, as non-nullable by default unless annotated otherwise (`kotlin-docs-java-interop#jspecify-support`).

`@NullUnmarked` reverses the effect of `@NullMarked`, making all types within the scope as platform types (`kotlin-docs-java-interop#jspecify-support`).

If the `@Nonnull(when = ...)` value of JSR-305 is `When.ALWAYS`, the annotated type is treated as non-nullable (`kotlin-docs-java-interop#jsr-305-support`).

`When.MAYBE` and `When.NEVER` denote a nullable type (`kotlin-docs-java-interop#jsr-305-support`).

`When.UNKNOWN` forces the type to be platform one (`kotlin-docs-java-interop#jsr-305-support`).

## Declaration-site variance, projections, reified type parameters and type erasure
<!-- bullets: 4.1.c -->

In Kotlin, you can annotate a type parameter to make sure that it is only returned (produced) from members of its class, and never consumed (`kotlin-docs-generics#declaration-site-variance`).

To do this, use the `out` modifier (`kotlin-docs-generics#declaration-site-variance`).

When a type parameter `T` of a class `C` is declared `out`, it may occur only in the out-position in the members of `C`, but in return `C<Base>` can safely be a supertype of `C<Derived>` (`kotlin-docs-generics#declaration-site-variance`).

The `in` modifier makes a type parameter contravariant, meaning it can only be consumed and never produced (`kotlin-docs-generics#declaration-site-variance`).

The `out` modifier is called a variance annotation, and since it is provided at the type parameter declaration site, it provides declaration-site variance (`kotlin-docs-generics#declaration-site-variance`).

Java's use-site variance uses wildcards in the type usages to make the types covariant (`kotlin-docs-generics#declaration-site-variance`).

The snippet widens a `Source<String>` to a `Source<Any>`, checks types with a `reified` parameter and compares the classes of two `ArrayList` instances with different type arguments.

```kotlin snippet=m04-l01/VarianceAndReified.kt
interface Source<out T> {
    fun nextT(): T
}

fun widen(strings: Source<String>): Source<Any> = strings

inline fun <reified T> isInstance(value: Any): Boolean = value is T

fun main() {
    val strings = object : Source<String> {
        override fun nextT(): String = "kotlin"
    }
    println(widen(strings).nextT())
    println(isInstance<String>("kotlin"))
    println(isInstance<Int>("kotlin"))
    println(arrayListOf<String>()::class == arrayListOf<Int>()::class)
}
```

Because `Source<out T>` is covariant, `widen` returns a `Source<String>` as a `Source<Any>`, and `nextT()` prints `kotlin`.

The `reified` function `isInstance<T>` prints `true` for `isInstance<String>("kotlin")` and `false` for `isInstance<Int>("kotlin")`.

The classes of an `ArrayList<String>` and an `ArrayList<Int>` compare equal, so the last line is `true`.

`Array<T>` is invariant in `T`, so neither `Array<Int>` nor `Array<Any>` is a subtype of the other (`kotlin-docs-generics#use-site-variance-type-projections`).

With a type projection such as `Array<out Any>`, you can only call methods that return the type parameter `T`, which means you can only call `get()` (`kotlin-docs-generics#use-site-variance-type-projections`).

`Array<in String>` corresponds to Java's `Array<? super String>` (`kotlin-docs-generics#use-site-variance-type-projections`).

For `Foo<out T : TUpper>`, where `T` is a covariant type parameter with the upper bound `TUpper`, `Foo<*>` is equivalent to `Foo<out TUpper>` (`kotlin-docs-generics#star-projections`).

For `Foo<in T>`, where `T` is a contravariant type parameter, `Foo<*>` is equivalent to `Foo<in Nothing>` (`kotlin-docs-generics#star-projections`).

There is nothing you can write to `Foo<*>` in a safe way when `T` is unknown (`kotlin-docs-generics#star-projections`).

For `interface Function<in T, out U>`, `Function<*, String>` means `Function<in Nothing, String>` (`kotlin-docs-generics#star-projections`).

For `interface Function<in T, out U>`, `Function<Int, *>` means `Function<Int, out Any?>` (`kotlin-docs-generics#star-projections`).

For `interface Function<in T, out U>`, `Function<*, *>` means `Function<in Nothing, out Any?>` (`kotlin-docs-generics#star-projections`).

Star-projections are very much like Java's raw types, but safe (`kotlin-docs-generics#star-projections`).

Inline functions support reified type parameters (`kotlin-docs-inline-functions#reified-type-parameters`).

Normal functions (not marked as `inline`) cannot have reified parameters (`kotlin-docs-inline-functions#reified-type-parameters`).

Since the function is inlined, no reflection is needed and normal operators like `!is` and `as` are available for a reified type parameter (`kotlin-docs-inline-functions#reified-type-parameters`).

A type that does not have a run-time representation, for example a non-reified type parameter or a fictitious type like `Nothing`, cannot be used as an argument for a reified type parameter (`kotlin-docs-inline-functions#reified-type-parameters`).

The type safety checks that Kotlin performs for generic declaration usages are done at compile time (`kotlin-docs-generics#type-erasure`).

At runtime, the instances of generic types do not hold any information about their actual type arguments (`kotlin-docs-generics#type-erasure`).

The type information is said to be erased (`kotlin-docs-generics#type-erasure`).

:::esquema{kind=tabla title="Variance forms in Kotlin generics"}
| Form | Meaning | Source |
|---|---|---|
| `out` on a type parameter | The type parameter may occur only in the out-position in the members of the class | `kotlin-docs-generics#declaration-site-variance` |
| `in` on a type parameter | The type parameter is contravariant and can only be consumed, never produced | `kotlin-docs-generics#declaration-site-variance` |
| `Array<out Any>` | A type projection: you can only call methods that return the type parameter | `kotlin-docs-generics#use-site-variance-type-projections` |
| `Foo<*>` for `Foo<in T>` | Equivalent to `Foo<in Nothing>` | `kotlin-docs-generics#star-projections` |
:::

## Key points

- A nullable type is written with `?`, and accessing `length` directly on a `String?` is a compile error.
- The safe call `?.` returns null instead of throwing an NPE when the object is null.
- The Elvis operator `?:` returns the left side when it is not null, and evaluates the right side only when the left side is null.
- The compiler inserts smart casts for immutable values, also after a negative check that leads to a return.
- A `lateinit` property must be a non-nullable, non-primitive `var`, cannot be in the primary constructor, and throws when read before it is set.
- Java types without nullability annotations are platform types, which cannot be written explicitly and may fail at runtime with a `NullPointerException`.
- Annotated Java types become nullable or non-nullable Kotlin types, and JSpecify is the only flavor that is strict by default.
- `out` marks a producer and `in` a consumer, and Kotlin states this at the declaration site, where Java uses wildcards at the use site.
- `Foo<*>` is `Foo<in Nothing>` for a contravariant parameter and `Foo<out TUpper>` for a covariant one.
- A `reified` type parameter needs an `inline` function, and generic types are erased at runtime.

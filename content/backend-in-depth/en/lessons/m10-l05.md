# Kubernetes in production and continuous delivery

## Liveness, readiness and start-up probes
<!-- bullets: 10.5.a -->

Kubernetes lets you define probes to continuously monitor the health of containers in a Pod (`k8s-pod-lifecycle#container-probes`).

A probe is a diagnostic performed periodically by the kubelet on a container (`k8s-pod-lifecycle#container-probes`).

Based on the probe results, Kubernetes can restart unhealthy containers or stop sending traffic to containers that are not ready (`k8s-pod-lifecycle#container-probes`).

Liveness probes determine when to restart a container (`k8s-pod-lifecycle#liveness-probe`).

A liveness probe could catch a deadlock, where an application is running but unable to make progress (`k8s-pod-lifecycle#liveness-probe`).

Liveness probes do not wait for readiness probes to succeed (`k8s-pod-lifecycle#liveness-probe`).

To wait before executing a liveness probe, define `initialDelaySeconds` or use a startup probe (`k8s-pod-lifecycle#liveness-probe`).

If a container fails its liveness probe more times than the configured tolerance, the kubelet restarts that container (`k8s-pod-lifecycle#liveness-probe`).

Readiness probes determine when a container is ready to accept traffic (`k8s-pod-lifecycle#readiness-probe`).

If the readiness probe returns a failed state, the EndpointSlice controller removes the Pod's IP address from the EndpointSlices of all Services that match the Pod (`k8s-pod-lifecycle#readiness-probe`).

Readiness probes run on the container during its whole lifecycle (`k8s-pod-lifecycle#readiness-probe`).

A Pod with containers reporting that they are not ready does not receive traffic through Kubernetes Services (`k8s-probes#define-readiness-probes`).

If a startup probe is configured, Kubernetes does not execute liveness or readiness probes until the startup probe succeeds (`k8s-pod-lifecycle#startup-probe`).

A startup probe is only executed at startup, unlike liveness and readiness probes, which are run periodically (`k8s-pod-lifecycle#startup-probe`).

If the startup probe fails, the kubelet kills the container, and the container is subjected to its restart policy (`k8s-pod-lifecycle#startup-probe`).

For a slow-starting application, the startup probe uses the same check as the liveness probe, with a `failureThreshold * periodSeconds` long enough to cover the worst case startup time (`k8s-probes#define-startup-probes`).

```yaml
startupProbe:
  httpGet:
    path: /healthz
    port: liveness-port
  failureThreshold: 30
  periodSeconds: 10
```

With `failureThreshold: 30` and `periodSeconds: 10` on the startup probe, the application has a maximum of 5 minutes (30 * 10 = 300s) to finish its startup (`k8s-probes#define-startup-probes`).

Once the startup probe has succeeded once, the liveness probe takes over to provide a fast response to container deadlocks (`k8s-probes#define-startup-probes`).

If the command of an exec liveness probe returns a non-zero value, the kubelet kills the container and restarts it (`k8s-probes#define-a-liveness-command`).

## Probes in Spring Boot
<!-- bullets: 10.5.a -->

Spring Boot exposes the liveness and readiness health groups as separate HTTP probes at `/actuator/health/liveness` and `/actuator/health/readiness` (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes`).

These health groups are automatically enabled (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes`).

The health groups can be disabled with the `management.endpoint.health.probes.enabled` configuration property (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes`).

A `startupProbe` is generally not needed, because the `readinessProbe` fails until all startup tasks are done (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes`).

If an application takes a long time to start, a `startupProbe` that uses the liveness HTTP probe keeps Kubernetes from killing the application while it is starting (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes`).

On a separate management context, a probe check could be successful even if the main application does not work properly, for example because it cannot accept new connections (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes`).

Setting `management.endpoint.health.probes.add-additional-paths=true` makes the liveness group available at `/livez` and the readiness group at `/readyz` on the main server port (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes`).

By default, Spring Boot does not add other health indicators to the liveness and readiness groups (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.external-state`).

The liveness probe should not depend on health checks for external systems (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.external-state`).

If the liveness state of an application is broken, Kubernetes tries to solve the problem by restarting the application instance (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.external-state`).

If an external system fails, Kubernetes might restart all application instances and create cascading failures (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.external-state`).

Spring Boot does not include any additional health checks in the readiness probe because the choice of checking external systems must be made carefully by the application developers (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.external-state`).

If all instances of an application are unready, a Kubernetes Service with `type=ClusterIP` or `NodePort` does not accept any incoming connections (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.external-state`).

When all instances are unready, a `ClusterIP` or `NodePort` Service sends no HTTP error response such as `503`, since there is no connection (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.external-state`).

## Graceful shutdown of a Pod
<!-- bullets: 10.5.b -->

To stop the containers in a Pod, the kubelet makes requests to the container runtime that first send a TERM (SIGTERM) signal, with a grace period timeout, to the main process in each container (`k8s-pod-lifecycle#pod-termination`).

The requests to stop the containers are processed by the container runtime asynchronously (`k8s-pod-lifecycle#pod-termination`).

Many container runtimes respect the `STOPSIGNAL` value defined in the container image and send it instead of TERM when it is different (`k8s-pod-lifecycle#pod-termination`).

Once the grace period has expired, the KILL signal is sent to any remaining processes, and the Pod is then deleted from the API Server (`k8s-pod-lifecycle#pod-termination`).

The default `terminationGracePeriodSeconds` setting is 30 seconds (`k8s-pod-lifecycle#pod-termination-flow`).

If a container defines a `preStop` hook and `terminationGracePeriodSeconds` is not 0, the kubelet runs that hook inside of the container (`k8s-pod-lifecycle#pod-termination-flow`).

If the `preStop` hook is still running after the grace period expires, the kubelet requests a small, one-off grace period extension of 2 seconds (`k8s-pod-lifecycle#pod-termination-flow`).

The `PostStart` hook is executed immediately after a container is created (`k8s-container-lifecycle-hooks#container-hooks`).

The `PostStart` hook runs concurrently with the container's `ENTRYPOINT`, so it may run before, during, or after the main process starts (`k8s-container-lifecycle-hooks#container-hooks`).

Hook delivery is intended to be at least once, so a hook may be called multiple times for any given event, such as for `PostStart` or `PreStop` (`k8s-container-lifecycle-hooks#hook-delivery-guarantees`).

It is up to the hook implementation to handle repeated delivery correctly (`k8s-container-lifecycle-hooks#hook-delivery-guarantees`).

If an HTTP hook receiver is down and cannot take traffic, there is no attempt to resend (`k8s-container-lifecycle-hooks#hook-delivery-guarantees`).

For an endpoint backed by a Pod, the terminating condition is set when the Pod is first deleted, most likely before the Pod's containers exit (`k8s-endpoint-slices#terminating`).

Service proxies normally ignore terminating endpoints, but they may route traffic to endpoints that are both serving and terminating if all available endpoints are terminating (`k8s-endpoint-slices#terminating`).

During a graceful node shutdown, the kubelet ensures that Pods follow the normal Pod termination process (`k8s-kubelet-graceful-shutdown#graceful-node-shutdown`).

During node shutdown, the kubelet does not accept new Pods, even if those Pods are already bound to the node (`k8s-kubelet-graceful-shutdown#graceful-node-shutdown`).

## Connection draining in Spring Boot and Kafka consumers
<!-- bullets: 10.5.b -->

Graceful shutdown is enabled by default with all three embedded web servers (Jetty, Reactor Netty and Tomcat) and with both reactive and servlet-based web applications (`spring-boot-web-graceful-shutdown#page-title`).

Graceful shutdown occurs as part of closing the application context and is performed in the earliest phase of stopping `SmartLifecycle` beans (`spring-boot-web-graceful-shutdown#page-title`).

The stop processing uses a timeout that provides a grace period during which existing requests are allowed to complete but no new requests are permitted (`spring-boot-web-graceful-shutdown#page-title`).

The timeout period is configured with the `spring.lifecycle.timeout-per-shutdown-phase` property (`spring-boot-web-graceful-shutdown#page-title`).

Jetty, Reactor Netty and Tomcat stop accepting new requests at the network layer (`spring-boot-web-graceful-shutdown#web.graceful-shutdown.rejecting-requests-during-the-grace-period`).

The use of persistent connections can change the way that requests stop being accepted (`spring-boot-web-graceful-shutdown#web.graceful-shutdown.rejecting-requests-during-the-grace-period`).

Shutdown in an IDE may be immediate rather than graceful if the IDE does not send a proper `SIGTERM` signal (`spring-boot-web-graceful-shutdown#page-title`).

`KafkaConsumer.close()` closes the consumer with default leave group behavior, waiting for up to the default timeout of 30 seconds for any needed cleanup (`kafka-javadoc-kafkaconsumer#close()`).

If auto-commit is enabled, `close()` commits the current offsets if possible within the default timeout (`kafka-javadoc-kafkaconsumer#close()`).

`wakeup()` cannot be used to interrupt `close()` (`kafka-javadoc-kafkaconsumer#close()`).

The close operation attempts all shutdown steps even if one of them fails, logs all encountered errors and finally throws the first error found (`kafka-javadoc-kafkaconsumer#close()`).

`close(Duration)` has been deprecated since Kafka 4.1 in favour of `close(CloseOptions)` (`kafka-javadoc-kafkaconsumer#close(java.time.Duration)`).

With `close(Duration)`, a consumer that cannot complete offset commits and leave the group before the timeout expires is force closed (`kafka-javadoc-kafkaconsumer#close(java.time.Duration)`).

With `close(Duration)`, a timeout of zero means do not wait for pending requests to complete (`kafka-javadoc-kafkaconsumer#close(java.time.Duration)`).

## Rolling updates, disruption budgets and spreading
<!-- bullets: 10.5.c -->

A Deployment updates Pods in a rolling update fashion, gradually scaling down the old ReplicaSets and scaling up the new one, when `.spec.strategy.type==RollingUpdate` (`k8s-deployment#rolling-update-deployment`).

`maxUnavailable` and `maxSurge` control the rolling update process (`k8s-deployment#rolling-update-deployment`).

`.spec.strategy.rollingUpdate.maxUnavailable` specifies the maximum number of Pods that can be unavailable during the update process (`k8s-deployment#max-unavailable`).

The absolute number for `maxUnavailable` is calculated from the percentage by rounding down (`k8s-deployment#max-unavailable`).

The default value of `maxUnavailable` is 25% (`k8s-deployment#max-unavailable`).

`maxUnavailable` cannot be 0 if `maxSurge` is 0 (`k8s-deployment#max-unavailable`).

`.spec.strategy.rollingUpdate.maxSurge` specifies the maximum number of Pods that can be created over the desired number of Pods (`k8s-deployment#max-surge`).

The absolute number for `maxSurge` is calculated from the percentage by rounding up (`k8s-deployment#max-surge`).

The default value of `maxSurge` is 25% (`k8s-deployment#max-surge`).

With `maxSurge` set to 30%, the total number of Pods running at any time during the update is at most 130% of desired Pods (`k8s-deployment#max-surge`).

With `maxUnavailable` set to 30%, the total number of Pods available at all times during the update is at least 70% of the desired Pods (`k8s-deployment#max-unavailable`).

A PodDisruptionBudget (PDB) limits the number of Pods of a replicated application that are down simultaneously from voluntary disruptions (`k8s-disruptions#pod-disruption-budgets`).

For a Deployment with `.spec.replicas: 5` whose PDB allows 4 Pods at a time, the Eviction API allows voluntary disruption of one, but not two, Pods at a time (`k8s-disruptions#pod-disruption-budgets`).

Involuntary disruptions cannot be prevented by PDBs, but they do count against the budget (`k8s-disruptions#pod-disruption-budgets`).

Workload resources such as Deployment and StatefulSet are not limited by PDBs when doing rolling upgrades (`k8s-disruptions#pod-disruption-budgets`).

Cluster managers and hosting providers should use tools that respect PodDisruptionBudgets by calling the Eviction API instead of directly deleting Pods or Deployments (`k8s-disruptions#pod-disruption-budgets`).

When you run `kubectl drain`, the tool tries to evict all of the Pods on the Node you are taking out of service (`k8s-disruptions#pod-disruption-budgets`).

When a Pod is evicted using the Eviction API, it is gracefully terminated, honoring the `terminationGracePeriodSeconds` setting in its PodSpec (`k8s-disruptions#pod-disruption-budgets`).

The default behavior of a PDB during a node drain is to wait for the application Pods to become healthy before the drain can proceed (`k8s-disruptions#pod-disruption-budgets`).

Inter-pod affinity and anti-affinity constrain which nodes Pods can be scheduled on based on the labels of Pods already running on that node, instead of the node labels (`k8s-affinity#inter-pod-affinity-and-anti-affinity`).

The Pod API includes the field `spec.topologySpreadConstraints` (`k8s-topology-spread#topologyspreadconstraints-field`).

## Deployment strategies and progressive delivery
<!-- bullets: 10.5.d -->

:::esquema{kind=tabla title="Deployment strategies"}
| Strategy | How it works | Source |
|---|---|---|
| Rolling update | Gradually scale down the old ReplicaSets and scale up the new one | `k8s-deployment#rolling-update-deployment` |
| Blue-green | The new and old versions are deployed at the same time, and only the old version receives production traffic | `argo-rollouts-concepts#blue-green` |
| Canary | A subset of users is exposed to the new version while the rest of the traffic goes to the old version | `argo-rollouts-concepts#canary` |
:::

A Blue-Green deployment allows developers to run tests against the new version before switching the live traffic to it (`argo-rollouts-concepts#blue-green`).

In a canary deployment, once the new version is verified to be correct, it can gradually replace the old version (`argo-rollouts-concepts#canary`).

Ingress controllers and service meshes such as NGINX and Istio enable more sophisticated traffic shaping for canarying than what is natively available (`argo-rollouts-concepts#canary`).

To roll out releases to a subset of users or servers with a Deployment, you can create multiple Deployments, one for each release, following the canary pattern (`k8s-deployment#canary-deployments`).

Progressive delivery releases updates in a controlled and gradual manner, typically coupling automation and metric analysis to drive the automated promotion or rollback of the update (`argo-rollouts-concepts#progressive-delivery`).

Progressive delivery limits the exposure of the new version to a subset of users, observes and analyzes for correct behavior, then progressively increases the exposure while continuously verifying correctness (`argo-rollouts-concepts#progressive-delivery`).

A Deployment can be rolled back, for example when it is not stable, such as crash looping (`k8s-deployment#rolling-back-a-deployment`).

By default, all of a Deployment's rollout history is kept in the system so that you can roll back at any time, and the revision history limit changes that (`k8s-deployment#rolling-back-a-deployment`).

With Argo Rollouts you can define the exact number of canary stages and the percentages of traffic according to your use case (`argo-rollouts-concepts#canary`).

## Feature flags
<!-- bullets: 10.5.e -->

:::judgement{source="Pete Hodgson, Feature Toggles, martinfowler.com" ref="fowler-feature-toggles#CategoriesOfToggles"}
According to Pete Hodgson, a feature toggle ships alternative codepaths within one deployable unit and chooses between them at runtime. He warns against putting all toggles into one bucket and sorts them along two dimensions: how long the toggle will live and how dynamic the toggling decision must be.
:::

:::judgement{source="Pete Hodgson, Feature Toggles, martinfowler.com" ref="fowler-feature-toggles#ReleaseToggles"}
According to Pete Hodgson, release toggles allow incomplete and untested codepaths to be shipped to production as latent code that may never be turned on. He describes them as flags that enable trunk-based development for teams practicing continuous delivery, and as transitionary by nature, generally lasting no longer than a week or two.
:::

:::judgement{source="Pete Hodgson, Feature Toggles, martinfowler.com" ref="fowler-feature-toggles#OpsToggles"}
According to Pete Hodgson, ops toggles control operational aspects of a system, so that operators can disable or degrade a feature quickly in production. Because operators need to react quickly, he says that needing to roll out a new release to flip an ops toggle is unlikely to make an operations person happy.
:::

:::judgement{source="Pete Hodgson, Feature Toggles, martinfowler.com" ref="fowler-feature-toggles#ManagingTheCarryingCostOfFeatureToggles"}
According to Pete Hodgson, toggles come with a carrying cost: they require new abstractions or conditional logic in the code and a significant testing burden. He says that savvy teams treat their toggles as inventory to keep as low as possible, for example by adding a toggle removal task to the backlog whenever a release toggle is first introduced, or by putting expiration dates on toggles.
:::

## GitOps and pipeline design
<!-- bullets: 10.5.f -->

A system managed by GitOps must have its desired state expressed declaratively (`opengitops-principles#declarative`).

In GitOps, desired state is stored in a way that enforces immutability, versioning and retains a complete version history (`opengitops-principles#versioned-and-immutable`).

In GitOps, software agents automatically pull the desired state declarations from the source (`opengitops-principles#pulled-automatically`).

In GitOps, software agents continuously observe actual system state and attempt to apply the desired state (`opengitops-principles#continuously-reconciled`).

:::esquema{kind=tabla title="Argo CD core concepts"}
| Term | Meaning | Source |
|---|---|---|
| Target state | The desired state of an application, as represented by files in a Git repository | `argocd-core-concepts#core-concepts` |
| Live state | The live state of that application: what pods etc. are deployed | `argocd-core-concepts#core-concepts` |
| Sync status | Whether or not the live state matches the target state | `argocd-core-concepts#core-concepts` |
| Sync | The process of making an application move to its target state | `argocd-core-concepts#core-concepts` |
| Sync operation status | Whether or not a sync succeeded | `argocd-core-concepts#core-concepts` |
| Refresh | Compare the latest code in Git with the live state and figure out what is different | `argocd-core-concepts#core-concepts` |
| Health | The health of the application: is it running correctly and can it serve requests | `argocd-core-concepts#core-concepts` |
:::

In trunk-based development, each developer divides their own work into small batches and merges that work into trunk at least once, and potentially several times, a day (`dora-capabilities-trunk#searchLinkMobile`).

Feature branches typically involve multiple developers and take days or even weeks of work (`dora-capabilities-trunk#searchLinkMobile`).

Branches in trunk-based development typically last no more than a few hours, with many developers merging their individual changes into trunk frequently (`dora-capabilities-trunk#searchLinkMobile`).

In cases where releases happen multiple times a day, release branches are not required at all, because changes can be pushed directly into trunk and deployed from there (`dora-capabilities-trunk#searchLinkMobile`).

Trunk-based development is a required practice for continuous integration (`dora-capabilities-trunk#how-to-implement-trunk-based-development`).

Continuous integration (CI) is the combination of practicing trunk-based development and maintaining a suite of fast automated tests that run after each commit to trunk to make sure the system is always working (`dora-capabilities-trunk#how-to-implement-trunk-based-development`).

If the CI process fails, developers must stop what they are doing either to fix the problem immediately or to revert the change if it cannot be fixed in a few minutes (`dora-capabilities-trunk#how-to-implement-trunk-based-development`).

DORA data from 2016 and 2017 shows that teams achieve higher software delivery and operational performance if they have three or fewer active branches in the application's code repository (`dora-capabilities-trunk#how-to-implement-trunk-based-development`).

The same DORA analysis points to merging branches to trunk at least once a day (`dora-capabilities-trunk#how-to-implement-trunk-based-development`).

The same DORA analysis points to having no code freezes and no integration phases (`dora-capabilities-trunk#how-to-implement-trunk-based-development`).

At SLSA Build L1, the package has provenance showing how it was built (`slsa-build-track-basics#build-l1-provenance-exists`).

Build L1 provenance can be used to prevent mistakes but is trivial to bypass or forge (`slsa-build-track-basics#build-l1-provenance-exists`).

At Build L1 the build platform automatically generates provenance describing what entity built the package, what build process they used, and what the top-level input to the build were (`slsa-build-track-basics#build-l1-provenance-exists`).

Provenance may be incomplete or unsigned at Build L1 (`slsa-build-track-basics#build-l1-provenance-exists`).

Keyless signing associates identities, rather than keys, with an artifact signature (`sigstore-cosign-signing#overview`).

Fulcio issues short-lived certificates binding an ephemeral key to an OpenID Connect identity (`sigstore-cosign-signing#overview`).

Signing events are logged in Rekor, a signature transparency log, providing an auditable record of when a signature was created (`sigstore-cosign-signing#overview`).

## Database migrations inside a deployment
<!-- bullets: 10.5.g -->

Flyway migrations are SQL scripts that capture schema and data changes and should be tracked in version control (`flyway-migrations#migrations`).

The same migration scripts run in the same order on each environment, which gives a repeatable deployment process (`flyway-migrations#migrations`).

Flyway Migrate scans the filesystem or classpath for available migrations, compares them to the migrations applied to the database and, if any difference is found, migrates the database to close the gap (`flyway-migrations#Migrations-Migrate`).

Flyway Migrate should preferably be executed on application startup to avoid any incompatibilities between the database and the expectations of the code (`flyway-migrations#Migrations-Migrate`).

Executing Migrate is idempotent and can be done safely regardless of the current version of the schema (`flyway-migrations#Migrations-Migrate`).

Flyway adds a schema history table to your schema to keep track of which migrations have been applied, when and by whom (`flyway-migrations#Migrations-Schemahistory`).

By default Flyway wraps the execution of each migration script in a single transaction and applies them in order (`flyway-migrations#Migrations-Transactionhandling`).

A changeset is the basic unit of change in Liquibase (`liquibase-changeset#main-header`).

By default, Liquibase runs a changeset as a single transaction, and the `runInTransaction` attribute modifies this behavior (`liquibase-changeset#main-header`).

Once a changeset has run, Liquibase does not re-run it unless `runAlways` or `runOnChange` is specified for that changeset (`liquibase-changeset#main-header`).

:::judgement{source="Danilo Sato, Parallel Change, martinfowler.com" ref="fowler-parallel-change#banner"}
According to Danilo Sato, parallel change, also known as expand and contract, is a pattern for implementing backward-incompatible changes to an interface in a safe manner by breaking the change into three phases: expand, migrate and contract. In the expand phase the interface supports both the old and the new versions, in the migrate phase clients move to the new version, and in the contract phase the old version is removed. Sato says the pattern is particularly useful when practicing continuous delivery, and that its downside is that during the migrate phase the supplier has to support two different versions.
:::

## DORA metrics
<!-- bullets: 10.5.h -->

DORA has identified five software delivery performance metrics that provide an effective way of measuring the outcomes of the software delivery process (`dora-metrics#by-nathen-harvey`).

The metrics shifted from the original four keys to the current five-metric model (`dora-metrics#by-nathen-harvey`).

The metrics divide into those that show the throughput of software changes and those that show the instability of software changes (`dora-metrics#throughput-and-instability`).

Throughput is a measure of how many changes can move through the system over a period of time (`dora-metrics#throughput`).

DORA measures throughput with three factors: change lead time, deployment frequency and failed deployment recovery time (`dora-metrics#throughput`).

Change lead time is the amount of time it takes for a change to go from committed to version control to deployed in production (`dora-metrics#throughput`).

Failed deployment recovery time is the time it takes to recover from a deployment that fails and requires immediate intervention (`dora-metrics#throughput`).

Instability is a measure of how well the software deployments go (`dora-metrics#instability`).

DORA measures instability with two factors: change fail rate and deployment rework rate (`dora-metrics#instability`).

Change fail rate is the ratio of deployments that require immediate intervention following a deployment, likely resulting in a rollback or a hotfix (`dora-metrics#instability`).

Deployment rework rate is the ratio of deployments that are unplanned but happen as a result of an incident in production (`dora-metrics#instability`).

## Key points

- Liveness probes decide when to restart a container, readiness probes decide whether it receives Service traffic, and a startup probe holds both off until the application has started.
- The liveness probe of a Spring Boot application should not depend on external systems, or a failing database can restart every instance.
- On deletion the kubelet sends SIGTERM, and it sends KILL to the remaining processes once the grace period, 30 seconds by default, has expired.
- Spring Boot graceful shutdown is on by default and lets existing requests finish; a Kafka consumer's `close()` commits offsets under auto-commit within a 30-second default timeout.
- `maxUnavailable` rounds down and `maxSurge` rounds up, and both default to 25%.
- A PodDisruptionBudget limits voluntary disruptions through the Eviction API, and rolling upgrades of a Deployment are not limited by it.
- Blue-green keeps the old version on production traffic while the new one is tested, and a canary sends a subset of users to the new version.
- GitOps keeps desired state declarative and versioned, and agents pull it and keep reconciling the live state.
- Trunk-based development merges small batches into trunk at least once a day, and continuous integration adds fast automated tests after each commit.
- Flyway tracks applied migrations in a schema history table, and Flyway and Liquibase run each migration or changeset in a transaction by default.
- DORA splits its five metrics into throughput (lead time, deployment frequency, failed deployment recovery time) and instability (change fail rate, deployment rework rate).

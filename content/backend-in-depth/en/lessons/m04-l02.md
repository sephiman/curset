# Idiomatic Kotlin

## Data classes, sealed types, objects and value classes
<!-- bullets: 4.2.a -->

Data classes in Kotlin are primarily used to hold data (`kotlin-docs-data-classes#data-classes.md`).

For a data class, the compiler automatically derives `equals()`/`hashCode()`, `toString()`, `componentN()` and `copy()` from all properties declared in the primary constructor (`kotlin-docs-data-classes#data-classes.md`).

The primary constructor of a data class must have at least one parameter (`kotlin-docs-data-classes#data-classes.md`).

All primary constructor parameters of a data class must be marked as `val` or `var` (`kotlin-docs-data-classes#data-classes.md`).

Data classes can't be abstract, open, sealed, or inner (`kotlin-docs-data-classes#data-classes.md`).

If there are explicit implementations of `equals()`, `hashCode()`, or `toString()` in the data class body or final implementations in a superclass, then these functions are not generated (`kotlin-docs-data-classes#data-classes.md`).

Providing explicit implementations for the `componentN()` and `copy()` functions is not allowed (`kotlin-docs-data-classes#data-classes.md`).

To declare a sealed class or interface, use the `sealed` modifier (`kotlin-docs-sealed-classes#declare-a-sealed-class-or-interface`).

With a sealed hierarchy of error classes, library authors can be sure that they know all the possible error types and that other error types can't appear later (`kotlin-docs-sealed-classes#declare-a-sealed-class-or-interface`).

You can create single instances of objects in Kotlin using object declarations, which always have a name following the `object` keyword (`kotlin-docs-object-declarations#object-declarations-overview`).

The initialization of an object declaration is thread-safe and done on first access (`kotlin-docs-object-declarations#object-declarations-overview`).

Object declarations are not expressions, so they cannot be used on the right-hand side of an assignment statement (`kotlin-docs-object-declarations#object-declarations-overview`).

You can nest object declarations inside other object declarations or non-inner classes, but not directly inside functions, because object declarations can't be local (`kotlin-docs-object-declarations#object-declarations-overview`).

When printing a plain object declaration, the string representation contains both its name and the hash of the object (`kotlin-docs-object-declarations#data-objects`).

By marking an object declaration with the `data` modifier, you can instruct the compiler to return the actual name of the object when calling `toString()` (`kotlin-docs-object-declarations#data-objects`).

You can't provide a custom `equals` or `hashCode` implementation for a data object (`kotlin-docs-object-declarations#data-objects`).

Compare data objects only structurally (using the `==` operator) and never by reference (using the `===` operator) (`kotlin-docs-object-declarations#data-objects`).

The generated `hashCode()` function of a data object is consistent with `equals()`, so that all runtime instances of a data object have the same hash code (`kotlin-docs-object-declarations#data-objects`).

Wrapping a value in a class introduces runtime overhead due to additional heap allocations (`kotlin-docs-inline-classes#inline-classes.md`).

To solve this, Kotlin introduces a special kind of class called an inline class (`kotlin-docs-inline-classes#inline-classes.md`).

Inline classes are a subset of value-based classes (`kotlin-docs-inline-classes#inline-classes.md`).

Inline classes don't have an identity and can only hold values (`kotlin-docs-inline-classes#inline-classes.md`).

To declare an inline class, use the `value` modifier before the name of the class (`kotlin-docs-inline-classes#inline-classes.md`).

To declare an inline class for the JVM backend, use the `value` modifier along with the `@JvmInline` annotation before the class declaration (`kotlin-docs-inline-classes#inline-classes.md`).

An inline class must have a single property initialized in the primary constructor (`kotlin-docs-inline-classes#inline-classes.md`).

At runtime, instances of an inline class are represented using that single property (`kotlin-docs-inline-classes#inline-classes.md`).

The snippet prints a data class instance, compares it with an equal one, calls `copy`, prints a data object and applies a `when` with a guard condition to a sealed interface.

```kotlin snippet=m04-l02/DataClassAndSealed.kt
data class User(val name: String, val age: Int)

sealed interface Shape {
    data class Circle(val radius: Double) : Shape
    data class Square(val side: Double) : Shape
    data object Empty : Shape
}

fun label(shape: Shape): String = when (shape) {
    is Shape.Circle if shape.radius > 10 -> "large circle"
    is Shape.Circle -> "circle"
    is Shape.Square -> "square"
    Shape.Empty -> "empty"
}

fun main() {
    val user = User("John", 42)
    println(user)
    println(user == User("John", 42))
    println(user.copy(age = 43))
    println(Shape.Empty)
    println(label(Shape.Circle(11.0)))
    println(label(Shape.Circle(1.0)))
}
```

The snippet prints `User(name=John, age=42)` for the data class instance.

The comparison with an equal `User` prints `true`, and `user.copy(age = 43)` prints `User(name=John, age=43)`.

The data object `Shape.Empty` prints `Empty`, its name without a hash.

## Exhaustive when and guard conditions
<!-- bullets: 4.2.a 4.2.d -->

`when` is a conditional expression that runs code based on multiple possible values or conditions (`kotlin-docs-control-flow#when-expressions-and-statements`).

`when` evaluates its argument and compares the result against each branch in order until one branch condition is satisfied (`kotlin-docs-control-flow#when-expressions-and-statements`).

You can use `when` either as an expression or a statement (`kotlin-docs-control-flow#when-expressions-and-statements`).

As an expression, `when` returns a value you can use later in your code (`kotlin-docs-control-flow#when-expressions-and-statements`).

Covering all possible cases is called being exhaustive (`kotlin-docs-control-flow#when-expressions-and-statements`).

The `when` expression, used with a sealed class, allows the Kotlin compiler to check exhaustively that all possible cases are covered (`kotlin-docs-sealed-classes#use-sealed-classes-with-when-expression`).

In such cases, you don't need to add an `else` clause (`kotlin-docs-sealed-classes#use-sealed-classes-with-when-expression`).

In multiplatform projects, if you have a sealed class with a `when` expression as an expected declaration in your common code, you still need an `else` branch (`kotlin-docs-sealed-classes#use-sealed-classes-with-when-expression`).

Guard conditions allow you to include more than one condition to the branches of a `when` expression or statement (`kotlin-docs-control-flow#guard-conditions-in-when-expressions`).

You can use guard conditions with `when` as long as it has a subject (`kotlin-docs-control-flow#guard-conditions-in-when-expressions`).

Place a guard condition after the primary condition in the same branch, separated by `if` (`kotlin-docs-control-flow#guard-conditions-in-when-expressions`).

You can't use guard conditions when you have multiple conditions separated by a comma (`kotlin-docs-control-flow#guard-conditions-in-when-expressions`).

The code in a branch with a guard condition runs only if both the primary condition and the guard condition evaluate to true (`kotlin-docs-control-flow#guard-conditions-in-when-expressions`).

If the primary condition doesn't match, the guard condition isn't evaluated (`kotlin-docs-control-flow#guard-conditions-in-when-expressions`).

Since `when` statements don't need to cover all cases, using guard conditions in `when` statements without an `else` branch means that if no conditions match, no code is run (`kotlin-docs-control-flow#guard-conditions-in-when-expressions`).

Unlike statements, `when` expressions must cover all cases (`kotlin-docs-control-flow#guard-conditions-in-when-expressions`).

In the snippet, `label(Shape.Circle(11.0))` prints `large circle` because the guard `shape.radius > 10` holds, and `label(Shape.Circle(1.0))` prints `circle`.

## Extension functions and scope functions
<!-- bullets: 4.2.b -->

To create your own extension function, prefix its name with a receiver type followed by a `.` (`kotlin-docs-extensions#extension-functions`).

Defining an extension on an interface is useful when you want to add functionality to all types that implement the interface only once (`kotlin-docs-extensions#extension-functions`).

You can define extension functions with a nullable receiver type, which allows you to call them on a variable even if its value is null (`kotlin-docs-extensions#nullable-receivers`).

When the receiver is null, `this` is also null (`kotlin-docs-extensions#nullable-receivers`).

The context object of `let` is available as an argument (`it`) (`kotlin-docs-scope-functions#let`).

The return value of `let` is the lambda result (`kotlin-docs-scope-functions#let`).

To perform actions on a nullable object, use the safe call operator `?.` on it and call `let` with the actions in its lambda (`kotlin-docs-scope-functions#let`).

The context object of `run` is available as a receiver (`this`) (`kotlin-docs-scope-functions#run`).

The return value of `run` is the lambda result (`kotlin-docs-scope-functions#run`).

`run` does the same as `with` but it is implemented as an extension function (`kotlin-docs-scope-functions#run`).

The non-extension variant of `run` has no context object, but it still returns the lambda result (`kotlin-docs-scope-functions#run`).

The context object of `apply` is available as a receiver (`this`) (`kotlin-docs-scope-functions#apply`).

The return value of `apply` is the object itself (`kotlin-docs-scope-functions#apply`).

The most common use case for `apply` is object configuration (`kotlin-docs-scope-functions#apply`).

The context object of `also` is available as an argument (`it`) (`kotlin-docs-scope-functions#also`).

The return value of `also` is the object itself (`kotlin-docs-scope-functions#also`).

Use `also` for actions that need a reference to the object rather than its properties and functions, or when you don't want to shadow the `this` reference from an outer scope (`kotlin-docs-scope-functions#also`).

The context object of `with` is available as a receiver (`this`) (`kotlin-docs-scope-functions#with`).

The return value of `with` is the lambda result (`kotlin-docs-scope-functions#with`).

`with` is not an extension function: the context object is passed as an argument (`kotlin-docs-scope-functions#with`).

The documentation recommends avoiding nesting scope functions and being careful when chaining them, because it's easy to get confused about the current context object and value of `this` or `it` (`kotlin-docs-scope-functions#function-selection`).

:::esquema{kind=tabla title="Scope functions"}
| Function | Object reference | Return value | Extension function | Source |
|---|---|---|---|---|
| `let` | `it` | Lambda result | Yes | `kotlin-docs-scope-functions#function-selection` |
| `run` | `this` | Lambda result | Yes | `kotlin-docs-scope-functions#function-selection` |
| `with` | `this` | Lambda result | No: takes the context object as an argument | `kotlin-docs-scope-functions#function-selection` |
| `apply` | `this` | Context object | Yes | `kotlin-docs-scope-functions#function-selection` |
| `also` | `it` | Context object | Yes | `kotlin-docs-scope-functions#function-selection` |
:::

The snippet calls each scope function on a small object and prints what it returns.

```kotlin snippet=m04-l02/ScopeFunctions.kt
class Config {
    var host = ""
    var port = 0
}

fun main() {
    println("kotlin".let { it.length })
    println("kotlin".run { length + 1 })
    val config = Config().apply {
        host = "localhost"
        port = 8080
    }
    println("${config.host}:${config.port}")
    println(mutableListOf("a").also { it.add("b") })
    println(with(config) { port + 1 })
    val missing: String? = null
    println(missing?.let { it.length })
}
```

`"kotlin".let { it.length }` prints `6` and `"kotlin".run { length + 1 }` prints `7`, each the lambda result.

`Config().apply { ... }` returns the `Config` itself, so the snippet prints `localhost:8080`.

`mutableListOf("a").also { it.add("b") }` returns the list, so the snippet prints `[a, b]`.

`with(config) { port + 1 }` returns the lambda result, so the snippet prints `8081`.

`missing?.let { it.length }` on a null `String?` prints `null`, because the safe call skips `let`.

## Read-only collections, sequences and delegation
<!-- bullets: 4.2.c -->

Each main collection type has a read-only interface, such as `List`, and a corresponding mutable interface, such as `MutableList` (`kotlin-docs-collections-overview#read-only-and-mutable-collections`).

Read-only interfaces provide operations for accessing elements, while mutable interfaces add operations for adding, removing, and updating them (`kotlin-docs-collections-overview#read-only-and-mutable-collections`).

Prefer read-only interfaces when callers don't need to modify a collection (`kotlin-docs-collections-overview#read-only-and-mutable-collections`).

An immutable collection doesn't allow you to change its elements after creation (`kotlin-docs-collections-overview#read-only-and-mutable-collections`).

`Collection<T>` is the common superinterface of `List` and `Set` (`kotlin-docs-collections-overview#read-only-and-mutable-collections`).

`Map` doesn't extend `Collection` (`kotlin-docs-collections-overview#read-only-and-mutable-collections`).

Stateless sequence operations require no state and process each element independently, for example `map()` or `filter()` (`kotlin-docs-sequences#sequence-operations`).

Stateful sequence operations require a significant amount of state, usually proportional to the number of elements in a sequence (`kotlin-docs-sequences#sequence-operations`).

If a sequence operation returns another sequence, which is produced lazily, it's called intermediate (`kotlin-docs-sequences#sequence-operations`).

Otherwise, the sequence operation is terminal (`kotlin-docs-sequences#sequence-operations`).

Sequence elements can be retrieved only with terminal operations (`kotlin-docs-sequences#sequence-operations`).

Sequences can be iterated multiple times; however, some sequence implementations might constrain themselves to be iterated only once (`kotlin-docs-sequences#sequence-operations`).

With a list, `filter()` shows its output for all elements first, and `map()` then runs for the elements left after filtering (`kotlin-docs-sequences#iterable`).

With a sequence, the `filter()` and `map()` functions are called only when building the result list (`kotlin-docs-sequences#sequence`).

When the result size reaches the size that `take()` asks for, the processing stops because it's the largest possible size that `take()` can return (`kotlin-docs-sequences#sequence`).

The snippet changes a mutable list through its read-only view, then logs every `filter` and `map` call on a list and on a sequence with `take(2)`.

```kotlin snippet=m04-l02/CollectionsAndSequences.kt
fun main() {
    val mutable = mutableListOf(1, 2)
    val readOnly: List<Int> = mutable
    mutable.add(3)
    println(readOnly)

    val words = listOf("The", "quick", "brown", "fox", "jumps")
    val log = mutableListOf<String>()
    val fromList = words
        .filter { log += "f:$it"; it.length > 3 }
        .map { log += "m:$it"; it.length }
        .take(2)
    println(log.joinToString(" "))

    log.clear()
    val pipeline = words.asSequence()
        .filter { log += "f:$it"; it.length > 3 }
        .map { log += "m:$it"; it.length }
        .take(2)
    println(log.isEmpty())
    val fromSequence = pipeline.toList()
    println(log.joinToString(" "))
    println(fromList == fromSequence)
}
```

After `add(3)` on the mutable reference, the read-only reference prints `[1, 2, 3]`.

On the list, the log shows `filter` for all five words and then `map` for the three longer than three characters: `f:The f:quick f:brown f:fox f:jumps m:quick m:brown m:jumps`.

Before the terminal call `toList()`, the log of the sequence pipeline is empty, so the snippet prints `true`.

After `toList()`, the log shows each word going through `filter` and `map` in turn, and processing stops after two results: `f:The f:quick m:quick f:brown m:brown`.

The list pipeline and the sequence pipeline produce the same result, so the last line is `true`.

The Delegation pattern has proven to be a good alternative to implementation inheritance, and Kotlin supports it natively requiring zero boilerplate code (`kotlin-docs-delegation#delegation.md`).

A class `Derived` can implement an interface `Base` by delegating all of its public members to a specified object (`kotlin-docs-delegation#delegation.md`).

The `by` clause in the supertype list of `Derived` indicates that `b` will be stored internally in objects of `Derived` and the compiler will generate all the methods of `Base` that forward to `b` (`kotlin-docs-delegation#delegation.md`).

`lazy()` is a function that takes a lambda and returns an instance of `Lazy<T>`, which can serve as a delegate for implementing a lazy property (`kotlin-docs-delegated-properties#lazy-properties`).

The first call to `get()` executes the lambda passed to `lazy()` and remembers the result (`kotlin-docs-delegated-properties#lazy-properties`).

Subsequent calls to `get()` simply return the remembered result (`kotlin-docs-delegated-properties#lazy-properties`).

By default, the evaluation of lazy properties is synchronized: the value is computed only in one thread, but all threads will see the same value (`kotlin-docs-delegated-properties#lazy-properties`).

If the synchronization of the initialization delegate is not required to allow multiple threads to execute it simultaneously, pass `LazyThreadSafetyMode.PUBLICATION` as a parameter to `lazy()` (`kotlin-docs-delegated-properties#lazy-properties`).

If you're sure that the initialization will always happen in the same thread as the one where you use the property, you can use `LazyThreadSafetyMode.NONE` (`kotlin-docs-delegated-properties#lazy-properties`).

`LazyThreadSafetyMode.NONE` doesn't incur any thread-safety guarantees and related overhead (`kotlin-docs-delegated-properties#lazy-properties`).

The snippet delegates `Base` to a `BaseImpl` and reads a `lazy` property twice.

```kotlin snippet=m04-l02/DelegationAndLazy.kt
interface Base {
    fun print()
}

class BaseImpl(val x: Int) : Base {
    override fun print() {
        println(x)
    }
}

class Derived(b: Base) : Base by b

val lazyValue: String by lazy {
    println("computed!")
    "Hello"
}

fun main() {
    Derived(BaseImpl(10)).print()
    println(lazyValue)
    println(lazyValue)
}
```

`Derived(BaseImpl(10)).print()` prints `10`, because the call is forwarded to the delegate `b`.

The first read of `lazyValue` prints `computed!` and `Hello`, and the second read prints only `Hello`.

## Comparison with Java records, sealed classes and pattern matching
<!-- bullets: 4.2.d -->

JEP 395 enhances the Java programming language with records, which are classes that act as transparent carriers for immutable data (`jep-395#Summary`).

Records can be thought of as nominal tuples (`jep-395#Summary`).

JEP 409 enhances the Java programming language with sealed classes and interfaces (`jep-409#Summary`).

Sealed classes and interfaces restrict which other classes or interfaces may extend or implement them (`jep-409#Summary`).

JEP 440 enhances the Java programming language with record patterns to deconstruct record values (`jep-440#Summary`).

Record patterns and type patterns can be nested to enable a composable form of data navigation and processing (`jep-440#Summary`).

Extending pattern matching to `switch` allows an expression to be tested against a number of patterns, each with a specific action (`jep-441#Summary`).

:::esquema{kind=tabla title="Java features and their Kotlin counterparts"}
| Purpose | Java | Kotlin | Source |
|---|---|---|---|
| Carry data | A record is a transparent carrier for immutable data | A data class is primarily used to hold data | `jep-395#Summary`; `kotlin-docs-data-classes#data-classes.md` |
| Restrict a hierarchy | Sealed classes and interfaces restrict which classes may extend or implement them | A sealed class or interface is declared with the `sealed` modifier | `jep-409#Summary`; `kotlin-docs-sealed-classes#declare-a-sealed-class-or-interface` |
| Test a value against patterns | Pattern matching for `switch` | `when` with a subject, optionally with guard conditions | `jep-441#Summary`; `kotlin-docs-control-flow#guard-conditions-in-when-expressions` |
:::

## Key points

- A data class derives `equals()`/`hashCode()`, `toString()`, `componentN()` and `copy()` from the properties of its primary constructor, which needs at least one `val` or `var` parameter.
- An explicit `equals()`, `hashCode()` or `toString()` replaces the generated one, but explicit `componentN()` and `copy()` are not allowed.
- An object declaration is a singleton initialized thread-safely on first access, and a `data object` prints its name.
- A `value` class has no identity, holds a single property, and is represented at runtime by that property.
- A `when` over a sealed type is checked for exhaustiveness without `else`, and a guard condition is evaluated only when the primary condition matches.
- `let` and `run` return the lambda result, `apply` and `also` return the object itself, and `with` is not an extension function.
- A read-only collection interface does not make a collection immutable.
- A sequence runs its operations lazily, element by element, and only a terminal operation produces a result.
- The `by` clause delegates an interface to an object, and a `lazy` property is computed on the first read and by default in a synchronized way.
- Java records, sealed classes and pattern matching for `switch` have Kotlin counterparts in data classes, sealed types and `when`.

# Round D3, Part B — variant family writer brief

Read: `CLAUDE.md`, `docs/prose-voice.md`, `docs/backend-question-style.md` (sections 1, 3, 7), `docs/backend-verification/s1/contracts.md`,
`backend/scripts/tech_course/build_variants.py` (the builder; do NOT edit it: the coordinator owns it; it runs the key three times and drops a variant whose runs differ, runs mutants once, emits `family: <file stem>`, and appends one sentence per distractor "`out` comes from this mistake: <mistake name>.") and
`backend/tests/fixtures/variants/loop-sum.yaml` (the family format), plus the lessons of your topics in `content/backend-in-depth/en/lessons/`.

Task: for each family of your topics write `content/backend-in-depth/variants/<family>.yaml` (template + parameter grid), build it, and keep 30 to 40 variants per family.
Rules
1. A family attaches to a lesson that already states the fact it practises; `citation` is a `source_id#anchor` from that lesson (the trailing parenthetical of a verified sentence, or a JLS/Javadoc anchor present in `content/backend-in-depth/sources/`). If no lesson states it, skip the family and log it. This round writes no theory; never edit a lesson.
2. `exercise:` is a new quiz exercise id `<lesson>-ex-<family>` (one exercise per family). The builder writes `content/backend-in-depth/exercises/<exercise>.yaml` and `variants/<family>.runs.json`. Do NOT edit `course.yaml`; log in `registration.md` per family: exercise id, lesson, file, number kept.
3. Never use code whose output depends on timing, thread scheduling, hash iteration order (use TreeMap/LinkedHashMap/List instead of HashMap/HashSet printing — unless the stem is about membership only and prints a size or boolean), the default locale or zone (use explicit `Locale.ROOT`, `ZoneId.of(..)`), identity hash codes, or the current date/time. Only the JDK 25 and the pinned Kotlin compiler (and pinned libraries amendment 16 allows); no network.
4. Mistakes are scripted `replace` pairs, each a TYPICAL real mistake with a name that reads after "comes from this mistake:" (e.g. "using groupingBy where partitioningBy was needed"). A variant whose wrong outputs are not all distinct from the key and from each other is dropped by the builder. Aim for at least 5 mistakes per family so most grid points keep 3 distinct wrong outputs.
5. Outputs are short (one to four lines), the stem `prompt` is 15 to 40 words and says what is asked ("What does this program print?" plus any condition, version e.g. "since Java 24" for Gatherers/streams features when it changes the answer). Each template differs across the grid in a way that changes the output (not just names). The grid should give at least 40 points so 30+ survive.
6. `explanation` is a template that walks through the evaluation step by step with `@@param@@` placeholders and `@@key@@`; code identifiers inline code; no option named by letter; no reference to options. Voice per docs/prose-voice.md.
7. Run: `cd backend && uv run python -m scripts.tech_course.build_variants --family <family> --jobs 3` (it takes a few minutes; other writers share the CPU). Check the printed skipped lines; widen the grid or fix mistakes until 30–40 kept (cap at 40 by trimming the grid, do not exceed). Then print five sampled variants' stems with their key and distractors for yourself, and run `uv run python -m scripts.tech_course.lint_questions` on your exercise files if it accepts files.
8. Tests: add `backend/tests/test_variant_families_<writer>.py` (integration marker not needed; skip if no JDK) asserting for each of your families: kept count 30–40 from the committed `.runs.json`, four distinct options per variant in the exercise file, key text equals recorded stdout, ids unique, `family` set. Write it first.
9. Do not touch other writers' files, `catalogue.py`, `course.yaml`, lessons, README. No git command that rewrites the working tree; never commit.
10. Log decisions `D3-B-<writer>-n` to `docs/_work/backend-in-depth/d3/<writer>/decisions.tsv` (id, lesson, decision, rule), progress per family in `progress.md`.
11. A family that cannot be made correct (or cannot reach 30 kept) is dropped and logged. Report at the end, under 25 lines: per family, lesson, citation, variants kept, dropped families and why.

## Added during the round
12. A mistake may carry `why:` (one sentence, fact that rules the wrong output out, may use `@@param@@`); the builder appends it to that distractor's explanation sentence. Style section 1 asks for the fact that rules a distractor out: supply `why` for every mistake. The verifier also checks that the cited anchor states the fact the key rests on (one family = one citation: split a family when two facts rest on different anchors), that explanation sentences are true for the variant they appear in (use grid parameters like `@@why@@`), that identifiers (`describe`, `int`, `BigDecimal`) are inline code in the stem, and that mistake names match the mutation they apply.
13. Builder `cases:` (added after the first blind checks). Top-level `cases:` is a list of parameter sets crossed with `parameters:`. A case may carry `why` (a variant-specific explanation sentence used as `@@why@@` in the explanation) and `citation` (overrides the family's citation for those variants: use the method-level anchor that states the fact the key rests on). The three commonest first-round failures were: (1) one generic explanation stating rules that do not apply to the variant; (2) a class-level citation where the fact is on a method anchor; (3) mistake names that do not match their mutation, false claims in the stem, identifiers outside inline code. Check all three before handing over.

# Observability of distributed systems

## Structured logs and correlation
<!-- bullets: 10.1.a -->

A structured log is a log with a defined, consistent schema or typed fields that downstream systems can reliably parse and interpret (`otel-logs#structured-logs`).

What makes a log structured is the presence of a stable schema (field names, types, and semantics), not merely that it is valid JSON (`otel-logs#structured-logs`).

Spring Boot supports structured logging with JSON formats out of the box, including Elastic Common Schema (ECS), Graylog Extended Log Format (GELF) and Logstash (`spring-boot-features-logging#features.logging.structured`).

To enable structured logging in Spring Boot, set `logging.structured.format.console` for console output or `logging.structured.format.file` for file output to the id of the format you want to use (`spring-boot-features-logging#features.logging.structured`).

The default Spring Boot log line includes a correlation ID if tracing is enabled (`spring-boot-features-logging#features.logging.log-format`).

Logback does not have a `FATAL` level, and it is mapped to `ERROR` (`spring-boot-features-logging#features.logging.log-format`).

The `TraceId` field of the OpenTelemetry log data model is the request trace ID as defined in W3C Trace Context (`otel-spec-logs-data-model#field-traceid`).

The `TraceId` field can be set for logs that are part of request processing and have an assigned trace ID (`otel-spec-logs-data-model#field-traceid`).

The `SpanId` field can be set for logs that are part of a particular processing span (`otel-spec-logs-data-model#field-spanid`).

If `SpanId` is present, `TraceId` should also be present (`otel-spec-logs-data-model#field-spanid`).

The `SpanId` field is optional (`otel-spec-logs-data-model#field-spanid`).

## Spans, context and propagation
<!-- bullets: 10.1.a -->

A span represents a unit of work or operation (`otel-traces#spans`).

Spans are the building blocks of traces (`otel-traces#spans`).

A root span has an empty parent span ID (`otel-traces#spans`).

Child spans represent sub-operations (`otel-traces#spans`).

The span context of a span is an immutable object that contains the trace ID, the span ID, the trace flags and the trace state (`otel-traces#span-context`).

The span context is the part of a span that is serialized and propagated alongside Distributed Context and Baggage (`otel-traces#span-context`).

Propagation is the mechanism that moves context between services and processes (`otel-context-propagation#propagation`).

The default OpenTelemetry propagator uses the headers specified by the W3C TraceContext specification (`otel-context-propagation#propagation`).

The `traceparent` HTTP header field identifies the incoming request in a tracing system (`w3c-trace-context#x3-2-traceparent-header`).

The `traceparent` header has four fields: version, trace-id, parent-id and trace-flags (`w3c-trace-context#x3-2-traceparent-header`).

A `TextMapPropagator` performs the injection and extraction of a cross-cutting concern value as string key/value pairs into carriers that travel in-band across process boundaries (`otel-spec-propagators#textmap-propagator`).

The carrier of propagated data on both the client and the server side is usually an HTTP request (`otel-spec-propagators#textmap-propagator`).

The key-value pairs of a `TextMapPropagator` must only consist of US-ASCII characters that make up valid HTTP header fields as per RFC 9110 (`otel-spec-propagators#textmap-propagator`).

Spring Boot's observability support relies on the Context Propagation library for forwarding the current observation across threads and reactive pipelines (`spring-boot-actuator-observability#actuator.observability.context-propagation`).

By default, `ThreadLocal` values are not automatically reinstated in reactive operators (`spring-boot-actuator-observability#actuator.observability.context-propagation`).

The `spring.reactor.context-propagation` property, set to `auto`, enables automatic propagation in reactive operators (`spring-boot-actuator-observability#actuator.observability.context-propagation`).

If you work with `@Async` methods and the `AsyncTaskExecutor` is auto-configured, you have to opt in to context propagation with the `spring.task.execution.propagate-context` property (`spring-boot-actuator-observability#actuator.observability.context-propagation`).

If you configure the `AsyncTaskExecutor` yourself, you need to register a `ContextPropagatingTaskDecorator` bean (`spring-boot-actuator-observability#actuator.observability.context-propagation`).

## Observability in Spring Boot and Micrometer
<!-- bullets: 10.1.a -->

Observability is the ability to observe the internal state of a running system from the outside (`spring-boot-actuator-observability#page-title`).

Observability consists of the three pillars of logging, metrics and traces (`spring-boot-actuator-observability#page-title`).

For metrics and traces, Spring Boot uses Micrometer Observation (`spring-boot-actuator-observability#page-title`).

Low cardinality tags are added to metrics and traces, while high cardinality tags are only added to traces (`spring-boot-actuator-observability#page-title`).

Micrometer is a metrics instrumentation library for JVM-based applications (`micrometer-concepts#concepts-purpose`).

Micrometer provides a simple facade over the instrumentation clients for the most popular monitoring systems (`micrometer-concepts#concepts-purpose`).

Starting from Micrometer 1.10, Micrometer provides the Observation API and a plugin mechanism that lets you add capabilities, including the tracing features (`micrometer-concepts#concepts-purpose`).

The main idea behind Micrometer Observation is to instrument code once and get multiple benefits out of it (`micrometer-observation#page-title`).

## Metric instruments and Prometheus metric types
<!-- bullets: 10.1.a -->

An OpenTelemetry metric instrument is defined by a name, a kind, an optional unit and an optional description (`otel-metrics#metric-instruments`).

An OpenTelemetry counter is a value that accumulates over time and only ever goes up (`otel-metrics#metric-instruments`).

An OpenTelemetry `UpDownCounter` is a value that accumulates over time but can also go down again (`otel-metrics#metric-instruments`).

An OpenTelemetry gauge measures a current value at the time it is read (`otel-metrics#metric-instruments`).

An OpenTelemetry histogram is a client-side aggregation of values, such as request latencies (`otel-metrics#metric-instruments`).

:::esquema{kind=tabla title="Prometheus metric types"}
| Type | What it is | Source |
|---|---|---|
| Counter | A cumulative metric whose value can only increase or be reset to zero on restart | `prom-metric-types#counter` |
| Gauge | A single numerical value that can arbitrarily go up and down | `prom-metric-types#gauge` |
| Histogram | Observations counted in configurable buckets, with a sum of all observed values | `prom-metric-types#histogram` |
| Summary | Configurable quantiles calculated over a sliding time window | `prom-metric-types#summary` |
:::

A counter must not expose a value that can decrease, such as the number of currently running processes, which belongs in a gauge (`prom-metric-types#counter`).

A classic histogram with the base metric name `<basename>` results in the time series `<basename>_bucket{le="<upper inclusive bound>"}`, `<basename>_sum` and `<basename>_count` (`prom-metric-types#histogram`).

The buckets of a classic histogram are cumulative, so every bucket counts all observations less than or equal to the upper boundary provided as a label (`prom-metric-types#histogram`).

A summary exposes streaming φ-quantiles as `<basename>{quantile="<φ>"}`, together with `<basename>_sum` and `<basename>_count` (`prom-metric-types#summary`).

A Prometheus metric name should use base units, such as seconds and bytes, not milliseconds or megabytes (`prom-naming#metric-names`).

A Prometheus metric name must refer to a single unit and to a single quantity (`prom-naming#metric-names`).

A Prometheus metric name should have a suffix describing the unit, in plural form (`prom-naming#metric-names`).

An accumulating count has `total` as a suffix in its Prometheus metric name, in addition to the unit if applicable (`prom-naming#metric-names`).

Spring Boot provides an actuator endpoint at `/actuator/prometheus` to present a Prometheus scrape in the appropriate format (`spring-boot-actuator-metrics#actuator.metrics.export.prometheus`).

By default, the `/actuator/prometheus` endpoint is not available and must be exposed (`spring-boot-actuator-metrics#actuator.metrics.export.prometheus`).

Prometheus expects to scrape or poll individual application instances for metrics (`spring-boot-actuator-metrics#actuator.metrics.export.prometheus`).

For ephemeral or batch jobs that may not exist long enough to be scraped, Spring Boot supports Prometheus Pushgateway to expose the metrics to Prometheus (`spring-boot-actuator-metrics#actuator.metrics.export.prometheus`).

By default, only sampled traces are included as Prometheus exemplars in Spring Boot (`spring-boot-actuator-metrics#actuator.metrics.export.prometheus`).

The value `all` of `management.tracing.exemplars.include` is not supported with Prometheus (`spring-boot-actuator-metrics#actuator.metrics.export.prometheus`).

## Histograms, summaries and percentiles
<!-- bullets: 10.1.a -->

Aggregating the precomputed quantiles from a summary rarely makes sense (`prom-histograms#quantiles`).

Averaging the precomputed quantiles of a summary across instances yields statistically nonsensical values (`prom-histograms#quantiles`).

Histograms can be aggregated across instances with the `histogram_quantile()` function (`prom-histograms#quantiles`).

Summary observations are relatively expensive due to the streaming quantile calculation (`prom-histograms#quantiles`).

Classic histogram observations are cheap as they only need to increment counters (`prom-histograms#quantiles`).

The quantile error of a classic histogram is limited by the width of the bucket the quantile is located in (`prom-histograms#quantiles`).

A summary needs its φ-quantiles and sliding window picked during instrumentation, and other φ-quantiles and sliding windows cannot be calculated later (`prom-histograms#quantiles`).

In Micrometer, `publishPercentiles` publishes percentile values computed in your application, and these values are non-aggregable across dimensions (`micrometer-concepts-histogram#page-title`).

In Micrometer, `publishPercentileHistogram` publishes a histogram suitable for computing aggregable percentile approximations in Prometheus by using `histogram_quantile` (`micrometer-concepts-histogram#page-title`).

In Micrometer, `serviceLevelObjectives` publishes a cumulative histogram with buckets defined by your SLOs (`micrometer-concepts-histogram#page-title`).

`publishPercentileHistogram` has no effect on systems that do not support aggregable percentile approximations (`micrometer-concepts-histogram#page-title`).

Where percentiles can be approximated from a histogram, it is usually unnecessary to also publish client-side percentiles with `publishPercentiles` (`micrometer-concepts-histogram#page-title`).

Micrometer clamps timers by default to a range of 1 millisecond to 1 minute, yielding 73 histogram buckets per timer dimension (`micrometer-concepts-histogram#page-title`).

Since shipping percentiles generates additional time series, it is generally preferable not to configure them in core libraries that are included as dependencies in applications (`micrometer-concepts-histogram#page-title`).

## The USE and RED methods
<!-- bullets: 10.1.a -->

:::judgement{source="Brendan Gregg, The USE Method" ref="gregg-use-method#Summary"}
According to Brendan Gregg, the USE Method can be summarized as: for every resource, check utilization, saturation, and errors. He defines a resource as all physical server functional components, such as CPUs, disks and busses. He defines utilization as the average time that the resource was busy servicing work, saturation as the degree to which the resource has extra work which it can't service, often queued, and errors as the count of error events.
:::

:::judgement{source="Brendan Gregg, The USE Method" ref="gregg-use-method#Summary"}
According to the same page, the metrics are usually expressed as a percent over a time interval for utilization, as a queue length for saturation, and as scalar counts for errors. It is intended to be used early in a performance investigation, to identify systemic bottlenecks.
:::

:::judgement{source="Grafana Labs, blog post on a talk by Tom Wilkie" ref="grafana-red-method#the-red-method"}
According to a Grafana Labs blog post on a talk by Tom Wilkie, the RED Method monitors, for every resource, the rate (the number of requests per second), the errors (the number of those requests that are failing) and the duration (the amount of time those requests take). The post quotes Tom Wilkie saying that the USE Method does not really apply to services, because it applies to hardware, network disks and things like that, and that the team wanted a microservices-oriented monitoring philosophy.
:::

## Alerting on SLOs and burn rate
<!-- bullets: 10.1.b -->

:::judgement{source="Prometheus documentation, alerting practices" ref="prom-alerting-practices#what-to-alert-on"}
According to the Prometheus documentation on alerting, aim to have as few alerts as possible, by alerting on symptoms that are associated with end-user pain rather than trying to catch every possible way that pain could be caused. Alerts should link to relevant consoles and make it easy to figure out which component is at fault. Allow for slack in alerting to accommodate small blips.
:::

:::judgement{source="Google, The Site Reliability Workbook, chapter on alerting on SLOs" ref="sre-workbook-slo-alerting#4-alert-on-burn-rate"}
According to Google's Site Reliability Workbook, burn rate is how fast, relative to the SLO, the service consumes the error budget. A burn rate of 1 means that the service consumes error budget at a rate that leaves exactly 0 budget at the end of the SLO's time window. With an SLO of 99.9% over a time window of 30 days, a constant 0.1% error rate uses exactly all of the error budget: a burn rate of 1.
:::

:::judgement{source="Google, The Site Reliability Workbook, chapter on alerting on SLOs" ref="sre-workbook-slo-alerting#6-multiwindow-multi-burn-rate-alerts"}
According to the same chapter, a good guideline is to make the short window 1/12 the duration of the long window, so that the alert stops firing soon after the errors stop. For a 99.9% SLO, the chapter recommends as a starting point a page at a burn rate of 14.4 over a long window of 1 hour and a short window of 5 minutes, a page at a burn rate of 6 over 6 hours and 30 minutes, and a ticket at a burn rate of 1 over 3 days and 6 hours.
:::

The snippet computes the burn rate for a 5% budget spend in 1 hour, the budget consumed at a burn rate of 14.4 over 1 hour, and the hours to exhaust the budget at a burn rate of 10, for a 30-day period of 720 hours.

```java snippet=m10-l01/BurnRate.java
public class BurnRate {
    public static void main(String[] args) {
        long periodHours = 30 * 24;
        System.out.println("burn rate for 5% in 1 hour: " + 5 * periodHours / (100 * 1));
        System.out.println("budget consumed at 14.4 over 1 hour: " + 144 * 1 * 100 / (10 * periodHours) + "%");
        System.out.println("hours to exhaust at burn rate 10: " + periodHours / 10);
    }
}
```

Spending 5% of a 30-day error budget in 1 hour takes 5 × 720 ÷ 100 = 36 times the sustainable rate, so the snippet prints `burn rate for 5% in 1 hour: 36`.

At a burn rate of 14.4, one hour consumes 14.4 × 1 ÷ 720 = 2% of the budget, so the snippet prints `budget consumed at 14.4 over 1 hour: 2%`.

At a burn rate of 10, the 720-hour budget lasts 720 ÷ 10 = 72 hours, so the snippet prints `hours to exhaust at burn rate 10: 72`.

## Key points

- A structured log has a stable schema of field names, types and semantics, and valid JSON alone does not make a log structured.
- Spring Boot enables structured logging through `logging.structured.format.console` or `logging.structured.format.file`, set to the id of ECS, GELF or Logstash.
- The `TraceId` and `SpanId` fields of an OpenTelemetry log record are optional, and `TraceId` should be present when `SpanId` is.
- A span is a unit of work, a root span has an empty parent span ID, and the span context carries the trace ID, span ID, trace flags and trace state.
- The default OpenTelemetry propagator uses the W3C `traceparent` header, whose four fields are version, trace-id, parent-id and trace-flags.
- In Spring Boot, `ThreadLocal` values are not reinstated in reactive operators unless `spring.reactor.context-propagation` is `auto`, and `@Async` needs `spring.task.execution.propagate-context` or a `ContextPropagatingTaskDecorator` bean.
- Low cardinality tags go to metrics and traces, and high cardinality tags go only to traces.
- A Prometheus counter only increases or resets to zero, a gauge goes up and down, and a classic histogram exposes `_bucket`, `_sum` and `_count` series with cumulative buckets.
- Prometheus metric names use base units, a single unit and quantity, a unit suffix in plural form and `total` for accumulating counts.
- Spring Boot's `/actuator/prometheus` endpoint is not available until it is exposed, and the Pushgateway covers jobs too short-lived to be scraped.
- Quantiles of a summary cannot be meaningfully aggregated across instances, while histograms are aggregated with `histogram_quantile()`.
- Micrometer's `publishPercentiles` values are non-aggregable, and `publishPercentileHistogram` publishes buckets from which Prometheus computes aggregable percentiles.
- A 5% error budget spend in 1 hour over 30 days needs a burn rate of 36, and a burn rate of 10 exhausts a 30-day budget in 72 hours.

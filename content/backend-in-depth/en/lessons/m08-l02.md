# Event-driven architecture (Kafka and RabbitMQ)

## Partitions, replicas and the in-sync replica set
<!-- bullets: 8.2.a -->

Kafka replicates the log for each topic's partitions across a configurable number of servers (`kafka-design#replication`).

Under non-failure conditions, each partition in Kafka has a single leader and zero or more followers (`kafka-design#replication`).

The total number of replicas including the leader constitute the replication factor (`kafka-design#replication`).

All writes go to the leader of the partition, and reads can go to the leader or the followers of the partition (`kafka-design#replication`).

Replicas that cannot catch up to the end of the log on the leader within the max time set by `replica.lag.time.max.ms` are removed from the ISR (`kafka-design#replication`).

A write to a Kafka partition is not considered committed until all in-sync replicas have received the write (`kafka-design#replicated-logs-quorums-isrs-and-state-machines-oh-my`).

Only members of the ISR are eligible for election as leader (`kafka-design#replicated-logs-quorums-isrs-and-state-machines-oh-my`).

With the ISR model and f+1 replicas, a Kafka topic can tolerate f failures without losing committed messages (`kafka-design#replicated-logs-quorums-isrs-and-state-machines-oh-my`).

If the controller detects the failure of a broker, it is responsible for electing one of the remaining members of the ISR to serve as the new leader (`kafka-design#replica-management`).

When the number of acknowledgements required and the number of logs that must be compared to elect a leader are chosen such that there is guaranteed to be an overlap, this is called a quorum (`kafka-design#replicated-logs-quorums-isrs-and-state-machines-oh-my`).

With a majority vote, tolerating one failure requires three copies of the data, and tolerating two failures requires five copies (`kafka-design#replicated-logs-quorums-isrs-and-state-machines-oh-my`).

Only committed messages are ever given out to the consumer (`kafka-design#replication`).

Eligible Leader Replicas are enabled by default on new clusters starting with Kafka 4.1 (`kafka-eligible-leader-replicas#overview`).

## Producer acknowledgements and minimum in-sync replicas
<!-- bullets: 8.2.a -->

With `acks=0`, the producer will not wait for any acknowledgment from the server at all (`kafka-producer-configs#acks`).

With `acks=1`, the leader writes the record to its local log but responds without awaiting full acknowledgement from all followers (`kafka-producer-configs#acks`).

With `acks=all`, the leader waits for the full set of in-sync replicas to acknowledge the record (`kafka-producer-configs#acks`).

The default value of `acks` is `all` (`kafka-producer-configs#acks`).

By default, when `acks=all`, acknowledgement happens as soon as all the current in-sync replicas have received the message (`kafka-design#availability-and-durability-guarantees`).

If a topic has only two replicas and one fails, writes that specify `acks=all` succeed (`kafka-design#availability-and-durability-guarantees`).

`min.insync.replicas` specifies the minimum number of in-sync replicas, including the leader, required for a write to succeed when a producer sets `acks` to `all` (`kafka-topic-configs#min.insync.replicas`).

If `acks=all` and the ISR has fewer than `min.insync.replicas` members, the producer raises `NotEnoughReplicas` or `NotEnoughReplicasAfterAppend` (`kafka-topic-configs#min.insync.replicas`).

The default value of `min.insync.replicas` is 1 (`kafka-topic-configs#min.insync.replicas`).

A topic with a replication factor of 3, `min.insync.replicas` set to 2 and producers using `acks` of `all` ensures that a majority of replicas must persist a write before it is successful (`kafka-topic-configs#min.insync.replicas`).

A minimum ISR size makes the partition accept writes only if the size of the ISR is above that minimum (`kafka-design#availability-and-durability-guarantees`).

The minimum ISR size only takes effect if the producer uses `acks=all` (`kafka-design#availability-and-durability-guarantees`).

A higher minimum ISR size guarantees better consistency, because the message is written to more replicas (`kafka-design#availability-and-durability-guarantees`).

A higher minimum ISR size reduces availability, because the partition is unavailable for writes if the number of in-sync replicas drops below the minimum threshold (`kafka-design#availability-and-durability-guarantees`).

Acknowledgement by all replicas does not guarantee that the full set of assigned replicas have received the message (`kafka-design#availability-and-durability-guarantees`).

Disabling unclean leader election keeps the partition unavailable until the most recent leader becomes available again, if all replicas become unavailable (`kafka-design#availability-and-durability-guarantees`).

:::esquema{kind=tabla title="Producer acknowledgement settings"}
| Setting | Leader waits for | Source |
|---|---|---|
| `acks=0` | Nothing: the producer does not wait for any acknowledgment | `kafka-producer-configs#acks` |
| `acks=1` | Its own write to the local log, not full acknowledgement from all followers | `kafka-producer-configs#acks` |
| `acks=all` | The full set of in-sync replicas | `kafka-producer-configs#acks` |
:::

## Consumer groups, offsets and rebalancing
<!-- bullets: 8.2.a -->

Each partition is consumed by exactly one consumer within each subscribing consumer group at any given time (`kafka-design#consumer-position`).

The position of a consumer in each partition is a single integer, the offset of the next message to consume (`kafka-design#consumer-position`).

A consumer can deliberately rewind back to an old offset and re-consume data (`kafka-design#consumer-position`).

Kafka can store the offsets for a consumer group in a designated broker called the group coordinator (`kafka-implementation-distribution#consumer-offset-tracking`).

The group coordinator appends an `OffsetCommitRequest` to a special compacted topic named `__consumer_offsets` (`kafka-implementation-distribution#consumer-offset-tracking`).

The broker sends a successful offset commit response only after all the replicas of the offsets topic receive the offsets (`kafka-implementation-distribution#consumer-offset-tracking`).

`StickyAssignor` guarantees an assignment that is maximally balanced while preserving as many existing partition assignments as possible (`kafka-consumer-configs#partition.assignment.strategy`).

`CooperativeStickyAssignor` follows the `StickyAssignor` logic but allows for cooperative rebalancing (`kafka-consumer-configs#partition.assignment.strategy`).

The default assignor is `[RangeAssignor, CooperativeStickyAssignor]`, which uses the `RangeAssignor` by default (`kafka-consumer-configs#partition.assignment.strategy`).

The supported values of `group.protocol` are `classic` or `consumer`, and the default value is `classic` (`kafka-consumer-configs#group.protocol`).

Starting from Apache Kafka 4.0, the next generation of the consumer rebalance protocol (KIP-848) is generally available (`kafka-consumer-rebalance-protocol#overview`).

The new protocol decreases rebalance times thanks to a fully incremental design that no longer relies on a global synchronization barrier (`kafka-consumer-rebalance-protocol#overview`).

The `group.protocol` configuration must be set to `consumer` to enable the new protocol on the consumer (`kafka-consumer-rebalance-protocol#consumer`).

The new protocol is not enabled by default on the consumer (`kafka-consumer-rebalance-protocol#consumer`).

When the new rebalance protocol is enabled, `heartbeat.interval.ms`, `session.timeout.ms` and `partition.assignment.strategy` are no longer usable (`kafka-consumer-rebalance-protocol#consumer`).

With the new protocol, the assignment strategy is controlled by the server (`kafka-consumer-rebalance-protocol#server`).

The `group.consumer.assignors` configuration specifies the list of available assignors for consumer groups (`kafka-consumer-rebalance-protocol#server`).

The `uniform` assignor is the default, unless the consumer selects a different one through `group.remote.assignor` (`kafka-consumer-rebalance-protocol#server`).

:::esquema{kind=tabla title="Classic and consumer group protocols in Apache Kafka 4"}
| Aspect | Classic protocol | Consumer protocol | Source |
|---|---|---|---|
| Where the assignment strategy is controlled | On the consumer, through `partition.assignment.strategy` | On the server, through `group.consumer.assignors` | `kafka-consumer-configs#partition.assignment.strategy`; `kafka-consumer-rebalance-protocol#server` |
| Default assignor | `RangeAssignor`, with `CooperativeStickyAssignor` as the upgrade | `uniform` | `kafka-consumer-configs#partition.assignment.strategy`; `kafka-consumer-rebalance-protocol#server` |
| How the consumer enables it | Default value of `group.protocol` | `group.protocol` set to `consumer` | `kafka-consumer-rebalance-protocol#consumer` |
:::

## Schema contracts and partition keys
<!-- bullets: 8.2.b -->

BACKWARD compatibility means that consumers using the new schema can read data produced with the last schema (`confluent-schema-evolution#avro-backward-compatibility`).

FORWARD compatibility means that data produced with a new schema can be read by consumers using the last schema (`confluent-schema-evolution#avro-forward-compatibility`).

FULL compatibility means schemas are both backward and forward compatible (`confluent-schema-evolution#avro-full-compatibility`).

The Confluent Schema Registry default compatibility type is `BACKWARD`, not `BACKWARD_TRANSITIVE` (`confluent-schema-evolution#avro-backward-compatibility`).

Transitive compatibility checks a new schema against all previously registered schemas, and non-transitive checks it only against the latest schema (`confluent-schema-evolution#transitive-property`).

An example of a backward compatible change is removing a field (`confluent-schema-evolution#avro-backward-compatibility`).

An example of a forward compatible schema modification is adding a new field (`confluent-schema-evolution#avro-forward-compatibility`).

In Avro and Protobuf, adding or removing a field with a default value is a fully compatible change (`confluent-schema-evolution#avro-full-compatibility`).

Under `BACKWARD` or `BACKWARD_TRANSITIVE`, all consumers are upgraded before new events are produced (`confluent-schema-evolution#order-of-upgrading-clients`).

Under `FORWARD` or `FORWARD_TRANSITIVE`, all producers are upgraded first, and the consumers after (`confluent-schema-evolution#order-of-upgrading-clients`).

Under `FULL` or `FULL_TRANSITIVE`, producers and consumers can be upgraded independently (`confluent-schema-evolution#order-of-upgrading-clients`).

The client controls which partition it publishes messages to (`kafka-design#load-balancing`).

The producer can specify a key to partition by, and Kafka hashes it to a partition (`kafka-design#load-balancing`).

If the key chosen is a user id, all data for a given user is sent to the same partition (`kafka-design#load-balancing`).

In the default partitioning logic, if no partition is specified but a key is present, the partition is chosen from a hash of the key (`kafka-producer-configs#partitioner.class`).

In the default partitioning logic, if no partition or key is present, the producer chooses the sticky partition that changes when at least `batch.size` bytes are produced to the partition (`kafka-producer-configs#partitioner.class`).

With `partitioner.adaptive.partitioning.enable` set to `true`, the producer tries to adapt to broker performance and produces more messages to partitions hosted on faster brokers (`kafka-producer-configs#partitioner.adaptive.partitioning.enable`).

:::esquema{kind=tabla title="Order of upgrading clients per compatibility type"}
| Compatibility type | Order | Source |
|---|---|---|
| `BACKWARD` or `BACKWARD_TRANSITIVE` | Upgrade all consumers before producing new events | `confluent-schema-evolution#order-of-upgrading-clients` |
| `FORWARD` or `FORWARD_TRANSITIVE` | Upgrade all producers first, then the consumers | `confluent-schema-evolution#order-of-upgrading-clients` |
| `FULL` or `FULL_TRANSITIVE` | Upgrade producers and consumers independently | `confluent-schema-evolution#order-of-upgrading-clients` |
:::

## Error handling, retries and dead letters
<!-- bullets: 8.2.c -->

In Spring for Apache Kafka, the `DefaultErrorHandler` can recover a record that keeps failing, and by default it logs the failed record at the ERROR level after ten failures (`spring-kafka-error-handling#default-eh`).

The default recoverer logs the failed record after retries are exhausted (`spring-kafka-error-handling#default-eh`).

In the `DefaultErrorHandler` example with `FixedBackOff(1000L, 2L)`, failures are simply logged after retries are exhausted (`spring-kafka-error-handling#default-eh`).

Using a `FixedBackOff` with `FixedBackOff.UNLIMITED_ATTEMPTS` causes effectively infinite retries (`spring-kafka-error-handling#default-eh`).

The framework provides the `DeadLetterPublishingRecoverer`, which publishes the failed message to another topic (`spring-kafka-error-handling#dead-letters`).

By default, the dead-letter record is sent to a topic named after the original topic with the suffix `-dlt` and to the same partition as the original record (`spring-kafka-error-handling#dead-letters`).

With the default resolver, the dead-letter topic must have at least as many partitions as the original topic (`spring-kafka-error-handling#dead-letters`).

The record sent to the dead-letter topic retains all the headers of the original record (`spring-kafka-error-handling#dead-letters`).

With non-blocking retries, a message whose processing fails is forwarded to a retry topic with a back off timestamp (`spring-kafka-retrytopic-how-it-works#page-title`).

With non-blocking retries, a retry topic consumer that finds a message not yet due pauses the consumption for that topic's partition (`spring-kafka-retrytopic-how-it-works#page-title`).

With an exponential backoff of 1000ms, a multiplier of 2 and 4 max attempts, `main-topic` gets the topics `main-topic-retry-1000`, `main-topic-retry-2000`, `main-topic-retry-4000` and `main-topic-dlt` (`spring-kafka-retrytopic-how-it-works#page-title`).

By using non-blocking retries, a topic loses Kafka's ordering guarantees (`spring-kafka-retrytopic-how-it-works#page-title`).

Non-blocking retries are not supported with batch listeners (`spring-kafka-retrytopic#page-title`).

If no DLT handler is provided, the default `RetryTopicConfigurer.LoggingDltListenerHandlerMethod` is used (`spring-kafka-retrytopic-dlt-strategies#dlt-processing-method`).

`ExponentialBackOffWithMaxRetries(6)` with an initial interval of 1 second, a multiplier of 2 and a maximum interval of 10 seconds retries after 1, 2, 4, 8, 10 and 10 seconds before calling the recoverer (`spring-kafka-error-handling#exp-backoff`).

An Axon Dead-Letter Queue parks an event that could not be handled so it can be handled again later (`axon-dead-letter-queue#cmdk-launch`).

An Axon Dead-Letter Queue prevents handling of later events in the same sequence until the failed event is successfully processed, which preserves event ordering (`axon-dead-letter-queue#cmdk-launch`).

RabbitMQ dead-letters a message by republishing it to an exchange when it is rejected, expires, exceeds a queue length limit or exceeds a quorum queue's delivery limit (`rabbitmq-dlx#overview`).

:::esquema{kind=tabla title="Events that dead-letter a RabbitMQ message"}
| Event | Condition | Source |
|---|---|---|
| Negative acknowledgement | A consumer uses `basic.reject` or `basic.nack` with `requeue` set to false | `rabbitmq-dlx#overview` |
| Expiry | The message expires due to per-message TTL | `rabbitmq-dlx#overview` |
| Length limit | The message is dropped because its queue exceeded a length limit | `rabbitmq-dlx#overview` |
| Delivery limit | The message is returned more times to a quorum queue than the delivery-limit | `rabbitmq-dlx#overview` |
:::

If an entire queue expires, the messages in the queue are not dead-lettered (`rabbitmq-dlx#overview`).

Quorum queues natively support delayed retry, which is the recommended approach for retrying after a transient failure (`rabbitmq-dlx#delayed-retries`).

RabbitMQ detects a dead-letter cycle and drops the message if there was no rejection in the entire cycle (`rabbitmq-dlx#dead-letter-cycle`).

The Kafka consumer's `currentLag` returns the consumer's current lag on a partition (`kafka-javadoc-kafkaconsumer#currentLag(org.apache.kafka.common.TopicPartition)`).

The `currentLag` method returns an empty `OptionalLong` if the lag is not known, for example if there is no position yet or the end offset is not known yet (`kafka-javadoc-kafkaconsumer#currentLag(org.apache.kafka.common.TopicPartition)`).

The `currentLag` method uses locally cached metadata (`kafka-javadoc-kafkaconsumer#currentLag(org.apache.kafka.common.TopicPartition)`).

## Delivery semantics and idempotent consumers
<!-- bullets: 8.2.d -->

At most once means messages may be lost but are never redelivered (`kafka-design#message-delivery-semantics`).

At least once means messages are never lost but may be redelivered (`kafka-design#message-delivery-semantics`).

Exactly once means each message is processed once and only once (`kafka-design#message-delivery-semantics`).

Since 0.11.0.0, the Kafka producer supports an idempotent delivery option which guarantees that resending will not result in duplicate entries in the log (`kafka-design#message-delivery-semantics`).

For idempotent delivery, the broker assigns each producer an ID and deduplicates messages using a sequence number sent by the producer with every message (`kafka-design#message-delivery-semantics`).

When `enable.idempotence` is `true`, the producer ensures that exactly one copy of each message is written in the stream (`kafka-producer-configs#enable.idempotence`).

Enabling idempotence requires `max.in.flight.requests.per.connection` to be at most 5, `retries` to be greater than 0, and `acks` to be `all` (`kafka-producer-configs#enable.idempotence`).

Idempotence is enabled by default if no conflicting configurations are set (`kafka-producer-configs#enable.idempotence`).

A consumer that reads the messages, saves its position and then processes the messages gives at-most-once semantics, because a crash after saving the position leaves messages unprocessed (`kafka-design#message-delivery-semantics`).

A consumer that reads the messages, processes them and then saves its position gives at-least-once semantics, because a crash before saving the position makes the new process receive messages that were already processed (`kafka-design#message-delivery-semantics`).

In many cases messages have a primary key, so updates are idempotent and receiving the same message twice just overwrites a record with another copy of itself (`kafka-design#message-delivery-semantics`).

Kafka guarantees at-least-once delivery by default, and allows the user to implement at-most-once delivery by disabling retries on the producer and committing offsets in the consumer prior to processing a batch of messages (`kafka-design#message-delivery-semantics`).

Exactly-once delivery for destination systems other than Kafka generally requires cooperation with such systems (`kafka-design#message-delivery-semantics`).

In Kafka, the consumer and producer are separate, and only the producer is transactional (`kafka-design#using-transactions`).

The consumer configuration for exactly-once processing must include `isolation.level=read_committed` and `enable.auto.commit=false` (`kafka-design#using-transactions`).

The producer must set `transactional.id`, and only the producer has the `transactional.id` configuration (`kafka-design#using-transactions`).

With `isolation.level` set to `read_committed`, `consumer.poll()` only returns transactional messages which have been committed (`kafka-consumer-configs#isolation.level`).

With `read_uncommitted`, which is the default, `consumer.poll()` returns all messages, even transactional messages which have been aborted (`kafka-consumer-configs#isolation.level`).

In `read_committed` mode, `consumer.poll()` only returns messages up to the last stable offset, which is one less than the offset of the first open transaction (`kafka-consumer-configs#isolation.level`).

Messages after messages belonging to ongoing transactions are withheld until the relevant transaction has been completed (`kafka-consumer-configs#isolation.level`).

Messages are always returned in offset order (`kafka-consumer-configs#isolation.level`).

In `read_committed` mode, consumers cannot read up to the high watermark when there are in-flight transactions (`kafka-consumer-configs#isolation.level`).

To enable exactly-once semantics in Kafka Streams, set `processing.guarantee`, whose default value is `at_least_once`, to `StreamsConfig.EXACTLY_ONCE_V2` (`kafka-streams-core-concepts#processing-guarantees`).

In Spring for Apache Kafka, using transactions enables exactly-once semantics, and for a read, process, write sequence the sequence is completed exactly once while the read and process have at-least-once semantics (`spring-kafka-exactly-once#page-title`).

In RabbitMQ, messages can be redelivered after a network or node failure, and consumers must be prepared to handle deliveries they have seen in the past (`rabbitmq-reliability#consumer-side`).

RabbitMQ recommends that a consumer is designed to be idempotent rather than to explicitly perform deduplication (`rabbitmq-reliability#consumer-side`).

If the redelivered flag is not set on a RabbitMQ message, it is guaranteed that the message has not been seen before (`rabbitmq-reliability#consumer-side`).

A RabbitMQ publisher cannot assume that a message written to its socket has reached the server and was successfully processed (`rabbitmq-confirms#publisher-confirms`).

In RabbitMQ, a transactional channel cannot be put into confirm mode, and a channel in confirm mode cannot be made transactional (`rabbitmq-confirms#publisher-confirms`).

In AMQP 0-9-1, transactions are unnecessarily heavyweight and decrease throughput by a factor of 250 (`rabbitmq-confirms#publisher-confirms`).

## Key points

- Kafka replicates each partition's log, a write is committed only when all in-sync replicas have received it, and only ISR members can be elected leader.
- With `acks=all`, acknowledgement happens as soon as all current in-sync replicas have the message, and `min.insync.replicas` sets how many in-sync replicas a write needs.
- A higher minimum ISR size guarantees better consistency and reduces availability.
- A consumer's position in a partition is a single offset, and each partition is consumed by exactly one consumer in a group.
- In Apache Kafka 4 the new consumer rebalance protocol is generally available but must be enabled with `group.protocol=consumer`, and the server then controls assignment.
- The Confluent Schema Registry default compatibility type is `BACKWARD`, which is non-transitive.
- A message key hashes to a partition, so all records with the same key go to the same partition.
- After retries are exhausted, the Spring Kafka default recoverer only logs the failed record, and `DeadLetterPublishingRecoverer` publishes it to a dead-letter topic.
- Non-blocking retries lose Kafka's ordering guarantees for the topic.
- RabbitMQ dead-letters a message on rejection, per-message TTL expiry, a queue length limit or a quorum queue delivery limit, but not when a whole queue expires.
- Kafka guarantees at-least-once delivery by default, and idempotence needs `acks=all`.
- A `read_committed` consumer reads only up to the last stable offset.
- RabbitMQ consumers must be prepared for redelivery, and designing them to be idempotent is recommended.

# Zero-downtime schema evolution

## Versioned migrations with Flyway and Liquibase
<!-- bullets: 6.4.a -->

Flyway migrations capture incremental changes to your development database (`flyway-migrations#migrations`).

Flyway migrations are SQL scripts that can capture schema and data changes, such as `CREATE`, `ALTER`, `INSERT` and `UPDATE` (`flyway-migrations#migrations`).

Flyway migrations should be tracked in version control (`flyway-migrations#migrations`).

The same Flyway scripts are run in the same order on each environment, which gives a repeatable deployment process (`flyway-migrations#migrations`).

Flyway migrations can be versioned, repeatable or baseline (`flyway-migrations#migrations`).

Versioned Flyway migrations come in two forms, regular and undo (`flyway-migrations#migrations`).

A changeset is the basic unit of change in Liquibase, and all changesets are stored in the changelog (`liquibase-changeset#main-header`).

A Liquibase changeset contains change types that specify what each change does, such as creating a new table or adding a column to an existing table (`liquibase-changeset#main-header`).

A changeset is uniquely tagged by both the `author` and `id` attributes, as well as the changelog file path (`liquibase-changeset#main-header`).

The `id` of a changeset does not direct the order in which changes are run and does not have to be an integer (`liquibase-changeset#main-header`).

By default, Liquibase runs a changeset as a single transaction, and the `runInTransaction` attribute modifies this behavior (`liquibase-changeset#main-header`).

Once Liquibase has run a changeset, it does not re-run it unless `runAlways` or `runOnChange` is specified for that changeset (`liquibase-changeset#main-header`).

Each Liquibase changeset either succeeds or fails, and a failed changeset can be corrected and deployed again (`liquibase-changeset#main-header`).

```yaml
databaseChangeLog:
  - changeSet:
      id: 1
      author: course
      changes:
        - createIndex:
            tableName: orders
            indexName: orders_customer_idx
            columns:
              - column:
                  name: customer_id
```

:::judgement{source="Liquibase documentation, What is a Changeset?" ref="liquibase-changeset#main-header"}
According to the Liquibase documentation, it is a best practice to specify only one type of change per changeset. Doing so avoids failed auto-commit statements that can leave the database in an unexpected state.
:::

## Locks taken by ALTER TABLE
<!-- bullets: 6.4.a -->

`ALTER TABLE` changes the definition of an existing table (`pg-sql-altertable#id-1.9.3.35.5`).

The lock level required may differ for each `ALTER TABLE` subform (`pg-sql-altertable#id-1.9.3.35.5`).

An `ACCESS EXCLUSIVE` lock is acquired unless explicitly noted (`pg-sql-altertable#id-1.9.3.35.5`).

When multiple subcommands are given, the lock acquired is the strictest one required by any subcommand (`pg-sql-altertable#id-1.9.3.35.5`).

`SET STATISTICS` acquires a `SHARE UPDATE EXCLUSIVE` lock (`pg-sql-altertable#id-1.9.3.35.5`).

Most forms of `ADD table_constraint` require an `ACCESS EXCLUSIVE` lock, but `ADD FOREIGN KEY` requires only a `SHARE ROW EXCLUSIVE` lock (`pg-sql-altertable#id-1.9.3.35.5`).

`ADD FOREIGN KEY` also acquires a `SHARE ROW EXCLUSIVE` lock on the referenced table (`pg-sql-altertable#id-1.9.3.35.5`).

:::esquema{kind=tabla title="Lock levels of ALTER TABLE subforms in PostgreSQL 18"}
| Subform | Lock | Source |
|---|---|---|
| Any subform not explicitly noted | `ACCESS EXCLUSIVE` | `pg-sql-altertable#id-1.9.3.35.5` |
| `ADD FOREIGN KEY` | `SHARE ROW EXCLUSIVE`, also on the referenced table | `pg-sql-altertable#id-1.9.3.35.5` |
| `SET STATISTICS` | `SHARE UPDATE EXCLUSIVE` | `pg-sql-altertable#id-1.9.3.35.5` |
| Several subcommands in one statement | The strictest lock required by any subcommand | `pg-sql-altertable#id-1.9.3.35.5` |
:::

## Building indexes without blocking writes
<!-- bullets: 6.4.a -->

Normally PostgreSQL locks the table to be indexed against writes and performs the entire index build with a single scan of the table (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

While a standard index build runs, other transactions can still read the table, but inserts, updates and deletes block until the build is finished (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

PostgreSQL supports building indexes without locking out writes by specifying the `CONCURRENTLY` option of `CREATE INDEX` (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

A concurrent index build must perform two scans of the table (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

A concurrent index build must wait for all existing transactions that could potentially modify or use the index to terminate (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

A concurrent index build requires more total work than a standard index build and takes significantly longer to complete (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

The extra CPU and I/O load imposed by the index creation might slow other operations (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

In a concurrent index build, the index is entered as an "invalid" index into the system catalogs in one transaction, then two table scans occur in two more transactions (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

After a concurrent build finishes, the index may not be immediately usable for queries, and in the worst case it cannot be used as long as transactions exist that predate the start of the index build (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

If a problem arises while scanning the table, such as a deadlock or a uniqueness violation in a unique index, `CREATE INDEX CONCURRENTLY` fails but leaves behind an "invalid" index (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

An invalid index is ignored for querying purposes because it might be incomplete, but it still consumes update overhead (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

The recommended recovery method is to drop the index and try again to perform `CREATE INDEX CONCURRENTLY` (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

Another possibility is to rebuild the index with `REINDEX INDEX CONCURRENTLY` (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

When a unique index is built concurrently, the uniqueness constraint is already enforced against other transactions when the second table scan begins (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

Concurrent builds of expression indexes and partial indexes are supported (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

Only one concurrent index build can occur on a table at a time (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

A regular `CREATE INDEX` command can be performed within a transaction block, but `CREATE INDEX CONCURRENTLY` cannot (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

Concurrent index builds on partitioned tables are currently not supported (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

You may build the index concurrently on each partition individually and then create the partitioned index non-concurrently, and building the partitioned index is then a metadata only operation (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).

```sql
CREATE INDEX CONCURRENTLY orders_customer_idx ON orders (customer_id);
```

## Changing columns and constraints in small steps
<!-- bullets: 6.4.a -->

`ADD COLUMN` adds a new column to the table, using the same syntax as `CREATE TABLE` (`pg-sql-altertable#id-1.9.3.35.5`).

`SET DEFAULT` and `DROP DEFAULT` apply the new default value only to subsequent `INSERT` or `UPDATE` commands, and do not cause rows already in the table to change (`pg-sql-altertable#id-1.9.3.35.5`).

`ADD table_constraint` normally causes a scan of the table to verify that all existing rows satisfy the new constraint (`pg-sql-altertable#id-1.9.3.35.5`).

With the `NOT VALID` option, `ADD table_constraint` skips that potentially lengthy scan (`pg-sql-altertable#id-1.9.3.35.5`).

`NOT VALID` is currently only allowed for foreign-key, `CHECK` and not-null constraints (`pg-sql-altertable#id-1.9.3.35.5`).

A constraint added as `NOT VALID` is still applied against subsequent inserts or updates (`pg-sql-altertable#id-1.9.3.35.5`).

The database does not assume that a `NOT VALID` constraint holds for all rows in the table until it is validated with the `VALIDATE CONSTRAINT` option (`pg-sql-altertable#id-1.9.3.35.5`).

`SET NOT NULL` may only be applied to a column when none of the records in the table contain a `NULL` value for the column (`pg-sql-altertable#id-1.9.3.35.5`).

`SET NOT NULL` is ordinarily checked by scanning the entire table, unless a valid `CHECK` constraint exists which proves that no `NULL` can exist, in which case the table scan is skipped (`pg-sql-altertable#id-1.9.3.35.5`).

`ADD table_constraint_using_index` adds a new `PRIMARY KEY` or `UNIQUE` constraint to a table based on an existing unique index (`pg-sql-altertable#id-1.9.3.35.5`).

The index used by `ADD table_constraint_using_index` cannot have expression columns, cannot be a partial index, and must be a b-tree index with default sort ordering (`pg-sql-altertable#id-1.9.3.35.5`).

If `PRIMARY KEY` is specified and the index's columns are not already marked `NOT NULL`, `ADD table_constraint_using_index` attempts `SET NOT NULL` on each such column, which requires a full table scan (`pg-sql-altertable#id-1.9.3.35.5`).

`ADD table_constraint_using_index` is not currently supported on partitioned tables (`pg-sql-altertable#id-1.9.3.35.5`).

`SET DATA TYPE` changes the type of a column of a table (`pg-sql-altertable#id-1.9.3.35.5`).

A `USING` clause must be provided in `SET DATA TYPE` if there is no implicit or assignment cast from the old type to the new (`pg-sql-altertable#id-1.9.3.35.5`).

After `SET DATA TYPE`, the column's statistics are removed, so running `ANALYZE` on the table afterwards is recommended (`pg-sql-altertable#id-1.9.3.35.5`).

`DROP COLUMN` drops a column from a table, and indexes and table constraints involving the column are dropped automatically (`pg-sql-altertable#id-1.9.3.35.5`).

`DROP COLUMN` needs `CASCADE` if anything outside the table depends on the column, for example foreign key references or views (`pg-sql-altertable#id-1.9.3.35.5`).

```sql
ALTER TABLE orders ADD CONSTRAINT orders_customer_fk
    FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk;
```

## Key points

- Flyway runs the same migration scripts in the same order on each environment (`flyway-migrations#migrations`).
- A Liquibase changeset is uniquely tagged by `author`, `id` and the changelog file path, and is not re-run unless `runAlways` or `runOnChange` is specified (`liquibase-changeset#main-header`).
- An `ACCESS EXCLUSIVE` lock is acquired by `ALTER TABLE` unless a subform explicitly notes otherwise (`pg-sql-altertable#id-1.9.3.35.5`).
- A standard index build blocks inserts, updates and deletes until it is finished (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).
- `CREATE INDEX CONCURRENTLY` builds an index without locking out writes, at the cost of two table scans and a longer build (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).
- A failed concurrent build leaves an invalid index that is ignored for queries but still consumes update overhead (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).
- `CREATE INDEX CONCURRENTLY` cannot be performed within a transaction block (`pg-sql-createindex#SQL-CREATEINDEX-CONCURRENTLY`).
- `ADD table_constraint ... NOT VALID` skips the table scan and still applies the constraint to subsequent inserts and updates (`pg-sql-altertable#id-1.9.3.35.5`).
- `SET DEFAULT` does not change rows already in the table (`pg-sql-altertable#id-1.9.3.35.5`).

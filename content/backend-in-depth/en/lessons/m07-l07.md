# API evolution and governance

## Compatible and breaking changes in Protocol Buffers
<!-- bullets: 7.7.a -->

A wire-safe change in Protocol Buffers may still be a breaking change to application code in a given language (`protobuf-proto3#wire-safe-changes`).

Adding a value to a preexisting enum would be a compilation break for any code with an exhaustive switch on that enum (`protobuf-proto3#wire-safe-changes`).

Wire-compatible means that the same data can be parsed both before and after a given change, although a parse of the data may be lossy (`protobuf-proto3#conditionally-safe-changes`).

Changing an `int32` to an `int64` is a compatible change, but a client that reads a value larger than `INT32_MAX` as an `int32` discards the high order bits of the number (`protobuf-proto3#conditionally-safe-changes`).

Compatible changes can be made only if the roll out to the system is managed carefully (`protobuf-proto3#conditionally-safe-changes`).

A team may change an `int32` to an `int64` while it keeps writing only legal `int32` values until the new schema is deployed to all endpoints (`protobuf-proto3#conditionally-safe-changes`).

If a schema is published outside the organization, wire-compatible changes should generally not be made, because the deployment of the new schema cannot be managed (`protobuf-proto3#conditionally-safe-changes`).

`int32`, `uint32`, `int64`, `uint64` and `bool` are all compatible (`protobuf-proto3#conditionally-safe-changes`).

`sint32` and `sint64` are compatible with each other but not with the other integer types (`protobuf-proto3#conditionally-safe-changes`).

`string` and `bytes` are compatible as long as the bytes are valid UTF-8 (`protobuf-proto3#conditionally-safe-changes`).

Wire-unsafe changes should only be made if all serializers and deserializers of the data are using the new schema (`protobuf-proto3#wire-unsafe-changes`).

The Protocol Buffers best-practices guide says never to re-use a tag number, because it messes up deserialization (`protobuf-proto-best-practices#reuse-number`).

Even if a field is believed unused, a tag number should not be re-used, because serialized versions of the proto could be in a log or old code in another server could break (`protobuf-proto-best-practices#reuse-number`).

The best-practices guide says to almost never change the type of a field, because it messes up deserialization, the same as re-using a tag number (`protobuf-proto-best-practices#change-type`).

Changing the type of a field can be difficult to roll out safely even when the new schema can successfully parse old data (`protobuf-proto-best-practices#change-type`).

:::esquema{kind=tabla title="Protocol Buffers schema changes"}
| Change | Class | Source |
|---|---|---|
| Adding a new field | Wire-safe | `protobuf-proto3#wire-safe-changes` |
| Changing `int32` to `int64` | Wire-compatible, conditionally safe; lossy above `INT32_MAX` | `protobuf-proto3#conditionally-safe-changes` |
| Changing the number of an existing field | Wire-unsafe | `protobuf-proto3#wire-unsafe-changes` |
| Re-using a tag number | Never, according to the best-practices guide | `protobuf-proto-best-practices#reuse-number` |
:::

## API versioning in Spring
<!-- bullets: 7.7.a -->

In Spring Framework 7 there is no standard way to specify an API version, so enabling API versioning in the MVC Config requires specifying how to resolve the version (`spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version`).

The MVC Config creates an `ApiVersionStrategy` that is used to map requests (`spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version`).

:::esquema{kind=tabla title="Values of the version attribute of @RequestMapping"}
| Value | Matches | Source |
|---|---|---|
| Fixed version, such as `"1.2"` | The given version only | `spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version` |
| Baseline version, such as `"1.2+"` | The given version and the supported versions above | `spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version` |
| No value | Any version, but a more specific version match supersedes it | `spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version` |
:::

If multiple controller methods have a version less than or equal to the request version, the highest of those, and closest to the request version, is the one considered (`spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version`).

Among mappings for no version, `1.1`, `1.2+` and `1.5`, a request with version `1.3` is matched by the `1.2+` method, as the highest match (`spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version`).

Among those mappings, a request with version `1.6` has no match, because the unversioned and `1.2+` methods are superseded by the `1.5` method, which allows only a strict match (`spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version`).

In that scenario a `NotAcceptableApiVersionException` results in a `400` response (`spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version`).

Controller methods without a version are intended to support clients created before a versioned alternative was introduced, so an unversioned method gets the lowest priority (`spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version`).

Both `WebClient` and `RestClient` support making versioned remote HTTP calls so that APIs can be evolved over time (`spring-boot-io-rest-client#io.rest-client.apiversioning`).

Versioned calls commonly involve sending an HTTP header, a query parameter or a URL path segment that indicates the version of the API (`spring-boot-io-rest-client#io.rest-client.apiversioning`).

API versioning on a client is configured with methods on `WebClient.Builder` or `RestClient.Builder` (`spring-boot-io-rest-client#io.rest-client.apiversioning`).

In Spring Boot 4 the server-side API versioning configuration is not taken into account to auto-configure the client, so a client that should use a versioning strategy needs to configure it explicitly (`spring-boot-io-rest-client#io.rest-client.apiversioning`).

## Tolerant reader and the robustness principle
<!-- bullets: 7.7.b -->

The robustness principle advises to be strict when sending and tolerant when receiving (`rfc9413#section-2`).

Under the robustness principle, implementations must follow specifications precisely when sending to the network, and tolerate faulty input from the network (`rfc9413#section-2`).

The robustness principle has three main aspects: robustness to software defects, to attacks and to the unexpected (`rfc9413#section-2`).

An interpretation of the robustness principle that advocates tolerating unexpected inputs is no longer considered best practice in all scenarios (`rfc9413#section-2`).

Time and experience show that negative consequences to interoperability accumulate over time if implementations silently accept faulty input (`rfc9413#section-2`).

Many problems that tolerating unexpected input was meant to solve can be better addressed by active maintenance, in which protocol designers, implementers and deployers work together to improve specifications alongside implementations (`rfc9413#section-2`).

Tolerating unexpected input might be an expedient tool for systems in early phases of deployment, but the deferral can amplify the ultimate cost of handling interoperability problems (`rfc9413#section-4.1`).

A flaw can become entrenched as a de facto standard, and any implementation of the protocol is then required to replicate the aberrant behavior, or it is not interoperable (`rfc9413#section-4.1`).

Overapplication of the robustness principle encourages a chain reaction that can create interoperability problems over time (`rfc9413#section-4.1`).

Clients consuming problem details MUST ignore any extension members that they do not recognize, which allows problem types to evolve and include additional information in the future (`rfc9457#section-3.2`).

## Deprecation and sunset signals
<!-- bullets: 7.7.b -->

The `Deprecation` HTTP response header field allows a server to communicate to a client application that the resource will be or has been deprecated (`rfc9745#section-2`).

The server can use links with the `deprecation` link relation type to tell the client application developer where to find more information about the deprecation (`rfc9745#section-3`).

A link with the `deprecation` relation can be sent before the actual deprecation, to make a deprecation policy discoverable, or after it, when there may be documentation about how to manage it (`rfc9745#section-3`).

RFC 9745 places no restrictions on the representation of the linked deprecation policy, which may be human-readable documentation or a machine-readable description (`rfc9745#section-3`).

For Web APIs, deprecation often happens in two stages: the API is no longer the preferred or recommended version, and then the API or a specific version of it is decommissioned (`rfc8594#section-1.4`).

For the first stage the `Sunset` header field is not appropriate, because the API remains operational and can still be used (`rfc8594#section-1.4`).

For the second stage, when the API or a version is decommissioned, the `Sunset` header field is appropriate, because the API or version becomes unresponsive (`rfc8594#section-1.4`).

The announced sunset date typically affects all of the deprecated API or parts of it, and not just a single resource (`rfc8594#section-1.4`).

The `Sunset` header field allows a server to communicate that a resource is expected to become unresponsive at a specific point in time (`rfc8594#section-3`).

The `Sunset` value is an HTTP-date timestamp and SHOULD be a timestamp in the future (`rfc8594#section-3`).

It is safest to consider a `Sunset` timestamp in the past to mean the present time, meaning that the resource is expected to become unavailable at any time (`rfc8594#section-3`).

Clients SHOULD treat `Sunset` timestamps as hints, because it is not guaranteed that the resource will be available until that time and not after it (`rfc8594#section-3`).

After the `Sunset` time has arrived, interactions with the resource are likely to result in `4xx` errors or `3xx` redirects, or the client might not be able to interact with it at all, and the header does not say which (`rfc8594#section-3`).

:::esquema{kind=tabla title="Signals of deprecation and sunset"}
| Signal | What it communicates | Source |
|---|---|---|
| `Deprecation` response header field | The resource will be or has been deprecated | `rfc9745#section-2` |
| `deprecation` link relation type | Where to find more information about the deprecation | `rfc9745#section-3` |
| `Sunset` response header field | The point in time when the resource is expected to become unresponsive | `rfc8594#section-3` |
:::

## API style guides and design review
<!-- bullets: 7.7.c -->

:::judgement{source="Google, API Improvement Proposals, AIP-1" ref="google-aip-1#what-is-an-aip"}
According to Google's AIP-1, an API Improvement Proposal is a design document that gives high-level, concise documentation for API development. The AIPs serve as the source of truth for API-related documentation at Google and as the means by which API teams discuss and come to consensus on API guidance.
:::

:::judgement{source="Google, API Improvement Proposals, AIP-100" ref="google-aip-100#why-is-design-review-important"}
According to Google's AIP-100, design review exists to make the APIs that Google presents to customers simple, intuitive and consistent. The reviewer approaches the API as a naive user and also checks that it is consistent with Google's existing corpus of APIs, because many customers use multiple APIs and conventions and naming choices should line up with their expectations.
:::

:::judgement{source="Google, API Improvement Proposals, AIP-100" ref="google-aip-100#what-is-precedent"}
According to Google's AIP-100, precedent means decisions already made by previous APIs, which generally should be binding upon newer APIs in similar situations. The AIP names naming as the most common example and says that all APIs should implement pagination the same way, and likewise long-running operations, import and export.
:::

:::judgement{source="Google, API Improvement Proposals, AIP-100" ref="google-aip-100#if-my-api-needs-to-violate-a-standard"}
According to Google's AIP-100, an API that needs to violate a design guideline should say so in an internal comment in the proto, with the rationale, and the comment must be prefixed with `aip.dev/not-precedent`. The rationale should follow one of the enumerated reasons listed in AIP-200, and if it does not, the team works with the API reviewer to decide.
:::

:::judgement{source="Google, API Improvement Proposals, AIP-100" ref="google-aip-100#do-i-need-api-design-approval"}
According to Google's AIP-100, a team usually needs API design approval when it launches an API that users can code against, now or in the future, at the beta or GA quality level. The AIP says design review is only expected for APIs that users code directly against.
:::

:::judgement{source="Google, API Improvement Proposals, AIP-190" ref="google-aip-190#guidance"}
According to Google's AIP-190, all names used by an API should be straightforward, intuitive and consistent, across interfaces, resources, collections, methods and messages. The AIP says to use the same name or term for the same concept, to avoid name overloading, and to prefer specific names over overly general ones such as instance, info and service.
:::

## Key points

- Wire-safe changes in Protocol Buffers carry no risk of data loss or new parse failures, but they may still break application code in a given language (`protobuf-proto3#wire-safe-changes`).
- Wire-compatible changes parse before and after, but may be lossy, and should generally not be made when the schema is published outside the organization (`protobuf-proto3#conditionally-safe-changes`).
- A tag number is never re-used, and the type of a field is almost never changed (`protobuf-proto-best-practices#reuse-number`; `protobuf-proto-best-practices#change-type`).
- In Spring Framework 7 the `version` attribute of `@RequestMapping` takes a fixed version, a baseline version with `+`, or no value, and a request version with no match results in a `400` response (`spring-fw-webmvc-controller-ann-requestmapping#mvc-ann-requestmapping-version`).
- A Spring Boot 4 client that should send an API version configures its versioning strategy explicitly (`spring-boot-io-rest-client#io.rest-client.apiversioning`).
- RFC 9413 says the interpretation of the robustness principle that tolerates unexpected input is no longer best practice in all scenarios, because interoperability problems accumulate (`rfc9413#section-2`; `rfc9413#section-4.1`).
- The `Deprecation` header field and the `deprecation` link relation signal deprecation, and the `Sunset` header field gives the point in time when a resource is expected to become unresponsive (`rfc9745#section-2`; `rfc9745#section-3`; `rfc8594#section-3`).
- `Sunset` is appropriate for the decommissioning stage of deprecation and not for the stage where the API is merely no longer preferred (`rfc8594#section-1.4`).

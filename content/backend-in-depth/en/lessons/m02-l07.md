# Pattern recognition

## Signals for backtracking
<!-- bullets: 2.7.a -->

A problem whose answer is a sequence of decisions, one per step, points to backtracking. The data structure to design is a summary of the decisions already made, and it should be as small as possible.

:::judgement{source="Jeff Erickson, Algorithms, chapter on backtracking" ref="erickson-backtracking#p9"}
According to Jeff Erickson, a problem whose goal is a sequence of decisions, such as where to place the queen in each row or whether to include each input element, is a candidate for backtracking. In his formulation each recursive call makes exactly one decision that is consistent with the earlier ones, so the data structure to choose is a summary of the decisions already made, and it should be as small as possible.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on backtracking" ref="erickson-backtracking#p10"}
In Jeff Erickson's account, when designing a new backtracking algorithm one must work out in advance what information about past decisions is needed in the middle of the algorithm. He writes that if this information is nontrivial, the recursive algorithm might need to solve a more general problem than the one originally asked.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on backtracking" ref="erickson-backtracking#p10"}
As Jeff Erickson describes it, the n-queens problem needs the positions of all previously placed queens, so its past decisions must be remembered in complete detail. The game tree problem needs only the current state of the game, because who wins from a game state does not depend on the moves that created it.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on backtracking" ref="erickson-backtracking#p8"}
According to Jeff Erickson, when designing backtracking algorithms one should aim for the simplest possible variant of the problem, computing a number or even a single boolean instead of more complex information or structure.
:::

## Signals for dynamic programming
<!-- bullets: 2.7.a -->

Dynamic programming fits when a backtracking algorithm solves the same subproblems again and again. The number of distinct subproblems then gives the space of the memoised algorithm.

:::judgement{source="Jeff Erickson, Algorithms, chapter on dynamic programming" ref="erickson-dynamic-programming#p9"}
According to Jeff Erickson, dynamic programming is recursion without repetition. His text segmentation example shows the signal: the backtracking algorithm takes exponential time, yet for a fixed string there are only n different ways to call the recursive function, so the same subproblems repeat.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on dynamic programming" ref="erickson-dynamic-programming#p11"}
According to Jeff Erickson, once the subproblems are identified the remaining steps are to choose a memoization data structure, identify the dependencies between subproblems, find an evaluation order, analyse the space and running time, and write down the algorithm. He says the number of distinct subproblems gives the space complexity of the memoized algorithm.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on dynamic programming" ref="erickson-dynamic-programming#p10"}
Jeff Erickson writes that dynamic programming algorithms are best developed in two stages: formulate the problem recursively, then build solutions to the recurrence from the bottom up. He calls the recursive formulation the hard part, and it begins with a precise specification of the problem to solve.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on depth-first search" ref="erickson-dfs#p10"}
Jeff Erickson holds that the dependency graph of a recurrence must be acyclic, or the naive recursive algorithm would never halt. He states that evaluating any recurrence with memoization is exactly the same as performing a depth-first search of that graph.
:::

## Signals for a greedy algorithm
<!-- bullets: 2.7.a -->

Greed is the tempting first idea for an optimisation problem, and Erickson says it almost never works. He asks for a proof of correctness when it does.

:::judgement{source="Jeff Erickson, Algorithms, chapter on dynamic programming" ref="erickson-dynamic-programming#p11"}
According to Jeff Erickson, a greedy strategy is many students' first intuition for problems that should be solved by backtracking or dynamic programming, and it almost never works.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on greedy algorithms" ref="erickson-greedy#p3"}
According to Jeff Erickson, when file sizes and access frequencies both vary, the files should be sorted by the ratio of length to frequency, and swapping two adjacent files that are out of order improves the total cost.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on dynamic programming" ref="erickson-dynamic-programming#p12"}
In Jeff Erickson's advice, whenever you write, or even think, the word greedy, your subconscious is telling you to use dynamic programming.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on dynamic programming" ref="erickson-dynamic-programming#p12"}
According to Jeff Erickson, even for problems that can be correctly solved by greedy algorithms, it is usually more productive to develop a backtracking or dynamic programming algorithm first.
:::

:::judgement{source="Jeff Erickson, Algorithms, chapter on dynamic programming" ref="erickson-dynamic-programming#p12"}
According to Jeff Erickson, a greedy algorithm should earn no credit in any algorithms course without a formal proof of correctness, even if the algorithm is correct.
:::

## The cost of the naive and the better solution
<!-- bullets: 2.7.a -->

Setting the cost of the naive solution next to the better one shows what the pattern buys. In Erickson's text segmentation and longest increasing subsequence examples, dynamic programming turns an exponential cost into a polynomial one.

:::esquema{kind=tabla title="Naive and better solutions in Erickson's examples"}
| Problem | Solution | What the book states | Citation |
| --- | --- | --- | --- |
| Text segmentation | Recursive backtracking | Calls `IsWord` `O(2^n)` times in the worst case | `erickson-dynamic-programming#p9` |
| Text segmentation | Dynamic programming | Makes `O(n^2)` calls to `IsWord`, an exponential improvement | `erickson-dynamic-programming#p9` |
| Longest increasing subsequence | Recursive backtracking | Both backtracking algorithms run in `O(2^n)` time in the worst case | `erickson-dynamic-programming#p13` |
| Longest increasing subsequence | Dynamic programming | The array-based algorithm runs in `O(n^2)` time and uses `O(n)` space | `erickson-dynamic-programming#p15` |
| Class scheduling | Dynamic programming | Evaluating the recursive solution from the bottom up gives an algorithm that runs in `O(n^3)` time | `erickson-greedy#p4` |
| Class scheduling | Greedy | After the initial sort the algorithm is a linear-time loop, so it runs in `O(n log n)` time | `erickson-greedy#p4` |
| Edit distance | Dynamic programming | The memoisation structure uses `O(mn)` space and the algorithm runs in `O(mn)` time | `erickson-dynamic-programming#p18` |
:::

## From a problem statement to a structure
<!-- bullets: 2.7.a -->

Some statements name their structure. The rows below pair a statement with the structure that serves it and the cost its source gives.

:::esquema{kind=tabla title="Problem statements, structures and costs"}
| Problem statement | Structure or pattern | What the source states | Citation |
| --- | --- | --- | --- |
| Fewest edges from a start vertex | Breadth-first search with a queue | Queues support insertion and deletion in `O(1)` time each, so the algorithm runs in `O(V + E)` time | `erickson-graphs#p16` |
| Cheapest path with non-negative weights | Dijkstra's algorithm with a binary heap | Runs in `O(E log V)` time | `erickson-shortest-paths#p16` |
| Order tasks so that every dependency comes first | Depth-first search, reversed postorder | Writing the vertices in reverse postorder takes `O(V + E)` time | `erickson-dfs#p8` |
| Merge groups and ask which group an element belongs to | Disjoint sets with union by rank and path compression | Find still runs in `O(log n)` time in the worst case | `erickson-union-find#p5` |
| Always take the smallest remaining element | `PriorityQueue` | `O(log(n))` time for `offer` and `poll` | `javadoc-priorityqueue#class-priorityqueue-e` |
| Evict the least recently used entry | Access-ordered `LinkedHashMap` | Constant-time performance for the basic operations, assuming the hash function disperses elements properly | `javadoc-linkedhashmap#class-linkedhashmap-k-v` |
:::

## Key points

- The class scheduling problem takes `O(n^3)` time with dynamic programming and `O(n log n)` time with a greedy algorithm, and the edit distance algorithm takes `O(mn)` time.
- A breadth-first search takes `O(V + E)` time, Dijkstra's algorithm with a binary heap takes `O(E log V)` time, and a `PriorityQueue` takes `O(log(n))` time for `offer` and `poll`.
- A backtracking algorithm and a dynamic programming algorithm for text segmentation call `IsWord` `O(2^n)` and `O(n^2)` times in the worst case.
- The two backtracking algorithms for the longest increasing subsequence run in `O(2^n)` time, and the array-based dynamic programming algorithm runs in `O(n^2)` time and uses `O(n)` space.

# Deterministic testing

## Parameterized tests and assertions in JUnit 5
<!-- bullets: 11.4.a -->

Parameterized tests make it possible to run a test method multiple times with different arguments. (`junit-writing-parameterized#parameterized-classes-and-tests`)

A parameterized test is declared like a regular `@Test` method but uses the `@ParameterizedTest` annotation instead. (`junit-writing-parameterized#parameterized-classes-and-tests`)

A parameterized test must declare at least one source that provides the arguments for each invocation. (`junit-writing-parameterized#parameterized-classes-and-tests`)

In the user guide's `@ValueSource` example, each invocation is reported separately. (`junit-writing-parameterized#parameterized-classes-and-tests`)

The same `@ValueSource` annotation can be used to specify the source of arguments for a `@ParameterizedClass`. (`junit-writing-parameterized#parameterized-classes-and-tests`)

All JUnit Jupiter assertions are static methods in the `org.junit.jupiter.api.Assertions` class. (`junit-writing-assertions#assertions`)

An assertion method optionally accepts the assertion message as its third parameter, either a `String` or a `Supplier<String>`. (`junit-writing-assertions#assertions`)

When the message is a `Supplier<String>`, it is evaluated lazily. (`junit-writing-assertions#assertions`)

A lazily evaluated message is only evaluated when the assertion fails. (`junit-writing-assertions#assertions`)

In an `assertAll` group, all assertions are executed and all failures are reported together. (`junit-writing-assertions#assertions`)

Within a code block of a grouped assertion, if an assertion fails the subsequent code in the same block is skipped. (`junit-writing-assertions#assertions`)

In the user guide, `assertThrows` receives the expected exception type and an executable, and the exception it returns is checked for the message `/ by zero`. (`junit-writing-assertions#assertions`)

The `assertTimeoutPreemptively` methods execute the provided executable or supplier in a different thread than that of the calling code. (`junit-writing-assertions#assertions`)

Running in a different thread can lead to undesirable side effects if the executed code relies on `java.lang.ThreadLocal` storage. (`junit-writing-assertions#assertions`)

Spring's testing support binds transaction state to the current thread, via a `ThreadLocal`, before a test method is invoked. (`junit-writing-assertions#assertions`)

Actions of a Spring-managed component called from `assertTimeoutPreemptively` are committed to the persistent store even though the test-managed transaction is rolled back. (`junit-writing-assertions#assertions`)

## Test instances and their lifecycle
<!-- bullets: 11.4.a -->

JUnit creates a new instance of each test class before executing each test method. (`junit-writing-lifecycle#test-instance-lifecycle`)

This per-method test instance lifecycle is the default behavior in JUnit Jupiter. (`junit-writing-lifecycle#test-instance-lifecycle`)

Annotating a test class with `@TestInstance(Lifecycle.PER_CLASS)` makes JUnit Jupiter execute all test methods on the same test instance. (`junit-writing-lifecycle#test-instance-lifecycle`)

In per-class mode, a new test instance is created once per test class. (`junit-writing-lifecycle#test-instance-lifecycle`)

In per-class mode, `@BeforeAll` and `@AfterAll` can be declared on non-static methods. (`junit-writing-lifecycle#test-instance-lifecycle`)

In per-class mode, tests that rely on state stored in instance variables may need to reset that state in `@BeforeEach` or `@AfterEach` methods. (`junit-writing-lifecycle#test-instance-lifecycle`)

A test class is still instantiated when a test method is disabled via a condition such as `@Disabled`, even in per-method mode. (`junit-writing-lifecycle#test-instance-lifecycle`)

:::esquema{kind=tabla title="JUnit Jupiter test instance lifecycle modes"}
| Mode | Test instances | Source |
|---|---|---|
| Per-method (default) | A new instance of the test class before each test method | `junit-writing-lifecycle#test-instance-lifecycle` |
| Per-class (`@TestInstance(Lifecycle.PER_CLASS)`) | One instance per test class; `@BeforeAll` and `@AfterAll` may be non-static | `junit-writing-lifecycle#test-instance-lifecycle` |
:::

## Mockito and AssertJ
<!-- bullets: 11.4.a -->

Once created, a Mockito mock remembers all interactions. (`mockito-javadoc-source#1`)

The Mockito Javadoc asks readers not to mock the `List` class in reality and to use a real instance instead. (`mockito-javadoc-source#1`)

Mockito can mock concrete classes, not just interfaces. (`mockito-javadoc-source#2`)

By default, for all methods that return a value, a mock returns either `null`, a primitive or primitive wrapper value, or an empty collection, as appropriate. (`mockito-javadoc-source#2`)

An unstubbed mock returns `0` for an `int` or `Integer` and `false` for a `boolean` or `Boolean`. (`mockito-javadoc-source#2`)

A call stubbed with `thenThrow(new RuntimeException())` throws a runtime exception. (`mockito-javadoc-source#2`)

Once stubbed, a method always returns the stubbed value, however many times it is called. (`mockito-javadoc-source#2`)

When the same method is stubbed with the same arguments many times, the last stubbing is the one that counts. (`mockito-javadoc-source#2`)

Overriding a stubbing is a potential code smell that points out too much stubbing. (`mockito-javadoc-source#2`)

Verifying a stubbed invocation is possible but usually redundant. (`mockito-javadoc-source#2`)

The AssertJ Core Javadoc explains each assertion, most of them with code examples. (`assertj-docs#assertj-core-assertions-guide`)

## Injecting a Clock and testing edge cases
<!-- bullets: 11.4.a -->

`Clock.fixed(Instant, ZoneId)` obtains a clock that always returns the same instant. (`javadoc-clock#fixed(java.time.Instant,java.time.ZoneId)`)

The main use case of a fixed clock is testing, where it ensures tests are not dependent on the current clock. (`javadoc-clock#fixed(java.time.Instant,java.time.ZoneId)`)

The clock returned by `Clock.fixed` is immutable, thread-safe and `Serializable`. (`javadoc-clock#fixed(java.time.Instant,java.time.ZoneId)`)

The zone of a fixed clock converts its instant to date-time. (`javadoc-clock#fixed(java.time.Instant,java.time.ZoneId)`)

The `Invoice` below takes the `Clock` as a parameter instead of reading the system time. The test code builds a fixed clock for `2026-03-31T23:30:00Z` in two zones.

```java snippet=m11-l04/FixedClockDemo.java
import java.time.Clock;
import java.time.Instant;
import java.time.LocalDate;
import java.time.ZoneId;

public class FixedClockDemo {
    record Invoice(LocalDate dueDate) {
        boolean isOverdue(Clock clock) {
            return LocalDate.now(clock).isAfter(dueDate);
        }
    }

    public static void main(String[] args) {
        Instant instant = Instant.parse("2026-03-31T23:30:00Z");
        Clock utc = Clock.fixed(instant, ZoneId.of("UTC"));
        Clock madrid = Clock.fixed(instant, ZoneId.of("Europe/Madrid"));
        Invoice invoice = new Invoice(LocalDate.of(2026, 3, 31));
        System.out.println(LocalDate.now(utc));
        System.out.println(LocalDate.now(madrid));
        System.out.println(invoice.isOverdue(utc));
        System.out.println(invoice.isOverdue(madrid));
        System.out.println(utc.instant().equals(madrid.instant()));
    }
}
```

`LocalDate.now(utc)` prints `2026-03-31`.

`LocalDate.now(madrid)` for the same instant prints `2026-04-01`.

An invoice due on `2026-03-31` is not overdue under the `UTC` clock.

The same invoice is overdue under the `Europe/Madrid` clock.

The two clocks report equal instants.

A boundary check runs the same method with the clock one second before, exactly at and one second after the expiry.

```java snippet=m11-l04/ExpiryBoundary.java
import java.time.Clock;
import java.time.Instant;
import java.time.ZoneOffset;

public class ExpiryBoundary {
    static boolean isExpired(Instant expiresAt, Clock clock) {
        return clock.instant().isAfter(expiresAt);
    }

    public static void main(String[] args) {
        Instant expiresAt = Instant.parse("2026-01-01T00:00:00Z");
        for (long offsetSeconds : new long[] {-1, 0, 1}) {
            Clock clock = Clock.fixed(expiresAt.plusSeconds(offsetSeconds), ZoneOffset.UTC);
            System.out.println("offset " + offsetSeconds + ": " + isExpired(expiresAt, clock));
        }
        Clock stopped = Clock.fixed(expiresAt, ZoneOffset.UTC);
        System.out.println("same instant twice: " + stopped.instant().equals(stopped.instant()));
    }
}
```

`isAfter` reports an instant exactly at the expiry as not expired.

One second after the expiry the token is expired.

A fixed clock returns an equal instant on every call.

Integer overflow is an edge case a table of inputs catches. The expected value in the snippet is computed with `long` arithmetic.

```java snippet=m11-l04/MidpointCases.java
public class MidpointCases {
    static int midpoint(int low, int high) {
        return (low + high) / 2;
    }

    public static void main(String[] args) {
        int[][] cases = {{0, 10}, {4, 4}, {Integer.MAX_VALUE - 1, Integer.MAX_VALUE}};
        for (int[] c : cases) {
            long expected = ((long) c[0] + c[1]) / 2;
            System.out.println(c[0] + "," + c[1] + " -> " + midpoint(c[0], c[1]) + " expected " + expected);
        }
    }
}
```

`midpoint(Integer.MAX_VALUE - 1, Integer.MAX_VALUE)` returns `-1` instead of `2147483646`.

## Integration tests with Testcontainers
<!-- bullets: 11.4.b -->

The Testcontainers JUnit 5 module provides an API based on the JUnit Jupiter extension model. (`testcontainers-junit5#jupiter-junit-5`)

The extension supports a mode in which containers are restarted for every test method. (`testcontainers-junit5#jupiter-junit-5`)

The extension supports a mode in which containers are shared between all methods of a test class. (`testcontainers-junit5#jupiter-junit-5`)

The Jupiter integration is packaged as a separate library JAR. (`testcontainers-junit5#jupiter-junit-5`)

Shared containers are defined as static fields in a top level test class and have to be annotated with `@Container`. (`testcontainers-junit5#shared-containers`)

Shared containers can't be declared inside nested test classes. (`testcontainers-junit5#shared-containers`)

A PostgreSQL container instance can be started from any Java application with `new PostgreSQLContainer("postgres:9.6.12")`. (`testcontainers-postgres#usage-example`)

:::esquema{kind=tabla title="Testcontainers container lifetime with the JUnit Jupiter extension"}
| Mode | Container lifetime | Source |
|---|---|---|
| Restarted | Restarted for every test method | `testcontainers-junit5#jupiter-junit-5` |
| Shared | Shared between all methods of a test class; a static `@Container` field of a top level test class | `testcontainers-junit5#jupiter-junit-5`; `testcontainers-junit5#shared-containers` |
:::

## Key points

- A parameterized test uses `@ParameterizedTest` and declares at least one source of arguments.
- All JUnit Jupiter assertions are static methods of `org.junit.jupiter.api.Assertions`, and a `Supplier<String>` message is evaluated lazily.
- `assertTimeoutPreemptively` runs the executable in a different thread, so `ThreadLocal` state such as Spring's test transaction does not follow it.
- JUnit Jupiter creates a new test instance before each test method by default, and `@TestInstance(Lifecycle.PER_CLASS)` shares one instance.
- An unstubbed Mockito mock returns `null`, a primitive wrapper value or an empty collection; the last stubbing of the same call wins.
- `Clock.fixed` returns the same instant on every call, and the zone decides the date: `2026-03-31T23:30:00Z` is `2026-04-01` in `Europe/Madrid`.
- A boundary test checks one second before, exactly at and one second after the limit; `(low + high) / 2` overflows near `Integer.MAX_VALUE`.
- Testcontainers shared containers are static `@Container` fields of a top level test class, containers in the restarted mode live for one test method.

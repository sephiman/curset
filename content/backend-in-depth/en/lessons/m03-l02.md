# Classic concurrency and the Java Memory Model

## Visibility, ordering and happens-before
<!-- bullets: 3.2.a -->

Memory that can be shared between threads is called shared memory or heap memory (`jls-17#jls-17.4.1`).

All instance fields, static fields, and array elements are stored in heap memory (`jls-17#jls-17.4.1`).

Local variables, formal method parameters, and exception handler parameters are never shared between threads and are unaffected by the memory model (`jls-17#jls-17.4.1`).

The results of a write by one thread are guaranteed to be visible to a read by another thread only if the write operation happens-before the read operation (`javadoc-concurrent-package#MemoryVisibility`).

If one action happens-before another, then the first is visible to and ordered before the second (`jls-17#jls-17.4.5`).

If two actions are of the same thread and the first comes before the second in program order, then the first happens-before the second (`jls-17#jls-17.4.5`).

If an action synchronizes-with a following action, then the first also happens-before the second (`jls-17#jls-17.4.5`).

The happens-before relation is transitive (`jls-17#jls-17.4.5`).

An unlock action on a monitor synchronizes-with all subsequent lock actions on that monitor (`jls-17#jls-17.4.4`).

A write to a volatile variable synchronizes-with all subsequent reads of that variable by any thread (`jls-17#jls-17.4.4`).

A write to a volatile field happens-before every subsequent read of that field (`jls-17#jls-17.4.5`).

Writes and reads of volatile fields have similar memory consistency effects as entering and exiting monitors, but do not entail mutual exclusion locking (`javadoc-concurrent-package#MemoryVisibility`).

A call to `start()` on a thread happens-before any actions in the started thread (`jls-17#jls-17.4.5`).

All actions in a thread happen-before any other thread successfully returns from a `join()` on that thread (`jls-17#jls-17.4.5`).

Actions in a thread prior to the submission of a `Runnable` to an `Executor` happen-before its execution begins (`javadoc-concurrent-package#MemoryVisibility`).

Actions in a thread prior to placing an object into any concurrent collection happen-before actions subsequent to the access or removal of that element from the collection in another thread (`javadoc-concurrent-package#MemoryVisibility`).

Actions taken by the asynchronous computation represented by a `Future` happen-before actions subsequent to the retrieval of the result via `Future.get()` in another thread (`javadoc-concurrent-package#MemoryVisibility`).

Actions prior to releasing synchronizer methods such as `Lock.unlock`, `Semaphore.release` and `CountDownLatch.countDown` happen-before actions subsequent to a successful acquiring method on the same synchronizer object in another thread (`javadoc-concurrent-package#MemoryVisibility`).

The snippet writes a plain `int` field and then sets a `volatile` flag in one thread, while the main thread spins on the flag.

```java snippet=m03-l02/VolatileHandoff.java
public class VolatileHandoff {
    static int payload;
    static volatile boolean ready;

    public static void main(String[] args) throws InterruptedException {
        Thread writer = new Thread(() -> {
            payload = 42;
            ready = true;
        });
        writer.start();
        while (!ready) {
            Thread.onSpinWait();
        }
        System.out.println("payload after the volatile read: " + payload);
        writer.join();
        System.out.println("writer alive after join: " + writer.isAlive());
    }
}
```

The snippet prints `payload after the volatile read: 42`, because the write of the flag happens-before the read that sees it.

It then prints `writer alive after join: false`, after `join()` returns.

For the purposes of the Java programming language memory model, a single write to a non-volatile `long` or `double` value is treated as two separate writes, one to each 32-bit half (`jls-17#jls-17.7`).

A thread can see the first 32 bits of a 64-bit value from one write and the second 32 bits from another write (`jls-17#jls-17.7`).

Writes and reads of volatile `long` and `double` values are always atomic (`jls-17#jls-17.7`).

Writes to and reads of references are always atomic, regardless of whether they are implemented as 32-bit or 64-bit values (`jls-17#jls-17.7`).

An implementation of the Java Virtual Machine is free to perform writes to `long` and `double` values atomically or in two parts (`jls-17#jls-17.7`).

Programmers are encouraged to declare shared 64-bit values as `volatile` or synchronize their programs correctly to avoid possible complications (`jls-17#jls-17.7`).

:::esquema{kind=tabla title="Edges that give happens-before"}
| Edge | What it orders | Source |
|---|---|---|
| Monitor unlock and later lock | An unlock of a monitor happens-before every subsequent lock of that monitor | `jls-17#jls-17.4.5` |
| Volatile write and later read | A write to a volatile field happens-before every subsequent read of that field | `jls-17#jls-17.4.5` |
| `Thread.start()` | A call to `start()` happens-before any action in the started thread | `jls-17#jls-17.4.5` |
| `Thread.join()` | All actions in a thread happen-before another thread returns from `join()` on it | `jls-17#jls-17.4.5` |
| Submission to an `Executor` | Actions before the submission of a `Runnable` happen-before its execution begins | `javadoc-concurrent-package#MemoryVisibility` |
| Placing an object into a concurrent collection | Actions before the placement happen-before actions after its access or removal in another thread | `javadoc-concurrent-package#MemoryVisibility` |
:::

## Atomic classes
<!-- bullets: 3.2.a -->

The `java.util.concurrent.atomic` package is a small toolkit of classes that support lock-free thread-safe programming on single variables (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

Instances of the `Atomic` classes maintain values that are accessed and updated using methods otherwise available for fields using associated atomic `VarHandle` operations (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

`AtomicBoolean`, `AtomicInteger`, `AtomicLong` and `AtomicReference` each provide access and updates to a single variable of the corresponding type (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

`AtomicLong` and `AtomicInteger` provide atomic increment methods (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

Arbitrary transformations of the contained value are provided both by low-level read-modify-write operations such as `compareAndSet` and by higher-level methods such as `getAndUpdate` (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

The atomic classes are not general purpose replacements for `java.lang.Integer` and related classes (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

Because atomic variables are expected to be mutated, they are poor choices for hash table keys (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

`AtomicIntegerArray`, `AtomicLongArray` and `AtomicReferenceArray` provide volatile access semantics for their array elements (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

The `AtomicStampedReference` class associates an integer value with a reference (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

The `AtomicMarkableReference` class associates a single boolean with a reference (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

`LongAdder` holds one or more variables that together maintain an initially zero long sum (`javadoc-atomic-package#package-java-util-concurrent-atomic`).

The snippet increments an `AtomicInteger` and a `LongAdder` from four threads, then applies `compareAndSet` and `getAndUpdate`.

```java snippet=m03-l02/AtomicCounters.java
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.AtomicReference;
import java.util.concurrent.atomic.LongAdder;

public class AtomicCounters {
    public static void main(String[] args) throws InterruptedException {
        AtomicInteger counter = new AtomicInteger();
        LongAdder adder = new LongAdder();
        Thread[] threads = new Thread[4];
        for (int i = 0; i < threads.length; i++) {
            threads[i] = new Thread(() -> {
                for (int n = 0; n < 10_000; n++) {
                    counter.incrementAndGet();
                    adder.increment();
                }
            });
            threads[i].start();
        }
        for (Thread thread : threads) {
            thread.join();
        }
        System.out.println(counter.get() + " " + adder.sum());
        System.out.println(counter.compareAndSet(40_000, 1) + " " + counter.compareAndSet(40_000, 2) + " " + counter.get());
        System.out.println(counter.getAndUpdate(value -> value + 10) + " " + counter.get());
        AtomicReference<String> owner = new AtomicReference<>("none");
        System.out.println(owner.compareAndSet("none", "alice") + " " + owner.compareAndSet("none", "bob") + " " + owner.get());
    }
}
```

The snippet prints `40000 40000`, because each of the four threads adds 10,000 increments to both the `AtomicInteger` and the `LongAdder`.

It prints `true false 1`, because the first `compareAndSet(40_000, 1)` succeeds and the second `compareAndSet(40_000, 2)` finds the value 1.

It prints `1 11`, because `getAndUpdate` returns the previous value 1 and leaves 11.

It prints `true false alice`, because only the first `compareAndSet` on the `AtomicReference` finds the expected value `none`.

## Executors, thread pools and ForkJoinPool
<!-- bullets: 3.2.b -->

An `ExecutorService` is an `Executor` that provides methods to manage termination and methods that can produce a `Future` for tracking progress of one or more asynchronous tasks (`javadoc-executorservice#interface-executorservice`).

An `ExecutorService` can be shut down, which will cause it to reject new tasks (`javadoc-executorservice#interface-executorservice`).

The `shutdown()` method will allow previously submitted tasks to execute before terminating, while the `shutdownNow()` method prevents waiting tasks from starting and attempts to stop currently executing tasks (`javadoc-executorservice#interface-executorservice`).

An unused `ExecutorService` should be shut down to allow reclamation of its resources (`javadoc-executorservice#interface-executorservice`).

The `submit` method extends `Executor.execute(Runnable)` by creating and returning a `Future` that can be used to cancel execution and/or wait for completion (`javadoc-executorservice#interface-executorservice`).

The `invokeAny` and `invokeAll` methods execute a collection of tasks and then wait for at least one, or all, to complete (`javadoc-executorservice#interface-executorservice`).

The `Executors` class provides factory methods for the executor services provided in the `java.util.concurrent` package (`javadoc-executorservice#interface-executorservice`).

Thread pools provide a means of bounding and managing the resources, including threads, consumed when executing a collection of tasks (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

`Executors.newFixedThreadPool(int)` creates a fixed size thread pool (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

`Executors.newCachedThreadPool()` creates an unbounded thread pool, with automatic thread reclamation (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

`Executors.newSingleThreadExecutor()` creates a single background thread (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

If fewer than `corePoolSize` threads are running when a task is submitted with `execute(Runnable)`, a new thread is created to handle the request, even if other worker threads are idle (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

If fewer than `maximumPoolSize` threads are running, a new thread will be created to handle the request only if the queue is full (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

By setting `corePoolSize` and `maximumPoolSize` the same, you create a fixed-size thread pool (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

If `corePoolSize` or more threads are running, the executor always prefers queuing a request rather than adding a new thread (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

If a request cannot be queued, a new thread is created unless this would exceed `maximumPoolSize`, in which case the task will be rejected (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

An unbounded queue, for example a `LinkedBlockingQueue` without a predefined capacity, causes new tasks to wait in the queue when all `corePoolSize` threads are busy (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

With an unbounded queue, no more than `corePoolSize` threads will ever be created (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

With an unbounded queue, the value of `maximumPoolSize` does not have any effect (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

A good default choice for a work queue is a `SynchronousQueue` that hands off tasks to threads without otherwise holding them (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

Direct handoffs generally require unbounded `maximumPoolSize` values to avoid rejection of new submitted tasks (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

A bounded queue, for example an `ArrayBlockingQueue`, helps prevent resource exhaustion when used with finite `maximumPoolSize` values, but can be more difficult to tune and control (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

New tasks are rejected when the executor has been shut down, and also when the executor uses finite bounds for both maximum threads and work queue capacity and is saturated (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

In the default `ThreadPoolExecutor.AbortPolicy`, the handler throws a runtime `RejectedExecutionException` upon rejection (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

In `ThreadPoolExecutor.CallerRunsPolicy`, the thread that invokes `execute` itself runs the task (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

In `ThreadPoolExecutor.DiscardPolicy`, a task that cannot be executed is simply dropped (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

By default, even core threads are initially created and started only when new tasks arrive (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).

The snippet builds a pool with one core thread, a maximum of one thread and an `ArrayBlockingQueue` of capacity one, and submits three tasks that block until released.

```java snippet=m03-l02/BoundedPool.java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class BoundedPool {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch release = new CountDownLatch(1);
        ThreadPoolExecutor pool = new ThreadPoolExecutor(1, 1, 0L, TimeUnit.SECONDS, new ArrayBlockingQueue<>(1));
        Runnable blocking = () -> {
            try {
                release.await();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        };
        pool.execute(blocking);
        pool.execute(blocking);
        System.out.println("pool size " + pool.getPoolSize() + ", queued " + pool.getQueue().size());
        try {
            pool.execute(blocking);
        } catch (RejectedExecutionException e) {
            System.out.println("third task: " + e.getClass().getSimpleName());
        }
        release.countDown();
        pool.shutdown();
        System.out.println("terminated: " + pool.awaitTermination(5, TimeUnit.SECONDS));
        System.out.println("completed tasks: " + pool.getCompletedTaskCount());
    }
}
```

The snippet prints `pool size 1, queued 1`, because the first task took the only thread and the second waits in the queue.

It prints `third task: RejectedExecutionException`, because the queue is full and the pool cannot exceed one thread.

It then prints `terminated: true` and `completed tasks: 2` after the latch is released and the pool is shut down.

A `ForkJoinPool` differs from other kinds of `ExecutorService` mainly by virtue of employing work-stealing (`javadoc-forkjoinpool#class-forkjoinpool`).

In a `ForkJoinPool`, all threads in the pool attempt to find and execute tasks submitted to the pool and/or created by other active tasks (`javadoc-forkjoinpool#class-forkjoinpool`).

All worker threads of a `ForkJoinPool` are initialized with `Thread.isDaemon()` set true (`javadoc-forkjoinpool#class-forkjoinpool`).

A static `commonPool()` is available and appropriate for most applications (`javadoc-forkjoinpool#class-forkjoinpool`).

The common pool is used by any `ForkJoinTask` that is not explicitly submitted to a specified pool (`javadoc-forkjoinpool#class-forkjoinpool`).

A `ForkJoinPool` may be constructed with a given target parallelism level, which by default is equal to the number of available processors (`javadoc-forkjoinpool#class-forkjoinpool`).

## CompletableFuture
<!-- bullets: 3.2.b -->

A `CompletableFuture` is a `Future` that may be explicitly completed, and may be used as a `CompletionStage`, supporting dependent functions and actions that trigger upon its completion (`javadoc-completablefuture#class-completablefuture-t`).

When two or more threads attempt to complete, `completeExceptionally` or cancel a `CompletableFuture`, only one of them succeeds (`javadoc-completablefuture#class-completablefuture-t`).

All async methods without an explicit `Executor` argument, as well as those involving delays, are performed using the `ForkJoinPool.commonPool()` (`javadoc-completablefuture#class-completablefuture-t`).

`supplyAsync(Supplier, Executor)` returns a new `CompletableFuture` that is asynchronously completed by a task running in the given executor with the value obtained by calling the given `Supplier` (`javadoc-completablefuture#supplyAsync(java.util.function.Supplier,java.util.concurrent.Executor)`).

Actions supplied for dependent completions of non-async methods may be performed by the thread that completes the current `CompletableFuture`, or by any other caller of a completion method (`javadoc-completablefuture#class-completablefuture-t`).

Cancellation of a `CompletableFuture` is treated as just another form of exceptional completion (`javadoc-completablefuture#class-completablefuture-t`).

The `cancel` method has the same effect as `completeExceptionally(new CancellationException())` (`javadoc-completablefuture#class-completablefuture-t`).

The `isCompletedExceptionally()` method can be used to determine if a `CompletableFuture` completed in any exceptional fashion (`javadoc-completablefuture#class-completablefuture-t`).

In case of exceptional completion with a `CompletionException`, the methods `get()` and `get(long, TimeUnit)` throw an `ExecutionException` with the same cause as held in the corresponding `CompletionException` (`javadoc-completablefuture#class-completablefuture-t`).

The methods `join()` and `getNow(T)` instead throw the `CompletionException` directly in these cases (`javadoc-completablefuture#class-completablefuture-t`).

Passing a null value for a parameter that is not a completion result of type `T` will result in a `NullPointerException` being thrown (`javadoc-completablefuture#class-completablefuture-t`).

The snippet runs `supplyAsync` on a fixed pool whose threads are named `billing-`, fails one future with an `IllegalStateException`, and reads the failure with `join`, `get`, `exceptionally` and `handle`.

```java snippet=m03-l02/CompletableFutureFlow.java
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CompletionException;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;

public class CompletableFutureFlow {
    public static void main(String[] args) throws Exception {
        AtomicInteger sequence = new AtomicInteger();
        ExecutorService pool = Executors.newFixedThreadPool(2, task -> new Thread(task, "billing-" + sequence.incrementAndGet()));
        try {
            CompletableFuture<String> named = CompletableFuture.supplyAsync(() -> Thread.currentThread().getName(), pool);
            System.out.println("runs on a billing thread: " + named.join().startsWith("billing-"));

            CompletableFuture<Integer> failing = CompletableFuture.supplyAsync(() -> {
                throw new IllegalStateException("tariff missing");
            }, pool);
            try {
                failing.join();
            } catch (CompletionException e) {
                System.out.println("join throws " + e.getClass().getSimpleName() + " caused by " + e.getCause());
            }
            try {
                failing.get();
            } catch (ExecutionException e) {
                System.out.println("get throws " + e.getClass().getSimpleName() + " caused by " + e.getCause());
            }
            System.out.println(failing.exceptionally(error -> -1).join());
            System.out.println(failing.handle((value, error) -> error == null ? "ok" : "failed").join());
            System.out.println(failing.isCompletedExceptionally());

            CompletableFuture<Integer> cancelled = new CompletableFuture<>();
            cancelled.cancel(true);
            System.out.println(cancelled.isCompletedExceptionally());
        } finally {
            pool.shutdown();
        }
    }
}
```

The snippet prints `runs on a billing thread: true`, because `supplyAsync` ran the supplier in the executor passed to it.

It prints `join throws CompletionException caused by java.lang.IllegalStateException: tariff missing`.

It prints `get throws ExecutionException caused by java.lang.IllegalStateException: tariff missing`, with the same cause.

It prints `-1` for `exceptionally`, `failed` for `handle` and `true` for `isCompletedExceptionally`, and prints `true` again for the future that was cancelled.

## Locks and semaphores
<!-- bullets: 3.2.b -->

A `ReentrantLock` is a reentrant mutual exclusion `Lock` with the same basic behavior and semantics as the implicit monitor lock accessed using `synchronized` methods and statements, but with extended capabilities (`javadoc-reentrantlock#class-reentrantlock`).

A `ReentrantLock` is owned by the thread last successfully locking, but not yet unlocking it (`javadoc-reentrantlock#class-reentrantlock`).

The `lock` method returns immediately if the current thread already owns the lock (`javadoc-reentrantlock#class-reentrantlock`).

The constructor of `ReentrantLock` accepts an optional fairness parameter (`javadoc-reentrantlock#class-reentrantlock`).

When the fairness parameter is set true, under contention, locks favor granting access to the longest-waiting thread (`javadoc-reentrantlock#class-reentrantlock`).

Without fairness, a `ReentrantLock` does not guarantee any particular access order (`javadoc-reentrantlock#class-reentrantlock`).

Fair locks accessed by many threads may display lower overall throughput than the default setting, but have smaller variances in times to obtain locks and guarantee lack of starvation (`javadoc-reentrantlock#class-reentrantlock`).

Fairness of locks does not guarantee fairness of thread scheduling (`javadoc-reentrantlock#class-reentrantlock`).

The untimed `tryLock()` method does not honor the fairness setting (`javadoc-reentrantlock#class-reentrantlock`).

It is recommended practice to always immediately follow a call to `lock` with a `try` block, and to always immediately call `unlock` as the first statement in the `finally` block (`javadoc-reentrantlock#class-reentrantlock`).

A `ReentrantLock` supports a maximum of 2147483647 recursive locks by the same thread (`javadoc-reentrantlock#class-reentrantlock`).

A `StampedLock` is a capability-based lock with three modes for controlling read/write access (`javadoc-stampedlock#class-stampedlock`).

`StampedLock` acquisition methods return a stamp that represents and controls access with respect to a lock state (`javadoc-stampedlock#class-stampedlock`).

When a `StampedLock` is held in write mode, no read locks may be obtained, and all optimistic read validations will fail (`javadoc-stampedlock#class-stampedlock`).

The `tryOptimisticRead()` method returns a non-zero stamp only if the lock is not currently held in write mode (`javadoc-stampedlock#class-stampedlock`).

The `validate(long)` method returns true if the lock has not been acquired in write mode since obtaining a given stamp (`javadoc-stampedlock#class-stampedlock`).

The use of optimistic read mode for short read-only code segments often reduces contention and improves throughput (`javadoc-stampedlock#class-stampedlock`).

Fields read while in optimistic read mode may be wildly inconsistent (`javadoc-stampedlock#class-stampedlock`).

`StampedLock` instances are not reentrant (`javadoc-stampedlock#class-stampedlock`).

Like `Semaphore`, but unlike most `Lock` implementations, a `StampedLock` has no notion of ownership (`javadoc-stampedlock#class-stampedlock`).

Locks acquired in one thread of a `StampedLock` can be released or converted in another (`javadoc-stampedlock#class-stampedlock`).

`StampedLock` does not directly implement the `Lock` or `ReadWriteLock` interfaces (`javadoc-stampedlock#class-stampedlock`).

A zero return from any `try` method of `StampedLock` does not carry any information about the state of the lock, and a subsequent invocation may succeed (`javadoc-stampedlock#class-stampedlock`).

A `Semaphore` is a counting semaphore that conceptually maintains a set of permits (`javadoc-semaphore#class-semaphore`).

Each `acquire()` blocks if necessary until a permit is available, and then takes it (`javadoc-semaphore#class-semaphore`).

Each `release()` adds a permit, potentially releasing a blocking acquirer (`javadoc-semaphore#class-semaphore`).

No actual permit objects are used, because the `Semaphore` just keeps a count of the number available (`javadoc-semaphore#class-semaphore`).

Semaphores are often used to restrict the number of threads that can access some physical or logical resource (`javadoc-semaphore#class-semaphore`).

A semaphore initialized to one and used so that it has at most one permit available is more commonly known as a binary semaphore (`javadoc-semaphore#class-semaphore`).

A binary semaphore can be released by a thread other than the owner, as semaphores have no notion of ownership (`javadoc-semaphore#class-semaphore`).

When the fairness parameter of a `Semaphore` is set false, the class makes no guarantees about the order in which threads acquire permits (`javadoc-semaphore#class-semaphore`).

Without fairness, barging is permitted, so a thread invoking `acquire()` can be allocated a permit ahead of a thread that has been waiting (`javadoc-semaphore#class-semaphore`).

When fairness is set true, the semaphore guarantees that threads invoking any of the acquire methods are selected to obtain permits in first-in-first-out order (`javadoc-semaphore#class-semaphore`).

The untimed `tryAcquire` methods do not honor the fairness setting, but will take any permits that are available (`javadoc-semaphore#class-semaphore`).

Semaphores used to control resource access should generally be initialized as fair, to ensure that no thread is starved out from accessing a resource (`javadoc-semaphore#class-semaphore`).

The snippet takes a `ReentrantLock` twice, reads a `StampedLock` optimistically before and during a write, and drains a `Semaphore` of two permits.

```java snippet=m03-l02/LockModes.java
import java.util.concurrent.Semaphore;
import java.util.concurrent.locks.ReentrantLock;
import java.util.concurrent.locks.StampedLock;

public class LockModes {
    public static void main(String[] args) {
        ReentrantLock lock = new ReentrantLock();
        lock.lock();
        lock.lock();
        System.out.println("hold count " + lock.getHoldCount() + ", held " + lock.isHeldByCurrentThread());
        lock.unlock();
        lock.unlock();
        System.out.println("hold count " + lock.getHoldCount() + ", locked " + lock.isLocked());

        StampedLock stamped = new StampedLock();
        long optimistic = stamped.tryOptimisticRead();
        System.out.println("nonzero stamp " + (optimistic != 0L) + ", valid " + stamped.validate(optimistic));
        long write = stamped.writeLock();
        stamped.unlockWrite(write);
        System.out.println("valid after a write " + stamped.validate(optimistic));
        long writeAgain = stamped.writeLock();
        System.out.println("optimistic stamp while writing " + stamped.tryOptimisticRead());
        stamped.unlockWrite(writeAgain);

        Semaphore permits = new Semaphore(2);
        System.out.println(permits.tryAcquire() + " " + permits.tryAcquire() + " " + permits.tryAcquire());
        permits.release();
        System.out.println("available " + permits.availablePermits());
    }
}
```

The snippet prints `hold count 2, held true` while the `ReentrantLock` is locked twice, and `hold count 0, locked false` after two `unlock` calls.

It prints `nonzero stamp true, valid true`, then `valid after a write false`, once a write lock was taken and released after the optimistic stamp.

It prints `optimistic stamp while writing 0`, because `tryOptimisticRead()` returns zero while the lock is held in write mode.

It prints `true true false` for three `tryAcquire()` calls on a `Semaphore` of two permits, and `available 1` after one `release()`.

## Concurrent collections
<!-- bullets: 3.2.c -->

A `ConcurrentHashMap` is a hash table supporting full concurrency of retrievals and high expected concurrency for updates (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

In a `ConcurrentHashMap` all operations are thread-safe, retrieval operations do not entail locking, and there is not any support for locking the entire table in a way that prevents all access (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

Retrieval operations of a `ConcurrentHashMap`, including `get`, generally do not block, so they may overlap with update operations, including `put` and `remove` (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

An update operation for a given key in a `ConcurrentHashMap` bears a happens-before relation with any non-null retrieval for that key reporting the updated value (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

The iterators of a `ConcurrentHashMap` do not throw `ConcurrentModificationException` (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

The iterators of a `ConcurrentHashMap` are designed to be used by only one thread at a time (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

When a map is undergoing concurrent updates, the results of aggregate status methods including `size`, `isEmpty` and `containsValue` reflect transient states that may be adequate for monitoring or estimation purposes, but not for program control (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

Like `Hashtable` but unlike `HashMap`, a `ConcurrentHashMap` does not allow null to be used as a key or value (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

Resizing a hash table may be a relatively slow operation, so it is a good idea to provide a size estimate as the optional `initialCapacity` constructor argument (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

A `ConcurrentHashMap` can be used as a scalable frequency map by using `LongAdder` values and initializing via `computeIfAbsent` (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

The bulk operations of a `ConcurrentHashMap` proceed sequentially if the current map size is estimated to be less than the given `parallelismThreshold` (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

Using a `parallelismThreshold` of `Long.MAX_VALUE` suppresses all parallelism (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).

When many threads are expected to access a given collection, a `ConcurrentHashMap` is normally preferable to a synchronized `HashMap` (`javadoc-concurrent-package#concurrent-collections-heading`).

A concurrent collection is thread-safe, but not governed by a single exclusion lock (`javadoc-concurrent-package#concurrent-collections-heading`).

The iterators and spliterators of most concurrent collections provide weakly consistent rather than fast-fail traversal (`javadoc-concurrent-package#concurrent-collections-heading`).

A weakly consistent traversal is guaranteed to traverse elements as they existed upon construction exactly once, and may reflect any modifications subsequent to construction (`javadoc-concurrent-package#concurrent-collections-heading`).

A `CopyOnWriteArrayList` is a thread-safe variant of `ArrayList` in which all mutative operations are implemented by making a fresh copy of the underlying array (`javadoc-copyonwritearraylist#class-copyonwritearraylist-e`).

A `CopyOnWriteArrayList` may be more efficient than alternatives when traversal operations vastly outnumber mutations (`javadoc-copyonwritearraylist#class-copyonwritearraylist-e`).

A `CopyOnWriteArrayList` is preferable to a synchronized `ArrayList` when the expected number of reads and traversals greatly outnumber the number of updates to a list (`javadoc-concurrent-package#concurrent-collections-heading`).

The snapshot style iterator of a `CopyOnWriteArrayList` uses a reference to the state of the array at the point that the iterator was created (`javadoc-copyonwritearraylist#class-copyonwritearraylist-e`).

The iterator of a `CopyOnWriteArrayList` will not reflect additions, removals, or changes to the list since the iterator was created (`javadoc-copyonwritearraylist#class-copyonwritearraylist-e`).

The iterator of a `CopyOnWriteArrayList` is guaranteed not to throw `ConcurrentModificationException` (`javadoc-copyonwritearraylist#class-copyonwritearraylist-e`).

The element-changing operations on iterators of a `CopyOnWriteArrayList`, `remove`, `set` and `add`, throw `UnsupportedOperationException` (`javadoc-copyonwritearraylist#class-copyonwritearraylist-e`).

All elements are permitted in a `CopyOnWriteArrayList`, including null (`javadoc-copyonwritearraylist#class-copyonwritearraylist-e`).

A `BlockingQueue` is a `Queue` that additionally supports operations that wait for the queue to become non-empty when retrieving an element, and wait for space to become available in the queue when storing an element (`javadoc-blockingqueue#interface-blockingqueue-e`).

A `BlockingQueue` does not accept null elements (`javadoc-blockingqueue#interface-blockingqueue-e`).

Implementations of `BlockingQueue` throw `NullPointerException` on attempts to add, put or offer a null (`javadoc-blockingqueue#interface-blockingqueue-e`).

A null is used as a sentinel value to indicate failure of `poll` operations (`javadoc-blockingqueue#interface-blockingqueue-e`).

A `BlockingQueue` without any intrinsic capacity constraints always reports a remaining capacity of `Integer.MAX_VALUE` (`javadoc-blockingqueue#interface-blockingqueue-e`).

`BlockingQueue` implementations are designed to be used primarily for producer-consumer queues (`javadoc-blockingqueue#interface-blockingqueue-e`).

All queuing methods of a `BlockingQueue` achieve their effects atomically using internal locks or other forms of concurrency control (`javadoc-blockingqueue#interface-blockingqueue-e`).

The bulk operations `addAll`, `containsAll`, `retainAll` and `removeAll` of a `BlockingQueue` are not necessarily performed atomically unless specified otherwise in an implementation (`javadoc-blockingqueue#interface-blockingqueue-e`).

A `BlockingQueue` does not intrinsically support any kind of close or shutdown operation to indicate that no more items will be added (`javadoc-blockingqueue#interface-blockingqueue-e`).

A common tactic is for producers to insert special end-of-stream or poison objects, which are interpreted accordingly when taken by consumers (`javadoc-blockingqueue#interface-blockingqueue-e`).

The `ConcurrentLinkedQueue` class supplies an efficient scalable thread-safe non-blocking FIFO queue (`javadoc-concurrent-package#queues-heading`).

Five implementations in `java.util.concurrent` support the extended `BlockingQueue` interface: `LinkedBlockingQueue`, `ArrayBlockingQueue`, `SynchronousQueue`, `PriorityBlockingQueue` and `DelayQueue` (`javadoc-concurrent-package#queues-heading`).

The snippet changes an `ArrayList` during iteration, takes an iterator over a `CopyOnWriteArrayList` before an `add`, and exercises `ConcurrentHashMap` and an `ArrayBlockingQueue` of capacity one.

```java snippet=m03-l02/ConcurrentCollections.java
import java.util.ArrayList;
import java.util.ConcurrentModificationException;
import java.util.Iterator;
import java.util.List;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CopyOnWriteArrayList;

public class ConcurrentCollections {
    public static void main(String[] args) {
        List<Integer> plain = new ArrayList<>(List.of(1, 2, 3));
        try {
            for (Integer value : plain) {
                plain.add(value + 10);
            }
        } catch (ConcurrentModificationException e) {
            System.out.println("ArrayList: ConcurrentModificationException");
        }

        List<Integer> snapshotList = new CopyOnWriteArrayList<>(List.of(1, 2, 3));
        Iterator<Integer> snapshot = snapshotList.iterator();
        snapshotList.add(4);
        int seen = 0;
        while (snapshot.hasNext()) {
            snapshot.next();
            seen++;
        }
        System.out.println("CopyOnWriteArrayList: iterator saw " + seen + " of " + snapshotList.size());
        try {
            snapshotList.iterator().remove();
        } catch (UnsupportedOperationException e) {
            System.out.println("iterator remove: UnsupportedOperationException");
        }

        ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
        counts.merge("a", 1, Integer::sum);
        counts.merge("a", 1, Integer::sum);
        System.out.println("merge result " + counts);
        try {
            counts.put(null, 1);
        } catch (NullPointerException e) {
            System.out.println("ConcurrentHashMap null key: NullPointerException");
        }

        BlockingQueue<String> queue = new ArrayBlockingQueue<>(1);
        System.out.println(queue.offer("first") + " " + queue.offer("second") + " " + queue.remainingCapacity());
        try {
            queue.add("third");
        } catch (IllegalStateException e) {
            System.out.println("add on a full queue: IllegalStateException");
        }
        System.out.println(queue.poll() + " " + queue.poll());
        try {
            queue.offer(null);
        } catch (NullPointerException e) {
            System.out.println("offer null: NullPointerException");
        }
    }
}
```

The snippet prints `ArrayList: ConcurrentModificationException`, because the plain list changes while the loop iterates over it.

It prints `CopyOnWriteArrayList: iterator saw 3 of 4`, because the iterator traverses the snapshot taken before the `add`.

It prints `iterator remove: UnsupportedOperationException`, `merge result {a=2}` and `ConcurrentHashMap null key: NullPointerException`.

It prints `true false 0` for two `offer` calls and the remaining capacity of the full queue, and `add on a full queue: IllegalStateException` for the `add`.

It prints `first null` for two `poll` calls, and `offer null: NullPointerException` for a null element.

## Data races and deadlocks
<!-- bullets: 3.2.c -->

Two accesses to the same variable are said to be conflicting if at least one of the accesses is a write (`jls-17#jls-17.4.1`).

When a program contains two conflicting accesses that are not ordered by a happens-before relationship, it is said to contain a data race (`jls-17#jls-17.4.5`).

The happens-before relation defines when data races take place (`jls-17#jls-17.4.5`).

A data race cannot cause incorrect behavior such as returning the wrong length for an array (`jls-17#jls-17.4.5`).

A program is correctly synchronized if and only if all sequentially consistent executions are free of data races (`jls-17#jls-17.4.5`).

If a program is correctly synchronized, then all executions of the program will appear to be sequentially consistent (`jls-17#jls-17.4.5`).

The use of correct synchronization does not ensure that the overall behavior of a program is correct (`jls-17#jls-17.4.5`).

Sequential consistency and freedom from data races still allow errors arising from groups of operations that need to be perceived atomically and are not (`jls-17#jls-17.4.3`).

Within a sequentially consistent execution, there is a total order over all individual actions which is consistent with the order of the program, and each individual action is atomic and immediately visible to every thread (`jls-17#jls-17.4.3`).

Without correct synchronization, very strange, confusing and counterintuitive behaviors are possible (`jls-17#jls-17.4.5`).

In addition to the thread stacks, the Control+Break handler executes a deadlock detection algorithm (`jdk-troubleshoot-tools#JSTGD-GUID-1B4B0983-C25D-40FD-9D59-BF5E8C720F57`).

If any deadlocks are detected, the Control+Break handler prints additional information after the thread dump about each deadlocked thread (`jdk-troubleshoot-tools#JSTGD-GUID-1B4B0983-C25D-40FD-9D59-BF5E8C720F57`).

If the JVM flag `-XX:+PrintConcurrentLocks` is set, the Control+Break handler also prints the list of concurrent locks owned by each thread (`jdk-troubleshoot-tools#JSTGD-GUID-1B4B0983-C25D-40FD-9D59-BF5E8C720F57`).

The default deadlock detection works with locks obtained using the `synchronized` keyword, as well as with locks obtained using the `java.util.concurrent` package (`jdk-troubleshoot-hangs#JSTGD-GUID-5A88BA3D-D0FC-466F-B5B9-566ED0D62DF1`).

The snippet starts two daemon threads that take two `synchronized` monitors in opposite order, and asks `ThreadMXBean.findDeadlockedThreads()` for the result.

```java snippet=m03-l02/DeadlockDetection.java
import java.lang.management.ManagementFactory;
import java.util.Arrays;
import java.util.concurrent.CountDownLatch;

public class DeadlockDetection {
    static final Object first = new Object();
    static final Object second = new Object();

    static Thread worker(String name, Object held, Object wanted, CountDownLatch bothHold) {
        Thread thread = new Thread(() -> {
            synchronized (held) {
                bothHold.countDown();
                try {
                    bothHold.await();
                } catch (InterruptedException e) {
                    return;
                }
                synchronized (wanted) {
                    System.out.println(name + " got both locks");
                }
            }
        }, name);
        thread.setDaemon(true);
        return thread;
    }

    public static void main(String[] args) throws InterruptedException {
        CountDownLatch bothHold = new CountDownLatch(2);
        worker("worker-A", first, second, bothHold).start();
        worker("worker-B", second, first, bothHold).start();
        long[] ids = null;
        while (ids == null) {
            Thread.sleep(20);
            ids = ManagementFactory.getThreadMXBean().findDeadlockedThreads();
        }
        String[] names = Arrays.stream(ManagementFactory.getThreadMXBean().getThreadInfo(ids))
                .map(info -> info.getThreadName() + " is " + info.getThreadState())
                .sorted()
                .toArray(String[]::new);
        System.out.println(ids.length + " deadlocked threads: " + String.join(", ", names));
    }
}
```

The snippet prints `2 deadlocked threads: worker-A is BLOCKED, worker-B is BLOCKED`, because each thread holds one monitor and waits for the other.

## Key points

- Only a write that happens-before a read is guaranteed to be visible to it (`javadoc-concurrent-package#MemoryVisibility`).
- A write to a volatile field happens-before every subsequent read of that field, and it gives no mutual exclusion (`jls-17#jls-17.4.5`; `javadoc-concurrent-package#MemoryVisibility`).
- Writes and reads of volatile `long` and `double` values are always atomic, while a non-volatile one is treated as two separate 32-bit writes (`jls-17#jls-17.7`).
- The `Atomic*` classes support lock-free thread-safe programming on single variables, and they are poor hash table keys (`javadoc-atomic-package#package-java-util-concurrent-atomic`).
- A `ThreadPoolExecutor` prefers a new thread below `corePoolSize`, then queuing, then a new thread up to `maximumPoolSize`, and then rejection (`javadoc-threadpoolexecutor#class-threadpoolexecutor`).
- A pool with finite bounds and a full queue throws `RejectedExecutionException` under the default `AbortPolicy`.
- `CompletableFuture` runs async methods without an explicit executor on `ForkJoinPool.commonPool()`, and `get()` and `join()` report a failure as `ExecutionException` and `CompletionException` with the same cause (`javadoc-completablefuture#class-completablefuture-t`).
- A `StampedLock` is not reentrant and has no notion of ownership, and an optimistic stamp fails validation after a write (`javadoc-stampedlock#class-stampedlock`).
- A fair `ReentrantLock` favors the longest-waiting thread at a cost in throughput, and the untimed `tryLock()` ignores fairness (`javadoc-reentrantlock#class-reentrantlock`).
- A `Semaphore` keeps a count of permits, and a binary one can be released by a thread other than its acquirer (`javadoc-semaphore#class-semaphore`).
- `ConcurrentHashMap` retrievals do not lock, its iterators never throw `ConcurrentModificationException`, and it rejects `null` keys and values (`javadoc-concurrenthashmap#class-concurrenthashmap-k-v`).
- A `CopyOnWriteArrayList` iterator traverses a snapshot and does not reflect later changes (`javadoc-copyonwritearraylist#class-copyonwritearraylist-e`).
- A `BlockingQueue` rejects `null` and reports `Integer.MAX_VALUE` as the remaining capacity when it has no capacity constraint (`javadoc-blockingqueue#interface-blockingqueue-e`).
- Two conflicting accesses not ordered by happens-before make a data race, and correct synchronization does not make the whole program correct (`jls-17#jls-17.4.5`).
- The default deadlock detection covers `synchronized` locks and `java.util.concurrent` locks (`jdk-troubleshoot-hangs#JSTGD-GUID-5A88BA3D-D0FC-466F-B5B9-566ED0D62DF1`).

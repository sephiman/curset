# IoC container and bean lifecycle

## Bean definitions, containers and scopes
<!-- bullets: 5.1.a -->

A Spring IoC container manages one or more beans, created with the configuration metadata that you supply to the container (`spring-fw-beans-definition#bean-overview`).

Within the container, bean definitions are represented as `BeanDefinition` objects (`spring-fw-beans-definition#bean-overview`).

A `BeanDefinition` includes bean behavioral configuration elements, which state how the bean should behave in the container, such as scope and lifecycle callbacks (`spring-fw-beans-definition#bean-overview`).

A `BeanDefinition` also holds references to other beans that the bean needs, and these references are called collaborators or dependencies (`spring-fw-beans-definition#bean-overview`).

You should use an `ApplicationContext` unless you have a good reason for not doing so (`spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory`).

An `ApplicationContext` includes all the functionality of a `BeanFactory`, so it is generally recommended over a plain `BeanFactory` (`spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory`).

With only a plain `DefaultListableBeanFactory`, bean post-processors do not get detected and activated by default (`spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory`).

:::esquema{kind=tabla title="BeanFactory and ApplicationContext"}
| Feature | BeanFactory | ApplicationContext | Citation |
| --- | --- | --- | --- |
| Bean instantiation/wiring | Yes | Yes | `spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory` |
| Integrated lifecycle management | No | Yes | `spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory` |
| Automatic `BeanPostProcessor` registration | No | Yes | `spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory` |
| Built-in `ApplicationEvent` publication mechanism | No | Yes | `spring-fw-beans-beanfactory#context-introduction-ctx-vs-beanfactory` |
:::

The Spring Framework supports six scopes, four of which are available only with a web-aware `ApplicationContext` (`spring-fw-beans-factory-scopes#bean-scopes`).

The `singleton` scope is the default and gives a single object instance for each Spring IoC container (`spring-fw-beans-factory-scopes#bean-scopes`).

The `prototype` scope gives any number of object instances for a single bean definition (`spring-fw-beans-factory-scopes#bean-scopes`).

The scope of the Spring singleton is best described as being per-container and per-bean (`spring-fw-beans-factory-scopes#beans-factory-scopes-singleton`).

The Gang of Four singleton hard-codes the scope of an object, so that one and only one instance of a class is created per `ClassLoader` (`spring-fw-beans-factory-scopes#beans-factory-scopes-singleton`).

The prototype scope creates a new bean instance every time a request for that specific bean is made (`spring-fw-beans-factory-scopes#beans-factory-scopes-prototype`).

By default, `ApplicationContext` implementations eagerly create and configure all singleton beans as part of the initialization process (`spring-fw-beans-factory-lazy-init#page-title`).

Singleton-scoped beans that are set to be pre-instantiated, which is the default, are created when the container is created (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

The container validates the configuration of each bean as the container is created, but the bean properties are not set until the bean is actually created (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

Without circular dependencies, each collaborating bean is totally configured before it is injected into the dependent bean (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

## Lifecycle callbacks and post-processors
<!-- bullets: 5.1.b -->

The container calls `afterPropertiesSet()` for `InitializingBean` and `destroy()` for `DisposableBean`, so the bean can act on initialization and destruction (`spring-fw-beans-factory-nature#beans-factory-lifecycle`).

The JSR-250 `@PostConstruct` and `@PreDestroy` annotations are generally considered best practice for receiving lifecycle callbacks in a modern Spring application (`spring-fw-beans-factory-nature#beans-factory-lifecycle`).

Internally, the Spring Framework uses `BeanPostProcessor` implementations to process any callback interfaces it can find and call the appropriate methods (`spring-fw-beans-factory-nature#beans-factory-lifecycle`).

`InitializingBean` lets a bean perform initialization work after the container has set all necessary properties on the bean (`spring-fw-beans-factory-nature#beans-factory-lifecycle-initializingbean`).

The documentation recommends against `InitializingBean`, because it unnecessarily couples the code to Spring (`spring-fw-beans-factory-nature#beans-factory-lifecycle-initializingbean`).

`@PostConstruct` and initialization methods in general are executed within the container's singleton creation lock (`spring-fw-beans-factory-nature#beans-factory-lifecycle-initializingbean`).

Implementing `DisposableBean` lets a bean get a callback when the container that contains it is destroyed (`spring-fw-beans-factory-nature#beans-factory-lifecycle-disposablebean`).

Spring supports inference of destroy methods, detecting a public `close` or `shutdown` method (`spring-fw-beans-factory-nature#beans-factory-lifecycle-disposablebean`).

As of Spring 2.5, a bean has three options for lifecycle behavior: the `InitializingBean` and `DisposableBean` interfaces, custom `init()` and `destroy()` methods, and the `@PostConstruct` and `@PreDestroy` annotations (`spring-fw-beans-factory-nature#beans-factory-lifecycle-combined-effects`).

If the same method name is configured for more than one lifecycle mechanism, that method is run once (`spring-fw-beans-factory-nature#beans-factory-lifecycle-combined-effects`).

With different initialization methods, the order is the `@PostConstruct` methods, then `afterPropertiesSet()` of `InitializingBean`, then a custom configured `init()` method (`spring-fw-beans-factory-nature#beans-factory-lifecycle-combined-effects`).

Destroy methods are called in the same order: the `@PreDestroy` methods, then `destroy()` of `DisposableBean`, then a custom configured destroy method (`spring-fw-beans-factory-nature#beans-factory-lifecycle-combined-effects`).

For a prototype bean, initialization callbacks are called, but configured destruction callbacks are not (`spring-fw-beans-factory-scopes#beans-factory-scopes-prototype`).

The client code must clean up prototype-scoped objects and release the expensive resources that they hold (`spring-fw-beans-factory-scopes#beans-factory-scopes-prototype`).

`BeanPostProcessor` instances operate on bean instances: the container instantiates a bean instance and then they do their work (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

For each bean instance, the post-processor gets a callback both before the initialization methods are called and after any bean initialization callbacks (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

A bean post-processor typically checks for callback interfaces, or it may wrap a bean with a proxy (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

An `ApplicationContext` automatically detects any beans in the configuration metadata that implement the `BeanPostProcessor` interface (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

You can set the `order` property of a `BeanPostProcessor` only if it implements the `Ordered` interface (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

`BeanPostProcessor` instances added programmatically do not respect the `Ordered` interface (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

`BeanPostProcessor` instances registered programmatically are always processed before those registered through auto-detection, regardless of any explicit ordering (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

Because AOP auto-proxying is implemented as a `BeanPostProcessor` itself, neither `BeanPostProcessor` instances nor the beans they directly reference are eligible for auto-proxying (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

To change the bean definition itself, you use a `BeanFactoryPostProcessor` (`spring-fw-beans-factory-extension#beans-factory-extension-bpp`).

## Injection, circular dependencies and candidate selection
<!-- bullets: 5.1.c -->

Constructor-based DI is accomplished by the container invoking a constructor with a number of arguments, each representing a dependency (`spring-fw-beans-dependencies-factory-collaborators#beans-constructor-injection`).

Setter-based DI is accomplished by the container calling setter methods on your beans after invoking a no-argument constructor or a no-argument static factory method (`spring-fw-beans-dependencies-factory-collaborators#beans-setter-injection`).

The `ApplicationContext` also supports setter-based DI after some dependencies have already been injected through the constructor (`spring-fw-beans-dependencies-factory-collaborators#beans-setter-injection`).

The Spring team generally advocates constructor injection, as it lets you implement application components as immutable objects and ensures that required dependencies are not null (`spring-fw-beans-dependencies-factory-collaborators#beans-setter-injection`).

Setter injection should primarily be used for optional dependencies that can be assigned reasonable default values within the class (`spring-fw-beans-dependencies-factory-collaborators#beans-setter-injection`).

An `@Autowired` annotation on a constructor is not necessary if the target bean defines only one constructor (`spring-fw-beans-annotation-config-autowired#page-title`).

The default behavior is to treat annotated methods and fields as indicating required dependencies (`spring-fw-beans-annotation-config-autowired#page-title`).

A non-required field is not populated at all when its dependency is not available, which leaves its default value in place (`spring-fw-beans-annotation-config-autowired#page-title`).

If you use predominantly constructor injection, it is possible to create an unresolvable circular dependency scenario (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

If classes A and B are injected into each other through constructors, the container detects the circular reference at runtime and throws a `BeanCurrentlyInCreationException` (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

Although it is not recommended, you can configure circular dependencies with setter injection (`spring-fw-beans-dependencies-factory-collaborators#beans-dependency-resolution`).

`@Primary` indicates that a particular bean should be given preference when multiple beans are candidates to be autowired to a single-valued dependency (`spring-fw-beans-annotation-config-autowired-primary#page-title`).

If exactly one primary bean exists among the candidates, it becomes the autowired value (`spring-fw-beans-annotation-config-autowired-primary#page-title`).

As of 6.2, the `@Fallback` annotation demarcates any beans other than the regular ones to be injected (`spring-fw-beans-annotation-config-autowired-primary#page-title`).

`@Qualifier` associates qualifier values with specific arguments, narrowing the set of type matches so that a specific bean is chosen for each argument (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

Qualifier values do not semantically express a reference to a unique bean id (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

Qualifiers do not have to be unique, and they constitute filtering criteria (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

With no qualifier, primary marker or fallback marker, Spring matches the injection point name against the target bean names and chooses the same-named candidate (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

Since version 6.1, matching by parameter name requires the `-parameters` Java compiler flag to be present (`spring-fw-beans-annotation-config-autowired-qualifiers#page-title`).

A lazy-initialized bean tells the IoC container to create a bean instance when it is first requested, rather than at startup (`spring-fw-beans-factory-lazy-init#page-title`).

When a lazy-initialized bean is a dependency of a singleton bean that is not lazy-initialized, the `ApplicationContext` creates the lazy-initialized bean at startup (`spring-fw-beans-factory-lazy-init#page-title`).

You can control lazy initialization for a set of beans with the `@Lazy` annotation on a `@Configuration` class (`spring-fw-beans-factory-lazy-init#page-title`).

## Configuration classes, conditions and profiles
<!-- bullets: 5.1.d -->

Annotating a class with `@Configuration` indicates that its primary purpose is as a source of bean definitions (`spring-fw-beans-java-basic-concepts#page-title`).

`@Configuration` classes let inter-bean dependencies be defined by calling other `@Bean` methods in the same class (`spring-fw-beans-java-basic-concepts#page-title`).

In full mode, cross-method references get redirected to the container's lifecycle management (`spring-fw-beans-java-basic-concepts#page-title`).

`@Bean` methods in a class without `@Configuration`, or in a class with `@Configuration(proxyBeanMethods=false)`, are processed in lite mode (`spring-fw-beans-java-basic-concepts#page-title`).

In lite mode, a Java call to a `@Bean` method is not intercepted by the container and creates a new instance every time (`spring-fw-beans-java-basic-concepts#page-title`).

In lite mode, no CGLIB subclassing has to be applied at runtime, which reduces the overhead and the footprint (`spring-fw-beans-java-basic-concepts#page-title`).

`@Bean` methods on classes without runtime proxying are not meant to declare inter-bean dependencies at all (`spring-fw-beans-java-basic-concepts#page-title`).

The `@Profile` annotation is implemented by using a much more flexible annotation called `@Conditional` (`spring-fw-beans-java-composing#beans-java-conditional`).

`@Conditional` indicates specific `Condition` implementations that should be consulted before a `@Bean` is registered (`spring-fw-beans-java-composing#beans-java-conditional`).

A `@Conditional` annotation on an enclosing `@Configuration` class is applied to a nested `@Configuration` class only if the nested class is reached through the parser's recursion from its enclosing class, or via `@Import` (`spring-fw-beans-java-composing#beans-java-conditional`).

A nested class discovered independently, for example via `@ComponentScan`, is processed using only its own `@Conditional` annotations (`spring-fw-beans-java-composing#beans-java-conditional`).

The `@Profile` annotation lets you indicate that a component is eligible for registration when one or more specified profiles are active (`spring-fw-beans-environment#beans-definition-profiles-java`).

You can activate profiles declaratively through the `spring.profiles.active` property, set through system environment variables, JVM system properties, servlet context parameters in `web.xml`, or an entry in JNDI (`spring-fw-beans-environment#beans-definition-profiles-enable`).

You can activate multiple profiles at once (`spring-fw-beans-environment#beans-definition-profiles-enable`).

In integration tests, active profiles can be declared by using the `@ActiveProfiles` annotation in the `spring-test` module (`spring-fw-beans-environment#beans-definition-profiles-enable`).

## Key points

- Within the container, bean definitions are represented as `BeanDefinition` objects, which include scope, lifecycle callbacks and references to collaborators.
- An `ApplicationContext` includes all the functionality of a `BeanFactory`; a plain `DefaultListableBeanFactory` does not detect bean post-processors by default.
- `singleton` is the default scope, per container and per bean. `prototype` creates a new instance for each request, and its configured destruction callbacks are not called.
- `@PostConstruct` runs first, then `afterPropertiesSet()`, then a custom `init()` method; destruction follows the same order.
- Programmatically registered `BeanPostProcessor` instances ignore `Ordered` and are processed before auto-detected ones.
- Constructor injection can produce an unresolvable circular dependency, reported as a `BeanCurrentlyInCreationException`.
- `@Primary` gives preference to one candidate; `@Qualifier` values narrow the type matches and need not be unique.
- Since 6.1, matching an injection point name to a bean name requires the `-parameters` compiler flag.
- In lite mode, calls between `@Bean` methods are plain Java calls and create a new instance every time.
- A nested class discovered by `@ComponentScan` is processed using only its own `@Conditional` annotations.

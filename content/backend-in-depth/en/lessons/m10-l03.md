# FinOps and infrastructure efficiency

## Requests, limits and QoS classes
<!-- bullets: 10.3.a -->

If the node where a Pod is running has enough of a resource available, it is possible and allowed for a container to use more of that resource than its request specifies (`k8s-resource-management#requests-and-limits`).

Both `cpu` and `memory` limits are applied by the kubelet (and container runtime), and are ultimately enforced by the kernel (`k8s-resource-management#requests-and-limits`).

On Linux, the container runtime typically configures kernel cgroups that apply and enforce the limits you defined (`k8s-resource-management#how-pods-with-resource-limits-are-run`).

`cpu` limits are enforced by CPU throttling (`k8s-resource-management#requests-and-limits`).

Containers may not use more CPU than is specified in their `cpu` limit (`k8s-resource-management#requests-and-limits`).

The CPU limit defines a hard ceiling on how much CPU time the container can use (`k8s-resource-management#how-pods-with-resource-limits-are-run`).

Container runtimes don't terminate Pods or containers for excessive CPU usage (`k8s-resource-management#how-pods-with-resource-limits-are-run`).

`memory` limits are enforced by the kernel with out of memory (OOM) kills (`k8s-resource-management#requests-and-limits`).

Terminations by the kernel for exceeding a memory limit only happen when the kernel detects memory pressure (`k8s-resource-management#requests-and-limits`).

Memory limits are enforced reactively (`k8s-resource-management#requests-and-limits`).

If the process stopped by the out-of-memory subsystem is the container's PID 1, and the container is marked as restartable, Kubernetes restarts the container (`k8s-resource-management#how-pods-with-resource-limits-are-run`).

The CPU request typically defines a weighting (`k8s-resource-management#how-pods-with-resource-limits-are-run`).

If several different containers (cgroups) want to run on a contended system, workloads with larger CPU requests are allocated more CPU time than workloads with small requests (`k8s-resource-management#how-pods-with-resource-limits-are-run`).

The memory request is mainly used during (Kubernetes) Pod scheduling (`k8s-resource-management#how-pods-with-resource-limits-are-run`).

If a container exceeds its memory request and the node that it runs on becomes short of memory overall, it is likely that the Pod the container belongs to will be evicted (`k8s-resource-management#how-pods-with-resource-limits-are-run`).

Kubernetes classifies a Pod into a quality of service (QoS) class based on the resource requests of its Containers, along with how those requests relate to resource limits (`k8s-qos#quality-of-service-classes`).

The possible QoS classes are `Guaranteed`, `Burstable`, and `BestEffort` (`k8s-qos#quality-of-service-classes`).

When a Node runs out of resources, Kubernetes first evicts `BestEffort` Pods running on that Node, followed by `Burstable` and finally `Guaranteed` Pods (`k8s-qos#quality-of-service-classes`).

When the eviction is due to resource pressure, only Pods exceeding resource requests are candidates for eviction (`k8s-qos#quality-of-service-classes`).

## Autoscaling with the HPA and KEDA
<!-- bullets: 10.3.a -->

The HorizontalPodAutoscaler controller operates on the ratio between the desired metric value and the current metric value (`k8s-hpa#algorithm-details`).

If the current metric value is 200m and the desired value is 100m, the number of replicas will be doubled (`k8s-hpa#algorithm-details`).

If the current metric value is instead 50m, you halve the number of replicas (`k8s-hpa#algorithm-details`).

The control plane skips any scaling action if the ratio is sufficiently close to 1.0, within a configurable tolerance of 0.1 by default (`k8s-hpa#algorithm-details`).

When a `targetAverageValue` or `targetAverageUtilization` is specified, the `currentMetricValue` is computed by taking the average of the given metric across all Pods in the scale target of the HorizontalPodAutoscaler (`k8s-hpa#algorithm-details`).

If there were any missing metrics, the control plane recomputes the average more conservatively, assuming those pods were consuming 100% of the desired value in case of a scale down, and 0% in case of a scale up (`k8s-hpa#algorithm-details`).

If any not-yet-ready pods were present and the workload would have scaled up without factoring in missing metrics or not-yet-ready pods, the controller assumes that the not-yet-ready pods are consuming 0% of the desired metric (`k8s-hpa#algorithm-details`).

If multiple metrics are specified in a HorizontalPodAutoscaler, the calculation is done for each metric, and then the largest of the desired replica counts is chosen (`k8s-hpa#algorithm-details`).

The controller considers all recommendations within a configurable window and chooses the highest recommendation from within that window (`k8s-hpa#algorithm-details`).

The `--horizontal-pod-autoscaler-downscale-stabilization` command line option, which configures that window, defaults to 5 minutes (`k8s-hpa#algorithm-details`).

Scaledowns occur gradually, smoothing out the impact of rapidly fluctuating metric values (`k8s-hpa#algorithm-details`).

The `--horizontal-pod-autoscaler-initial-readiness-delay` command line option has a default of 30 seconds (`k8s-hpa#algorithm-details`).

The `--horizontal-pod-autoscaler-cpu-initialization-period` command line option has a default of 5 minutes (`k8s-hpa#algorithm-details`).

If you use the v2 HorizontalPodAutoscaler API, you can use the `behavior` field to configure separate scale-up and scale-down behaviors (`k8s-hpa#configurable-scaling-behavior`).

Configurable scaling behavior is stable since Kubernetes v1.23 (`k8s-hpa#configurable-scaling-behavior`).

Scaling policies let you control the rate of change of replicas while scaling (`k8s-hpa#configurable-scaling-behavior`).

Two settings can be used to prevent flapping: a stabilization window for smoothing replica counts, and a tolerance to ignore minor metric fluctuations below a specified threshold (`k8s-hpa#configurable-scaling-behavior`).

KEDA monitors external event sources, like message queues, databases, or APIs, and automatically adjusts the number of running pods based on real-time demand (`keda-concepts#how-keda-works`).

When things go quiet, KEDA scales back down, all the way to zero if needed (`keda-concepts#how-keda-works`).

KEDA works alongside the existing Kubernetes Horizontal Pod Autoscaler rather than replacing it (`keda-concepts#how-keda-works`).

KEDA feeds the HPA with external metrics, extending it beyond CPU and memory to any event source you can connect to (`keda-concepts#how-keda-works`).

For batch workloads, instead of scaling a running deployment up or down, KEDA creates new Kubernetes Jobs in response to events (`keda-concepts#how-keda-works`).

Deployments and StatefulSets are the most common way to scale workloads with KEDA (`keda-scaling-deployments#scaling-deployments-and-statefulsets`).

Each replica of a resource scaled by KEDA is actively pulling items from the event source (`keda-scaling-deployments#scaling-deployments-and-statefulsets`).

With KEDA and scaling Deployments or StatefulSets, you can scale based on events while also preserving rich connection and processing semantics with the event source, such as in-order processing, retries, deadletter and checkpointing (`keda-scaling-deployments#scaling-deployments-and-statefulsets`).

With an Apache Kafka topic as event source, when no messages are pending processing, KEDA can scale the deployment to zero (`keda-scaling-deployments#scaling-deployments-and-statefulsets`).

When a message arrives, KEDA detects this event and activates the deployment (`keda-scaling-deployments#scaling-deployments-and-statefulsets`).

As more messages arrive at the Kafka topic, KEDA can feed this data to the HPA to drive scale out (`keda-scaling-deployments#scaling-deployments-and-statefulsets`).

## Keeping traffic inside a zone
<!-- bullets: 10.3.a -->

Topology Aware Routing provides a mechanism to help keep traffic within the zone it originated from (`k8s-topology-aware-routing#motivation`).

When calculating the endpoints for a Service, the EndpointSlice controller considers the topology (region and zone) of each endpoint and populates the `hints` field to allocate it to a zone (`k8s-topology-aware-routing#motivation`).

Cluster components such as kube-proxy can consume those hints and use them to influence how the traffic is routed, favoring topologically closer endpoints (`k8s-topology-aware-routing#motivation`).

The `.spec.trafficDistribution` field provides another way to influence traffic routing within a Kubernetes Service (`k8s-service#traffic-distribution`).

While traffic policies focus on strict semantic guarantees, traffic distribution allows you to express preferences, such as routing to topologically closer endpoints (`k8s-service#traffic-distribution`).

Traffic distribution can help optimize for performance, cost, or reliability (`k8s-service#traffic-distribution`).

:::esquema{kind=tabla title="Values of `.spec.trafficDistribution` in Kubernetes 1.37"}
| Value | Meaning | Source |
|---|---|---|
| `PreferSameZone` | A preference for routing traffic to endpoints that are in the same zone as the client | `k8s-service#traffic-distribution` |
| `PreferSameNode` | A preference for routing traffic to endpoints that are on the same node as the client | `k8s-service#traffic-distribution` |
| `PreferClose` (deprecated) | An older alias for `PreferSameZone` that is less clear about the semantics | `k8s-service#traffic-distribution` |
:::

If the field is not set, the implementation will apply its default routing strategy (`k8s-service#traffic-distribution`).

## Telemetry cost: sampling and retention
<!-- bullets: 10.3.a -->

Sampling is one of the most effective ways to reduce the costs of observability without losing visibility (`otel-sampling#why-sampling`).

Other ways to lower costs, such as filtering or aggregating data, do not adhere to the concept of representativeness (`otel-sampling#why-sampling`).

Representativeness is the principle that a smaller group can accurately represent a larger group (`otel-sampling#why-sampling`).

The more data you generate, the less data you actually need to have a representative sample (`otel-sampling#why-sampling`).

For high-volume systems, it is quite common for a sampling rate of 1% or lower to very accurately represent the other 99% of data (`otel-sampling#why-sampling`).

Tail sampling is where the decision to sample a trace takes place by considering all or most of the spans within the trace (`otel-sampling#tail-sampling`).

Tail sampling gives you the option to sample your traces based on specific criteria derived from different parts of a trace, which is not an option with head sampling (`otel-sampling#tail-sampling`).

One use of tail sampling is always sampling traces that contain an error (`otel-sampling#tail-sampling`).

One use of tail sampling is sampling traces based on overall latency (`otel-sampling#tail-sampling`).

There are three primary downsides to tail sampling today (`otel-sampling#tail-sampling`).

Tail sampling can be difficult to implement (`otel-sampling#tail-sampling`).

The component or components that implement tail sampling must be stateful systems that can accept and store a large amount of data (`otel-sampling#tail-sampling`).

Tail samplers often end up as vendor-specific technology today (`otel-sampling#tail-sampling`).

For some systems, tail sampling might be used in conjunction with head sampling (`otel-sampling#tail-sampling`).

Using head sampling before tail sampling is often done in the interest of protecting the telemetry pipeline from being overloaded (`otel-sampling#tail-sampling`).

If neither `--storage.tsdb.retention.time` nor `storage.tsdb.retention.size` is set, the Prometheus retention time defaults to 15d (`prom-storage#operational-aspects`).

The `--storage.tsdb.retention.size` flag sets the maximum number of bytes of storage blocks to retain, removes the oldest data first, and defaults to 0 or disabled (`prom-storage#operational-aspects`).

If both time and size retention policies are specified, whichever triggers first will be used (`prom-storage#operational-aspects`).

Prometheus stores an average of only 1-2 bytes per sample (`prom-storage#operational-aspects`).

To plan the capacity of a Prometheus server, you can use the rough formula `needed_disk_space = retention_time_seconds * ingested_samples_per_second * bytes_per_sample` (`prom-storage#operational-aspects`).

To lower the rate of ingested samples, you can either reduce the number of time series you scrape or increase the scrape interval (`prom-storage#operational-aspects`).

Reducing the number of series is likely more effective than increasing the scrape interval, due to compression of samples within a series (`prom-storage#operational-aspects`).

The `--storage.tsdb.wal-compression` flag was introduced in Prometheus 2.11.0 and enabled by default in 2.20.0 (`prom-storage#operational-aspects`).

NFS filesystems, including AWS's EFS, are not supported for Prometheus' local storage (`prom-storage#operational-aspects`).

Expired block cleanup happens in the background and may take up to two hours to remove expired blocks (`prom-storage#operational-aspects`).

When setting a size limit with `storage.tsdb.retention.size`, it is wise to reduce the retention size to provide a buffer, ensuring that older entries will be removed before the allocated storage for Prometheus becomes full (`prom-storage#right-sizing-retention-size`).

At present, Prometheus recommends setting the retention size to, at most, 80-85% of your allocated Prometheus disk space (`prom-storage#right-sizing-retention-size`).

The remaining 15-20% buffer covers the temporary extra space required by in-progress compactions, which keep both the source blocks and the newly compacted block on disk at the same time before the old blocks are removed (`prom-storage#right-sizing-retention-size`).

The snippet applies the Prometheus capacity formula to 15 days of retention, 100,000 ingested samples per second and 2 bytes per sample, the HorizontalPodAutoscaler ratio to two examples, and the 85% retention size cap to a 500 GB disk, using `Math.ceilDiv` for the ceiling.

```java snippet=m10-l03/SizingArithmetic.java
public class SizingArithmetic {
    public static void main(String[] args) {
        long retentionSeconds = 15 * 24 * 3_600;
        long samplesPerSecond = 100_000;
        long bytesPerSample = 2;
        System.out.println("retention seconds: " + retentionSeconds);
        System.out.println("needed bytes: " + retentionSeconds * samplesPerSecond * bytesPerSample);
        System.out.println("desired replicas for 4 pods at 200m against 100m: " + Math.ceilDiv(4 * 200, 100));
        System.out.println("desired replicas for 3 pods at 150m against 100m: " + Math.ceilDiv(3 * 150, 100));
        System.out.println("retention size cap for a 500 GB disk at 85%: " + 500 * 85 / 100);
    }
}
```

Fifteen days are 15 × 24 × 3600 = 1296000 seconds, so the snippet prints `retention seconds: 1296000`.

At 100000 samples per second and 2 bytes per sample, 1296000 seconds need 259200000000 bytes, so the snippet prints `needed bytes: 259200000000`.

Four pods at 200m against a desired 100m give ceil(4 × 200 ÷ 100) = 8 replicas, so the snippet prints `desired replicas for 4 pods at 200m against 100m: 8`.

Three pods at 150m against a desired 100m give ceil(3 × 150 ÷ 100) = ceil(4.5) = 5 replicas, so the snippet prints `desired replicas for 3 pods at 150m against 100m: 5`.

At 85% of a 500 GB disk the retention size cap is 425 GB, so the snippet prints `retention size cap for a 500 GB disk at 85%: 425`.

## Storage selection and reclaim policy
<!-- bullets: 10.3.a -->

Each StorageClass contains the fields `provisioner`, `parameters`, and `reclaimPolicy`, which are used when a PersistentVolume belonging to the class needs to be dynamically provisioned to satisfy a PersistentVolumeClaim (PVC) (`k8s-storage-classes#storageclass-objects`).

The name of a StorageClass object is significant, and is how users can request a particular class (`k8s-storage-classes#storageclass-objects`).

As an administrator, you can specify a default StorageClass that applies to any PVCs that don't request a specific class (`k8s-storage-classes#storageclass-objects`).

In the example StorageClass of the Kubernetes documentation, `reclaimPolicy: Retain` is annotated as overriding the default value, which is `Delete` (`k8s-storage-classes#storageclass-objects`).

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: low-latency
provisioner: csi-driver.example-vendor.example
reclaimPolicy: Retain # default value is Delete
volumeBindingMode: WaitForFirstConsumer
```

PersistentVolumes that are dynamically created by a StorageClass have the reclaim policy specified in the `reclaimPolicy` field of the class, which can be either `Delete` or `Retain` (`k8s-storage-classes#reclaim-policy`).

If no `reclaimPolicy` is specified when a StorageClass object is created, it will default to `Delete` (`k8s-storage-classes#reclaim-policy`).

PersistentVolumes that are created manually and managed via a StorageClass will have whatever reclaim policy they were assigned at creation (`k8s-storage-classes#reclaim-policy`).

## Key points

- A container may use more of a resource than its request when the node has it free, while `cpu` limits are enforced by throttling and `memory` limits reactively by OOM kills.
- The CPU request is a weighting under contention, and the memory request is mainly used during Pod scheduling.
- The QoS classes are `Guaranteed`, `Burstable` and `BestEffort`, and under node pressure `BestEffort` Pods are evicted first.
- The HPA scales on the ratio of current to desired metric value, skips a ratio within a tolerance of 0.1 by default, and with several metrics chooses the largest desired replica count.
- The HPA downscale stabilization window defaults to 5 minutes, and the highest recommendation within it is chosen.
- KEDA works alongside the HPA by feeding it external metrics, can scale to zero, and creates Jobs for batch workloads.
- Topology Aware Routing and `.spec.trafficDistribution` help keep traffic within a zone, optimizing for performance, cost or reliability.
- Sampling reduces the cost of observability while staying representative, and tail sampling decides on all or most spans of a trace at the price of statefulness.
- Prometheus retention defaults to 15d, retention size defaults to disabled, and when both are set whichever triggers first is used.
- Prometheus stores 1-2 bytes per sample, and capacity is retention seconds times ingested samples per second times bytes per sample, which comes to 259200000000 bytes for 15 days at 100000 samples per second and 2 bytes.
- Prometheus recommends a retention size of at most 80-85% of the allocated disk, leaving a buffer for compactions.
- A StorageClass defaults its `reclaimPolicy` to `Delete`, and manually created PersistentVolumes keep the policy assigned at creation.

# Design principles, pragmatism and data-oriented programming

## The single responsibility principle
<!-- bullets: 1.1.a -->

The single responsibility principle says that each software module should have one and only one reason to change. Robert C. Martin answers what a reason to change is with people: a module should answer to a single person, or to a single tightly coupled group of people representing one narrowly defined business function.

:::judgement{source="Robert C. Martin, The Single Responsibility Principle (blog.cleancoder.com, 2014)" ref="martin-srp-blog#blog"}
According to Robert C. Martin, the Single Responsibility Principle states that each software module should have one and only one reason to change. He asks what defines a reason to change and answers that the reasons are people: a module should answer to a single person, or a single tightly coupled group of people representing one narrowly defined business function. He gives a second wording, which is to gather together the things that change for the same reasons and to separate the things that change for different reasons. He calls this another way to define cohesion and coupling: raise the cohesion between things that change for the same reasons, and lower the coupling between things that change for different reasons.
:::

## DRY, YAGNI and KISS
<!-- bullets: 1.1.b -->

Yagni is Martin Fowler's argument against building a capability before it is needed. He counts four costs of a presumptive feature and applies the same argument to abstractions. Refactoring is outside it.

:::judgement{source="Martin Fowler, Yagni (martinfowler.com, 2015)" ref="fowler-yagni#banner"}
According to Martin Fowler, yagni, "You Aren't Gonna Need It", says that a capability presumed necessary in the future should not be built now. He names four costs of a presumptive feature: the cost of build, the cost of delayed value, the cost of carry, and the cost of repair when the feature is built wrong. He applies the same argument to abstractions that support future flexibility: any abstraction that makes the code for current requirements harder to understand is presumed guilty. He states that yagni covers capabilities built for a presumptive feature and not the effort to make software easier to modify, so refactoring is not a violation of yagni.
:::

:::judgement{source="Thomas and Hunt, The Pragmatic Programmer, 2nd edition (2019); Ousterhout, A Philosophy of Software Design, 2nd edition (2021)"}
According to the course's registered chapter lists, The Pragmatic Programmer treats this subject in chapter 1, "A Pragmatic Philosophy", and A Philosophy of Software Design in chapter 6, "General-Purpose Modules are Deeper".
:::

## Records as immutable data carriers
<!-- bullets: 1.1.c -->

A record is a class that carries a fixed set of values. Its component fields are final, it cannot extend another class, and the compiler derives `equals`, `hashCode` and `toString` from the components. The immutability is shallow, so a record that holds a mutable list shows later changes to that list. The canonical constructor is where to validate arguments and make defensive copies.

A record declaration specifies a new record class, a restricted kind of class that defines a simple aggregate of values (`jls-8-records#jls-8.10`).

A record declaration may specify a top level record class, a member record class, or a local record class (`jls-8-records#jls-8.10`).

A record class is implicitly final (`jls-8-records#jls-8.10`).

A nested record class is implicitly static (`jls-8-records#jls-8.10`).

It is a compile-time error if a record declaration has the modifier `abstract`, `sealed` or `non-sealed` (`jls-8-records#jls-8.10`).

A record declaration does not have an `extends` clause, and the direct superclass type of a record class is `Record` (`jls-8-records#jls-8.10`).

A record class cannot specify a superclass, since that would mean inherited state beyond the state described in the header (`jep-395#Rules-for-record-classes`).

A record class can, however, freely specify superinterfaces and declare instance methods to implement them (`jep-395#Rules-for-record-classes`).

A record object is deserialized using the canonical constructor (`jls-8-records#jls-8.10`).

A record class is a shallowly immutable, transparent carrier for a fixed set of values, called the record components (`javadoc-record#class-record`).

For each record component, a record class has a component field that is `private`, `final` and non-static (`jls-8-records#jls-8.10.3`).

Record classes may explicitly declare instance methods other than accessor methods, but may not explicitly declare instance variables (`jls-8-records#jls-8.10.3`).

The implicit declarations of `equals`, `hashCode` and `toString` are derived from all of the component fields (`javadoc-record#class-record`).

The primary reasons to provide an explicit declaration for the canonical constructor or the accessor methods are to validate constructor arguments, perform defensive copies on mutable components, or normalize groups of components (`javadoc-record#class-record`).

The intent of a compact constructor declaration is that only code to validate or normalize parameters needs to be given in the constructor body, and the remaining initialization code is supplied by the compiler (`jls-8-records#jls-8.10.4.2`).

In the body of a compact constructor, the simple name of a record component denotes the implicit formal parameter and not the component field (`jls-8-records#jls-8.10.4.2`).

The body of a compact constructor must not contain a `return` statement or an explicit constructor invocation (`jls-8-records#jls-8.10.4.2`).

The body of a compact constructor must not contain an assignment to a component field (`jls-8-records#jls-8.10.4.2`).

After the last statement in the body of the compact constructor has completed normally, all component fields of the record class are implicitly initialized to the values of the corresponding formal parameters (`jls-8-records#jls-8.10.4.2`).

The snippet declares two records over a `List` component. The second record validates its `id` and copies the list in a compact constructor.

```java snippet=m01-l01/ShallowRecord.java
import java.util.ArrayList;
import java.util.List;

public class ShallowRecord {
    record Order(String id, List<String> lines) {}

    record SafeOrder(String id, List<String> lines) {
        SafeOrder {
            if (id.isBlank()) {
                throw new IllegalArgumentException("id is blank");
            }
            lines = List.copyOf(lines);
        }
    }

    public static void main(String[] args) {
        List<String> lines = new ArrayList<>(List.of("tea"));
        Order order = new Order("A1", lines);
        SafeOrder safe = new SafeOrder("A1", lines);
        lines.add("milk");
        System.out.println(order);
        System.out.println(safe);
        System.out.println(order.equals(new Order(order.id(), order.lines())));
        try {
            new SafeOrder(" ", List.of());
        } catch (IllegalArgumentException e) {
            System.out.println(e.getMessage());
        }
    }
}
```

The snippet prints `Order[id=A1, lines=[tea, milk]]`, because the record holds the caller's list and the later `add` shows through.

It prints `SafeOrder[id=A1, lines=[tea]]`, because the compact constructor stored a copy made by `List.copyOf`.

It prints `true` for the copy of the first record built from its own accessors, and `id is blank` for the rejected blank `id`.

For all record classes, if a record `R` has components `c1, c2, ... cn` and an instance `r` is copied as `new R(r.c1(), r.c2(), ..., r.cn())`, then `r.equals(copy)` must hold (`javadoc-record#class-record`).

## Views, copies and delegation in the JDK
<!-- bullets: 1.1.c -->

Several JDK wrappers hold another object and forward calls to it. `Collections.unmodifiableList` returns a read-only view that reads through to the list behind it, while `List.copyOf` returns a separate list. `Executors.unconfigurableExecutorService` forwards the `ExecutorService` methods to an executor and exposes nothing else. An `HttpClient` cannot change once it is built.

`Collections.unmodifiableList` returns an unmodifiable view of the specified list, and query operations on the returned list "read through" to the specified list (`javadoc-collections#unmodifiableList(java.util.List)`).

Attempts to modify the returned list, whether direct or via its iterator, result in an `UnsupportedOperationException` (`javadoc-collections#unmodifiableList(java.util.List)`).

`List.copyOf` returns an unmodifiable `List` containing the elements of the given `Collection`, in its iteration order (`javadoc-list#copyOf(java.util.Collection)`).

If the given `Collection` is subsequently modified, the returned `List` will not reflect such modifications (`javadoc-list#copyOf(java.util.Collection)`).

Elements cannot be added to, removed from or replaced in a list created by `List.of` or `List.copyOf`, but if the contained elements are themselves mutable, this may cause the list's contents to appear to change (`javadoc-list#unmodifiable`).

Lists created by `List.of` and `List.copyOf` disallow null elements (`javadoc-list#unmodifiable`).

The snippet changes a list after taking a view of it and a copy of it.

```java snippet=m01-l01/ListViews.java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class ListViews {
    public static void main(String[] args) {
        List<String> source = new ArrayList<>(List.of("tea"));
        List<String> view = Collections.unmodifiableList(source);
        List<String> copy = List.copyOf(source);
        source.add("milk");
        System.out.println(view);
        System.out.println(copy);
        try {
            view.add("rum");
        } catch (UnsupportedOperationException e) {
            System.out.println("view refuses add");
        }
        try {
            copy.add("rum");
        } catch (UnsupportedOperationException e) {
            System.out.println("copy refuses add");
        }
    }
}
```

The view prints `[tea, milk]` and the copy prints `[tea]`, so the later `add` to the source list reached the view and not the copy.

Both the view and the copy throw `UnsupportedOperationException` on `add`, and the snippet reports each as `view refuses add` and `copy refuses add`.

`Executors.unconfigurableExecutorService` returns an object that delegates all defined `ExecutorService` methods to the given executor, but not any other methods that might otherwise be accessible using casts (`javadoc-executors#unconfigurableExecutorService(java.util.concurrent.ExecutorService)`).

This provides a way to safely "freeze" configuration and disallow tuning of a given concrete implementation (`javadoc-executors#unconfigurableExecutorService(java.util.concurrent.ExecutorService)`).

An `HttpClient` is created through a builder, and once built it is immutable and can be used to send multiple requests (`javadoc-java-net-http-httpclient#class-httpclient`).

## Sealed hierarchies as domain models
<!-- bullets: 1.1.d -->

A sealed class or interface restricts which other classes or interfaces may extend or implement it. The restriction is a `permits` clause, or the declarations found in the same compilation unit when there is none. Each permitted subtype states whether it is `final`, `sealed` or `non-sealed`. A hierarchy closed this way can model the kinds of values in a domain, and a record can be one of its kinds because a record is implicitly final.

Sealed classes and interfaces restrict which other classes or interfaces may extend or implement them (`jep-409#Summary`).

A class can be declared `sealed` if all its direct subclasses are known when the class is declared, and no other direct subclasses are desired or required (`jls-8-records#jls-8.1.1.2`).

The optional `permits` clause in a normal class declaration specifies all the classes intended as direct subclasses of the class being declared (`jls-8-records#jls-8.1.6`).

It is a compile-time error if a class declaration has a `permits` clause but no `sealed` modifier (`jls-8-records#jls-8.1.6`).

If the declaration of a sealed class that is not an enum class lacks a `permits` clause, its permitted direct subclasses are the classes declared in the same compilation unit that have a canonical name and whose direct superclass is that class (`jls-8-records#jls-8.1.6`).

Explicit and exhaustive control over a class's direct subclasses is useful when the class hierarchy is used to model the kinds of values in a domain, rather than as a mechanism for code inheritance and reuse (`jls-8-records#jls-8.1.1.2`).

It is a compile-time error if a class has a sealed direct superclass or a sealed direct superinterface and is not declared `final`, `sealed` or `non-sealed`, either explicitly or implicitly (`jls-8-records#jls-8.1.1.2`).

An effect of the `sealed` keyword is to force all direct subclasses to explicitly declare whether they are `final`, `sealed` or `non-sealed`, which avoids accidentally exposing a sealed class hierarchy to unwanted subclassing (`jls-8-records#jls-8.1.1.2`).

A class that has a sealed direct superclass or a sealed direct superinterface is freely extensible if and only if it is declared `non-sealed` (`jls-8-records#jls-8.1.1.2`).

A record class is implicitly final, so it can implement a sealed interface (`jls-8-records#jls-8.1.1.2`).

An interface can be declared `sealed` if all its direct subclasses and direct subinterfaces are known when the interface is declared (`jls-9-interfaces#jls-9.1.1.4`).

If the declaration of a sealed interface lacks a `permits` clause, its permitted direct subclasses and subinterfaces are the classes and interfaces declared in the same compilation unit that have a canonical name and whose direct superinterfaces include it (`jls-9-interfaces#jls-9.1.4`).

If a sealed interface is associated with an unnamed module, every class or interface specified in its `permits` clause must belong to the same package as the interface (`jls-9-interfaces#jls-9.1.4`).

A sealed interface hierarchy should always be declared within a single maintenance domain, where the same developer or group of developers is responsible for maintaining the hierarchy (`jls-9-interfaces#jls-9.1.4`).

JEP 395 describes records as classes that act as transparent carriers for immutable data (`jep-395#Summary`).

The combination of sealed classes and record classes is sometimes referred to as algebraic data types, where record classes express product types and sealed classes express sum types (`jep-409#Sealing-and-record-classes`).

## Pattern matching on records
<!-- bullets: 1.1.d -->

A record pattern takes a record apart where it is tested. It checks that the value is that record type and then matches each component against its own pattern, which may be another record pattern. If any part fails to match, the whole pattern fails. A record pattern never matches `null`, and an accessor that throws makes the match throw a `MatchException`.

Pattern matching for `switch` allows an expression to be tested against a number of patterns, each with a specific action (`jep-441#Summary`).

Record patterns deconstruct record values, and record patterns and type patterns can be nested (`jep-440#Summary`).

A record pattern is used to test whether a value is an instance of a record class type and, if it is, to recursively perform pattern matching on the record component values (`jls-14-statements#jls-14.30.1`).

A value matches the pattern `Pair(String s, String t)` if it is a `Pair` and, recursively, its component values match the type patterns `String s` and `String t` (`jep-440#Nested-record-patterns`).

A value fails to match a nested pattern `P(Q)` if either, or both, of the subpatterns fail to match (`jep-440#Nested-record-patterns`).

The null reference does not match a record pattern (`jls-14-statements#jls-14.30.2`).

The length of a record pattern's component pattern list must be the same as the length of the record component list of the record class, or a compile-time error occurs (`jls-14-statements#jls-14.30.1`).

The match-all pattern is written `_` and can only appear directly in the component pattern list of a record pattern (`jls-14-statements#jls-14.30.1`).

Every value matches a match-all pattern (`jls-14-statements#jls-14.30.2`).

If invoking the accessor method of a component completes abruptly for reason `S`, pattern matching completes abruptly by throwing a `MatchException` with cause `S` (`jls-14-statements#jls-14.30.2`).

The next snippet gives a record an accessor that always throws.

```java snippet=m01-l01/AccessorFailure.java
public class AccessorFailure {
    record Gauge(int reading) {
        @Override
        public int reading() {
            throw new IllegalStateException("sensor offline");
        }
    }

    public static void main(String[] args) {
        Object value = new Gauge(7);
        try {
            if (value instanceof Gauge(int reading)) {
                System.out.println(reading);
            }
        } catch (MatchException e) {
            System.out.println("MatchException caused by " + e.getCause());
        }
        System.out.println(value instanceof Gauge);
    }
}
```

The snippet prints `MatchException caused by java.lang.IllegalStateException: sensor offline`, and then `true` for the plain type test.

## Case labels, guards and exhaustiveness
<!-- bullets: 1.1.d -->

A pattern `switch` picks the first case label that applies to the value. A `when` clause narrows a pattern label, and a label that an earlier one already covers is a compile-time error. A pattern `switch` must be exhaustive, and over a sealed type the compiler checks coverage against the permitted subclasses, so a `default` label may not be needed. A `null` selector throws unless the switch has a `null` label.

The first case label appearing in a switch block that applies to a value is chosen (`jep-441#Dominance-of-case-labels`).

It is a compile-time error for a case label in a switch block to be dominated by any preceding case label in that switch block (`jep-441#Dominance-of-case-labels`).

An unguarded pattern case label dominates a guarded pattern case label that has the same pattern (`jep-441#Dominance-of-case-labels`).

A `when` clause specifies a guard on a pattern case label, and the boolean expression is called the guard (`jep-441#Case-refinement`).

The label `case null, default` matches a value that is the null reference or that no other case label matches (`jep-441#Dealing-with-null`).

```java snippet=m01-l01/GuardedSwitch.java
public class GuardedSwitch {
    static String classify(Object value) {
        return switch (value) {
            case Integer i when i > 100 -> "big " + i;
            case Integer i -> "int " + i;
            case CharSequence text -> "text of " + text.length();
            case null, default -> "other";
        };
    }

    public static void main(String[] args) {
        System.out.println(classify(500));
        System.out.println(classify(7));
        System.out.println(classify("abc"));
        System.out.println(classify(new StringBuilder("hello")));
        System.out.println(classify(2.5));
        System.out.println(classify(null));
    }
}
```

`classify(500)` prints `big 500`, because the guarded label comes first and its guard holds. `classify(7)` fails that guard and prints `int 7` from the unguarded `Integer` label.

The `String` `abc` and the `StringBuilder` of `hello` both reach the `CharSequence` label and print `text of 3` and `text of 5`.

`2.5` and `null` both print `other`, the second through `case null, default`.

If the selector expression evaluates to null, any `null` case label is said to match (`jep-441#Dealing-with-null`).

If there is no `null` case label associated with the switch block, the switch throws `NullPointerException` (`jep-441#Dealing-with-null`).

If the selector expression evaluates to a non-null value, a matching case label is selected as normal, and if no case label matches then any `default` label is considered to match (`jep-441#Dealing-with-null`).

If no label in a pattern switch matches the value of the selector expression, the switch completes abruptly by throwing a `MatchException`, since pattern switches must be exhaustive (`jep-441#Errors`).

Both switch expressions and pattern switch statements must be exhaustive, which means the switch block must have clauses that deal with all possible values of the selector expression (`jep-440#Record-patterns-and-exhaustive-switch`).

A default label is permitted, but not required, when the switch block exhausts all the permitted direct subclasses and subinterfaces of an abstract sealed class or sealed interface (`jls-14-statements#jls-14.11.1.1`).

If the type of the selector expression is a sealed class, the type coverage check can take into account the `permits` clause of the sealed class to determine whether a switch block is exhaustive, which can sometimes remove the need for a `default` clause (`jep-441#Exhaustiveness-and-sealed-classes`).

Exhaustiveness is required of any switch statement that uses pattern or null labels, or whose selector expression is not one of `char`, `byte`, `short`, `int`, `Character`, `Byte`, `Short`, `Integer`, `String` or an enum type (`jep-441#Exhaustiveness-and-compatibility`).

The next snippet is deliberately broken. Its `switch` covers two of the three permitted subclasses of a sealed interface.

```java snippet=m01-l01/MissingCase.java
public class MissingCase {
    sealed interface Payment permits Card, Transfer, Voucher {}

    record Card(String last4) implements Payment {}

    record Transfer(String iban) implements Payment {}

    record Voucher(String code) implements Payment {}

    static String describe(Payment payment) {
        return switch (payment) {
            case Card card -> "card " + card.last4();
            case Transfer transfer -> "transfer " + transfer.iban();
        };
    }

    public static void main(String[] args) {
        System.out.println(describe(new Voucher("W-9")));
    }
}
```

The compiler rejects `MissingCase` with `error: the switch expression does not cover all possible input values`, and the program never runs.

The snippet models a `Payment` as a sealed interface with three record implementations, and switches over it with no `default` label.

```java snippet=m01-l01/PaymentSwitch.java
public class PaymentSwitch {
    sealed interface Payment permits Card, Transfer, Voucher {}

    record Card(String last4, long cents) implements Payment {}

    record Transfer(String iban, long cents) implements Payment {}

    record Voucher(String code) implements Payment {}

    record Receipt(String customer, Payment payment) {}

    static String describe(Payment payment) {
        return switch (payment) {
            case Card(String last4, long cents) -> "card " + last4 + " for " + cents;
            case Transfer(String iban, long cents) -> "transfer from " + iban + " for " + cents;
            case Voucher(String code) -> "voucher " + code;
        };
    }

    static String describe(Receipt receipt) {
        return switch (receipt) {
            case Receipt(String customer, Card(var last4, var cents)) -> customer + " paid by card " + last4;
            case Receipt(String customer, Transfer transfer) -> customer + " paid by transfer from " + transfer.iban();
            case Receipt(String customer, Voucher voucher) -> customer + " paid by voucher " + voucher.code();
        };
    }

    public static void main(String[] args) {
        System.out.println(describe(new Card("4242", 1500)));
        System.out.println(describe(new Voucher("W-9")));
        System.out.println(describe(new Receipt("Ana", new Transfer("ES00", 900))));
        try {
            describe((Payment) null);
        } catch (NullPointerException e) {
            System.out.println("NullPointerException");
        }
    }
}
```

The snippet prints `card 4242 for 1500`, `voucher W-9` and `Ana paid by transfer from ES00`, one line each, from the record patterns and the nested record pattern.

It then prints `NullPointerException`, because the `switch` over a `null` `Payment` has no `case null` label.

## Key points

- A record class is implicitly final and has a private final field per component (`jls-8-records#jls-8.10`; `jls-8-records#jls-8.10.3`).
- A record is a shallowly immutable carrier, and an explicit canonical constructor is the place to validate and make defensive copies (`javadoc-record#class-record`).
- A record class cannot specify a superclass, because that would mean inherited state beyond the state described in the header (`jep-395#Rules-for-record-classes`).
- A compact constructor needs only validation or normalization code and cannot assign a component field (`jls-8-records#jls-8.10.4.2`).
- A record that holds a mutable `List` shows later changes to that list, and `List.copyOf` in a compact constructor prevents it.
- `Collections.unmodifiableList` is a view that reads through to the specified list, and `List.copyOf` does not reflect later changes to the given collection (`javadoc-collections#unmodifiableList(java.util.List)`; `javadoc-list#copyOf(java.util.Collection)`).
- A sealed class or interface has all its direct subclasses known when it is declared (`jls-8-records#jls-8.1.1.2`; `jls-9-interfaces#jls-9.1.1.4`).
- A class with a sealed direct superclass or superinterface is freely extensible if and only if it is declared `non-sealed` (`jls-8-records#jls-8.1.1.2`).
- The first case label that applies to a value is chosen, and a case label dominated by a preceding one is a compile-time error (`jep-441#Dominance-of-case-labels`).
- A `switch` over a sealed type that covers every permitted direct subclass needs no `default` label (`jls-14-statements#jls-14.11.1.1`).
- A `switch` without a `null` case label throws `NullPointerException` for a null selector, and a pattern switch that matches no label throws `MatchException` (`jep-441#Dealing-with-null`; `jep-441#Errors`).
- The null reference does not match a record pattern, and a throwing accessor surfaces as a `MatchException` (`jls-14-statements#jls-14.30.2`).

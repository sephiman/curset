# Web layer

## The request path through Spring MVC
<!-- bullets: 5.5.a -->

A request passes through several stages before a controller method runs, and the actual work is performed by configurable delegate components. Servlet filters run first, then the `DispatcherServlet` finds a handler through a `HandlerMapping`, runs the interceptors, and lets a `HandlerAdapter` invoke the method. A converter turns the request body into an argument. Knowing the order shows where cross-cutting logic belongs. Interceptors are a poor place for security, because their path matching can differ from the controller's.

In the Servlet API, you can add a `jakarta.servlet.Filter` to apply interception-style logic before and after the rest of the processing chain of filters and the target Servlet (`spring-fw-webmvc-filters#page-title`).

`OncePerRequestFilter` extends `GenericFilterBean` and supports a single invocation at the start of a request, during the REQUEST dispatch phase, and ignores further handling via FORWARD dispatches (`spring-fw-webmvc-filters#page-title`).

In a Spring Boot application, you can declare `Filter` instances as beans and Boot will have them configured (`spring-fw-webmvc-filters#page-title`).

Any `Servlet`, `Filter` or servlet `*Listener` instance that is a Spring bean is registered with the embedded container (`spring-boot-web-servlet#web.servlet.embedded-container.servlets-filters-listeners.beans`).

If a specific filter order is required, annotate the `Filter` with `@Order` or make it implement `Ordered`, because annotating its bean method with `@Order` does not configure the order of a `Filter` (`spring-boot-web-servlet#web.servlet.embedded-container.servlets-filters-listeners.beans`).

Enabling debug level logging for the web logging group (`logging.level.web=debug`) logs every registered filter with its order and URL patterns at startup (`spring-boot-web-servlet#web.servlet.embedded-container.servlets-filters-listeners.beans`).

Spring MVC is designed around the front controller pattern, where a central Servlet, the `DispatcherServlet`, provides a shared algorithm for request processing, while actual work is performed by configurable delegate components (`spring-fw-webmvc-dispatcher#page-title`).

The `DispatcherServlet` delegates to special beans to process requests and render the appropriate responses (`spring-fw-webmvc-dispatcher-special-beans#page-title`).

A `HandlerMapping` maps a request to a handler along with a list of interceptors for pre- and post-processing (`spring-fw-webmvc-dispatcher-special-beans#page-title`).

The two main `HandlerMapping` implementations are `RequestMappingHandlerMapping`, which supports `@RequestMapping` annotated methods, and `SimpleUrlHandlerMapping`, which maintains explicit registrations of URI path patterns to handlers (`spring-fw-webmvc-dispatcher-special-beans#page-title`).

A `HandlerAdapter` helps the `DispatcherServlet` to invoke a handler mapped to a request, regardless of how the handler is actually invoked (`spring-fw-webmvc-dispatcher-special-beans#page-title`).

The main purpose of a `HandlerAdapter` is to shield the `DispatcherServlet` from details such as resolving the annotations of an annotated controller (`spring-fw-webmvc-dispatcher-special-beans#page-title`).

If a handler is found, the execution chain associated with the handler (preprocessors, postprocessors, and controllers) is run to prepare a model for rendering (`spring-fw-webmvc-dispatcher-sequence#page-title`).

For annotated controllers, the response can be rendered within the `HandlerAdapter` instead of returning a view (`spring-fw-webmvc-dispatcher-sequence#page-title`).

The `HandlerExceptionResolver` beans declared in the `WebApplicationContext` are used to resolve exceptions thrown during request processing (`spring-fw-webmvc-dispatcher-sequence#page-title`).

:::diagram{kind="flow" caption="Order of the stages a request passes through in Spring MVC"}
description: A Filter runs before the DispatcherServlet; the DispatcherServlet uses a HandlerMapping to map the request to a handler and its interceptors, a HandlerAdapter to invoke the handler, and a HandlerExceptionResolver to resolve exceptions thrown during processing.
filter: Servlet Filter
servlet: DispatcherServlet
mapping: HandlerMapping
adapter: HandlerAdapter
resolver: HandlerExceptionResolver
filter -> servlet: runs before the Servlet
servlet -> mapping: maps request to handler and interceptors
servlet -> adapter: invokes the mapped handler

:::

Interceptors are not ideally suited as a security layer due to the potential for a mismatch with annotated controller path matching (`spring-fw-webmvc-handlermapping-interceptor#page-title`).

Generally, the documentation recommends using Spring Security, or alternatively a similar approach integrated with the Servlet filter chain and applied as early as possible, instead of interceptors as a security layer (`spring-fw-webmvc-handlermapping-interceptor#page-title`).

The Java config passes interceptors only to the `HandlerMapping` beans it manages (`spring-fw-webmvc-handlermapping-interceptor#page-title`).

`java.util.Optional` is supported as a method argument in combination with annotations that have a `required` attribute, such as `@RequestParam` and `@RequestHeader`, and is equivalent to `required=false` (`spring-fw-webmvc-controller-ann-arguments#page-title`).

Reactive types are not supported for any controller method arguments (`spring-fw-webmvc-controller-ann-arguments#page-title`).

A `jakarta.servlet.http.HttpSession` argument enforces the presence of a session (`spring-fw-webmvc-controller-ann-arguments#page-title`).

Session access is not thread-safe (`spring-fw-webmvc-controller-ann-arguments#page-title`).

If a method argument matches none of the other entries of the argument table and is a simple type, it is resolved as a `@RequestParam`; otherwise it is resolved as a `@ModelAttribute` (`spring-fw-webmvc-controller-ann-arguments#page-title`).

`@RequestBody` reads the request body and deserializes it into an `Object` through an `HttpMessageConverter` (`spring-fw-webmvc-controller-ann-requestbody#page-title`).

Form data should be read using `@RequestParam`, not `@RequestBody`, because in the Servlet API request parameter access causes the request body to be parsed and it cannot be read again (`spring-fw-webmvc-controller-ann-requestbody#page-title`).

Spring MVC uses the `HttpMessageConverter` interface to convert HTTP requests and responses (`spring-boot-web-servlet#web.servlet.spring-mvc.message-converters`).

Objects can be automatically converted to JSON by using the Jackson library (`spring-boot-web-servlet#web.servlet.spring-mvc.message-converters`).

Any `HttpMessageConverter` bean that is present in the context is added to the list of converters (`spring-boot-web-servlet#web.servlet.spring-mvc.message-converters`).

To add or customize converters, declare one or more `ClientHttpMessageConvertersCustomizer` or `ServerHttpMessageConvertersCustomizer` beans (`spring-boot-web-servlet#web.servlet.spring-mvc.message-converters`).

With a customizer, `addCustomConverter` adds a converter before the default ones, while `withJsonConverter` overrides a specific default converter (`spring-boot-web-servlet#web.servlet.spring-mvc.message-converters`).

By default, Spring MVC encodes strings in UTF-8 (`spring-boot-web-servlet#web.servlet.spring-mvc.message-converters`).

You can configure the `HttpMessageConverter` instances to use by overriding `configureMessageConverters()` (`spring-fw-webmvc-message-converters#page-title`).

## Validation, controller advice and the error model
<!-- bullets: 5.5.b -->

When a request is wrong, validation raises an exception that depends on how the controller method is written. An `@ExceptionHandler` turns the exception into a response. Declared in a controller it applies only to that controller, and declared in an `@ControllerAdvice` it applies to any controller. `ProblemDetail` renders the response body in the RFC 9457 format.

To be eligible for Spring-driven method validation, target classes need to be annotated with Spring’s `@Validated` annotation (`spring-fw-validation-beanvalidation#validation-beanvalidation-spring-method`).

Spring-driven method validation is integrated into a Spring context through a `MethodValidationPostProcessor` bean definition (`spring-fw-validation-beanvalidation#validation-beanvalidation-spring-method`).

Method validation relies on AOP proxies around the target classes, either JDK dynamic proxies for methods on interfaces or CGLIB proxies (`spring-fw-validation-beanvalidation#validation-beanvalidation-spring-method`).

Spring MVC and WebFlux have built-in support for the same underlying method validation but without the need for AOP (`spring-fw-validation-beanvalidation#validation-beanvalidation-spring-method`).

By default, method validation raises `jakarta.validation.ConstraintViolationException` with the set of `ConstraintViolation` objects returned by `jakarta.validation.Validator` (`spring-fw-validation-beanvalidation#validation-beanvalidation-spring-method-exceptions`).

Setting `adaptConstraintViolations` on the `MethodValidationPostProcessor` raises `MethodValidationException` instead, with the violations adapted to `MessageSourceResolvable` errors (`spring-fw-validation-beanvalidation#validation-beanvalidation-spring-method-exceptions`).

Java Bean Validation is applied individually to an `@ModelAttribute`, `@RequestBody` or `@RequestPart` method parameter annotated with `@jakarta.validation.Valid` or Spring’s `@Validated`, so long as it is a command object rather than a container such as `Map` or `Collection`, it does not have `Errors` or `BindingResult` immediately after in the method signature, and it does not otherwise require method validation, and `MethodArgumentNotValidException` is the exception raised when validating a method parameter individually (`spring-fw-webmvc-controller-ann-validation#page-title`).

Java Bean Validation is applied to the whole method when `@Constraint` annotations such as `@Min` and `@NotBlank` are declared directly on method parameters or on the method for the return value, and `HandlerMethodValidationException` is the exception raised then (`spring-fw-webmvc-controller-ann-validation#page-title`).

Applications should handle both `MethodArgumentNotValidException` and `HandlerMethodValidationException`, since either may be raised depending on the controller method signature (`spring-fw-webmvc-controller-ann-validation#page-title`).

`@Valid` is not a constraint annotation, so by itself it does not lead to method validation, while adding `@NotNull` to an `@Valid` parameter does (`spring-fw-webmvc-controller-ann-validation#page-title`).

With `@RequestBody` and `@Valid`, validation errors by default cause a `MethodArgumentNotValidException`, which is turned into a 400 (`BAD_REQUEST`) response (`spring-fw-webmvc-controller-ann-requestbody#page-title`).

If a controller has a class level `@Validated`, method validation is applied through an AOP proxy, and the class level `@Validated` must be removed to use the built-in Spring MVC support added in Spring Framework 6.1 (`spring-fw-webmvc-controller-ann-validation#page-title`).

:::esquema{kind=tabla title="Which exception validation raises"}
| Situation | Exception raised | Source |
|---|---|---|
| `@Valid` or `@Validated` on a `@RequestBody` parameter, validated individually | `MethodArgumentNotValidException` | `spring-fw-webmvc-controller-ann-validation#page-title` |
| `@Constraint` annotations on method parameters or on the method return value | `HandlerMethodValidationException` | `spring-fw-webmvc-controller-ann-validation#page-title` |

`@ExceptionHandler`, `@InitBinder` and `@ModelAttribute` methods apply only to the `@Controller` class, or class hierarchy, in which they are declared (`spring-fw-webmvc-controller-advice#page-title`).

If they are declared in an `@ControllerAdvice` or `@RestControllerAdvice` class, they apply to any controller (`spring-fw-webmvc-controller-advice#page-title`).

`@RestControllerAdvice` is a shortcut annotation that combines `@ControllerAdvice` with `@ResponseBody` (`spring-fw-webmvc-controller-advice#page-title`).

By default, both `@ControllerAdvice` and `@RestControllerAdvice` apply to any controller, including `@Controller` and `@RestController` (`spring-fw-webmvc-controller-advice#page-title`).

Attributes of the annotation narrow the set of controllers and handlers that an advice applies to, and these selectors are evaluated at runtime and may negatively impact performance if used extensively (`spring-fw-webmvc-controller-advice#page-title`).

Global `@ExceptionHandler` methods, from an `@ControllerAdvice`, are applied after local ones, from the `@Controller` (`spring-fw-webmvc-controller-advice#page-title`).

Global `@ModelAttribute` and `@InitBinder` methods are applied before local ones (`spring-fw-webmvc-controller-advice#page-title`).

When multiple exception methods match, a root exception match is generally preferred to a cause exception match (`spring-fw-webmvc-exceptionhandler#mvc-ann-exceptionhandler-exc`).

`ExceptionDepthComparator` sorts matching exceptions based on their depth from the thrown exception type (`spring-fw-webmvc-exceptionhandler#mvc-ann-exceptionhandler-exc`).

Since Spring Framework 5.3, an exception handler can match at arbitrary cause levels, whereas previously only an immediate cause was considered (`spring-fw-webmvc-exceptionhandler#mvc-ann-exceptionhandler-exc`).

An `@ExceptionHandler` whose argument is `Exception` is always invoked with the wrapper exception in a wrapping scenario, and the matching exception is found through `ex.getCause()` (`spring-fw-webmvc-exceptionhandler#mvc-ann-exceptionhandler-exc`).

A root exception match is preferred only among the methods of a given controller or `@ControllerAdvice` class, so a cause match on a higher-priority `@ControllerAdvice` bean is preferred to any match on a lower-priority one (`spring-fw-webmvc-exceptionhandler#mvc-ann-exceptionhandler-exc`).

An `@ExceptionHandler` method can back out of dealing with an exception by rethrowing it in its original form, and the exception then propagates through the remaining resolution chain (`spring-fw-webmvc-exceptionhandler#mvc-ann-exceptionhandler-exc`).

The Spring Framework supports the “Problem Details for HTTP APIs” specification, RFC 9457 (`spring-fw-webmvc-ann-rest-exceptions#page-title`).

`ErrorResponse` is the contract to expose HTTP error response details including status, headers and a body in the format of RFC 9457, and all Spring MVC exceptions implement it (`spring-fw-webmvc-ann-rest-exceptions#page-title`).

You can return `ProblemDetail` or `ErrorResponse` from any `@ExceptionHandler` or from any `@RequestMapping` method to render an RFC 9457 response (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-render`).

The `status` property of `ProblemDetail` determines the HTTP status (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-render`).

The `instance` property of `ProblemDetail` is set from the current URL path, if not already set (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-render`).

To enable RFC 9457 responses for Spring MVC exceptions and for any `ErrorResponseException`, extend `ResponseEntityExceptionHandler` and declare it as an `@ControllerAdvice` in Spring configuration (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-render`).

A non-standard field is added to an RFC 9457 response by inserting it into the `properties` Map of `ProblemDetail` (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-non-standard`).

By default, Spring Boot provides an `/error` mapping that handles all errors in a sensible way, and it is registered as a “global” error page in the servlet container (`spring-boot-web-servlet#web.servlet.spring-mvc.error-handling`).

Spring Boot enables RFC 9457 Problem Details support by setting `spring.mvc.problemdetails.enabled` to `true` (`spring-boot-web-servlet#web.servlet.spring-mvc.error-handling`).

With `spring.mvc.problemdetails.enabled`, Spring Boot autoconfigures a `ResponseEntityExceptionHandler` whose order is 0, so a handler that takes over a specific built-in exception must be ordered ahead of it (`spring-fw-webmvc-ann-rest-exceptions#mvc-ann-rest-exceptions-non-standard`).

To replace the default error behavior completely, you can implement `ErrorController` and register a bean definition of that type (`spring-boot-web-servlet#web.servlet.spring-mvc.error-handling`).

## Spring MVC, WebFlux and virtual threads
<!-- bullets: 5.5.c -->

The two web stacks make opposite assumptions about threads. Spring MVC assumes that a request may block its thread, so the container supplies many threads. Spring WebFlux assumes that nothing blocks, so a few threads serve every request. Both support annotated controllers. Reactive code generally does not run faster, and its expected benefit is scaling with a small, fixed number of threads. Virtual threads are lightweight threads that reduce the effort of writing high-throughput concurrent applications.

Both Spring MVC and Spring WebFlux support annotated controllers (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

In Spring MVC, and servlet applications in general, it is assumed that applications can block the current thread, for example for remote calls (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

For this reason, servlet containers use a large thread pool to absorb potential blocking during request handling (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

In Spring WebFlux, and non-blocking servers in general, it is assumed that applications do not block (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

Non-blocking servers use a small, fixed-size thread pool, called event loop workers, to handle requests (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

Never blocking the current thread and relying on callbacks means that you do not need extra threads, as there are no blocking calls to absorb (`spring-fw-webflux-new-framework#webflux-concurrency-model`).

Reactive and non-blocking generally do not make applications run faster (`spring-fw-webflux-new-framework#webflux-performance`).

It requires more work to do things the non-blocking way, and that can slightly increase the required processing time (`spring-fw-webflux-new-framework#webflux-performance`).

The key expected benefit of reactive and non-blocking is the ability to scale with a small, fixed number of threads and less memory (`spring-fw-webflux-new-framework#webflux-performance`).

To observe those benefits, you need to have some latency, including a mix of slow and unpredictable network I/O (`spring-fw-webflux-new-framework#webflux-performance`).

If you have a Spring MVC application that works fine, there is no need to change (`spring-fw-webflux-new-framework#webflux-framework-choice`).

If you have blocking persistence APIs (JPA, JDBC) or networking APIs to use, Spring MVC is the best choice for common architectures at least (`spring-fw-webflux-new-framework#webflux-framework-choice`).

Reactive Streams is a small spec, also adopted in Java 9, that defines the interaction between asynchronous components with back pressure (`spring-fw-webflux-new-framework#webflux-why-reactive`).

If a publisher cannot slow down, it has to decide whether to buffer, drop, or fail (`spring-fw-webflux-new-framework#webflux-why-reactive`).

Virtual threads are lightweight threads that dramatically reduce the effort of writing, maintaining, and observing high-throughput concurrent applications (`jep-444#Summary`).

The number of available platform threads is limited because the JDK implements threads as wrappers around operating system threads, and pooling them does not increase the total number of threads (`jep-444#The-thread-per-request-style`).

A virtual thread is an instance of `java.lang.Thread` that is not tied to a particular operating system thread (`jep-444#Preserving-the-thread-per-request-style-with-virtual-threads`).

A virtual thread consumes an operating system thread only while it performs calculations on the CPU (`jep-444#Preserving-the-thread-per-request-style-with-virtual-threads`).

To Java developers, virtual threads are simply threads that are cheap to create and almost infinitely plentiful (`jep-444#Preserving-the-thread-per-request-style-with-virtual-threads`).

When code running in a virtual thread calls a blocking I/O operation in the `java.*` API, the runtime performs a non-blocking operating system call and automatically suspends the virtual thread until it can be resumed later (`jep-444#Preserving-the-thread-per-request-style-with-virtual-threads`).

There is never a need to pool virtual threads, and a pool should not be used to limit concurrency, for which constructs such as semaphores are designed (`jep-444#Do-not-pool-virtual-threads`).

In the absence of an `Executor` bean in the context, Spring Boot auto-configures an `AsyncTaskExecutor` (`spring-boot-features-task-execution-and-scheduling#page-title`).

When virtual threads are enabled, using Java 21+ and `spring.threads.virtual.enabled` set to `true`, the auto-configured executor is a `SimpleAsyncTaskExecutor` that uses virtual threads (`spring-boot-features-task-execution-and-scheduling#page-title`).

Otherwise, the auto-configured executor is a `ThreadPoolTaskExecutor` with sensible defaults (`spring-boot-features-task-execution-and-scheduling#page-title`).

The auto-configured `AsyncTaskExecutor` is used for asynchronous request handling in Spring MVC unless a custom `Executor` bean is defined (`spring-boot-features-task-execution-and-scheduling#page-title`).

Spring MVC and Spring WebFlux require a bean named `applicationTaskExecutor`, and that bean must be of type `AsyncTaskExecutor` (`spring-boot-features-task-execution-and-scheduling#page-title`).

The `SimpleAsyncTaskScheduler` that uses virtual threads will ignore any pooling related properties (`spring-boot-features-task-execution-and-scheduling#page-title`).

## HTTP clients
<!-- bullets: 5.5.d -->

An application that calls other services needs a client. Spring offers `RestClient`, the non-blocking `WebClient`, and Java interfaces with `@HttpExchange` methods that sit in front of either. `RestClient` runs on an underlying HTTP library, which Spring Boot picks from the classpath unless a factory is set explicitly. Timeouts are common settings of all clients, and Reactor Netty keeps a connection pool.

If you are not using Spring WebFlux or Project Reactor in your application, Spring Boot recommends that you use `RestClient` to call remote REST services (`spring-boot-io-rest-client#io.rest-client.restclient`).

Spring Boot creates and pre-configures a prototype `RestClient.Builder` bean (`spring-boot-io-rest-client#io.rest-client.restclient`).

Once created, a `RestClient` is safe to use in multiple threads (`spring-fw-integration-rest-clients#_create_a_restclient`).

By default, `RestClient` throws a subclass of `RestClientException` when retrieving a response with a 4xx or 5xx status code, and `onStatus` overrides this behavior (`spring-fw-integration-rest-clients#_error_handling`).

To execute the HTTP request, `RestClient` uses a client HTTP library (`spring-fw-integration-rest-clients#rest-request-factories`).

If no request factory is specified when the `RestClient` was built, it will use the Apache or Jetty `HttpClient` if they are available on the classpath (`spring-fw-integration-rest-clients#rest-request-factories`).

Otherwise, if the `java.net.http` module is loaded, the `RestClient` uses Java’s `HttpClient` (`spring-fw-integration-rest-clients#rest-request-factories`).

Finally, the `RestClient` resorts to the simple default (`spring-fw-integration-rest-clients#rest-request-factories`).

The `SimpleClientHttpRequestFactory` may raise an exception when accessing the status of a response that represents an error, for example `401` (`spring-fw-integration-rest-clients#rest-request-factories`).

Spring Boot auto-detects which HTTP client to use with `RestClient` and `RestTemplate` from the libraries on the classpath, in the order Apache `HttpClient`, Jetty `HttpClient`, Reactor Netty `HttpClient`, the JDK `java.net.http.HttpClient`, and the simple JDK `java.net.HttpURLConnection` client (`spring-boot-io-rest-client#io.rest-client.clienthttprequestfactory`).

If multiple clients are available on the classpath and no global configuration is provided, the most preferred client is used (`spring-boot-io-rest-client#io.rest-client.clienthttprequestfactory`).

`WebClient` is a non-blocking, reactive client to perform HTTP requests (`spring-fw-integration-rest-clients#rest-webclient`).

Regardless of the underlying technology being used, all HTTP clients have common settings that can be configured (`spring-boot-io-rest-client#io.rest-client.global-configuration`).

The common settings are connection timeouts, read timeouts, how HTTP redirects are handled, how HTTP cookies are handled, and which SSL bundle is used (`spring-boot-io-rest-client#io.rest-client.global-configuration`).

The `spring.http.clients` properties, such as `connect-timeout` and `read-timeout`, apply the same configuration to all auto-configured clients (`spring-boot-io-rest-client#io.rest-client.global-configuration`).

When `spring.http.clients.cookie-handling` is not set, the default cookie handling of the underlying HTTP client library is used (`spring-boot-io-rest-client#io.rest-client.global-configuration`).

You can use the `spring.http.clients.imperative.factory` property to pick a specific factory if the auto-detected HTTP client does not meet your needs (`spring-boot-io-rest-client#io.rest-client.clienthttprequestfactory.configuration`).

By default, the Reactor Netty `HttpClient` participates in the global resources held in `reactor.netty.http.HttpResources`, including event loop threads and a connection pool (`spring-fw-webflux-client-builder#webflux-client-builder-reactor-resources`).

Sharing these global resources is the recommended mode, since fixed, shared resources are preferred for event loop concurrency (`spring-fw-webflux-client-builder#webflux-client-builder-reactor-resources`).

The global resources remain active until the process exits, and a `ReactorResourceFactory` bean ensures that they are shut down when the Spring `ApplicationContext` is closed (`spring-fw-webflux-client-builder#webflux-client-builder-reactor-resources`).

With the Reactor Netty connector, a connection timeout is set with `ChannelOption.CONNECT_TIMEOUT_MILLIS`, and a read or write timeout with `ReadTimeoutHandler` and `WriteTimeoutHandler` (`spring-fw-webflux-client-builder#webflux-client-builder-reactor-timeout`).

A response timeout for all requests is set with `responseTimeout` on the Reactor Netty `HttpClient`, and it can also be set for a specific request (`spring-fw-webflux-client-builder#webflux-client-builder-reactor-timeout`).

You can define an HTTP Service as a Java interface with `@HttpExchange` methods, and use `HttpServiceProxyFactory` to create a client proxy from it for remote access over HTTP via `RestClient`, `WebClient`, or `RestTemplate` (`spring-fw-integration-rest-clients#rest-http-service-client`).

On the server side, an `@Controller` class can implement the same interface to handle requests with `@HttpExchange` controller methods (`spring-fw-integration-rest-clients#rest-http-service-client`).

HTTP Service interfaces define a service contract by using methods annotated with `@HttpExchange`, or more typically the method specific variants such as `@GetExchange` and `@PostExchange` (`spring-boot-io-rest-client#io.rest-client.httpservice`).

Configuration properties for HTTP Services can be specified under `spring.http.serviceclient.<group-name>` (`spring-boot-io-rest-client#io.rest-client.httpservice.properties`).

## Key points

- The `DispatcherServlet` is the front controller of Spring MVC and delegates to special beans such as `HandlerMapping` and `HandlerAdapter`.
- Interceptors are not ideally suited as a security layer.
- Spring MVC uses `HttpMessageConverter` to convert HTTP requests and responses, and strings are encoded in UTF-8 by default.
- `@Valid` on a `@RequestBody` parameter raises `MethodArgumentNotValidException`, while `@Constraint` annotations on parameters raise `HandlerMethodValidationException`, so both should be handled.
- Global `@ExceptionHandler` methods from an `@ControllerAdvice` are applied after local ones, while global `@ModelAttribute` and `@InitBinder` methods are applied before local ones.
- A `ProblemDetail` returned from an exception handler renders an RFC 9457 response.
- Servlet containers use a large thread pool because Spring MVC assumes blocking, and non-blocking servers use a small, fixed-size pool.
- Reactive and non-blocking generally do not make applications run faster; the key expected benefit is scaling with a small, fixed number of threads and less memory.
- With virtual threads enabled, Spring Boot auto-configures a `SimpleAsyncTaskExecutor` that uses virtual threads.
- A `RestClient` without a request factory uses the Apache or Jetty `HttpClient`, then Java’s `HttpClient`, then the simple default.
- An HTTP Service is a Java interface with `@HttpExchange` methods, turned into a client proxy by `HttpServiceProxyFactory`.

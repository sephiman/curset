# Spring Security

## Filters, chains and their order
<!-- bullets: 5.6.a -->

Spring Security's Servlet support is based on Servlet filters. The container only knows filters it registered itself, so a bridge, `DelegatingFilterProxy`, wraps a Spring bean. That bean, `FilterChainProxy`, invokes the first `SecurityFilterChain` that matches the request, and the filters of that chain run in a fixed order. Order matters because a filter affects only the filters after it, and authentication must come before authorization.

The client sends a request to the application, and the container creates a `FilterChain`, which contains the `Filter` instances and `Servlet` that should process the `HttpServletRequest`, based on the path of the request URI (`spring-security-servlet-architecture#servlet-filters-review`).

A `Filter` impacts only downstream `Filter` instances and the `Servlet`, so the order in which each `Filter` is invoked is extremely important (`spring-security-servlet-architecture#servlet-filters-review`).

`DelegatingFilterProxy` allows delaying looking up `Filter` bean instances (`spring-security-servlet-architecture#servlet-delegatingfilterproxy`).

Delaying the lookup is important because the container needs to register the `Filter` instances before the container can start up (`spring-security-servlet-architecture#servlet-delegatingfilterproxy`).

The Servlet container allows registering `Filter` instances by using its own standards, but it is not aware of Spring-defined beans (`spring-security-servlet-architecture#servlet-delegatingfilterproxy`).

Spring typically uses a `ContextLoaderListener` to load the Spring beans, which is not done until after the `Filter` instances need to be registered (`spring-security-servlet-architecture#servlet-delegatingfilterproxy`).

`FilterChainProxy` is a special `Filter` provided by Spring Security that allows delegating to many `Filter` instances through `SecurityFilterChain` (`spring-security-servlet-architecture#servlet-filterchainproxy`).

Since `FilterChainProxy` is a bean, it is typically wrapped in a `DelegatingFilterProxy` (`spring-security-servlet-architecture#servlet-filterchainproxy`).

`SecurityFilterChain` is used by `FilterChainProxy` to determine which Spring Security `Filter` instances should be invoked for the current request (`spring-security-servlet-architecture#servlet-securityfilterchain`).

The security filters in a `SecurityFilterChain` are typically beans, but they are registered with `FilterChainProxy` instead of `DelegatingFilterProxy` (`spring-security-servlet-architecture#servlet-securityfilterchain`).

`FilterChainProxy` provides a number of advantages to registering directly with the Servlet container or `DelegatingFilterProxy` (`spring-security-servlet-architecture#servlet-securityfilterchain`).

`FilterChainProxy` clears out the `SecurityContext` to avoid memory leaks (`spring-security-servlet-architecture#servlet-securityfilterchain`).

`FilterChainProxy` also applies Spring Security’s `HttpFirewall` to protect applications against certain types of attacks (`spring-security-servlet-architecture#servlet-securityfilterchain`).

In a Servlet container, `Filter` instances are invoked based upon the URL alone (`spring-security-servlet-architecture#servlet-securityfilterchain`).

`FilterChainProxy` can determine invocation based upon anything in the `HttpServletRequest` by using the `RequestMatcher` interface (`spring-security-servlet-architecture#servlet-securityfilterchain`).

Only the first `SecurityFilterChain` that matches is invoked (`spring-security-servlet-architecture#servlet-securityfilterchain`).

A request for `/api/messages/` first matches the `/api/**` pattern of `SecurityFilterChain0`, so only `SecurityFilterChain0` is invoked, even though it also matches `SecurityFilterChainn` (`spring-security-servlet-architecture#servlet-securityfilterchain`).

A `SecurityFilterChain` might have zero security `Filter` instances if the application wants Spring Security to ignore certain requests (`spring-security-servlet-architecture#servlet-securityfilterchain`).

:::diagram{kind="structure" caption="How a request reaches the security filters"}
description: DelegatingFilterProxy delegates to the FilterChainProxy bean, which uses the first matching SecurityFilterChain, SecurityFilterChain0 for /api/**, whose security filters are then invoked.
proxy: DelegatingFilterProxy
chainproxy: FilterChainProxy
chain0: SecurityFilterChain0 (/api/**)
chainn: SecurityFilterChainn
filters: Security filters
proxy -> chainproxy: wraps the bean
chainproxy -> chain0: first match is invoked
chainproxy -> chainn: not invoked when chain0 matches
chain0 -> filters: filters to invoke
:::

The security filters are inserted into the `FilterChainProxy` with the `SecurityFilterChain` API (`spring-security-servlet-architecture#servlet-security-filters`).

The filters are executed in a specific order to guarantee that they are invoked at the right time, for example, the `Filter` that performs authentication should be invoked before the `Filter` that performs authorization (`spring-security-servlet-architecture#servlet-security-filters`).

These security filters are most often declared using an `HttpSecurity` instance (`spring-security-servlet-architecture#servlet-security-filters`).

The ordering of Spring Security’s filters can be checked in the `FilterOrderRegistration` code (`spring-security-servlet-architecture#servlet-security-filters`).

With `csrf`, `httpBasic`, `formLogin` and `authorizeHttpRequests` configured, the `CsrfFilter` is invoked first to protect against CSRF attacks (`spring-security-servlet-architecture#servlet-security-filters`).

With the same configuration, the authentication filters are invoked second to authenticate the request (`spring-security-servlet-architecture#servlet-security-filters`).

With the same configuration, the `AuthorizationFilter` is invoked third to authorize the request (`spring-security-servlet-architecture#servlet-security-filters`).

The `AuthorizationFilter` is last in the Spring Security filter chain by default (`spring-security-servlet-authorization-authorize-http-requests#_authorizationfilter_is_last_by_default`).

Spring MVC endpoints are executed by the `DispatcherServlet`, which comes after the `AuthorizationFilter`, so they need to be included in `authorizeHttpRequests` to be permitted (`spring-security-servlet-authorization-authorize-http-requests#_authorizationfilter_is_last_by_default`).

The `ExceptionTranslationFilter` allows translation of `AccessDeniedException` and `AuthenticationException` into HTTP responses (`spring-security-servlet-architecture#servlet-exceptiontranslationfilter`).

An `AuthenticationException` or `AccessDeniedException` thrown by the `AuthorizationFilter` or by method security is caught and handled by the `ExceptionTranslationFilter`, because invoking `FilterChain.doFilter(request, response)` is the equivalent of invoking the rest of the application (`spring-security-servlet-architecture#servlet-exceptiontranslationfilter`).

If the user is not authenticated or it is an `AuthenticationException`, the `AuthenticationEntryPoint` is used to request credentials from the client (`spring-security-servlet-architecture#servlet-exceptiontranslationfilter`).

Otherwise, if it is an `AccessDeniedException`, the `AccessDeniedHandler` is invoked to handle access denied (`spring-security-servlet-architecture#servlet-exceptiontranslationfilter`).

`HttpSecurity` comes with three methods for adding filters: `addFilterBefore` adds a filter before another filter, `addFilterAfter` adds it after another filter, and `addFilterAt` replaces another filter with the new one (`spring-security-servlet-architecture#adding-filters-to-chain`).

## Authentication and the SecurityContext
<!-- bullets: 5.6.b -->

Authentication answers who is calling, and the answer has to be available everywhere in the code that handles the request. Spring Security keeps it in a `SecurityContext` held by the `SecurityContextHolder`, which by default is tied to the current thread. An `AuthenticationManager` produces the answer, usually through a `ProviderManager` that delegates to a list of `AuthenticationProvider` instances. Work handed to another thread needs the context transferred, because the holder acts on a per-thread basis in most cases.

The `SecurityContextHolder` is where Spring Security stores the details of who is authenticated (`spring-security-servlet-authentication-architecture#servlet-authentication-securitycontextholder`).

Spring Security does not care how the `SecurityContextHolder` is populated (`spring-security-servlet-authentication-architecture#servlet-authentication-securitycontextholder`).

You should create a new `SecurityContext` instance instead of using `SecurityContextHolder.getContext().setAuthentication(authentication)` to avoid race conditions across multiple threads (`spring-security-servlet-authentication-architecture#servlet-authentication-securitycontextholder`).

In Spring MVC, you can resolve the current principal with `@AuthenticationPrincipal` and the full `SecurityContext` with `@CurrentSecurityContext` (`spring-security-servlet-authentication-architecture#servlet-authentication-securitycontextholder`).

By default, `SecurityContextHolder` uses a `ThreadLocal` to store these details, which means that the `SecurityContext` is always available to methods in the same thread, even if the `SecurityContext` is not explicitly passed around as an argument to those methods (`spring-security-servlet-authentication-architecture#servlet-authentication-securitycontextholder`).

Using a `ThreadLocal` in this way is quite safe if you take care to clear the thread after the present principal’s request is processed (`spring-security-servlet-authentication-architecture#servlet-authentication-securitycontextholder`).

For a standalone application, the `SecurityContextHolder.MODE_GLOBAL` strategy makes all threads in a Java Virtual Machine use the same security context (`spring-security-servlet-authentication-architecture#servlet-authentication-securitycontextholder`).

`SecurityContextHolder.MODE_INHERITABLETHREADLOCAL` makes threads spawned by the secure thread assume the same security identity (`spring-security-servlet-authentication-architecture#servlet-authentication-securitycontextholder`).

The default mode is `SecurityContextHolder.MODE_THREADLOCAL`, and it can be changed with a system property or by calling a static method on `SecurityContextHolder` (`spring-security-servlet-authentication-architecture#servlet-authentication-securitycontextholder`).

The `Authentication` interface serves as an input to `AuthenticationManager`, where `isAuthenticated()` returns false, and represents the currently authenticated user (`spring-security-servlet-authentication-architecture#servlet-authentication-authentication`).

An `Authentication` contains the principal, the credentials and the authorities (`spring-security-servlet-authentication-architecture#servlet-authentication-authentication`).

The credentials are often a password, and in many cases they are cleared after the user is authenticated, to ensure that they are not leaked (`spring-security-servlet-authentication-architecture#servlet-authentication-authentication`).

`GrantedAuthority` instances are high-level permissions that the user is granted, and two examples are roles and scopes (`spring-security-servlet-authentication-architecture#servlet-authentication-granted-authority`).

Usually, the `GrantedAuthority` objects are application-wide permissions, not specific to a given domain object (`spring-security-servlet-authentication-architecture#servlet-authentication-granted-authority`).

`AuthenticationManager` is the API that defines how Spring Security’s filters perform authentication (`spring-security-servlet-authentication-architecture#servlet-authentication-authenticationmanager`).

The `Authentication` that is returned is then set on the `SecurityContextHolder` by the filters that invoked the `AuthenticationManager` (`spring-security-servlet-authentication-architecture#servlet-authentication-authenticationmanager`).

While the implementation of `AuthenticationManager` could be anything, the most common implementation is `ProviderManager` (`spring-security-servlet-authentication-architecture#servlet-authentication-authenticationmanager`).

`ProviderManager` delegates to a `List` of `AuthenticationProvider` instances (`spring-security-servlet-authentication-architecture#servlet-authentication-providermanager`).

Each `AuthenticationProvider` has an opportunity to indicate that authentication should be successful, fail, or indicate it cannot make a decision and allow a downstream `AuthenticationProvider` to decide (`spring-security-servlet-authentication-architecture#servlet-authentication-providermanager`).

`ProviderManager` also allows configuring an optional parent `AuthenticationManager`, which is consulted in the event that no `AuthenticationProvider` can perform authentication (`spring-security-servlet-authentication-architecture#servlet-authentication-providermanager`).

By default, `ProviderManager` tries to clear any sensitive credentials information from the `Authentication` object that is returned by a successful authentication request (`spring-security-servlet-authentication-architecture#servlet-authentication-providermanager`).

Clearing credentials prevents information, such as passwords, being retained longer than necessary in the `HttpSession` (`spring-security-servlet-authentication-architecture#servlet-authentication-providermanager`).

If the `Authentication` contains a reference to an object in a cache, such as a `UserDetails` instance, and this has its credentials removed, it is no longer possible to authenticate against the cached value (`spring-security-servlet-authentication-architecture#servlet-authentication-providermanager`).

`DaoAuthenticationProvider` supports username/password-based authentication, while `JwtAuthenticationProvider` supports authenticating a JWT token (`spring-security-servlet-authentication-architecture#servlet-authentication-authenticationprovider`).

When the user submits their credentials, the `AbstractAuthenticationProcessingFilter` creates an `Authentication` from the `HttpServletRequest` and passes it into the `AuthenticationManager` to be authenticated (`spring-security-servlet-authentication-architecture#servlet-authentication-abstractprocessingfilter`).

If authentication fails, the `SecurityContextHolder` is cleared out (`spring-security-servlet-authentication-architecture#servlet-authentication-abstractprocessingfilter`).

If authentication is successful, the `Authentication` is set on the `SecurityContextHolder` (`spring-security-servlet-authentication-architecture#servlet-authentication-abstractprocessingfilter`).

To save the `SecurityContext` so that it is automatically set on future requests, `SecurityContextRepository#saveContext` must be explicitly invoked (`spring-security-servlet-authentication-architecture#servlet-authentication-abstractprocessingfilter`).

`DelegatingSecurityContextRunnable` wraps a delegate `Runnable` in order to initialize the `SecurityContextHolder` with a specified `SecurityContext` for the delegate (`spring-security-servlet-concurrency#_delegatingsecuritycontextrunnable`).

`DelegatingSecurityContextRunnable` then invokes the delegate `Runnable`, ensuring to clear the `SecurityContextHolder` afterwards (`spring-security-servlet-concurrency#_delegatingsecuritycontextrunnable`).

`DelegatingSecurityContextRunnable` makes it seamless to transfer the `SecurityContext` from one `Thread` to another (`spring-security-servlet-concurrency#_delegatingsecuritycontextrunnable`).

Transferring the `SecurityContext` is important since, in most cases, the `SecurityContextHolder` acts on a per `Thread` basis (`spring-security-servlet-concurrency#_delegatingsecuritycontextrunnable`).

`DelegatingSecurityContextExecutor` accepts a delegate `Executor` instead of a delegate `Runnable`, and it wraps any `Runnable` passed into `execute` with a `DelegatingSecurityContextRunnable` (`spring-security-servlet-concurrency#_delegatingsecuritycontextexecutor`).

When a `DelegatingSecurityContextExecutor` is constructed with a `SecurityContext`, the same `SecurityContext` is used for every `Runnable` submitted to it (`spring-security-servlet-concurrency#_delegatingsecuritycontextexecutor`).

When it is constructed without a `SecurityContext`, the `SecurityContext` is obtained from the `SecurityContextHolder` each time `execute` is called, so the `Runnable` runs with the same user that invoked `execute` (`spring-security-servlet-concurrency#_delegatingsecuritycontextexecutor`).

## Request-level and method-level authorization
<!-- bullets: 5.6.c -->

Authorization decides what an authenticated caller may do, and Spring Security applies it at two levels. Request-level rules run in `AuthorizationFilter`, which passes the request to an `AuthorizationManager` that matches it to patterns. Method-level rules sit on beans and run through Spring AOP. Unannotated methods are not secured by annotation-based Method Security.

The `AuthorizationFilter` first constructs a `Supplier` that retrieves an `Authentication` from the `SecurityContextHolder` (`spring-security-servlet-authorization-authorize-http-requests#request-authorization-architecture`).

The `AuthorizationManager` matches the request to the patterns in `authorizeHttpRequests`, and runs the corresponding rule (`spring-security-servlet-authorization-authorize-http-requests#request-authorization-architecture`).

If authorization is denied, an `AuthorizationDeniedEvent` is published, and an `AccessDeniedException` is thrown (`spring-security-servlet-authorization-authorize-http-requests#request-authorization-architecture`).

The `ExceptionTranslationFilter` handles the `AccessDeniedException` (`spring-security-servlet-authorization-authorize-http-requests#request-authorization-architecture`).

If access is granted, an `AuthorizationGrantedEvent` is published and `AuthorizationFilter` continues with the `FilterChain` (`spring-security-servlet-authorization-authorize-http-requests#request-authorization-architecture`).

The `AuthorizationFilter` runs not just on every request, but on every dispatch, so REQUEST, FORWARD, ERROR and INCLUDE dispatches all need authorization (`spring-security-servlet-authorization-authorize-http-requests#_all_dispatches_are_authorized`).

When Spring MVC forwards to a view resolver, or Spring Boot dispatches an error, authorization happens twice, once for the endpoint and once for the FORWARD or ERROR dispatch (`spring-security-servlet-authorization-authorize-http-requests#_all_dispatches_are_authorized`).

:::esquema{kind=tabla title="Built-in request authorization rules"}
| Rule | What it requires | Source |
|---|---|---|
| `permitAll` | No authorization; the request is a public endpoint and the `Authentication` is never retrieved from the session | `spring-security-servlet-authorization-authorize-http-requests#authorize-requests` |
| `denyAll` | The request is not allowed under any circumstances | `spring-security-servlet-authorization-authorize-http-requests#authorize-requests` |
| `hasAuthority` | The `Authentication` has a `GrantedAuthority` that matches the given value | `spring-security-servlet-authorization-authorize-http-requests#authorize-requests` |
| `access` | A custom `AuthorizationManager` determines access | `spring-security-servlet-authorization-authorize-http-requests#authorize-requests` |
:::

`hasRole` is a shortcut for `hasAuthority` that prefixes `ROLE_` or whatever is configured as the default prefix (`spring-security-servlet-authorization-authorize-http-requests#authorize-requests`).

Each authorization rule is considered in the order it was declared (`spring-security-servlet-authorization-authorize-http-requests#authorize-requests`).

With `anyRequest().denyAll()` last, any URL that has not already been matched on is denied access (`spring-security-servlet-authorization-authorize-http-requests#authorize-requests`).

Method Security is built using Spring AOP (`spring-security-servlet-authorization-method-security#method-security-architecture`).

`@EnableMethodSecurity` supersedes `@EnableGlobalMethodSecurity` (`spring-security-servlet-authorization-method-security#method-security-architecture`).

`@EnableMethodSecurity` enables `@PreAuthorize`, `@PostAuthorize`, `@PreFilter` and `@PostFilter` by default (`spring-security-servlet-authorization-method-security#method-security-architecture`).

Method authorization is a combination of before- and after-method authorization (`spring-security-servlet-authorization-method-security#method-security-architecture`).

Spring AOP invokes its proxy method, and among the proxy’s other advisors it invokes an `AuthorizationManagerBeforeMethodInterceptor` that matches the `@PreAuthorize` pointcut (`spring-security-servlet-authorization-method-security#method-security-architecture`).

The interceptor invokes `PreAuthorizeAuthorizationManager#authorize` (`spring-security-servlet-authorization-method-security#method-security-architecture`).

If the `@PreAuthorize` evaluation passes, Spring AOP proceeds to invoke the method (`spring-security-servlet-authorization-method-security#method-security-architecture`).

If the evaluation does not pass, the interceptor publishes an `AuthorizationDeniedEvent` and throws an `AccessDeniedException`, which the `ExceptionTranslationFilter` catches and returns a 403 status code to the response (`spring-security-servlet-authorization-method-security#method-security-architecture`).

:::diagram{kind="flow" caption="How a @PreAuthorize call is authorized"}
description: Spring AOP invokes its proxy method, which invokes the AuthorizationManagerBeforeMethodInterceptor matching the @PreAuthorize pointcut; the interceptor invokes PreAuthorizeAuthorizationManager#authorize, and if the evaluation passes Spring AOP invokes the method, otherwise an AccessDeniedException is thrown.
proxy: Spring AOP proxy
interceptor: AuthorizationManagerBeforeMethodInterceptor
manager: PreAuthorizeAuthorizationManager
method: Target method
denied: AccessDeniedException
proxy -> interceptor: invokes the advisor matching @PreAuthorize
interceptor -> manager: invokes authorize
manager -> method: evaluation passes
manager -> denied: evaluation does not pass
:::

A method annotated with `@PreAuthorize("hasRole('ADMIN')")` can only be invoked if the provided expression `hasRole('ADMIN')` passes (`spring-security-servlet-authorization-method-security#use-preauthorize`).

A method annotated with `@PostAuthorize` can only return the value if the provided expression passes, and `returnObject` represents the object to be returned (`spring-security-servlet-authorization-method-security#use-postauthorize`).

`@PostAuthorize` is not recommended for classes that perform database writes, since that typically means that a database change was made before the security invariants were checked (`spring-security-servlet-authorization-method-security#use-postauthorize`).

If a method invocation involves multiple Method Security annotations, each of them is processed one at a time, so for an invocation to be authorized all annotation inspections need to pass authorization (`spring-security-servlet-authorization-method-security#unanimous-based-authorization-decisions`).

There is a Spring AOP method interceptor for each annotation, and each has a location in the Spring AOP advisor chain, with the `@PreFilter` interceptor’s order at 100 and the `@PreAuthorize` interceptor’s at 200 (`spring-security-servlet-authorization-method-security#changing-the-order`).

When Method Security annotations are declared at the class level, all methods inherit the class-level behavior, and a method that declares the annotation overrides the class-level one (`spring-security-servlet-authorization-method-security#class-or-interface-annotations`).

If a class inherits a Method Security annotation from two different interfaces, startup fails, because Spring Security has no way to tell which one you want to use (`spring-security-servlet-authorization-method-security#class-or-interface-annotations`).

When you use annotation-based Method Security, unannotated methods are not secured (`spring-security-servlet-authorization-method-security#request-vs-method`).

To protect against unsecured methods, declare a catch-all authorization rule in your `HttpSecurity` instance (`spring-security-servlet-authorization-method-security#request-vs-method`).

Instead of a complicated SpEL expression, you can grant `permission:read` to those with `ROLE_ADMIN`, for example with a `RoleHierarchy` (`spring-security-servlet-authorization-method-security#favor-granting-authorities`).

## A resource server with JWT
<!-- bullets: 5.6.d -->

A resource server authenticates requests that carry a bearer token. With a JWT, the server checks the token itself: the signature against a public key, then the timestamps and the issuer. It maps each scope to an authority. A resource server is multi-tenant when there are multiple strategies for verifying a bearer token, keyed by some tenant identifier. Taking any issuer to build a verifier is unsafe, so the issuer must be checked against a trusted source such as a list of allowed issuers.

In a Spring Boot application, the `issuer-uri` property specifies which authorization server to use, and Resource Server uses it to self-configure, discover the authorization server’s public keys, and subsequently validate incoming JWTs (`spring-security-servlet-oauth2-resource-server-jwt#_specifying_the_authorization_server`).

Resource Server attempts to process any request containing an `Authorization: Bearer` header (`spring-security-servlet-oauth2-resource-server-jwt#_runtime_expectations`).

`JwtAuthenticationProvider` is an `AuthenticationProvider` implementation that leverages a `JwtDecoder` and `JwtAuthenticationConverter` to authenticate a JWT (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-architecture`).

The authentication `Filter` passes a `BearerTokenAuthenticationToken` to the `AuthenticationManager`, which is implemented by `ProviderManager` (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-architecture`).

`JwtAuthenticationProvider` decodes, verifies, and validates the `Jwt` using a `JwtDecoder` (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-architecture`).

`JwtAuthenticationProvider` then uses the `JwtAuthenticationConverter` to convert the `Jwt` into a `Collection` of granted authorities (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-architecture`).

Given a well-formed JWT, Resource Server validates its signature against a public key obtained from the `jwks_url` endpoint during startup or on first request, depending on configuration (`spring-security-servlet-oauth2-resource-server-jwt#_runtime_expectations`).

Resource Server also validates the JWT’s `exp` and `nbf` timestamps and the JWT’s `iss` claim (`spring-security-servlet-oauth2-resource-server-jwt#_runtime_expectations`).

Resource Server maps each scope to an authority with the prefix `SCOPE_` (`spring-security-servlet-oauth2-resource-server-jwt#_runtime_expectations`).

To protect an endpoint or method with a scope derived from a JWT, the corresponding expression includes the `SCOPE_` prefix, for example `hasAuthority('SCOPE_messages')` (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-authorization`).

As the authorization server makes available new keys, Spring Security will automatically rotate the keys used to validate JWTs (`spring-security-servlet-oauth2-resource-server-jwt#_runtime_expectations`).

By default, `Authentication#getPrincipal` is a Spring Security `Jwt` object, and `Authentication#getName` maps to the JWT’s `sub` property, if one is present (`spring-security-servlet-oauth2-resource-server-jwt#_runtime_expectations`).

Exposing a `JwtDecoder` bean has the same effect as `decoder()` (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-decoder-bean`).

Spring Security ships with `JwtAuthenticationConverter`, which is responsible for converting a `Jwt` into an `Authentication` (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-authorization-extraction`).

By default, Spring Security wires the `JwtAuthenticationProvider` with a default instance of `JwtAuthenticationConverter` (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-authorization-extraction`).

The claim that `JwtAuthenticationConverter` inspects for authorities can be configured, for example when the authorization server communicates authorities in a custom claim called `authorities` (`spring-security-servlet-oauth2-resource-server-jwt#jwt-granted-authorities-custom-claim-name`).

Resource Server also accepts custom `OAuth2TokenValidator` instances when validation needs to be customized (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-validation`).

Resource Server uses `JwtTimestampValidator` to verify a token’s validity window, and by default it configures a clock skew of 60 seconds (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-validation-clockskew`).

By default, Resource Server uses connection and socket timeouts of 30 seconds each for coordinating with the authorization server (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-timeouts`).

By default, Resource Server caches in memory the authorization server’s JWK set for 5 minutes (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-timeouts`).

A resource server is considered multi-tenant when there are multiple strategies for verifying a bearer token, keyed by some tenant identifier (`spring-security-servlet-oauth2-resource-server-multitenancy#oauth2resourceserver-multitenancy`).

Multi-tenancy requires two things, resolving the tenant and propagating the tenant (`spring-security-servlet-oauth2-resource-server-multitenancy#oauth2resourceserver-multitenancy`).

One way to differentiate tenants is by the issuer claim (`spring-security-servlet-oauth2-resource-server-multitenancy#_resolving_the_tenant_by_claim`).

The issuer claim accompanies signed JWTs, so tenants can be resolved with the `JwtIssuerAuthenticationManagerResolver` (`spring-security-servlet-oauth2-resource-server-multitenancy#_resolving_the_tenant_by_claim`).

The issuer endpoints are loaded lazily, so the corresponding `JwtAuthenticationProvider` is instantiated only when the first request with the corresponding issuer is sent (`spring-security-servlet-oauth2-resource-server-multitenancy#_resolving_the_tenant_by_claim`).

Lazy loading allows for an application startup that is independent from those authorization servers being up and available (`spring-security-servlet-oauth2-resource-server-multitenancy#_resolving_the_tenant_by_claim`).

To add a tenant without restarting the application, the `JwtIssuerAuthenticationManagerResolver` can be configured with a repository of `AuthenticationManager` instances, which can be edited at runtime (`spring-security-servlet-oauth2-resource-server-multitenancy#_dynamic_tenants`).

It would be unsafe to simply take any issuer and construct an `AuthenticationManager` from it (`spring-security-servlet-oauth2-resource-server-multitenancy#_dynamic_tenants`).

The issuer should be one that the code can verify from a trusted source like a list of allowed issuers (`spring-security-servlet-oauth2-resource-server-multitenancy#_dynamic_tenants`).

## Key points

- `DelegatingFilterProxy` delays looking up `Filter` beans, and the security filters themselves are registered with `FilterChainProxy`.
- `FilterChainProxy` invokes only the first `SecurityFilterChain` that matches the request.
- The security filters run in a specific order, so the authentication filter runs before the authorization filter, and the `AuthorizationFilter` is last by default.
- `ExceptionTranslationFilter` catches the `AccessDeniedException` and `AuthenticationException` thrown by the `AuthorizationFilter` or by method security.
- `SecurityContextHolder` stores who is authenticated and uses a `ThreadLocal` by default.
- `ProviderManager` is the most common `AuthenticationManager` and delegates to `AuthenticationProvider` instances.
- `DelegatingSecurityContextRunnable` transfers the `SecurityContext` to another thread and clears it afterwards.
- `AuthorizationFilter` denies a request with an `AccessDeniedException` that `ExceptionTranslationFilter` handles.
- `AuthorizationFilter` runs on every dispatch, so FORWARD and ERROR dispatches need authorization too.
- Unannotated methods are not secured by annotation-based Method Security.
- `JwtAuthenticationProvider` decodes the `Jwt` with a `JwtDecoder` and converts it to authorities with `JwtAuthenticationConverter`.
- Resource Server maps each scope to an authority with the prefix `SCOPE_`.
- A resource server that resolves tenants by issuer loads the issuer endpoints lazily and should only accept issuers from a trusted source.

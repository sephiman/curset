# Spring Boot auto-configuration

## Discovery, ordering and the condition report
<!-- bullets: 5.2.a -->

Spring Boot auto-configuration attempts to automatically configure your Spring application based on the jar dependencies that you have added (`spring-boot-using-auto-configuration#page-title`).

You opt in to auto-configuration by adding `@EnableAutoConfiguration` or `@SpringBootApplication` to one of your `@Configuration` classes (`spring-boot-using-auto-configuration#page-title`).

You should only ever add one `@SpringBootApplication` or `@EnableAutoConfiguration` annotation (`spring-boot-using-auto-configuration#page-title`).

The documentation generally recommends adding one or the other to your primary `@Configuration` class only (`spring-boot-using-auto-configuration#page-title`).

Classes that implement auto-configuration are annotated with `@AutoConfiguration`, which is meta-annotated with `@Configuration`, so auto-configurations are standard `@Configuration` classes (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.understanding-auto-configured-beans`).

Auto-configuration classes usually use the `@ConditionalOnClass` and `@ConditionalOnMissingBean` annotations (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.understanding-auto-configured-beans`).

This ensures that auto-configuration applies only when relevant classes are found and when you have not declared your own `@Configuration` (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.understanding-auto-configured-beans`).

Spring Boot checks for the presence of a `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` file within your published jar (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

Auto-configurations must be loaded only by being named in the imports file (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

To apply a configuration in a specific order, use the `before`, `beforeName`, `after` and `afterName` attributes of `@AutoConfiguration`, or the dedicated `@AutoConfigureBefore` and `@AutoConfigureAfter` annotations (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

`@AutoConfigureOrder` has the same semantic as the regular `@Order` annotation but provides a dedicated order for auto-configuration classes (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

The order in which auto-configuration classes are applied only affects the order in which their beans are defined (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

The order in which those beans are subsequently created is unaffected and is determined by each bean's dependencies and any `@DependsOn` relationships (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

A `ConditionEvaluationReport` is available in any Spring Boot `ApplicationContext` (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

You can see the report if you enable `DEBUG` logging output (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

With the actuator, a `conditions` endpoint renders the report in JSON (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

Adding `--debug` to the command line or the system property `-Ddebug` logs all the auto-configuration decisions that were made in your app on the console (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

Classes annotated with `@ConfigurationProperties`, such as `ServerProperties`, show the available external configuration options (`spring-boot-howto-application#howto.application.troubleshoot-auto-configuration`).

## Starters and externalised configuration
<!-- bullets: 5.2.b -->

Starters are a set of convenient dependency descriptors that you can include in your application (`spring-boot-using-build-systems#using.build-systems.starters`).

To use Spring and JPA for database access, include the `spring-boot-starter-data-jpa` dependency in your project (`spring-boot-using-build-systems#using.build-systems.starters`).

All official starters follow the naming pattern `spring-boot-starter-*`, where `*` is a particular type of application (`spring-boot-using-build-systems#using.build-systems.starters`).

Third-party starters should not start with `spring-boot`, as it is reserved for official Spring Boot artifacts (`spring-boot-using-build-systems#using.build-systems.starters`).

A third-party starter typically starts with the name of the project (`spring-boot-using-build-systems#using.build-systems.starters`).

Spring Boot lets you externalize your configuration so that you can work with the same application code in different environments (`spring-boot-features-external-config#page-title`).

Property values can be injected into your beans with `@Value`, accessed through the `Environment` abstraction, or bound to structured objects through `@ConfigurationProperties` (`spring-boot-features-external-config#page-title`).

`@ConfigurationProperties` lets strongly typed beans govern and validate the configuration of your application (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties`).

Spring Boot uses relaxed rules for binding `Environment` properties to `@ConfigurationProperties` beans, so the property name and the bean property name do not need to match exactly (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding`).

A dash-separated property such as `context-path` binds to `contextPath`, and a capitalized property such as `PORT` binds to `port` (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding`).

:::esquema{kind=tabla title="Relaxed binding of one property"}
| Property | Note | Citation |
| --- | --- | --- |
| `my.main-project.person.first-name` | Kebab case, which is recommended for use in `.properties` and YAML files | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding` |
| `my.main-project.person.firstName` | Standard camel case syntax | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding` |
| `my.main-project.person.first_name` | Underscore notation, which is an alternative format for use in `.properties` and YAML files | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding` |
| `MY_MAINPROJECT_PERSON_FIRSTNAME` | Upper case format, which is recommended when using system environment variables | `spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding` |
:::

The prefix value of the `@ConfigurationProperties` annotation must be in kebab case (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding`).

The documentation recommends that properties are stored in lower-case kebab format when possible, such as `my.person.first-name=Rod` (`spring-boot-features-external-config#features.external-config.typesafe-configuration-properties.relaxed-binding`).

Spring Boot uses a very particular `PropertySource` order, and later property sources can override the values defined in earlier ones (`spring-boot-features-external-config#page-title`).

Among the sources, config data such as `application.properties` files is considered first, then `random.*` properties, then OS environment variables, then Java System properties, then JNDI attributes (`spring-boot-features-external-config#page-title`).

After `ServletContext` and `ServletConfig` init parameters and `SPRING_APPLICATION_JSON`, command line arguments are considered (`spring-boot-features-external-config#page-title`).

Config data files are considered in this order: application properties inside your jar, profile-specific properties inside your jar, application properties outside your jar, profile-specific properties outside your jar (`spring-boot-features-external-config#page-title`).

If configuration files in both `.properties` and YAML format are in the same location, `.properties` takes precedence (`spring-boot-features-external-config#page-title`).

Spring Boot automatically finds and loads `application.properties` and `application.yaml` files from locations on the classpath and in the current directory when your application starts (`spring-boot-features-external-config#features.external-config.files`).

The list of default locations is ordered by precedence, with values from lower items overriding earlier ones (`spring-boot-features-external-config#features.external-config.files`).

You can switch to another file name than `application` by specifying a `spring.config.name` environment property (`spring-boot-features-external-config#features.external-config.files`).

The `spring.config.location` environment property accepts a comma-separated list of one or more locations to check (`spring-boot-features-external-config#features.external-config.files`).

Locations configured by using `spring.config.location` replace the default locations (`spring-boot-features-external-config#features.external-config.files`).

To add locations rather than replace the default ones, use `spring.config.additional-location`; properties loaded from additional locations can override those in the default locations (`spring-boot-features-external-config#features.external-config.files`).

The `spring.config.name`, `spring.config.location` and `spring.config.additional-location` properties are used very early to determine which files have to be loaded (`spring-boot-features-external-config#features.external-config.files`).

They must be defined as an environment property, typically an OS environment variable, a system property or a command-line argument (`spring-boot-features-external-config#features.external-config.files`).

Use the prefix `optional:` if the locations are optional and you do not mind if they do not exist (`spring-boot-features-external-config#features.external-config.files`).

## Writing an auto-configuration and a starter
<!-- bullets: 5.2.c -->

The imports file should list your configuration classes, with one class name per line (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

You can add comments to the imports file using the `#` character (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

If an auto-configuration class is not a top-level class, its class name should use `$` to separate it from its containing class (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

Auto-configurations should be defined in a specific package space and must never be the target of component scanning (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

Auto-configuration classes should not enable component scanning to find additional components, and specific `@Import` annotations should be used instead (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.locating-auto-configuration-candidates`).

You almost always want to include one or more `@Conditional` annotations on your auto-configuration class (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations`).

`@ConditionalOnMissingBean` is a common example used to allow developers to override auto-configuration if they are not happy with your defaults (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations`).

Spring Boot includes `@Conditional` annotations in six groups: class, bean, property, resource, web application and SpEL expression conditions (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.condition-annotations`).

A typical Spring Boot starter contains code to auto-configure and customize the infrastructure of a given technology (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

To make the starter easily extensible, a number of configuration keys in a dedicated namespace can be exposed to the environment (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

A starter can have one module with the auto-configuration code and any API to use the feature, and a second module that provides a dependency to the other starters required, to the first module, and potentially additional dependencies (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

This separation in two modules is in no way necessary (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

If the technology has several flavors, options or optional features, it is better to separate the auto-configuration, as you can clearly express the fact that some features are optional (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

If the auto-configuration is relatively straightforward and does not have optional features, merging the two modules in the starter is definitely an option (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

A separate test-scoped starter can offer test-specific auto-configurations, for example to replace external dependencies with in-memory alternatives (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.custom-starter`).

An auto-configuration can be affected by many factors: user configuration, condition evaluation and others (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

Each test should create a well defined `ApplicationContext` that represents a combination of those customizations (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

`ApplicationContextRunner` does not work when running the tests in a native image (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

If multiple auto-configurations have to be defined, there is no need to order their declarations, as they are invoked in the exact same order as when running the application (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

The runner can also display the `ConditionEvaluationReport`, which can be printed at `INFO` or `DEBUG` level (`spring-boot-features-developing-auto-configuration#features.developing-auto-configuration.testing`).

## Key points

- Auto-configuration is opt-in through `@EnableAutoConfiguration` or `@SpringBootApplication`, added once, on the primary `@Configuration` class.
- Auto-configuration classes are `@Configuration` classes loaded only by being named in the `AutoConfiguration.imports` file, never by component scanning.
- Ordering auto-configurations affects only the order in which beans are defined; bean creation order follows dependencies and `@DependsOn`.
- The `ConditionEvaluationReport` shows the auto-configuration decisions: with `DEBUG` logging, `--debug`, or the `conditions` endpoint.
- All official starters follow the naming pattern `spring-boot-starter-*`; a third-party starter typically starts with the name of the project.
- Kebab case is the recommended format for property names in `.properties` and YAML files, and the prefix of `@ConfigurationProperties` must be in kebab case.
- Later property sources override earlier ones; command line arguments come after OS environment variables and Java System properties.
- `spring.config.location` replaces the default locations, and `spring.config.additional-location` adds to them.
- Splitting a starter into an auto-configuration module and a starter module is not necessary.
- Each auto-configuration test should create a well defined `ApplicationContext`.

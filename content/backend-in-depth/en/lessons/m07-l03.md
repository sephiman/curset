# Load balancing and the edge

## Load balancers in front of Kubernetes Services
<!-- bullets: 7.3.a -->

On cloud providers which support external load balancers, setting the type field of a Service to LoadBalancer provisions a load balancer for your Service (`k8s-service#loadbalancer`).

The actual creation of the load balancer happens asynchronously (`k8s-service#loadbalancer`).

Traffic from the external load balancer is directed at the backend Pods, and the cloud provider decides how it is load balanced (`k8s-service#loadbalancer`).

To implement a Service of type LoadBalancer, Kubernetes typically starts off by making the changes that are equivalent to requesting a Service of type NodePort (`k8s-service#loadbalancer`).

The cloud-controller-manager component then configures the external load balancer to forward traffic to that assigned node port (`k8s-service#loadbalancer`).

To make sure that connections from a particular client are passed to the same Pod each time, you can configure session affinity based on the client's IP address (`k8s-service#session-stickiness`).

The .spec.trafficDistribution field provides another way to influence traffic routing within a Kubernetes Service (`k8s-service#traffic-distribution`).

While traffic policies focus on strict semantic guarantees, traffic distribution allows you to express preferences, such as routing to topologically closer endpoints (`k8s-service#traffic-distribution`).

The PreferSameZone value indicates a preference for routing traffic to endpoints that are in the same zone as the client (`k8s-service#traffic-distribution`).

The PreferSameNode value indicates a preference for routing traffic to endpoints that are on the same node as the client (`k8s-service#traffic-distribution`).

If the .spec.trafficDistribution field is not set, the implementation applies its default routing strategy (`k8s-service#traffic-distribution`).

## Balancing algorithms
<!-- bullets: 7.3.a -->

:::judgement{source="Envoy project, Supported load balancers" ref="envoy-load-balancers#arch-overview-load-balancing-types-round-robin"}
According to the Envoy project's documentation, a round robin policy selects each available upstream host in turn, and when weights are assigned, higher weighted endpoints appear more often in the rotation.
:::

:::judgement{source="Envoy project, Supported load balancers" ref="envoy-load-balancers#arch-overview-load-balancing-types-least-request"}
According to the Envoy project's documentation, when all weights are equal the least request balancer selects N random available hosts (2 by default) and picks the one with the fewest active requests, an approach also known as power of two choices.
:::

:::judgement{source="Envoy project, Supported load balancers" ref="envoy-load-balancers#arch-overview-load-balancing-types-ring-hash"}
According to the Envoy project's documentation, a ring hash balancer implements consistent hashing: each host is mapped onto a circle by hashing its address, and each request goes to the nearest host clockwise from the hash of some property of the request.
:::

:::judgement{source="Envoy project, Supported load balancers" ref="envoy-load-balancers#arch-overview-load-balancing-types-random"}
According to the Envoy project's documentation, a random balancer selects a random available host, and it generally performs better than round robin when no health checking policy is configured.
:::

## Health checks and readiness
<!-- bullets: 7.3.a -->

Applications can be temporarily unable to serve traffic, for example while they load large data or configuration files during startup or depend on external services after startup (`k8s-probes#define-readiness-probes`).

In such cases you do not want to kill the application, but you do not want to send it requests either (`k8s-probes#define-readiness-probes`).

Kubernetes provides readiness probes to detect and mitigate these situations (`k8s-probes#define-readiness-probes`).

A pod with containers reporting that they are not ready does not receive traffic through Kubernetes Services (`k8s-probes#define-readiness-probes`).

The serving condition of an endpoint indicates that the endpoint is currently serving responses, and so it should be used as a target for Service traffic (`k8s-endpoint-slices#serving`).

For endpoints backed by a Pod, the serving condition maps to the Pod's Ready condition (`k8s-endpoint-slices#serving`).

:::judgement{source="Envoy project, Health checking" ref="envoy-health-checking#arch-overview-health-checking"}
According to the Envoy project's documentation, during HTTP health checking Envoy sends an HTTP request to the upstream host and by default expects a 200 response if the host is healthy, while L3/L4 health checking sends a configurable byte buffer that the host must echo.
:::

:::judgement{source="Envoy project, Health checking" ref="envoy-health-checking#passive-health-checking"}
According to the Envoy project's documentation, Envoy also supports passive health checking through outlier detection.
:::

## Connection draining
<!-- bullets: 7.3.a -->

The terminating condition of an endpoint indicates that the endpoint is terminating (`k8s-endpoint-slices#terminating`).

For endpoints backed by a Pod, the terminating condition is set when the Pod is first deleted, when it receives a deletion timestamp, but most likely before the Pod's containers exit (`k8s-endpoint-slices#terminating`).

Service proxies will normally ignore endpoints that are terminating, but they may route traffic to endpoints that are both serving and terminating if all available endpoints are terminating (`k8s-endpoint-slices#terminating`).

Routing to serving and terminating endpoints helps to ensure that no Service traffic is lost during rolling updates of the underlying Pods (`k8s-endpoint-slices#terminating`).

The default grace period when you delete a Pod is 30 seconds (`k8s-pod-lifecycle#pod-termination-flow`).

As soon as the kubelet sees that a Pod has been marked as terminating, the kubelet begins the local Pod shutdown process (`k8s-pod-lifecycle#pod-termination-flow`).

If one of the Pod's containers has defined a preStop hook and terminationGracePeriodSeconds is not set to 0, the kubelet runs that hook inside of the container (`k8s-pod-lifecycle#pod-termination-flow`).

The default terminationGracePeriodSeconds setting is 30 seconds (`k8s-pod-lifecycle#pod-termination-flow`).

If the preStop hook is still running after the grace period expires, the kubelet requests a small, one-off grace period extension of 2 seconds (`k8s-pod-lifecycle#pod-termination-flow`).

## Reverse proxies and gateways
<!-- bullets: 7.3.b -->

HTTP enables the use of intermediaries to satisfy requests through a chain of connections (`rfc9110#section-3.7`).

There are three common forms of HTTP intermediary: proxy, gateway, and tunnel (`rfc9110#section-3.7`).

A proxy is a message-forwarding agent that is chosen by the client, usually via local configuration rules (`rfc9110#section-3.7`).

A gateway, also called a reverse proxy, is an intermediary that acts as an origin server for the outbound connection but translates received requests and forwards them inbound to another server or servers (`rfc9110#section-3.7`).

Gateways are often used to encapsulate legacy or untrusted information services, to improve server performance through accelerator caching, and to enable partitioning or load balancing of HTTP services across multiple machines (`rfc9110#section-3.7`).

A tunnel acts as a blind relay between two connections without changing the messages (`rfc9110#section-3.7`).

In HTTP, inbound means toward the origin server, whereas outbound means toward the user agent (`rfc9110#section-3.7`).

An interception proxy differs from an HTTP proxy because it is not chosen by the client (`rfc9110#section-3.7`).

Proxies are often used to group an organization's HTTP requests through a common intermediary for the sake of security services, annotation services, or shared caching (`rfc9110#section-3.7`).

## Ingress
<!-- bullets: 7.3.b -->

The Kubernetes project recommends using Gateway instead of Ingress, and the Ingress API has been frozen (`k8s-ingress#note`).

The Kubernetes project has no plans to remove Ingress from Kubernetes (`k8s-ingress#note`).

The Ingress API is no longer being developed, and will have no further changes or updates made to it (`k8s-ingress#note`).

Ingress exposes HTTP and HTTPS routes from outside the cluster to services within the cluster (`k8s-ingress#what-is-ingress`).

Traffic routing is controlled by rules defined on the Ingress resource (`k8s-ingress#what-is-ingress`).

An Ingress controller is responsible for fulfilling the Ingress, usually with a load balancer (`k8s-ingress#what-is-ingress`).

An Ingress does not expose arbitrary ports or protocols (`k8s-ingress#what-is-ingress`).

Both the host and path must match the content of an incoming request before the load balancer directs traffic to the referenced Service (`k8s-ingress#ingress-rules`).

A defaultBackend is often configured in an Ingress controller to service any requests that do not match a path in the spec (`k8s-ingress#ingress-rules`).

Paths that do not include an explicit pathType will fail validation (`k8s-ingress#path-types`).

:::esquema{kind=tabla title="Ingress path types"}
| Path type | Matching | Source |
|---|---|---|
| `Exact` | Matches the URL path exactly and with case sensitivity | `k8s-ingress#path-types` |
| `Prefix` | Matches based on a URL path prefix split by `/` | `k8s-ingress#path-types` |
| `ImplementationSpecific` | Matching is up to the IngressClass | `k8s-ingress#path-types` |
:::

## Gateway API
<!-- bullets: 7.3.b -->

Gateway API has four stable API kinds: GatewayClass, Gateway, HTTPRoute and GRPCRoute (`k8s-gateway-api-concept#resource-model`).

GatewayClass defines a set of gateways with common configuration and managed by a controller that implements the class (`k8s-gateway-api-concept#resource-model`).

Gateway defines an instance of traffic handling infrastructure, such as cloud load balancer (`k8s-gateway-api-concept#resource-model`).

HTTPRoute defines HTTP-specific rules for mapping traffic from a Gateway listener to a representation of backend network endpoints (`k8s-gateway-api-concept#resource-model`).

GRPCRoute defines gRPC-specific rules for mapping traffic from a Gateway listener to a representation of backend network endpoints (`k8s-gateway-api-concept#resource-model`).

A Gateway object is associated with exactly one GatewayClass, which describes the gateway controller responsible for managing Gateways of this class (`k8s-gateway-api-concept#resource-model`).

Each GatewayClass will be handled by a single controller, although controllers may handle more than one GatewayClass (`gateway-api-concepts-api-overview#gatewayclass`).

GatewayClass is a cluster-scoped resource (`gateway-api-concepts-api-overview#gatewayclass`).

There must be at least one GatewayClass defined in order to be able to have functional Gateways (`gateway-api-concepts-api-overview#gatewayclass`).

Gateway objects bind one or more Addresses to one or more Listeners (`gateway-api-concepts-api-overview#gateway`).

Listeners describe how the Gateway should listen for traffic, and have a port, a protocol, and other protocol-specific details (`gateway-api-concepts-api-overview#gateway`).

HTTPRoute is for multiplexing HTTP or terminated HTTPS connections (`gateway-api-concepts-api-overview#httproute`).

For a Route to attach to a Listener, the Route must reference a Gateway in its parentRefs stanza (`gateway-api-concepts-api-overview#attaching-routes-to-gateways`).

For a Route to attach to a Listener, the Listener must accept the Route's attachment (`gateway-api-concepts-api-overview#attaching-routes-to-gateways`).

A Gateway can have many Routes bound to it that are owned by different teams from across different Namespaces (`gateway-api-concepts-api-overview#attaching-routes-to-gateways`).

A single Route can be bound to more than one Gateway, allowing it to control application exposure across different IPs, load balancers, or networks (`gateway-api-concepts-api-overview#attaching-routes-to-gateways`).

The Ingress API only supports TLS termination and simple content-based request routing of HTTP traffic (`gateway-api-migrating-from-ingress#reasons-to-switch-to-gateway-api`).

The annotations approach to extensibility of Ingress leads to limited portability as every implementation has its own supported extensions that may not translate to any other implementation (`gateway-api-migrating-from-ingress#reasons-to-switch-to-gateway-api`).

The Ingress API is not well-suited for multi-team clusters with shared load-balancing infrastructure (`gateway-api-migrating-from-ingress#reasons-to-switch-to-gateway-api`).

The Ingress API is widely adopted by Kubernetes users and well-supported by vendors with many implementations available (`gateway-api-migrating-from-ingress#reasons-to-switch-to-gateway-api`).

## Shared caches
<!-- bullets: 7.3.c -->

A cache is a local store of previous response messages and the subsystem that controls its message storage, retrieval, and deletion (`rfc9110#section-3.8`).

A cache stores cacheable responses in order to reduce the response time and network bandwidth consumption on future, equivalent requests (`rfc9110#section-3.8`).

Content delivery networks use gateway caching to optimize regional and global distribution of popular sites (`rfc9110#section-3.8`).

A cache must not store a response to a request unless, among other conditions, the no-store cache directive is not present in the response (`rfc9111#section-3`).

If the cache is shared, a cache must not store a response unless the Authorization header field is not present in the request or a response directive explicitly allows shared caching (`rfc9111#section-3`).

A fresh response is one whose age has not yet exceeded its freshness lifetime, and a stale response is one where it has (`rfc9111#section-4.2`).

When a response is fresh, it can be used to satisfy subsequent requests without contacting the origin server, thereby improving efficiency (`rfc9111#section-4.2`).

The primary mechanism for determining freshness is for an origin server to provide an explicit expiration time in the future, using either the Expires header field or the max-age response directive (`rfc9111#section-4.2`).

The s-maxage response directive indicates that, for a shared cache, the maximum age specified by this directive overrides the maximum age specified by either the max-age directive or the Expires header field (`rfc9111#section-5.2.2.10`).

A shared cache must not reuse a stale response with s-maxage to satisfy another request until it has been successfully validated by the origin (`rfc9111#section-5.2.2.10`).

The s-maxage directive also permits a shared cache to reuse a response to a request containing an Authorization header field (`rfc9111#section-5.2.2.10`).

The s-maxage directive uses the token form of the argument syntax, and a sender must not generate the quoted-string form (`rfc9111#section-5.2.2.10`).

A stored response with a Vary header field value containing a member * always fails to match (`rfc9111#section-4.1`).

A cache must not generate a stale response unless it is disconnected or doing so is explicitly permitted by the client or origin server (`rfc9111#section-4.2.4`).

The stale-while-revalidate Cache-Control extension indicates that caches may serve the response after it becomes stale, up to the indicated number of seconds (`rfc5861#section-3`).

If a cached response is served stale due to stale-while-revalidate, the cache should attempt to revalidate it while still serving stale responses, without blocking (`rfc5861#section-3`).

If delta-seconds passes without the cached entity being revalidated, it should not continue to be served stale, absent other information (`rfc5861#section-3`).

## CDNs and edge caching
<!-- bullets: 7.3.c -->

:::judgement{source="Cloudflare documentation, Cache" ref="cloudflare-cache-overview#_top"}
According to the Cloudflare documentation, a CDN cache stores copies of frequently accessed content, such as images, videos or webpages, in geographically distributed data centers located closer to end users than origin servers, which reduces server load and improves website performance.
:::

:::judgement{source="Cloudflare documentation, Purge cache" ref="cloudflare-cache-purge#_top"}
According to the Cloudflare documentation, purging by URL is the recommended way to remove cached content, and a successful purge request returns HTTP 200, which shows that Cloudflare received the request and does not confirm that it evicted any content.
:::

## Key points

- A Service of type `LoadBalancer` provisions an external load balancer on cloud providers that support one, and the cloud provider decides how traffic is balanced.
- Kubernetes implements `LoadBalancer` by first doing what a `NodePort` Service does, and the cloud-controller-manager then points the balancer at the node port.
- A Pod whose containers report not ready receives no traffic through Kubernetes Services, and the endpoint's serving condition maps to the Pod's Ready condition.
- An endpoint becomes terminating when its Pod is first deleted, and Service proxies normally ignore terminating endpoints.
- The default termination grace period is 30 seconds, and a `preStop` hook that is still running gets a one-off extension of 2 seconds.
- RFC 9110 names three intermediaries: a proxy chosen by the client, a gateway also called a reverse proxy, and a tunnel that relays blindly.
- The Ingress API has been frozen, and the Kubernetes project recommends using Gateway instead.
- Ingress has three path types: `Exact`, `Prefix` and `ImplementationSpecific`.
- Gateway API separates `GatewayClass`, `Gateway` and route kinds such as `HTTPRoute`, and a Gateway has exactly one `GatewayClass`.
- A Route attaches to a Listener when it references the Gateway in `parentRefs` and the Listener accepts it.
- For a shared cache, `s-maxage` overrides `max-age` and `Expires` and requires validation of a stale response before reuse.
- `stale-while-revalidate` lets a cache serve a stale response for the indicated number of seconds while it revalidates.

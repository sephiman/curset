# Spring Data and JPA

## Repositories and derived queries
<!-- bullets: 5.7.a -->

A Spring Data repository is an interface that you declare, and Spring Data JPA creates the queries for it from the method names. The lookup strategy decides whether a query is created from the name, taken from a declaration, or taken from a declaration first and created only when none exists.

The central interface in the Spring Data repository abstraction is `Repository` (`spring-data-jpa-repositories-core-concepts#page-title`).

`Repository` acts primarily as a marker interface to capture the types to work with and to help you to discover interfaces that extend it (`spring-data-jpa-repositories-core-concepts#page-title`).

The `CrudRepository` and `ListCrudRepository` interfaces provide CRUD functionality for the entity class that is being managed (`spring-data-jpa-repositories-core-concepts#page-title`).

`ListCrudRepository` offers equivalent methods to `CrudRepository`, but they return `List` where the `CrudRepository` methods return an `Iterable` (`spring-data-jpa-repositories-core-concepts#page-title`).

`JpaRepository` is a persistence technology-specific abstraction that extends `CrudRepository` and exposes the capabilities of the underlying persistence technology (`spring-data-jpa-repositories-core-concepts#page-title`).

`PagingAndSortingRepository` adds methods to ease paginated access to entities (`spring-data-jpa-repositories-core-concepts#page-title`).

Spring Data JPA repositories are interfaces that you can define to access data, and JPA queries are created automatically from your method names (`spring-boot-data-sql#data.sql.jpa-and-spring-data.repositories`).

Parsing query method names is divided into subject and predicate (`spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-creation`).

The first `By` in a query method name acts as a delimiter to indicate the start of the actual criteria predicate (`spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-creation`).

The supported operators in derived queries can vary by datastore (`spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-creation`).

The method parser supports setting an `IgnoreCase` flag for individual properties, for example `findByLastnameIgnoreCase(…)` (`spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-creation`).

Static ordering is applied by appending an `OrderBy` clause that references a property and a sorting direction, `Asc` or `Desc` (`spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-creation`).

`CREATE_IF_NOT_FOUND` is the default lookup strategy and is used if you do not configure anything explicitly (`spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-lookup-strategies`).

:::esquema{kind=tabla title="Query lookup strategies"}
| Strategy | What the repository infrastructure does | Source |
|---|---|---|
| `CREATE` | Constructs a store-specific query from the query method name | `spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-lookup-strategies` |
| `USE_DECLARED_QUERY` | Looks for a declared query and fails at bootstrap time if it finds none | `spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-lookup-strategies` |
| `CREATE_IF_NOT_FOUND` | Looks up a declared query first and, if none is found, creates a method name-based query | `spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-lookup-strategies` |
:::

## Declared queries, projections and specifications
<!-- bullets: 5.7.a -->

A query declared with `@Query` is bound to the repository method that runs it. A projection limits what a query returns to a subset of the attributes. A specification expresses a predicate in code, so that repositories can reuse it.

Queries annotated to the query method take precedence over queries defined using `@NamedQuery` or named queries declared in `orm.xml` (`spring-data-jpa-query-methods#jpa.query-methods.at-query`).

Using `@Query` frees the domain class from persistence specific information and co-locates the query to the repository interface (`spring-data-jpa-query-methods#jpa.query-methods.at-query`).

By default, Spring Data JPA uses position-based parameter binding (`spring-data-jpa-query-methods#jpa.named-parameters`).

The `@Param` annotation gives a method parameter a concrete name that the query can bind (`spring-data-jpa-query-methods#jpa.named-parameters`).

Annotating the query method with `@Modifying` triggers the annotated query as an updating query instead of a selecting one (`spring-data-jpa-query-methods#jpa.modifying-queries`).

Spring Data does not automatically clear the `EntityManager` after a modifying query, because clearing it drops all non-flushed changes still pending in it (`spring-data-jpa-query-methods#jpa.modifying-queries`).

Setting the `clearAutomatically` attribute of `@Modifying` to `true` clears the `EntityManager` automatically (`spring-data-jpa-query-methods#jpa.modifying-queries`).

The `@Modifying` annotation is only relevant in combination with the `@Query` annotation (`spring-data-jpa-query-methods#jpa.modifying-queries`).

The `@EntityGraph` annotation lets a query method reference a `@NamedEntityGraph` definition, and its `type` attribute selects Fetch or Load (`spring-data-jpa-query-methods#jpa.entity-graph`).

An ad hoc entity graph is defined through the `attributePaths` of `@EntityGraph`, without a `@NamedEntityGraph` on the domain type (`spring-data-jpa-query-methods#jpa.entity-graph`).

The easiest way to limit the result of a query to some attributes is an interface that exposes accessor methods for the properties to be read (`spring-data-jpa-projections#projections.interfaces`).

For an interface-based projection, the query execution engine creates proxy instances of that interface at runtime for each element returned and forwards calls to the exposed methods to the target object (`spring-data-jpa-projections#projections.interfaces`).

Projections can be used recursively (`spring-data-jpa-projections#projections.interfaces`).

Class-based projections can be used in exactly the same way as projection interfaces, except that no proxying happens and no nested projections can be applied (`spring-data-jpa-projections#projections.dtos`).

If the store optimizes the query execution by limiting the fields to be loaded, the fields to be loaded are determined from the parameter names of the constructor that is exposed (`spring-data-jpa-projections#projections.dtos`).

A projection interface whose accessor methods all match properties of the target aggregate is a closed projection, and Spring Data can optimize the query execution for it (`spring-data-jpa-projections#projections.interfaces.closed`).

A projection interface using `@Value` is an open projection, and Spring Data cannot apply query execution optimizations to it (`spring-data-jpa-projections#projections.interfaces.open`).

A query method with a `Class<T>` parameter lets the caller select the projection type at invocation time (`spring-data-jpa-projections#projection.dynamic`).

Spring Data JPA Specification provides a small, focused API to express predicates over entities and reuse them across repositories (`spring-data-jpa-specifications#page-title`).

To support specifications, a repository interface extends `JpaSpecificationExecutor` (`spring-data-jpa-specifications#page-title`).

`PredicateSpecification` is a query-type-agnostic interface introduced with Spring Data JPA 4.0 (`spring-data-jpa-specifications#page-title`).

The `Specification` interface is tied to a particular query type (select, update, delete) as per Criteria API restrictions (`spring-data-jpa-specifications#specification-interfaces`).

## Entity states and the persistence context
<!-- bullets: 5.7.b -->

A persistence context is the context in which the Hibernate `Session` and the `EntityManager` deal with persistent data. An entity is new, managed, detached or removed in relation to it, and the lifetime of the context decides when managed entities become detached.

Both the `org.hibernate.Session` API and the `jakarta.persistence.EntityManager` API represent a context for dealing with persistent data (`hibernate-user-guide#pc`).

This concept is called a persistence context (`hibernate-user-guide#pc`).

Persistent data has a state in relation to both a persistence context and the underlying database (`hibernate-user-guide#pc`).

A new entity instance has no persistent identity, and is not yet associated with a persistence context (`jakarta-persistence-spec#a1929`).

A managed entity instance is an instance with a persistent identity that is currently associated with a persistence context (`jakarta-persistence-spec#a1929`).

A detached entity instance is an instance with a persistent identity that is not, or no longer, associated with a persistence context (`jakarta-persistence-spec#a1929`).

A removed entity instance is an instance with a persistent identity, associated with a persistence context, that will be removed from the database upon transaction commit (`jakarta-persistence-spec#a1929`).

An entity instance created with the `new` operator is in the new state, and it becomes persistent when it is associated with an `EntityManager` or a `Session` (`hibernate-user-guide#pc-persist`).

Closing the persistence context detaches all data that was associated with it, clearing the persistence context has the same effect, and evicting a particular entity detaches that entity (`hibernate-user-guide#pc-detach`).

Detached data can still be manipulated, but the persistence context no longer automatically knows about the modifications, and the application needs to intervene to make the changes persistent again (`hibernate-user-guide#pc-detach`).

Merging takes an incoming detached entity instance and copies its data over onto a new managed instance (`hibernate-user-guide#pc-merge`).

The entity instance passed to `remove` on `jakarta.persistence.EntityManager` must be in the managed state (`hibernate-user-guide#pc-remove`).

By default, the lifetime of the persistence context of a container-managed entity manager corresponds to the scope of a transaction (`jakarta-persistence-spec#a2027`).

An extended persistence context exists from the time the `EntityManager` instance is created until it is closed (`jakarta-persistence-spec#a2027`).

The transaction-scoped persistence context ends when the associated JTA transaction commits or rolls back, and all entities that were managed by the `EntityManager` become detached (`jakarta-persistence-spec#a11805`).

If the entity manager is invoked outside the scope of a transaction, any entities loaded from the database immediately become detached at the end of the method call (`jakarta-persistence-spec#a11805`).

## Dirty checking and flushing
<!-- bullets: 5.7.b -->

An entity changed inside a persistence context is not written at that moment. The context queues the change and writes it at a flush, so the application does not call a save method for each change. The flush mode decides when a flush happens, and the order of the statements is the persistence context's, not the application's.

Entities in the managed state may be manipulated by the application, and any changes are automatically detected and persisted when the persistence context is flushed (`hibernate-user-guide#pc-managed-state`).

By default, when you modify an entity, Hibernate sets all columns but the identifier during the update (`hibernate-user-guide#pc-managed-state`).

Flushing is the process of synchronizing the state of the persistence context with the underlying database (`hibernate-user-guide#flushing`).

The persistence context acts as a transactional write-behind cache, queuing any entity state change (`hibernate-user-guide#flushing`).

The dirty checking mechanism is responsible for determining if a managed entity has been modified since it was first loaded (`hibernate-user-guide#flushing-order`).

Jakarta Persistence defines only two flushing strategies, `AUTO` and `COMMIT`, while Hibernate has a much broader spectrum of flush types (`hibernate-user-guide#flushing`).

By default, Hibernate uses the `AUTO` flush mode, which triggers a flush prior to committing a `Transaction` (`hibernate-user-guide#flushing-auto`).

The `AUTO` flush mode also triggers a flush before executing any native SQL query that has no registered synchronization (`hibernate-user-guide#flushing-auto`).

The `AUTO` flush mode triggers a flush prior to executing a JPQL or HQL query that overlaps with the queued entity actions (`hibernate-user-guide#flushing-auto`).

:::esquema{kind=tabla title="Hibernate flush modes"}
| Mode | When the Session flushes | Source |
|---|---|---|
| `ALWAYS` | Before every query | `hibernate-user-guide#flushing` |
| `AUTO` | Only if necessary, and it is the default | `hibernate-user-guide#flushing` |
| `COMMIT` | It tries to delay the flush until the current Transaction is committed, although it might flush prematurely too | `hibernate-user-guide#flushing` |
| `MANUAL` | Only when the application calls `Session.flush()` explicitly | `hibernate-user-guide#flushing` |
:::

If there is no transaction active, or if the persistence context has not been joined to the current transaction, the persistence provider must not flush to the database (`jakarta-persistence-spec#a1955`).

Hibernate does not execute the SQL statements in the order of their associated entity state operations (`hibernate-user-guide#flushing-order`).

Even if you remove the first entity and then persist a new one, Hibernate is going to execute the `DELETE` statement after the `INSERT` (`hibernate-user-guide#flushing-order`).

The order in which SQL statements are executed is given by the `ActionQueue` and not by the order in which entity state operations have been previously defined (`hibernate-user-guide#flushing-order`).

The `ActionQueue` executes `OrphanRemovalAction` first, runs `EntityInsertAction` or `EntityIdentityInsertAction` before `EntityUpdateAction`, and executes `EntityDeleteAction` last (`hibernate-user-guide#flushing-order`).

## Saving entities and repository transactions
<!-- bullets: 5.7.b -->

A repository method has to know whether to insert or update. Spring Data JPA works that out by inspecting the entity, and it can be told otherwise. Repository methods also run in transactions, and the defaults differ between the inherited CRUD methods and the declared query methods.

If an entity has a version property of non-primitive type, Spring Data JPA considers the entity new if the value of that property is `null` (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

Without a version property, Spring Data JPA inspects the identifier property of the given entity (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

JPA considers 0 (zero) as the first inserted version of an entity, so a primitive version property cannot be used to determine whether an entity is new (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

Inspecting the identifier is not an option for entities that use manually assigned identifiers and no version attribute, because the identifier is always non-null for them (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

If an entity implements `Persistable`, Spring Data JPA delegates the new detection to the `isNew(…)` method of the entity (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

The `Persistable.isNew()` flag tells Spring Data repositories whether to call `EntityManager.persist()` or `merge()` (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

By default, methods inherited from `CrudRepository` inherit the transactional configuration from `SimpleJpaRepository` (`spring-data-jpa-transactions#page-title`).

For read operations, the transaction configuration `readOnly` flag is set to `true`, and all other methods are configured with a plain `@Transactional` (`spring-data-jpa-transactions#page-title`).

Declared query methods, including default methods, do not get any transaction configuration applied by default (`spring-data-jpa-transactions#transactional-query-methods`).

The `readOnly` flag does not act as a check that a manipulating query is not triggered (`spring-data-jpa-transactions#transactional-query-methods`).

When used with Hibernate, the flush mode is set to `MANUAL` when a transaction is configured as `readOnly`, which causes Hibernate to skip dirty checks (`spring-data-jpa-transactions#transactional-query-methods`).

## Open EntityManager in View
<!-- bullets: 5.7.b -->

In a web application, Spring Boot applies the Open EntityManager in View pattern by default, so that lazy loading works in web views. The setting can be turned off.

If you are running a web application, Spring Boot by default registers `OpenEntityManagerInViewInterceptor` to apply the “Open EntityManager in View” pattern, to allow for lazy loading in web views (`spring-boot-data-sql#data.sql.jpa-and-spring-data.open-entity-manager-in-view`).

To turn off this behaviour, set `spring.jpa.open-in-view` to `false` in your `application.properties` (`spring-boot-data-sql#data.sql.jpa-and-spring-data.open-entity-manager-in-view`).

With the `SELECT` fetch strategy, a lazy fetch delays the second select until the data is needed (`hibernate-user-guide#fetching-basics`).

## Auditing
<!-- bullets: 5.7.c -->

Auditing records who created or changed an entity and when. The entity carries the metadata, and the application supplies the current user and switches auditing on.

Spring Data provides `@CreatedBy` and `@LastModifiedBy` to capture the user who created or modified the entity, and `@CreatedDate` and `@LastModifiedDate` to capture when the change happened (`spring-data-jpa-auditing#auditing.annotations`).

Auditing metadata can be defined either with annotations or by implementing an interface (`spring-data-jpa-auditing#auditing.basics`).

The annotations that capture when changes are made can be used on properties of JDK8 date and time types, `long`, `Long`, and legacy Java `Date` and `Calendar` (`spring-data-jpa-auditing#auditing.annotations`).

By default, the `DateTimeProvider` that gives the time is a `CurrentDateTimeProvider` (`spring-data-jpa-auditing#auditing.annotations`).

When `@CreatedBy` or `@LastModifiedBy` is used, the application implements the `AuditorAware<T>` interface to tell the infrastructure who the current user is (`spring-data-jpa-auditing#auditing.auditor-aware`).

Spring Data JPA ships with an entity listener, `AuditingEntityListener`, that triggers the capturing of auditing information (`spring-data-jpa-auditing#jpa.auditing.configuration`).

The `AuditingEntityListener` is registered for all entities in the `orm.xml` file, or enabled for a single entity with the `@EntityListeners` annotation (`spring-data-jpa-auditing#jpa.auditing.configuration`).

The auditing feature requires `spring-aspects.jar` to be on the classpath (`spring-data-jpa-auditing#jpa.auditing.configuration`).

If you expose a bean of type `AuditorAware` to the `ApplicationContext`, the auditing infrastructure automatically picks it up and uses it to determine the current user to be set on domain types (`spring-data-jpa-auditing#jpa.auditing.configuration`).

You can enable auditing by annotating a configuration class with the `@EnableJpaAuditing` annotation (`spring-data-jpa-auditing#jpa.auditing.configuration`).

## Optimistic locking
<!-- bullets: 5.7.c -->

Optimistic locking detects conflicting updates to the same entity. The persistence provider keeps a version for the entity and updates it on each write, and a mismatch between versions raises an exception.

A query method annotated with `@Lock` is equipped with the `LockModeType` given to the annotation, for example `READ` (`spring-data-jpa-locking#page-title`).

Hibernate provides two mechanisms for storing versioning information, a dedicated version number or a timestamp (`hibernate-user-guide#locking-optimistic`).

The version number mechanism for optimistic locking is provided through a `@Version` annotation (`hibernate-user-guide#locking-optimistic-version-number`).

The entity manager uses the version property to detect conflicting updates, and prevent the loss of updates that would otherwise be overwritten by a last-commit-wins strategy (`hibernate-user-guide#locking-optimistic-version-number`).

Hibernate detects any instance with a null version or timestamp as transient, regardless of other unsaved-value strategies (`hibernate-user-guide#locking-optimistic`).

Your application is forbidden from altering the version number set by Hibernate (`hibernate-user-guide#locking-optimistic-version-number`).

The entity version must be updated by the persistence provider each time the state of an entity instance is written to the database (`jakarta-persistence-spec#a2059`).

If the versions in memory and in the database do not match, the persistence provider must throw an `OptimisticLockException` (`jakarta-persistence-spec#a2059`).

The timing of the version check for a detached entity instance that is merged is provider-dependent (`jakarta-persistence-spec#a2059`).

If an update or merge operation involves entities without versions, the absence of a version does not impede completion of the operation (`jakarta-persistence-spec#a2059`).

The version must be of type `int`, `Integer`, `short`, `Short`, `long`, `Long`, `java.time.LocalDateTime`, `java.time.Instant` or `java.sql.Timestamp`, and an entity class should have at most one version (`jakarta-persistence-spec#a2060`).

By default, an HQL `UPDATE` statement does not affect the version or timestamp property values of the affected entities, and the `VERSIONED` keyword after `UPDATE` forces Hibernate to reset them (`hibernate-user-guide#batch-bulk-hql-update-delete`).

## Batching and bulk statements
<!-- bullets: 5.7.c -->

Without batching, every insert statement needs a database round trip, and a persistence context that holds every inserted entity grows with the work. Batching groups statements, and HQL and JPQL support bulk `UPDATE` and `DELETE` statements.

Because DML statements are grouped together at a flush, Hibernate can apply batching transparently (`hibernate-user-guide#flushing`).

JDBC offers support for batching together SQL statements that can be represented as a single `PreparedStatement` (`hibernate-user-guide#batch-jdbcbatch`).

`hibernate.jdbc.batch_size` controls the maximum number of statements Hibernate will batch together before asking the driver to execute the batch (`hibernate-user-guide#batch-jdbcbatch`).

A `hibernate.jdbc.batch_size` of zero or a negative number disables batching (`hibernate-user-guide#batch-jdbcbatch`).

JDBC batching is not enabled by default, so every insert statement requires a database round trip (`hibernate-user-guide#batch-session-batch`).

Hibernate disables insert batching at the JDBC level transparently if you use an identity identifier generator (`hibernate-user-guide#batch-session-batch`).

`hibernate.order_updates` forces Hibernate to order SQL updates by the entity type and the primary key value of the items being updated (`hibernate-user-guide#batch-jdbcbatch`).

`hibernate.order_inserts` forces Hibernate to order inserts to allow for more batching to be used (`hibernate-user-guide#batch-jdbcbatch`).

Since version 5.2, Hibernate allows overriding the global JDBC batch size on a per `Session` basis (`hibernate-user-guide#batch-jdbcbatch`).

Hibernate caches all newly inserted instances in the session-level cache, so a loop that persists 100 000 entities in one transaction leaves 100 000 entities managed by the persistence context (`hibernate-user-guide#batch-session-batch`).

Both the Hibernate Query Language and JPQL support bulk `UPDATE` and `DELETE` (`hibernate-user-guide#batch-bulk-hql-update-delete`).

Joins, either implicit or explicit, are prohibited in a bulk HQL query (`hibernate-user-guide#batch-bulk-hql-update-delete`).

## Key points

- `Repository` is the central marker interface of Spring Data, and `ListCrudRepository` returns `List` where `CrudRepository` returns `Iterable`.
- Query method names are parsed into a subject and a predicate, and the first `By` starts the predicate.
- `CREATE_IF_NOT_FOUND` is the default lookup strategy, and `USE_DECLARED_QUERY` fails at bootstrap time when no declared query is found.
- A query annotated with `@Query` takes precedence over `@NamedQuery` and `orm.xml` named queries.
- `@Modifying` does not clear the `EntityManager` unless `clearAutomatically` is `true`.
- Class-based projections need no proxying and cannot be nested, while interface-based projections are proxied at runtime, and a projection using `@Value` is open.
- An entity is new, managed, detached or removed in relation to a persistence context.
- Closing, clearing or evicting detaches entities, and merging copies a detached instance onto a new managed one.
- Hibernate executes SQL statements in the order given by the `ActionQueue`, so a `DELETE` follows an `INSERT` even if the entity was removed first.
- `AUTO` is the default flush mode, `MANUAL` flushes only on an explicit `flush()`, and a `readOnly` transaction sets `MANUAL` with Hibernate.
- In a web application, Spring Boot registers `OpenEntityManagerInViewInterceptor` by default, and `spring.jpa.open-in-view` set to `false` turns it off.
- `@Version` lets the entity manager detect conflicting updates, and the application must not alter the version number.
- `hibernate.jdbc.batch_size` sets the maximum batch size, and zero or a negative number disables batching.

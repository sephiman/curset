# Consensus and coordination

## Partial failures, asynchronous networks and process pauses
<!-- bullets: 8.5.a -->

The Paxos paper uses the customary asynchronous, non-Byzantine model (`paper-lamport-paxos-simple#p4`).

In that model agents operate at arbitrary speed, may fail by stopping, and may restart (`paper-lamport-paxos-simple#p5`).

Messages can take arbitrarily long to be delivered, can be duplicated, and can be lost, but they are not corrupted (`paper-lamport-paxos-simple#p5`).

The SWIM paper states that a process that is losing messages is indistinguishable from one that has failed (`paper-swim#p1`).

A network partition divides an etcd cluster into two parts, one with a member majority and the other with a member minority (`etcd-failures#network-partition`).

In etcd the failure detection model is timeout based, so electing a new leader takes about an election timeout (`etcd-failures#leader-failure`).

Heartbeating to all members makes the message load grow quadratically with the group size (`paper-swim#p2`).

SWIM reduces false failure detections by letting group members suspect a process before declaring it as failed (`paper-swim#p1`).

SWIM guarantees a deterministic time bound to detect failures (`paper-swim#p1`).

The Raft dissertation describes a leader lease that assumes a bound on clock drift across servers (`paper-raft-dissertation#p92`).

Maintaining that bound might be hard because of scheduling and garbage collection pauses, virtual machine migrations, or clock rate adjustments for time synchronization (`paper-raft-dissertation#p92`).

If the clock assumptions are violated, the system could return arbitrarily stale information (`paper-raft-dissertation#p92`).

## Raft
<!-- bullets: 8.5.b -->

Raft first elects a server as leader, then concentrates all decision-making onto the leader (`paper-raft-dissertation#p4`).

Raft elects a leader using voting and randomized timeouts (`paper-raft-dissertation#p4`).

Data only flows outwards from the leader to other servers (`paper-raft-dissertation#p4`).

At any given time each Raft server is in one of three states: leader, follower, or candidate (`paper-raft-dissertation#p32`).

Followers are passive: they issue no requests on their own but simply respond to requests from leaders and candidates (`paper-raft-dissertation#p32`).

A Raft cluster of five servers tolerates two failures (`paper-raft-dissertation#p32`).

Raft divides time into terms of arbitrary length, numbered with consecutive integers (`paper-raft-dissertation#p32`).

Terms act as a logical clock in Raft and allow servers to detect obsolete information such as stale leaders (`paper-raft-dissertation#p33`).

If a server receives a request with a stale term number, it rejects the request (`paper-raft-dissertation#p33`).

Leaders send periodic heartbeats, which are AppendEntries RPCs that carry no log entries, to all followers to maintain their authority (`paper-raft-dissertation#p34`).

A follower that receives no communication over the election timeout assumes there is no viable leader and begins an election (`paper-raft-dissertation#p34`).

A candidate wins an election if it receives votes from a majority of the servers in the full cluster for the same term (`paper-raft-dissertation#p34`).

Each server votes for at most one candidate in a given term (`paper-raft-dissertation#p34`).

Election timeouts are chosen randomly from a fixed interval, for example 150 to 300 ms (`paper-raft-dissertation#p35`).

The leader appends a client command to its log as a new entry, then issues AppendEntries RPCs in parallel to replicate it (`paper-raft-dissertation#p35`).

An entry is considered committed if it is safe for that entry to be applied to state machines (`paper-raft-dissertation#p36`).

A log entry is committed once the leader that created it has replicated it on a majority of the servers (`paper-raft-dissertation#p36`).

The broadcast time should be an order of magnitude less than the election timeout, and the election timeout a few orders of magnitude less than the mean time between failures (`paper-raft-dissertation#p46`).

:::esquema{kind=tabla title="Three Raft safety properties"}
| Property | Statement | Source |
|---|---|---|
| Election Safety | At most one leader can be elected in a given term | `paper-raft-dissertation#p32` |
| Leader Append-Only | A leader never overwrites or deletes entries in its log; it only appends new entries | `paper-raft-dissertation#p32` |
| Log Matching | If two logs contain an entry with the same index and term, then the logs are identical in all entries up through the given index | `paper-raft-dissertation#p32` |
:::

Switching directly from one configuration to another can be unsafe because different servers will switch at different times (`paper-raft-dissertation#p52`).

In every single-server membership change, an overlap between any majority of the old cluster and any majority of the new cluster is preserved (`paper-raft-dissertation#p52`).

To ensure safety across arbitrary changes, the cluster first switches to a transitional configuration called joint consensus and, once that is committed, to the new configuration (`paper-raft-dissertation#p62`).

Joint consensus requires separate majorities from both the old and the new configuration for elections and entry commitment (`paper-raft-dissertation#p62`).

A new server first joins as a non-voting member, so that its catching up does not create availability gaps (`paper-raft-dissertation#p55`).

The dissertation changes membership by adding or removing one server at a time (`paper-raft-dissertation#p4`).

Each Raft server takes snapshots independently, covering just the committed entries in its log (`paper-raft-dissertation#p69`).

Raft stores the index and term of the last entry included in a snapshot and then discards the log prefix up through that index (`paper-raft-dissertation#p69`).

The leader sends a slow follower its latest snapshot with the InstallSnapshot RPC (`paper-raft-dissertation#p70`).

In Paxos, any two majorities have at least one acceptor in common (`paper-lamport-paxos-simple#p5`).

In Paxos a proposer asks acceptors for a promise never again to accept a proposal numbered less than n (`paper-lamport-paxos-simple#p7`).

## Quorums, split brain and leader election in practice
<!-- bullets: 8.5.c -->

By default ZooKeeper uses majority quorums, so every vote in its protocols requires a majority (`zk-internals#sc_quorum`).

The ZooKeeper leader can only commit once it receives an acknowledgement from a quorum of servers (`zk-internals#sc_quorum`).

ZooKeeper can be configured to use majority quorums, weights, or a hierarchy of groups (`zk-internals#sc_quorum`).

With 9 servers split into 3 groups and a weight of 1 each, hierarchical quorums can have size 4 (`zk-internals#sc_quorum`).

ZooKeeper leader activation requires that the leader has seen the highest zxid of all the followers (`zk-internals#sc_leaderElection`).

A new ZooKeeper leader will not accept new proposals until the NEW_LEADER proposal has been committed (`zk-internals#sc_leaderElection`).

In the ZooKeeper recipe the process that created the znode with the smallest appended sequence number is the leader (`zk-recipes#sc_leaderElection`).

To avoid the herd effect it is sufficient to watch the next znode down in the sequence of znodes (`zk-recipes#sc_leaderElection`).

There is no split-brain in etcd because each membership change is approved by the current majority of members (`etcd-failures#network-partition`).

The majority side of an etcd partition becomes the available cluster and the minority side is unavailable (`etcd-failures#network-partition`).

A leader on the minority side of a partition steps down and the majority side elects a new leader (`etcd-failures#network-partition`).

During an etcd leader election the cluster cannot process any writes (`etcd-failures#leader-failure`).

No committed write is ever lost in an etcd leader change (`etcd-failures#leader-failure`).

When the majority of etcd members fail, the cluster fails and cannot accept more writes (`etcd-failures#majority-failure`).

Replacing an etcd node starts by removing the member and then adding its replacement (`etcd-faq#should-i-add-a-member-before-removing-an-unhealthy-member`).

Adding a member to a 3-member etcd cluster raises the quorum to 3 because 3 votes are a majority of 4 members (`etcd-faq#should-i-add-a-member-before-removing-an-unhealthy-member`).

A leader that loses connectivity from the quorum reverts back to follower (`etcd-design-learner#21-leader-isolation`).

A Redis deployment with just two Sentinels on two boxes is broken, because losing the master's box also stops one Sentinel and the other cannot authorize a failover (`redis-sentinel#example-1-just-two-sentinels-dont-do-this`).

Redis recommends deploying at least three Sentinels in three different boxes (`redis-sentinel#example-1-just-two-sentinels-dont-do-this`).

A majority of the KRaft controllers must be alive to maintain availability (`kafka-operations-kraft#controllers`).

For the KRaft controller cluster to withstand N concurrent failures it must include 2N + 1 controllers (`kafka-operations-kraft#deploying-considerations`).

Combined broker and controller mode can be used in development but should be avoided in critical deployments (`kafka-operations-kraft#deploying-considerations`).

With a dynamic KRaft quorum controller.quorum.voters must not be set and controller.quorum.bootstrap.servers is set instead (`kafka-operations-kraft#static-versus-dynamic-kraft-quorums`).

| KRaft, 3 controllers | 1 | `kafka-operations-kraft#controllers` |

## Distributed locks, leases and fencing tokens
<!-- bullets: 8.5.d -->

etcd provides a lease mechanism whose primary use case is implementing distributed coordination mechanisms like distributed locks (`etcd-api-guarantees#lease-apis`).

An etcd lease is created with the grant API, attached to a key with the put API, revoked with the revoke API, and expired by the wall clock time to live (TTL) (`etcd-api-guarantees#lease-apis`).

An etcd operation that modifies the key value store is assigned a single increasing revision (`etcd-api-guarantees#revision`).

The etcd revision can be used as a logical clock for the key value store (`etcd-api-guarantees#revision`).

A new etcd leader extends timeouts automatically for all leases, so a lease does not expire before its granted TTL even if the old leader granted it (`etcd-failures#leader-failure`).

The Redis lock design has mutual exclusion as its safety property: at any given moment, only one client can hold a lock (`redis-distributed-locks#safety-and-liveness-guarantees`).

Its first liveness property is deadlock freedom: eventually it is always possible to acquire a lock, even if the client that locked a resource crashes or gets partitioned (`redis-distributed-locks#safety-and-liveness-guarantees`).

The ZooKeeper shared lock recipe calls getChildren without setting the watch flag, which avoids the herd effect (`zk-recipes#Shared+Locks`).

:::judgement{source="Martin Kleppmann, How to do distributed locking" ref="kleppmann-distributed-locking#making-the-lock-safe-with-fencing"}
According to Martin Kleppmann, the fix for a client that wakes up after a long pause is to include a fencing token with every write request to the storage service. He defines a fencing token as a number that increases every time a client acquires the lock. The storage server remembers the highest token it has processed and rejects any write whose token has gone backwards. He adds that a ZooKeeper user can take the `zxid` or the znode version number as the fencing token.
:::

:::judgement{source="Martin Kleppmann, How to do distributed locking" ref="kleppmann-distributed-locking#what-are-you-using-that-lock-for"}
According to Martin Kleppmann, a lock is wanted for one of two reasons, efficiency or correctness. If the lock fails under the efficiency reason, two nodes do the same work twice at a minor cost. If it fails under the correctness reason, two nodes work on the same data and the result can be a corrupted file or data loss.
:::

## Two-phase commit
<!-- bullets: 8.5.e -->

A two-phase commit protocol is an algorithm that lets all clients in a distributed system agree either to commit a transaction or abort (`zk-recipes#sc_recipes_twoPhasedCommit`).

In the ZooKeeper recipe a coordinator creates a transaction node and one child node per participating site (`zk-recipes#sc_recipes_twoPhasedCommit`).

Each site votes commit or abort by writing to its own node, and a node can decide abort earlier if some site votes abort (`zk-recipes#sc_recipes_twoPhasedCommit`).

The message complexity of that ZooKeeper recipe is O(n²) (`zk-recipes#sc_recipes_twoPhasedCommit`).

Failures of sites cannot be detected through ephemeral nodes in that recipe, because a site would have to create the node to be detected (`zk-recipes#sc_recipes_twoPhasedCommit`).

PostgreSQL does not offer synchronous multimaster replication, but its two-phase commit, PREPARE TRANSACTION and COMMIT PREPARED, can implement it in application code or middleware (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

:::judgement{source="Martin Kleppmann, Concurrent and Distributed Systems lecture notes, University of Cambridge" ref="cam-concdissys-notes#p68"}
According to Martin Kleppmann's Cambridge lecture notes, the coordinator sends a prepare message to each replica, and each replica replies whether it can commit. The replicas do not commit yet, but they must write all updates to disk and check integrity constraints before replying ok, while holding the locks. If all nodes reply ok the coordinator decides to commit, and if any node wants to abort or fails to reply within a timeout it decides to abort. The notes name the coordinator as the single point of failure: transactions that have prepared but not yet committed or aborted when it crashes are in doubt, and they must wait until the coordinator recovers because they cannot decide unilaterally.
:::

## Gossip protocols and cluster membership
<!-- bullets: 8.5.f -->

SWIM separates the failure detection and membership update dissemination functionalities of the membership protocol (`paper-swim#p1`).

SWIM propagates information about membership changes by piggybacking it on ping messages and acknowledgments (`paper-swim#p1`).

This results in an infection style, also called epidemic or gossip style, of dissemination (`paper-swim#p1`).

The expected time to first detection of each process failure and the expected message load per member do not vary with group size in SWIM (`paper-swim#p1`).

In Dynamo, decentralized failure detection protocols use a simple gossip-style protocol that lets each node learn about the arrival or departure of other nodes (`paper-dynamo#p9`).

## Key points

- Asynchronous networks can delay, duplicate and lose messages, and a process that is losing messages is indistinguishable from one that has failed.
- A leader lease assumes a bound on clock drift, and violating it could return arbitrarily stale information.
- Raft elects a leader with voting and randomized election timeouts; a candidate needs votes from a majority of the full cluster for the same term.
- Raft changes membership through joint consensus, which needs separate majorities from the old and the new configuration.
- A Raft snapshot records the last included index, the index of the last entry the snapshot replaces.
- A partition leaves the majority side of an etcd cluster available and the minority side unavailable; etcd has no split-brain.
- A KRaft controller cluster needs 2N + 1 controllers to withstand N concurrent failures.
- An etcd lease expires by its TTL, and a new leader extends the timeouts of all leases.
- A two-phase commit lets all participants agree to commit or abort; the ZooKeeper recipe has O(n²) message complexity.
- SWIM separates failure detection from membership update dissemination and spreads updates by piggybacking them on ping messages and acknowledgments.

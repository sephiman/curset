# Operating and testing Spring Boot applications

## Actuator, health, metrics and observability
<!-- bullets: 5.8.a -->

By default, only the `health` endpoint is exposed over HTTP and JMX (`spring-boot-actuator-endpoints#actuator.endpoints.exposing`).

The `include` property lists the IDs of the endpoints that are exposed (`spring-boot-actuator-endpoints#actuator.endpoints.exposing`).

The `exclude` property takes precedence over the `include` property (`spring-boot-actuator-endpoints#actuator.endpoints.exposing`).

`*` can be used to select all endpoints (`spring-boot-actuator-endpoints#actuator.endpoints.exposing`).

The default value of `management.endpoint.health.show-details` is `never` (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

A `HealthContributor` can be either a `HealthIndicator` or a `CompositeHealthContributor` (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

A `HealthIndicator` provides actual health information, including a `Status` (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

By default, the final system health is derived by a `StatusAggregator`, which sorts the statuses from each `HealthIndicator` based on an ordered list of statuses (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

If no `HealthIndicator` returns a status that is known to the `StatusAggregator`, an `UNKNOWN` status is used (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

To create a health indicator group, you can use the `management.endpoint.health.group.<name>` property and specify a list of health indicator IDs to include or exclude (`spring-boot-actuator-endpoints#actuator.endpoints.health.groups`).

By default, startup will fail if a health group includes or excludes a health indicator that does not exist (`spring-boot-actuator-endpoints#actuator.endpoints.health.groups`).

By default, groups inherit the same `StatusAggregator` and `HttpCodeStatusMapper` settings as the system health (`spring-boot-actuator-endpoints#actuator.endpoints.health.groups`).

If Spring Security is on the classpath and no other `SecurityFilterChain` bean is present, all actuators other than `/health` are secured by Spring Boot auto-configuration (`spring-boot-actuator-endpoints#actuator.endpoints.security`).

If you define a custom `SecurityFilterChain` bean, Spring Boot auto-configuration backs off and lets you fully control the actuator access rules (`spring-boot-actuator-endpoints#actuator.endpoints.security`).

You can register any number of `MeterRegistryCustomizer` beans to further configure the registry, such as applying common tags, before any meters are registered with the registry (`spring-boot-actuator-metrics#actuator.metrics.getting-started`).

Observability is the ability to observe the internal state of a running system from the outside (`spring-boot-actuator-observability#page-title`).

Observability consists of the three pillars: logging, metrics and traces (`spring-boot-actuator-observability#page-title`).

For metrics and traces, Spring Boot uses Micrometer Observation (`spring-boot-actuator-observability#page-title`).

Low cardinality tags will be added to metrics and traces, while high cardinality tags will only be added to traces (`spring-boot-actuator-observability#page-title`).

## Start-up events, availability and graceful shutdown
<!-- bullets: 5.8.b -->

In addition to the usual Spring Framework events, such as `ContextRefreshedEvent`, a `SpringApplication` sends some additional application events (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

Some events are triggered before the `ApplicationContext` is created, so you cannot register a listener on those as a `@Bean` (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationStartingEvent` is sent at the start of a run but before any processing, except for the registration of listeners and initializers (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationEnvironmentPreparedEvent` is sent when the `Environment` to be used in the context is known but before the context is created (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationPreparedEvent` is sent just before the refresh is started but after bean definitions have been loaded (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationStartedEvent` is sent after the context has been refreshed but before any application and command-line runners have been called (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationReadyEvent` is sent after any application and command-line runners have been called (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationFailedEvent` is sent if there is an exception on startup (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `AvailabilityChangeEvent` is sent right after `ApplicationReadyEvent` with `ReadinessState.ACCEPTING_TRAFFIC` to indicate that the application is ready to service requests (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

Event listeners should not run potentially lengthy tasks as they execute in the same thread by default (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

Spring Boot includes out-of-the box support for the commonly used “liveness” and “readiness” availability states (`spring-boot-features-spring-application#features.spring-application.application-availability`).

If you are using Spring Boot’s “actuator” support then the liveness and readiness states are exposed as health endpoint groups (`spring-boot-features-spring-application#features.spring-application.application-availability`).

Each `SpringApplication` registers a shutdown hook with the JVM to ensure that the `ApplicationContext` closes gracefully on exit (`spring-boot-features-spring-application#features.spring-application.application-exit`).

If there is more than one `ExitCodeGenerator`, the first non-zero exit code that is generated is used (`spring-boot-features-spring-application#features.spring-application.application-exit`).

Graceful shutdown is enabled by default with all three embedded web servers (Jetty, Reactor Netty, and Tomcat) and with both reactive and servlet-based web applications (`spring-boot-web-graceful-shutdown#page-title`).

Graceful shutdown occurs as part of closing the application context and is performed in the earliest phase of stopping `SmartLifecycle` beans (`spring-boot-web-graceful-shutdown#page-title`).

Shutdown in your IDE may be immediate rather than graceful if it does not send a proper SIGTERM signal (`spring-boot-web-graceful-shutdown#page-title`).

Jetty, Reactor Netty, and Tomcat will stop accepting new requests at the network layer (`spring-boot-web-graceful-shutdown#web.graceful-shutdown.rejecting-requests-during-the-grace-period`).

## Test slices, the test context cache and Testcontainers
<!-- bullets: 5.8.c -->

Each test slice restricts component scan to appropriate components and loads a very restricted set of auto-configuration classes (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-tests`).

You can use the `@DataJpaTest` annotation from the `spring-boot-data-jpa-test` module to test Data JPA applications (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

By default, `@DataJpaTest` scans for `@Entity` classes and configures Spring Data JPA repositories (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

If an embedded database is available on the classpath, `@DataJpaTest` configures one as well (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

Regular `@Component` and `@ConfigurationProperties` beans are not scanned when the `@DataJpaTest` annotation is used (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

By default, data JPA tests are transactional and roll back at the end of each test (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

`@WebMvcTest` is often limited to a single controller and is used in combination with `@MockitoBean` to provide mock implementations for required collaborators (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.spring-mvc-tests`).

By default, `@SpringBootTest` does not start the server but instead sets up a mock environment for testing web endpoints (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.with-mock-environment`).

With Spring MVC, we can query our web endpoints using `MockMvc` (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.with-mock-environment`).

Once the TestContext framework loads an `ApplicationContext` for a test, that context is cached and reused for all subsequent tests that declare the same unique context configuration within the same test suite (`spring-fw-testing-ctx-caching#page-title`).

The context cache key includes `@DynamicPropertySource` methods and bean overrides such as `@TestBean`, `@MockitoBean` and `@MockitoSpyBean` (`spring-fw-testing-ctx-caching#page-title`).

The Spring TestContext framework stores application contexts in a static cache (`spring-fw-testing-ctx-caching#page-title`).

If tests run in separate processes, the static cache is cleared between each test execution, which effectively disables the caching mechanism (`spring-fw-testing-ctx-caching#page-title`).

The size of the context cache is bounded with a default maximum size of 32 (`spring-fw-testing-ctx-caching#page-title`).

Whenever the maximum size is reached, a least recently used (LRU) eviction policy is used to evict and close stale contexts (`spring-fw-testing-ctx-caching#page-title`).

`@DirtiesContext` instructs Spring to remove the context from the cache and rebuild the application context before running the next test that requires the same application context (`spring-fw-testing-ctx-caching#page-title`).

A service connection is a connection to any remote service (`spring-boot-testing-testcontainers#testing.testcontainers.service-connections`).

When a service connection is used, the connection details take precedence over any connection-related configuration properties (`spring-boot-testing-testcontainers#testing.testcontainers.service-connections`).

You need to add the `spring-boot-testcontainers` module as a test dependency in order to use service connections with Testcontainers (`spring-boot-testing-testcontainers#testing.testcontainers.service-connections`).

Container beans are created and started before all other beans (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Container beans are stopped after the destruction of all other beans (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Container beans are created and started once per application context managed by Spring’s TestContext Framework (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Container beans are stopped as part of the TestContext Framework’s standard application context shutdown process (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Having containers managed by Testcontainers instead of as Spring beans provides no guarantee of the order in which beans and containers will shutdown (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

## Key points

- By default, only the `health` endpoint is exposed over HTTP and JMX, and `exclude` takes precedence over `include`.
- The default value of `management.endpoint.health.show-details` is `never`.
- A `StatusAggregator` derives the system health from the `HealthIndicator` statuses, and `UNKNOWN` is used when none is known.
- Spring Boot auto-configuration secures all actuators other than `/health` when Spring Security is present and no custom `SecurityFilterChain` bean exists.
- `ApplicationStartedEvent` is sent after the context refresh and before the runners, and `ApplicationReadyEvent` after the runners.
- Liveness and readiness are exposed as health endpoint groups when the actuator is used.
- Graceful shutdown is enabled by default with Jetty, Reactor Netty and Tomcat, and it stops accepting new requests at the network layer.
- A test slice restricts component scan and loads a very restricted set of auto-configuration classes.
- The test context cache is static, bounded to 32 contexts by default, and evicts the least recently used one.
- Container beans are started before all other beans and stopped after their destruction.

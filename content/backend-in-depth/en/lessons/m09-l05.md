# Storage engines and non-relational databases

## LSM-trees versus B-trees
<!-- bullets: 9.5.a -->

An LSM-tree is composed of two or more tree-like component data structures (`paper-oneil-lsm-tree#p4`).

A two component LSM-tree has a smaller component which is entirely memory resident, known as the C0 tree (or C0 component), and a larger component which is resident on disk, known as the C1 tree (or C1 component) (`paper-oneil-lsm-tree#p4`).

A log record to recover an insert is first written to the sequential log file in the usual way, and the index entry is then inserted into the memory resident C0 tree (`paper-oneil-lsm-tree#p4`).

Any search for an index entry will look first in C0 and then in C1 (`paper-oneil-lsm-tree#p4`).

The operation of inserting an index entry into the memory resident C0 tree has no I/O cost (`paper-oneil-lsm-tree#p4`).

Whenever the C0 tree reaches a threshold size near the maximum allotted, an ongoing rolling merge process serves to delete some contiguous segment of entries from the C0 tree and merge it into the C1 tree on disk (`paper-oneil-lsm-tree#p4`).

The C1 tree has a comparable directory structure to a B-tree, but is optimized for sequential disk access, with nodes 100% full (`paper-oneil-lsm-tree#p4`).

The LSM-tree uses an algorithm that defers and batches index changes, migrating the changes out to disk in a particularly efficient way reminiscent of merge sort (`paper-oneil-lsm-tree#p3`).

In an LSM-tree, only finds that require immediate response remain relatively costly (`paper-oneil-lsm-tree#p3`).

A major area of effective use for the LSM-tree is in applications where retrieval is much less frequent than insert (`paper-oneil-lsm-tree#p3`).

With randomly chosen keys, each insert into a B-tree index requires at least one page read from the index and, in the steady state, a page write as well (`paper-oneil-lsm-tree#p3`).

B-trees can handle equality and range queries on data that can be sorted into some ordering (`pg-indexes-types#INDEXES-TYPES-BTREE`).

B-tree indexes can also be used to retrieve data in sorted order (`pg-indexes-types#INDEXES-TYPES-BTREE`).

The PostgreSQL optimizer can use a B-tree index for queries involving the pattern matching operators `LIKE` and `~` if the pattern is a constant and is anchored to the beginning of the string (`pg-indexes-types#INDEXES-TYPES-BTREE`).

It is also possible to use B-tree indexes for `ILIKE` and `~*`, but only if the pattern starts with non-alphabetic characters (`pg-indexes-types#INDEXES-TYPES-BTREE`).

In Bigtable, the recently committed updates are stored in memory in a sorted buffer called a memtable, and the older updates are stored in a sequence of SSTables (`paper-bigtable#p6`).

When the memtable size reaches a threshold, the memtable is frozen, a new memtable is created, and the frozen memtable is converted to an SSTable (`paper-bigtable#p6`).

Every minor compaction creates a new SSTable (`paper-bigtable#p6`).

A merging compaction that rewrites all SSTables into exactly one SSTable is called a major compaction (`paper-bigtable#p6`).

A valid read operation is executed on a merged view of the sequence of SSTables and the memtable (`paper-bigtable#p6`).

In Bigtable, a read operation has to read from all SSTables that make up the state of a tablet (`paper-bigtable#p7`).

A Bloom filter allows Bigtable to ask whether an SSTable might contain any data for a specified row/column pair (`paper-bigtable#p7`).

Most lookups for non-existent rows or columns do not need to touch disk when Bloom filters are used (`paper-bigtable#p7`).

A Bloom filter for representing a set of n elements is described by an array of m bits, initially all set to 0 (`paper-broder-bloom-filters#p2`).

A Bloom filter uses k independent hash functions (`paper-broder-bloom-filters#p2`).

To check if an item y is in the set, a Bloom filter checks whether all of its k bit positions are set to 1, and if not, then clearly y is not a member of the set (`paper-broder-bloom-filters#p3`).

If all k bit positions of an item are set to 1, the Bloom filter assumes that the item is in the set, although it is wrong with some probability (`paper-broder-bloom-filters#p3`).

A Bloom filter offers a representation that can dramatically reduce space, at the cost of introducing false positives (`paper-broder-bloom-filters#p2`).

:::esquema{kind=tabla title="Bigtable compactions"}
| Compaction | What it does | Source |
|---|---|---|
| Minor | Converts the frozen memtable to a new SSTable | `paper-bigtable#p6` |
| Major | Rewrites all SSTables into exactly one SSTable | `paper-bigtable#p6` |
:::

## Row-oriented versus columnar storage
<!-- bullets: 9.5.b -->

The `index.mode` setting affects the storage and query profile for an index or for the backing indices of a data stream (`es-index-basics#index-mode`).

The `index.mode` setting changes default settings, how Elasticsearch stores fields on disk, and whether it keeps the original JSON (`_source`) or reconstructs it (`es-index-basics#index-mode`).

Standard (`standard`) mode is optimized for search and any type of retrieval (`es-index-basics#index-mode`).

Columnar (`columnar`) mode is optimized for storage efficiency and analytics (`es-index-basics#index-mode`).

TSDB (`time_series`) mode is optimized for metrics and time series use cases (`es-index-basics#index-mode`).

TSDB mode is only applicable to data streams (`es-index-basics#index-mode`).

:::judgement{source="Microsoft, Azure Architecture Center, Understand data store models" ref="azure-data-store-models#column-family-data-stores-"}
According to Microsoft's Azure Architecture Center, a column-family database stores sparse data into rows and organizes dynamic columns into column families to support co-access, and column orientation improves scans over selected column sets.
:::

:::judgement{source="Microsoft, Azure Architecture Center, Understand data store models" ref="azure-data-store-models#choose-among-models-heuristics"}
According to the same page, a relational store is preferred for strict multi-entity transactions, and an analytics or OLAP store for massive historical analytical scans.
:::

## Redis internals
<!-- bullets: 9.5.c -->

Redis Open Source implements the following data types: Strings, Bitmaps, Bitfields, Arrays, Geospatial indexes, Hashes, JSON, Lists, Probabilistic data types, Sets, Sorted sets, Streams, Time series and Vector sets (`redis-data-types#data-types`).

By default Redis saves snapshots of the dataset on disk, in a binary file called `dump.rdb` (`redis-persistence#snapshotting`).

You can configure Redis to save the dataset every N seconds if there are at least M changes in the dataset, or you can manually call the `SAVE` or `BGSAVE` commands (`redis-persistence#snapshotting`).

The configuration `save 60 1000` makes Redis automatically dump the dataset to disk every 60 seconds if at least 1000 keys changed (`redis-persistence#snapshotting`).

If your computer running Redis stops, your power line fails, or you accidentally `kill -9` your instance, the latest data written to Redis will be lost with snapshotting alone (`redis-persistence#append-only-file`).

The append-only file is an alternative, fully-durable strategy for Redis (`redis-persistence#append-only-file`).

Every time Redis receives a command that changes the dataset (e.g. `SET`) it will append it to the AOF, and when you restart Redis it will re-play the AOF to rebuild the state (`redis-persistence#append-only-file`).

Since Redis 7.0.0, Redis uses a multi part AOF mechanism, so the original single AOF file is split into base file (at most one) and incremental files (there may be more than one) (`redis-persistence#append-only-file`).

In the multi part AOF, all the files are put in a separate directory and are tracked by a manifest file (`redis-persistence#append-only-file`).

The AOF gets bigger and bigger as write operations are performed (`redis-persistence#log-rewriting`).

If you are incrementing a counter 100 times, you'll end up with a single key in your dataset containing the final value, but 100 entries in your AOF (`redis-persistence#log-rewriting`).

Redis is able to rebuild the AOF in the background without interrupting service to clients (`redis-persistence#log-rewriting`).

Whenever you issue a `BGREWRITEAOF`, Redis will write the shortest sequence of commands needed to rebuild the current dataset in memory (`redis-persistence#log-rewriting`).

Since Redis 2.4 is able to trigger log rewriting automatically (`redis-persistence#log-rewriting`).

`appendfsync always` fsyncs every time new commands are appended to the AOF, and is very very slow, very safe (`redis-persistence#how-durable-is-the-append-only-file`).

`appendfsync everysec` fsyncs every second, and you may lose 1 second of data if there is a disaster (`redis-persistence#how-durable-is-the-append-only-file`).

`appendfsync no` never fsyncs and puts your data in the hands of the Operating System (`redis-persistence#how-durable-is-the-append-only-file`).

The suggested (and default) policy is to fsync every second (`redis-persistence#how-durable-is-the-append-only-file`).

The `always` policy supports group commit, so if there are multiple parallel writes Redis will try to perform a single fsync operation (`redis-persistence#how-durable-is-the-append-only-file`).

Use the `maxmemory-policy` configuration directive to select the eviction policy you want to use when the limit set by `maxmemory` is reached (`redis-eviction#eviction-policies`).

With `noeviction`, keys are not evicted but the server will return an error when you try to execute commands that cache new data (`redis-eviction#eviction-policies`).

With `noeviction`, commands that only read existing data still work as normal (`redis-eviction#eviction-policies`).

`allkeys-lru` evicts the least recently used (LRU) keys (`redis-eviction#eviction-policies`).

`allkeys-random` evicts keys at random (`redis-eviction#eviction-policies`).

`volatile-lru` evicts the least recently used keys that have an associated expiration (TTL) (`redis-eviction#eviction-policies`).

`volatile-ttl` evicts keys with an associated expiration (TTL) that have the shortest remaining TTL value (`redis-eviction#eviction-policies`).

The `volatile-xxx` policies behave like `noeviction` if no keys have an associated expiration (`redis-eviction#eviction-policies`).

`allkeys-lru` is a good default option if you have no reason to prefer any other policy (`redis-eviction#eviction-policies`).

Setting an expire value for a key costs memory, so a policy like `allkeys-lru` is more memory efficient since it doesn't need an expire value to operate (`redis-eviction#eviction-policies`).

In Redis Sentinel, failure detection is performed when multiple Sentinels agree about the fact a given master is no longer available, which lowers the probability of false positives (`redis-sentinel#sentinel-as-a-distributed-system`).

Sentinel works even if not all the Sentinel processes are working, making the system robust against failures (`redis-sentinel#sentinel-as-a-distributed-system`).

Redis Cluster does not guarantee strong consistency (`redis-scaling#redis-cluster-consistency-guarantees`).

The first reason why Redis Cluster can lose writes is because it uses asynchronous replication (`redis-scaling#redis-cluster-consistency-guarantees`).

The master does not wait for an acknowledgement from its replicas before replying to the client, since this would be a prohibitive latency penalty for Redis (`redis-scaling#redis-cluster-consistency-guarantees`).

If the master acknowledges a write but crashes before being able to send the write to its replicas, one of the replicas that did not receive the write can be promoted to master, losing the write forever (`redis-scaling#redis-cluster-consistency-guarantees`).

Redis Cluster has support for synchronous writes when absolutely needed, implemented via the `WAIT` command (`redis-scaling#redis-cluster-consistency-guarantees`).

Redis Cluster does not implement strong consistency even when synchronous replication is used (`redis-scaling#redis-cluster-consistency-guarantees`).

After node timeout has elapsed, a master node is considered to be failing, and can be replaced by one of its replicas (`redis-scaling#redis-cluster-consistency-guarantees`).

After node timeout has elapsed without a master node being able to sense the majority of the other master nodes, it enters an error state and stops accepting writes (`redis-scaling#redis-cluster-consistency-guarantees`).

Redis Cluster uses asynchronous replication between nodes, and last failover wins implicit merge function (`redis-cluster-spec#write-safety`).

Redis Cluster tries harder to retain writes that are performed by clients connected to the majority of masters, compared to writes performed in the minority side (`redis-cluster-spec#write-safety`).

For a master to be failed over it must be unreachable by the majority of masters for at least `NODE_TIMEOUT` (`redis-cluster-spec#write-safety`).

Redis Cluster is not available in the minority side of the partition (`redis-cluster-spec#availability`).

Thanks to a Redis Cluster feature called replicas migration, replicas migrate to orphaned masters (masters no longer having replicas) (`redis-cluster-spec#availability`).

## Elasticsearch internals
<!-- bullets: 9.5.d -->

Each shard is a self-contained Apache Lucene index (`es-index-basics#how-an-index-stores-data`).

Inside each shard, data is organized into immutable segments that are written as documents are indexed (`es-index-basics#how-an-index-stores-data`).

Every document belongs to exactly one primary shard (`es-index-basics#how-an-index-stores-data`).

The number of primary shards is fixed at index creation (`es-index-basics#how-an-index-stores-data`).

You can adjust the number of replicas at any time using the `index.number_of_replicas` setting (`es-index-basics#how-an-index-stores-data`).

A replica shard is a copy of a primary shard (`es-clusters-nodes-shards#elastic-docs-v3`).

Replicas maintain redundant copies of your data across the nodes in your cluster, which protects against hardware failure and increases capacity to serve read requests (`es-clusters-nodes-shards#elastic-docs-v3`).

The `index.number_of_replicas` setting is the number of replicas each primary shard has, and it defaults to 1 (`es-index-modules#dynamic-index-settings`).

Every indexing operation in Elasticsearch is first resolved to a replication group using routing, typically based on the document ID (`es-reading-and-writing-documents#basic-write-model`).

The in-sync copies are the set of "good" shard copies that are guaranteed to have processed all of the index and delete operations that have been acknowledged to the user (`es-reading-and-writing-documents#basic-write-model`).

The list of in-sync copies is maintained by the master node (`es-reading-and-writing-documents#basic-write-model`).

Since replicas can be offline, the primary is not required to replicate to all replicas (`es-reading-and-writing-documents#basic-write-model`).

Once all in-sync replicas have successfully performed the operation and responded to the primary, the primary acknowledges the successful completion of the request to the client (`es-reading-and-writing-documents#basic-write-model`).

In Elasticsearch, the process of writing and opening a new segment is called a refresh (`es-near-real-time-search#elastic-docs-v3`).

A refresh makes all operations performed on an index since the last refresh available for search (`es-near-real-time-search#elastic-docs-v3`).

The new segment is written to the filesystem cache first (which is cheap) and only later is it flushed to disk (which is expensive) (`es-near-real-time-search#elastic-docs-v3`).

Lucene allows new segments to be written and opened, making the documents they contain visible to search without performing a full commit (`es-near-real-time-search#elastic-docs-v3`).

By default, Elasticsearch periodically refreshes indices every second, but only on indices that have received one search request or more in the last 30 seconds (`es-near-real-time-search#elastic-docs-v3`).

The `index.refresh_interval` value defaults to `1s` in Elastic Stack and `5s` in Serverless (`es-index-modules#dynamic-index-settings`).

The `index.refresh_interval` setting can be set to `-1` to disable periodic refresh operations (`es-index-modules#dynamic-index-settings`).

The `index.search.idle.after` setting is how long a shard can not receive a search or get request until it is considered search idle, and its default is `30s` (`es-index-modules#dynamic-index-settings`).

Smaller merges are prioritized over larger ones, across all shards on the node (`es-merge-settings#merge-scheduling`).

Merges are disk IO throttled so that bursts, while merging activity is otherwise low, are smoothed out in order to not impact indexing throughput (`es-merge-settings#merge-scheduling`).

There is no limit on the number of merges that can be enqueued for execution on the thread pool (`es-merge-settings#merge-scheduling`).

Beyond a certain per-shard limit, after merging is completely disk IO un-throttled, indexing for the shard will itself be throttled until merging catches up (`es-merge-settings#merge-scheduling`).

`index.merge.scheduler.max_thread_count` defaults to half the number of processors the JVM sees on the node, with a minimum of 1 (`es-merge-settings#merge-scheduling`).

If your index is on spinning platter drives, decrease `index.merge.scheduler.max_thread_count` to 1 (`es-merge-settings#merge-scheduling`).

`index.merge.scheduler.max_merge_count` defaults to `index.merge.scheduler.max_thread_count` + 5 (`es-merge-settings#merge-scheduling`).

Changes to Lucene are only persisted to disk during a Lucene commit, which is a relatively expensive operation and so cannot be performed after every index or delete operation (`es-translog#elastic-docs-v3`).

Each shard copy also writes operations into its transaction log known as the translog, because Lucene commits are too expensive to perform on every individual change (`es-translog#elastic-docs-v3`).

All index and delete operations are written to the translog after being processed by the internal Lucene index but before they are acknowledged (`es-translog#elastic-docs-v3`).

In the event of a crash, recent operations that have been acknowledged but not yet included in the last Lucene commit are recovered from the translog when the shard recovers (`es-translog#elastic-docs-v3`).

An Elasticsearch flush is the process of performing a Lucene commit and starting a new translog generation (`es-translog#elastic-docs-v3`).

The translog size will never exceed 1% of the disk size (`es-translog#elastic-docs-v3`).

An analyzer, whether built-in or custom, is a package which contains three lower-level building blocks: character filters, tokenizers, and token filters (`es-anatomy-of-an-analyzer#elastic-docs-v3`).

In most cases, the same analyzer should be used at index and search time (`es-index-search-analysis#analysis-same-index-search-analyzer`).

Using the same analyzer ensures the values and query strings for a field are changed into the same form of tokens (`es-index-search-analysis#analysis-same-index-search-analyzer`).

The query string is analyzed using the same analyzer (`es-index-search-analysis#analysis-same-index-search-analyzer`).

Text analysis consists of a pipeline of sequential transformations (`es-how-full-text-works#elastic-docs-v3`).

Text is transformed into a format optimized for searching using techniques such as stemming, lowercasing, and stop word elimination (`es-how-full-text-works#elastic-docs-v3`).

In a `search_after` request, if provided, the `from` argument must be 0 (default) or -1 (`es-paginate-search-results#search-after`).

Search after requests have optimizations that make them faster when the sort order is `_shard_doc` and total hits are not tracked (`es-paginate-search-results#search-after`).

If you need to preserve the index state while paging through more than 10,000 hits, use the `search_after` parameter with a point in time (PIT) (`es-paginate-search-results#scroll-search-results`).

Scrolling is not intended for real time user requests, but rather for processing large amounts of data (`es-paginate-search-results#scroll-search-results`).

## Choosing between document, key-value, wide-column and time-series stores
<!-- bullets: 9.5.e -->

:::judgement{source="Microsoft, Azure Architecture Center, Understand data store models" ref="azure-data-store-models#document-data-stores-"}
According to Microsoft's Azure Architecture Center, document data stores store semi-structured documents, often in JSON format, where each document includes named fields and data. The page lists natural application object mapping, denormalized aggregates and multi-field indexing as strengths, and document size growth and selective transactional scope as considerations.
:::

:::judgement{source="Microsoft, Azure Architecture Center, Understand data store models" ref="azure-data-store-models#key-value-data-stores-"}
According to the same page, a key-value data store associates each data value with a unique key, and most key-value stores only support simple query, insert, and delete operations. It lists simplicity, low latency and linear scalability as strengths, and limited query expressiveness and the cost of large value overwrites as considerations.
:::

:::judgement{source="Microsoft, Azure Architecture Center, Understand data store models" ref="azure-data-store-models#column-family-data-stores-"}
According to the same page, a column-family database, also known as a wide-column database, stores sparse data into rows and organizes dynamic columns into column families to support co-access. It lists high write throughput and efficient retrieval of wide or sparse datasets as strengths, and up-front row key and column family design as a consideration.
:::

:::judgement{source="Microsoft, Azure Architecture Center, Understand data store models" ref="azure-data-store-models#time-series-data-stores-"}
According to the same page, time-series data stores manage a set of values organized by time, are typically append-only databases, and are optimized to ingest and analyze large volumes of data in near real time. It lists high-volume ingestion and time-window queries and aggregations as strengths, and tag cardinality management and downsampling strategy as considerations.
:::

:::judgement{source="Microsoft, Azure Architecture Center, Understand data store models" ref="azure-data-store-models#combine-models-and-avoid-pitfalls"}
According to the same page, more than one model fits when access patterns diverge, when life cycle and retention differ, or when latency and throughput requirements conflict. It advises using one service when it still meets performance, scale and governance objectives, and it lists a search index that becomes the primary data store as a common antipattern.
:::

## Key points

- A two-component LSM-tree keeps a smaller memory-resident C0 tree and a larger disk-resident C1 tree, and a rolling merge moves entries from C0 to C1.
- An insert into C0 has no I/O cost, and a search looks first in C0 and then in C1.
- Bigtable keeps recent updates in a sorted memtable and older updates in SSTables, and a frozen memtable is converted to an SSTable.
- A Bloom filter has no false negatives, and Bigtable uses one to avoid disk reads for SSTables that cannot contain a row.
- A PostgreSQL B-tree handles equality and range queries on sortable data and can retrieve data in sorted order.
- The Elasticsearch `index.mode` setting changes default settings and how fields are stored on disk.
- Standard mode is optimized for search and retrieval, and columnar mode for storage efficiency and analytics.
- Redis Open Source implements strings, hashes, lists, sets, sorted sets, streams and other data types.
- Snapshotting writes `dump.rdb`, and the append-only file appends every command that changes the dataset and replays it on restart.
- `appendfsync everysec` is the suggested and default policy, and it may lose 1 second of data in a disaster.
- `noeviction` returns an error for commands that cache new data, and the `volatile-xxx` policies behave like it when no key has an expiration.
- Sentinel agrees on failure detection among several processes, and Redis Cluster uses asynchronous replication, so it can lose acknowledged writes.
- An Elasticsearch shard is a self-contained Lucene index whose data is organized into immutable segments.
- A refresh writes and opens a new segment so that documents become searchable, and `index.refresh_interval` defaults to `1s` in the Elastic Stack.
- The translog records operations before they are acknowledged, and a flush performs a Lucene commit and starts a new translog generation.
- The number of primary shards is fixed at index creation, while the number of replica shards can be changed at any time.
- A primary acknowledges an indexing request after all in-sync replicas have performed it.

# Security, identity and compliance

## Zero trust between services
<!-- bullets: 10.2.a -->

In a zero trust architecture, network location alone does not imply trust (`nist-sp-800-207#p15`).

A zero trust architecture requires all communication to be secured regardless of network location (`nist-sp-800-207#p15`).

A zero trust architecture grants access to individual enterprise resources on a per-session basis (`nist-sp-800-207#p15`).

Access to an enterprise resource should be granted with the least privileges needed to complete the task (`nist-sp-800-207#p15`).

Authentication and authorization to one resource will not automatically grant access to a different resource (`nist-sp-800-207#p15`).

In a zero trust architecture, access to resources is determined by dynamic policy, including the observable state of client identity, application or service, and the requesting asset (`nist-sp-800-207#p15`).

In a zero trust architecture, no asset is inherently trusted (`nist-sp-800-207#p16`).

SPIFFE, the Secure Production Identity Framework for Everyone, is a set of open-source standards for securely identifying software systems in dynamic and heterogeneous environments (`spiffe-overview#_top`).

Systems that adopt SPIFFE can easily and reliably mutually authenticate wherever they are running (`spiffe-overview#_top`).

Conventional security practices, such as network policies that only allow traffic between particular IP addresses, struggle to scale under the complexity of dynamic production environments (`spiffe-overview#_top`).

The heart of the SPIFFE specifications is the one that defines short lived cryptographic identity documents, called SVIDs, via a simple API (`spiffe-overview#_top`).

Workloads can use these identity documents when authenticating to other workloads, for example by establishing a TLS connection or by signing and verifying a JWT token (`spiffe-overview#_top`).

In TLS 1.3 the server side of the channel is always authenticated, and the client side is optionally authenticated (`rfc8446#section-1`).

In TLS 1.3 a server that is authenticating with a certificate may optionally request a certificate from the client (`rfc8446#section-4.3.2`).

In TLS 1.3 a server that is authenticating with a PSK must not send the `CertificateRequest` message in the main handshake (`rfc8446#section-4.3.2`).

By default, if no policies exist in a namespace, then all ingress and egress traffic is allowed to and from pods in that namespace (`k8s-network-policies#default-policies`).

You can create a default policy for a namespace that prevents all ingress and egress traffic by creating a `NetworkPolicy` with an empty `podSelector` and both policy types in that namespace (`k8s-network-policies#default-deny-all-ingress-and-all-egress-traffic`).

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

That policy ensures that even pods that are not selected by any other `NetworkPolicy` will not be allowed ingress or egress traffic (`k8s-network-policies#default-deny-all-ingress-and-all-egress-traffic`).

The database secrets engine of Vault generates database credentials dynamically based on configured roles (`vault-dynamic-secrets-database#database-secrets-engine`).

With dynamic secrets, services that need to access a database no longer need to hardcode credentials: they can request them from Vault, and use Vault's leasing mechanism to more easily roll keys (`vault-dynamic-secrets-database#database-secrets-engine`).

Since every service accesses the database with unique credentials, auditing is much easier when questionable data access is discovered, because it can be tracked down to the specific instance of a service based on the SQL username (`vault-dynamic-secrets-database#database-secrets-engine`).

Vault uses its own internal revocation system to ensure that users become invalid within a reasonable time of the lease expiring (`vault-dynamic-secrets-database#database-secrets-engine`).

A Kubernetes Secret is only sent to a node if a Pod on that node requires it (`k8s-secrets#information-security-for-secrets`).

For mounting Secrets into Pods, the kubelet stores a copy of the data into a `tmpfs` so that the confidential data is not written to durable storage (`k8s-secrets#information-security-for-secrets`).

Granting `list` or `watch` permissions on Secrets allows a subject to read all Secret data in that namespace, not only the Secrets explicitly referenced by its Pods (`k8s-secrets#information-security-for-secrets`).

One Pod does not have access to the Secrets of another Pod (`k8s-secrets#information-security-for-secrets`).

## OAuth 2.0 grants and OpenID Connect
<!-- bullets: 10.2.b -->

An authorization grant is a credential representing the resource owner's authorization (to access its protected resources) used by the client to obtain an access token (`rfc6749#section-1.3`).

RFC 6749 defines four grant types: authorization code, implicit, resource owner password credentials, and client credentials (`rfc6749#section-1.3`).

The authorization code grant type is used to obtain both access tokens and refresh tokens and is optimized for confidential clients (`rfc6749#section-4.1`).

The authorization code grant is a redirection-based flow, so the client must be capable of interacting with the resource owner's user-agent and capable of receiving incoming requests from the authorization server (`rfc6749#section-4.1`).

In the authorization code flow, the client requests an access token from the token endpoint of the authorization server by including the authorization code (`rfc6749#section-4.1`).

In the last step of the authorization code flow, the authorization server authenticates the client, validates the authorization code, and ensures that the redirection URI received matches the URI used to redirect the client (`rfc6749#section-4.1`).

The client can request an access token using only its client credentials when it is requesting access to the protected resources under its control (`rfc6749#section-4.4`).

The client credentials grant type must only be used by confidential clients (`rfc6749#section-4.4`).

Clients and authorization servers must not expose open redirectors, which forward the user's browser to arbitrary URIs obtained from a query parameter (`rfc9700#section-2.1`).

Clients must prevent Cross-Site Request Forgery (`rfc9700#section-2.1`).

In OpenID Connect flows, the `nonce` parameter provides CSRF protection (`rfc9700#section-2.1`).

When an OAuth client can interact with more than one authorization server, a defense against mix-up attacks is required (`rfc9700#section-2.1`).

:::esquema{kind=tabla title="OAuth 2.0 security requirements in RFC 9700"}
| Subject | Requirement | Source |
|---|---|---|
| Redirection URIs | Authorization servers must use exact string matching against pre-registered URIs, except for port numbers in localhost redirection URIs of native apps | `rfc9700#section-2.1` |
| Public clients | Must use PKCE to prevent authorization code injection attacks and misuse of authorization codes | `rfc9700#section-2.1.1` |
| Confidential clients | The use of PKCE is recommended | `rfc9700#section-2.1.1` |
| Authorization servers | Must support PKCE | `rfc9700#section-2.1.1` |
| Implicit grant | Clients should not use the implicit grant (response type `token`) or other response types issuing access tokens in the authorization response | `rfc9700#section-2.1.2` |
:::

When using PKCE, clients should use PKCE code challenge methods that do not expose the PKCE verifier in the authorization request (`rfc9700#section-2.1.1`).

Currently, `S256` is the only PKCE code challenge method that does not expose the verifier (`rfc9700#section-2.1.1`).

Authorization servers must mitigate PKCE downgrade attacks by ensuring that a token request containing a `code_verifier` parameter is accepted only if a `code_challenge` parameter was present in the authorization request (`rfc9700#section-2.1.1`).

It is recommended for authorization servers to publish `code_challenge_methods_supported` in their Authorization Server Metadata, so that the client can detect PKCE support (`rfc9700#section-2.1.1`).

The implicit grant is vulnerable to access token leakage and access token replay (`rfc9700#section-2.1.2`).

Clients should instead use the response type `code`, which is the authorization code grant type (`rfc9700#section-2.1.2`).

The primary extension that OpenID Connect makes to OAuth 2.0 to enable End-Users to be Authenticated is the ID Token data structure (`oidc-core#rfc.section.2`).

The ID Token is represented as a JSON Web Token (JWT) (`oidc-core#rfc.section.2`).

The `aud` claim of an ID Token must contain the OAuth 2.0 `client_id` of the Relying Party as an audience value (`oidc-core#rfc.section.2`).

An ID Token must not be accepted on or after the expiration time given by its `exp` claim (`oidc-core#rfc.section.2`).

Implementers may provide for some small leeway, usually no more than a few minutes, to account for clock skew (`oidc-core#rfc.section.2`).

The `nonce` claim is a string value used to associate a Client session with an ID Token, and to mitigate replay attacks (`oidc-core#rfc.section.2`).

ID Tokens must be signed using JWS (`oidc-core#rfc.section.2`).

ID Tokens must not use `none` as the `alg` value unless the Response Type used returns no ID Token from the Authorization Endpoint and the Client explicitly requested the use of `none` at Registration time (`oidc-core#rfc.section.2`).

When using the Authorization Code Flow of OpenID Connect, all tokens are returned from the Token Endpoint (`oidc-core#rfc.section.3.1`).

The Authorization Code Flow returns an Authorization Code to the Client, which can then exchange it for an ID Token and an Access Token directly (`oidc-core#rfc.section.3.1`).

The Authorization Code Flow provides the benefit of not exposing any tokens to the User Agent and possibly other malicious applications with access to the User Agent (`oidc-core#rfc.section.3.1`).

The Authorization Code flow is suitable for Clients that can securely maintain a Client Secret between themselves and the Authorization Server (`oidc-core#rfc.section.3.1`).

A Security Token Service (STS) is a service capable of validating security tokens provided to it and issuing new security tokens in response (`rfc8693#section-1`).

RFC 8693 defines a protocol extending OAuth 2.0 that enables clients to request and obtain security tokens from authorization servers acting in the role of an STS (`rfc8693#section-1`).

RFC 8693 defines a new grant type for a token exchange request and the associated specific parameters for such a request to the token endpoint (`rfc8693#section-1`).

An OAuth resource server might assume the role of the client during token exchange in order to trade an access token that it received in a protected resource request for a new token that is appropriate to include in a call to a backend service (`rfc8693#section-1`).

## JWT validation and key identifiers
<!-- bullets: 10.2.b -->

None of the registered claims of RFC 7519 are intended to be mandatory to use or implement in all cases (`rfc7519#section-4.1`).

Applications using JWTs should define which specific claims they use and when they are required or optional (`rfc7519#section-4.1`).

If any of the listed validation steps fails, the JWT must be rejected, that is, treated by the application as an invalid input (`rfc7519#section-7.2`).

The order of the validation steps is not significant in cases where there are no dependencies between the inputs and outputs of the steps (`rfc7519#section-7.2`).

The first validation step is to verify that the JWT contains at least one period character (`rfc7519#section-7.2`).

If the JOSE Header contains a `cty` value of `JWT`, the Message is a JWT that was the subject of nested signing or encryption operations, and validation returns to step 1 using the Message as the JWT (`rfc7519#section-7.2`).

It is an application decision which algorithms may be used in a given context (`rfc7519#section-7.2`).

Even if a JWT can be successfully validated, the application should reject the JWT unless the algorithms used in the JWT are acceptable to it (`rfc7519#section-7.2`).

The `kid` (key ID) header parameter is a hint indicating which key was used to secure the JWS (`rfc7515#section-4.1.4`).

The `kid` header parameter allows originators to explicitly signal a change of key to recipients (`rfc7515#section-4.1.4`).

Use of the `kid` header parameter is optional (`rfc7515#section-4.1.4`).

The `kid` parameter of a JWK is used to match a specific key, for instance to choose among a set of keys within a JWK Set during key rollover (`rfc7517#section-4.5`).

When `kid` values are used within a JWK Set, different keys within the JWK Set should use distinct `kid` values (`rfc7517#section-4.5`).

The structure of the `kid` value of a JWK is unspecified (`rfc7517#section-4.5`).

In Spring Security, `JwtAuthenticationProvider` decodes, verifies, and validates the `Jwt` using a `JwtDecoder` (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-architecture`).

`JwtAuthenticationProvider` then uses the `JwtAuthenticationConverter` to convert the `Jwt` into a collection of granted authorities (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-architecture`).

When authentication is successful, the `Authentication` that is returned is of type `JwtAuthenticationToken` (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-architecture`).

If the authorization server does not support any configuration endpoints, or if the Resource Server must be able to initialize independently from the authorization server, the `jwk-set-uri` can be supplied (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-jwkseturi`).

The JWK Set uri is not standardized (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-jwkseturi`).

With `jwk-set-uri` supplied, the Resource Server will not ping the authorization server at startup (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-jwkseturi`).

The `issuer-uri` is still specified so that the Resource Server still validates the `iss` claim on incoming JWTs (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-jwkseturi`).

JWTs typically have a window of validity, with the start of the window indicated in the `nbf` claim and the end indicated in the `exp` claim (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-validation-clockskew`).

Every server can experience clock drift, which can cause tokens to appear expired to one server, but not to another (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-validation-clockskew`).

Resource Server uses `JwtTimestampValidator` to verify a token's validity window, and it can be configured with a `clockSkew` (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-validation-clockskew`).

By default, Resource Server configures a clock skew of 60 seconds (`spring-security-servlet-oauth2-resource-server-jwt#oauth2resourceserver-jwt-validation-clockskew`).

## RBAC and ABAC
<!-- bullets: 10.2.b -->

A Kubernetes RBAC `Role` or `ClusterRole` contains rules that represent a set of permissions (`k8s-rbac#role-and-clusterrole`).

Kubernetes RBAC permissions are purely additive, and there are no deny rules (`k8s-rbac#role-and-clusterrole`).

A `Role` always sets permissions within a particular namespace (`k8s-rbac#role-and-clusterrole`).

`ClusterRole` is a non-namespaced resource (`k8s-rbac#role-and-clusterrole`).

Role-Based Access Control (RBAC) is a model of access control in which access is granted or denied based upon the roles assigned to a user (`owasp-cs-authorization#prefer-attribute-and-relationship-based-access-control-over-rbac`).

Attribute-Based Access Control (ABAC) is defined by NIST SP 800-162, quoted by OWASP, as a model where subject requests to perform operations on objects are granted or denied based on assigned attributes of the subject, assigned attributes of the object, environment conditions, and a set of policies that are specified in terms of those attributes and conditions (`owasp-cs-authorization#prefer-attribute-and-relationship-based-access-control-over-rbac`).

Relationship-Based Access Control (ReBAC) is an access control model that grants access based on the relationships between resources (`owasp-cs-authorization#prefer-attribute-and-relationship-based-access-control-over-rbac`).

ABAC and ReBAC should typically be preferred over RBAC for application development (`owasp-cs-authorization#prefer-attribute-and-relationship-based-access-control-over-rbac`).

In RBAC, role explosion can occur when a system defines too many roles (`owasp-cs-authorization#prefer-attribute-and-relationship-based-access-control-over-rbac`).

If users send their credential and roles through means like HTTP headers, which have size limits, there may not be enough space to include all of the user's roles (`owasp-cs-authorization#prefer-attribute-and-relationship-based-access-control-over-rbac`).

ABAC can incorporate environmental and other dynamic attributes, such as time of day, type of device used, and geographic location (`owasp-cs-authorization#prefer-attribute-and-relationship-based-access-control-over-rbac`).

By default, Spring Security requires that every request be authenticated (`spring-security-servlet-authorization-authorize-http-requests#page-title`).

Any time you use an `HttpSecurity` instance, it is necessary to declare your authorization rules (`spring-security-servlet-authorization-authorize-http-requests#page-title`).

Spring Security also supports modeling authorization at the method level (`spring-security-servlet-authorization-method-security#page-title`).

You can activate method security by annotating any `@Configuration` class with `@EnableMethodSecurity` (`spring-security-servlet-authorization-method-security#page-title`).

With method security active, you can annotate any Spring-managed class or method with `@PreAuthorize`, `@PostAuthorize`, `@PreFilter` and `@PostFilter` to authorize method invocations, including the input parameters and return values (`spring-security-servlet-authorization-method-security#page-title`).

Spring Boot Starter Security does not activate method-level authorization by default (`spring-security-servlet-authorization-method-security#page-title`).

## Privacy by design and the GDPR
<!-- bullets: 10.2.c -->

:::esquema{kind=tabla title="Principles relating to processing of personal data (GDPR Article 5(1))"}
| Principle | Personal data shall be | Source |
|---|---|---|
| Lawfulness, fairness and transparency | Processed lawfully, fairly and in a transparent manner in relation to the data subject | `gdpr-eurlex#art_5` |
| Purpose limitation | Collected for specified, explicit and legitimate purposes and not further processed in a manner that is incompatible with those purposes | `gdpr-eurlex#art_5` |
| Data minimisation | Adequate, relevant and limited to what is necessary in relation to the purposes for which they are processed | `gdpr-eurlex#art_5` |
| Accuracy | Accurate and, where necessary, kept up to date | `gdpr-eurlex#art_5` |
| Storage limitation | Kept in a form which permits identification of data subjects for no longer than is necessary for the purposes for which the personal data are processed | `gdpr-eurlex#art_5` |
| Integrity and confidentiality | Processed in a manner that ensures appropriate security of the personal data, including protection against unauthorised or unlawful processing and against accidental loss, destruction or damage | `gdpr-eurlex#art_5` |
:::

The controller is responsible for, and must be able to demonstrate compliance with, the principles of Article 5(1) (`gdpr-eurlex#art_5`).

Article 25(1) requires the controller, both at the time of the determination of the means for processing and at the time of the processing itself, to implement appropriate technical and organisational measures, such as pseudonymisation, which are designed to implement data-protection principles, such as data minimisation, in an effective manner (`gdpr-eurlex#art_25`).

Article 25(2) requires the controller to implement appropriate technical and organisational measures for ensuring that, by default, only personal data which are necessary for each specific purpose of the processing are processed (`gdpr-eurlex#art_25`).

That obligation applies to the amount of personal data collected, the extent of their processing, the period of their storage and their accessibility (`gdpr-eurlex#art_25`).

Such measures shall ensure that by default personal data are not made accessible without the individual's intervention to an indefinite number of natural persons (`gdpr-eurlex#art_25`).

Each controller shall maintain a record of processing activities under its responsibility (`gdpr-eurlex#art_30`).

Each processor shall maintain a record of all categories of processing activities carried out on behalf of a controller (`gdpr-eurlex#art_30`).

The records of processing activities shall be in writing, including in electronic form (`gdpr-eurlex#art_30`).

The controller or the processor shall make the record available to the supervisory authority on request (`gdpr-eurlex#art_30`).

The record obligations do not apply to an enterprise or an organisation employing fewer than 250 persons unless the processing is likely to result in a risk to the rights and freedoms of data subjects, the processing is not occasional, or the processing includes special categories of data (`gdpr-eurlex#art_30`).

Article 32(1) requires the controller and the processor to implement appropriate technical and organisational measures to ensure a level of security appropriate to the risk (`gdpr-eurlex#art_32`).

The measures of Article 32(1) include, as appropriate, the pseudonymisation and encryption of personal data (`gdpr-eurlex#art_32`).

The measures of Article 32(1) include the ability to restore the availability and access to personal data in a timely manner in the event of a physical or technical incident (`gdpr-eurlex#art_32`).

The measures of Article 32(1) include a process for regularly testing, assessing and evaluating the effectiveness of technical and organisational measures for ensuring the security of the processing (`gdpr-eurlex#art_32`).

## Encryption in transit and at rest, and audit logs
<!-- bullets: 10.2.c -->

The primary goal of TLS is to provide a secure channel between two communicating peers (`rfc8446#section-1`).

In TLS, confidentiality means that data sent over the channel after establishment is only visible to the endpoints (`rfc8446#section-1`).

In TLS, integrity means that data sent over the channel after establishment cannot be modified by attackers without detection (`rfc8446#section-1`).

TLS does not hide the length of the data it transmits, though endpoints are able to pad TLS records in order to obscure lengths (`rfc8446#section-1`).

TLS consists of two primary components, the first being a handshake protocol that authenticates the communicating parties, negotiates cryptographic modes and parameters, and establishes shared keying material (`rfc8446#section-1`).

The second primary component of TLS is a record protocol that uses the parameters established by the handshake protocol to protect traffic between the communicating peers (`rfc8446#section-1`).

In a Kubernetes `EncryptionConfiguration`, the first provider in the list is used to encrypt resources written into the storage (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

When reading resources from storage, each provider that matches the stored data attempts in order to decrypt the data (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

If no provider can read the stored data due to a mismatch in format or secret key, an error is returned which prevents clients from accessing that resource (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

Only one provider type may be specified per entry of the `providers` array (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

Each provider supports multiple keys, the keys are tried in order for decryption, and if the provider is the first provider, the first key is used for encryption (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

In the example `EncryptionConfiguration`, the `identity` provider is annotated as plain text, in other words no encryption (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

If custom resources are added to `EncryptionConfiguration` and the cluster version is 1.26 or newer, any newly created custom resources mentioned in the `EncryptionConfiguration` will be encrypted (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

Any custom resources that existed in etcd prior to that version and configuration will be unencrypted until they are next written to storage (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

The `'*.*'` entry will encrypt all resources, even custom resources that are added after API server start (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

A wildcard match in an `EncryptionConfiguration` requires Kubernetes 1.27 or later (`k8s-encrypt-data#understanding-the-encryption-at-rest-configuration`).

The logging mechanisms and collected event data must be protected from mis-use such as tampering in transit, and unauthorized access, modification and deletion once stored (`owasp-cs-logging#protection`).

For logs at rest, OWASP advises to build in tamper detection so you know if a record has been modified or deleted (`owasp-cs-logging#protection`).

For logs at rest, OWASP advises to store or copy log data to read-only media as soon as possible (`owasp-cs-logging#protection`).

For logs at rest, OWASP advises that all access to the logs must be recorded and monitored (`owasp-cs-logging#protection`).

For logs at rest, OWASP advises that the privileges to read log data should be restricted and reviewed periodically (`owasp-cs-logging#protection`).

For logs in transit, OWASP advises that if log data is sent over untrusted networks, a secure transmission protocol should be used (`owasp-cs-logging#protection`).

## Key points

- A zero trust architecture does not treat network location as trust, secures all communication, and grants access to each resource per session with least privilege.
- SPIFFE identities are short lived cryptographic identity documents called SVIDs, which workloads use for TLS connections or signed JWTs.
- In TLS 1.3 the server is always authenticated and the client only optionally, by answering a `CertificateRequest`.
- With no `NetworkPolicy` in a namespace all ingress and egress traffic is allowed, and a policy with an empty `podSelector` and both policy types denies it all.
- Vault's database secrets engine generates unique, leased database credentials, so services do not hardcode them and access can be traced to a service instance.
- RFC 6749 defines four grant types, and the client credentials grant must only be used by confidential clients.
- RFC 9700 requires exact redirect URI matching, requires PKCE for public clients, recommends it for confidential clients and advises against the implicit grant.
- An OpenID Connect ID Token is a signed JWT, and its `aud` claim must contain the `client_id` of the Relying Party.
- A JWT that fails any validation step must be rejected, and it should also be rejected when its algorithms are not acceptable to the application.
- The `kid` header parameter is a hint for which key secured a JWS and lets recipients follow a key change, and keys of a JWK Set should use distinct `kid` values.
- Spring Security's resource server configures a clock skew of 60 seconds by default, and a supplied `jwk-set-uri` stops it from pinging the authorization server at startup.
- Kubernetes RBAC permissions are purely additive and have no deny rules, and OWASP says ABAC and ReBAC should typically be preferred over RBAC.
- GDPR Article 5(1) lists six principles, Article 25 requires data protection by design and by default, and Article 30 requires records of processing activities.
- An `EncryptionConfiguration` encrypts with the first provider and reads with whichever provider matches, and it returns an error when none can read the data.
- OWASP advises tamper detection, read-only media, monitored access and secure transmission for logs.

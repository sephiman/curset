## Modules and their boundaries in Spring Modulith
<!-- bullets: 1.3.b -->

In a Spring Boot application, an application module is a unit of functionality (`spring-modulith-fundamentals#modules`).

A module's internal implementation components are not supposed to be accessed by other modules (`spring-modulith-fundamentals#modules`).

By default, a module's base package is the API package and the only package that allows incoming dependencies from other modules (`spring-modulith-fundamentals#modules.named-interfaces`).

To expose an additional package to other modules, you annotate its `package-info.java` with `@NamedInterface` (`spring-modulith-fundamentals#modules.named-interfaces`).

With `@ApplicationModule(allowedDependencies = "order :: spi")` on the `inventory` module, its code may depend on the types in the `order.spi` named interface but not on `OrderManagement` (`spring-modulith-fundamentals#modules.named-interfaces`).

Calling `ApplicationModules.of(Application.class).verify()` rejects cycles at the module level, because the dependencies between modules have to form a directed acyclic graph (`spring-modulith-verification#page-title`).

The same verification rejects references to types that reside in application module internal packages, while dependencies into internals of open application modules are allowed (`spring-modulith-verification#page-title`).

Spring Modulith says that the primary means of interaction between application modules should be event publication and consumption (`spring-modulith-events#page-title`).

The event publication registry writes an entry for each transactional event listener into an event publication log as part of the original business transaction (`spring-modulith-events#publication-registry`).

## Architecture tests with ArchUnit
<!-- bullets: 1.3.c -->

ArchUnit offers a fluent, DSL-like API to express architectural rules such as "Services should only be accessed by Controllers" (`archunit-user-guide#_asserting_architectural_constraints`).

The entry point for specifying a rule is the class `ArchRuleDefinition` (`archunit-user-guide#_asserting_architectural_constraints`).

A rule of type `ArchRule` is evaluated against imported classes by calling `check(importedClasses)` (`archunit-user-guide#_asserting_architectural_constraints`).

:::esquema{kind=tabla title="A layer check in ArchUnit"}
| Declaration | What it states | Source |
|---|---|---|
| `layer("Controller").definedBy("..controller..")` | The `Controller` layer is the classes in the `..controller..` package pattern | `archunit-user-guide#_layer_checks` |
| `whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")` | Only the `Controller` layer may access the `Service` layer | `archunit-user-guide#_layer_checks` |
| `whereLayer("Controller").mayNotBeAccessedByAnyLayer()` | No layer may access the `Controller` layer | `archunit-user-guide#_layer_checks` |
:::

The `Architectures` entry point provides a check for a layered architecture and for an onion architecture (`archunit-user-guide#_architectures`).

Slice rules sort classes into slices by package and make assertions on those slices (`archunit-user-guide#_slices`).

`SlicesRuleDefinition.slices().matching("..myapp.(*)..").should().beFreeOfCycles()` sorts classes by the first package after `myapp` and checks those slices for cyclic dependencies (`archunit-user-guide#_slices`).

`notDependOnEachOther()` checks that slices have no dependencies on each other (`archunit-user-guide#_slices`).

:::judgement{source="Building Evolutionary Architectures, authors' precis, section Fitness Functions" ref="bea-evolutionary-architecture-precis#fitness-functions"}
According to the authors of *Building Evolutionary Architectures*, an architectural fitness function provides an objective integrity assessment of some architectural characteristic or characteristics. According to them, fitness functions encompass existing engineering practices such as testing and metrics.
:::

## Aggregates, value objects and domain events
<!-- bullets: 1.3.d -->

Entities managed by Spring Data repositories are aggregate roots (`spring-data-commons-domain-events#page-title`).

In a Domain-Driven Design application, aggregate roots usually publish domain events (`spring-data-commons-domain-events#page-title`).

A method of an aggregate root annotated with `@DomainEvents` can return a single event instance or a collection, and it must not take any arguments (`spring-data-commons-domain-events#page-title`).

Spring Data calls that method every time `save(…)`, `saveAll(…)`, `delete(…)`, `deleteAll(…)`, `deleteAllInBatch(…)` or `deleteInBatch(…)` is called (`spring-data-commons-domain-events#page-title`).

`deleteById(…)` is absent from that list because an implementation might issue a query that deletes the instance, and then it never has access to the aggregate instance (`spring-data-commons-domain-events#page-title`).

:::judgement{source="Eric Evans, Domain-Driven Design, part II; Vaughn Vernon, Implementing Domain-Driven Design, chapters 6, 8 and 10"}
According to Vaughn Vernon, *Implementing Domain-Driven Design* treats value objects in chapter 6, domain events in chapter 8 and aggregates in chapter 10. According to Eric Evans, the building blocks of *Domain-Driven Design* are covered in part II.
:::

## Key points

- A Spring Modulith module exposes its base package by default; `@NamedInterface` exposes more.
- `verify()` rejects module-level cycles and references to internal packages of other modules.
- ArchUnit evaluates an `ArchRule` against imported classes with `check(importedClasses)`.
- Layer rules in ArchUnit state which layer may access which, and slice rules check slices for cyclic dependencies.
- An aggregate root can publish events from a `@DomainEvents` method, called on `save(…)` and `delete(…)` calls.

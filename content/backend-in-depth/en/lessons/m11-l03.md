# Production debugging and incident triage

## Stack traces and cause chains
<!-- bullets: 11.3.a -->

Instances of `Error` and `Exception` are conventionally used to indicate that exceptional situations have occurred (`javadoc-throwable#class-throwable`).

These instances are typically created in the context of the exceptional situation, so that they include relevant information such as stack trace data (`javadoc-throwable#class-throwable`).

A throwable contains a snapshot of the execution stack of its thread at the time it was created (`javadoc-throwable#class-throwable`).

A throwable can also contain a cause: another throwable that caused it to be constructed (`javadoc-throwable#class-throwable`).

The recording of causal information is referred to as the chained exception facility, because the cause can itself have a cause, leading to a chain of exceptions, each caused by another (`javadoc-throwable#class-throwable`).

The snippet throws a `TimeoutException` in a repository method, wraps it in a service method and wraps that again in a controller method. It then walks the chain of causes from the outermost exception and prints each message with the method that created the exception.

```java snippet=m11-l03/CauseChain.java
import java.util.concurrent.TimeoutException;

public class CauseChain {
    static void repository() throws TimeoutException {
        throw new TimeoutException("pool timeout after 30000 ms");
    }

    static void service() {
        try {
            repository();
        } catch (TimeoutException e) {
            throw new IllegalStateException("could not load order 17", e);
        }
    }

    static void controller() {
        try {
            service();
        } catch (IllegalStateException e) {
            throw new RuntimeException("request failed", e);
        }
    }

    public static void main(String[] args) {
        try {
            controller();
        } catch (RuntimeException caught) {
            for (Throwable t = caught; t != null; t = t.getCause()) {
                System.out.println(t.getMessage() + " (thrown in " + t.getStackTrace()[0].getMethodName() + ")");
            }
        }
    }
}
```

The snippet prints `request failed (thrown in controller)`, `could not load order 17 (thrown in service)` and `pool timeout after 30000 ms (thrown in repository)`, in that order, because each exception was created in the method named on its line.

It prints the root cause last, because the last exception of the chain has no cause of its own.

## Thread dumps
<!-- bullets: 11.3.a -->

A thread dump consists of the thread stack, including the thread state, for all Java threads in the virtual machine (`jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238`).

A thread dump does not terminate the application, which continues after the thread information is printed (`jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238`).

Java threads are printed first in a thread dump, followed by information about VM internal threads (`jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238`).

Each thread entry consists of a header line followed by the thread stack trace (`jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238`).

:::esquema{kind=tabla title="Fields of a thread dump header line"}
| Field | What it gives | Source |
|---|---|---|
| Thread ID (`tid`) | The address of a thread structure in memory | `jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238` |
| Native thread ID (`nid`) | The ID of the native thread | `jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238` |
| Thread state | What the thread was doing at the time of the thread dump | `jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238` |
| Address range | An estimate of the valid stack region for the thread | `jdk-troubleshoot-tools#JSTGD-GUID-489BB790-A7C7-4CF0-9A6B-63FA12230238` |
:::

## Latency percentiles
<!-- bullets: 11.3.a -->

In `wrk`, the `done()` function receives a table of result data and two statistics objects, for the sampled per-request latency and the per-thread request rate (`wrk2-readme#scripting`).

In `wrk`, duration and latency are microsecond values, and rate is measured in requests per second (`wrk2-readme#scripting`).

In `wrk`, `latency:percentile(99.0)` gives the 99th percentile value (`wrk2-readme#scripting`).

In `wrk`, `summary.errors.status` counts the total HTTP status codes greater than 399 (`wrk2-readme#scripting`).

In `wrk`, `summary.errors.timeout` counts the total request timeouts (`wrk2-readme#scripting`).

The snippet holds 100 latencies: 98 of 10 ms and 2 of 1,000 ms. It reads a percentile by the nearest-rank method, the value at rank `ceil(p / 100 * n)` of the sorted samples.

```java snippet=m11-l03/PercentileTail.java
import java.util.Arrays;

public class PercentileTail {
    static int nearestRank(int[] sorted, double percentile) {
        int rank = (int) Math.ceil(percentile / 100 * sorted.length);
        return sorted[rank - 1];
    }

    public static void main(String[] args) {
        int[] latenciesMs = new int[100];
        Arrays.fill(latenciesMs, 0, 98, 10);
        Arrays.fill(latenciesMs, 98, 100, 1000);
        Arrays.sort(latenciesMs);

        System.out.println("mean " + Arrays.stream(latenciesMs).average().orElseThrow());
        System.out.println("p50 " + nearestRank(latenciesMs, 50));
        System.out.println("p98 " + nearestRank(latenciesMs, 98));
        System.out.println("p99 " + nearestRank(latenciesMs, 99));
    }
}
```

The snippet prints `mean 29.8`, which is neither of the two latencies in the data.

It prints `p50 10` and `p98 10`, because ranks 50 and 98 fall among the 98 fast samples.

It prints `p99 1000`, because rank 99 is the first of the two slow samples.

## Connection-pool saturation
<!-- bullets: 11.3.a -->

A pool should be small, a few dozen connections at most, with the rest of the application threads blocked on the pool awaiting connections (`hikaricp-pool-sizing#axiom-you-want-a-small-pool-saturated-with-threads-waiting-for-connections`).

A properly tuned pool is set right at the limit of the number of queries the database can process simultaneously, which is rarely much more than CPU cores times 2 (`hikaricp-pool-sizing#axiom-you-want-a-small-pool-saturated-with-threads-waiting-for-connections`).

A pool of 10,000 connections for 10,000 front-end users would be "shear insanity" (`hikaricp-pool-sizing#axiom-you-want-a-small-pool-saturated-with-threads-waiting-for-connections`).

"Pool-locking" is largely an application-level issue (`hikaricp-pool-sizing#pool-locking`).

Increasing the pool size can alleviate lockups from a single actor that acquires many connections, but the application level should be examined before enlarging the pool (`hikaricp-pool-sizing#pool-locking`).

The pool size that avoids deadlock is `pool size = Tn x (Cm - 1) + 1` (`hikaricp-pool-sizing#pool-locking`).

In that formula, `Tn` is the maximum number of threads and `Cm` is the maximum number of simultaneous connections held by a single thread (`hikaricp-pool-sizing#pool-locking`).

For 3 threads that each need 4 connections, the pool size that makes deadlock impossible is 10 (`hikaricp-pool-sizing#pool-locking`).

For 8 threads that each need 3 connections, the pool size that makes deadlock impossible is 17 (`hikaricp-pool-sizing#pool-locking`).

The formula gives the minimum pool size required to avoid deadlock, which is not necessarily the optimal pool size (`hikaricp-pool-sizing#pool-locking`).

Using a JTA transaction manager can dramatically reduce the number of connections required, by returning the same `Connection` to a thread that already holds one in the current transaction (`hikaricp-pool-sizing#pool-locking`).

The snippet models the pool as a `Semaphore`. Three threads each take 3 permits, wait for each other, and then try to take a fourth for 500 ms. It runs once with the formula minus one permit and once with the formula result.

```java snippet=m11-l03/PoolLocking.java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.CyclicBarrier;
import java.util.concurrent.Semaphore;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class PoolLocking {
    static int threadsThatFinish(int poolSize, int threads, int connectionsPerThread) throws Exception {
        Semaphore pool = new Semaphore(poolSize);
        CyclicBarrier allHoldAllButOne = new CyclicBarrier(threads);
        CountDownLatch outcomes = new CountDownLatch(threads);
        AtomicInteger finished = new AtomicInteger();
        Thread[] workers = new Thread[threads];
        for (int i = 0; i < threads; i++) {
            workers[i] = new Thread(() -> {
                try {
                    int held = connectionsPerThread - 1;
                    pool.acquire(held);
                    allHoldAllButOne.await();
                    boolean gotLast = pool.tryAcquire(500, TimeUnit.MILLISECONDS);
                    if (gotLast) {
                        finished.incrementAndGet();
                        held++;
                    }
                    outcomes.countDown();
                    if (!gotLast) {
                        outcomes.await();
                    }
                    pool.release(held);
                } catch (Exception e) {
                    throw new IllegalStateException(e);
                }
            });
            workers[i].start();
        }
        for (Thread worker : workers) {
            worker.join();
        }
        return finished.get();
    }

    public static void main(String[] args) throws Exception {
        int threads = 3;
        int connectionsPerThread = 4;
        int minimum = threads * (connectionsPerThread - 1) + 1;
        System.out.println("minimum pool " + minimum);
        System.out.println("pool " + (minimum - 1) + ": " + threadsThatFinish(minimum - 1, threads, connectionsPerThread) + " of 3 finish");
        System.out.println("pool " + minimum + ": " + threadsThatFinish(minimum, threads, connectionsPerThread) + " of 3 finish");
    }
}
```

The snippet prints `minimum pool 10` for 3 threads that hold 4 connections each.

It prints `pool 9: 0 of 3 finish`, because every thread holds 3 permits and none is left for the fourth.

It prints `pool 10: 3 of 3 finish`, because one spare permit lets one thread finish and release its permits for the others.

## GC pauses
<!-- bullets: 11.3.a -->

Recordings from Flight Recorder can help diagnose Java application issues with garbage collections (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

To investigate garbage collection issues, take a profiling flight recording without the heap statistics, because they trigger extra old collections (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The `jfr` tool prints the `jdk.GCPhasePause` events that were recorded (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

From the `jdk.GCPhasePause` events, one can calculate the average sum of pauses for each GC, the maximum sum of pauses and the total pause time (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The sum of pauses is the total amount of time that the application was paused during a GC (`jdk-troubleshoot-jfr#JSTGD-GUID-E9C795D6-3D7A-4CD8-84DD-4F7DE3200614`).

For GCs that do most of their work in the background, the length of the GC does not matter and what matters is how long the application actually had to stop (`jdk-troubleshoot-jfr#JSTGD-GUID-E9C795D6-3D7A-4CD8-84DD-4F7DE3200614`).

The main performance problems with garbage collections are usually that individual GCs take too long, or that too much time is spent in paused GCs (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

When an individual GC takes too long, the GC strategy may need to change (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

A Full GC event in a recording indicates that the application needs more memory than was allocated (`jdk-troubleshoot-jfr#JSTGD-GUID-E9C795D6-3D7A-4CD8-84DD-4F7DE3200614`).

The bigger the Java heap, the longer the time between GCs (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

Memory leaks may cause more and more frequent GCs until an `OutOfMemoryError` is thrown (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

To reduce the number of GCs, an application can allocate fewer temporary objects (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The `jdk.ObjectAllocationInNewTLAB` and `jdk.ObjectAllocationOutsideTLAB` events provide information about the allocation of temporary objects (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

To reduce the need of GCs, an application can decrease the allocation rate (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The `jdk.ThreadAllocationStatistics` event provides information about the allocations per thread (`jdk-troubleshoot-jfr#JSTGD-GUID-3839D694-F0F7-4E43-93BE-3BF13F4D2102`).

The snippet groups five pauses by GC identifier and computes the sum of pauses per GC, the total, the largest sum and the average sum.

```java snippet=m11-l03/GcPauseSums.java
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.TreeMap;

public class GcPauseSums {
    record Pause(int gcId, int millis) {}

    public static void main(String[] args) {
        List<Pause> pauses = List.of(
                new Pause(1, 3), new Pause(1, 1),
                new Pause(2, 2),
                new Pause(3, 10), new Pause(3, 1));

        Map<Integer, Integer> sumPerGc = new TreeMap<>();
        for (Pause pause : pauses) {
            sumPerGc.merge(pause.gcId(), pause.millis(), Integer::sum);
        }

        int total = sumPerGc.values().stream().mapToInt(Integer::intValue).sum();
        int largest = sumPerGc.values().stream().mapToInt(Integer::intValue).max().orElseThrow();
        System.out.println("sum of pauses per GC " + sumPerGc);
        System.out.println("total " + total + " ms");
        System.out.println("largest sum " + largest + " ms");
        System.out.printf(Locale.ROOT, "average sum %.2f ms%n", (double) total / sumPerGc.size());
    }
}
```

The snippet prints `sum of pauses per GC {1=4, 2=2, 3=11}`, because GC 3 had pauses of 10 ms and 1 ms.

It prints `total 17 ms` and `largest sum 11 ms`, and the largest single pause is not the same as the largest sum.

It prints `average sum 5.67 ms`, the total divided by the three GCs.

## Consumer lag
<!-- bullets: 11.3.a -->

Kafka has a tool that shows the position of all consumers in a consumer group and how far behind the end of the log they are (`kafka-ops-basic-operations#checking-consumer-position`).

The documentation runs it for a consumer group named `my-group` as `bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group my-group` (`kafka-ops-basic-operations#checking-consumer-position`).

Its output has the columns `TOPIC`, `PARTITION`, `CURRENT-OFFSET`, `LOG-END-OFFSET`, `LAG`, `CONSUMER-ID`, `HOST` and `CLIENT-ID` (`kafka-ops-basic-operations#checking-consumer-position`).

In the documentation's example, partition 0 of `my-topic` shows a `CURRENT-OFFSET` of 2, a `LOG-END-OFFSET` of 4 and a `LAG` of 2 (`kafka-ops-basic-operations#checking-consumer-position`).

## Triage and evidence
<!-- bullets: 11.3.a -->

:::judgement{source="Chris Jones, in Google, Site Reliability Engineering, ch. 12" ref="sre-book-effective-troubleshooting#triage-BVs0truY"}
According to Chris Jones, in chapter 12 of Google's Site Reliability Engineering, the first response in a major outage should not be to look for the root cause. The priority is to make the system work as well as it can, for example by diverting traffic, dropping traffic to prevent a cascading failure or disabling subsystems, while preserving evidence such as logs for the later root-cause analysis.
:::

:::judgement{source="Chris Jones, in Google, Site Reliability Engineering, ch. 12" ref="sre-book-effective-troubleshooting#examine-MQsnhjuB"}
According to the same chapter, the metrics of a monitoring system are a good place to start, and graphing time series can show correlations that suggest where a problem began. Logs show what a process was doing at a given point in time, and tracing requests through the whole stack helps to understand a distributed system.
:::

:::judgement{source="Chris Jones, in Google, Site Reliability Engineering, ch. 12" ref="sre-book-effective-troubleshooting#logging-0bS8hLhruA"}
According to the same chapter, it is useful to have several verbosity levels and a way to raise them on the fly without restarting the process. Depending on the traffic, statistical sampling, such as one operation out of every 1,000, may be better.
:::

:::judgement{source="Andrew Stribblehill, in Google, Site Reliability Engineering, ch. 14" ref="sre-book-managing-incidents#managing-incidents"}
According to Andrew Stribblehill, in chapter 14 of Google's Site Reliability Engineering, effective incident management is key to limiting the disruption caused by an incident and restoring normal business operations as quickly as possible.
:::

## Key points

- A throwable holds a snapshot of the stack of its thread and can hold a cause, so a chain of causes ends at the root cause.
- A thread dump lists the stack and state of all Java threads and does not stop the application.
- In a thread dump header, `tid` is the address of a thread structure, `nid` the ID of the native thread, and the state says what the thread was doing.
- In `wrk`, latencies are in microseconds and `latency:percentile(99.0)` gives the 99th percentile.
- A mean can sit far from every sample: two slow samples in 100 leave the mean at 29.8 ms and move the 99th percentile to 1,000 ms.
- A properly tuned pool is small, near the number of queries the database processes at once, and the other threads wait on it.
- `Tn x (Cm - 1) + 1` is the minimum pool size that makes deadlock impossible, not the optimal size.
- The sum of pauses is the time the application was stopped during a GC; the `jfr` tool prints `jdk.GCPhasePause` events to compute it.
- A bigger heap lengthens the time between GCs, memory leaks shorten it, and fewer temporary objects mean fewer GCs.
- The Kafka tool `kafka-consumer-groups.sh` shows the position of each consumer in a group and how far behind the end of the log it is.

# Spring Data and JPA

## Repositories, queries and projections
<!-- bullets: 5.7.a -->

The central interface in the Spring Data repository abstraction is `Repository` (`spring-data-jpa-repositories-core-concepts#page-title`).

`Repository` acts primarily as a marker interface to capture the types to work with and to help you to discover interfaces that extend it (`spring-data-jpa-repositories-core-concepts#page-title`).

`ListCrudRepository` offers equivalent methods to `CrudRepository`, but they return `List` where the `CrudRepository` methods return an `Iterable` (`spring-data-jpa-repositories-core-concepts#page-title`).

Parsing query method names is divided into subject and predicate (`spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-creation`).

The first `By` in a query method name acts as a delimiter to indicate the start of the actual criteria predicate (`spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-creation`).

The supported operators in derived queries can vary by datastore (`spring-data-jpa-repositories-query-methods-details#repositories.query-methods.query-creation`).

Queries annotated to the query method take precedence over queries defined using `@NamedQuery` or named queries declared in `orm.xml` (`spring-data-jpa-query-methods#jpa.query-methods.at-query`).

Using `@Query` frees the domain class from persistence specific information and co-locates the query to the repository interface (`spring-data-jpa-query-methods#jpa.query-methods.at-query`).

For an interface-based projection, the query execution engine creates proxy instances of that interface at runtime for each element returned and forwards calls to the exposed methods to the target object (`spring-data-jpa-projections#projections.interfaces`).

Projections can be used recursively (`spring-data-jpa-projections#projections.interfaces`).

Class-based projections can be used in exactly the same way as projection interfaces, except that no proxying happens and no nested projections can be applied (`spring-data-jpa-projections#projections.dtos`).

If the store optimizes the query execution by limiting the fields to be loaded, the fields to be loaded are determined from the parameter names of the constructor that is exposed (`spring-data-jpa-projections#projections.dtos`).

The `Specification` interface is tied to a particular query type (select, update, delete) as per Criteria API restrictions (`spring-data-jpa-specifications#specification-interfaces`).

## The persistence context, entity states and flushing
<!-- bullets: 5.7.b -->

Both the `org.hibernate.Session` API and the `jakarta.persistence.EntityManager` API represent a context for dealing with persistent data (`hibernate-user-guide#pc`).

This concept is called a persistence context (`hibernate-user-guide#pc`).

A new entity instance has no persistent identity, and is not yet associated with a persistence context (`jakarta-persistence-spec#a1929`).

A managed entity instance is an instance with a persistent identity that is currently associated with a persistence context (`jakarta-persistence-spec#a1929`).

A detached entity instance is an instance with a persistent identity that is not, or no longer, associated with a persistence context (`jakarta-persistence-spec#a1929`).

A removed entity instance is an instance with a persistent identity, associated with a persistence context, that will be removed from the database upon transaction commit (`jakarta-persistence-spec#a1929`).

The dirty checking mechanism is responsible for determining if a managed entity has been modified since it was first loaded (`hibernate-user-guide#flushing-order`).

By default, Hibernate uses the `AUTO` flush mode, which triggers a flush prior to committing a `Transaction` (`hibernate-user-guide#flushing-auto`).

The `AUTO` flush mode also triggers a flush before executing any native SQL query that has no registered synchronization (`hibernate-user-guide#flushing-auto`).

Hibernate does not execute the SQL statements in the order of their associated entity state operations (`hibernate-user-guide#flushing-order`).

Even if you remove the first entity and then persist a new one, Hibernate is going to execute the `DELETE` statement after the `INSERT` (`hibernate-user-guide#flushing-order`).

The order in which SQL statements are executed is given by the `ActionQueue` and not by the order in which entity state operations have been previously defined (`hibernate-user-guide#flushing-order`).

By default, the lifetime of the persistence context of a container-managed entity manager corresponds to the scope of a transaction (`jakarta-persistence-spec#a2027`).

An extended persistence context exists from the time the `EntityManager` instance is created until it is closed (`jakarta-persistence-spec#a2027`).

If an entity has a version property of non-primitive type, Spring Data JPA considers the entity new if the value of that property is `null` (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

Without a version property, Spring Data JPA inspects the identifier property of the given entity (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

If an entity implements `Persistable`, Spring Data JPA delegates the new detection to the `isNew(…)` method of the entity (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

The `Persistable.isNew()` flag tells Spring Data repositories whether to call `EntityManager.persist()` or `merge()` (`spring-data-jpa-entity-persistence#jpa.entity-persistence.saving-entities.strategies`).

If you are running a web application, Spring Boot by default registers `OpenEntityManagerInViewInterceptor` to apply the “Open EntityManager in View” pattern, to allow for lazy loading in web views (`spring-boot-data-sql#data.sql.jpa-and-spring-data.open-entity-manager-in-view`).

To turn off this behaviour, set `spring.jpa.open-in-view` to `false` in your `application.properties` (`spring-boot-data-sql#data.sql.jpa-and-spring-data.open-entity-manager-in-view`).

## Auditing, optimistic locking and batching
<!-- bullets: 5.7.c -->

Spring Data provides `@CreatedBy` and `@LastModifiedBy` to capture the user who created or modified the entity, and `@CreatedDate` and `@LastModifiedDate` to capture when the change happened (`spring-data-jpa-auditing#auditing.annotations`).

By default, the `DateTimeProvider` that gives the time is a `CurrentDateTimeProvider` (`spring-data-jpa-auditing#auditing.annotations`).

The auditing feature requires `spring-aspects.jar` to be on the classpath (`spring-data-jpa-auditing#jpa.auditing.configuration`).

If you expose a bean of type `AuditorAware` to the `ApplicationContext`, the auditing infrastructure automatically picks it up and uses it to determine the current user to be set on domain types (`spring-data-jpa-auditing#jpa.auditing.configuration`).

You can enable auditing by annotating a configuration class with the `@EnableJpaAuditing` annotation (`spring-data-jpa-auditing#jpa.auditing.configuration`).

A query method annotated with `@Lock` is equipped with the `LockModeType` given to the annotation, for example `READ` (`spring-data-jpa-locking#page-title`).

The version number mechanism for optimistic locking is provided through a `@Version` annotation (`hibernate-user-guide#locking-optimistic-version-number`).

The entity manager uses the version property to detect conflicting updates, and prevent the loss of updates that would otherwise be overwritten by a last-commit-wins strategy (`hibernate-user-guide#locking-optimistic-version-number`).

Your application is forbidden from altering the version number set by Hibernate (`hibernate-user-guide#locking-optimistic-version-number`).

The entity version must be updated by the persistence provider each time the state of an entity instance is written to the database (`jakarta-persistence-spec#a2059`).

The timing of the version check for a detached entity instance that is merged is provider-dependent (`jakarta-persistence-spec#a2059`).

If an update or merge operation involves entities without versions, the absence of a version does not impede completion of the operation (`jakarta-persistence-spec#a2059`).

JDBC offers support for batching together SQL statements that can be represented as a single `PreparedStatement` (`hibernate-user-guide#batch-jdbcbatch`).

`hibernate.jdbc.batch_size` controls the maximum number of statements Hibernate will batch together before asking the driver to execute the batch (`hibernate-user-guide#batch-jdbcbatch`).

A `hibernate.jdbc.batch_size` of zero or a negative number disables batching (`hibernate-user-guide#batch-jdbcbatch`).

`hibernate.order_updates` forces Hibernate to order SQL updates by the entity type and the primary key value of the items being updated (`hibernate-user-guide#batch-jdbcbatch`).

`hibernate.order_inserts` forces Hibernate to order inserts to allow for more batching to be used (`hibernate-user-guide#batch-jdbcbatch`).

Since version 5.2, Hibernate allows overriding the global JDBC batch size on a per `Session` basis (`hibernate-user-guide#batch-jdbcbatch`).

## Key points

- `Repository` is the central marker interface of Spring Data, and `ListCrudRepository` returns `List` where `CrudRepository` returns `Iterable`.
- Query method names are parsed into a subject and a predicate, and the first `By` starts the predicate.
- A query annotated with `@Query` takes precedence over `@NamedQuery` and `orm.xml` named queries.
- Class-based projections need no proxying and cannot be nested, while interface-based projections are proxied at runtime.
- An entity is new, managed, detached or removed in relation to a persistence context.
- Hibernate executes SQL statements in the order given by the `ActionQueue`, so a `DELETE` follows an `INSERT` even if the entity was removed first.
- In a web application, Spring Boot registers `OpenEntityManagerInViewInterceptor` by default, and `spring.jpa.open-in-view` set to `false` turns it off.
- `@Version` lets the entity manager detect conflicting updates, and the application must not alter the version number.
- `hibernate.jdbc.batch_size` sets the maximum batch size, and zero or a negative number disables batching.

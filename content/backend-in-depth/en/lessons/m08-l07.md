# Stream processing

## Batch versus stream; event time versus processing time
<!-- bullets: 8.7.a -->

It is impossible to count all elements in a stream, because streams are in general infinite (`flink-time#windowing`).

Aggregates on streams are scoped by windows, such as the count over the last 5 minutes or the sum of the last 100 elements (`flink-time#windowing`).

Flink executes batch programs as a special case of streaming programs, where the streams are bounded (`flink-stateful-stream-processing#state-and-fault-tolerance-in-batch-programs`).

Fault tolerance for batch programs does not use checkpointing, and recovery happens by fully replaying the streams (`flink-stateful-stream-processing#state-and-fault-tolerance-in-batch-programs`).

Replaying the streams is possible because the inputs are bounded (`flink-stateful-stream-processing#state-and-fault-tolerance-in-batch-programs`).

Processing time refers to the system time of the machine that is executing the respective operation (`flink-time#notions-of-time-event-time-and-processing-time`).

Processing time is the simplest notion of time, with the best performance and the lowest latency (`flink-time#notions-of-time-event-time-and-processing-time`).

In distributed and asynchronous environments processing time does not provide determinism (`flink-time#notions-of-time-event-time-and-processing-time`).

Event time is the time that each individual event occurred on its producing device (`flink-time#notions-of-time-event-time-and-processing-time`).

In event time, the progress of time depends on the data, not on any wall clocks (`flink-time#notions-of-time-event-time-and-processing-time`).

Unless events are known to arrive in order, event time processing incurs some latency while waiting for out-of-order events (`flink-time#notions-of-time-event-time-and-processing-time`).

Kafka Streams defines ingestion time as the point in time when a record is stored in a topic partition by a Kafka broker (`kafka-streams-core-concepts#time`).

Kafka Streams assigns a timestamp to every data record via the `TimestampExtractor` interface (`kafka-streams-core-concepts#time`).

The time of a Kafka Streams application only advances when a new record arrives at the processor (`kafka-streams-core-concepts#time`).

## Windows, watermarks, late data and grace periods
<!-- bullets: 8.7.b -->

Tumbling windows model fixed-size, non-overlapping, gap-less windows (`kafka-streams-dsl-api#tumbling-time-windows`).

A tumbling window is a hopping window whose window size is equal to its advance interval (`kafka-streams-dsl-api#tumbling-time-windows`).

Since tumbling windows never overlap, a data record will belong to one and only one window (`kafka-streams-dsl-api#tumbling-time-windows`).

Tumbling windows are aligned to the epoch, with an inclusive lower bound and an exclusive upper bound (`kafka-streams-dsl-api#tumbling-time-windows`).

A hopping window is defined by two properties, the window's size and its advance interval (`kafka-streams-dsl-api#hopping-time-windows`).

Since hopping windows can overlap, a data record may belong to more than one window (`kafka-streams-dsl-api#hopping-time-windows`).

Kafka Streams follows the academic terminology, where sliding windows have different semantics from hopping windows (`kafka-streams-dsl-api#hopping-time-windows`).

Hopping windows are aligned to the epoch (`kafka-streams-dsl-api#hopping-time-windows`).

Sliding windows are aligned to the data record timestamps, not to the epoch (`kafka-streams-dsl-api#sliding-time-windows`).

Sessions represent a period of activity separated by a defined gap of inactivity (`kafka-streams-dsl-api#session-windows`).

Events that fall within the inactivity gap of existing sessions are merged into the existing sessions (`kafka-streams-dsl-api#session-windows`).

An event that falls outside of the session gap creates a new session (`kafka-streams-dsl-api#session-windows`).

:::esquema{kind=tabla title="Four window types in Kafka Streams"}
| Window | Property | Source |
|---|---|---|
| Tumbling | Fixed-size, non-overlapping, gap-less windows | `kafka-streams-dsl-api#tumbling-time-windows` |
| Hopping | Fixed-sized, possibly overlapping windows | `kafka-streams-dsl-api#hopping-time-windows` |
| Sliding | A fixed-size window that slides continuously over the time axis | `kafka-streams-dsl-api#sliding-time-windows` |
| Session | Key-based events aggregated into sessions separated by a gap of inactivity | `kafka-streams-dsl-api#session-windows` |
:::

In Kafka Streams, windowed computations update their results continuously (`kafka-streams-dsl-api#window-final-results`).

With a 10-minute grace period, the 09:00 to 10:00 window accepts out-of-order records until 10:10, at which point the window is closed (`kafka-streams-dsl-api#window-final-results`).

The grace period bounds the lateness of events that the window will accept (`kafka-streams-dsl-api#window-final-results`).

`Suppressed.untilWindowCloses` emits nothing for a window until it closes, and then emits the final result (`kafka-streams-dsl-api#window-final-results`).

In Flink the mechanism to measure progress in event time is watermarks (`flink-time#event-time-and-watermarks`).

A `Watermark(t)` declares that event time has reached time t in that stream, so no more elements with a timestamp at or below t should arrive (`flink-time#event-time-and-watermarks`).

Event time can progress independently of processing time (`flink-time#event-time-and-watermarks`).

An operator with several input streams has a current event time equal to the minimum of its input streams' event times (`flink-time#watermarks-in-parallel-streams`).

Late elements are elements that arrive after the event time clock, as signaled by the watermarks, has passed the time of their timestamp (`flink-time#lateness`).

Delaying the watermarks by too much is often not desirable, because it causes too much delay in the evaluation of event time windows (`flink-time#lateness`).

In Kafka Streams, out-of-order data could make stateful operations such as aggregations and joins incorrect (`kafka-streams-core-concepts#out-of-order-handling`).

For Stream-Stream joins, all three types handle out-of-order records correctly (`kafka-streams-core-concepts#out-of-order-handling`).

Flink comes with pre-defined tumbling, sliding, session and global window assigners (`flink-windows#window-assigners`).

Flink time-based windows have an inclusive start timestamp and an exclusive end timestamp (`flink-windows#window-assigners`).

## Stateful processing: state stores, changelog topics and recovery
<!-- bullets: 8.7.c -->

Operations that remember information across multiple events, such as window operators, are called stateful (`flink-stateful-stream-processing#what-is-state`).

When aggregating events per minute, hour or day, the state holds the pending aggregates (`flink-stateful-stream-processing#what-is-state`).

Every task in Kafka Streams embeds one or more state stores (`kafka-streams-core-concepts#states`).

State stores can be a persistent key-value store, an in-memory hashmap, or another convenient data structure (`kafka-streams-core-concepts#states`).

The Kafka Streams DSL automatically creates and manages state stores when stateful operators such as `join()` or `aggregate()` are called or a stream is windowed (`kafka-streams-architecture#local-state-stores`).

For each state store, Kafka Streams maintains a replicated changelog Kafka topic in which it tracks any state updates (`kafka-streams-architecture#fault-tolerance`).

Log compaction is enabled on the changelog topics so that old data can be purged safely (`kafka-streams-architecture#fault-tolerance`).

After a failure, Kafka Streams restores the state stores to their content before the failure by replaying the changelog topics before it resumes processing (`kafka-streams-architecture#fault-tolerance`).

Standby replicas are fully replicated copies of the state that minimize the restoration time (`kafka-streams-architecture#fault-tolerance`).

Starting in 2.6, Kafka Streams assigns a task only to an instance with a fully caught-up local copy of the state, if such an instance exists (`kafka-streams-architecture#fault-tolerance`).

`acceptable.recovery.lag` is the maximum lag, in offsets to catch up from the changelog, for an instance to be considered caught-up (`kafka-streams-config#acceptablerecoverylag`).

Since Kafka 4.3, Kafka Streams stores each persistent store's changelog offset inside RocksDB rather than in a per-task `.checkpoint` file (`kafka-streams-memory-mgmt#rocksdb-offset-durability`).

Flink implements fault tolerance using a combination of stream replay and checkpointing (`flink-stateful-stream-processing#state-persistence`).

A checkpoint marks a specific point in each of the input streams along with the corresponding state for each of the operators (`flink-stateful-stream-processing#state-persistence`).

Upon a failure, Flink selects the latest completed checkpoint k and gives each operator the state snapshotted as part of it (`flink-stateful-stream-processing#recovery`).

After recovery the sources start reading the stream from position Sk (`flink-stateful-stream-processing#recovery`).

## Kafka Streams: KStream, KTable, joins and co-partitioning
<!-- bullets: 8.7.d -->

A `KStream` is an abstraction of a record stream, where each data record represents a self-contained datum in the unbounded data set (`kafka-streams-dsl-api#kstream`).

Summing the values per user over a `KStream` of (alice, 1) and (alice, 3) returns 4 for alice (`kafka-streams-dsl-api#kstream`).

In a `KStream` the second record would not be considered an update of the previous record (`kafka-streams-dsl-api#kstream`).

A `KTable` is an abstraction of a changelog stream, where each data record represents an update (`kafka-streams-dsl-api#ktable`).

In a `KTable` a record with a null value represents a delete, or tombstone, for the record's key (`kafka-streams-dsl-api#ktable`).

Log compaction is safe for a `KTable` but a mistake for a `KStream` (`kafka-streams-dsl-api#ktable`).

A stream can be viewed as a table, and a table can be viewed as a stream (`kafka-streams-core-concepts#duality-of-streams-and-tables`).

:::esquema{kind=tabla title="Join types in Kafka Streams"}
| Join | Type | Inner | Left | Outer | Source |
|---|---|---|---|---|---|
| KStream-to-KStream | Windowed | Supported | Supported | Supported | `kafka-streams-dsl-api#joining` |
| KTable-to-KTable | Non-windowed | Supported | Supported | Supported | `kafka-streams-dsl-api#joining` |
| KTable-to-KTable foreign-key | Non-windowed | Supported | Supported | Not supported | `kafka-streams-dsl-api#joining` |
| KStream-to-KTable | Non-windowed | Supported | Supported | Not supported | `kafka-streams-dsl-api#joining` |
:::

For equi-joins, input data must be co-partitioned when joining (`kafka-streams-dsl-api#join-co-partitioning-requirements`).

The input topics of the join, left side and right side, must have the same number of partitions (`kafka-streams-dsl-api#join-co-partitioning-requirements`).

Co-partitioning is not required for KTable-KTable foreign-key joins and Global KTable joins (`kafka-streams-dsl-api#join-co-partitioning-requirements`).

At runtime Kafka Streams verifies that both sides of a join have the same number of partitions, and throws a `TopologyBuilderException` if they do not (`kafka-streams-dsl-api#join-co-partitioning-requirements`).

Kafka Streams cannot verify whether the partitioning strategy matches between the inputs of a join (`kafka-streams-dsl-api#join-co-partitioning-requirements`).

Each stream partition maps to a Kafka topic partition (`kafka-streams-architecture#stream-partitions-and-tasks`).

Kafka Streams creates a fixed number of tasks based on the input stream partitions, and the assignment of partitions to tasks never changes (`kafka-streams-architecture#stream-partitions-and-tasks`).

With an input topic of 5 partitions you can run up to 5 application instances (`kafka-streams-architecture#stream-partitions-and-tasks`).

Excess application instances launch but remain idle (`kafka-streams-architecture#stream-partitions-and-tasks`).

The topology optimizations include moving or reducing repartition topics and reusing the source topic as the changelog for source KTables (`kafka-streams-config#topologyoptimization`).

Enabling optimizations also requires passing the same `Properties` object to `StreamsBuilder.build(Properties)` (`kafka-streams-config#topologyoptimization`).

## Exactly-once processing: idempotent producers and Kafka transactions
<!-- bullets: 8.7.e -->

At most once means messages may be lost but are never redelivered (`kafka-design#message-delivery-semantics`).

At least once means messages are never lost but may be redelivered (`kafka-design#message-delivery-semantics`).

Exactly once means each message is processed once and only once (`kafka-design#message-delivery-semantics`).

Since 0.11.0.0 the Kafka producer supports an idempotent delivery option that guarantees resending does not result in duplicate entries in the log (`kafka-design#message-delivery-semantics`).

The broker assigns each producer an ID and deduplicates messages using a sequence number sent with every message (`kafka-design#message-delivery-semantics`).

The producer can send messages atomically to multiple topic partitions using transactions, so that either all messages are written or none (`kafka-design#message-delivery-semantics`).

With `enable.idempotence` set to true, the producer ensures that exactly one copy of each message is written in the stream (`kafka-producer-configs#enable.idempotence`).

Idempotence requires `acks` to be `all` (`kafka-producer-configs#enable.idempotence`).

Idempotence is enabled by default if no conflicting configurations are set (`kafka-producer-configs#enable.idempotence`).

If idempotence is explicitly enabled and conflicting configurations are set, a `ConfigException` is thrown (`kafka-producer-configs#enable.idempotence`).

Without a `transactional.id` the producer is limited to idempotent delivery (`kafka-producer-configs#transactional.id`).

If a `transactional.id` is configured, `enable.idempotence` is implied (`kafka-producer-configs#transactional.id`).

By default the transactional id is not configured, which means transactions cannot be used (`kafka-producer-configs#transactional.id`).

In Kafka the consumer and producer are separate, and only the producer is transactional (`kafka-design#using-transactions`).

The producer makes transactional updates to the consumer's position, the committed offset, which gives the overall exactly-once behavior (`kafka-design#using-transactions`).

The consumer configuration must include `isolation.level=read_committed` and `enable.auto.commit=false` (`kafka-design#using-transactions`).

A consumer that does not use read-committed isolation sees records from aborted transactions and from open transactions (`kafka-design#using-transactions`).

To handle transactions properly with rebalancing, it is advisable to use one producer instance for each consumer instance (`kafka-design#using-transactions`).

Kafka Streams guarantees that the processing result of any record read from the source topics is reflected exactly once in the output topic and in the state stores (`kafka-streams-core-concepts#processing-guarantees`).

Kafka Streams completes commits on the input topic offsets, updates on the state stores, and writes to the output topics atomically (`kafka-streams-core-concepts#processing-guarantees`).

Exactly-once v2 needs broker version 2.5.0 or newer (`kafka-streams-core-concepts#processing-guarantees`).

The possible values of `processing.guarantee` are `at_least_once`, which is the default, and `exactly_once_v2` (`kafka-streams-config#processingguarantee`).

With exactly-once processing enabled, the default of `commit.interval.ms` changes to 100ms (`kafka-streams-config#processingguarantee`).

With exactly-once processing enabled, consumers are configured with `isolation.level="read_committed"` and producers with `enable.idempotence=true` by default (`kafka-streams-config#processingguarantee`).

By default exactly-once processing requires a cluster of at least three brokers (`kafka-streams-config#processingguarantee`).

With exactly-once processing enabled, Kafka Streams sets `transaction.timeout.ms` to 10000 by default (`kafka-streams-config#processingguarantee`).

Since Kafka 4.0 the producer epoch is bumped on every transaction (`kafka-transaction-protocol#overview`).

## Apache Flink as a reference: checkpoints, savepoints and back pressure
<!-- bullets: 8.7.f -->

In order to make state fault tolerant, Flink needs to checkpoint the state (`flink-checkpointing#checkpointing`).

Checkpoints allow Flink to recover state and positions in the streams to give the application the same semantics as a failure-free execution (`flink-checkpointing#checkpointing`).

By default, checkpointing is disabled in Flink (`flink-stateful-stream-processing#state-persistence`).

The checkpoint interval trades off the overhead of fault tolerance during execution against the recovery time (`flink-stateful-stream-processing#state-persistence`).

The data stream source must be able to rewind the stream to a defined recent point for the mechanism to realize its full guarantees (`flink-stateful-stream-processing#state-persistence`).

Barriers never overtake records, they flow strictly in line (`flink-stateful-stream-processing#barriers`).

A barrier separates the records into the set that goes into the current snapshot and the set that goes into the next snapshot (`flink-stateful-stream-processing#barriers`).

Each barrier carries the ID of the snapshot whose records it pushed in front of it (`flink-stateful-stream-processing#barriers`).

Barriers do not interrupt the flow of the stream and are hence very lightweight (`flink-stateful-stream-processing#barriers`).

After all sinks have acknowledged a snapshot, it is considered completed (`flink-stateful-stream-processing#barriers`).

The alignment step may add latency to the streaming program (`flink-stateful-stream-processing#exactly-once-vs-at-least-once`).

Flink has a switch to skip the stream alignment during a checkpoint (`flink-stateful-stream-processing#exactly-once-vs-at-least-once`).

When the alignment is skipped, records that belong to checkpoint n+1 occur as duplicates on a restore (`flink-stateful-stream-processing#exactly-once-vs-at-least-once`).

Dataflows with only embarrassingly parallel operations give exactly once guarantees even in at least once mode (`flink-stateful-stream-processing#exactly-once-vs-at-least-once`).

A savepoint is a consistent image of the execution state of a streaming job, created via Flink's checkpointing mechanism (`flink-savepoints#what-is-a-savepoint`).

Savepoints can be used to stop-and-resume, fork, or update Flink jobs (`flink-savepoints#what-is-a-savepoint`).

Savepoints differ from checkpoints the way backups differ from recovery logs in traditional database systems (`flink-checkpoints-vs-savepoints#overview`).

:::esquema{kind=tabla title="Checkpoint and savepoint compared"}
| Aspect | Checkpoint | Savepoint | Source |
|---|---|---|---|
| Purpose | A recovery mechanism in case of unexpected job failures | Planned, manual operations such as updating Flink or changing the job graph | `flink-checkpoints-vs-savepoints#overview` |
| Owner | Created, owned and released by Flink | Created, owned and deleted solely by the user | `flink-checkpoints-vs-savepoints#overview` |
| After the job ends | Deleted if the user terminates the application, unless configured to be retained | Not deleted by Flink after job termination or restore | `flink-checkpoints-vs-savepoints#overview` |
:::

A back pressure warning for a task means it is producing data faster than the downstream operators can consume (`flink-back-pressure#back-pressure`).

Back pressure is propagated in the opposite direction of the records, up the stream (`flink-back-pressure#back-pressure`).

The back pressure status HIGH means a subtask is back pressured more than 50% and up to 100% of the time (`flink-back-pressure#back-pressure-status`).

## Key points

- A stream is unbounded, so aggregates over it are scoped by windows; Flink runs batch programs as the special case of bounded streams.
- Processing time is the system time of the executing machine, and event time is the time the event occurred on its producing device.
- A tumbling window puts a record in one and only one window, and a hopping window can put it in more than one.
- A session window ends after a defined gap of inactivity, and an event outside the gap creates a new session.
- A watermark declares that event time has reached time t, and an operator with several inputs takes the minimum of their event times.
- A grace period bounds how late an event the window will accept can be; with a 10-minute grace period the 09:00 to 10:00 window accepts records until 10:10.
- Kafka Streams keeps state in state stores backed by changelog topics, and replays the changelog to restore a store after a failure.
- A `KStream` treats each record as an insert, while a `KTable` treats each record as an update and a null value as a delete.
- An equi-join needs co-partitioned inputs with the same number of partitions, and Kafka Streams cannot verify that the partitioning strategy matches.
- Kafka Streams creates a fixed number of tasks from the input partitions, so instances beyond that number stay idle.
- Setting `processing.guarantee` to `exactly_once_v2` makes Kafka Streams commit offsets, state store updates and output writes atomically.
- An idempotent producer deduplicates with a producer ID and sequence numbers; a transactional producer needs a `transactional.id`, and its consumers should use `read_committed`.
- A Flink checkpoint is owned by Flink and used for recovery; a savepoint is owned by the user and used for planned operations.
- Skipping the stream alignment in a Flink checkpoint trades exactly-once for lower latency, and records can occur as duplicates after a restore.

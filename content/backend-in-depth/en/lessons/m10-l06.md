In the Top 10:2025, 100% of the applications tested were found to have some form of broken access control (`owasp-top10-2025-a01#background`).

Access control enforces policy such that users cannot act outside of their intended permissions (`owasp-top10-2025-a01#description`).

An injection vulnerability is an application flaw that allows untrusted user input to be sent to an interpreter and causes the interpreter to execute parts of that input as commands (`owasp-top10-2025-a05#description`).

The API1:2023 risk, Broken Object Level Authorization, calls for object level authorization checks in every function that accesses a data source using an ID from the user (`owasp-api-top10-2023#owasp-top-10-api-security-risks-2023`).

API3:2023, Broken Object Property Level Authorization, combines API3:2019 Excessive Data Exposure and API6:2019 Mass Assignment, focusing on the lack of or improper authorization validation at the object property level (`owasp-api-top10-2023#owasp-top-10-api-security-risks-2023`).

API7:2023, Server Side Request Forgery, can occur when an API fetches a remote resource without validating the user-supplied URI (`owasp-api-top10-2023#owasp-top-10-api-security-risks-2023`).

## Broken access control
<!-- bullets: 10.6.b -->

Failures of access control typically lead to unauthorized information disclosure, modification or destruction of all data, or performing a business function outside the user's limits (`owasp-top10-2025-a01#description`).

Permitting viewing or editing someone else's account by providing its unique identifier is an insecure direct object reference (`owasp-top10-2025-a01#description`).

Insecure Direct Object Reference (IDOR) is a vulnerability that arises when attackers can access or modify objects by manipulating identifiers used in a web application's URLs or parameters (`owasp-cs-idor#introduction`).

An IDOR occurs due to missing access control checks, which fail to verify whether a user should be allowed to access specific data (`owasp-cs-idor#introduction`).

An IDOR has three ingredients: an object, a reference to that object, and a missing object-level authorization check (`owasp-cs-idor#introduction`).

In the Spring Boot example, the `{id}` path variable is controlled by the requester and flows directly into `findById()` (`owasp-cs-idor#java-and-spring-boot-example`).

In that example nothing verifies that the returned document belongs to the currently authenticated user, so any user who can guess or obtain a valid identifier can read another user's document (`owasp-cs-idor#java-and-spring-boot-example`).

Attackers can exploit API endpoints that are vulnerable to broken object-level authorization by manipulating the ID of an object that is sent within the request (`owasp-api1-bola#api12023-broken-object-level-authorization`).

Object IDs can be anything from sequential integers, UUIDs, or generic strings (`owasp-api1-bola#api12023-broken-object-level-authorization`).

Every API endpoint that receives an ID of an object, and performs any action on the object, should implement object-level authorization checks (`owasp-api1-bola#is-the-api-vulnerable`).

The object-level checks should validate that the logged-in user has permissions to perform the requested action on the requested object (`owasp-api1-bola#is-the-api-vulnerable`).

Comparing the user ID of the current session with the vulnerable ID parameter is not a sufficient solution to Broken Object Level Authorization (`owasp-api1-bola#is-the-api-vulnerable`).

Reaching an API endpoint or function the attacker should not have access to is Broken Function Level Authorization (BFLA) rather than BOLA (`owasp-api1-bola#is-the-api-vulnerable`).

APIs tend to expose endpoints that return all object’s properties (`owasp-api3-bopla#api32023-broken-object-property-level-authorization`).

When exposing an object through an API endpoint, make sure that the user should have access to the object's properties you expose (`owasp-api3-bopla#how-to-prevent`).

Avoid generic methods such as `to_json()` and `to_string()`, and cherry-pick the specific object properties you want to return (`owasp-api3-bopla#how-to-prevent`).

If possible, avoid functions that automatically bind a client's input into code variables, internal objects, or object properties (`owasp-api3-bopla#how-to-prevent`).

Allow changes only to the object's properties that should be updated by the client (`owasp-api3-bopla#how-to-prevent`).

A schema-based response validation mechanism is an extra layer of security that defines and enforces the data returned by all API methods (`owasp-api3-bopla#how-to-prevent`).

Software frameworks sometimes allow developers to automatically bind HTTP request parameters into program code variables or objects (`owasp-cs-mass-assignment#definition`).

Attackers can use this binding to create new parameters that the developer never intended, which creates or overwrites variables or objects in program code (`owasp-cs-mass-assignment#definition`).

:::esquema{kind=tabla title="Names of the mass assignment vulnerability"}
| Name | Language or framework | Source |
|---|---|---|
| Mass Assignment | Ruby on Rails, NodeJS | `owasp-cs-mass-assignment#alternative-names` |
| Autobinding | Spring MVC, ASP NET MVC | `owasp-cs-mass-assignment#alternative-names` |
| Object injection | PHP | `owasp-cs-mass-assignment#alternative-names` |
:::

Permission should be validated correctly on every request, regardless of whether the request was initiated by an AJAX script, server-side, or any other source (`owasp-cs-authorization#validate-the-permissions-on-every-request`).

The technology used to perform permission checks should allow global, application-wide configuration rather than needing to be applied individually to every method or class (`owasp-cs-authorization#validate-the-permissions-on-every-request`).

Even if a single access control check is missed, the confidentiality or integrity of a resource can be jeopardized (`owasp-cs-authorization#validate-the-permissions-on-every-request`).

Validating permissions correctly on just the majority of requests is insufficient (`owasp-cs-authorization#validate-the-permissions-on-every-request`).

Java/Jakarta EE Filters, including implementations in Spring Security, can help developers perform consistent permission checks (`owasp-cs-authorization#validate-the-permissions-on-every-request`).

## Injection, SSRF, deserialization and path traversal
<!-- bullets: 10.6.c -->

The best means to prevent injection requires keeping data separate from commands and queries (`owasp-top10-2025-a05#how-to-prevent`).

The preferred option against injection is a safe API that avoids the interpreter entirely, provides a parameterized interface, or migrates to Object Relational Mapping Tools (ORMs) (`owasp-top10-2025-a05#how-to-prevent`).

Positive server-side input validation is not a complete defense against injection, because many applications require special characters (`owasp-top10-2025-a05#how-to-prevent`).

SQL structures such as table names and column names cannot be escaped, so user-supplied structure names are dangerous (`owasp-top10-2025-a05#how-to-prevent`).

For SQL requests that include dynamic data, the preferred pattern is parameterized queries (`owasp-cs-sql-injection#primary-defenses`).

For structural parts of a query that cannot be parameterized, such as table names, column names and sort direction, map user choices to a strict allow-list of fixed, application-owned values (`owasp-cs-sql-injection#primary-defenses`).

Relying on manually escaping dynamic inputs is error-prone and is strongly discouraged (`owasp-cs-sql-injection#primary-defenses`).

Notable CWEs in A01:2025 include CWE-918 Server-Side Request Forgery (SSRF) and CWE-352 Cross-Site Request Forgery (CSRF) (`owasp-top10-2025-a01#background`).

Exploiting SSRF requires the attacker to find an API endpoint that accesses a URI provided by the client (`owasp-api7-ssrf#api72023-server-side-request-forgery`).

Successful SSRF exploitation might lead to internal services enumeration, information disclosure, bypassing firewalls, or other security mechanisms (`owasp-api7-ssrf#api72023-server-side-request-forgery`).

SSRF is an attack vector that abuses an application to interact with the internal or external network or the machine itself (`owasp-cs-ssrf#context`).

To prevent SSRF, isolate the resource fetching mechanism in your network (`owasp-api7-ssrf#how-to-prevent`).

To prevent SSRF, use allow lists of remote origins users are expected to download resources from, URL schemes and ports, and accepted media types (`owasp-api7-ssrf#how-to-prevent`).

To prevent SSRF, disable HTTP redirections (`owasp-api7-ssrf#how-to-prevent`).

To prevent SSRF, use a well-tested and maintained URL parser to avoid issues caused by URL parsing inconsistencies (`owasp-api7-ssrf#how-to-prevent`).

To prevent SSRF, do not send raw responses to clients (`owasp-api7-ssrf#how-to-prevent`).

An `InetAddressFilter` only allows outgoing calls of a Spring Boot HTTP client to addresses that match the filter (`spring-boot-io-rest-client#io.rest-client.global-configuration.inetaddress-filtering`).

The `InetAddressFilter` only filters requests that originate from your Spring Boot application, so it does not restrict calls that a configured proxy makes on your behalf (`spring-boot-io-rest-client#io.rest-client.global-configuration.inetaddress-filtering`).

For Java's Serializable format, configure serialization filters with an application-specific class allowlist and resource limits before reading objects (`owasp-cs-deserialization#java`).

Overriding `ObjectInputStream.resolveClass()` restricts ordinary class resolution during deserialization (`owasp-cs-deserialization#harden-your-own-javaioobjectinputstream`).

A `resolveClass()` allowlist does not check every object, because the serialization specification handles strings separately and resolves dynamic proxy class descriptors through `resolveProxyClass()` (`owasp-cs-deserialization#harden-your-own-javaioobjectinputstream`).

Serialization filtering combines a class allowlist with limits on graph depth, references, array lengths and stream bytes (`owasp-cs-deserialization#harden-your-own-javaioobjectinputstream`).

The serialized input size must be bounded separately, because filters are not called for concretely encoded strings or primitives (`owasp-cs-deserialization#harden-your-own-javaioobjectinputstream`).

Filtering does not make arbitrary untrusted deserialization safe (`owasp-cs-deserialization#harden-your-own-javaioobjectinputstream`).

Creating a random string as a filename, such as generating a UUID/GUID, is essential to avoid the dangers of user-supplied filenames (`owasp-cs-file-upload#filename-safety`).

If user filenames are required, restrict the use of leading periods (hidden files) and sequential periods (directory traversal) (`owasp-cs-file-upload#filename-safety`).

If user filenames are required, restrict characters to an allowed subset such as alphanumeric characters, hyphen, spaces and periods, and implement a maximum length (`owasp-cs-file-upload#filename-safety`).

Only if restricting characters is not possible should dangerous characters be block-listed (`owasp-cs-file-upload#filename-safety`).

On Windows/NTFS, a long filename may have an 8.3 short name alias, so a collision check on the long name alone can be bypassed (`owasp-cs-file-upload#filename-safety`).

```java snippet=m10-l06/PathTraversal.java
import java.nio.file.Path;

public class PathTraversal {
    public static void main(String[] args) {
        Path uploads = Path.of("/var/uploads");
        Path requested = uploads.resolve("../etc/passwd").normalize();
        System.out.println(requested + " " + requested.startsWith(uploads));
    }
}
```

The snippet prints `/var/etc/passwd false`: normalizing `/var/uploads/../etc/passwd` leaves a path that does not start with `/var/uploads`.

## The HTTP surface: CORS, CSRF, headers and input validation
<!-- bullets: 10.6.d -->

CSRF protection in Spring Security is provided by several components that are composed within the `CsrfFilter` (`spring-security-servlet-exploits-csrf#csrf-components`).

If the request requires CSRF protection, the actual CSRF token provided by the client is compared against the persisted `CsrfToken`, and if valid the filter chain continues (`spring-security-servlet-exploits-csrf#csrf-components`).

If the actual CSRF token is invalid or missing, an `AccessDeniedException` is passed to the `AccessDeniedHandler` and processing ends (`spring-security-servlet-exploits-csrf#csrf-components`).

The synchronizer token pattern is one of the most popular and recommended methods to mitigate CSRF (`owasp-cs-csrf#token-based-mitigation`).

Servers can use Fetch Metadata headers, most importantly `Sec-Fetch-Site`, as a lightweight and reliable method to block obvious cross-site requests (`owasp-cs-csrf#fetch-metadata-headers`).

Because some legacy browsers do not send `Sec-Fetch-*` headers, a fallback to standard origin verification headers is a mandatory requirement for any Fetch Metadata implementation (`owasp-cs-csrf#fetch-metadata-headers`).

`Sec-Fetch-Site` is the primary signal for CSRF protection and indicates the relationship between the request initiator's origin and its target's origin: `same-origin`, `same-site`, `cross-site`, or `none` (`owasp-cs-csrf#fetch-metadata-headers`).

`Sec-Fetch-*` is supported in all major browsers since March 2023 (`owasp-cs-csrf#fetch-metadata-headers`).

Spring Security adds default security headers, and a specific header can be customized while keeping the defaults, for example `SAMEORIGIN` for `X-Frame-Options` (`spring-security-servlet-exploits-headers#servlet-headers-default`).

With `defaultsDisabled()` and `cacheControl(withDefaults())`, Spring Security adds only Cache Control (`spring-security-servlet-exploits-headers#servlet-headers-default`).

If necessary, `headers.disable()` disables all of the HTTP security response headers (`spring-security-servlet-exploits-headers#servlet-headers-default`).

The easiest way to ensure that CORS is handled first is to use the `CorsFilter` (`spring-security-servlet-integrations-cors#cors-configuration-source`).

Spring Security automatically configures CORS only if a `UrlBasedCorsConfigurationSource` instance is present (`spring-security-servlet-integrations-cors#cors-configuration-source`).

CORS misconfiguration allows API access from unauthorized or untrusted origins (`owasp-top10-2025-a01#description`).

Input validation checks both syntax, the expected type and format, and semantics, whether the value makes sense for the operation (`owasp-cs-input-validation#input-validation-strategies`).

Define what the application accepts and reject values outside those rules, instead of trying to recognize every malicious string (`owasp-cs-input-validation#allowlist-vs-denylist`).

Blocking apostrophes rejects legitimate names without making a database query safe (`owasp-cs-input-validation#allowlist-vs-denylist`).

For free-form comments, an allowlist can permit broad Unicode text while limiting its length, and need not restrict users to letters and digits (`owasp-cs-input-validation#allowlist-vs-denylist`).

Bean Validation provides a common way of validation through constraint declaration and metadata for Java applications (`spring-fw-validation-beanvalidation#validation-beanvalidation-overview`).

With Bean Validation, you annotate domain model properties with declarative validation constraints, which the runtime then enforces (`spring-fw-validation-beanvalidation#validation-beanvalidation-overview`).

## Secrets and sensitive data in logs, traces and dumps
<!-- bullets: 10.6.e -->

Some data should usually not be recorded directly in the logs, but instead removed, masked, sanitized, hashed, or encrypted (`owasp-cs-logging#data-to-exclude`).

:::esquema{kind=tabla title="Data that should usually not be recorded directly in the logs"}
| Data | Source |
|---|---|
| Session identification values (consider replacing with a hashed value if needed to track session specific events) | `owasp-cs-logging#data-to-exclude` |
| Access tokens | `owasp-cs-logging#data-to-exclude` |
| Authentication passwords | `owasp-cs-logging#data-to-exclude` |
| Database connection strings | `owasp-cs-logging#data-to-exclude` |
| Encryption keys and other primary secrets | `owasp-cs-logging#data-to-exclude` |
| Bank account or payment card holder data | `owasp-cs-logging#data-to-exclude` |
:::

In Java, do not use immutable structures such as Strings to store secrets, since it is impossible to force them to be garbage collected (`owasp-cs-secrets#25-handling-secrets-in-memory`).

Instead, use primitive types such as byte arrays or char arrays, where the memory can be directly overwritten (`owasp-cs-secrets#25-handling-secrets-in-memory`).

After a secret has been used, the memory it occupied should be zeroed out to prevent it from lingering in memory where it could potentially be accessed (`owasp-cs-secrets#25-handling-secrets-in-memory`).

The goal is to minimize the time window where the secret is in plaintext in memory as much as possible (`owasp-cs-secrets#25-handling-secrets-in-memory`).

An advanced attacker who can cause a system to crash and gain access to a memory dump may be able to extract secrets from it (`owasp-cs-secrets#25-handling-secrets-in-memory`).

Granting `list` or `watch` permissions on Secrets allows a subject to read all Secret data in that namespace, not only the Secrets explicitly referenced by its Pods (`k8s-secrets#information-security-for-secrets`).

A Secret is only sent to a node if a Pod on that node requires it (`k8s-secrets#information-security-for-secrets`).

For mounting Secrets into Pods, the kubelet stores a copy of the data into a `tmpfs` so that the confidential data is not written to durable storage (`k8s-secrets#information-security-for-secrets`).

Only the Secrets that a Pod requests are potentially visible within its containers, so one Pod does not have access to the Secrets of another Pod (`k8s-secrets#information-security-for-secrets`).

Since baggage is propagated across service boundaries, avoid putting sensitive information such as user credentials, API keys or PII in it, as it might be logged or sent to untrusted downstream services (`otel-context-propagation#baggage`).

Malicious actors could send forged trace headers to manipulate your tracing data or potentially exploit vulnerabilities in context parsing (`otel-context-propagation#external-services`).

Internal trace IDs, span IDs, or baggage items might reveal sensitive information about your internal architecture or business logic (`otel-context-propagation#external-services`).

Information returned by the `/env`, `/configprops` and `/quartz` endpoints can be sensitive, so by default values are always fully sanitized and replaced by `******` (`spring-boot-actuator-endpoints#actuator.endpoints.sanitization`).

With `show-values` set to `never`, values are always fully sanitized (`spring-boot-actuator-endpoints#actuator.endpoints.sanitization`).

With `show-values` set to `when-authorized`, values are shown only to authorized users, as long as no `SanitizingFunction` bean applies (`spring-boot-actuator-endpoints#actuator.endpoints.sanitization`).

For HTTP endpoints, by default any authenticated user is authorized (`spring-boot-actuator-endpoints#actuator.endpoints.sanitization`).

For JMX endpoints, all users are always authorized (`spring-boot-actuator-endpoints#actuator.endpoints.sanitization`).

## Supply chain
<!-- bullets: 10.6.f -->

A03:2025 in the Top 10 is Software Supply Chain Failures (`owasp-top10-2025#top-102025-list`).

The CycloneDX object model is a structured framework for representing information relevant for software and system transparency (`cyclonedx-spec#the-cyclonedx-object-model`).

CycloneDX components describe the complete inventory of first-party and third-party components (`cyclonedx-spec#components`).

CycloneDX can represent software, hardware devices, machine learning models, source code, and configurations (`cyclonedx-spec#components`).

The CycloneDX dependency graph is capable of representing both direct and transitive relationships (`cyclonedx-spec#dependencies`).

Components that depend on services can be represented in the CycloneDX dependency graph (`cyclonedx-spec#dependencies`).

The OWASP vulnerable dependencies cheat sheet proposes an approach for handling vulnerable third-party dependencies when they are detected (`owasp-cs-vulnerable-deps#introduction`).

Keyless signing associates identities, rather than keys, with an artifact signature (`sigstore-cosign-signing#overview`).

Fulcio issues short-lived certificates binding an ephemeral key to an OpenID Connect identity (`sigstore-cosign-signing#overview`).

Sigstore logs signing events in Rekor, a signature transparency log, which provides an auditable record of when a signature was created (`sigstore-cosign-signing#overview`).

To verify a signature, Sigstore compares a tuple of signature, key or certificate, and artifact from the timestamped object against the timestamped Rekor entry (`sigstore-cosign-signing#verifying-the-signed-artifact`).

Because Rekor's transparency log is immutable, the signer can monitor the log for occurrences of their identity and will know if there is an unexpected signing event (`sigstore-cosign-signing#verifying-the-signed-artifact`).

Supply-chain Levels for Software Artifacts, or SLSA (“salsa”), is a set of incrementally adoptable guidelines for supply chain security, established by industry consensus (`slsa-about#what-is-slsa`).

The SLSA build track describes increasing levels of trustworthiness and completeness in a package artifact’s provenance (`slsa-tracks#build-track`).

Provenance describes what entity built the artifact, what process they used, and what the inputs were (`slsa-tracks#build-track`).

The lowest build level only requires the provenance to exist, while higher levels provide increasing protection against tampering of the build, the provenance, or the artifact (`slsa-tracks#build-track`).

:::esquema{kind=tabla title="SLSA build levels"}
| Level | In practice | Source |
|---|---|---|
| Build L1 | The package has provenance showing how it was built | `slsa-build-track-basics#build-l1-provenance-exists` |
| Build L2 | Builds run on a hosted platform that generates and signs the provenance | `slsa-build-track-basics#build-l2-hosted-build-platform` |
| Build L3 | Builds run on a hardened build platform that offers strong tamper protection | `slsa-build-track-basics#build-l3-hardened-builds` |
:::

Provenance may be incomplete or unsigned at Build L1 (`slsa-build-track-basics#build-l1-provenance-exists`).

At Build L3 the build platform must prevent secret material used to sign the provenance from being accessible to the user-defined build steps (`slsa-build-track-basics#build-l3-hardened-builds`).

At Build L3 the build platform must prevent runs from influencing one another, even within the same project (`slsa-build-track-basics#build-l3-hardened-builds`).

Source L1 requires a version control system (`slsa-source-requirements#basics`).

Source L4 requires code review (`slsa-source-requirements#basics`).

A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts (`reproducible-builds-definition#when-is-a-build-reproducible`).

The artifacts of a build are the parts of the build results that are the desired primary output (`reproducible-builds-definition#when-is-a-build-reproducible`).

## Threat modelling with STRIDE
<!-- bullets: 10.6.g -->

STRIDE is a mature and popular threat modeling technique and mnemonic originally developed by Microsoft employees (`owasp-cs-threat-modeling#threat-identification`).

STRIDE groups threats into one of six general prompts, and each STRIDE threat may be considered a violation of a desirable security attribute (`owasp-cs-threat-modeling#threat-identification`).

:::esquema{kind=tabla title="STRIDE categories"}
| Threat category | Violates | Example | Source |
|---|---|---|---|
| Spoofing | Authentication | An attacker steals the authentication token of a legitimate user and uses it to impersonate the user | `owasp-cs-threat-modeling#threat-identification` |
| Tampering | Integrity | An attacker abuses the application to perform unintended updates to a database | `owasp-cs-threat-modeling#threat-identification` |
| Repudiation | Accounting | An attacker manipulates logs to cover their actions | `owasp-cs-threat-modeling#threat-identification` |
| Information Disclosure | Confidentiality | An attacker extracts data from a database containing user account info | `owasp-cs-threat-modeling#threat-identification` |
| Denial of Service | Availability | An attacker locks a legitimate user out of their account by performing many failed authentication attempts | `owasp-cs-threat-modeling#threat-identification` |
| Elevation of Privileges | Authorization | An attacker tampers with a JWT to change their role | `owasp-cs-threat-modeling#threat-identification` |
:::

After threats are identified, people frequently rank them; in theory, ranking is based on the mathematical product of a threat's likelihood and its impact (`owasp-cs-threat-modeling#threat-identification`).

Likelihood and impact can be challenging to calculate, and they ignore the work to fix a problem (`owasp-cs-threat-modeling#threat-identification`).

## Key points

- The OWASP Top 10:2025 ranks Broken Access Control first, Injection fifth and Software Supply Chain Failures third.
- BOLA and IDOR come from a missing object-level authorization check on an ID the client controls, and comparing the session user ID with the ID parameter is not sufficient.
- To prevent excessive data exposure and mass assignment, cherry-pick the properties you return, avoid automatic binding of client input and allow changes only to the properties that should be updated.
- Permissions are validated on every request, with application-wide configuration rather than per-method checks.
- Injection is prevented by keeping data separate from commands: parameterized queries, with allow-lists for table names, column names and sort direction.
- SSRF prevention uses allow lists, disabled HTTP redirections, a well-tested URL parser and no raw responses to clients.
- Java deserialization needs serialization filters with a class allowlist and resource limits, and filtering does not make arbitrary untrusted deserialization safe.
- A random stored filename is essential, and a collision check on the long filename alone can be bypassed through an 8.3 short name alias.
- A missing or invalid CSRF token ends in an `AccessDeniedException`, and Fetch Metadata headers need a fallback to origin verification headers.
- Input validation defines what is accepted and rejects the rest, instead of recognizing every malicious string.
- Access tokens, passwords, connection strings and keys should not be written directly to logs, and baggage should hold no credentials or PII.
- Actuator sanitizes `/env`, `/configprops` and `/quartz` values by default, and `when-authorized` shows them only to authorized users.
- SLSA Build L1 requires provenance to exist, L2 a hosted platform that signs it, and L3 a hardened platform that protects the signing material.
- A reproducible build lets any party recreate bit-by-bit identical copies of the specified artifacts from the same source, environment and instructions.
- STRIDE sorts threats into six categories, each violating one security attribute.

# Platform engineering and architecture of systems with AI

## Threat-modelling templates
<!-- bullets: 10.4.a -->

:::judgement{source="OWASP, Threat Modeling Cheat Sheet" ref="owasp-cs-threat-modeling#overview"}
According to the OWASP Threat Modeling Cheat Sheet, threat modeling is a structured, repeatable process that models a system from a security perspective, identifies the threats that apply and determines responses to them. It is ideally performed early, during design, and the threat model is maintained and updated alongside the system. The cheat sheet builds the process on four questions from the Threat Modeling Manifesto: what are we working on, what can go wrong, what are we going to do about it, and did we do a good enough job.
:::

:::judgement{source="OWASP, Threat Modeling Cheat Sheet" ref="owasp-cs-threat-modeling#choosing-a-threat-modeling-technique"}
According to the same cheat sheet, a team starts with STRIDE for a technical design and selects another technique only when the scope needs a different view, such as attack trees for a high-value attacker goal or LINDDUN for privacy harms. The cheat sheet adds that techniques are not added only to make the model look comprehensive, and that the team states why each one fits the scope.
:::

## Golden paths
<!-- bullets: 10.4.a -->

:::judgement{source="Gary Niemen, Spotify Engineering, How We Use Golden Paths to Solve Fragmentation in Our Software Ecosystem" ref="spotify-golden-paths#the-golden-path-today"}
According to Gary Niemen of Spotify, the Golden Path, as Spotify defines it today, is the "opinionated and supported" path to "build something", for example a backend service, a website or a data pipeline. The Golden Path tutorial is a step-by-step tutorial that walks through that path. The tools on the path are visualized in the Explore section of Backstage, Spotify's internal developer portal, with filtering per discipline. The post says the idea is not to limit or stifle engineers, or to set standards for the sake of it: with Golden Paths in place, teams do not have to reinvent the wheel and have fewer decisions to make.
:::

:::judgement{source="Gary Niemen, Spotify Engineering, How We Use Golden Paths to Solve Fragmentation in Our Software Ecosystem" ref="spotify-golden-paths#hello-golden-path"}
According to the same post by Gary Niemen, the first Golden Path and tutorial were developed for backend engineering as a Hack Week project. It quotes the platform team's write-up, which says an engineer can leave the Golden Path and do their own thing, but then will not have the same support.
:::

## Workflows and agents
<!-- bullets: 10.4.b -->

:::judgement{source="Anthropic, Building effective agents" ref="anthropic-building-effective-agents#what-are-agents"}
According to Anthropic, workflows are systems where LLMs and tools are orchestrated through predefined code paths, and agents are systems where LLMs dynamically direct their own processes and tool usage. Anthropic recommends finding the simplest solution possible and increasing complexity only when needed, because agentic systems often trade latency and cost for better task performance. In its view workflows offer predictability and consistency for well-defined tasks, and agents are the better option when flexibility and model-driven decision-making are needed at scale.
:::

:::judgement{source="Anthropic, Building effective agents" ref="anthropic-building-effective-agents#agents"}
According to Anthropic, the autonomy of agents means higher costs and the potential for compounding errors, so it recommends extensive testing in sandboxed environments along with appropriate guardrails. It names stopping conditions, such as a maximum number of iterations, as a way to keep control of an agent that would otherwise run until the task ends.
:::

## Authorization in the Model Context Protocol
<!-- bullets: 10.4.c -->

Authorization is optional for Model Context Protocol (MCP) implementations (`mcp-authorization#protocol-requirements`).

An MCP implementation that uses an HTTP-based transport should conform to the MCP authorization specification (`mcp-authorization#protocol-requirements`).

An MCP implementation that uses an STDIO transport should not follow that specification and should retrieve credentials from the environment instead (`mcp-authorization#protocol-requirements`).

An MCP implementation that uses an alternative transport must follow the established security best practices for its protocol (`mcp-authorization#protocol-requirements`).

An MCP client must send the access token in the `Authorization` request header as `Authorization: Bearer <access-token>` (`mcp-authorization#token-requirements`).

Authorization must be included in every HTTP request from client to server (`mcp-authorization#token-requirements`).

Access tokens must not be included in the URI query string (`mcp-authorization#token-requirements`).

MCP servers should include a `scope` parameter in the `WWW-Authenticate` header to indicate the scopes required for accessing the resource (`mcp-authorization#scope-selection-strategy`).

Clients must treat the scopes provided in the challenge as authoritative for the current operation (`mcp-authorization#scope-selection-strategy`).

Clients must not assume any particular set relationship between the challenged scope set and `scopes_supported` (`mcp-authorization#scope-selection-strategy`).

When re-authorizing, clients should include the challenged scopes alongside any previously granted scopes to avoid losing permissions needed for other operations (`mcp-authorization#scope-selection-strategy`).

During the initial authorization handshake, a client should first use the `scope` parameter from the `WWW-Authenticate` header of the `401` response, if provided (`mcp-authorization#scope-selection-strategy`).

If no `scope` is available, the client should use all scopes defined in `scopes_supported` from the Protected Resource Metadata document, and omit the `scope` parameter if `scopes_supported` is undefined (`mcp-authorization#scope-selection-strategy`).

The `scopes_supported` field is intended to represent the minimal set of scopes necessary for basic functionality (`mcp-authorization#scope-selection-strategy`).

Additional scopes are requested incrementally through the step-up authorization flow (`mcp-authorization#scope-selection-strategy`).

Servers are not required to surface every dynamically issued scope through `scopes_supported` (`mcp-authorization#scope-selection-strategy`).

Scope challenge handling covers insufficient scope errors during runtime operations, when a client already has a token but needs additional permissions (`mcp-authorization#scope-challenge-handling`).

## Confused deputy and token passthrough
<!-- bullets: 10.4.c -->

Attackers can exploit MCP proxy servers that connect to third-party APIs, creating “confused deputy” vulnerabilities (`mcp-security-best-practices#confused-deputy-problem`).

The attack allows malicious clients to obtain authorization codes without proper user consent by exploiting the combination of static client IDs, dynamic client registration and consent cookies (`mcp-security-best-practices#confused-deputy-problem`).

“Token passthrough” is an anti-pattern where an MCP server accepts tokens from an MCP client without validating that the tokens were properly issued to the MCP server and passes them through to the downstream API (`mcp-security-best-practices#token-passthrough`).

When an MCP server does not verify that tokens were specifically intended for it, for example through the audience claim, it may accept tokens originally issued for other services (`mcp-security-best-practices#token-passthrough`).

Accepting tokens issued for other services breaks a fundamental OAuth security boundary and lets attackers reuse legitimate tokens across different services than intended (`mcp-security-best-practices#token-passthrough`).

A server that also forwards unmodified tokens with incorrect audiences to downstream services can cause the “confused deputy” problem (`mcp-security-best-practices#token-passthrough`).

## Protections an MCP proxy server must implement
<!-- bullets: 10.4.c 10.4.d -->

An MCP proxy server must maintain a registry of approved `client_id` values per user (`mcp-security-best-practices#required-protections`).

An MCP proxy server must check that registry before initiating the third-party authorization flow (`mcp-security-best-practices#required-protections`).

An MCP proxy server must validate that the `redirect_uri` in authorization requests exactly matches the registered URI (`mcp-security-best-practices#required-protections`).

The comparison of the `redirect_uri` must use exact string matching, not pattern matching or wildcards (`mcp-security-best-practices#required-protections`).

The MCP-level consent page must prevent iframing through the `frame-ancestors` CSP directive or `X-Frame-Options: DENY` to prevent clickjacking (`mcp-security-best-practices#required-protections`).

A consent cookie must use the `__Host-` prefix for its name (`mcp-security-best-practices#required-protections`).

A consent cookie must set the `Secure`, `HttpOnly` and `SameSite=Lax` attributes (`mcp-security-best-practices#required-protections`).

A consent cookie must bind to the specific `client_id`, not just to “user has consented” (`mcp-security-best-practices#required-protections`).

The proxy must generate a cryptographically secure random `state` value for each authorization request (`mcp-security-best-practices#required-protections`).

`state` values must be single-use, deleted after validation, and have a short expiration time such as 10 minutes (`mcp-security-best-practices#required-protections`).

The consent cookie or session containing the `state` value must not be set until after the user has approved the consent screen at the MCP server’s authorization endpoint (`mcp-security-best-practices#required-protections`).

## Tool calls under least privilege
<!-- bullets: 10.4.c -->

:::esquema{kind=tabla title="Security duties for MCP tools"}
| Party | Duty | Source |
|---|---|---|
| Servers MUST | Validate all tool inputs | `mcp-tools#security-considerations` |
| Servers MUST | Implement proper access controls | `mcp-tools#security-considerations` |
| Servers MUST | Rate limit tool invocations | `mcp-tools#security-considerations` |
| Servers MUST | Sanitize tool outputs | `mcp-tools#security-considerations` |
| Clients SHOULD | Prompt for user confirmation on sensitive operations | `mcp-tools#security-considerations` |
| Clients SHOULD | Show tool inputs to the user before calling the server, to avoid malicious or accidental data exfiltration | `mcp-tools#security-considerations` |
| Clients SHOULD | Validate tool results before passing to LLM | `mcp-tools#security-considerations` |
| Clients SHOULD | Implement timeouts for tool calls | `mcp-tools#security-considerations` |
| Clients SHOULD | Log tool usage for audit purposes | `mcp-tools#security-considerations` |
:::

To reduce disclosure from an LLM application, access to sensitive data is limited based on the principle of least privilege (`owasp-llm-sensitive-disclosure#1-enforce-strict-access-controls`).

Only data that is necessary for the specific user or process is granted (`owasp-llm-sensitive-disclosure#1-enforce-strict-access-controls`).

## Permission-aware vector databases
<!-- bullets: 10.4.c -->

OWASP recommends fine-grained access controls and permission-aware vector and embedding stores (`owasp-llm08-vector-embedding#1-permission-and-access-control`).

Datasets in the vector database need strict logical and access partitioning, to prevent unauthorized access between different classes of users or different groups (`owasp-llm08-vector-embedding#1-permission-and-access-control`).

When different groups of users share the same vector database in a multi-tenant environment, embeddings from one group might be inadvertently retrieved in response to queries from another group's LLM (`owasp-llm08-vector-embedding#scenario-2-access-control--data-leakage-risk-by-combining-data-with-different-access-restrictions`).

That retrieval can leak sensitive business information (`owasp-llm08-vector-embedding#scenario-2-access-control--data-leakage-risk-by-combining-data-with-different-access-restrictions`).

The mitigation is a permission-aware vector database that restricts access so that only authorized groups can reach their specific information (`owasp-llm08-vector-embedding#scenario-2-access-control--data-leakage-risk-by-combining-data-with-different-access-restrictions`).

## Sensitive data in LLM applications
<!-- bullets: 10.4.d -->

Sensitive information includes personal identifiable information (PII), financial details, health records, confidential business data, security credentials and legal documents (`owasp-llm-sensitive-disclosure#main`).

LLM applications should perform adequate data sanitization to prevent user data from entering the training model (`owasp-llm-sensitive-disclosure#main`).

Application owners should provide clear Terms of Use policies that allow users to opt out of having their data included in the training model (`owasp-llm-sensitive-disclosure#main`).

Restrictions in the system prompt about the data types the LLM should return can mitigate sensitive information disclosure (`owasp-llm-sensitive-disclosure#main`).

Such restrictions may not always be honored and could be bypassed via prompt injection or other methods (`owasp-llm-sensitive-disclosure#main`).

Personal identifiable information (PII) may be disclosed during interactions with the LLM (`owasp-llm-sensitive-disclosure#1-pii-leakage`).

## Indirect prompt injection
<!-- bullets: 10.4.d -->

Indirect prompt injections occur when an LLM accepts input from external sources, such as websites or files (`owasp-llm-top10-prompt-injection#indirect-prompt-injections`).

Like direct injections, indirect injections can be either intentional or unintentional (`owasp-llm-top10-prompt-injection#indirect-prompt-injections`).

The severity and impact of a successful prompt injection depend largely on the business context the model operates in and on the agency with which the model is architected (`owasp-llm-top10-prompt-injection#indirect-prompt-injections`).

:::esquema{kind=tabla title="Outcomes of a successful prompt injection"}
| Outcome | Source |
|---|---|
| Disclosure of sensitive information | `owasp-llm-top10-prompt-injection#indirect-prompt-injections` |
| Revealing sensitive information about AI system infrastructure or system prompts | `owasp-llm-top10-prompt-injection#indirect-prompt-injections` |
| Content manipulation leading to incorrect or biased outputs | `owasp-llm-top10-prompt-injection#indirect-prompt-injections` |
| Providing unauthorized access to functions available to the LLM | `owasp-llm-top10-prompt-injection#indirect-prompt-injections` |
| Executing arbitrary commands in connected systems | `owasp-llm-top10-prompt-injection#indirect-prompt-injections` |
| Manipulating critical decision-making processes | `owasp-llm-top10-prompt-injection#indirect-prompt-injections` |
:::

In multimodal AI, malicious actors could exploit interactions between modalities, such as hiding instructions in images that accompany benign text (`owasp-llm-top10-prompt-injection#indirect-prompt-injections`).

Given the stochastic influence at the heart of the way models work, it is unclear whether fool-proof methods of preventing prompt injection exist (`owasp-llm-top10-prompt-injection#prevention-and-mitigation-strategies`).

Adversarial testing means regular penetration testing and breach simulations that treat the model as an untrusted user to test the effectiveness of trust boundaries and access controls (`owasp-llm-top10-prompt-injection#7-conduct-adversarial-testing-and-attack-simulations`).

## Grading evaluations of model output
<!-- bullets: 10.4.d -->

:::judgement{source="Anthropic, Claude documentation: Create strong empirical evaluations" ref="anthropic-develop-tests#grade-your-evaluations"}
According to Anthropic's Claude documentation, the method to grade evals should be the fastest, most reliable and most scalable one. Code-based grading is the fastest and most reliable and extremely scalable, but it lacks nuance for complex judgments that need less rule-based rigidity. Its examples are exact match, `output == golden_answer`, and string match, `key_phrase in output`. Human grading is the most flexible and of the highest quality, but slow and expensive, and the documentation says to avoid it if possible. LLM-based grading is fast and flexible, scalable and suitable for complex judgment, and the documentation says to test it for reliability first and then scale.
:::

## Key points

- MCP authorization is optional; HTTP-based transports should conform to it, and STDIO ones retrieve credentials from the environment.
- An MCP client sends the access token in the `Authorization` request header on every HTTP request, never in the URI query string.
- Clients treat the scopes in a `WWW-Authenticate` challenge as authoritative for the current operation and keep previously granted scopes when they re-authorize.
- Token passthrough is an anti-pattern: accepting tokens that were not issued to the MCP server breaks an OAuth security boundary.
- An MCP proxy server keeps a registry of approved `client_id` values, matches `redirect_uri` exactly and sets the consent cookie only after consent.
- MCP servers must validate tool inputs, apply access controls, rate limit invocations and sanitize outputs.
- LLM applications limit access to sensitive data by least privilege, and system-prompt restrictions may be bypassed by prompt injection.
- OWASP recommends permission-aware vector and embedding stores, with strict logical and access partitioning of datasets between groups of users.
- Indirect prompt injection comes from external content, no prevention is known to be fool-proof, and adversarial testing treats the model as an untrusted user.

# HTTP semantics

## Safe methods
<!-- bullets: 7.4.a -->

Request methods are considered "safe" if their defined semantics are essentially read-only, so the client does not request, and does not expect, any state change on the origin server (`rfc9110#section-9.2.1`).

Of the request methods defined by RFC 9110, the GET, HEAD, OPTIONS, and TRACE methods are defined to be safe (`rfc9110#section-9.2.1`).

Appending request information to access log files at the completion of every response is considered safe, even though the log storage might become full and cause the server to fail (`rfc9110#section-9.2.1`).

The purpose of distinguishing between safe and unsafe methods is to allow automated retrieval processes and cache performance optimization to work without fear of causing harm (`rfc9110#section-9.2.1`).

If a resource performs an unsafe action selected by parameters in the target URI, the resource owner must disable or disallow that action when it is accessed using a safe request method (`rfc9110#section-9.2.1`).

## Idempotent methods and retries
<!-- bullets: 7.4.a -->

A request method is considered "idempotent" if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request (`rfc9110#section-9.2.2`).

Of the request methods defined by RFC 9110, PUT, DELETE, and safe request methods are idempotent (`rfc9110#section-9.2.2`).

The idempotent property only applies to what has been requested by the user, so a server is free to log each request separately, retain a revision control history, or implement other non-idempotent side effects (`rfc9110#section-9.2.2`).

:::esquema{kind=tabla title="Safe and idempotent methods in RFC 9110"}
| Property | Methods | Source |
|---|---|---|
| Safe | `GET`, `HEAD`, `OPTIONS`, `TRACE` | `rfc9110#section-9.2.1` |
| Idempotent | `PUT`, `DELETE` and the safe methods | `rfc9110#section-9.2.2` |
:::

Idempotent methods are distinguished because the request can be repeated automatically if a communication failure occurs before the client is able to read the server's response (`rfc9110#section-9.2.2`).

Repeating an idempotent request has the same intended effect, even if the original request succeeded, though the response might differ (`rfc9110#section-9.2.2`).

A client should not automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent, or some means to detect that the original request was never applied (`rfc9110#section-9.2.2`).

A proxy must not automatically retry non-idempotent requests (`rfc9110#section-9.2.2`).

A client should not automatically retry a failed automatic retry (`rfc9110#section-9.2.2`).

## Status code classes
<!-- bullets: 7.4.a -->

The reason phrases of the status codes are only recommendations and can be replaced by local equivalents or left out altogether without affecting the protocol (`rfc9110#section-15.1`).

Responses with status codes defined as heuristically cacheable, such as 200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414 and 501, can be reused by a cache with heuristic expiration unless otherwise indicated, and all other status codes are not heuristically cacheable (`rfc9110#section-15.1`).

:::esquema{kind=tabla title="Status code classes in RFC 9110"}
| Class | Meaning | Source |
|---|---|---|
| `2xx` Successful | The client's request was successfully received, understood, and accepted | `rfc9110#section-15.3` |
| `3xx` Redirection | Further action needs to be taken by the user agent in order to fulfill the request | `rfc9110#section-15.4` |
| `4xx` Client Error | The client seems to have erred | `rfc9110#section-15.5` |
| `5xx` Server Error | The server is aware that it has erred or is incapable of performing the requested method | `rfc9110#section-15.6` |
:::

Except when responding to a HEAD request, the server should send a representation containing an explanation of the error situation, and whether it is a temporary or permanent condition (`rfc9110#section-15.5`).

The 4xx status codes are applicable to any request method (`rfc9110#section-15.5`).

## Redirect status codes
<!-- bullets: 7.4.a -->

The status codes 301 (Moved Permanently), 302 (Found), 307 (Temporary Redirect) and 308 (Permanent Redirect) indicate that this resource might be available at a different URI, as provided by the Location header field (`rfc9110#section-15.4`).

The 300 (Multiple Choices) status code offers a choice among matching resources capable of representing this resource (`rfc9110#section-15.4`).

The 303 (See Other) status code redirects to a different resource, identified by the Location header field, that can represent an indirect response to the request (`rfc9110#section-15.4`).

The 304 (Not Modified) status code redirects to a previously stored result (`rfc9110#section-15.4`).

In HTTP/1.0, 303 (See Other) was defined for a redirection that changed its method to GET (`rfc9110#section-15.4`).

307 (Temporary Redirect) and 308 (Permanent Redirect) were later added to unambiguously indicate method-preserving redirects, and status codes 301 and 302 have been adjusted to allow a POST request to be redirected as GET (`rfc9110#section-15.4`).

If a Location header field is provided, the user agent may automatically redirect its request to the referenced URI, even if the specific status code is not understood (`rfc9110#section-15.4`).

A client should detect and intervene in cyclical redirections (`rfc9110#section-15.4`).

## Cache-Control and freshness
<!-- bullets: 7.4.b -->

The Cache-Control header field is used to list directives for caches along the request/response chain (`rfc9111#section-5.2`).

Cache directives are unidirectional, in that the presence of a directive in a request does not imply that the same directive is present or copied in the response (`rfc9111#section-5.2`).

A proxy, whether or not it implements a cache, must pass cache directives through in forwarded messages (`rfc9111#section-5.2`).

It is not possible to target a directive to a specific cache (`rfc9111#section-5.2`).

Cache directives are identified by a token, to be compared case-insensitively (`rfc9111#section-5.2`).

A response's freshness lifetime is the length of time between its generation by the origin server and its expiration time (`rfc9111#section-4.2`).

A response's age is the time that has passed since it was generated by, or successfully validated with, the origin server (`rfc9111#section-4.2`).

A response is fresh when freshness_lifetime is greater than current_age (`rfc9111#section-4.2`).

```java snippet=m07-l04/Freshness.java
public class Freshness {
    static boolean responseIsFresh(long freshnessLifetime, long currentAge) {
        return freshnessLifetime > currentAge;
    }

    public static void main(String[] args) {
        for (long age : new long[] {59, 60, 61}) {
            String state = responseIsFresh(60, age) ? "fresh" : "stale";
            System.out.println("lifetime 60, age " + age + ": " + state);
        }
    }
}
```

With a freshness lifetime of 60 and an age of 59, the response is fresh, so the snippet prints `fresh`.

With a freshness lifetime of 60 and an age of 60, the response is stale, because the comparison is strict, so the snippet prints `stale`.

If an origin server wishes to force a cache to validate every request, it can assign an explicit expiration time in the past to indicate that the response is already stale (`rfc9111#section-4.2`).

Since origin servers do not always provide explicit expiration times, caches are also allowed to use a heuristic to determine an expiration time under certain circumstances (`rfc9111#section-4.2`).

Freshness applies only to cache operation and cannot be used to force a user agent to refresh its display or reload a resource (`rfc9111#section-4.2`).

When a cache cannot serve any stored response, it can use the conditional request mechanism in the forwarded request, a process known as validating or revalidating the stored response (`rfc9111#section-4.3`).

## ETag and conditional requests
<!-- bullets: 7.4.b -->

The ETag field in a response provides the current entity tag for the selected representation, as determined at the conclusion of handling the request (`rfc9110#section-8.8.3`).

An entity tag consists of an opaque quoted string, possibly prefixed by a weakness indicator (`rfc9110#section-8.8.3`).

An entity tag can be either a weak or strong validator, with strong being the default (`rfc9110#section-8.8.3`).

If the generation of an entity tag does not satisfy all of the characteristics of a strong validator, the origin server must mark the entity tag as weak by prefixing its opaque value with W/ (`rfc9110#section-8.8.3`).

An entity tag can be more reliable for validation than a modification date where the one-second resolution of HTTP-date values is not sufficient (`rfc9110#section-8.8.3`).

It is preferable to send ETag as a header field unless the entity tag is generated while sending the content (`rfc9110#section-8.8.3`).

A strong validator is representation metadata that changes value whenever a change occurs to the representation data that would be observable in the content of a 200 (OK) response to GET (`rfc9110#section-8.8.1`).

A weak validator is representation metadata that might not change for every change to the representation data (`rfc9110#section-8.8.1`).

If the origin server sends the same validator for a representation with a gzip content coding applied as for a representation with no content coding, that validator is weak (`rfc9110#section-8.8.1`).

Strong validators are usable for all conditional requests, including cache validation, partial content ranges, and lost update avoidance (`rfc9110#section-8.8.1`).

Weak validators are only usable when the client does not require exact equality with previously obtained representation data (`rfc9110#section-8.8.1`).

A conditional request is an HTTP request with one or more request header fields that indicate a precondition to be tested before applying the request method to the target resource (`rfc9110#section-13`).

Conditional GET requests are the most efficient mechanism for HTTP cache updates (`rfc9110#section-13`).

Conditionals can also be applied to state-changing methods, such as PUT and DELETE, to prevent the lost update problem: one client accidentally overwriting the work of another client that has been acting in parallel (`rfc9110#section-13`).

A recipient must use the weak comparison function when comparing entity tags for If-None-Match, since weak entity tags can be used for cache validation even if there have been changes to the representation data (`rfc9110#section-13.1.2`).

A client updating stored responses that have entity tags should send an If-None-Match header field with a list of those entity tags in a GET request, which allows the server to send a 304 (Not Modified) response when one of them matches (`rfc9110#section-13.1.2`).

If the If-None-Match field value is *, the condition is false if the origin server has a current representation for the target resource (`rfc9110#section-13.1.2`).

If the If-None-Match field value is a list of entity tags, the condition is false if one of the listed tags matches the entity tag of the selected representation (`rfc9110#section-13.1.2`).

An origin server must not perform the requested method when the If-None-Match condition evaluates to false, and responds with 304 (Not Modified) for GET or HEAD and 412 (Precondition Failed) for all other request methods (`rfc9110#section-13.1.2`).

If-None-Match with the value * can prevent an unsafe request method, such as PUT, from inadvertently modifying an existing representation of the target resource when the client believes that the resource does not have a current representation (`rfc9110#section-13.1.2`).

An If-None-Match header field with a list value containing * and other values is syntactically invalid (`rfc9110#section-13.1.2`).

## Vary and cache keys
<!-- bullets: 7.4.b -->

The Vary header field in a response describes what parts of a request message, aside from the method and target URI, might have influenced the origin server's process for selecting the content of this response (`rfc9110#section-12.5.5`).

A Vary field containing a list of field names has two purposes (`rfc9110#section-12.5.5`).

Vary expands the cache key required to match a new request to the stored cache entry (`rfc9110#section-12.5.5`).

Vary also informs user agent recipients that the response was subject to content negotiation and a different representation might be sent in a subsequent request if other values are provided in the listed header fields (`rfc9110#section-12.5.5`).

A proxy must not generate * in a Vary field value (`rfc9110#section-12.5.5`).

An origin server should generate a Vary header field on a cacheable response when it wishes that response to be selectively reused for subsequent requests (`rfc9110#section-12.5.5`).

There is no need to send the Authorization field name in Vary because reuse of that response for a different user is prohibited by the field definition (`rfc9110#section-12.5.5`).

A cache must not use a stored response with a Vary header field without revalidation unless all the presented request header fields nominated by that Vary field value match those fields in the original request (`rfc9111#section-4.1`).

If a header field is absent from a request, it can only match another request if it is also absent there (`rfc9111#section-4.1`).

If multiple stored responses match and no preference mechanism applies, the most recent response, as determined by the Date header field, is chosen (`rfc9111#section-4.1`).

## Content negotiation
<!-- bullets: 7.4.c -->

HTTP provides mechanisms for content negotiation because an origin server often has different ways of representing information and users or user agents have different capabilities or preferences (`rfc9110#section-12`).

In proactive negotiation, the server selects the representation based upon the user agent's stated preferences (`rfc9110#section-12`).

In reactive negotiation, the server provides a list of representations for the user agent to choose from (`rfc9110#section-12`).

In request content negotiation, the user agent selects the representation for a future request based upon the server's stated preferences in past responses (`rfc9110#section-12`).

In all cases of content negotiation, HTTP is not aware of the resource semantics (`rfc9110#section-12`).

Proactive negotiation is also called server-driven negotiation (`rfc9110#section-12.1`).

Proactive negotiation is advantageous when the algorithm for selecting from among the available representations is difficult to describe to a user agent (`rfc9110#section-12.1`).

Proactive negotiation limits the reusability of responses for shared caching (`rfc9110#section-12.1`).

Having the user agent describe its capabilities in every request can be both very inefficient and a potential risk to the user's privacy (`rfc9110#section-12.1`).

A user agent cannot rely on proactive negotiation preferences being consistently honored (`rfc9110#section-12.1`).

The request header fields Accept, Accept-Charset, Accept-Encoding, and Accept-Language are defined for a user agent to engage in proactive negotiation of the response content (`rfc9110#section-12.1`).

The Accept-Language header field can be used by user agents to indicate the set of natural languages that are preferred in the response (`rfc9110#section-12.5.4`).

No quality value is the same as q=1 for a language range (`rfc9110#section-12.5.4`).

A user agent that does not provide user control over language preferences must not send an Accept-Language header field (`rfc9110#section-12.5.4`).

## Content codings and compression
<!-- bullets: 7.4.c -->

The Content-Encoding header field indicates what content codings have been applied to the representation, beyond those inherent in the media type (`rfc9110#section-8.4`).

Content-Encoding is primarily used to allow a representation's data to be compressed without losing the identity of its underlying media type (`rfc9110#section-8.4`).

A sender that applied encodings must generate a Content-Encoding header field that lists the content codings in the order in which they were applied (`rfc9110#section-8.4`).

Unlike Transfer-Encoding, the codings listed in Content-Encoding are a characteristic of the representation (`rfc9110#section-8.4`).

An origin server may respond with a status code of 415 (Unsupported Media Type) if a representation in the request message has a content coding that is not acceptable (`rfc9110#section-8.4`).

When sent by a user agent in a request, Accept-Encoding indicates the content codings acceptable in a response (`rfc9110#section-12.5.3`).

If no Accept-Encoding header field is in the request, any content coding is considered acceptable by the user agent (`rfc9110#section-12.5.3`).

An identity token is used as a synonym for no encoding in order to communicate when no encoding is preferred (`rfc9110#section-12.5.3`).

The asterisk in an Accept-Encoding field matches any available content coding not explicitly listed in the field (`rfc9110#section-12.5.3`).

An Accept-Encoding header field with an empty field value implies that the user agent does not want any content coding in response (`rfc9110#section-12.5.3`).

A content coding accompanied by a qvalue of 0 is not acceptable (`rfc9110#section-12.5.3`).

When selecting between multiple content codings that have the same purpose, the acceptable content coding with the highest non-zero qvalue is preferred (`rfc9110#section-12.5.3`).

Servers that fail a request due to an unsupported content coding ought to respond with a 415 (Unsupported Media Type) status and include an Accept-Encoding header field in that response (`rfc9110#section-12.5.3`).

## Key points

- Safe methods are essentially read-only, and `GET`, `HEAD`, `OPTIONS` and `TRACE` are the safe methods of RFC 9110.
- `PUT`, `DELETE` and the safe methods are idempotent, so the request can be repeated automatically if a communication failure occurs before the client is able to read the server's response.
- A client should not automatically retry a non-idempotent request, and a proxy must not.
- The status code classes are `2xx` successful, `3xx` redirection, `4xx` client error and `5xx` server error.
- `307` and `308` unambiguously preserve the method, while `301` and `302` allow a `POST` to be redirected as `GET`.
- Cache directives are unidirectional, and a proxy must pass them through whether or not it implements a cache.
- A response is fresh when its freshness lifetime is greater than its current age, so equal values are stale.
- A validator shared by a gzip-coded and an uncoded representation is weak, and an entity tag that is not strong must be prefixed with `W/`.
- A conditional request with `If-None-Match` is answered with `304` for `GET` or `HEAD` and `412` for other methods when the condition is false.
- `Vary` expands the cache key, and a proxy must not generate `*` in it.
- The three negotiation patterns of RFC 9110 are proactive, reactive and request content, and proactive negotiation limits the reuse of responses in shared caches.
- `Content-Encoding` lists the codings applied to the representation, and a qvalue of 0 in `Accept-Encoding` means not acceptable.

# AOP and proxies

## JDK dynamic proxies, CGLIB and self-invocation
<!-- bullets: 5.3.a -->

Spring AOP is proxy-based (`spring-fw-aop-pfb#page-title`).

Spring AOP defaults to using standard JDK dynamic proxies for AOP proxies (`spring-fw-aop-pfb#page-title`).

JDK dynamic proxies enable any interface, or set of interfaces, to be proxied (`spring-fw-aop-pfb#page-title`).

Spring AOP can also use CGLIB proxies, which are necessary to proxy classes rather than interfaces (`spring-fw-aop-pfb#page-title`).

By default, CGLIB is used if a business object does not implement an interface (`spring-fw-aop-pfb#page-title`).

If the target object implements at least one interface, a JDK dynamic proxy is used, and all of the interfaces implemented by the target type are proxied (`spring-fw-aop-proxying#proxying-mechanisms`).

If the target object does not implement any interfaces, a CGLIB proxy is created, which is a runtime-generated subclass of the target type (`spring-fw-aop-proxying#proxying-mechanisms`).

You can force the use of CGLIB proxying, for example to proxy every method defined for the target object, not only those implemented by its interfaces (`spring-fw-aop-proxying#proxying-mechanisms`).

To force CGLIB proxies, set the value of the `proxy-target-class` attribute of the `<aop:config>` element to `true` (`spring-fw-aop-proxying#aop-forcing-proxy-types`).

`@EnableAspectJAutoProxy`, `@EnableTransactionManagement` and related configuration annotations offer a corresponding `proxyTargetClass` attribute (`spring-fw-aop-proxying#aop-forcing-proxy-types`).

The core framework suggests interface-based proxies by default, but Spring Boot may, depending on configuration properties, enable class-based proxies by default (`spring-fw-aop-proxying#aop-forcing-proxy-types`).

As of 7.0, `@Proxyable` on a `@Bean` method or `@Component` class forces a specific proxy type, with `@Proxyable(INTERFACES)` or `@Proxyable(TARGET_CLASS)` overriding any globally configured default (`spring-fw-aop-proxying#aop-forcing-proxy-types`).

Once the call has reached the target object, any method calls it makes on itself, such as `this.bar()` or `this.foo()`, are invoked against the `this` reference and not the proxy (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

Self invocation via an explicit or implicit `this` reference bypasses the advice (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

The best approach is to refactor your code so that the self invocation does not happen (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

The documentation calls refactoring the best, least-invasive approach (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

An alternative approach is to make use of self injection, and invoke methods on the proxy via the self reference instead of via `this` (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

`AopContext.currentProxy()` totally couples your code to Spring AOP, and the documentation highly discourages it (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

`AopContext.currentProxy()` also requires that the `ProxyFactory` is configured to expose the proxy (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

AspectJ compile-time weaving and load-time weaving do not have the self-invocation issue because they apply advice within the bytecode instead of via a proxy (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

## Limits of proxies
<!-- bullets: 5.3.b -->

`final` classes cannot be proxied, because they cannot be extended (`spring-fw-aop-proxying#proxying-mechanisms`).

`final` methods cannot be advised, because they cannot be overridden (`spring-fw-aop-proxying#proxying-mechanisms`).

`private` methods cannot be advised, because they cannot be overridden (`spring-fw-aop-proxying#proxying-mechanisms`).

Methods that are not visible, for example package-private methods in a parent class from a different package, cannot be advised because they are effectively private (`spring-fw-aop-proxying#proxying-mechanisms`).

The constructor of your proxied object is not called twice, since the CGLIB proxy instance is created through Objenesis (`spring-fw-aop-proxying#proxying-mechanisms`).

If your JVM does not allow for constructor bypassing, you might see double invocations and corresponding debug log entries from Spring's AOP support (`spring-fw-aop-proxying#proxying-mechanisms`).

You cannot create a CGLIB proxy for a class from the `java.lang` package when deploying on the module path (`spring-fw-aop-proxying#proxying-mechanisms`).

The proxy must be fully initialized to provide the expected behavior, so you should not rely on `@Transactional` in your initialization code (`spring-fw-tx-declarative-annotations#using-transactional`).

The `@Transactional` annotation is typically used on methods with public visibility (`spring-fw-tx-declarative-annotations#using-transactional`).

As of 6.0, protected or package-visible methods can also be made transactional for class-based proxies by default (`spring-fw-tx-declarative-annotations#using-transactional`).

Transactional methods in interface-based proxies must always be public and defined in the proxied interface (`spring-fw-tx-declarative-annotations#using-transactional`).

A class-level `@Transactional` annotation does not apply to ancestor classes up the class hierarchy (`spring-fw-tx-declarative-annotations#using-transactional`).

The Spring team recommends that you annotate methods of concrete classes with `@Transactional`, rather than relying on annotated methods in interfaces (`spring-fw-tx-declarative-annotations#using-transactional`).

## Proxy-based annotations and their ordering
<!-- bullets: 5.3.c -->

In proxy mode, which is the default, only external method calls coming in through the proxy are intercepted (`spring-fw-tx-declarative-annotations#using-transactional`).

The mere presence of the `@Transactional` annotation is not enough to activate the transactional behavior (`spring-fw-tx-declarative-annotations#using-transactional`).

You make the bean instance transactional through an `@EnableTransactionManagement` annotation in a `@Configuration` class (`spring-fw-tx-declarative-annotations#using-transactional`).

Consider using AspectJ mode if you expect self-invocations to be wrapped with transactions as well (`spring-fw-tx-declarative-annotations#using-transactional`).

The default advice mode for processing `@Transactional` annotations is proxy, which allows for interception of calls through the proxy only (`spring-fw-tx-declarative-annotations#using-transactional`).

`@Async` makes the caller return immediately, while the actual execution of the method occurs in a task submitted to a Spring `TaskExecutor` (`spring-fw-async#scheduling-annotation-support-async`).

A method that returns a value can be invoked asynchronously only if it has a `Future`-typed return value (`spring-fw-async#scheduling-annotation-support-async`).

`@Async` methods may declare `CompletableFuture` as a return type as well as a regular `Future` (`spring-fw-async#scheduling-annotation-support-async`).

You can not use `@Async` in conjunction with lifecycle callbacks such as `@PostConstruct` (`spring-fw-async#scheduling-annotation-support-async`).

`@Cacheable` demarcates methods for which the result is stored in the cache, so that later invocations with the same arguments return the cached value without invoking the method (`spring-fw-cache-annotations#cache-annotations-cacheable`).

`@Retryable` specifies retry characteristics for an individual method, or for all proxy-invoked methods in a given class hierarchy when it is declared at the type level (`spring-fw-resilience#resilience-annotations-retryable`).

By default, the invocation is retried for any exception thrown, with at most 3 retry attempts after an initial failure and a delay of 1 second between attempts (`spring-fw-resilience#resilience-annotations-retryable`).

A `@Retryable` method is invoked at least once and retried at most `maxRetries` times, where `maxRetries` is the maximum number of retry attempts (`spring-fw-resilience#resilience-annotations-retryable`).

Total attempts are 1 initial attempt plus `maxRetries` attempts (`spring-fw-resilience#resilience-annotations-retryable`).

If `maxRetries` is set to 4, the `@Retryable` method is invoked at least once and at most 5 times (`spring-fw-resilience#resilience-annotations-retryable`).

If all attempts have failed and the retry policy has been exhausted, the last original exception from the target method is propagated to the caller (`spring-fw-resilience#resilience-annotations-retryable`).

When `@Async` is combined with `@Retryable`, the async advice is applied outermost, so all retry attempts run on the async executor thread (`spring-fw-async#scheduling-annotation-support-async`).

When `@Cacheable` is combined with `@Retryable`, the retry advice is applied outermost, so each retry attempt checks the cache before invoking the method (`spring-fw-cache-annotations#cache-annotations-cacheable`).

When `@Transactional` is combined with `@Retryable`, the retry advice is applied outermost, so each retry attempt runs in its own transaction (`spring-fw-tx-declarative-annotations#using-transactional`).

Both the retry and the async post-processors are plain `Ordered` bean post-processors, so you can change their relative ordering by setting the `order` attribute on `@EnableResilientMethods` and/or `@EnableAsync` (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

With the reversed order, in which retry is outermost and async innermost, exceptions thrown during asynchronous execution are not retried, because the retry interceptor only sees the `Future` handle (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

Such an arrangement only retries synchronous submission failures, such as a rejected task submission, and is rarely desirable in practice (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

The technique of changing the order attribute does not apply to `@Transactional` or `@Cacheable` (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

The advisors of `@Transactional` and `@Cacheable` are registered through Spring's shared `InfrastructureAdvisorAutoProxyCreator`, whose own post-processor order is fixed at `Ordered.HIGHEST_PRECEDENCE` (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

Retry advice is always applied outside `@Transactional` and `@Cacheable`, regardless of the order configured on `@EnableResilientMethods` (`spring-fw-resilience#resilience-annotations-retryable-combining-order`).

Spring AOP follows the same precedence rules as AspectJ to determine the order of advice execution (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

When two pieces of advice defined in different aspects both need to run at the same join point, unless you specify otherwise, the order of execution is undefined (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

You control the order by implementing the `org.springframework.core.Ordered` interface in the aspect class or annotating it with the `@Order` annotation (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

Given two aspects, the aspect returning the lower value from `Ordered.getOrder()`, or the annotation value, has the higher precedence (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

Advice methods defined in the same `@Aspect` class are assigned precedence by advice type, from highest to lowest: `@Around`, `@Before`, `@After`, `@AfterReturning`, `@AfterThrowing` (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

Two pieces of the same type of advice in the same `@Aspect` class have an undefined order, since there is no way to retrieve the source code declaration order through reflection for javac-compiled classes (`spring-fw-aop-ataspectj-advice-ordering#aop-ataspectj-advice-ordering`).

## Key points

- Spring AOP is proxy-based. A target that implements an interface gets a JDK dynamic proxy by default; otherwise it gets a CGLIB proxy, a runtime-generated subclass.
- The core framework suggests interface-based proxies by default, and Spring Boot may enable class-based proxies by default.
- Self invocation through `this` bypasses the advice; refactoring so that it does not happen is the best, least-invasive approach.
- `final` classes, `final` methods and `private` methods cannot be proxied or advised by CGLIB.
- The proxy must be fully initialized, so `@Transactional` is not reliable in initialization code.
- `@Async` cannot be used with lifecycle callbacks such as `@PostConstruct`.
- A `@Retryable` method is invoked at most `maxRetries` plus one times.
- Retry advice is always applied outside `@Cacheable` and `@Transactional`; with `@Async`, the async advice is outermost by default, and the `order` attributes can change that.
- Two aspects without an order have an undefined order; the lower `@Order` value has the higher precedence.
- In one `@Aspect` class, precedence by advice type runs `@Around`, `@Before`, `@After`, `@AfterReturning`, `@AfterThrowing`.

# A step-by-step framework for system design

## Requirements: SLIs, SLOs and SLAs
<!-- bullets: 9.1.a -->

:::judgement{source="Google, Site Reliability Engineering, chapter on service level objectives" ref="sre-book-slo#indicators-o8seIAcZ"}
According to Google's Site Reliability Engineering book, an SLI is a service level indicator: a carefully defined quantitative measure of some aspect of the level of service that is provided. Most services consider request latency, how long it takes to return a response to a request, as a key SLI. Other common SLIs include the error rate, often expressed as a fraction of all requests received, and system throughput, typically measured in requests per second.
:::

:::judgement{source="Google, Site Reliability Engineering, chapter on service level objectives" ref="sre-book-slo#indicators-o8seIAcZ"}
According to the same book, another kind of SLI important to SREs is availability, or the fraction of the time that a service is usable. It is often defined in terms of the fraction of well-formed requests that succeed, sometimes called yield, and the industry commonly expresses high-availability values in terms of the number of "nines": availabilities of 99% and 99.999% can be referred to as "2 nines" and "5 nines" availability, respectively.
:::

:::judgement{source="Google, Site Reliability Engineering, chapter on service level objectives" ref="sre-book-slo#objectives-g0s1tdcz"}
According to the same book, an SLO is a service level objective: a target value or range of values for a service level that is measured by an SLI. A natural structure for SLOs is thus SLI ≤ target, or lower bound ≤ SLI ≤ upper bound.
:::

:::judgement{source="Google, Site Reliability Engineering, chapter on service level objectives" ref="sre-book-slo#agreements-q8sZhAcV"}
According to the same book, SLAs are service level agreements: an explicit or implicit contract with your users that includes consequences of meeting (or missing) the SLOs they contain. An easy way to tell an SLO from an SLA is to ask what happens if the SLOs aren't met: if there is no explicit consequence, you are almost certainly looking at an SLO. SRE doesn't typically get involved in constructing SLAs, because SLAs are closely tied to business and product decisions.
:::

:::judgement{source="Google, The Site Reliability Workbook, chapter on implementing SLOs" ref="sre-workbook-implementing-slos#reliability-targets-and-error-budgets"}
According to Google's Site Reliability Workbook, experience has shown that 100% reliability is the wrong target. The number one source of outages is change, and as you go from 99% to 99.9% to 99.99% reliability, each extra nine comes at an increased cost, but the marginal utility to your customers steadily approaches zero. Once you have an SLO target below 100%, it needs to be owned by someone in the organization who is empowered to make tradeoffs between feature velocity and reliability.
:::

## Latency percentiles
<!-- bullets: 9.1.a -->

The φ-quantile is the observation value that ranks at number φ*N among the N observations (`prom-histograms#quantiles`).

The 0.95-quantile is also called the 95th percentile (`prom-histograms#quantiles`).

Histograms expose bucketed observation counts and the calculation of quantiles from the buckets of a histogram happens on the Prometheus server using the histogram_quantile() function (`prom-histograms#quantiles`).

Summaries calculate streaming φ-quantiles within the instrumented program and expose them directly (`prom-histograms#quantiles`).

You cannot use a summary if you need to aggregate the observations from a number of instances (`prom-histograms#errors-of-quantile-estimation`).

Quantiles, whether calculated by the instrumented binary or on the Prometheus server, are estimated (`prom-histograms#errors-of-quantile-estimation`).

When all observations fall into the classic histogram bucket from 200ms to 300ms, the interpolation estimates the 95th percentile at 295ms, with the guarantee that the true value is between 200ms and 300ms (`prom-histograms#errors-of-quantile-estimation`).

## Back-of-the-envelope capacity estimation
<!-- bullets: 9.1.b -->

The O'Neil paper that introduces the LSM-tree sizes an index this way: entries are generated 1000 per second, over a 20 day period of accumulation, with eight hour days and 16 byte index entries, which implies 576,000,000 entries on 9.2 GBytes of disk, or about 2.3 million pages needed on the index leaf level (`paper-oneil-lsm-tree#p3`).

The snippet repeats that arithmetic from the stated assumptions and, as one more assumption, a page of 4,000 bytes.

```java snippet=m09-l01/IndexCapacity.java
import java.util.Locale;

public class IndexCapacity {
    public static void main(String[] args) {
        long entriesPerSecond = 1_000;
        long secondsPerDay = 8 * 3_600;
        long days = 20;
        long entryBytes = 16;
        long pageBytes = 4_000;

        long entries = entriesPerSecond * secondsPerDay * days;
        long bytes = entries * entryBytes;
        System.out.println("seconds per day: " + secondsPerDay);
        System.out.println("entries: " + entries);
        System.out.println("bytes: " + bytes);
        System.out.println(String.format(Locale.ROOT, "gigabytes: %.1f", bytes / 1e9));
        System.out.println("leaf pages: " + bytes / pageBytes);
    }
}
```

An eight-hour day is 28800 seconds, so the snippet prints `seconds per day: 28800`.

The 1000 entries per second over 20 days of 28800 seconds make 576000000 entries, so the snippet prints `entries: 576000000`.

At 16 bytes per entry, 576000000 entries are 9216000000 bytes, so the snippet prints `bytes: 9216000000`.

The 9216000000 bytes are 9.2 gigabytes, so the snippet prints `gigabytes: 9.2`.

With a page of 4,000 bytes, the 9216000000 bytes fill 2304000 leaf pages, so the snippet prints `leaf pages: 2304000`.

A second estimate starts from traffic: 10 million users a day, 5 writes per user per day, 10 reads per write, a peak of 3 times the average, 1,000 bytes per record and 3 replicas.

```java snippet=m09-l01/TrafficEstimate.java
import java.util.Locale;

public class TrafficEstimate {
    public static void main(String[] args) {
        long dailyUsers = 10_000_000;
        long writesPerUserPerDay = 5;
        long readsPerWrite = 10;
        long peakFactor = 3;
        long recordBytes = 1_000;
        long secondsPerDay = 86_400;
        long replicas = 3;

        long writesPerDay = dailyUsers * writesPerUserPerDay;
        long readsPerDay = writesPerDay * readsPerWrite;
        System.out.println("writes per day: " + writesPerDay);
        System.out.println("average writes per second: " + writesPerDay / secondsPerDay);
        System.out.println("peak writes per second: " + writesPerDay * peakFactor / secondsPerDay);
        System.out.println("average reads per second: " + readsPerDay / secondsPerDay);
        System.out.println("peak reads per second: " + readsPerDay * peakFactor / secondsPerDay);
        double gigabytesPerDay = writesPerDay * recordBytes / 1e9;
        System.out.println(String.format(Locale.ROOT, "gigabytes per day: %.0f", gigabytesPerDay));
        System.out.println(String.format(Locale.ROOT, "terabytes per year: %.2f", gigabytesPerDay * 365 / 1000));
        System.out.println(String.format(Locale.ROOT, "terabytes per year with %d replicas: %.2f", replicas, gigabytesPerDay * 365 * replicas / 1000));
    }
}
```

The 10 million users make 50 million writes a day, so the snippet prints `writes per day: 50000000`.

Spread over 86400 seconds, 50 million writes are 578 writes per second on average, so the snippet prints `average writes per second: 578`.

The peak of 3 times the average is 1736 writes per second, so the snippet prints `peak writes per second: 1736`.

At 10 reads per write, the 500 million reads a day are 5787 reads per second on average, so the snippet prints `average reads per second: 5787`.

The peak of 3 times the average is 17361 reads per second, so the snippet prints `peak reads per second: 17361`.

At 1,000 bytes per record, the 50 million writes a day add 50 gigabytes, so the snippet prints `gigabytes per day: 50`.

Over 365 days that is 18.25 terabytes, so the snippet prints `terabytes per year: 18.25`.

With 3 replicas it is 54.75 terabytes, so the snippet prints `terabytes per year with 3 replicas: 54.75`.

## API contracts and choice of storage engine
<!-- bullets: 9.1.c -->

The OpenAPI Specification (OAS) defines a standard, programming language-agnostic interface description for HTTP APIs, which allows both humans and computers to discover and understand the capabilities of a service without requiring access to source code, additional documentation, or inspection of network traffic (`openapi-spec#abstract`).

Never re-use a tag number in a Protobuf message (`protobuf-proto-best-practices#reuse-number`).

Re-using a tag number messes up deserialization (`protobuf-proto-best-practices#reuse-number`).

If the change was live ever, there could be serialized versions of your proto in a log somewhere (`protobuf-proto-best-practices#reuse-number`).

When you delete a field that’s no longer used, reserve its tag number so that no one accidentally re-uses it in the future (`protobuf-proto-best-practices#reserve-tag-numbers`).

Just `reserved 2, 3;` is enough to reserve tag numbers, and no type is required (`protobuf-proto-best-practices#reserve-tag-numbers`).

Almost never change the type of a field (`protobuf-proto-best-practices#change-type`).

An idempotency key is a unique value generated by the client which the resource uses to recognize subsequent retries of the same request (`ietf-httpapi-idempotency-key#content`).

The HTTP `Idempotency-Key` request header field carries the idempotency key (`ietf-httpapi-idempotency-key#content`).

Per RFC 9110, the methods OPTIONS, HEAD, GET, PUT and DELETE are idempotent while methods POST and PATCH are not (`ietf-httpapi-idempotency-key#content`).

If there is an attempt to reuse an idempotency key with a different request payload, the resource SHOULD reply with an HTTP 422 status code (`ietf-httpapi-idempotency-key#content`).

If the `Idempotency-Key` request header is missing for a documented idempotent operation requiring this header, the resource SHOULD reply with an HTTP 400 status code (`ietf-httpapi-idempotency-key#content`).

If the request is retried, while the original request is still being processed, the resource SHOULD reply with an HTTP 409 status code (`ietf-httpapi-idempotency-key#content`).

B-trees can handle equality and range queries on data that can be sorted into some ordering (`pg-indexes-types#INDEXES-TYPES-BTREE`).

B-tree indexes can also be used to retrieve data in sorted order (`pg-indexes-types#INDEXES-TYPES-BTREE`).

The optimizer can use a B-tree index for queries involving the pattern matching operators `LIKE` and `~` if the pattern is a constant and is anchored to the beginning of the string, such as `col LIKE 'foo%'`, but not `col LIKE '%bar'` (`pg-indexes-types#INDEXES-TYPES-BTREE`).

The LSM-tree uses an algorithm that defers and batches index changes, migrating the changes out to disk in a particularly efficient way reminiscent of merge sort (`paper-oneil-lsm-tree#p3`).

With an LSM-tree, only finds that require immediate response remain relatively costly (`paper-oneil-lsm-tree#p3`).

The LSM-tree access method enables the frequent index inserts for an Account-ID||Timestamp index with much less disk arm use, therefore at an order of magnitude lower cost (`paper-oneil-lsm-tree#p3`).

## High-level architecture and end-to-end data flow
<!-- bullets: 9.1.d -->

:::judgement{source="Microsoft, Azure Well-Architected Framework, design diagrams" ref="azure-waf-design-diagrams#high-level-system-or-container-diagram"}
According to Microsoft's Azure Well-Architected Framework, a high-level system diagram provides a broad overview of an entire workload or a major subsection within a workload. It decomposes the workload into its main components, their relationships, and the general flow of data through the system, and arrows indicate the direction of interactions and dependencies.
:::

:::judgement{source="Microsoft, Azure Well-Architected Framework, design diagrams" ref="azure-waf-design-diagrams#high-level-system-or-container-diagram"}
According to the same Microsoft guidance, such a diagram is used after context alignment to expose macro structure, hosting models such as PaaS or self-managed, and external dependencies.
:::

:::judgement{source="Microsoft, Azure Well-Architected Framework, design diagrams" ref="azure-waf-design-diagrams#data-flow-diagram-dfd"}
According to Microsoft's Azure Well-Architected Framework, a data-flow diagram illustrates how data moves, transforms, is stored, and exits the system, emphasizing sources, sinks, transformation stages, classification, and whether movement is batch, streaming, or near real time.
:::

:::judgement{source="Microsoft, Azure Well-Architected Framework, design diagrams" ref="azure-waf-design-diagrams#types-of-design-diagrams"}
According to Microsoft's Azure Well-Architected Framework, to visualize a workload one should favor a minimal set of purposeful diagrams over creating every possible type, starting broad and progressively narrowing.
:::

## Key points

- The 0.95-quantile is the 95th percentile, and quantiles are estimated, whether computed by the instrumented binary or on the Prometheus server.
- Summaries cannot be aggregated across instances.
- An estimate multiplies written-down assumptions: 1000 entries per second for 20 days of eight hours at 16 bytes give 576000000 entries and 9.2 gigabytes.
- 10 million users making 5 writes a day give 578 writes per second on average and 1736 at a peak of 3 times the average.
- Never re-use a Protobuf tag number; reserve the tag numbers of deleted fields.
- An idempotency key is a unique value generated by the client that lets the resource recognize retries of the same request.
- A B-tree index supports equality, range and sorted retrieval, and an LSM-tree defers and batches index changes.

# How this course works

## Who it is for

The course is for a senior backend engineer who wants to get better at the job and reach Staff level. Interview preparation is one use of it, not its driver. There is no exam date, no call and no official exam.

You never write code here. There is no editor in the platform and no companion repository of exercises. Answers are chosen, not typed: no free-text answers, and no live model grades anything.

## The twelve modules

1. Pragmatic software design and patterns goes from design principles to auditing and defending AI-assisted code.
2. Algorithms and data structures goes from complexity and Java collections internals to the design structures common in interviews and pattern recognition.
3. Modern JVM, concurrency and performance goes from JVM internals to profiling and benchmarking, with the Java Memory Model and Project Loom in between.
4. Kotlin for Java developers goes from the type system and null safety to interoperability and migration from Java.
5. Spring Framework and Spring Boot internals goes from the IoC container to operating and testing Spring Boot applications.
6. Relational persistence, transactions and SQL optimisation goes from ACID, MVCC and PostgreSQL internals to zero-downtime schema evolution.
7. Networking and API design goes from networking fundamentals to API evolution and governance.
8. Distributed systems, messaging and resilience goes from the fundamentals of distributed systems to stream processing.
9. System design and data scalability starts with a step-by-step framework for system design and ends with storage engines and non-relational databases.
10. Platform, observability, security and AI integration goes from the observability of distributed systems to application security and the supply chain.
11. Code reading, debugging and testing goes from Java Streams in depth to advanced testing and test strategy.
12. Staff-level technical leadership goes from architecture documentation and decision making to technical strategy and large migrations.

## Where the content comes from

Each product is pinned to one version. A fact comes from a stored source for that version or from a record of running code, never from memory. When a fact differs between versions, the sentence names the version, as in "since Java 24".

Sources come in three tiers. Tier A is primary and normative: language and VM specifications, official reference documentation, RFCs, OWASP projects and freely available original papers. Tier B is books, cited by chapter for orientation only. Tier C is public reference material, such as published engineering career ladders and articles by identifiable authors.

Only Tier A supports a tested fact. Forums, Q&A sites, aggregators, anonymous blogs, tutorials and any model output are not sources.

Each lesson is checked sentence by sentence against the stored source by an agent that did not write it.

## Three kinds of content

**Fact, executable fact and judgement**

| Class | What it is | How it is checked | Can it be a question key |
|---|---|---|---|
| F, fact | A statement verifiable against a stored Tier A source for the pinned version | Sentence by sentence against the source, by a separate check | Yes |
| X, executable fact | A claim about what a Java or Kotlin snippet prints, returns or throws | The snippet is run on the pinned JDK; the snippet, the command and the hash of its output are stored | Yes |
| J, judgement | A trade-off, criterion, practice, or career or communication advice | Only that the attribution to the named source is faithful, not that the judgement is true | No |

You meet a fact with its citation inline. You meet an executable fact as a snippet that was run, and a snippet that is deliberately broken says so and records the compiler or runtime error. You meet a judgement rendered differently from the facts and attributed in the text, as in "According to …".

An executable fact is limited to code that runs with the JDK and the Kotlin compiler alone. A claim that needs a database, a broker or any external service is a fact from documentation, or it is dropped.

## How you practise

Questions come in four kinds:

- Multiple choice, with four options, one correct, an explanation and a citation. The explanation never refers to options by letter.
- Code reading: what a snippet prints, which line holds the bug, what the complexity is, which refactoring preserves behaviour.
- Generators, which produce a fresh question from a seed and compute the key in code. The explanation shows the computation.
- System-design cases, each a scenario with keyed questions. There is no free text.

Only facts and executable facts become questions. A question that fails verification is discarded, not repaired.

The presets are by lesson, by module, mixed review, code reading only and generators only. The clock stays optional.

The scheduler shows unseen questions first and shuffles the options. A failed question returns at increasing intervals. There are no streaks, no points and no reminders.

## Key points

:::note{type=info}
- The course is for a senior backend engineer. It has no coding exercises, no free-text answers and no exam.
- There are twelve modules, from pragmatic software design to Staff-level technical leadership.
- Each product is pinned to one version; a fact that differs between versions names the version.
- Only Tier A sources support a tested fact. Books are for orientation and Tier C material is judgement.
- F is a verifiable fact, X is a claim checked by running a snippet, J is an attributed judgement shown differently. Only F and X can be question keys.
- Questions are multiple choice, code reading, generators and system-design cases.
- Unseen questions come first, failed ones return at increasing intervals, and there are no streaks, points or reminders.
:::

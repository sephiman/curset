# Design structures common in interviews

## LRU cache with a linked hash map
<!-- bullets: 2.6.a -->

A `LinkedHashMap` differs from a `HashMap` in that it maintains a doubly-linked list running through all of its entries (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The linked list defines the encounter order, which is normally the order in which keys were inserted into the map (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The encounter order is not affected if a key is re-inserted into the map with the `put` method (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

A special constructor creates a linked hash map whose encounter order is the order in which its entries were last accessed, from least-recently accessed to most-recently (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

An access-ordered linked hash map is well-suited to building LRU caches (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Invoking `put`, `putIfAbsent`, `get`, `getOrDefault`, `compute`, `computeIfAbsent`, `computeIfPresent` or `merge` results in an access to the corresponding entry (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The `putAll` method generates one entry access for each mapping in the specified map (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Operations on the `keySet`, `values` and `entrySet` views do not affect the encounter order of the backing map (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

Explicit-positioning methods such as `putFirst` or `lastEntry` do not generate entry accesses (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

The `removeEldestEntry` method is invoked by `put` and `putAll` after inserting a new entry into the map (`javadoc-linkedhashmap#removeEldestEntry(java.util.Map.Entry)`).

The default `removeEldestEntry` merely returns false, so the eldest element is never removed (`javadoc-linkedhashmap#removeEldestEntry(java.util.Map.Entry)`).

Overriding `removeEldestEntry` to return `size() > MAX_ENTRIES` lets the map grow up to MAX_ENTRIES entries and then delete the eldest entry each time a new entry is added (`javadoc-linkedhashmap#removeEldestEntry(java.util.Map.Entry)`).

Like `HashMap`, a `LinkedHashMap` provides constant-time performance for the basic operations, assuming the hash function disperses elements properly among the buckets (`javadoc-linkedhashmap#class-linkedhashmap-k-v`).

In a `LinkedHashSet`, the hash table finds the relevant list node in constant time and the list node is then deleted, also in constant time (`ods-3-2-dllist-doubly-linked-li#SECTION00622000000000000000`).

Linked list structures are well-suited to applications where references to list nodes can be obtained through external means (`ods-3-2-dllist-doubly-linked-li#SECTION00622000000000000000`).

The snippet subclasses `LinkedHashMap` with the access-order constructor and a capacity of 3. It puts a, b and c, reads a, and puts d. A second map keeps insertion order and puts a again.

```java snippet=m02-l06/LruCache.java
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(16, 0.75f, true);
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }

    public static void main(String[] args) {
        LruCache<String, Integer> cache = new LruCache<>(3);
        cache.put("a", 1);
        cache.put("b", 2);
        cache.put("c", 3);
        cache.get("a");
        cache.put("d", 4);
        System.out.println("access-ordered " + List.copyOf(cache.keySet()));

        Map<String, Integer> insertionOrdered = new LinkedHashMap<>();
        insertionOrdered.put("a", 1);
        insertionOrdered.put("b", 2);
        insertionOrdered.put("c", 3);
        insertionOrdered.put("a", 4);
        System.out.println("insertion-ordered " + List.copyOf(insertionOrdered.keySet()));
    }
}
```

The cache prints `access-ordered [c, a, d]`, because b is the eldest entry when d arrives.

The second map prints `insertion-ordered [a, b, c]`.

## LFU eviction and an in-memory rate limiter
<!-- bullets: 2.6.a -->

Starting with Redis 4.0, the Least Frequently Used eviction mode is available (`redis-eviction#lfu-eviction`).

In Redis LFU mode, Redis tries to track the frequency of access of items, so the ones used rarely are evicted (`redis-eviction#lfu-eviction`).

The `allkeys-lfu` policy evicts any key using approximated LFU (`redis-eviction#lfu-eviction`).

The `volatile-lfu` policy evicts using approximated LFU among the keys with an expire set (`redis-eviction#lfu-eviction`).

Redis approximates LFU with a probabilistic counter, called a Morris counter, which estimates the access frequency using just a few bits per object (`redis-eviction#lfu-eviction`).

By default Redis decays the LFU counter every one minute (`redis-eviction#lfu-eviction`).

The LFU frequency counter is in the range 0-255 (`redis-eviction#lfu-eviction`).

A token bucket rate limiter allows controlled bursts of traffic while enforcing a steady average rate (`redis-ratelimiting-algorithms#how-it-works-3`).

In a token bucket rate limiter, each request consumes one token, and when the bucket is empty, requests are denied until more tokens refill (`redis-ratelimiting-algorithms#how-it-works-3`).

:::judgement{source="Vladimir Bukhtoyarov, Bucket4j README" ref="bucket4j-readme#top"}
According to Vladimir Bukhtoyarov, Bucket4j is a Java rate-limiting library based on the token-bucket algorithm. He writes that, besides clustered usage on top of back-ends, it supports local in-memory buckets, for cases where distributed synchronization is unnecessary.
:::

## Iterator over nested structures
<!-- bullets: 2.6.a -->

`Iterator` takes the place of `Enumeration` in the Java Collections Framework (`javadoc-iterator#interface-iterator-e`).

Iterators allow the caller to remove elements from the underlying collection during the iteration with well-defined semantics (`javadoc-iterator#interface-iterator-e`).

A recursive traversal of a binary tree can use more stack space than is available when the height of the tree is very large, causing a crash (`ods-6-1-binarytree-basic-binary#SECTION00912000000000000000`).

The maximum depth of the recursion is given by the height of the tree (`ods-6-1-binarytree-basic-binary#SECTION00912000000000000000`).

The snippet implements `Iterator<Integer>` over a list of lists. Its `hasNext` moves to the next inner list while the current one is exhausted, so empty inner lists are skipped. It keeps no recursion, only the position in the outer and the inner iterator.

```java snippet=m02-l06/NestedIterator.java
import java.util.ArrayList;
import java.util.Iterator;
import java.util.List;
import java.util.NoSuchElementException;

public class NestedIterator implements Iterator<Integer> {
    private final Iterator<List<Integer>> outer;
    private Iterator<Integer> inner = List.<Integer>of().iterator();

    NestedIterator(List<List<Integer>> nested) {
        this.outer = nested.iterator();
    }

    @Override
    public boolean hasNext() {
        while (!inner.hasNext() && outer.hasNext()) {
            inner = outer.next().iterator();
        }
        return inner.hasNext();
    }

    @Override
    public Integer next() {
        if (!hasNext()) {
            throw new NoSuchElementException();
        }
        return inner.next();
    }

    static List<Integer> drain(List<List<Integer>> nested) {
        List<Integer> values = new ArrayList<>();
        new NestedIterator(nested).forEachRemaining(values::add);
        return values;
    }

    public static void main(String[] args) {
        System.out.println("values " + drain(List.of(List.of(1, 2), List.of(), List.of(3), List.of())));
        System.out.println("values of two empty lists " + drain(List.of(List.of(), List.of())));
    }
}
```

The nested list `[[1, 2], [], [3], []]` yields `values [1, 2, 3]`.

Two empty inner lists yield `values of two empty lists []`.

## Running median with two heaps
<!-- bullets: 2.6.a -->

The elements of a `PriorityQueue` are ordered according to their natural ordering, or by a `Comparator` provided at queue construction time (`javadoc-priorityqueue#class-priorityqueue-e`).

The head of a `PriorityQueue` is the least element with respect to the specified ordering (`javadoc-priorityqueue#class-priorityqueue-e`).

The `Iterator` of a `PriorityQueue` is not guaranteed to traverse the elements in any particular order (`javadoc-priorityqueue#class-priorityqueue-e`).

A `PriorityQueue` provides O(log(n)) time for `offer`, `poll`, `remove()` and `add` (`javadoc-priorityqueue#class-priorityqueue-e`).

A `PriorityQueue` provides linear time for `remove(Object)` and `contains(Object)` (`javadoc-priorityqueue#class-priorityqueue-e`).

A `PriorityQueue` provides constant time for `peek`, `element` and `size` (`javadoc-priorityqueue#class-priorityqueue-e`).

A binary heap stores the smallest value of the priority queue at position 0, the root (`ods-10-1-binaryheap-implicit-bi#SECTION001310000000000000000`).

The first snippet adds 5, 1 and 3 to a `PriorityQueue`, prints the queue and then polls it empty.

```java snippet=m02-l06/PriorityQueueOrder.java
import java.util.ArrayList;
import java.util.List;
import java.util.PriorityQueue;

public class PriorityQueueOrder {
    public static void main(String[] args) {
        PriorityQueue<Integer> queue = new PriorityQueue<>();
        queue.add(5);
        queue.add(1);
        queue.add(3);
        System.out.println("queue as printed " + queue);

        List<Integer> polled = new ArrayList<>();
        while (!queue.isEmpty()) {
            polled.add(queue.poll());
        }
        System.out.println("queue polled " + polled);
    }
}
```

The queue prints as `queue as printed [1, 5, 3]`.

Polling returns the values as `queue polled [1, 3, 5]`.

The second snippet keeps the lower half of a stream in a `PriorityQueue` ordered largest first and the upper half in one ordered smallest first. After each value it moves one head across when needed so that the lower queue has the same size as the upper one or one element more, and it reads the median from the lower head when that queue is larger, or from the mean of the two heads when the sizes are equal.

```java snippet=m02-l06/RunningMedian.java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.PriorityQueue;

public class RunningMedian {
    private final PriorityQueue<Integer> lower = new PriorityQueue<>(Collections.reverseOrder());
    private final PriorityQueue<Integer> upper = new PriorityQueue<>();

    void add(int value) {
        if (lower.isEmpty() || value <= lower.peek()) {
            lower.add(value);
        } else {
            upper.add(value);
        }
        if (lower.size() > upper.size() + 1) {
            upper.add(lower.poll());
        } else if (upper.size() > lower.size()) {
            lower.add(upper.poll());
        }
    }

    double median() {
        return lower.size() > upper.size() ? lower.peek() : (lower.peek() + upper.peek()) / 2.0;
    }

    public static void main(String[] args) {
        RunningMedian stream = new RunningMedian();
        List<Double> medians = new ArrayList<>();
        for (int value : new int[] {5, 15, 1, 3}) {
            stream.add(value);
            medians.add(stream.median());
        }
        System.out.println("medians " + medians);
    }
}
```

For the stream 5, 15, 1, 3 it prints `medians [5.0, 10.0, 5.0, 4.0]`.

## Key points

- A `LinkedHashMap` keeps a doubly-linked list through its entries, and the access-order constructor makes it well-suited to LRU caches.
- Overriding `removeEldestEntry` to return `size() > MAX_ENTRIES` deletes the eldest entry after each `put` that passes the limit.
- Re-inserting a key with `put` does not change the encounter order of an insertion-ordered map.
- Of the cache snippet, the access-ordered map printed `[c, a, d]` and the insertion-ordered map printed `[a, b, c]`.
- An iterator over nested lists can skip empty inner lists in `hasNext` without recursion.
- A `PriorityQueue` has its least element at the head, but its iterator and `toString` do not follow the ordering, as `[1, 5, 3]` showed.
- A `PriorityQueue` takes O(log(n)) for `offer` and `poll`, linear time for `contains(Object)` and constant time for `peek`.
- The two-heap snippet printed the medians `[5.0, 10.0, 5.0, 4.0]` for the stream 5, 15, 1, 3.
- Redis offers an approximated LFU eviction mode that evicts rarely used keys, with a decay period of one minute by default.
- A token bucket rate limiter denies requests when the bucket is empty, until more tokens refill.

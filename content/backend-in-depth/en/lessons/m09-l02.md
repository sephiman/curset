# Data scalability: replication, sharding and caching

## When to scale up, replicate, partition or shard
<!-- bullets: 9.2.a -->

The benefits of partitioning will normally be worthwhile only when a table would otherwise be very large (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

The exact point at which a table will benefit from partitioning depends on the application, although a rule of thumb is that the size of the table should exceed the physical memory of the database server (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

Partitioning effectively substitutes for the upper tree levels of indexes, making it more likely that the heavily-used parts of the indexes fit in memory (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

Seldom-used data can be migrated to cheaper and slower storage media (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

:::judgement{source="Microsoft, Azure Architecture Center, data partitioning guidance" ref="azure-data-partitioning#benefits-of-data-partitioning"}
According to Microsoft's Azure Architecture Center, when you scale up a single database system, the database eventually reaches a physical hardware limit, and if you divide data across multiple partitions, with each partition hosted on a separate server, you can scale out the system almost indefinitely. It adds that operations that affect more than one partition can run in parallel, and that if one instance fails, only the data in that partition is unavailable.
:::

:::judgement{source="Microsoft, Azure Architecture Center, data partitioning guidance" ref="azure-data-partitioning#select-the-right-partitioning-strategy"}
According to the same guidance, there are three typical strategies for partitioning data. In horizontal partitioning, often called sharding, each partition is a separate data store with the same schema. In vertical partitioning, each partition holds a subset of the fields of the items. In functional partitioning, data is aggregated according to how each bounded context in the system uses the data.
:::

Data partitioning splits tables into data sets, and each set can be modified by only one server (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

Multiple-server parallel query execution is usually accomplished by splitting the data among servers and having each server execute its part of the query and return results to a central server where they are combined and returned to the user (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

## Partitioning a table in PostgreSQL
<!-- bullets: 9.2.a 9.2.c -->

Partitioning refers to splitting what is logically one large table into smaller physical pieces (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

:::esquema{kind=tabla title="Built-in forms of partitioning in PostgreSQL"}
| Form | How rows are assigned | Source |
|---|---|---|
| Range | The table is partitioned into ranges defined by a key column or set of columns, with no overlap between the ranges of values assigned to different partitions | `pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW` |
| List | The table is partitioned by explicitly listing which key values appear in each partition | `pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW` |
| Hash | Each partition holds the rows for which the hash value of the partition key divided by the specified modulus produces the specified remainder | `pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW` |
:::

Each range's bounds are understood as being inclusive at the lower end and exclusive at the upper end (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

For example, if one partition's range is from 1 to 10, and the next one's range is from 10 to 20, then value 10 belongs to the second partition not the first (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

In hash partitioning, the table is partitioned by specifying a modulus and a remainder for each partition (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

Dropping an individual partition using DROP TABLE, or doing ALTER TABLE DETACH PARTITION, is far faster than a bulk operation (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

These commands also entirely avoid the VACUUM overhead caused by a bulk DELETE (`pg-ddl-partitioning#DDL-PARTITIONING-OVERVIEW`).

The partitioned table itself is a “virtual” table having no storage of its own (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

Instead, the storage belongs to partitions, which are otherwise-ordinary tables associated with the partitioned table (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

All rows inserted into a partitioned table will be routed to the appropriate one of the partitions based on the values of the partition key column(s) (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

Updating the partition key of a row will cause it to be moved into a different partition if it no longer satisfies the partition bounds of its original partition (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

It is not possible to turn a regular table into a partitioned table or vice versa (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

However, it is possible to add an existing regular or partitioned table as a partition of a partitioned table, or remove a partition from a partitioned table turning it into a standalone table (`pg-ddl-partitioning#DDL-PARTITIONING-DECLARATIVE`).

## Replication in PostgreSQL
<!-- bullets: 9.2.b -->

Write-ahead log shipping can be synchronous or asynchronous and can only be done for the entire database server (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

Logical replication allows replication of data changes on a per-table basis (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

A server that is publishing its own changes can also subscribe to changes from another server, allowing data to flow in multiple directions (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

Logical replication uses a publish and subscribe model with one or more subscribers subscribing to one or more publications on a publisher node (`pg-logical-replication#LOGICAL-REPLICATION`).

The subscriber applies the data in the same order as the publisher so that transactional consistency is guaranteed for publications within a single subscription (`pg-logical-replication#LOGICAL-REPLICATION`).

The standby connects to the primary, which streams WAL records to the standby as they're generated, without waiting for the WAL file to be filled (`pg-warm-standby#STREAMING-REPLICATION`).

PostgreSQL streaming replication is asynchronous by default (`pg-warm-standby#SYNCHRONOUS-REPLICATION`).

The delay between committing a transaction in the primary and the changes becoming visible in the standby is typically under one second assuming the standby is powerful enough to keep up with the load (`pg-warm-standby#STREAMING-REPLICATION`).

If the primary server crashes then some transactions that were committed may not have been replicated to the standby server, causing data loss (`pg-warm-standby#SYNCHRONOUS-REPLICATION`).

The amount of data loss is proportional to the replication delay at the time of failover (`pg-warm-standby#SYNCHRONOUS-REPLICATION`).

When requesting synchronous replication, each commit of a write transaction will wait until confirmation is received that the commit has been written to the write-ahead log on disk of both the primary and standby server (`pg-warm-standby#SYNCHRONOUS-REPLICATION`).

The only possibility that data can be lost is if both the primary and the standby suffer crashes at the same time (`pg-warm-standby#SYNCHRONOUS-REPLICATION`).

The minimum wait time is the round-trip time between primary and standby (`pg-warm-standby#SYNCHRONOUS-REPLICATION`).

Read-only transactions and transaction rollbacks need not wait for replies from standby servers (`pg-warm-standby#SYNCHRONOUS-REPLICATION`).

Subtransaction commits do not wait for responses from standby servers, only top-level commits (`pg-warm-standby#SYNCHRONOUS-REPLICATION`).

Long running actions such as data loading or index building do not wait until the very final commit message (`pg-warm-standby#SYNCHRONOUS-REPLICATION`).

## Multi-leader replication and handling replication lag
<!-- bullets: 9.2.b -->

Using asynchronous multimaster replication, each server works independently, and periodically communicates with the other servers to identify conflicting transactions (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

The conflicts can be resolved by users or conflict resolution rules (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

In synchronous multimaster replication, each server can accept write requests, and modified data is transmitted from the original server to every other server before each transaction commits (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

Heavy write activity can cause excessive locking and commit delays, leading to poor performance (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

PostgreSQL does not offer this type of replication, though PostgreSQL two-phase commit (PREPARE TRANSACTION and COMMIT PREPARED) can be used to implement this in application code or middleware (`pg-different-replication-solutions#DIFFERENT-REPLICATION-SOLUTIONS`).

On a hot standby, the WAL-logged action already occurred on the primary so the standby must not fail to apply it (`pg-hot-standby#HOT-STANDBY-CONFLICT`).

Application of a vacuum cleanup record from WAL conflicts with standby transactions whose snapshots can still “see” any of the rows to be removed (`pg-hot-standby#HOT-STANDBY-CONFLICT`).

Allowing WAL application to wait indefinitely may be very undesirable, because the standby's state will become increasingly far behind the primary's (`pg-hot-standby#HOT-STANDBY-CONFLICT`).

The standby server must either delay application of the WAL records (and everything after them, too) or else cancel the conflicting query so that the DROP TABLE can be applied (`pg-hot-standby#HOT-STANDBY-CONFLICT`).

## Replication in Redis and Elasticsearch
<!-- bullets: 9.2.b -->

Every Redis master has a replication ID: it is a large pseudo random string that marks a given history of the dataset (`redis-replication#how-redis-replication-works`).

Each master also takes an offset that increments for every byte of replication stream that it is produced to be sent to replicas, to update the state of the replicas with the new changes modifying the dataset (`redis-replication#how-redis-replication-works`).

When replicas connect to masters, they use the PSYNC command to send their old master replication ID and the offsets they processed so far (`redis-replication#how-redis-replication-works`).

If there is not enough backlog in the master buffers, or if the replica is referring to an history (replication ID) which is no longer known, then a full resynchronization happens (`redis-replication#how-redis-replication-works`).

The master starts a background saving process to produce an RDB file (`redis-replication#how-redis-replication-works`).

If the master receives multiple concurrent replica synchronization requests, it performs a single background save in to serve all of them (`redis-replication#how-redis-replication-works`).

Every indexing operation in Elasticsearch is first resolved to a replication group using routing, typically based on the document ID (`es-reading-and-writing-documents#basic-write-model`).

The primary shard is responsible for validating the operation and forwarding it to the other replicas (`es-reading-and-writing-documents#basic-write-model`).

Since replicas can be offline, the primary is not required to replicate to all replicas (`es-reading-and-writing-documents#basic-write-model`).

The primary shard has to replicate all operations to each copy in the in-sync copies, the set of "good" shard copies that are guaranteed to have processed all of the index and delete operations that have been acknowledged to the user (`es-reading-and-writing-documents#basic-write-model`).

Once all in-sync replicas have successfully performed the operation and responded to the primary, the primary acknowledges the successful completion of the request to the client (`es-reading-and-writing-documents#basic-write-model`).

Each primary stage will not complete until the in-sync replicas have finished indexing the docs locally and responded to the replica requests (`es-reading-and-writing-documents#basic-write-model`).

The coordinating stage is not complete until each primary stage, which may be spread out across different primary shards, has completed (`es-reading-and-writing-documents#basic-write-model`).

## Leaderless replication and quorums
<!-- bullets: 9.2.b -->

Dynamo provides eventual consistency, which allows for updates to be propagated to all replicas asynchronously (`paper-dynamo#p6`).

Each data item in Dynamo is replicated at N hosts, where N is a parameter configured “per-instance” (`paper-dynamo#p6`).

A typical value of N used by Dynamo’s users is 3 (`paper-dynamo#p10`).

R is the minimum number of nodes that must participate in a successful read operation (`paper-dynamo#p7`).

W is the minimum number of nodes that must participate in a successful write operation (`paper-dynamo#p7`).

Setting R and W such that R + W > N yields a quorum-like system (`paper-dynamo#p7`).

```java snippet=m09-l02/QuorumOverlap.java
public class QuorumOverlap {
    record Setting(int replicas, int readQuorum, int writeQuorum) {
        boolean overlaps() {
            return readQuorum + writeQuorum > replicas;
        }
    }

    public static void main(String[] args) {
        Setting[] settings = {
            new Setting(3, 2, 2),
            new Setting(3, 1, 1),
            new Setting(3, 1, 3),
            new Setting(3, 2, 1),
            new Setting(5, 3, 3),
            new Setting(5, 2, 2),
        };
        for (Setting s : settings) {
            System.out.println("N=" + s.replicas() + " R=" + s.readQuorum() + " W=" + s.writeQuorum()
                    + " R+W=" + (s.readQuorum() + s.writeQuorum()) + " overlap=" + s.overlaps());
        }
    }
}
```

With N=3, R=2 and W=2 the sum is 4, so the snippet prints `N=3 R=2 W=2 R+W=4 overlap=true`.

With N=3, R=1 and W=1 the sum is 2, so the snippet prints `N=3 R=1 W=1 R+W=2 overlap=false`.

With N=3, R=1 and W=3 the sum is 4, so the snippet prints `N=3 R=1 W=3 R+W=4 overlap=true`.

With N=3, R=2 and W=1 the sum is 3, which is not greater than N, so the snippet prints `N=3 R=2 W=1 R+W=3 overlap=false`.

With N=5, R=3 and W=3 the sum is 6, so the snippet prints `N=5 R=3 W=3 R+W=6 overlap=true`.

With N=5, R=2 and W=2 the sum is 4, so the snippet prints `N=5 R=2 W=2 R+W=4 overlap=false`.

Dynamo uses a “sloppy quorum”: all read and write operations are performed on the first N healthy nodes from the preference list, which may not always be the first N nodes encountered while walking the consistent hashing ring (`paper-dynamo#p8`).

Applications that need the highest level of availability can set W to 1, which ensures that a write is accepted as long as a single node in the system has durably written the key to its local store (`paper-dynamo#p8`).

## Sharding with hash slots
<!-- bullets: 9.2.c -->

Redis Cluster does not use consistent hashing, but a different form of sharding where every key is conceptually part of what we call a hash slot (`redis-scaling#redis-cluster-data-sharding`).

There are 16384 hash slots in Redis Cluster, and to compute the hash slot for a given key, we simply take the CRC16 of the key modulo 16384 (`redis-scaling#redis-cluster-data-sharding`).

14 out of 16 CRC16 output bits are used (this is why there is a modulo 16384 operation in the formula above) (`redis-cluster-spec#key-distribution-model`).

Every node in a Redis Cluster is responsible for a subset of the hash slots (`redis-scaling#redis-cluster-data-sharding`).

Moving hash slots from a node to another does not require stopping any operations; therefore, adding and removing nodes, or changing the percentage of hash slots held by a node, requires no downtime (`redis-scaling#redis-cluster-data-sharding`).

Resharding basically means to move hash slots from a set of nodes to another set of nodes (`redis-scaling#reshard-the-cluster`).

Currently there is no way for redis-cli to automatically rebalance the cluster checking the distribution of keys across the cluster nodes and intelligently moving slots as needed (`redis-scaling#reshard-the-cluster`).

Redis Cluster supports multiple key operations as long as all of the keys involved in a single command execution (or whole transaction, or Lua script execution) belong to the same hash slot (`redis-scaling#redis-cluster-data-sharding`).

Hash tags are a way to ensure that multiple keys are allocated in the same hash slot (`redis-cluster-spec#hash-tags`).

If the key contains a "{...}" pattern only the substring between { and } is hashed in order to obtain the hash slot (`redis-cluster-spec#hash-tags`).

```java snippet=m09-l02/HashSlot.java
public class HashSlot {
    static int crc16(byte[] data) {
        int crc = 0;
        for (byte b : data) {
            crc ^= (b & 0xFF) << 8;
            for (int bit = 0; bit < 8; bit++) {
                crc = (crc & 0x8000) != 0 ? (crc << 1) ^ 0x1021 : crc << 1;
                crc &= 0xFFFF;
            }
        }
        return crc;
    }

    static String hashedPart(String key) {
        int open = key.indexOf('{');
        if (open < 0) {
            return key;
        }
        int close = key.indexOf('}', open + 1);
        if (close < 0 || close == open + 1) {
            return key;
        }
        return key.substring(open + 1, close);
    }

    static int slot(String key) {
        return crc16(hashedPart(key).getBytes(java.nio.charset.StandardCharsets.UTF_8)) % 16384;
    }

    public static void main(String[] args) {
        System.out.println("crc16 of 123456789: " + Integer.toHexString(crc16("123456789".getBytes(java.nio.charset.StandardCharsets.UTF_8))).toUpperCase());
        System.out.println("slot of 123456789: " + slot("123456789"));
        System.out.println("{user1000}.following and {user1000}.followers share a slot: " + (slot("{user1000}.following") == slot("{user1000}.followers")));
        System.out.println("foo{}{bar} is hashed as a whole key: " + (slot("foo{}{bar}") != slot("bar")));
        System.out.println("foo{{bar}}zap hashes {bar: " + (slot("foo{{bar}}zap") == slot("{bar")));
        System.out.println("foo{bar}{zap} hashes bar: " + (slot("foo{bar}{zap}") == slot("bar")));
    }
}
```

The CRC16 of the string `123456789` is `31C3`, so the snippet prints `crc16 of 123456789: 31C3`.

The CRC16 value 31C3 is 12739, which is below 16384, so the snippet prints `slot of 123456789: 12739`.

Only `user1000` is hashed in both `{user1000}.following` and `{user1000}.followers`, so the snippet prints `{user1000}.following and {user1000}.followers share a slot: true`.

The first `{` of `foo{}{bar}` is followed by `}` with no characters between, so the whole key is hashed and the snippet prints `foo{}{bar} is hashed as a whole key: true`.

The substring between the first `{` and the first `}` of `foo{{bar}}zap` is `{bar`, so the snippet prints `foo{{bar}}zap hashes {bar: true`.

The algorithm stops at the first match of `{` and `}` in `foo{bar}{zap}`, so the snippet prints `foo{bar}{zap} hashes bar: true`.

## Consistent hashing and virtual nodes
<!-- bullets: 9.2.c -->

Dynamo’s partitioning scheme relies on consistent hashing to distribute the load across multiple storage hosts (`paper-dynamo#p5`).

In consistent hashing, the output range of a hash function is treated as a fixed circular space or “ring” (`paper-dynamo#p5`).

The principle advantage of consistent hashing is that departure or arrival of a node only affects its immediate neighbors and other nodes remain unaffected (`paper-dynamo#p6`).

The basic consistent hashing algorithm presents some challenges (`paper-dynamo#p6`).

The random position assignment of each node on the ring leads to non-uniform data and load distribution (`paper-dynamo#p6`).

Instead of mapping a node to a single point in the circle, each node in Dynamo gets assigned to multiple points in the ring, using the concept of “virtual nodes” (`paper-dynamo#p6`).

If a node becomes unavailable, the load handled by its virtual nodes is evenly dispersed across the remaining available nodes (`paper-dynamo#p6`).

The number of virtual nodes that a node is responsible for can be decided based on its capacity, accounting for heterogeneity in the physical infrastructure (`paper-dynamo#p6`).

## Partition keys in Elasticsearch and Kafka
<!-- bullets: 9.2.c -->

Each index in Elasticsearch is a grouping of one or more physical shards, where each shard is a self-contained Lucene index containing a subset of the documents in the index (`es-clusters-nodes-shards#elastic-docs-v3`).

Each document in an index belongs to one primary shard (`es-clusters-nodes-shards#elastic-docs-v3`).

A replica shard is a copy of a primary shard (`es-clusters-nodes-shards#elastic-docs-v3`).

The number of primary shards in an index is fixed at the time that an index is created, but the number of replica shards can be changed at any time, without interrupting indexing or query operations (`es-clusters-nodes-shards#elastic-docs-v3`).

Kafka exposes the interface for semantic partitioning by allowing the user to specify a key to partition by and using this to hash to a partition (`kafka-design#load-balancing`).

If the key chosen was a user id then all data for a given user would be sent to the same partition (`kafka-design#load-balancing`).

:::judgement{source="Microsoft, Azure Architecture Center, data partitioning guidance" ref="azure-data-partitioning#horizontal-partitioning-sharding"}
According to Microsoft's Azure Architecture Center, the most important factor in sharding is the sharding key, which can be difficult to change after the system is in operation and must spread the workload as evenly as possible across the shards. It gives range sharding by the first letter of a customer's name as an example of a key that creates hot partitions, because some letters are more common than others, and recommends a customer identifier hash instead.
:::

:::judgement{source="Microsoft, Azure Architecture Center, data partitioning guidance" ref="azure-data-partitioning#rebalance-partitions"}
According to the same guidance, as a system matures individual partitions might start receiving a disproportionate volume of traffic and become hot, or approach capacity limits. Some data stores, such as Azure Cosmos DB, can rebalance partitions automatically; otherwise rebalancing means determining a new partitioning strategy and then migrating data, either offline, with the partitions unavailable, or online, while they are in use.
:::

## Distributed caching
<!-- bullets: 9.2.d -->

:::judgement{source="Amazon Web Services, Amazon ElastiCache User Guide, caching strategies" ref="aws-elasticache-caching-strategies#Strategies.LazyLoading"}
According to the Amazon ElastiCache User Guide, lazy loading is a caching strategy that loads data into the cache only when necessary: the application asks the cache first, and on a miss it reads the data store and writes the result to the cache.
:::

:::judgement{source="Amazon Web Services, Amazon ElastiCache User Guide, caching strategies" ref="aws-elasticache-caching-strategies#Strategies.LazyLoading.Evaluation"}
According to the same guide, the disadvantages of lazy loading are the cache miss penalty, where each miss results in three trips, and stale data, because there are no updates to the cache when data is changed in the database.
:::

:::judgement{source="Amazon Web Services, Amazon ElastiCache User Guide, caching strategies" ref="aws-elasticache-caching-strategies#Strategies.WriteThrough"}
According to the same guide, the write-through strategy adds data or updates data in the cache whenever data is written to the database.
:::

:::judgement{source="Amazon Web Services, Amazon ElastiCache User Guide, caching strategies" ref="aws-elasticache-caching-strategies#Strategies.WriteThrough.Evaluation"}
According to the same guide, with write-through the data in the cache is never stale and every write involves two trips, but a new node is missing data until it is added or updated on the database, and most data is never read, which is a waste of resources that adding a time to live value can minimize.
:::

:::judgement{source="Amazon Web Services, Amazon ElastiCache User Guide, caching strategies" ref="aws-elasticache-caching-strategies#Strategies.WithTTL"}
According to the same guide, adding a time to live to each write keeps data from getting too stale, although this approach does not guarantee that a value is not stale.
:::

When client-side caching is enabled, the Redis server remembers or tracks the set of keys that each client connection has previously read (`redis-client-side-caching#tracking`).

When any client writes new data to a tracked key, the server sends an invalidation message to all clients that have accessed that key previously (`redis-client-side-caching#tracking`).

This message warns the clients that their cached copies of the data are no longer valid and the clients will evict the stale data in response (`redis-client-side-caching#tracking`).

Next time a client reads from the same key, it will access the database directly and refresh its cache with the updated data (`redis-client-side-caching#tracking`).

If any connection from a client gets disconnected (including one from a connection pool), then the client will flush all keys from the client-side cache (`redis-client-side-caching#tracking`).

Caching gives the most benefit for keys that are read frequently and updated infrequently (`redis-client-side-caching#usage-recommendations`).

For data such as counters and scoreboards, the performance overhead of the invalidation messages can be greater than the savings made by caching (`redis-client-side-caching#usage-recommendations`).

If you had 10MB (or 10485760 bytes) available for the cache, and the average size of an item was 80 bytes, you could fit approximately 10485760 / 80 = 131072 items in the cache (`redis-client-side-caching#usage-recommendations`).

Use the maxmemory-policy configuration directive to select the eviction policy you want to use when the limit set by maxmemory is reached (`redis-eviction#eviction-policies`).

:::esquema{kind=tabla title="Redis eviction policies"}
| Policy | What it does | Source |
|---|---|---|
| `noeviction` | Keys are not evicted but the server will return an error when you try to execute commands that cache new data | `redis-eviction#eviction-policies` |
| `allkeys-lru` | Evict the least recently used (LRU) keys | `redis-eviction#eviction-policies` |
| `allkeys-lfu` | Evict the least frequently used (LFU) keys | `redis-eviction#eviction-policies` |
| `allkeys-random` | Evict keys at random | `redis-eviction#eviction-policies` |
| `volatile-ttl` | Evict keys with an associated expiration (TTL) that have the shortest remaining TTL value | `redis-eviction#eviction-policies` |
:::

The volatile-xxx policies behave like noeviction if no keys have an associated expiration (`redis-eviction#eviction-policies`).

allkeys-lru is a good default option if you have no reason to prefer any others (`redis-eviction#eviction-policies`).

The Redis LRU algorithm uses an approximation of the least recently used keys rather than calculating them exactly (`redis-eviction#apx-lru`).

The Redis LRU algorithm samples a small number of keys at random and then evicts the ones with the longest time since last access (`redis-eviction#apx-lru`).

The reason Redis does not use a true LRU implementation is because it costs more memory (`redis-eviction#apx-lru`).

Starting with Redis 4.0, the Least Frequently Used eviction mode is available (`redis-eviction#lfu-eviction`).

By default Redis is configured to saturate the LFU counter at, around, one million requests and to decay the counter every one minute (`redis-eviction#lfu-eviction`).

The counter logarithm factor changes how many hits are needed to saturate the frequency counter, which is just in the range 0-255 (`redis-eviction#lfu-eviction`).

## Key points

- Partitioning pays off normally only when a table would otherwise be very large, with a rule of thumb that the table size should exceed the physical memory of the database server.
- PostgreSQL offers range, list and hash partitioning, and the partitioned table is a virtual table with no storage of its own.
- Range bounds are inclusive at the lower end and exclusive at the upper end.
- PostgreSQL streaming replication is asynchronous by default, and the data loss on a crash is proportional to the replication delay at the time of failover.
- With synchronous replication, each commit of a write transaction waits for the standby, and the minimum wait is the round-trip time between primary and standby.
- A hot standby must either delay applying conflicting WAL records or cancel the conflicting query.
- Redis replicas send a replication ID and an offset with PSYNC, and a full resynchronization happens when the backlog is not enough or the replication ID is unknown.
- An Elasticsearch primary acknowledges a write only after all in-sync replicas have performed it.
- Setting R and W such that R + W > N yields a quorum-like system; with N=3, R=2 and W=1 the sum is 3, so `R + W > N` does not hold.
- Redis Cluster has 16384 hash slots, computed as the CRC16 of the key modulo 16384, and hash tags put keys in the same slot.
- Moving hash slots between Redis Cluster nodes needs no downtime, and redis-cli cannot rebalance the cluster automatically.
- In Elasticsearch the number of primary shards is fixed at index creation, while the number of replica shards can change at any time.
- Redis tracking sends an invalidation message to every client that previously read a key that another client writes.
- Redis offers `noeviction` and several `allkeys-` and `volatile-` eviction policies, approximates LRU by sampling, and has offered LFU since Redis 4.0.

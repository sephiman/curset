# Operating and testing Spring Boot applications

## Exposing and securing actuator endpoints
<!-- bullets: 5.8.a -->

Exposure and access are two separate settings. Exposure decides which endpoints are exposed over HTTP and JMX, and each endpoint's `access` property sets the access permitted to it. Only the `health` endpoint is exposed by default.

By default, only the `health` endpoint is exposed over HTTP and JMX (`spring-boot-actuator-endpoints#actuator.endpoints.exposing`).

The `include` property lists the IDs of the endpoints that are exposed (`spring-boot-actuator-endpoints#actuator.endpoints.exposing`).

The `exclude` property takes precedence over the `include` property (`spring-boot-actuator-endpoints#actuator.endpoints.exposing`).

`*` can be used to select all endpoints (`spring-boot-actuator-endpoints#actuator.endpoints.exposing`).

`*` has a special meaning in YAML, so quotation marks are needed to include or exclude all endpoints in a YAML file (`spring-boot-actuator-endpoints#actuator.endpoints.exposing`).

By default, access to all endpoints except for `shutdown` and `heapdump` is unrestricted (`spring-boot-actuator-endpoints#actuator.endpoints.controlling-access`).

Access to an endpoint is configured with its `management.endpoint.<id>.access` property (`spring-boot-actuator-endpoints#actuator.endpoints.controlling-access`).

Setting `management.endpoints.access.default` to `none` makes access opt-in rather than opt-out (`spring-boot-actuator-endpoints#actuator.endpoints.controlling-access`).

Inaccessible endpoints are removed entirely from the application context (`spring-boot-actuator-endpoints#actuator.endpoints.controlling-access`).

:::esquema{kind=tabla title="Exposure and access of actuator endpoints"}
| Setting | What it decides | Default | Source |
|---|---|---|---|
| `management.endpoints.web.exposure.include` and `exclude` | Which endpoints are exposed over HTTP | Only `health` is exposed | `spring-boot-actuator-endpoints#actuator.endpoints.exposing` |
| `management.endpoints.jmx.exposure.include` and `exclude` | Which endpoints are exposed over JMX | Only `health` is exposed | `spring-boot-actuator-endpoints#actuator.endpoints.exposing` |
| `management.endpoint.<id>.access` | The access permitted to one endpoint | Unrestricted, except for `shutdown` and `heapdump` | `spring-boot-actuator-endpoints#actuator.endpoints.controlling-access` |
:::

If Spring Security is on the classpath and no other `SecurityFilterChain` bean is present, all actuators other than `/health` are secured by Spring Boot auto-configuration (`spring-boot-actuator-endpoints#actuator.endpoints.security`).

If you define a custom `SecurityFilterChain` bean, Spring Boot auto-configuration backs off and lets you fully control the actuator access rules (`spring-boot-actuator-endpoints#actuator.endpoints.security`).

## Health information and health groups
<!-- bullets: 5.8.a -->

The health endpoint reports a system health. Indicators supply individual statuses and a `StatusAggregator` combines them into one status. Groups select subsets of the indicators.

The default value of `management.endpoint.health.show-details` is `never` (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

:::esquema{kind=tabla title="Values of management.endpoint.health.show-details"}
| Value | Who sees the details | Source |
|---|---|---|
| `never` | Details are never shown | `spring-boot-actuator-endpoints#actuator.endpoints.health` |
| `when-authorized` | Details are shown only to authorized users | `spring-boot-actuator-endpoints#actuator.endpoints.health` |
| `always` | Details are shown to all users | `spring-boot-actuator-endpoints#actuator.endpoints.health` |
:::

If the endpoint has no configured roles, which is the default, all authenticated users are considered authorized (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

A `HealthContributor` can be either a `HealthIndicator` or a `CompositeHealthContributor` (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

A `HealthIndicator` provides actual health information, including a `Status` (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

A `CompositeHealthContributor` provides a composite of other `HealthContributor` instances (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

By default, the final system health is derived by a `StatusAggregator`, which sorts the statuses from each `HealthIndicator` based on an ordered list of statuses (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

The first status in the sorted list is used as the overall health status (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

If no `HealthIndicator` returns a status that is known to the `StatusAggregator`, an `UNKNOWN` status is used (`spring-boot-actuator-endpoints#actuator.endpoints.health`).

To create a health indicator group, you can use the `management.endpoint.health.group.<name>` property and specify a list of health indicator IDs to include or exclude (`spring-boot-actuator-endpoints#actuator.endpoints.health.groups`).

```yaml
management:
  endpoint:
    health:
      group:
        custom:
          include: "db"
```

A group named `custom` that includes only the `db` indicator is available at `/actuator/health/custom` (`spring-boot-actuator-endpoints#actuator.endpoints.health.groups`).

By default, startup will fail if a health group includes or excludes a health indicator that does not exist (`spring-boot-actuator-endpoints#actuator.endpoints.health.groups`).

Setting `management.endpoint.health.validate-group-membership` to `false` disables that failure (`spring-boot-actuator-endpoints#actuator.endpoints.health.groups`).

By default, groups inherit the same `StatusAggregator` and `HttpCodeStatusMapper` settings as the system health (`spring-boot-actuator-endpoints#actuator.endpoints.health.groups`).

A group can override the `show-details` and `roles` properties (`spring-boot-actuator-endpoints#actuator.endpoints.health.groups`).

## Metrics and observability
<!-- bullets: 5.8.a -->

An application registers custom metrics through a `MeterRegistry`, and tags let a meter be drilled down dimensionally. Observability consists of logging, metrics and traces, and Micrometer Observation produces metrics and traces from one observation.

Navigating to `/actuator/metrics` displays a list of available meter names (`spring-boot-actuator-metrics#actuator.metrics.endpoint`).

A particular meter is selected by providing its name as a selector, and `tag=KEY:VALUE` query parameters drill down on it dimensionally (`spring-boot-actuator-metrics#actuator.metrics.endpoint`).

The selector must match the name used in the code, not the name after it has been normalized for a monitoring system (`spring-boot-actuator-metrics#actuator.metrics.endpoint`).

To register custom metrics, you inject a `MeterRegistry` into your component (`spring-boot-actuator-metrics#actuator.metrics.registering-custom`).

If your metrics depend on other beans, a `MeterBinder` is recommended to register them, and the metrics of all `MeterBinder` beans are automatically bound to the Spring-managed `MeterRegistry` by default (`spring-boot-actuator-metrics#actuator.metrics.registering-custom`).

You can register any number of `MeterRegistryCustomizer` beans to further configure the registry, such as applying common tags, before any meters are registered with the registry (`spring-boot-actuator-metrics#actuator.metrics.getting-started`).

Observability is the ability to observe the internal state of a running system from the outside (`spring-boot-actuator-observability#page-title`).

Observability consists of the three pillars: logging, metrics and traces (`spring-boot-actuator-observability#page-title`).

For metrics and traces, Spring Boot uses Micrometer Observation (`spring-boot-actuator-observability#page-title`).

To create your own observations, you inject an `ObservationRegistry` (`spring-boot-actuator-observability#page-title`).

Low cardinality tags will be added to metrics and traces, while high cardinality tags will only be added to traces (`spring-boot-actuator-observability#page-title`).

## Start-up events and runners
<!-- bullets: 5.8.b -->

A `SpringApplication` announces each stage of its start-up with an event. Some of the events come before the `ApplicationContext` is created, so a bean cannot listen to them. Tasks expected to run during startup belong in runners.

In addition to the usual Spring Framework events, such as `ContextRefreshedEvent`, a `SpringApplication` sends some additional application events (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

Some events are triggered before the `ApplicationContext` is created, so you cannot register a listener on those as a `@Bean` (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationStartingEvent` is sent at the start of a run but before any processing, except for the registration of listeners and initializers (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationEnvironmentPreparedEvent` is sent when the `Environment` to be used in the context is known but before the context is created (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationContextInitializedEvent` is sent when the `ApplicationContext` is prepared and `ApplicationContextInitializer` instances have been called but before any bean definitions are loaded (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationPreparedEvent` is sent just before the refresh is started but after bean definitions have been loaded (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

A `ContextRefreshedEvent` is published after `ApplicationPreparedEvent` and before `ApplicationStartedEvent` (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationStartedEvent` is sent after the context has been refreshed but before any application and command-line runners have been called (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `AvailabilityChangeEvent` is sent right after `ApplicationStartedEvent` with `LivenessState.CORRECT` to indicate that the application is considered as live (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationReadyEvent` is sent after any application and command-line runners have been called (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `AvailabilityChangeEvent` is sent right after `ApplicationReadyEvent` with `ReadinessState.ACCEPTING_TRAFFIC` to indicate that the application is ready to service requests (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

An `ApplicationFailedEvent` is sent if there is an exception on startup (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

The snippet starts a non-web `SpringApplication` with one listener that prints the application events, the `ContextRefreshedEvent` and the availability changes, and with one `ApplicationRunner` that prints a line.

```java snippet=m05-l08/StartupEvents.java
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.Banner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.WebApplicationType;
import org.springframework.boot.availability.AvailabilityChangeEvent;
import org.springframework.boot.context.event.SpringApplicationEvent;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.event.ContextRefreshedEvent;

public class StartupEvents {
    @Configuration
    static class App {
        @Bean
        ApplicationRunner runner() {
            return args -> System.out.println("runner called");
        }
    }

    public static void main(String[] args) {
        SpringApplication application = new SpringApplication(App.class);
        application.setWebApplicationType(WebApplicationType.NONE);
        application.setBannerMode(Banner.Mode.OFF);
        application.setLogStartupInfo(false);
        application.addListeners(event -> {
            if (event instanceof SpringApplicationEvent || event instanceof ContextRefreshedEvent) {
                System.out.println(event.getClass().getSimpleName());
            } else if (event instanceof AvailabilityChangeEvent<?> change) {
                System.out.println("AvailabilityChangeEvent " + change.getState());
            }
        });
        application.run(args).close();
    }
}
```

The program prints `ApplicationStartingEvent`, `ApplicationEnvironmentPreparedEvent`, `ApplicationContextInitializedEvent`, `ApplicationPreparedEvent`, `ContextRefreshedEvent` and `ApplicationStartedEvent`, then `AvailabilityChangeEvent CORRECT`, then `runner called`, then `ApplicationReadyEvent` and `AvailabilityChangeEvent ACCEPTING_TRAFFIC`, each on its own line.

:::diagram{kind="flow" caption="Order of the application events during start-up"}
description: ApplicationStartingEvent, ApplicationEnvironmentPreparedEvent, ApplicationContextInitializedEvent, ApplicationPreparedEvent, ContextRefreshedEvent, ApplicationStartedEvent, the runners, and ApplicationReadyEvent, in that order.
starting: ApplicationStartingEvent
environment: ApplicationEnvironmentPreparedEvent
initialized: ApplicationContextInitializedEvent
prepared: ApplicationPreparedEvent
refreshed: ContextRefreshedEvent
started: ApplicationStartedEvent
runners: Application and command-line runners
ready: ApplicationReadyEvent
starting -> environment
environment -> initialized
initialized -> prepared
prepared -> refreshed
refreshed -> started
started -> runners
runners -> ready
:::

Event listeners should not run potentially lengthy tasks as they execute in the same thread by default (`spring-boot-features-spring-application#features.spring-application.application-events-and-listeners`).

The `ApplicationRunner` and `CommandLineRunner` interfaces both offer a single `run` method, which is called just before `SpringApplication.run(…)` completes (`spring-boot-features-spring-application#features.spring-application.command-line-runner`).

If several runner beans must be called in a specific order, they additionally implement the `Ordered` interface or use the `@Order` annotation (`spring-boot-features-spring-application#features.spring-application.command-line-runner`).

Tasks expected to run during startup should be executed by `CommandLineRunner` and `ApplicationRunner` components instead of using Spring component lifecycle callbacks such as `@PostConstruct` (`spring-boot-features-spring-application#features.spring-application.application-availability.readiness`).

## Availability states and probes
<!-- bullets: 5.8.b -->

Spring Boot tracks two availability states, liveness and readiness, and actuator exposes both as health groups. Liveness tells whether the application works or can recover by itself, and readiness tells whether it is ready to handle traffic.

Spring Boot includes out-of-the box support for the commonly used “liveness” and “readiness” availability states (`spring-boot-features-spring-application#features.spring-application.application-availability`).

If you are using Spring Boot’s “actuator” support then the liveness and readiness states are exposed as health endpoint groups (`spring-boot-features-spring-application#features.spring-application.application-availability`).

The “Liveness” state of an application tells whether its internal state allows it to work correctly, or recover by itself if it is currently failing (`spring-boot-features-spring-application#features.spring-application.application-availability.liveness`).

An application is considered live as soon as the context has been refreshed (`spring-boot-features-spring-application#features.spring-application.application-availability.liveness`).

The “Readiness” state of an application tells whether the application is ready to handle traffic (`spring-boot-features-spring-application#features.spring-application.application-availability.readiness`).

An application is considered ready as soon as application and command-line runners have been called (`spring-boot-features-spring-application#features.spring-application.application-availability.readiness`).

Application components can retrieve the current availability state by injecting the `ApplicationAvailability` interface and calling methods on it (`spring-boot-features-spring-application#features.spring-application.application-availability.managing`).

If deployed in a Kubernetes environment, actuator gathers the liveness and readiness information from the `ApplicationAvailability` interface and uses it in `LivenessStateHealthIndicator` and `ReadinessStateHealthIndicator` (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes`).

The probes are exposed as the health groups `/actuator/health/liveness` and `/actuator/health/readiness`, and these groups can be disabled with `management.endpoint.health.probes.enabled` (`spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes`).

:::esquema{kind=tabla title="Availability states while a Spring Boot application starts and shuts down"}
| Phase | Liveness state | Readiness state | HTTP server | Source |
|---|---|---|---|---|
| Starting | `BROKEN` | `REFUSING_TRAFFIC` | Not started | `spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.lifecycle` |
| Started | `CORRECT` | `REFUSING_TRAFFIC` | Refuses requests | `spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.lifecycle` |
| Ready | `CORRECT` | `ACCEPTING_TRAFFIC` | Accepts requests | `spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.lifecycle` |
| Graceful shutdown | `CORRECT` | `REFUSING_TRAFFIC` | New requests are rejected | `spring-boot-actuator-endpoints#actuator.endpoints.kubernetes-probes.lifecycle` |
:::

## Exit codes and graceful shutdown
<!-- bullets: 5.8.b -->

On exit, a shutdown hook closes the `ApplicationContext`, and beans can supply the exit code. Graceful shutdown gives existing requests a grace period to complete while no new requests are permitted.

Each `SpringApplication` registers a shutdown hook with the JVM to ensure that the `ApplicationContext` closes gracefully on exit (`spring-boot-features-spring-application#features.spring-application.application-exit`).

Beans may implement the `ExitCodeGenerator` interface if they wish to return a specific exit code when `SpringApplication.exit()` is called (`spring-boot-features-spring-application#features.spring-application.application-exit`).

An exception may implement `ExitCodeGenerator`, and Spring Boot then returns the exit code provided by its `getExitCode()` method (`spring-boot-features-spring-application#features.spring-application.application-exit`).

If there is more than one `ExitCodeGenerator`, the first non-zero exit code that is generated is used (`spring-boot-features-spring-application#features.spring-application.application-exit`).

The snippet starts a fresh non-web application three times and passes different generators to `SpringApplication.exit`.

```java snippet=m05-l08/ExitCodes.java
import org.springframework.boot.Banner;
import org.springframework.boot.ExitCodeGenerator;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.WebApplicationType;
import org.springframework.context.annotation.Configuration;

public class ExitCodes {
    @Configuration
    static class App {}

    static int exitCode(ExitCodeGenerator... generators) {
        SpringApplication application = new SpringApplication(App.class);
        application.setWebApplicationType(WebApplicationType.NONE);
        application.setBannerMode(Banner.Mode.OFF);
        application.setLogStartupInfo(false);
        return SpringApplication.exit(application.run(), generators);
    }

    public static void main(String[] args) {
        ExitCodeGenerator ok = () -> 0;
        ExitCodeGenerator three = () -> 3;
        ExitCodeGenerator five = () -> 5;
        System.out.println(exitCode(ok, three, five));
        System.out.println(exitCode(five, ok, three));
        System.out.println(exitCode(ok));
    }
}
```

The program prints `3`, `5` and `0`, each on its own line.

Graceful shutdown is enabled by default with all three embedded web servers (Jetty, Reactor Netty, and Tomcat) and with both reactive and servlet-based web applications (`spring-boot-web-graceful-shutdown#page-title`).

Graceful shutdown occurs as part of closing the application context and is performed in the earliest phase of stopping `SmartLifecycle` beans (`spring-boot-web-graceful-shutdown#page-title`).

The stop processing uses a timeout that provides a grace period during which existing requests are allowed to complete but no new requests are permitted (`spring-boot-web-graceful-shutdown#page-title`).

The timeout is configured with the `spring.lifecycle.timeout-per-shutdown-phase` property (`spring-boot-web-graceful-shutdown#page-title`).

Shutdown in your IDE may be immediate rather than graceful if it does not send a proper SIGTERM signal (`spring-boot-web-graceful-shutdown#page-title`).

The exact way in which new requests are not permitted varies depending on the web server that is being used (`spring-boot-web-graceful-shutdown#web.graceful-shutdown.rejecting-requests-during-the-grace-period`).

Jetty, Reactor Netty, and Tomcat will stop accepting new requests at the network layer (`spring-boot-web-graceful-shutdown#web.graceful-shutdown.rejecting-requests-during-the-grace-period`).

Setting `server.shutdown` to `immediate` disables graceful shutdown (`spring-boot-web-graceful-shutdown#web.graceful-shutdown.disabling-graceful-shutdown`).

## Test slices and @SpringBootTest
<!-- bullets: 5.8.c -->

A test slice restricts component scan and loads a very restricted set of auto-configuration classes. `@SpringBootTest` sets up a mock web environment by default, and its `webEnvironment` attribute changes that.

Each test slice restricts component scan to appropriate components and loads a very restricted set of auto-configuration classes (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-tests`).

Including multiple slices by using several `@…Test` annotations in one test is not supported (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-tests`).

Regular `@Component` and `@ConfigurationProperties` beans are not scanned when the `@WebMvcTest` annotation is used (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.spring-mvc-tests`).

`@WebMvcTest` is often limited to a single controller and is used in combination with `@MockitoBean` to provide mock implementations for required collaborators (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.spring-mvc-tests`).

You can use the `@DataJpaTest` annotation from the `spring-boot-data-jpa-test` module to test Data JPA applications (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

By default, `@DataJpaTest` scans for `@Entity` classes and configures Spring Data JPA repositories (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

If an embedded database is available on the classpath, `@DataJpaTest` configures one as well (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

Regular `@Component` and `@ConfigurationProperties` beans are not scanned when the `@DataJpaTest` annotation is used (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

By default, data JPA tests are transactional and roll back at the end of each test (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.autoconfigured-spring-data-jpa`).

By default, `@SpringBootTest` does not start the server but instead sets up a mock environment for testing web endpoints (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.with-mock-environment`).

With Spring MVC, we can query our web endpoints using `MockMvc` (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.with-mock-environment`).

:::esquema{kind=tabla title="The webEnvironment modes of @SpringBootTest"}
| Mode | What it provides | Source |
|---|---|---|
| `MOCK` (default) | A web `ApplicationContext` and a mock web environment, with no embedded server started | `spring-boot-testing-spring-boot-applications#page-title` |
| `RANDOM_PORT` | A real web environment with embedded servers listening on a random port | `spring-boot-testing-spring-boot-applications#page-title` |
| `DEFINED_PORT` | A real web environment with embedded servers on the defined port or on the default port of 8080 | `spring-boot-testing-spring-boot-applications#page-title` |
| `NONE` | An `ApplicationContext` loaded by `SpringApplication`, with no web environment | `spring-boot-testing-spring-boot-applications#page-title` |
:::

If a test is `@Transactional` and uses `RANDOM_PORT` or `DEFINED_PORT`, any transaction initiated on the server does not roll back, because the HTTP client and the server run in separate threads and so in separate transactions (`spring-boot-testing-spring-boot-applications#page-title`).

A nested `@TestConfiguration` class is used in addition to the application's primary configuration, unlike a nested `@Configuration` class, which would be used instead of it (`spring-boot-testing-spring-boot-applications#testing.spring-boot-applications.detecting-configuration`).

## The test context cache
<!-- bullets: 5.8.c -->

The TestContext framework keeps loaded contexts and reuses them for tests with the same configuration. The cache is static and bounded, so the way tests are configured and run decides whether it helps.

Once the TestContext framework loads an `ApplicationContext` for a test, that context is cached and reused for all subsequent tests that declare the same unique context configuration within the same test suite (`spring-fw-testing-ctx-caching#page-title`).

The unique combination of configuration parameters is used to generate the key under which the context is cached (`spring-fw-testing-ctx-caching#page-title`).

The context cache key includes `@DynamicPropertySource` methods and bean overrides such as `@TestBean`, `@MockitoBean` and `@MockitoSpyBean` (`spring-fw-testing-ctx-caching#page-title`).

The Spring TestContext framework stores application contexts in a static cache (`spring-fw-testing-ctx-caching#page-title`).

If tests run in separate processes, the static cache is cleared between each test execution, which effectively disables the caching mechanism (`spring-fw-testing-ctx-caching#page-title`).

The size of the context cache is bounded with a default maximum size of 32 (`spring-fw-testing-ctx-caching#page-title`).

Whenever the maximum size is reached, a least recently used (LRU) eviction policy is used to evict and close stale contexts (`spring-fw-testing-ctx-caching#page-title`).

The maximum size can be configured by setting the JVM system property `spring.test.context.cache.maxSize` (`spring-fw-testing-ctx-caching#page-title`).

`@DirtiesContext` instructs Spring to remove the context from the cache and rebuild the application context before running the next test that requires the same application context (`spring-fw-testing-ctx-caching#page-title`).

## Testcontainers and service connections
<!-- bullets: 5.8.c -->

Testcontainers manages services running inside Docker containers. Spring Boot can manage those containers as beans and connect the application to them through service connections.

The Testcontainers library provides a way to manage services running inside Docker containers, and it is especially useful for integration tests that talk to a real backend service (`spring-boot-testing-testcontainers#page-title`).

The containers provided by Testcontainers can be managed by Spring Boot as beans (`spring-boot-testing-testcontainers#testing.testcontainers.spring-beans`).

When the containers are managed by Spring as beans, their lifecycle is managed by Spring (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Container beans are created and started before all other beans (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Container beans are stopped after the destruction of all other beans (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Container beans are created and started once per application context managed by Spring’s TestContext Framework (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Container beans are stopped as part of the TestContext Framework’s standard application context shutdown process (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Having containers managed by Testcontainers instead of as Spring beans provides no guarantee of the order in which beans and containers will shutdown (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

Containers can be shut down before the beans relying on container functionality are cleaned up, which can lead to exceptions thrown by client beans (`spring-boot-testing-testcontainers#testing.testcontainers.lifecycle`).

A service connection is a connection to any remote service (`spring-boot-testing-testcontainers#testing.testcontainers.service-connections`).

When a service connection is used, the connection details take precedence over any connection-related configuration properties (`spring-boot-testing-testcontainers#testing.testcontainers.service-connections`).

Annotating the container field in the test class with `@ServiceConnection` creates connection details automatically for a service running in a container (`spring-boot-testing-testcontainers#testing.testcontainers.service-connections`).

You need to add the `spring-boot-testcontainers` module as a test dependency in order to use service connections with Testcontainers (`spring-boot-testing-testcontainers#testing.testcontainers.service-connections`).

By default, with the exception of `RabbitStreamConnectionDetails`, all applicable connection details beans are created for a given container, so a `PostgreSQLContainer` creates both `JdbcConnectionDetails` and `R2dbcConnectionDetails` (`spring-boot-testing-testcontainers#testing.testcontainers.service-connections`).

For a `@Bean` method, Spring Boot uses the return type of the method to find out which connection details to use, and this stops working for a `GenericContainer` (`spring-boot-testing-testcontainers#testing.testcontainers.service-connections`).

A static `@DynamicPropertySource` method is a slightly more verbose but also more flexible alternative to service connections (`spring-boot-testing-testcontainers#testing.testcontainers.dynamic-properties`).

## Key points

- By default, only the `health` endpoint is exposed over HTTP and JMX, and `exclude` takes precedence over `include`.
- Access to endpoints is unrestricted by default except for `shutdown` and `heapdump`, and an inaccessible endpoint is removed from the application context.
- The default value of `management.endpoint.health.show-details` is `never`.
- A `StatusAggregator` derives the system health from the `HealthIndicator` statuses, and `UNKNOWN` is used when none is known.
- Startup fails by default when a health group includes or excludes an indicator that does not exist.
- Spring Boot auto-configuration secures all actuators other than `/health` when Spring Security is present and no custom `SecurityFilterChain` bean exists.
- Low cardinality tags are added to metrics and traces, and high cardinality tags only to traces.
- `ApplicationStartedEvent` is sent after the context refresh and before the runners, and `ApplicationReadyEvent` after the runners.
- Liveness and readiness are exposed as health endpoint groups when the actuator is used, and an application is live once the context is refreshed and ready once the runners have been called.
- With several `ExitCodeGenerator` instances, the first non-zero exit code that is generated is used.
- Graceful shutdown is enabled by default with Jetty, Reactor Netty and Tomcat, and it stops accepting new requests at the network layer.
- A test slice restricts component scan and loads a very restricted set of auto-configuration classes.
- `@SpringBootTest` uses the `MOCK` web environment by default, and a nested `@TestConfiguration` class is used in addition to the primary configuration.
- The test context cache is static, bounded to 32 contexts by default, and evicts the least recently used one.
- Container beans are started before all other beans and stopped after their destruction.
- `@ServiceConnection` creates connection details that take precedence over connection-related configuration properties.

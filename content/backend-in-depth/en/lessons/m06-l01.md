# ACID, MVCC and PostgreSQL internals

## MVCC in PostgreSQL 18
<!-- bullets: 6.1.a -->

PostgreSQL maintains data consistency internally with a multiversion model, Multiversion Concurrency Control (MVCC) (`pg-mvcc-intro#MVCC-INTRO`).

Under MVCC, each SQL statement sees a snapshot of data as it was some time ago, regardless of the current state of the underlying data (`pg-mvcc-intro#MVCC-INTRO`).

Locks acquired for reading data do not conflict with locks acquired for writing data, so reading never blocks writing and writing never blocks reading (`pg-mvcc-intro#MVCC-INTRO`).

PostgreSQL keeps that guarantee at the strictest isolation level too, through Serializable Snapshot Isolation (SSI) (`pg-mvcc-intro#MVCC-INTRO`).

Every table row starts with a fixed-size header, which occupies 23 bytes on most machines (`pg-storage-page-layout#STORAGE-TUPLE-LAYOUT`).

In that header, `t_xmin` holds the insert XID stamp and `t_xmax` holds the delete XID stamp (`pg-storage-page-layout#STORAGE-TUPLE-LAYOUT`).

The header field `t_ctid` holds the current TID of this row version or of a newer one (`pg-storage-page-layout#STORAGE-TUPLE-LAYOUT`).

## Write-ahead logging
<!-- bullets: 6.1.a -->

The central concept of Write-Ahead Logging (WAL) is that changes to data files must be written only after those changes have been logged (`pg-wal-intro#WAL-INTRO`).

Logged means that the WAL records describing the changes have been flushed to permanent storage (`pg-wal-intro#WAL-INTRO`).

With this procedure PostgreSQL does not need to flush data pages to disk on every transaction commit (`pg-wal-intro#WAL-INTRO`).

After a crash, any change not yet applied to the data pages can be redone from the WAL records; this is roll-forward recovery, also known as REDO (`pg-wal-intro#WAL-INTRO`).

All data recorded by a committed transaction should be stored in a nonvolatile area that is safe from power loss, operating system failure and hardware failure (`pg-wal-reliability#WAL-RELIABILITY`).

PostgreSQL typically writes 8192 bytes, or 16 sectors of 512 bytes, at a time, and a power loss can leave some of those sectors written and others not (`pg-wal-reliability#WAL-RELIABILITY`).

To guard against partial page writes, PostgreSQL periodically writes full page images to permanent WAL storage before it modifies the actual page on disk (`pg-wal-reliability#WAL-RELIABILITY`).

Each individual record in a WAL file is protected by a CRC-32C check (`pg-wal-reliability#WAL-RELIABILITY`).

Data pages are checksummed by default (`pg-wal-reliability#WAL-RELIABILITY`).

## Dead tuples, VACUUM and bloat
<!-- bullets: 6.1.b -->

An `UPDATE` or `DELETE` of a row does not immediately remove the old version of the row (`pg-routine-vacuuming#VACUUM-FOR-SPACE-RECOVERY`).

The old version stays because the row version must not be deleted while it is still potentially visible to other transactions (`pg-routine-vacuuming#VACUUM-FOR-SPACE-RECOVERY`).

Standard `VACUUM` removes dead row versions in tables and indexes and marks the space available for future reuse (`pg-routine-vacuuming#VACUUM-FOR-SPACE-RECOVERY`).

Standard `VACUUM` does not return the space to the operating system, except when one or more pages at the end of a table become entirely free and an exclusive table lock can be easily obtained (`pg-routine-vacuuming#VACUUM-FOR-SPACE-RECOVERY`).

Standard `VACUUM` can run in parallel with production operations: `SELECT`, `INSERT`, `UPDATE` and `DELETE` continue to function normally (`pg-routine-vacuuming#VACUUM-BASICS`).

`VACUUM FULL` writes a complete new version of the table file with no dead space, and it needs extra disk space for the new copy until the operation completes (`pg-routine-vacuuming#VACUUM-FOR-SPACE-RECOVERY`).

`VACUUM FULL` requires an `ACCESS EXCLUSIVE` lock on the table, so it cannot run in parallel with other use of the table (`pg-routine-vacuuming#VACUUM-BASICS`).

If a table has an unexpected spike in update activity under a fixed vacuum schedule, it may get bloated to the point that `VACUUM FULL` is really necessary to reclaim space (`pg-routine-vacuuming#VACUUM-FOR-SPACE-RECOVERY`).

:::judgement{source="PostgreSQL 18 documentation, Routine Vacuuming" ref="pg-routine-vacuuming#VACUUM-FOR-SPACE-RECOVERY"}
According to the PostgreSQL 18 documentation, moderately frequent standard `VACUUM` runs are a better approach than infrequent `VACUUM FULL` runs for maintaining heavily updated tables.
:::

## Autovacuum and its settings
<!-- bullets: 6.1.b -->

Autovacuum automates the execution of `VACUUM` and `ANALYZE` commands (`pg-routine-vacuuming#AUTOVACUUM`).

In the default configuration, autovacuuming is enabled (`pg-routine-vacuuming#AUTOVACUUM`).

Autovacuum cannot be used unless `track_counts` is set to true (`pg-routine-vacuuming#AUTOVACUUM`).

A persistent autovacuum launcher process starts autovacuum worker processes for all databases (`pg-routine-vacuuming#AUTOVACUUM`).

Autovacuum never issues `VACUUM FULL` (`pg-routine-vacuuming#VACUUM-FOR-SPACE-RECOVERY`).

A table is vacuumed when the number of tuples obsoleted since the last `VACUUM` exceeds the vacuum threshold (`pg-routine-vacuuming#AUTOVACUUM`).

```text
vacuum threshold = Minimum(vacuum max threshold,
                           vacuum base threshold + vacuum scale factor * number of tuples)
```

The number of tuples in that formula is `pg_class.reltuples` (`pg-routine-vacuuming#AUTOVACUUM`).

The settings can be overridden per table through storage parameters (`pg-routine-vacuuming#AUTOVACUUM`).

:::esquema{kind=tabla title="Autovacuum defaults in PostgreSQL 18"}
| Setting | Default | Source |
|---|---|---|
| `autovacuum_vacuum_threshold` | 50 tuples | `pg-runtime-config-autovacuum#RUNTIME-CONFIG-AUTOVACUUM` |
| `autovacuum_vacuum_scale_factor` | 0.2, which is 20% of table size | `pg-runtime-config-autovacuum#RUNTIME-CONFIG-AUTOVACUUM` |
| `autovacuum_vacuum_max_threshold` | 100,000,000 tuples | `pg-runtime-config-autovacuum#RUNTIME-CONFIG-AUTOVACUUM` |
| `autovacuum_analyze_scale_factor` | 0.1, which is 10% of table size | `pg-runtime-config-autovacuum#RUNTIME-CONFIG-AUTOVACUUM` |
| `autovacuum_max_workers` | 3 | `pg-runtime-config-autovacuum#RUNTIME-CONFIG-AUTOVACUUM` |
| `autovacuum_naptime` | one minute | `pg-runtime-config-autovacuum#RUNTIME-CONFIG-AUTOVACUUM` |
:::

Autovacuum does not process partitioned tables directly, but it does process their partitions like other tables (`pg-routine-vacuuming#AUTOVACUUM`).

If a process requests a lock that conflicts with the `SHARE UPDATE EXCLUSIVE` lock held by autovacuum, the lock acquisition interrupts the autovacuum (`pg-routine-vacuuming#AUTOVACUUM`).

An autovacuum that runs to prevent transaction ID wraparound is not automatically interrupted (`pg-routine-vacuuming#AUTOVACUUM`).

## Transaction ID wraparound
<!-- bullets: 6.1.b -->

Transaction IDs have a limited size of 32 bits (`pg-routine-vacuuming#VACUUM-FOR-WRAPAROUND`).

A cluster that runs for more than 4 billion transactions would suffer transaction ID wraparound, where the XID counter wraps around to zero (`pg-routine-vacuuming#VACUUM-FOR-WRAPAROUND`).

After wraparound, transactions that were in the past appear to be in the future, which makes their output invisible (`pg-routine-vacuuming#VACUUM-FOR-WRAPAROUND`).

To avoid this, every table in every database must be vacuumed at least once every two billion transactions (`pg-routine-vacuuming#VACUUM-FOR-WRAPAROUND`).

Normal XIDs are compared using modulo-2^32 arithmetic, so each normal XID has two billion XIDs that are older and two billion that are newer (`pg-routine-vacuuming#VACUUM-FOR-WRAPAROUND`).

`VACUUM` marks rows as frozen, which indicates that the inserting transaction committed far enough in the past for its effects to be visible to all current and future transactions (`pg-routine-vacuuming#VACUUM-FOR-WRAPAROUND`).

PostgreSQL reserves a special XID, `FrozenTransactionId`, which is always considered older than every normal XID (`pg-routine-vacuuming#VACUUM-FOR-WRAPAROUND`).

A table whose `relfrozenxid` is more than `autovacuum_freeze_max_age` transactions old is always vacuumed (`pg-routine-vacuuming#AUTOVACUUM`).

The default of `autovacuum_freeze_max_age` is 200 million transactions (`pg-runtime-config-autovacuum#RUNTIME-CONFIG-AUTOVACUUM`).

The system launches autovacuum processes to prevent wraparound even when `autovacuum` is disabled (`pg-runtime-config-autovacuum#RUNTIME-CONFIG-AUTOVACUUM`).

## Isolation levels in PostgreSQL 18
<!-- bullets: 6.1.c -->

The SQL standard defines four levels of transaction isolation, and the strictest is Serializable (`pg-transaction-iso#TRANSACTION-ISO`).

The other three levels are defined in terms of phenomena that must not occur at each level (`pg-transaction-iso#TRANSACTION-ISO`).

A dirty read is a transaction reading data written by a concurrent uncommitted transaction (`pg-transaction-iso#TRANSACTION-ISO`).

A phantom read is a transaction re-executing a query that returns a set of rows satisfying a search condition and finding that the set has changed because of another recently committed transaction (`pg-transaction-iso#TRANSACTION-ISO`).

PostgreSQL accepts a request for any of the four standard levels, but internally implements only three distinct ones (`pg-transaction-iso#TRANSACTION-ISO`).

PostgreSQL's Read Uncommitted mode behaves like Read Committed (`pg-transaction-iso#TRANSACTION-ISO`).

:::esquema{kind=tabla title="Phenomena per isolation level in PostgreSQL 18"}
| Level | Dirty read | Nonrepeatable read | Phantom read | Serialization anomaly | Source |
|---|---|---|---|---|---|
| Read uncommitted | Allowed, but not in PG | Possible | Possible | Possible | `pg-transaction-iso#TRANSACTION-ISO` |
| Read committed | Not possible | Possible | Possible | Possible | `pg-transaction-iso#TRANSACTION-ISO` |
| Repeatable read | Not possible | Not possible | Allowed, but not in PG | Possible | `pg-transaction-iso#TRANSACTION-ISO` |
| Serializable | Not possible | Not possible | Not possible | Not possible | `pg-transaction-iso#TRANSACTION-ISO` |
:::

## Read Committed
<!-- bullets: 6.1.c -->

Read Committed is the default isolation level in PostgreSQL (`pg-transaction-iso#XACT-READ-COMMITTED`).

In Read Committed, a `SELECT` query without a `FOR UPDATE` or `FOR SHARE` clause sees only data committed before the query began (`pg-transaction-iso#XACT-READ-COMMITTED`).

Two successive `SELECT` commands in one Read Committed transaction can see different data, if other transactions commit changes after the first `SELECT` starts and before the second starts (`pg-transaction-iso#XACT-READ-COMMITTED`).

When an `UPDATE` finds a target row that a concurrent transaction has already updated, it waits for that transaction to commit or roll back (`pg-transaction-iso#XACT-READ-COMMITTED`).

If the first updater commits, the second updater re-evaluates the `WHERE` clause on the updated version of the row and proceeds only if that version still matches (`pg-transaction-iso#XACT-READ-COMMITTED`).

An updating command in Read Committed can see the effects of concurrent updating commands on the rows it is updating, but not their effects on other rows (`pg-transaction-iso#XACT-READ-COMMITTED`).

## Repeatable Read
<!-- bullets: 6.1.c -->

A Repeatable Read transaction sees only data committed before the transaction began (`pg-transaction-iso#XACT-REPEATABLE-READ`).

Its snapshot is taken at the start of the first non-transaction-control statement in the transaction (`pg-transaction-iso#XACT-REPEATABLE-READ`).

Repeatable Read prevents all the phenomena of the isolation table except serialization anomalies (`pg-transaction-iso#XACT-REPEATABLE-READ`).

If a concurrent transaction commits an update or delete of a row that a Repeatable Read transaction tries to modify, the Repeatable Read transaction is rolled back (`pg-transaction-iso#XACT-REPEATABLE-READ`).

```text
ERROR: could not serialize access due to concurrent update
```

Applications using Repeatable Read must be prepared to retry transactions due to serialization failures (`pg-transaction-iso#XACT-REPEATABLE-READ`).

Read-only transactions at this level never have serialization conflicts (`pg-transaction-iso#XACT-REPEATABLE-READ`).

PostgreSQL implements Repeatable Read with a technique known as Snapshot Isolation (`pg-transaction-iso#XACT-REPEATABLE-READ`).

## Serializable
<!-- bullets: 6.1.c -->

The Serializable level works exactly like Repeatable Read, except that it also monitors for conditions that could make a set of concurrent serializable transactions behave inconsistently with all serial executions (`pg-transaction-iso#XACT-SERIALIZABLE`).

This monitoring introduces no blocking beyond that present in Repeatable Read, but it has some overhead (`pg-transaction-iso#XACT-SERIALIZABLE`).

To guarantee true serializability, PostgreSQL uses predicate locking (`pg-transaction-iso#XACT-SERIALIZABLE`).

In PostgreSQL, predicate locks do not cause any blocking and therefore cannot play any part in causing a deadlock (`pg-transaction-iso#XACT-SERIALIZABLE`).

Predicate locks show up in the `pg_locks` system view with a mode of `SIReadLock` (`pg-transaction-iso#XACT-SERIALIZABLE`).

When the monitoring detects a possible serialization anomaly, it triggers a serialization failure that always returns SQLSTATE `40001` (`pg-transaction-iso#XACT-SERIALIZABLE`).

Two serializable transactions that each sum one class of rows and insert the result into the other class can both commit under Repeatable Read, but under Serializable one of them is rolled back (`pg-transaction-iso#XACT-SERIALIZABLE`).

```text
ERROR: could not serialize access due to read/write dependencies among transactions
```

A `SERIALIZABLE READ ONLY DEFERRABLE` transaction blocks until it can establish that it is safe from such conflicts (`pg-transaction-iso#XACT-SERIALIZABLE`).

This is the only case where Serializable transactions block but Repeatable Read transactions do not (`pg-transaction-iso#XACT-SERIALIZABLE`).

The Serializable level is implemented with a technique known as Serializable Snapshot Isolation, which builds on Snapshot Isolation by adding checks for serialization anomalies (`pg-transaction-iso#XACT-SERIALIZABLE`).

:::judgement{source="PostgreSQL 18 documentation, Transaction Isolation" ref="pg-transaction-iso#XACT-SERIALIZABLE"}
According to the PostgreSQL 18 documentation, balanced against the cost and blocking of explicit locks and `SELECT FOR UPDATE`, Serializable transactions are the best performance choice for some environments.
:::

## Key points

- PostgreSQL keeps row versions, so each statement sees a snapshot and reading never blocks writing.
- Changes to data files are written only after the WAL records describing them have been flushed.
- An `UPDATE` or `DELETE` leaves the old row version in place until `VACUUM` removes it.
- Standard `VACUUM` marks space for reuse and runs alongside normal operations; `VACUUM FULL` rewrites the table and needs an `ACCESS EXCLUSIVE` lock.
- Autovacuum is enabled by default and never issues `VACUUM FULL`.
- Transaction IDs are 32 bits, and every table must be vacuumed at least once every two billion transactions.
- Read Committed is the default level, and Read Uncommitted behaves like it.
- Repeatable Read is Snapshot Isolation and rolls back a transaction that modifies a row changed by a concurrent commit.
- Serializable adds monitoring of read/write dependencies and fails with SQLSTATE `40001`.

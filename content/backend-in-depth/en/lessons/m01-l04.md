# Auditing and defending AI-assisted code

## Self-invocation and `@Transactional`
<!-- bullets: 1.4.b -->

Spring applies `@Transactional` through a proxy that wraps the bean. Only a call that comes in through the proxy is intercepted. A call the bean makes on itself does not pass through the proxy, so the annotation on the called method does not lead to a transaction.

Spring AOP is proxy-based (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

If the target object implements at least one interface, a JDK dynamic proxy is used, and if it implements none, a CGLIB proxy is created, which is a runtime-generated subclass of the target type (`spring-fw-aop-proxying#proxying-mechanisms`).

Client code that holds a proxy reference makes method calls on the proxy, and the proxy can delegate to all of the interceptors (advice) relevant to that method call (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

Once the call has reached the target object, any method calls it makes on itself, such as `this.bar()` or `this.foo()`, are invoked against the `this` reference and not the proxy (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

Self invocation via an explicit or implicit `this` reference bypasses the advice (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

:::diagram{kind="sequence" caption="A call through the proxy and a self-invocation inside the target"}
description: Client code calls foo on the proxy, the proxy delegates to the advice and then to the target, and the target calls bar on itself through this, which does not pass through the proxy.
client: Client code
proxy: Proxy
target: Target object
client -> proxy: foo()
proxy -> target: foo() after the advice
target -> target: this.bar()
:::

In proxy mode, which is the default, only external method calls coming in through the proxy are intercepted (`spring-fw-tx-declarative-annotations#using-transactional`).

Self-invocation, a method within the target object calling another method of the target object, does not lead to an actual transaction at runtime even if the invoked method is marked with `@Transactional` (`spring-fw-tx-declarative-annotations#using-transactional`).

The mere presence of the `@Transactional` annotation is not enough to activate the transactional behavior (`spring-fw-tx-declarative-annotations#using-transactional`).

The proxy must be fully initialized to provide the expected behavior, so the feature should not be relied on in initialization code such as a `@PostConstruct` method (`spring-fw-tx-declarative-annotations#using-transactional`).

In the documentation's examples that use programmatic configuration, the `@EnableTransactionManagement` annotation switches on actual transaction management at runtime (`spring-fw-tx-declarative-annotations#using-transactional`).

As of Spring Framework 6.0, protected or package-visible methods can also be made transactional for class-based proxies by default, while transactional methods in interface-based proxies must always be public and defined in the proxied interface (`spring-fw-tx-declarative-annotations#using-transactional`).

With CGLIB proxying, final methods and private methods cannot be advised, because they cannot be overridden (`spring-fw-aop-proxying#proxying-mechanisms`).

The Spring team recommends that you annotate methods of concrete classes with `@Transactional`, rather than relying on annotated methods in interfaces (`spring-fw-tx-declarative-annotations#using-transactional`).

Since Java annotations are not inherited from interfaces, interface-declared annotations are not recognized by the weaving infrastructure when using AspectJ mode, so the aspect does not get applied (`spring-fw-tx-declarative-annotations#using-transactional`).

As a consequence, transaction annotations may be silently ignored, and the code might appear to work until a rollback scenario is tested (`spring-fw-tx-declarative-annotations#using-transactional`).

The snippet calls `foo` on a JDK dynamic proxy whose handler records each intercepted method name. The target's `foo` calls `this.bar()`.

```java snippet=m01-l04/SelfInvocation.java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Proxy;
import java.util.ArrayList;
import java.util.List;

public class SelfInvocation {
    interface Pojo {
        void foo();

        void bar();
    }

    static class SimplePojo implements Pojo {
        public void foo() {
            this.bar();
        }

        public void bar() {
        }
    }

    public static void main(String[] args) {
        Pojo target = new SimplePojo();
        List<String> intercepted = new ArrayList<>();
        InvocationHandler handler = (proxy, method, arguments) -> {
            intercepted.add(method.getName());
            return method.invoke(target, arguments);
        };
        Pojo pojo = (Pojo) Proxy.newProxyInstance(
                Pojo.class.getClassLoader(), new Class<?>[] {Pojo.class}, handler);

        pojo.foo();
        System.out.println(intercepted);
        intercepted.clear();
        pojo.bar();
        System.out.println(intercepted);
    }
}
```

The snippet prints `[foo]` after `pojo.foo()`, because the call to `bar` made through `this` never reaches the handler.

It prints `[bar]` after `pojo.bar()`, because that call comes in through the proxy.

The next snippet gives a bean a `@Transactional` method `audit`, with a recording transaction manager that prints `begin` and `commit`. `viaThis` calls `audit` through `this`, and `viaSelf` calls it through a `@Lazy` self reference.

```java snippet=m01-l04/SelfReference.java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.annotation.*;
import org.springframework.transaction.*;
import org.springframework.transaction.annotation.*;
import org.springframework.transaction.support.*;

public class SelfReference {
    static class RecordingManager extends AbstractPlatformTransactionManager {
        protected Object doGetTransaction() { return new Object(); }
        protected void doBegin(Object tx, TransactionDefinition d) { System.out.println("begin"); }
        protected void doCommit(DefaultTransactionStatus s) { System.out.println("commit"); }
        protected void doRollback(DefaultTransactionStatus s) { System.out.println("rollback"); }
    }

    public static class Invoices {
        @Autowired @Lazy Invoices self;
        public void viaThis() { this.audit(); }
        public void viaSelf() { self.audit(); }
        @Transactional
        public void audit() { System.out.println("audit"); }
    }

    @Configuration
    @EnableTransactionManagement
    static class Config {
        @Bean Invoices invoices() { return new Invoices(); }
        @Bean PlatformTransactionManager transactionManager() { return new RecordingManager(); }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            Invoices invoices = context.getBean(Invoices.class);
            System.out.println("-- through this");
            invoices.viaThis();
            System.out.println("-- through the self reference");
            invoices.viaSelf();
        }
    }
}
```

The program prints `audit` alone for `viaThis`, with no `begin` or `commit`.

For `viaSelf` it prints `begin`, `audit` and `commit`, because the call went through the proxy.

Spring calls the `AopContext.currentProxy()` approach highly discouraged and offers it only as a last resort, and it says the approach totally couples the code to Spring AOP and makes the class aware that it is being used in an AOP context (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

:::esquema{kind=tabla title="Ways around self-invocation"}
| Option | What the documentation says | Citation |
| --- | --- | --- |
| Avoid self invocation | Refactor the code so that the self invocation does not happen | `spring-fw-aop-proxying#aop-understanding-aop-proxies` |
| Inject a self reference | Use self injection and invoke methods on the proxy via the self reference instead of via `this` | `spring-fw-aop-proxying#aop-understanding-aop-proxies` |
| `AopContext.currentProxy()` | Requires that the `ProxyFactory` is configured to expose the proxy | `spring-fw-aop-proxying#aop-understanding-aop-proxies` |
| AspectJ mode | The target class is woven and there is no proxy in the first place | `spring-fw-tx-declarative-annotations#using-transactional` |
:::

AspectJ compile-time weaving and load-time weaving do not have the self-invocation issue because they apply advice within the bytecode instead of via a proxy (`spring-fw-aop-proxying#aop-understanding-aop-proxies`).

## Blocking the common pool from `CompletableFuture`
<!-- bullets: 1.4.b -->

`CompletableFuture.supplyAsync` without an executor runs its task in the common pool. That pool is used by any `ForkJoinTask` that is not explicitly submitted to a specified pool. It is not guaranteed to add threads when tasks are blocked in I/O or other unmanaged synchronization.

`CompletableFuture.supplyAsync(Supplier)` returns a new `CompletableFuture` that is asynchronously completed by a task running in the `ForkJoinPool.commonPool()` with the value obtained by calling the given `Supplier` (`javadoc-completablefuture#supplyAsync(java.util.function.Supplier)`).

All async methods without an explicit `Executor` argument, as well as those involving delays, are performed using the `ForkJoinPool.commonPool()` (`javadoc-completablefuture#class-completablefuture-t`).

:::esquema{kind=tabla title="Where an async stage runs"}
| Call | Where it runs | Source |
|---|---|---|
| `supplyAsync(supplier)` | In a task running in the `ForkJoinPool.commonPool()` | `javadoc-completablefuture#supplyAsync(java.util.function.Supplier)` |
| `supplyAsync(supplier, executor)` | In a task running in the given executor | `javadoc-completablefuture#supplyAsync(java.util.function.Supplier,java.util.concurrent.Executor)` |
| `thenApplyAsync(fn)` | Using the stage's default asynchronous execution facility | `javadoc-completablefuture#thenApplyAsync(java.util.function.Function)` |
| `defaultExecutor()` | The `ForkJoinPool.commonPool()` if it supports more than one parallel thread, or else an executor using one thread per async task | `javadoc-completablefuture#defaultExecutor()` |
:::

The common pool is used by any `ForkJoinTask` that is not explicitly submitted to a specified pool (`javadoc-forkjoinpool#class-forkjoinpool`).

A `ForkJoinPool` differs from other kinds of `ExecutorService` mainly by employing work-stealing (`javadoc-forkjoinpool#class-forkjoinpool`).

The pool attempts to maintain enough active threads by dynamically adding, suspending or resuming internal worker threads, even if some tasks are stalled waiting to join others (`javadoc-forkjoinpool#class-forkjoinpool`).

No such adjustments are guaranteed in the face of blocked I/O or other unmanaged synchronization (`javadoc-forkjoinpool#class-forkjoinpool`).

The nested `ForkJoinPool.ManagedBlocker` interface enables extension of the kinds of synchronization accommodated (`javadoc-forkjoinpool#class-forkjoinpool`).

`ForkJoinPool.managedBlock` runs the given possibly blocking task, and when running in a `ForkJoinPool` it possibly arranges for a spare thread to be activated if necessary to ensure sufficient parallelism while the current thread is blocked in `blocker.block()` (`javadoc-forkjoinpool#managedBlock(java.util.concurrent.ForkJoinPool.ManagedBlocker)`).

All worker threads of a `ForkJoinPool` are initialized with `Thread.isDaemon()` set to true (`javadoc-forkjoinpool#class-forkjoinpool`).

The common pool is statically constructed, and its run state is unaffected by attempts to `shutdown()` or `shutdownNow()` (`javadoc-forkjoinpool#commonPool()`).

The common pool and any ongoing processing are automatically terminated upon `System.exit(int)` (`javadoc-forkjoinpool#commonPool()`).

A program that relies on asynchronous task processing to complete before program termination should invoke `commonPool().awaitQuiescence` before exit (`javadoc-forkjoinpool#commonPool()`).

The snippet runs `supplyAsync` without an executor, reads the thread that ran the task, and then calls `shutdown()` on the common pool.

```java snippet=m01-l04/CommonPoolDefault.java
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ForkJoinPool;

public class CommonPoolDefault {
    public static void main(String[] args) {
        String threadName = CompletableFuture.supplyAsync(() -> Thread.currentThread().getName()).join();
        System.out.println(threadName.startsWith("ForkJoinPool.commonPool-worker-"));

        boolean daemon = CompletableFuture.supplyAsync(() -> Thread.currentThread().isDaemon()).join();
        System.out.println(daemon);

        ForkJoinPool.commonPool().shutdown();
        System.out.println(ForkJoinPool.commonPool().isShutdown());

        String afterShutdown = CompletableFuture.supplyAsync(() -> "still runs").join();
        System.out.println(afterShutdown);
    }
}
```

The snippet prints `true` for the thread-name check, because the task ran in a `ForkJoinPool.commonPool-worker-` thread.

It prints `true` for the daemon check.

It prints `false` for `isShutdown()` after `shutdown()`.

It prints `still runs` for the next `supplyAsync` task, because the common pool still accepts it.

## Interrupt handling
<!-- bullets: 1.4.b -->

Typical implementations of `shutdownNow()` cancel a running task by interrupting its thread, and a task that does not respond to the interrupt may never terminate. A thread blocked in `wait`, `join` or `sleep` that is interrupted has its interrupt status cleared and receives an `InterruptedException`. A catch block that ignores the exception leaves no trace of the interrupt.

If a thread is blocked in `wait`, `join` or `sleep`, `Thread.interrupt()` clears its interrupt status and the thread receives an `InterruptedException` (`javadoc-thread#interrupt()`).

If a thread is blocked in an I/O operation upon an `InterruptibleChannel`, the channel is closed, the thread's interrupt status is set, and the thread receives a `ClosedByInterruptException` (`javadoc-thread#interrupt()`).

If a thread is blocked in a `Selector`, its interrupt status is set and it returns immediately from the selection operation (`javadoc-thread#interrupt()`).

If none of those conditions holds, `Thread.interrupt()` sets the thread's interrupt status (`javadoc-thread#interrupt()`).

Interrupting a thread that is not alive need not have any effect (`javadoc-thread#interrupt()`).

`Thread.interrupted()` tests whether the current thread has been interrupted (`javadoc-thread#interrupted()`).

`Thread.interrupted()` clears the interrupted status of the thread (`javadoc-thread#interrupted()`).

Two successive calls to `Thread.interrupted()` return false on the second call, unless the thread is interrupted again in between (`javadoc-thread#interrupted()`).

In the JDK Reference Implementation, interrupting a thread that is not alive still records that the interrupt request was made and reports it via `interrupted()` and `isInterrupted()` (`javadoc-thread#interrupt()`).

`Thread.sleep` throws an `InterruptedException` if any thread has interrupted the current thread, and the interrupted status of the current thread is cleared when this exception is thrown (`javadoc-thread#sleep(long)`).

`isInterrupted()` tests whether a thread has been interrupted, and it leaves the interrupted status of the thread unaffected (`javadoc-thread#isInterrupted()`).

:::diagram{kind="state" caption="The interrupt status of a thread"}
description: A thread with a clear interrupt status gets the status set by interrupt(); Thread.interrupted() and an InterruptedException from sleep clear it again.
clear: status clear
set: status set
clear -> set: interrupt() when the thread is not blocked in wait, join or sleep
set -> clear: Thread.interrupted()
set -> clear: sleep throws InterruptedException
:::

The snippet interrupts the main thread, calls `isInterrupted()` twice, then `Thread.interrupted()`, and finally `isInterrupted()` again.

```java snippet=m01-l04/InterruptQuery.java
public class InterruptQuery {
    public static void main(String[] args) {
        Thread.currentThread().interrupt();
        System.out.println(Thread.currentThread().isInterrupted());
        System.out.println(Thread.currentThread().isInterrupted());
        System.out.println(Thread.interrupted());
        System.out.println(Thread.currentThread().isInterrupted());
    }
}
```

The program prints `true` for both calls to `isInterrupted()`, `true` for `Thread.interrupted()`, and `false` for the last `isInterrupted()`.

The snippet interrupts the main thread and calls `Thread.interrupted()` twice. It then sleeps while interrupted, once with a catch block that ignores the exception and once with a catch block that calls `interrupt()` again.

```java snippet=m01-l04/InterruptStatus.java
public class InterruptStatus {
    public static void main(String[] args) {
        Thread.currentThread().interrupt();
        System.out.println(Thread.interrupted());
        System.out.println(Thread.interrupted());

        Thread.currentThread().interrupt();
        try {
            Thread.sleep(10);
        } catch (InterruptedException swallowed) {
            System.out.println("caught, status " + Thread.currentThread().isInterrupted());
        }

        Thread.currentThread().interrupt();
        try {
            Thread.sleep(10);
        } catch (InterruptedException restored) {
            Thread.currentThread().interrupt();
            System.out.println("caught, status " + Thread.currentThread().isInterrupted());
        }
    }
}
```

The snippet prints `true` and then `false` for the two calls to `Thread.interrupted()`.

It prints `caught, status false` for the catch block that ignores the exception, because the `InterruptedException` arrived with the interrupt status already cleared.

It prints `caught, status true` for the catch block that calls `interrupt()` again.

`ExecutorService.shutdownNow()` attempts to stop all actively executing tasks and halts the processing of waiting tasks (`javadoc-executorservice#shutdownNow()`).

There are no guarantees beyond best-effort attempts to stop processing actively executing tasks (`javadoc-executorservice#shutdownNow()`).

For example, typical implementations will cancel via `Thread.interrupt()`, so any task that fails to respond to interrupts may never terminate (`javadoc-executorservice#shutdownNow()`).

## Key points

- Spring AOP is proxy-based, and a call a target makes on itself through `this` is not intercepted.
- In proxy mode, self-invocation of a `@Transactional` method does not lead to an actual transaction at runtime.
- A self reference calls through the proxy, so the call gets the advice.
- AspectJ weaving applies advice within the bytecode, so it has no self-invocation issue.
- With CGLIB proxying, final and private methods cannot be advised.
- `CompletableFuture.supplyAsync(Supplier)` without an executor runs the task in `ForkJoinPool.commonPool()`.
- A `ForkJoinPool` does not guarantee thread adjustments in the face of blocked I/O or other unmanaged synchronization.
- The common pool's run state is unaffected by `shutdown()` and `shutdownNow()`.
- A thread blocked in `sleep`, `join` or `wait` that is interrupted has its interrupt status cleared and receives an `InterruptedException`.
- `Thread.interrupted()` clears the interrupted status, so a second call returns false, while `isInterrupted()` leaves it unaffected.
- Typical implementations of `shutdownNow()` cancel via `Thread.interrupt()`, so a task that fails to respond to interrupts may never terminate.

# Kotlin in Spring Boot

## Compiler plugins for Spring and JPA
<!-- bullets: 4.4.a -->

In Kotlin, classes and their members are final by default (`kotlin-docs-all-open-plugin#all-open-plugin.md`).

Classes that are final by default can cause issues with frameworks and libraries that rely on subclassing and runtime proxies, which require classes to be open (`kotlin-docs-all-open-plugin#all-open-plugin.md`).

The snippet declares a class and an `open` class, each with one function, and prints whether the class and its function are final.

```kotlin snippet=m04-l04/FinalByDefault.kt
import java.lang.reflect.Modifier

class Service {
    fun work() {}
}

open class OpenService {
    open fun work() {}
}

fun main() {
    println("Service is final: " + Modifier.isFinal(Service::class.java.modifiers))
    println("Service.work is final: " + Modifier.isFinal(Service::class.java.getDeclaredMethod("work").modifiers))
    println("OpenService is final: " + Modifier.isFinal(OpenService::class.java.modifiers))
    println("OpenService.work is final: " + Modifier.isFinal(OpenService::class.java.getDeclaredMethod("work").modifiers))
}
```

The snippet prints `Service is final: true` and `Service.work is final: true` for the class without `open`, and `OpenService is final: false` and `OpenService.work is final: false` for the `open` class.

The all-open compiler plugin makes classes and their members open at compile time without requiring the `open` keyword (`kotlin-docs-all-open-plugin#all-open-plugin.md`).

If a class or any of its superclasses is annotated with a configured annotation, the class and its members become open (`kotlin-docs-all-open-plugin#all-open-plugin.md`).

The all-open plugin also works with meta-annotations (`kotlin-docs-all-open-plugin#use-the-all-open-plugin`).

The `kotlin-spring` compiler plugin makes a class and its members open when they have a Spring annotation (`kotlin-docs-all-open-plugin#all-open-plugin.md`).

Spring Boot documents that, since Kotlin classes are final by default, you are likely to want to configure the `kotlin-spring` plugin to automatically open Spring-annotated classes so that they can be proxied (`spring-boot-features-kotlin#features.kotlin.requirements`).

The no-arg compiler plugin generates a zero-argument constructor for classes with a specific annotation (`kotlin-docs-no-arg-plugin#no-arg-plugin.md`).

The constructor that no-arg generates is annotated with `@Deprecated` at the `HIDDEN` level, so you can call it from Java but not from Kotlin (`kotlin-docs-no-arg-plugin#no-arg-plugin.md`).

Frameworks can call the constructor that no-arg generates through reflection (`kotlin-docs-no-arg-plugin#no-arg-plugin.md`).

The no-arg plugin allows frameworks such as the Java Persistence API (JPA) to instantiate Kotlin classes that don't declare a zero-argument constructor (`kotlin-docs-no-arg-plugin#no-arg-plugin.md`).

The `kotlin-jpa` plugin makes entities open and generates zero-argument constructors for them (`kotlin-docs-all-open-plugin#what-s-next`).

The `kotlin-jpa` plugin specifies JPA annotations such as `@Entity`, `@Embeddable` and `@MappedSuperclass` automatically (`kotlin-docs-no-arg-plugin#no-arg-plugin.md`).

Spring Boot requires at least Kotlin 2.2.x and manages a suitable Kotlin version through dependency management (`spring-boot-features-kotlin#features.kotlin.requirements`).

## JPA entities written as Kotlin classes
<!-- bullets: 4.4.b -->

For a data class, the compiler automatically derives an `equals()` and `hashCode()` pair from all properties declared in the primary constructor (`kotlin-docs-data-classes#data-classes.md`).

Data classes can't be abstract, open, sealed, or inner (`kotlin-docs-data-classes#data-classes.md`).

If there are explicit implementations of `equals()`, `hashCode()` or `toString()` in the data class body, these functions are not generated and the existing implementations are used (`kotlin-docs-data-classes#data-classes.md`).

On the JVM, if the generated class needs to have a parameterless constructor, default values for the properties have to be specified (`kotlin-docs-data-classes#data-classes.md`).

Non-data classes do not override the `equals()` function by default (`kotlin-docs-equality#structural-equality`).

Non-data classes implement the referential equality behavior inherited from the `Any` class (`kotlin-docs-equality#structural-equality`).

The snippet compares two `PlainBook` instances and two `Book` data class instances with the same properties, then adds an `Order` data class instance to a `HashSet` before and after its `id` property is assigned.

```kotlin snippet=m04-l04/DataClassEquality.kt
class PlainBook(val isbn: String, val title: String)

data class Book(val isbn: String, val title: String)

data class Order(var id: Long? = null, val customer: String)

fun main() {
    println(PlainBook("978", "Kotlin") == PlainBook("978", "Kotlin"))
    println(Book("978", "Kotlin") == Book("978", "Kotlin"))
    println(Book("978", "Kotlin").hashCode() == Book("978", "Kotlin").hashCode())
    println(Book("978", "Kotlin"))
    val orders = HashSet<Order>()
    val order = Order(customer = "ada")
    orders.add(order)
    println(orders.contains(order))
    order.id = 7
    println(orders.contains(order))
}
```

The snippet prints `false` for the two `PlainBook` instances and `true` for the two `Book` instances, and it prints `true` for their `hashCode()` comparison and `Book(isbn=978, title=Kotlin)` for the generated `toString()`.

The snippet prints `true` when the `HashSet` is asked for the `Order` before its `id` is assigned and `false` after, because the generated `hashCode()` depends on `id`.

Hibernate guarantees equivalence of persistent identity (database row) and Java identity inside a particular session scope (`hibernate-user-guide#mapping-model-pojo-equalshashcode`).

According to the Hibernate User Guide, a class that acts as an identifier must implement `equals` and `hashCode` based on the id values (`hibernate-user-guide#mapping-model-pojo-equalshashcode`).

The Hibernate User Guide says that, beyond that case and a few others, you may want to consider not implementing `equals` and `hashCode` altogether (`hibernate-user-guide#mapping-model-pojo-equalshashcode`).

`Set` says that the `equals` and `hashCode` value for an object should not change while the object is part of the `Set` (`hibernate-user-guide#mapping-model-pojo-equalshashcode`).

An `equals` and `hashCode` based on a generated id breaks for a transient entity added to a `Set`, because the id is not set until the Jakarta Persistence transaction is committed (`hibernate-user-guide#mapping-model-pojo-equalshashcode`).

With assigned identifiers an id-based `equals` and `hashCode` is not a problem, assuming the identifier value is assigned prior to adding to the `Set` (`hibernate-user-guide#mapping-model-pojo-equalshashcode`).

Using a natural-id is best for `equals` and `hashCode` (`hibernate-user-guide#mapping-model-pojo-equalshashcode`).

In fetching, "now" is generally termed eager or immediate while "later" is generally termed lazy or delayed (`hibernate-user-guide#fetching-basics`).

The Hibernate recommendation is to statically mark all associations lazy and to use dynamic fetching strategies for eagerness (`hibernate-user-guide#fetching-strategies`).

The Jakarta Persistence specification defines that all one-to-one and many-to-one associations should be eagerly fetched by default (`hibernate-user-guide#fetching-strategies`).

Hibernate, as a Jakarta Persistence provider, honors that default (`hibernate-user-guide#fetching-strategies`).

The `SELECT` fetch strategy is the one generally termed N+1 (`hibernate-user-guide#fetching-basics`).

The `JOIN` fetch strategy is inherently an eager style of fetching (`hibernate-user-guide#fetching-basics`).

## Suspend functions in controllers, repositories and transactions
<!-- bullets: 4.4.c -->

:::esquema{kind=tabla title="How reactive return types translate to coroutines"}
| Reactive signature | Coroutines signature | Source |
|---|---|---|
| `fun handler(): Mono<Void>` | `suspend fun handler()` | `spring-fw-kotlin-coroutines#how-reactive-translates-to-coroutines` |
| `fun handler(): Mono<T>` | `suspend fun handler(): T` or `suspend fun handler(): T?`, depending on whether the `Mono` can be empty | `spring-fw-kotlin-coroutines#how-reactive-translates-to-coroutines` |
| `fun handler(): Flux<T>` | `fun handler(): Flow<T>` | `spring-fw-kotlin-coroutines#how-reactive-translates-to-coroutines` |
:::

`Flow` is push-based while `Flux` is a push-pull hybrid (`spring-fw-kotlin-coroutines#how-reactive-translates-to-coroutines`).

In coroutines, backpressure is implemented via suspending functions (`spring-fw-kotlin-coroutines#how-reactive-translates-to-coroutines`).

A Coroutines router is defined via the `coRouter { }` DSL (`spring-fw-kotlin-coroutines#webflux-fn`).

Transactions on Coroutines are supported via the programmatic variant of the Reactive transaction management (`spring-fw-kotlin-coroutines#transactions`).

For suspending functions, a `TransactionalOperator.executeAndAwait` extension is provided (`spring-fw-kotlin-coroutines#transactions`).

For Kotlin `Flow`, a `Flow<T>.transactional` extension is provided (`spring-fw-kotlin-coroutines#transactions`).

Coroutines repositories are built on reactive repositories to expose the non-blocking nature of data access through Kotlin's Coroutines (`spring-data-commons-kotlin-coroutines#kotlin.coroutines.repositories`).

Coroutines repositories are only discovered when the repository extends the `CoroutineCrudRepository` interface (`spring-data-commons-kotlin-coroutines#kotlin.coroutines.repositories`).

To retain access to the coroutine context, declare the repository method using `suspend` or return a type that enables context propagation such as `Flow` (`spring-data-commons-kotlin-coroutines#kotlin.coroutines.repositories`).

A repository method that returns `Flow<User>` creates the `Flow` eagerly, and the data is fetched upon `Flow.collect(…)` (`spring-data-commons-kotlin-coroutines#kotlin.coroutines.repositories`).

A repository method declared as `fun getUser(): User` retrieves data once, blocking the thread and without context propagation (`spring-data-commons-kotlin-coroutines#kotlin.coroutines.repositories`).

The extensions of the Spring Boot Kotlin API for `TestRestTemplate` make it possible to take advantage of Kotlin reified type parameters (`spring-boot-features-kotlin#features.kotlin.api.extensions`).

## Testing with MockK and virtual time
<!-- bullets: 4.4.d -->

While it is possible to use JUnit 4 to test Kotlin code, Spring Boot provides JUnit 6 by default and recommends it (`spring-boot-features-kotlin#features.kotlin.testing`).

JUnit 6 enables a test class to be instantiated once and reused for all of the class's tests (`spring-boot-features-kotlin#features.kotlin.testing`).

To mock Kotlin classes, Spring Boot recommends MockK (`spring-boot-features-kotlin#features.kotlin.testing`).

SpringMockK provides the `@MockkBean` and `@SpykBean` annotations, which are the MockK equivalents of `@MockitoBean` and `@MockitoSpyBean` (`spring-boot-features-kotlin#features.kotlin.testing`).

MockK mocks suspend functions with `coEvery`, `coVerify`, `coMatch`, `coAssert`, `coRun`, `coAnswers` or `coInvoke` (`mockk-docs#coroutines`).

MockK simulates a never returning suspend function with `coJustAwait` (`mockk-docs#coroutines`).

A relaxed mock is the mock that returns some simple value for all functions (`mockk-docs#relaxed-mock`).

Relaxed mocking works badly with generic return types, and a class cast exception is usually thrown in this case (`mockk-docs#relaxed-mock`).

On JVM and Native, `runTest` behaves similarly to `runBlocking`, with the difference that the code that it runs will skip delays (`coroutines-api-test-run-test#content`).

Delay skipping is achieved by using virtual time (`coroutines-api-test-run-test#task-scheduling`).

The scheduler of `runTest` can be accessed via `TestScope.testScheduler` (`coroutines-api-test-run-test#task-scheduling`).

Delays in code that runs inside dispatchers that don't use a `TestCoroutineScheduler` don't get skipped (`coroutines-api-test-run-test#task-scheduling`).

The test body of `runTest` is run on a single thread, unless other `CoroutineDispatcher` are used for child coroutines (`coroutines-api-test-run-test#content`).

Child coroutines of `runTest` are not executed in parallel to the test body (`coroutines-api-test-run-test#content`).

`TestCoroutineScheduler` can advance the time via `advanceTimeBy` (`coroutines-api-test-scheduler#content`).

`TestCoroutineScheduler` can run all the scheduled tasks, advancing the virtual time as needed, via `advanceUntilIdle` (`coroutines-api-test-scheduler#content`).

Several test dispatchers can share the same scheduler, in which case their knowledge about the virtual time is synchronized (`coroutines-api-test-scheduler#content`).

## Key points

- Kotlin classes and their members are final by default, and the all-open plugin makes them open at compile time.
- The `kotlin-spring` plugin opens classes that have a Spring annotation, so that they can be proxied.
- The no-arg plugin generates a zero-argument constructor that frameworks such as JPA call through reflection.
- The `kotlin-jpa` plugin makes entities open and generates zero-argument constructors for them.
- A data class derives `equals()` and `hashCode()` from the primary constructor properties.
- In the snippet, assigning `id` after the `Order` is in a `HashSet` makes `contains` return `false`.
- Data classes can't be abstract, open, sealed, or inner.
- Hibernate recommends marking associations lazy statically, while Jakarta Persistence makes one-to-one and many-to-one associations eager by default.
- A `Mono<T>` becomes a `suspend` function and a `Flux<T>` becomes a `Flow<T>` when reactive code moves to coroutines.
- Coroutines repositories are discovered only when they extend `CoroutineCrudRepository`.
- `runTest` skips delays with virtual time, and the delays of dispatchers that don't use a `TestCoroutineScheduler` are not skipped.
- MockK mocks suspend functions with `coEvery` and `coVerify`.

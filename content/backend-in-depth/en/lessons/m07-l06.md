# gRPC, GraphQL and asynchronous APIs

## gRPC call types
<!-- bullets: 7.6.a -->

In a gRPC unary RPC, the client sends a single request and gets back a single response (`grpc-core-concepts#unary-rpc`).

Once the client calls a stub method, the server is notified that the RPC has been invoked with the client's metadata for the call, the method name, and the deadline if one was specified (`grpc-core-concepts#unary-rpc`).

The server can send back its initial metadata straight away, or wait for the client's request message, and the initial metadata must be sent before any response (`grpc-core-concepts#unary-rpc`).

A successful response is returned to the client together with status details, which are a status code and an optional status message, and optional trailing metadata (`grpc-core-concepts#unary-rpc`).

In a server-streaming RPC, the server returns a stream of messages in response to a client's request (`grpc-core-concepts#server-streaming-rpc`).

In a server-streaming RPC the server's status details and optional trailing metadata are sent after all its messages, and the client completes once it has all the server's messages (`grpc-core-concepts#server-streaming-rpc`).

In a client-streaming RPC, the client sends a stream of messages to the server instead of a single message (`grpc-core-concepts#client-streaming-rpc`).

In a client-streaming RPC the server responds with a single message, typically but not necessarily after it has received all the client's messages (`grpc-core-concepts#client-streaming-rpc`).

In a bidirectional streaming RPC, the call is initiated by the client invoking the method and the server receiving the client metadata, the method name and the deadline (`grpc-core-concepts#bidirectional-streaming-rpc`).

In a bidirectional streaming RPC the two streams are independent, so the client and server can read and write messages in any order (`grpc-core-concepts#bidirectional-streaming-rpc`).

In a bidirectional streaming RPC, a server can wait until it has received all of a client's messages before writing its messages, or the two sides can play ping-pong (`grpc-core-concepts#bidirectional-streaming-rpc`).

:::esquema{kind=tabla title="gRPC call types"}
| Call type | Client sends | Server returns | Source |
|---|---|---|---|
| Unary | A single request | A single response | `grpc-core-concepts#unary-rpc` |
| Server streaming | A single request | A stream of messages | `grpc-core-concepts#server-streaming-rpc` |
| Client streaming | A stream of messages | A single message | `grpc-core-concepts#client-streaming-rpc` |
| Bidirectional streaming | A stream of messages | A stream of messages, independent of the client's stream | `grpc-core-concepts#bidirectional-streaming-rpc` |
:::

## Deadlines and cancellation
<!-- bullets: 7.6.a -->

gRPC allows clients to specify how long they are willing to wait for an RPC to complete before the RPC is terminated with a `DEADLINE_EXCEEDED` error (`grpc-core-concepts#deadlines`).

On the server side, the server can query whether a particular RPC has timed out, or how much time is left to complete it (`grpc-core-concepts#deadlines`).

Specifying a deadline or a timeout is language specific: some language APIs work in terms of timeouts, some in terms of a deadline, and they may or may not have a default deadline (`grpc-core-concepts#deadlines`).

When a server also acts as a client, it would want to honor the deadline set by the original client (`grpc-deadlines#deadline-propagation`).

Automatically propagating the deadline from an incoming RPC to an outgoing one is supported by some gRPC implementations (`grpc-deadlines#deadline-propagation`).

In some languages deadline propagation needs to be explicitly enabled, for example in C++, and in others it is enabled by default, for example in Java and Go (`grpc-deadlines#deadline-propagation`).

Because a deadline is a set point in time and the clocks on two servers might not be synchronized, gRPC converts the deadline to a timeout from which the already elapsed time is deducted (`grpc-deadlines#deadline-propagation`).

Either the client or the server can cancel an RPC at any time (`grpc-core-concepts#cancelling-an-rpc`).

A cancellation terminates the RPC immediately so that no further work is done (`grpc-core-concepts#cancelling-an-rpc`).

Deadline expiration and I/O errors also trigger cancellation (`grpc-cancellation#overview`).

When an RPC is cancelled, the server should stop any ongoing computation and end its side of the stream (`grpc-cancellation#overview`).

Cancellation should ideally propagate to all ongoing computation in the system that was initiated by the original client RPC call (`grpc-cancellation#overview`).

## gRPC status codes
<!-- bullets: 7.6.a -->

`DEADLINE_EXCEEDED` means the deadline expired before the operation could complete (`grpc-status-codes#the-full-list-of-status-codes`).

For operations that change the state of the system, `DEADLINE_EXCEEDED` may be returned even if the operation has completed successfully (`grpc-status-codes#the-full-list-of-status-codes`).

`INVALID_ARGUMENT` indicates arguments that are problematic regardless of the state of the system, which differs from `FAILED_PRECONDITION` (`grpc-status-codes#the-full-list-of-status-codes`).

`FAILED_PRECONDITION` means the operation was rejected because the system is not in a state required for the operation's execution (`grpc-status-codes#the-full-list-of-status-codes`).

A service should use `UNAVAILABLE` if the client can retry just the failing call (`grpc-status-codes#the-full-list-of-status-codes`).

A service should use `ABORTED` if the client should retry at a higher level, for example when a client-specified test-and-set fails and the client should restart a read-modify-write sequence (`grpc-status-codes#the-full-list-of-status-codes`).

A service should use `FAILED_PRECONDITION` if the client should not retry until the system state has been explicitly fixed (`grpc-status-codes#the-full-list-of-status-codes`).

`UNAVAILABLE` is most likely a transient condition, which can be corrected by retrying with a backoff (`grpc-status-codes#the-full-list-of-status-codes`).

It is not always safe to retry non-idempotent operations after `UNAVAILABLE` (`grpc-status-codes#the-full-list-of-status-codes`).

`PERMISSION_DENIED` must not be used for rejections caused by exhausting some resource, for which `RESOURCE_EXHAUSTED` is used instead (`grpc-status-codes#the-full-list-of-status-codes`).

`PERMISSION_DENIED` must not be used if the caller cannot be identified, for which `UNAUTHENTICATED` is used instead (`grpc-status-codes#the-full-list-of-status-codes`).

Unlike `INVALID_ARGUMENT`, `OUT_OF_RANGE` indicates a problem that may be fixed if the system state changes (`grpc-status-codes#the-full-list-of-status-codes`).

| `INVALID_ARGUMENT` | 3 | The client specified an invalid argument | `grpc-status-codes#the-full-list-of-status-codes` |

## Protocol Buffers field numbers and message evolution
<!-- bullets: 7.6.a -->

Each field in a proto3 message needs a number between 1 and 536,870,911 that is unique among all fields for that message (`protobuf-proto3#assigning`).

Field numbers 19,000 to 19,999 are reserved for the Protobuf implementation (`protobuf-proto3#assigning`).

A field number cannot be changed once the message type is in use, because it identifies the field in the message wire format (`protobuf-proto3#assigning`).

Field numbers should never be reused, and a number should never be taken out of the reserved list for reuse with a new field definition (`protobuf-proto3#assigning`).

Field numbers 1 through 15 take one byte to encode, and field numbers 16 through 2047 take two bytes (`protobuf-proto3#assigning`).

Field numbers 1 through 15 should be used for the most frequently set fields, because lower field numbers take less space in the wire format (`protobuf-proto3#assigning`).

If an enum entry is entirely removed or commented out, future users can reuse its numeric value, which can cause severe issues when they load old instances, including data corruption and privacy bugs (`protobuf-proto3#reserved`).

Specifying the numeric values of deleted entries as reserved makes the Protobuf compiler complain if any future user tries to use those identifiers (`protobuf-proto3#reserved`).

Field names and numeric values cannot be mixed in the same `reserved` statement (`protobuf-proto3#reserved`).

Unknown fields are well-formed Protobuf serialized data representing fields that the parser does not recognize (`protobuf-proto3#unknowns`).

When an old binary parses data sent by a new binary with new fields, those new fields become unknown fields in the old binary (`protobuf-proto3#unknowns`).

Proto3 messages preserve unknown fields and include them during parsing and in the serialized output, which matches proto2 behavior (`protobuf-proto3#unknowns`).

Wire-safe changes are ones where it is fully safe to evolve the schema without risk of data loss or new parse failures (`protobuf-proto3#wire-safe-changes`).

Adding new fields is wire-safe, and so is removing fields, provided the same field number is not used again (`protobuf-proto3#wire-safe-changes`).

Adding additional values to an enum is wire-safe (`protobuf-proto3#wire-safe-changes`).

Wire-unsafe changes are schema changes that break if data serialized with the old schema is parsed with a parser using the new schema, or vice versa (`protobuf-proto3#wire-unsafe-changes`).

Changing the field number of any existing field is not safe, because it is equivalent to deleting the field and adding a new one with the same type (`protobuf-proto3#wire-unsafe-changes`).

Moving fields into an existing `oneof` is not safe (`protobuf-proto3#wire-unsafe-changes`).

## GraphQL schema and resolvers
<!-- bullets: 7.6.b -->

The GraphQL type system describes the capabilities of a GraphQL service, and is used to determine if a requested operation is valid and to guarantee the type of response results (`graphql-spec#sec-Type-System`).

The GraphQL language includes an IDL used to describe the type system of a GraphQL service (`graphql-spec#sec-Type-System`).

The collective type system capabilities of a GraphQL service are referred to as that service's schema (`graphql-spec#sec-Schema`).

A schema is defined in terms of the types and directives it supports and the root operation type for each kind of operation: query, mutation and subscription (`graphql-spec#sec-Schema`).

All types within a GraphQL schema must have unique names (`graphql-spec#sec-Schema`).

A type or directive name must not begin with two underscores, because that prefix is used exclusively by the introspection system (`graphql-spec#sec-Schema`).

A GraphQL service generates a response from a request via execution (`graphql-spec#sec-Execution`).

The document of a request for execution must contain an `OperationDefinition` and may contain a `FragmentDefinition` (`graphql-spec#sec-Execution`).

GraphQL requests do not require any specific serialization format or transport mechanism (`graphql-spec#sec-Execution`).

`ResolveFieldValue` produces a value for a given field on a type for a real value (`graphql-spec#sec-Value-Resolution`).

A resolver is the internal function provided by the object type for determining the resolved value of a field (`graphql-spec#sec-Value-Resolution`).

It is common for a resolver to be asynchronous, because it relies on reading an underlying database or networked service to produce a value (`graphql-spec#sec-Value-Resolution`).

## The N+1 problem and DataLoader
<!-- bullets: 7.6.b -->

In Spring for GraphQL, batch loading addresses the N+1 select problem through an `org.dataloader.DataLoader` that defers the loading of individual entity instances so they can be loaded together (`spring-graphql-controllers#controllers.batch-mapping`).

After a batch loading function is registered for an entity, a controller method can access the `DataLoader` for that entity by declaring a method argument of type `DataLoader` (`spring-graphql-controllers#controllers.schema-mapping.data-loader`).

By default `BatchLoaderRegistry` uses the full class name of the value type as the key of the registration (`spring-graphql-controllers#controllers.schema-mapping.data-loader`).

When a `@SchemaMapping` method only delegates to a `DataLoader`, a `@BatchMapping` method avoids that boilerplate (`spring-graphql-controllers#controllers.batch-mapping`).

A `@BatchMapping` method also binds a `DataFetcher` to the field, which delegates to the `DataLoader` for the parent instance (`spring-graphql-controllers#controllers.batch-mapping`).

To be used as a unique key, the parent type of a `@BatchMapping` method must implement `hashcode` and `equals` (`spring-graphql-controllers#controllers.batch-mapping`).

For a `@BatchMapping` method the field name defaults to the method name and the type name defaults to the simple class name of the input list element type, and both can be customized through annotation attributes (`spring-graphql-controllers#controllers.batch-mapping`).

If the use case needs more information about the parent `@SchemaMapping` call, such as `@Argument` or context data, using `BatchLoaderRegistry` is required (`spring-graphql-controllers#controllers.batch-mapping`).

## AsyncAPI
<!-- bullets: 7.6.c -->

The AsyncAPI Specification is a project used to describe message-driven APIs in a machine-readable format (`asyncapi-spec#introduction`).

AsyncAPI is protocol-agnostic, so it can be used for APIs that work over any protocol, such as AMQP, MQTT, WebSockets, Kafka, STOMP and HTTP (`asyncapi-spec#introduction`).

An AsyncAPI document SHOULD describe the operations an application performs (`asyncapi-spec#introduction`).

```yaml
channels:
  userSignedUp:
    # ...(redacted for brevity)
operations:
  onUserSignedUp:
    action: receive
    channel:
      $ref: '#/channels/userSignedUp'
```

In the specification's snippet, `action: receive` on the `userSignedUp` channel means that the application will receive messages from that channel (`asyncapi-spec#introduction`).

The AsyncAPI Specification does not assume any kind of software topology, architecture or pattern, so a server MAY be a message broker, a web server or any other program that can send or receive data (`asyncapi-spec#introduction`).

AsyncAPI offers a mechanism called bindings that helps to give more specific information about the protocol (`asyncapi-spec#introduction`).

It is NOT RECOMMENDED to derive a receiver AsyncAPI document from a sender one, or the reverse (`asyncapi-spec#introduction`).

There is no guarantee that the channel an application uses to receive messages is the channel where another application is sending them (`asyncapi-spec#introduction`).

Fields such as `summary`, `description` and the `id` of an operation might stop making sense when a document is derived from the opposite direction (`asyncapi-spec#introduction`).

A system may use a read-only channel for receiving messages, a different one for sending them, and an intermediary process that forwards messages from one channel to the other (`asyncapi-spec#introduction`).

The AsyncAPI Object is the root document object, which combines resource listing and API declaration into one document (`asyncapi-spec#asyncapi-object`).

A Channel Object describes a shared communication channel, and an Operation Object describes a specific operation (`asyncapi-spec#channel-object`; `asyncapi-spec#operation-object`).

## Choosing between REST, gRPC, GraphQL and messaging
<!-- bullets: 7.6.d -->

:::judgement{source="Microsoft, Communication in a microservice architecture" ref="ms-communication-microservice-architecture#communication-types"}
According to Microsoft's guide to communication in a microservice architecture, communication types fall on two axes: whether the protocol is synchronous or asynchronous, and whether the communication has a single receiver or multiple receivers. The guide says that the most common type in a microservice-based application is single-receiver communication over a synchronous protocol such as HTTP, and that microservices also typically use messaging protocols for asynchronous communication between services.
:::

:::judgement{source="Microsoft, Communication in a microservice architecture" ref="ms-communication-microservice-architecture#requestresponse-communication-with-http-and-rest"}
According to the same Microsoft guide, request/response communication is especially well suited to querying data for a real-time user interface, and a client that uses it assumes the response arrives within a short time. For delayed responses, the guide says to use asynchronous communication based on messaging patterns and messaging technologies.
:::

:::judgement{source="Microsoft, Choose between Azure messaging services" ref="ms-azure-messaging-choices#commands"}
According to Microsoft's Azure Architecture Center guide on messaging services, a command is a high-value message with strict delivery requirements that asks the consumer to perform an operation, and it must be delivered at least once.
:::

:::judgement{source="James Lewis and Martin Fowler, Microservices" ref="fowler-microservices#SynchronousCallsConsideredHarmful"}
According to James Lewis and Martin Fowler, a number of synchronous calls between services brings the multiplicative effect of downtime, where the downtime of the system becomes the product of the downtimes of the individual components. They say the choice is between making the calls asynchronous and managing the downtime.
:::

## Key points

- A gRPC call is unary, server-streaming, client-streaming or bidirectional streaming, and the two streams of a bidirectional call are independent (`grpc-core-concepts#unary-rpc`; `grpc-core-concepts#bidirectional-streaming-rpc`).
- A client-set deadline ends an RPC with `DEADLINE_EXCEEDED`, and gRPC propagates a deadline as a timeout with the elapsed time deducted (`grpc-core-concepts#deadlines`; `grpc-deadlines#deadline-propagation`).
- Either side can cancel an RPC, and a server should stop ongoing computation when the RPC is cancelled (`grpc-core-concepts#cancelling-an-rpc`; `grpc-cancellation#overview`).
- Service implementors choose between `UNAVAILABLE`, `ABORTED` and `FAILED_PRECONDITION` by what the client should do: retry just the failing call, retry at a higher level, or not retry until the system state is fixed (`grpc-status-codes#the-full-list-of-status-codes`).
- A Protocol Buffers field number identifies the field on the wire, cannot be changed once in use and should never be reused (`protobuf-proto3#assigning`).
- Adding or removing a field and adding an enum value are wire-safe, while changing a field number is not (`protobuf-proto3#wire-safe-changes`; `protobuf-proto3#wire-unsafe-changes`).
- A GraphQL schema is defined by its types, directives and the root operation types for query, mutation and subscription (`graphql-spec#sec-Schema`).
- A resolver produces the value of a field, and batch loading with a `DataLoader` addresses the N+1 select problem (`graphql-spec#sec-Value-Resolution`; `spring-graphql-controllers#controllers.batch-mapping`).
- An AsyncAPI document describes message-driven APIs over any protocol, and a receiver document should not be derived from a sender one (`asyncapi-spec#introduction`).

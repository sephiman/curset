# Advanced testing and test strategy

## The shape of the test suite
<!-- bullets: 11.6.a -->

:::judgement{source="Ham Vocke, The Practical Test Pyramid" ref="fowler-practical-test-pyramid#TheTestPyramid"}
According to Ham Vocke, writing on martinfowler.com, Mike Cohn's original test pyramid has three layers, from bottom to top: unit tests, service tests and user interface tests. Vocke says two things are worth remembering from it: write tests with different granularity, and the more high-level the tests get, the fewer of them there should be. He warns against ending up with a test ice-cream cone, which he calls a nightmare to maintain that takes way too long to run.
:::

:::judgement{source="Ham Vocke, The Practical Test Pyramid" ref="fowler-practical-test-pyramid#what-to-test"}
According to the same article, a unit test class should at least test the public interface of the class and should ensure that all non-trivial code paths are tested, including the happy path and edge cases. Vocke adds that unit tests should not be tied to the implementation too closely, that they should test observable behaviour instead of internal code structure, and that simple getters and setters and other trivial code are not worth testing.
:::

:::judgement{source="Ham Vocke, The Practical Test Pyramid" ref="fowler-practical-test-pyramid#End-to-endTests"}
According to the same article, end-to-end tests give the biggest confidence about whether the software works, and they are also notoriously flaky, require a lot of maintenance and run pretty slowly. Vocke advises reducing the number of end-to-end tests to a bare minimum and translating only the most important steps of the core user journeys into them.
:::

:::judgement{source="Google, Site Reliability Engineering, ch. 17" ref="sre-book-testing-reliability#system-tests"}
According to Google's Site Reliability Engineering book, a system test is the largest scale test that engineers run for an undeployed system, and its flavors include smoke tests, performance tests and regression tests. The chapter notes that tests have a cost in time and computational resources: unit tests can usually be completed in milliseconds on a laptop, while bringing up a complete server with its dependencies can take from several minutes to multiple hours.
:::

:::judgement{source="Google, Site Reliability Engineering, ch. 17" ref="sre-book-testing-reliability#integration-tests"}
According to the same chapter, engineers run an integration test on an assembled component to verify that it functions correctly. The chapter describes dependency injection as an extremely powerful technique for creating mocks of complex dependencies, and gives as an example replacing a stateful database with a lightweight mock that has precisely specified behavior.
:::

## Consumer-driven contract testing
<!-- bullets: 11.6.b -->

In Spring Cloud Contract, a contract is an agreement on how the API or message communication should look. (`spring-cloud-contract-intro#getting-started-what-is-a-contract`)

Spring Cloud Contract expects contracts to come from a trusted source. (`spring-cloud-contract-intro#getting-started-what-is-a-contract`)

Contracts coming from untrusted locations should never be downloaded or interacted with. (`spring-cloud-contract-intro#getting-started-what-is-a-contract`)

A consumer Pact test asks whether the consumer code correctly generates the request and handles the expected response, assuming the provider returns the expected response for that request. (`pact-how-it-works#consumer-testing`)

Each Pact interaction is tested using the Pact framework, driven by the unit test framework inside the consumer codebase. (`pact-how-it-works#consumer-testing`)

The consumer test code fires a real request to a mock provider created by the Pact framework. (`pact-how-it-works#consumer-testing`)

The mock provider compares the actual request with the expected request, and emits the expected response if the comparison is successful. (`pact-how-it-works#consumer-testing`)

In Pact, each interaction is considered to be independent. (`pact-how-it-works#consumer-testing`)

Each Pact test only tests one interaction. (`pact-how-it-works#consumer-testing`)

Provider states describe the preconditions on the provider that are required to generate the expected response. (`pact-how-it-works#consumer-testing`)

Once all interactions have been tested on the consumer side, the Pact framework generates a pact file, which describes each interaction. (`pact-how-it-works#consumer-testing`)

The pact file can be used to verify that the provider meets the consumer's expectations. (`pact-how-it-works#consumer-testing`)

Provider verification is entirely driven by the Pact framework. (`pact-how-it-works#provider-verification`)

In provider verification, each request is sent to the provider and the actual response is compared with the minimal expected response described in the consumer test. (`pact-how-it-works#provider-verification`)

Provider verification passes if each request generates a response that contains at least the data described in the minimal expected response. (`pact-how-it-works#provider-verification`)

The Pact framework sets up the data described by the provider state before the interaction is replayed. (`pact-how-it-works#provider-verification`)

Pact is most valuable where you control the development of both the consumer and the provider. (`pact-what-is-good-for#what-is-pact-good-for`)

Pact is most valuable where the consumer and the provider are both under active development. (`pact-what-is-good-for#what-is-pact-good-for`)

With Pact you can find out before you deploy whether your applications will work together. (`pact-what-is-good-for#what-is-pact-good-for`)

## Property-based testing
<!-- bullets: 11.6.c -->

Properties are the core concept of property-based testing. (`jqwik-user-guide#creating-a-property`)

In jqwik, a property is created by annotating a public, protected or package-scoped method with `@Property`. (`jqwik-user-guide#creating-a-property`)

A property method is supposed to have one or more parameters, all of which must be annotated with `@ForAll`. (`jqwik-user-guide#creating-a-property`)

At test runtime, jqwik fills in the exact parameter values of the property method. (`jqwik-user-guide#creating-a-property`)

A property method either returns a `boolean` that signifies success (`true`) or failure (`false`) of the property, or returns nothing. (`jqwik-user-guide#creating-a-property`)

A property method that returns nothing will probably use assertions to check the property's invariant. (`jqwik-user-guide#creating-a-property`)

If not specified differently, jqwik runs 1000 tries. (`jqwik-user-guide#creating-a-property`)

The first failed execution stops value generation and is reported as a failure. (`jqwik-user-guide#creating-a-property`)

A reported failure is usually followed by an attempt to shrink the falsified parameter set. (`jqwik-user-guide#creating-a-property`)

Only parameters annotated with `@ForAll` are considered for value generation. (`jqwik-user-guide#creating-a-property`)

If `@ForAll` has no value parameter, jqwik uses default generation for a fixed list of types. (`jqwik-user-guide#default-parameter-generation`)

Default generation covers all enum types. (`jqwik-user-guide#default-parameter-generation`)

Default generation covers `List<T>`, `Set<T>` and `Stream<T>` as long as `T` can also be provided by default generation. (`jqwik-user-guide#default-parameter-generation`)

With `@ForAll("aMethodName")`, the method `aMethodName` is called to provide an `Arbitrary` of the required type. (`jqwik-user-guide#default-parameter-generation`)

The `String` value of `@ForAll` is a reference to a method within the same class, or one of its superclasses or owning classes. (`jqwik-user-guide#arbitrary-provider-methods`)

That reference is either the method's name or the `String` value of the method's `@Provide` annotation. (`jqwik-user-guide#arbitrary-provider-methods`)

The jqwik user guide presents `Math.abs(anInteger) >= 0` as one of two properties whose failures might surprise you. (`jqwik-user-guide#creating-a-property`)

The snippet checks a counterexample for each of the two surprising properties in the guide: the absolute value of an integer, and the length of a concatenation.

```java snippet=m11-l06/PropertyCounterexamples.java
public class PropertyCounterexamples {
    public static void main(String[] args) {
        int smallest = Integer.MIN_VALUE;
        System.out.println("abs of smallest int = " + Math.abs(smallest));
        System.out.println("abs of smallest int >= 0: " + (Math.abs(smallest) >= 0));
        System.out.println("abs of largest int >= 0: " + (Math.abs(Integer.MAX_VALUE) >= 0));
        String string1 = "";
        String string2 = "a";
        String concatenated = string1 + string2;
        System.out.println("length of concatenation: " + concatenated.length());
        System.out.println("longer than string1: " + (concatenated.length() > string1.length()));
        System.out.println("longer than string2: " + (concatenated.length() > string2.length()));
    }
}
```

`Math.abs(Integer.MIN_VALUE)` returns `-2147483648`.

The check `Math.abs(x) >= 0` is `false` for `Integer.MIN_VALUE`.

The check `Math.abs(x) >= 0` is `true` for `Integer.MAX_VALUE`.

The concatenation of `""` and `"a"` has length `1`, which is longer than `""` and not longer than `"a"`.

If a property can be falsified with a generated set of values, jqwik tries to shrink the sample to find a smaller sample that also falsifies the property. (`jqwik-user-guide#result-shrinking`)

In the guide's `stringShouldBeShrunkToAA` property, the final sample is exactly `AA`, because it is the shortest failing string and `A` has the lowest numeric value of all allowed characters. (`jqwik-user-guide#result-shrinking`)

jqwik's shrinking approach is called integrated shrinking, as opposed to type-based shrinking, which most property-based testing tools use. (`jqwik-user-guide#integrated-shrinking`)

Sometimes there is no single smallest example. (`jqwik-user-guide#integrated-shrinking`)

In the guide's integrated shrinking example, the result depends on the starting random seed. (`jqwik-user-guide#integrated-shrinking`)

## Mutation testing
<!-- bullets: 11.6.d -->

PIT applies a configurable set of mutation operators, or mutators, to the bytecode generated by compiling your code. (`pitest-basic-concepts#mutation-operators`)

The `CONDITIONALS_BOUNDARY_MUTATOR` modifies the bytecode of `if ( i >= 0 )` to be equivalent to `if ( i > 0 )`. (`pitest-basic-concepts#mutation-operators`)

PIT mutates the bytecode in various ways, including removing method calls, inverting logic statements and altering return values. (`pitest-basic-concepts#mutation-operators`)

PIT requires line numbers and the source file name as debug information in the bytecode. (`pitest-basic-concepts#mutation-operators`)

A mutant is a Java class that contains a mutation, or fault, which should make it behave differently from the unmutated class. (`pitest-basic-concepts#mutants`)

PIT runs your tests using the mutant instead of the unmutated class. (`pitest-basic-concepts#mutants`)

An effective set of tests should fail in the presence of the mutant. (`pitest-basic-concepts#mutants`)

Not all mutations behave differently than the unmutated class, and the mutants that do not are referred to as equivalent mutations. (`pitest-basic-concepts#equivalent-mutations`)

A mutation can be equivalent because the resulting mutant behaves in exactly the same way as the original. (`pitest-basic-concepts#equivalent-mutations`)

A mutation can also be equivalent because the resulting mutant behaves differently in a way that is outside the scope of testing. (`pitest-basic-concepts#equivalent-mutations`)

PIT does not generate mutations for lines that contain a call to common logging frameworks. (`pitest-basic-concepts#equivalent-mutations`)

Disabling the `FLOGCALL` feature enables mutation of logging statements. (`pitest-basic-concepts#equivalent-mutations`)

The snippet applies the boundary mutation to an age check and counts a mutant as surviving when the tests cannot tell it from the original.

```java snippet=m11-l06/MutationDemo.java
import java.util.List;

public class MutationDemo {
    static boolean original(int age) {
        return age >= 18;
    }

    static boolean mutant(int age) {
        return age > 18;
    }

    static boolean survives(List<Integer> testAges) {
        for (int age : testAges) {
            if (original(age) != mutant(age)) {
                return false;
            }
        }
        return true;
    }

    public static void main(String[] args) {
        System.out.println("tests with ages 10 and 30: mutant survives = " + survives(List.of(10, 30)));
        System.out.println("tests with ages 10, 18 and 30: mutant survives = " + survives(List.of(10, 18, 30)));
        for (int i : new int[] {2, 1}) {
            System.out.println("i >= 1 and i > 1 agree for i = " + i + ": " + ((i >= 1) == (i > 1)));
        }
    }
}
```

A test suite that uses only the ages `10` and `30` does not kill the `age > 18` mutant.

Adding the age `18` to the test suite kills the mutant.

`i >= 1` and `i > 1` agree for `i = 2` and differ for `i = 1`.

## Load testing
<!-- bullets: 11.6.e -->

In a closed model, the execution time of each iteration dictates the number of iterations executed in the test. (`k6-open-vs-closed#closed-model`)

In a closed model, the next iteration doesn't start until the previous one finishes. (`k6-open-vs-closed#closed-model`)

In a closed model, the arrival rate of new VU iterations is tightly coupled with the iteration duration. (`k6-open-vs-closed#closed-model`)

In the k6 closed-model example, one VU runs for one minute and each request takes roughly 6 seconds, so 10 iterations are expected in total. (`k6-open-vs-closed#closed-model`)

In a closed model, the response time of the target system can influence the throughput of the test. (`k6-open-vs-closed#drawbacks-of-using-the-closed-model`)

In a closed model, slower response times mean longer iterations and a lower arrival rate of new iterations. (`k6-open-vs-closed#drawbacks-of-using-the-closed-model`)

k6 notes that in some testing literature this problem is known as coordinated omission. (`k6-open-vs-closed#drawbacks-of-using-the-closed-model`)

When the target system is stressed, a closed model load test waits, which lengthens the iterations and tapers off the arrival rate of new VU iterations. (`k6-open-vs-closed#drawbacks-of-using-the-closed-model`)

The closed model effect is not ideal when the goal is to simulate a certain arrival rate of new VUs. (`k6-open-vs-closed#drawbacks-of-using-the-closed-model`)

Compared to the closed model, the open model decouples VU iterations from the iteration duration. (`k6-open-vs-closed#open-model`)

In an open model, the response times of the target system no longer influence the load on the target system. (`k6-open-vs-closed#open-model`)

k6 implements the open model with two arrival rate executors, `constant-arrival-rate` and `ramping-arrival-rate`. (`k6-open-vs-closed#open-model`)

In the k6 open-model example, the `constant-arrival-rate` executor starts new VU iterations at a rate of 1 every second. (`k6-open-vs-closed#open-model`)

The snippet simulates both models for 60 seconds with 6-second and 12-second responses and counts the iterations started and the most iterations in flight at once.

```java snippet=m11-l06/WorkloadModels.java
import java.util.ArrayList;
import java.util.List;

public class WorkloadModels {
    record Result(int started, int peakInFlight) {}

    static Result run(boolean open, int testSeconds, int responseSeconds) {
        List<Integer> endTimes = new ArrayList<>();
        int peak = 0;
        int vuFreeAt = 0;
        for (int second = 0; second < testSeconds; second++) {
            boolean start = open || vuFreeAt <= second;
            if (!start) {
                continue;
            }
            endTimes.add(second + responseSeconds);
            vuFreeAt = second + responseSeconds;
            int now = second;
            peak = Math.max(peak, (int) endTimes.stream().filter(end -> end > now).count());
        }
        return new Result(endTimes.size(), peak);
    }

    public static void main(String[] args) {
        for (int responseSeconds : new int[] {6, 12}) {
            Result closed = run(false, 60, responseSeconds);
            Result open = run(true, 60, responseSeconds);
            System.out.println("closed, " + responseSeconds + " s responses: " + closed.started() + " started, peak " + closed.peakInFlight() + " in flight");
            System.out.println("open, " + responseSeconds + " s responses: " + open.started() + " started, peak " + open.peakInFlight() + " in flight");
        }
    }
}
```

With 6-second responses, the closed model starts 10 iterations in 60 seconds and never has more than 1 in flight.

With 6-second responses, the open model starts 60 iterations and peaks at 6 in flight.

With 12-second responses, the closed model starts 5 iterations and never has more than 1 in flight.

With 12-second responses, the open model still starts 60 iterations and peaks at 12 in flight.

Soak testing is another variation of the average-load test that focuses on extended periods. (`k6-soak#soak-testing`)

A soak test analyzes the system's degradation of performance and resource consumption over extended periods. (`k6-soak#soak-testing`)

The soak test differs from an average-load test in test duration. (`k6-soak#soak-testing`)

In a soak test, the peak load duration extends to several hours and even days. (`k6-soak#soak-testing`)

The ramp-up and ramp-down periods of a soak test are the same as in an average-load test. (`k6-soak#soak-testing`)

A soak test might also be called an endurance, constant high load or stamina test. (`k6-soak#soak-testing`)

A soak test checks for common performance defects that show only after extended use. (`k6-soak#when-to-perform-a-soak-test`)

Those defects include response time degradation, memory or other resource leaks, data saturation and storage depletion. (`k6-soak#when-to-perform-a-soak-test`)

## Flaky tests
<!-- bullets: 11.6.f -->

:::judgement{source="Google, Site Reliability Engineering, ch. 17" ref="sre-book-testing-reliability#the-need-for-speed"}
According to Google's Site Reliability Engineering book, the pass or fail indication of a test may change for repeated and seemingly identical runs. The chapter says the likelihood of a test passing or failing can be estimated by averaging over many runs, and that engineers want to know whether their code has an unanticipated race condition that makes the test flaky.
:::

:::judgement{source="Martin Fowler, Eradicating Non-Determinism in Tests" ref="fowler-eradicating-non-determinism#WhyNon-deterministicTestsAreAProblem"}
According to Martin Fowler, non-deterministic tests have two problems: they are useless, and they are a virulent infection that can ruin the entire test suite. When such a test goes red, he writes, you have no idea whether it is due to a bug, so people end up shrugging their shoulders when such tests go red, and the test becomes useless.
:::

:::judgement{source="Martin Fowler, Eradicating Non-Determinism in Tests" ref="fowler-eradicating-non-determinism#Quarantine"}
According to the same article, the essential advice is to quarantine non-deterministic tests: keep them in a different test suite from the healthy tests so the healthy tests keep giving good feedback. Fowler adds that quarantined tests should be fixed quickly and suggests a numeric limit, such as 8 tests, or a time limit, such as a week, so tests do not stay in quarantine too long.
:::

:::judgement{source="Martin Fowler, Eradicating Non-Determinism in Tests" ref="fowler-eradicating-non-determinism#LackOfIsolation"}
According to the same article, lack of isolation is a common cause: if one test creates data in the database and leaves it there, it can corrupt the run of another test. Fowler names two ways to get isolation, rebuilding the starting state from scratch or ensuring each test cleans up after itself, and prefers the former because with clean-up one test holds the bug while another test fails.
:::

:::judgement{source="Martin Fowler, Eradicating Non-Determinism in Tests" ref="fowler-eradicating-non-determinism#AsynchronousBehavior"}
According to the same article, the common mistake with asynchronous behavior is to throw in a sleep, which either wastes time or sometimes does not wait long enough and gives a false failure. Fowler urges never to use bare sleeps to wait for asynchronous responses and to use a callback or polling instead.
:::

:::judgement{source="Martin Fowler, Eradicating Non-Determinism in Tests" ref="fowler-eradicating-non-determinism#Time"}
According to the same article, a call to the system clock is non-deterministic because each call returns a new result. Fowler's advice is to always wrap the system clock so it can be replaced with a seeded value for testing.
:::

:::judgement{source="Martin Fowler, Eradicating Non-Determinism in Tests" ref="fowler-eradicating-non-determinism#RemoteServices"}
According to the same article, remote systems often have no test system or one that is not stable enough to give deterministic responses, so Fowler reaches for a test double that mimics the remote system's behavior in a way the team controls. He proposes contract tests that run the same interaction against the remote system and the double to check that the two match.
:::

:::judgement{source="Martin Fowler, Eradicating Non-Determinism in Tests" ref="fowler-eradicating-non-determinism#ResourceLeaks"}
According to the same article, a resource leak makes random tests fail, because whichever test pushes the leak over a limit gets the failure. For a resource pool, Fowler suggests configuring a size of 1 and making the pool throw an exception when it has no resource left, so the first test to request a resource after the leak fails.
:::

:::judgement{source="Ham Vocke, The Practical Test Pyramid" ref="fowler-practical-test-pyramid#End-to-endTests"}
According to Ham Vocke, end-to-end tests are notoriously flaky and often fail for unexpected and unforeseeable reasons, and he lists browser quirks, timing issues, animations and unexpected popup dialogs among them.
:::

## Chaos engineering
<!-- bullets: 11.6.g -->

Chaos Engineering is the discipline of experimenting on a distributed system in order to build confidence in its capability to withstand turbulent conditions in production. (`paper-basiri-chaos-engineering#p2`)

Those conditions can be anything from a hardware failure to an unexpected surge in the number of client requests to a malformed value appearing in a runtime configuration parameter. (`paper-basiri-chaos-engineering#p2`)

Chaos Engineering can be thought of as the facilitation of experiments to uncover systemic weaknesses. (`principles-of-chaos#chaos-in-practice`)

The first step of a chaos experiment is to define steady state as some measurable output of a system that indicates normal behavior. (`principles-of-chaos#chaos-in-practice`)

The second step is to hypothesize that this steady state will continue in both the control group and the experimental group. (`principles-of-chaos#chaos-in-practice`)

The third step is to introduce variables that reflect real world events, such as servers that crash, hard drives that malfunction and network connections that are severed. (`principles-of-chaos#chaos-in-practice`)

The fourth step is to try to disprove the hypothesis by looking for a difference in steady state between the control group and the experimental group. (`principles-of-chaos#chaos-in-practice`)

The harder it is to disrupt the steady state, the more confidence there is in the behavior of the system. (`principles-of-chaos#chaos-in-practice`)

If a weakness is uncovered, it becomes a target for improvement before that behavior manifests in the system at large. (`principles-of-chaos#chaos-in-practice`)

The paper identifies four principles that embody the Chaos Engineering approach to designing experiments. (`paper-basiri-chaos-engineering#p4`)

One of the four principles is to run experiments in production. (`paper-basiri-chaos-engineering#p4`)

Another of the four principles is to automate experiments to run continuously. (`paper-basiri-chaos-engineering#p4`)

Netflix uses SPS, stream starts per second, as its primary indicator of the overall health of the system. (`paper-basiri-chaos-engineering#p5`)

One of the fundamental assumptions of Chaos Engineering is that complex systems exhibit behaviors that are regular enough that they can be predicted. (`paper-basiri-chaos-engineering#p5`)

Chaos Engineering experimental designs focus on steady state characterizations that are visible at the boundary of the system and directly capture an interaction between the users and the system. (`paper-basiri-chaos-engineering#p6`)

Netflix does not use finer grained metrics for the design of Chaos Engineering experiments, since they are not a direct measure of system availability. (`paper-basiri-chaos-engineering#p6`)

Netflix does observe finer grained metrics when running Chaos Engineering experiments to check if the system is functioning properly. (`paper-basiri-chaos-engineering#p6`)

A recent study reported that 92% of catastrophic system failures were the result of incorrect handling of non-fatal errors. (`paper-basiri-chaos-engineering#p6`)

When designing chaos experiments, the stimulus is chosen by sampling from the space of all possible inputs that might occur in the real world. (`paper-basiri-chaos-engineering#p6`)

Netflix injects latency into requests between services in its experiments. (`paper-basiri-chaos-engineering#p6`)

Netflix terminates virtual machine instances in its experiments. (`paper-basiri-chaos-engineering#p6`)

In the paper's example experiment, failures are introduced by selectively failing the requests against the bookmark service that are associated with users in the experimental group. (`paper-basiri-chaos-engineering#p9`)

In the paper's example experiment, no failures are introduced for the users in the control group. (`paper-basiri-chaos-engineering#p9`)

The example hypothesizes that the SPS values will be approximately equal for the control group and the experimental group. (`paper-basiri-chaos-engineering#p9`)

The example involves only a small percentage of Netflix users. (`paper-basiri-chaos-engineering#p9`)

Experimenting in production has the potential to cause unnecessary customer pain. (`principles-of-chaos#minimize-blast-radius`)

It is the responsibility and obligation of the Chaos Engineer to ensure that the fallout from experiments is minimized and contained. (`principles-of-chaos#minimize-blast-radius`)

The Principles of Chaos give the principle of keeping the fallout of experiments small the heading "Minimize Blast Radius". (`principles-of-chaos#minimize-blast-radius`)

Chaos Monkey and Jepsen, used for distributed state, are among the statistical techniques that aren't necessarily repeatable tests. (`sre-book-testing-reliability#using-statistical-tests`)

Simply rerunning such a test after a code change doesn't definitively prove that the observed fault is fixed. (`sre-book-testing-reliability#using-statistical-tests`)

Such techniques can provide a log of all the randomly selected actions taken in a run, sometimes simply by logging the random number generator seed. (`sre-book-testing-reliability#using-statistical-tests`)

## Key points

- A consumer Pact test fires a real request to a mock provider, and the resulting pact file is used to verify the real provider, which passes if each response contains at least the data in the minimal expected response.
- Pact is most valuable where you control the development of both the consumer and the provider, and both are under active development.
- A jqwik property is a `@Property` method with `@ForAll` parameters that runs 1000 tries by default and stops at the first failure, which is usually followed by an attempt to shrink the sample.
- `Math.abs(Integer.MIN_VALUE)` is `-2147483648`, so the property `Math.abs(x) >= 0` fails for it, and a concatenation with an empty string is not longer than the other string.
- PIT runs the tests against mutants made from the bytecode, and an effective set of tests should fail in the presence of a mutant.
- A test suite that never checks the boundary age `18` does not kill the `age > 18` mutant of `age >= 18`.
- A closed model couples the arrival rate to the response time, which k6 links to coordinated omission, and an open model decouples them.
- In the simulation, 12-second responses cut the closed model from 10 iterations to 5 in 60 seconds, while the open model still starts 60 and peaks at 12 in flight.
- A soak test keeps an average load for hours or days to find defects that show only after extended use, such as resource leaks.
- Chaos Engineering experiments define steady state, hypothesize it continues, introduce real world variables and try to disprove the hypothesis.
- Netflix's example experiment fails the bookmark service only for a small percentage of users in an experimental group and compares SPS with a control group.
- Experiments in production must keep their fallout minimized and contained, and rerunning a randomized fault test does not prove that a fault is fixed.

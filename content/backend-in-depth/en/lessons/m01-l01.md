# Design principles, pragmatism and data-oriented programming

## The single responsibility principle
<!-- bullets: 1.1.a -->

:::judgement{source="Robert C. Martin, The Single Responsibility Principle (blog.cleancoder.com, 2014)" ref="martin-srp-blog#blog"}
According to Robert C. Martin, the Single Responsibility Principle states that each software module should have one and only one reason to change. He asks what defines a reason to change and answers that the reasons are people: a module should answer to a single person, or a single tightly coupled group of people representing one narrowly defined business function. He gives a second wording, which is to gather together the things that change for the same reasons and to separate the things that change for different reasons. He calls this another way to define cohesion and coupling: raise the cohesion between things that change for the same reasons, and lower the coupling between things that change for different reasons.
:::

## DRY, YAGNI and KISS
<!-- bullets: 1.1.b -->

:::judgement{source="Martin Fowler, Yagni (martinfowler.com, 2015)" ref="fowler-yagni#banner"}
According to Martin Fowler, yagni, "You Aren't Gonna Need It", says that a capability presumed necessary in the future should not be built now. He names four costs of a presumptive feature: the cost of build, the cost of delayed value, the cost of carry, and the cost of repair when the feature is built wrong. He applies the same argument to abstractions that support future flexibility: any abstraction that makes the code for current requirements harder to understand is presumed guilty. He states that yagni covers capabilities built for a presumptive feature and not the effort to make software easier to modify, so refactoring is not a violation of yagni.
:::

:::judgement{source="Thomas and Hunt, The Pragmatic Programmer, 2nd edition (2019); Ousterhout, A Philosophy of Software Design, 2nd edition (2021)"}
According to the course's registered chapter lists, The Pragmatic Programmer treats this subject in chapter 1, "A Pragmatic Philosophy", and A Philosophy of Software Design in chapter 6, "General-Purpose Modules are Deeper".

## Records as immutable data carriers
<!-- bullets: 1.1.c -->

A record declaration specifies a new record class, a restricted kind of class that defines a simple aggregate of values (`jls-8-records#jls-8.10`).

A record declaration may specify a top level record class, a member record class, or a local record class (`jls-8-records#jls-8.10`).

A record class is implicitly final (`jls-8-records#jls-8.10`).

A nested record class is implicitly static (`jls-8-records#jls-8.10`).

It is a compile-time error if a record declaration has the modifier `abstract`, `sealed` or `non-sealed` (`jls-8-records#jls-8.10`).

A record declaration does not have an `extends` clause, and the direct superclass type of a record class is `Record` (`jls-8-records#jls-8.10`).

A record object is deserialized using the canonical constructor (`jls-8-records#jls-8.10`).

A record class is a shallowly immutable, transparent carrier for a fixed set of values, called the record components (`javadoc-record#class-record`).

For each record component, a record class has a component field that is `private`, `final` and non-static (`jls-8-records#jls-8.10.3`).

Record classes may explicitly declare instance methods other than accessor methods, but may not explicitly declare instance variables (`jls-8-records#jls-8.10.3`).

The implicit declarations of `equals`, `hashCode` and `toString` are derived from all of the component fields (`javadoc-record#class-record`).

The primary reasons to provide an explicit declaration for the canonical constructor or the accessor methods are to validate constructor arguments, perform defensive copies on mutable components, or normalize groups of components (`javadoc-record#class-record`).

The snippet declares two records over a `List` component. The second record validates its `id` and copies the list in a compact constructor.

```java snippet=m01-l01/ShallowRecord.java
import java.util.ArrayList;
import java.util.List;

public class ShallowRecord {
    record Order(String id, List<String> lines) {}

    record SafeOrder(String id, List<String> lines) {
        SafeOrder {
            if (id.isBlank()) {
                throw new IllegalArgumentException("id is blank");
            }
            lines = List.copyOf(lines);
        }
    }

    public static void main(String[] args) {
        List<String> lines = new ArrayList<>(List.of("tea"));
        Order order = new Order("A1", lines);
        SafeOrder safe = new SafeOrder("A1", lines);
        lines.add("milk");
        System.out.println(order);
        System.out.println(safe);
        System.out.println(order.equals(new Order(order.id(), order.lines())));
        try {
            new SafeOrder(" ", List.of());
        } catch (IllegalArgumentException e) {
            System.out.println(e.getMessage());
        }
    }
}
```

The snippet prints `Order[id=A1, lines=[tea, milk]]`, because the record holds the caller's list and the later `add` shows through.

It prints `SafeOrder[id=A1, lines=[tea]]`, because the compact constructor stored a copy made by `List.copyOf`.

It prints `true` for the copy of the first record built from its own accessors, and `id is blank` for the rejected blank `id`.

For all record classes, if a record `R` has components `c1, c2, ... cn` and an instance `r` is copied as `new R(r.c1(), r.c2(), ..., r.cn())`, then `r.equals(copy)` must hold (`javadoc-record#class-record`).

## Sealed hierarchies as domain models
<!-- bullets: 1.1.d -->

Sealed classes and interfaces restrict which other classes or interfaces may extend or implement them (`jep-409#Summary`).

A class can be declared `sealed` if all its direct subclasses are known when the class is declared, and no other direct subclasses are desired or required (`jls-8-records#jls-8.1.1.2`).

Explicit and exhaustive control over a class's direct subclasses is useful when the class hierarchy is used to model the kinds of values in a domain, rather than as a mechanism for code inheritance and reuse (`jls-8-records#jls-8.1.1.2`).

It is a compile-time error if a class has a sealed direct superclass or a sealed direct superinterface and is not declared `final`, `sealed` or `non-sealed`, either explicitly or implicitly (`jls-8-records#jls-8.1.1.2`).

A record class is implicitly final, so it can implement a sealed interface (`jls-8-records#jls-8.1.1.2`).

An interface can be declared `sealed` if all its direct subclasses and direct subinterfaces are known when the interface is declared (`jls-9-interfaces#jls-9.1.1.4`).

JEP 395 describes records as classes that act as transparent carriers for immutable data (`jep-395#Summary`).

## Pattern matching on records
<!-- bullets: 1.1.d -->

Pattern matching for `switch` allows an expression to be tested against a number of patterns, each with a specific action (`jep-441#Summary`).

Record patterns deconstruct record values, and record patterns and type patterns can be nested (`jep-440#Summary`).

A record pattern is used to test whether a value is an instance of a record class type and, if it is, to recursively perform pattern matching on the record component values (`jls-14-statements#jls-14.30.1`).

A default label is permitted, but not required, when the switch block exhausts all the permitted direct subclasses and subinterfaces of an abstract sealed class or sealed interface (`jls-14-statements#jls-14.11.1.1`).

The null reference does not match a record pattern (`jls-14-statements#jls-14.30.2`).

The length of a record pattern's component pattern list must be the same as the length of the record component list of the record class, or a compile-time error occurs (`jls-14-statements#jls-14.30.1`).

The match-all pattern is written `_` and can only appear directly in the component pattern list of a record pattern (`jls-14-statements#jls-14.30.1`).

Every value matches a match-all pattern (`jls-14-statements#jls-14.30.2`).

If invoking the accessor method of a component completes abruptly for reason `S`, pattern matching completes abruptly by throwing a `MatchException` with cause `S` (`jls-14-statements#jls-14.30.2`).

The snippet models a `Payment` as a sealed interface with three record implementations, and switches over it with no `default` label.

```java snippet=m01-l01/PaymentSwitch.java
public class PaymentSwitch {
    sealed interface Payment permits Card, Transfer, Voucher {}

    record Card(String last4, long cents) implements Payment {}

    record Transfer(String iban, long cents) implements Payment {}

    record Voucher(String code) implements Payment {}

    record Receipt(String customer, Payment payment) {}

    static String describe(Payment payment) {
        return switch (payment) {
            case Card(String last4, long cents) -> "card " + last4 + " for " + cents;
            case Transfer(String iban, long cents) -> "transfer from " + iban + " for " + cents;
            case Voucher(String code) -> "voucher " + code;
        };
    }

    static String describe(Receipt receipt) {
        return switch (receipt) {
            case Receipt(String customer, Card(var last4, var cents)) -> customer + " paid by card " + last4;
            case Receipt(String customer, Transfer transfer) -> customer + " paid by transfer from " + transfer.iban();
            case Receipt(String customer, Voucher voucher) -> customer + " paid by voucher " + voucher.code();
        };
    }

    public static void main(String[] args) {
        System.out.println(describe(new Card("4242", 1500)));
        System.out.println(describe(new Voucher("W-9")));
        System.out.println(describe(new Receipt("Ana", new Transfer("ES00", 900))));
        try {
            describe((Payment) null);
        } catch (NullPointerException e) {
            System.out.println("NullPointerException");
        }
    }
}
```

The snippet prints `card 4242 for 1500`, `voucher W-9` and `Ana paid by transfer from ES00`, one line each, from the record patterns and the nested record pattern.

It then prints `NullPointerException`, because the `switch` over a `null` `Payment` has no `case null` label.

The next snippet gives a record an accessor that always throws.

```java snippet=m01-l01/AccessorFailure.java
public class AccessorFailure {
    record Gauge(int reading) {
        @Override
        public int reading() {
            throw new IllegalStateException("sensor offline");
        }
    }

    public static void main(String[] args) {
        Object value = new Gauge(7);
        try {
            if (value instanceof Gauge(int reading)) {
                System.out.println(reading);
            }
        } catch (MatchException e) {
            System.out.println("MatchException caused by " + e.getCause());
        }
        System.out.println(value instanceof Gauge);
    }
}
```

The snippet prints `MatchException caused by java.lang.IllegalStateException: sensor offline`, and then `true` for the plain type test.

## Key points

- A record class is implicitly final and has a private final field per component (`jls-8-records#jls-8.10`; `jls-8-records#jls-8.10.3`).
- A record is a shallowly immutable carrier, and an explicit canonical constructor is the place to validate and make defensive copies (`javadoc-record#class-record`).
- A record that holds a mutable `List` shows later changes to that list, and `List.copyOf` in a compact constructor prevents it.
- A sealed class or interface has all its direct subclasses known when it is declared (`jls-8-records#jls-8.1.1.2`; `jls-9-interfaces#jls-9.1.1.4`).
- A `switch` over a sealed type that covers every permitted direct subclass needs no `default` label (`jls-14-statements#jls-14.11.1.1`).
- The null reference does not match a record pattern, and a throwing accessor surfaces as a `MatchException` (`jls-14-statements#jls-14.30.2`).
